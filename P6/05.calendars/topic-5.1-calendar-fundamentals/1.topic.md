## 1. Executive Summary & The Core Mental Model

### 1.1 The Axiom: A Schedule Without Calendars is Just Abstract Math
In elementary project management tutorials, people often treat time as a simple continuous number line:
$$\text{Finish Date} = \text{Start Date} + \text{Duration}$$

If a software development task starts on Monday morning and has an estimated duration of 5 days, a junior developer might write:
$$\text{Finish} = \text{Monday 09:00} + 5 \times 24\text{ hours} = \text{Saturday 09:00}$$

In real-world construction, civil engineering, and infrastructure mega-projects, this naive equation causes catastrophic failure:
1. **Humans do not work 24 hours a day.** A crane operator or civil piling crew works 8 or 10 hours a day, punctuated by mandatory rest intervals.
2. **Commercial and legal institutions operate on restricted business rhythms.** Banks issuing Letters of Credit, government ministries approving environmental permits, and testing laboratories approving soil density reports operate strictly on 5-day office weeks.
3. **Physical and chemical processes ignore human work hours.** Once concrete is poured into a 220kV transformer foundation, the hydration reaction of Portland cement occurs 24 hours a day, 7 days a week, regardless of national holidays, Sundays, or worker strikes.
4. **Site environmental conditions impose severe operational boundaries.** In the Thar Desert of Rajasthan, midday ambient temperatures reach 49°C in May and June. Outdoor steel erection is prohibited between 12:00 PM and 3:00 PM to prevent fatal heat stroke and metal thermal distortion.


Therefore, in **Oracle Primavera P6**, Safran Project, and production scheduling engines:
> **A Calendar is a non-linear temporal filter (a boolean bitmask) mapped over universal physical time.**  
> It defines the precise intervals during which an activity or resource can consume planned duration.

When an activity has a duration of "40 Hours", the scheduling engine does not add 40 chronological hours to the start timestamp. Instead, it **walks forward through the calendar's working intervals**, consuming duration only when the calendar switch is `OPEN` (working), and pausing consumption whenever the calendar switch is `CLOSED` (non-working, lunch break, night, weekend, or holiday).

## 2. Mathematical Foundation: Time Discretization & Filtering

### 2.1 The Characteristic Indicator Function
Let universal physical time be represented as continuous real time $t \in \mathbb{R}$, measured in Unix seconds or minutes from an epoch $t_0$.

A **Calendar** $C$ is mathematically defined as a piecewise-constant characteristic indicator function:
$$W_C(t) = \begin{cases} 1 & \text{if instant } t \text{ is working time} \\ 0 & \text{if instant } t \text{ is non-working time} \end{cases}$$

If efficiency factors or partial productivity are modeled (e.g., night shift efficiency reduction), $W_C(t)$ generalizes to a continuous productivity factor:
$$W_C(t) \in [0.0, 1.0]$$

For enterprise CPM engines, binary quantization ($W_C(t) \in \{0, 1\}$) at minute resolution is the industry standard.

### 2.2 The Work Integral & Date Forward Calculation
Given an activity starting at instant $t_{\text{start}}$ with a required work quantity (duration) of $D_{\text{work}}$ (measured in minutes or hours), the finish instant $t_{\text{finish}}$ is the unique root of the integral equation:
$$\int_{t_{\text{start}}}^{t_{\text{finish}}} W_C(t) \, dt = D_{\text{work}}$$

```text
               t_finish
                  ⌠
                  │  W_C(t) dt  =  D_work
                  ⌡
               t_start
```

Because $W_C(t)$ alternates between $1$ and $0$, the chronological elapsed time $(t_{\text{finish}} - t_{\text{start}})$ is always greater than or equal to the work duration $D_{\text{work}}$:
$$(t_{\text{finish}} - t_{\text{start}}) \ge D_{\text{work}}$$

Equality holds **if and only if** the entire elapsed interval consists purely of uninterrupted working time (such as in a 24/7 curing calendar).

### 2.3 Discrete Minute Quantization
In digital scheduling engines written in Golang, continuous integration is discretized. We define time as discrete integer minutes:
$$m \in \mathbb{Z}_{\ge 0}, \quad m = \left\lfloor \frac{\text{UnixTimestamp}}{60} \right\rfloor$$

The forward date walking equation becomes a discrete summation:
$$\sum_{m = m_{\text{start}}}^{m_{\text{finish}} - 1} W_C[m] = D_{\text{work\_minutes}}$$

Where $m_{\text{finish}}$ is the smallest integer such that the accumulated sum reaches $D_{\text{work\_minutes}}$.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                          DISCRETE MINUTE ACCUMULATION EXAMPLE                                    │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  Suppose an activity requires D = 480 working minutes (8 hours).                                 │
│  Start Time: Friday 15:00.                                                                       │
│  Calendar: 5-Day Week (08:00 - 12:00, 13:00 - 17:00). Saturday and Sunday are Non-Working.       │
│                                                                                                  │
│  Minute by minute accumulation:                                                                  │
│  1. Friday 15:00 to 17:00:           120 working minutes accumulated.  (Remaining: 360 min)      │
│  2. Friday 17:00 to Monday 08:00:      0 working minutes accumulated.  (Weekend gap, W[m] = 0)   │
│  3. Monday 08:00 to 12:00:           240 working minutes accumulated.  (Remaining: 120 min)      │
│  4. Monday 12:00 to 13:00:             0 working minutes accumulated.  (Lunch break, W[m] = 0)   │
│  5. Monday 13:00 to 15:00:           120 working minutes accumulated.  (Remaining:   0 min)      │
│                                                                                                  │
│  Result: Finish Time = Monday 15:00.                                                             │
│  Elapsed Calendar Time: 72 hours.                                                                │
│  Consumed Work Time:    8 hours (480 minutes).                                                   │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.1 Pattern 1: 5-Day 40-Hour Week (Engineering, Legal, Procurement)
* **Weekly Schedule:** Monday through Friday. Saturday and Sunday are marked non-working.
* **Daily Shift Breakdown:**
  * Morning Work Block: `08:00 - 12:00` (4.0 hours)
  * Lunch Break (Unpaid): `12:00 - 13:00` (1.0 hour non-working)
  * Afternoon Work Block: `13:00 - 17:00` (4.0 hours)
  * Total Daily Work: `8.0 hours`
* **Real-World Application in Surya Solar:**
  * Preparing detailed electrical engineering schematics in ETAP.
  * Submitting grid synchronization reports to Rajasthan Rajya Vidyut Prasaran Nigam Limited (RRVPNL).
  * Contract negotiation for PV module supply contracts with Tier-1 manufacturers.

### 3.2 Pattern 2: 6-Day 60-Hour Week (Site Construction & Heavy Civil)
* **Weekly Schedule:** Monday through Saturday. Sunday is the solitary rest day for machine maintenance and labor recovery.
* **Daily Shift Breakdown:**
  * Morning Work Block: `07:00 - 12:00` (5.0 hours)
  * Lunch / Heat Rest Break: `12:00 - 13:00` (1.0 hour non-working)
  * Afternoon Work Block: `13:00 - 18:00` (5.0 hours)
  * Total Daily Work: `10.0 hours`
* **Real-World Application in Surya Solar:**
  * Ramming 6,800 steel piles into the desert ground using hydraulic pile-driving rigs.
  * Excavating 45 kilometers of 33kV medium-voltage cable trenches.
  * Mechanical assembly of single-axis tracker torque tubes and solar module clamping.

### 3.3 Pattern 3: 7-Day 24-Hour Continuous Week (168 Hours / Week)
* **Weekly Schedule:** All 7 days active, Monday through Sunday.
* **Daily Shift Breakdown:**
  * Shift 1 (Morning): `06:00 - 14:00` (8.0 hours)
  * Shift 2 (Evening): `14:00 - 22:00` (8.0 hours)
  * Shift 3 (Night):   `22:00 - 06:00` (8.0 hours)
  * Total Daily Work: `24.0 hours` (zero idle intervals)
* **Real-World Application in Surya Solar:**
  * **Concrete Hydration (Curing):** Inverter foundation concrete pads require 7 to 28 days of uninterrupted wet curing. Chemical crystallization of calcium silicate hydrate ($C\text{-}S\text{-}H$) does not pause for weekends.
  * **Transformer Oil Circulation & Soak Test:** Main 60MVA 33/220kV power transformers must undergo 24 hours of continuous energization soak testing prior to grid load connection.
  * **Site Perimeter Security & Diesel Generator Power:** Continuous non-stop operation.

## 4. Calendar Precision: Days vs. Hours vs. Minutes

One of the most persistent sources of confusion for software engineers building scheduling engines is **Temporal Precision**.

### 4.1 The Dangerous Illusion of the "Day" Unit
In common business speech, people say:
> *"Activity A takes 5 days."*

In a database, a developer might be tempted to store:
```sql
duration_days INT  -- e.g., 5
```

This is fundamentally flawed. When you tell a scheduling engine an activity takes "5 days", the engine must know:
* **How many hours are in a day for this specific calendar?** Is it 8 hours? 10 hours? 24 hours?
* **At what hour of the day does work start?** If it starts at 14:00 on Friday, when do the 5 days end?

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                         THE UNIT CONVERSION AMBIGUITY TRAP                                       │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  Suppose Activity X has a duration of "5 Days".                                                  │
│                                                                                                  │
│  Scenario A: Assigned to a 5-Day (8h/day) Office Calendar:                                       │
│  Total Work Required = 5 × 8 = 40 Hours.                                                         │
│                                                                                                  │
│  Scenario B: Assigned to a 6-Day (10h/day) Civil Site Calendar:                                  │
│  Total Work Required = 5 × 10 = 50 Hours.                                                        │
│                                                                                                  │
│  Scenario C: Assigned to a 7-Day (24h/day) Concrete Curing Calendar:                             │
│  Total Work Required = 5 × 24 = 120 Hours.                                                       │
│                                                                                                  │
│  If you store duration as "5 days" without an internal standard unit, switching the calendar     │
│  silently changes the physical work content from 40 hours to 120 hours!                          │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 Primavera P6 Internal Storage Architecture
In Oracle Primavera P6:
1. **Durations are ALWAYS stored internally in seconds or hours** (in the underlying P6 database schema table `TASK`, duration is stored as floating-point hours in columns like `target_drtn_hr_cnt`).
2. **Timestamps are ALWAYS stored with minute-level precision** (`YYYY-MM-DD HH:MM:00`).
3. **Display formatting is decoupled from storage:** A user can configure P6 to display dates as `12-OCT-26` or `12-OCT-26 08:00`. Even if the time component is hidden in the GUI, **the engine calculates down to the exact minute**.

### 4.3 The "Phantom Fractional Day" Problem
When planners hide the time display in P6, subtle issues arise that confuse project teams:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                            THE PHANTOM FRACTIONAL DAY TRAP                                       │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  Predecessor: Cable Pulling (Duration: 12 hours on a 8h/day calendar).                           │
│  Starts: Monday 08:00.                                                                           │

│                                                                                                  │
│  Successor: Megger Testing (Duration: 4 hours, FS relationship).                                 │
```

If your scheduling engine rounds dates to whole days at each step, you accumulate massive compound rounding errors, corrupting the Critical Path.

## 5. Shift Modeling: Morning Shift, Evening Shift, Lunch Breaks

In enterprise scheduling, a single working day is not an indivisible atom; it is composed of an ordered list of **Work Shifts** and **Break Intervals**.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                ANATOMY OF A WORKING DAY TIMELINE                                 │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  00:00        07:00             12:00   13:00             18:00                 24:00            │
│  ┌──────────────┬─────────────────┬───────┬─────────────────┬─────────────────────┐              │
│  │ Non-Working  │ Shift 1: Block A│ Break │ Shift 1: Block B│     Non-Working     │              │
│  │ (Night Idle) │   (Working)     │(Lunch)│   (Working)     │    (Evening Idle)   │              │
│  │   7.0 hrs    │     5.0 hrs     │1.0 hr │     5.0 hrs     │       6.0 hrs       │              │
│  └──────────────┴─────────────────┴───────┴─────────────────┴─────────────────────┘              │
│                 ▲                         ▲                 ▲                                    │
│                 Shift Start               Break             Shift End                            │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 5.1 Shift Properties
Each shift is formally characterized by:
* `StartMinute`: Minute of the day from `00:00` (e.g., `07:00` = $7 \times 60 = 420$).
* `EndMinute`: Minute of the day from `00:00` (e.g., `12:00` = $12 \times 60 = 720$).
* `WorkMinutes`: Calculated duration: $EndMinute - StartMinute$ (e.g., $720 - 420 = 300\text{ min} = 5.0\text{ hrs}$).
* `EfficiencyFactor`: Multiplier between `0.0` and `1.0` (default `1.0`).

### 5.2 Multi-Shift Operations
On mega-projects with tight contractual commercial operation dates (COD), critical path tasks use multiple rotating shifts:
* **Two-Shift Construction (16 Hours/Day):**
  * Shift 1 (Morning): `06:00 - 14:30` (8 working hours, 30 min meal break from 10:00-10:30).
  * Shift 2 (Afternoon/Night): `14:30 - 23:00` (8 working hours, 30 min meal break from 18:30-19:00).
  * Idle Maintenance Window: `23:00 - 06:00` (7 hours idle for equipment refueling and safety inspection).
* **Three-Shift Continuous (24 Hours/Day):**
  * Shift 1: `06:00 - 14:00` (8.0 hours).
  * Shift 2: `14:00 - 22:00` (8.0 hours).
  * Shift 3: `22:00 - 06:00` (8.0 hours).
  * Net work = 24.0 hours per day.

## 6. High-Performance Data Structures in Golang

When implementing a CPM scheduling engine in Golang that processes schedules with 50,000 activities and recalculates in under 200 milliseconds, how you model calendars in memory is critical.

### 6.1 Architecture Trade-Offs

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                            CALENDAR MEMORY MODEL COMPARISON                                      │
├──────────────────────┬───────────────────────────────┬───────────────────────────────────────────┤
│ Model                │ Advantages                    │ Disadvantages                             │
├──────────────────────┼───────────────────────────────┼───────────────────────────────────────────┤
│ 1. Time Interval     │ • Extremely compact memory.   │ • Binary search / slice iteration needed  │
│    List (`[]Interval`)│ • Natural for continuous math.│   for point-in-time checks.               │
│                      │ • Arbitrary date span.        │ • Boundary splitting requires slicing.    │
├──────────────────────┼───────────────────────────────┼───────────────────────────────────────────┤
│ 2. Daily Minute      │ • O(1) point-in-time lookup.  │ • 1,440 bits (180 bytes) per day template.│
│    Bitmask           │ • Ultra-fast bitwise ops.     │ • Requires looping over bits or bit-scans │
│    (`[23]uint64`)    │ • Zero heap allocations.      │   to calculate duration.                  │
├──────────────────────┼───────────────────────────────┼───────────────────────────────────────────┤
│ 3. Hybrid Precomputed│ • Instant duration arithmetic.│ • Slightly more memory.                   │
│    Cumulative Array  │ • O(1) interval work math.    │ • Re-indexing required when exceptions    │
│                      │ • Optimal for CPM engine.     │   are edited by user.                     │
└──────────────────────┴───────────────────────────────┴───────────────────────────────────────────┘
```

### 6.2 The Hybrid Production Model
In our Go scheduling engine, we implement the **Hybrid Model**:
1. **At the Day Level:** A precomputed array of working intervals (`[]WorkInterval`) representing active shifts for the day.
2. **At the Minute Level:** A compact bitmask of $1,440$ minutes per day stored across twenty-three 64-bit unsigned integers ($23 \times 64 = 1,472 \text{ bits} \ge 1,440$).
3. **Cumulative Minute Cache:** A cumulative working-minutes lookup array that allows computing the exact working minutes between any two minutes in the day in $O(1)$ time without a loop!

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                    MINUTE BITMASK LAYOUT (1,440 MINUTES = 23 × uint64)                           │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  Minute 0 (00:00) ──────────────► uint64[0], bit 0                                               │
│  Minute 63 (01:03) ─────────────► uint64[0], bit 63                                              │
│  Minute 64 (01:04) ─────────────► uint64[1], bit 0                                               │
│  ...                                                                                             │
│  Minute 1439 (23:59) ───────────► uint64[22], bit 31                                             │
│                                                                                                  │
│  Checking if minute m is working:                                                                │
│    wordIdx = m / 64                                                                              │
│    bitIdx  = m % 64                                                                              │
│    isWork  = (words[wordIdx] & (1 << bitIdx)) != 0                                               │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

## 7. Enterprise Relational Database Schema (PostgreSQL)

Here is the production-grade PostgreSQL DDL schema for storing calendar definitions, weekly patterns, shifts, and day templates.

```sql
-- 1. Calendars Table: Core header entity
CREATE TYPE calendar_type_enum AS ENUM ('GLOBAL', 'PROJECT', 'RESOURCE');

CREATE TABLE calendars (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE, -- NULL for GLOBAL calendars
    name VARCHAR(255) NOT NULL,
    calendar_type calendar_type_enum NOT NULL DEFAULT 'PROJECT',
    base_calendar_id UUID REFERENCES calendars(id) ON DELETE SET NULL,
    
    -- Nominal P6 hours conversion factors (used for reporting and unit display conversions)
    hours_per_day NUMERIC(5, 2) NOT NULL DEFAULT 8.00,
    hours_per_week NUMERIC(6, 2) NOT NULL DEFAULT 40.00,
    hours_per_month NUMERIC(7, 2) NOT NULL DEFAULT 173.33,
    hours_per_year NUMERIC(8, 2) NOT NULL DEFAULT 2080.00,
    
    is_default BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    CONSTRAINT uq_project_calendar_name UNIQUE (project_id, name)
);

CREATE INDEX idx_calendars_project_id ON calendars(project_id);
CREATE INDEX idx_calendars_type ON calendars(calendar_type);

-- 2. Calendar Weekly Patterns Table: 7 days of the week (0 = Sunday, 1 = Monday, ..., 6 = Saturday)
CREATE TABLE calendar_weekly_patterns (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    calendar_id UUID NOT NULL REFERENCES calendars(id) ON DELETE CASCADE,
    day_of_week SMALLINT NOT NULL CHECK (day_of_week BETWEEN 0 AND 6),
    is_working_day BOOLEAN NOT NULL DEFAULT TRUE,
    total_working_hours NUMERIC(5, 2) NOT NULL DEFAULT 8.00,
    
    CONSTRAINT uq_calendar_day_of_week UNIQUE (calendar_id, day_of_week)
);

CREATE INDEX idx_weekly_patterns_calendar ON calendar_weekly_patterns(calendar_id);

-- 3. Calendar Day Shifts Table: Specific shift blocks within each weekly pattern day
CREATE TABLE calendar_day_shifts (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    pattern_id UUID NOT NULL REFERENCES calendar_weekly_patterns(id) ON DELETE CASCADE,
    shift_index SMALLINT NOT NULL DEFAULT 1,
    start_minute_of_day SMALLINT NOT NULL CHECK (start_minute_of_day BETWEEN 0 AND 1439),
    end_minute_of_day SMALLINT NOT NULL CHECK (end_minute_of_day BETWEEN 1 AND 1440),
    efficiency_factor NUMERIC(3, 2) NOT NULL DEFAULT 1.00 CHECK (efficiency_factor BETWEEN 0.01 AND 1.00),
    description VARCHAR(100),
    
    CONSTRAINT uq_pattern_shift_index UNIQUE (pattern_id, shift_index),
    CONSTRAINT chk_shift_time_order CHECK (end_minute_of_day > start_minute_of_day)
);

CREATE INDEX idx_day_shifts_pattern ON calendar_day_shifts(pattern_id);
```

### 7.1 Schema Design Principles
1. **Normalized vs. JSONB:** While some developers store shifts as JSON arrays (`[{"start": 480, "end": 720}]`), strict relational normalization ensures database-level constraints (`CHECK (end_minute > start_minute)`) and foreign key cascading. When performance requires JSON serialization, our Go backend hydrates relational rows into an immutable in-memory calendar struct.
2. **Standard Minute Representation:** Minutes are stored as integers from `0` to `1440` (where `0 = 00:00`, `480 = 08:00`, `720 = 12:00`, `1440 = 24:00`). This completely eliminates timezone parsing and leap second bugs at the shift definition level!
3. **P6 Nominal Conversion Constants:** The `hours_per_day`, `hours_per_week`, etc., columns are **not** used to calculate dates. They are strictly display conversion factors. When a user in the UI types `Duration = 3d`, the frontend multiplies $3 \times \text{hours\_per\_day}$ to obtain working hours.

### Trap 1: Storing Shifts as Timezone-Aware Timestamps
If you store a site shift as `08:00:00+05:30` in PostgreSQL, daylight saving time (DST) shifts or server timezone migrations will mutate your site hours!
* **The Rule:** Shift definitions represent **Wall-Clock Time**. An 8:00 AM start time in Rajasthan is 8:00 AM on the wall clock at the site, regardless of the database server's UTC configuration. Store shifts as minute offsets from midnight (`[0..1440]`).

### Trap 2: The "5 Days = 120 Hours" Duration Fallacy
In standard programming languages, adding 5 days to a date is:
```go
// FATAL FLAW: Skips weekends, shifts, and breaks!
finish := start.AddDate(0, 0, 5) 
```
In a 5-day (8h/day) project, "5 days" means **40 working hours**. If work starts on Friday at 08:00, adding 40 working hours lands on the following Thursday at 17:00 (spanning 153 elapsed calendar hours).

## 9. Production-Grade Golang Implementation

Below is a complete, standalone, production-grade Golang implementation of the Calendar Fundamentals engine. It implements minute-level bitmasks, interval resolution, shift models, and pattern validation for the Surya 100MW Solar IPP Project.

```go
package calendar

import (
	"errors"
	"fmt"
	"time"
)

// MinutesPerDay is the total number of minutes in a standard solar day.
const MinutesPerDay = 1440

// DayBitmask represents the working status of all 1,440 minutes of a day.
// 1,440 bits fit within 23 uint64 words (23 * 64 = 1,472 bits).
type DayBitmask [23]uint64

// SetWorking marks the range [startMin, endMin) as working time (1).
func (bm *DayBitmask) SetWorking(startMin, endMin int) error {
	if startMin < 0 || endMin > MinutesPerDay || startMin >= endMin {
		return fmt.Errorf("invalid interval: [%d, %d)", startMin, endMin)
	}
	for m := startMin; m < endMin; m++ {
		wordIdx := m / 64
		bitIdx := uint(m % 64)
		bm[wordIdx] |= (1 << bitIdx)
	}
	return nil
}

// IsWorking checks if a specific minute of the day is working time.
func (bm *DayBitmask) IsWorking(minOfDay int) bool {
	if minOfDay < 0 || minOfDay >= MinutesPerDay {
		return false
	}
	wordIdx := minOfDay / 64
	bitIdx := uint(minOfDay % 64)
	return (bm[wordIdx] & (1 << bitIdx)) != 0
}

// TotalWorkingMinutes calculates the total working minutes in the day.
func (bm *DayBitmask) TotalWorkingMinutes() int {
	total := 0
	for m := 0; m < MinutesPerDay; m++ {
		if bm.IsWorking(m) {
			total++
		}
	}
	return total
}

// Shift represents a contiguous block of working time within a day.
type Shift struct {
	ShiftIndex       int
	StartMinuteOfDay int    // 0 to 1439 (e.g. 480 for 08:00)
	EndMinuteOfDay   int    // 1 to 1440 (e.g. 1020 for 17:00)
	Description      string
}

// DurationMinutes returns the duration of the shift in minutes.
func (s Shift) DurationMinutes() int {
	return s.EndMinuteOfDay - s.StartMinuteOfDay
}

// DayPattern defines the working schedule for a specific day of the week.
type DayPattern struct {
	DayOfWeek        time.Weekday // 0 = Sunday, 1 = Monday, ..., 6 = Saturday
	IsWorkingDay     bool
	Shifts           []Shift
	Bitmask          DayBitmask
	CumulativeMins   [MinutesPerDay + 1]int // Precomputed cumulative work minutes
}

// Compile compiles the shifts into the DayBitmask and cumulative minutes array.
func (dp *DayPattern) Compile() error {
	dp.Bitmask = DayBitmask{}
	if !dp.IsWorkingDay || len(dp.Shifts) == 0 {
		dp.IsWorkingDay = false
		for i := 0; i <= MinutesPerDay; i++ {
			dp.CumulativeMins[i] = 0
		}
		return nil
	}

	for _, s := range dp.Shifts {
		if s.StartMinuteOfDay < 0 || s.EndMinuteOfDay > MinutesPerDay || s.StartMinuteOfDay >= s.EndMinuteOfDay {
			return fmt.Errorf("shift %d has invalid boundaries: [%d, %d)", s.ShiftIndex, s.StartMinuteOfDay, s.EndMinuteOfDay)
		}
		if err := dp.Bitmask.SetWorking(s.StartMinuteOfDay, s.EndMinuteOfDay); err != nil {
			return err
		}
	}

	accum := 0
	for m := 0; m < MinutesPerDay; m++ {
		dp.CumulativeMins[m] = accum
		if dp.Bitmask.IsWorking(m) {
			accum++
		}
	}
	dp.CumulativeMins[MinutesPerDay] = accum
	return nil
}

// WorkingMinutesBetween returns working minutes between [startMin, endMin) in O(1) time.
func (dp *DayPattern) WorkingMinutesBetween(startMin, endMin int) int {
	if !dp.IsWorkingDay {
		return 0
	}
	if startMin < 0 {
		startMin = 0
	}
	if endMin > MinutesPerDay {
		endMin = MinutesPerDay
	}
	if startMin >= endMin {
		return 0
	}
	return dp.CumulativeMins[endMin] - dp.CumulativeMins[startMin]
}

// Calendar represents a full project calendar with a 7-day repeating weekly pattern.
type Calendar struct {
	ID            string
	Name          string
	HoursPerDay   float64
	HoursPerWeek  float64
	WeeklyPattern [7]DayPattern // Indexed by time.Weekday (0 = Sunday to 6 = Saturday)
}

// NewSuryaCorporateCalendar builds the 5-day 40h Engineering calendar.
// Monday-Friday: 08:00-12:00, 13:00-17:00 (8h work, 1h lunch). Sat-Sun: Non-working.
func NewSuryaCorporateCalendar() (*Calendar, error) {
	cal := &Calendar{
		ID:           "cal-surya-corp-5d",
		Name:         "Surya Corporate Engineering 5D-40H",
		HoursPerDay:  8.0,
		HoursPerWeek: 40.0,
	}

	for d := time.Sunday; d <= time.Saturday; d++ {
		pattern := DayPattern{DayOfWeek: d}
		if d == time.Sunday || d == time.Saturday {
			pattern.IsWorkingDay = false
		} else {
			pattern.IsWorkingDay = true
			pattern.Shifts = []Shift{
				{ShiftIndex: 1, StartMinuteOfDay: 480, EndMinuteOfDay: 720, Description: "Morning Work (08:00 - 12:00)"},
				{ShiftIndex: 2, StartMinuteOfDay: 780, EndMinuteOfDay: 1020, Description: "Afternoon Work (13:00 - 17:00)"},
			}
		}
		if err := pattern.Compile(); err != nil {
			return nil, err
		}
		cal.WeeklyPattern[d] = pattern
	}
	return cal, nil
}

// NewSuryaCivilSiteCalendar builds the 6-day 60h Desert Construction calendar.

			pattern.Shifts = []Shift{
				{ShiftIndex: 1, StartMinuteOfDay: 420, EndMinuteOfDay: 720, Description: "Morning Piling Shift (07:00 - 12:00)"},
				{ShiftIndex: 2, StartMinuteOfDay: 780, EndMinuteOfDay: 1080, Description: "Afternoon Piling Shift (13:00 - 18:00)"},
			}
		}
		if err := pattern.Compile(); err != nil {
			return nil, err
		}
		cal.WeeklyPattern[d] = pattern
	}

// NewSuryaContinuousCuringCalendar builds the 7-day 168h Concrete Curing calendar.
func NewSuryaContinuousCuringCalendar() (*Calendar, error) {
	cal := &Calendar{
		ID:           "cal-surya-curing-7d",
```
