### Solution 2: The Round-Trip Reversibility Invariant & Snapping Paradox

#### 1. Condition for Perfect Equality:
$$\text{BackwardWalk}(\text{ForwardWalk}(T, D), D) = T$$
This equality holds strictly **if and only if** the starting timestamp $T$ falls on a valid working minute within an active calendar shift:
$$W_C(T) = 1$$

#### 2. Why the Invariant Fails for Non-Working Instants:
When $T$ falls in non-working time ($W_C(T) = 0$, such as Sunday or midnight), the forward walking algorithm first executes a **Snap-Forward** operation to advance $T$ to the earliest available working instant $T_{\text{snapped}} > T$.
The forward calculation then adds duration $D$ starting from $T_{\text{snapped}}$:
$$T_{\text{finish}} = \text{ForwardWalk}(T_{\text{snapped}}, D)$$
When the backward walk is performed from $T_{\text{finish}}$ by duration $D$, it traces backward through active working intervals and stops precisely at $T_{\text{snapped}}$, because that is where the work physically began. It cannot "guess" which non-working minute preceded the work.

#### 3. Concrete Numerical Example:
* **Calendar:** Standard 5-Day Week (Monday–Friday, 08:00–17:00).
* **Work Duration:** $D = 8\text{ working hours}$.
* **Starting Timestamp ($T$):** Sunday, Oct 11, 2026 at 14:00 (Non-working weekend).
* **Forward Walk:**
  1. $T$ snaps forward to **Monday, Oct 12 at 08:00**.
  2. 8 hours of work consumed on Monday lands on **Monday, Oct 12 at 17:00** ($T_{\text{finish}}$).
* **Backward Walk:**
  1. Start at $T_{\text{finish}} = \text{Monday, Oct 12 at 17:00}$.
  2. Deduct 8 working hours backward.
  3. Reaches **Monday, Oct 12 at 08:00** ($T_{\text{start}}'$).
* **Comparison:**
  $$T_{\text{start}}' = \text{Monday 08:00} \ne \text{Sunday 14:00} = T$$
  The round-trip invariant returned the **physically effective start date**, losing the arbitrary non-working input instant.

### Solution 3: Cross-Midnight Shift Decomposition

#### 1. Why `[1260, 300]` Fails in Standard Schemas:
In relational databases, shifts are bounded by `CHECK (end_minute > start_minute)`. If a shift starts at 21:00 (1,260 min) and ends at 05:00 (300 min):
- $300 < 1260$, violating the ordering constraint.
- Duration calculations like `end_minute - start_minute` produce a negative number ($-960\text{ minutes}$).
- SQL queries filtering by `WHERE ? BETWEEN start_minute AND end_minute` fail completely.

#### 2. Formal Split Across Days:
A cross-midnight shift spanning from Day $N$ 21:00 to Day $N+1$ 05:00 is decomposed into two contiguous intra-day segments:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                            CROSS-MIDNIGHT SHIFT SEGMENTS                                         │
├─────────┬─────────────┬──────────────┬────────────┬──────────┬───────────────────────────────────┤
│ Day     │ Shift Block │ Start Minute │ End Minute │ Duration │ Operational Meaning               │
├─────────┼─────────────┼──────────────┼────────────┼──────────┼───────────────────────────────────┤
│ Day N   │ Segment 1   │ 1260 (21:00) │ 1440 (24:00│ 180 min  │ Late night concrete pour          │
│ Day N+1 │ Segment 2   │ 0000 (00:00) │ 0300 (05:00│ 300 min  │ Early dawn concrete finishing     │
└─────────┴─────────────┴──────────────┴────────────┴──────────┴───────────────────────────────────┘
```

#### 3. Progression for 12 Hours of Concrete Work Starting Monday 22:00:
* Start: Monday 22:00. Remaining Work: $12.0\text{ hours}$ (720 min).
* **Interval 1 (Monday Segment 1, 22:00 to 24:00):**
  - Consumes: $24:00 - 22:00 = 2.0\text{ hours}$ (120 min).
  - Remaining: $12.0 - 2.0 = 10.0\text{ hours}$ (600 min).
* **Interval 2 (Tuesday Segment 2, 00:00 to 05:00):**
  - Consumes: $05:00 - 00:00 = 5.0\text{ hours}$ (300 min).
  - Remaining: $10.0 - 5.0 = 5.0\text{ hours}$ (300 min).
* **Tuesday Daytime (05:00 to 21:00):**
  - High-heat non-working rest (0 hours consumed).
* **Interval 3 (Tuesday Segment 1, 21:00 to 24:00):**
  - Consumes: $24:00 - 21:00 = 3.0\text{ hours}$ (180 min).
  - Remaining: $5.0 - 3.0 = 2.0\text{ hours}$ (120 min).
* **Interval 4 (Wednesday Segment 2, 00:00 to 05:00):**
  - Available: 5.0 hours.
  - Consumes remaining 2.0 hours ($120\text{ min}$).
  - Finish timestamp: $00:00 + 2\text{ hours} = \text{02:00 AM}$.
* **Exact Finish Timestamp:** **Wednesday at 02:00 AM**.

### Solution 4: Zero-Duration Milestones on Non-Working Days

#### 1. Finish Milestone with Predecessor Ending Friday 17:00:
* A Finish Milestone represents a zero-duration state boundary.
* If predecessor finishes at Friday 17:00, the milestone is scheduled at:
  $$\text{Milestone Start} = \text{Friday 17:00}, \quad \text{Milestone Finish} = \text{Friday 17:00}$$
* It does not shift to Monday because Friday 17:00 is a valid working boundary moment.

#### 2. Project Manager Assigning Start Milestone to Sunday 12:00:
* **The Rule in Production Scheduling Engines (P6):** Milestones cannot occur during non-working periods because physical work and contractual handover require open site status.
* **Engine Behavior:**
  - The engine executes a **Snap-Forward** to the beginning of the next available working shift: **Monday at 08:00**.
  - If the user explicitly applies a hard constraint (*Mandatory Start On Sunday 12:00*), the engine accepts the date but flags it with negative float during the backward pass if logic conflicts arise.

### Solution 10: High-Performance Date Resolution Caching in Golang

#### 1. In-Memory Cache Design:
In Golang, caching resolved days by absolute date eliminates all slice scanning during CPM runs:

```go
type ResolvedDayCache struct {
	mu    sync.RWMutex
	cache map[int64]*ResolvedDay // Key: Unix day number (t.Unix() / 86400)
}

type ResolvedDay struct {
	IsWorking bool
	Shifts    []Shift
}

func (c *ResolvedDayCache) Get(t time.Time, resolver func(time.Time) (bool, []Shift)) (bool, []Shift) {
	dayKey := t.Unix() / 86400

	c.mu.RLock()
	if entry, ok := c.cache[dayKey]; ok {
		c.mu.RUnlock()
		return entry.IsWorking, entry.Shifts
	}
	c.mu.RUnlock()

	// Compute and populate cache
	c.mu.Lock()
	defer c.mu.Unlock()

	// Double-check after acquiring write lock
	if entry, ok := c.cache[dayKey]; ok {
		return entry.IsWorking, entry.Shifts
	}

	isWork, shifts := resolver(t)
	c.cache[dayKey] = &ResolvedDay{IsWorking: isWork, Shifts: shifts}
	return isWork, shifts
}
```

#### 2. Cache Invalidation Strategy:
* **Epoch-Based Generational Invalidation:** Each calendar struct maintains an `atomic.Uint64` version number (`version`). Whenever an exception or weekly pattern is updated via the API, the version is incremented.
* The cache either clears its map or maintains version-keyed entries. Because calendar updates happen infrequently (seconds or minutes) while CPM recalculations happen in bursts of 50,000 iterations, the cache hit rate exceeds 99.8%.

### Solution 11: PostgreSQL Exclusion Constraints for Overlapping Exceptions

To guarantee at the database storage engine level that no user can insert conflicting or overlapping exception date ranges for the same calendar:

```sql
-- 1. Enable the btree_gist extension (required for combining UUID with daterange in GiST)
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- 2. Alter calendar_exceptions table with an EXCLUDE constraint
ALTER TABLE calendar_exceptions
ADD CONSTRAINT uq_calendar_no_overlapping_exceptions
EXCLUDE USING gist (
    calendar_id WITH =,
    daterange(start_date, end_date, '[]') WITH &&
);
```

#### Explanation of the Constraint:
* `calendar_id WITH =`: Ensures the constraint only applies to exceptions belonging to the **same calendar**.
* `daterange(start_date, end_date, '[]') WITH &&`: Constructs an inclusive date range `[start_date, end_date]`. The `&&` operator is the PostgreSQL range overlap operator.
* If a transaction attempts to insert a record whose date range intersects with any existing record for that `calendar_id`, PostgreSQL aborts the transaction immediately with a constraint violation error, preventing silent schedule corruption.
