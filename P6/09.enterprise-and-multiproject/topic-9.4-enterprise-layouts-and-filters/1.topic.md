## 1. Executive Summary & Plain-English Analogy

### 1.1 The Camera Lenses on the Same 3D Scene Analogy
Imagine an architect creates a detailed 3D digital model of an international airport containing every structural beam, electrical cable, water pipe, and passenger terminal. 

Does the architect show the entire 3D wireframe to everyone?
* To the **Mayor and City Council**, the architect shows an aerial daylight rendering focusing on the passenger terminal facade and landscaped runways.
* To the **HVAC Contractor**, the architect isolates only the ventilation ducts, chilled water pipes, and cooling towers, hiding all walls and passenger seating.
* To the **Fire Safety Inspector**, the architect filters for emergency exits, sprinkler heads, and fire-rated stairwells, rendered in glowing red.

In software engineering terms:
* The **Project Network** is the **Immutable Canonical State** (Activities, Relationships, Dates, Floats).
* A **Layout** is a **Declarative Viewport Configuration** (Columns, Group & Sort rules, Bar Styles, Timescale, and Saved Filters).
* Changing a Layout modifies **zero bytes of project data**. It changes only the projection through which the client visualizes and interacts with that data.

## 3. Complex Boolean Filters & Dynamic Rolling Variables

### 3.1 Declarative Filter Architecture
A filter is a declarative query predicate evaluated against activity records. P6 supports arbitrary nesting of conjunctions (`ALL of` / `AND`) and disjunctions (`ANY of` / `OR`).

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                            NESTED BOOLEAN FILTER EXPRESSION TREE                                 │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   Target: "Critical Civil Activities at Risk in Block 01 or Block 02"                            │
│                                                                                                  │
│   ROOT (ALL of / AND)                                                                            │
│   ├── Total Float <= 0                                                                           │
│   ├── Activity Status != 'COMPLETED'                                                             │
│   ├── Discipline == 'CIVIL'                                                                      │
│   └── BRANCH (ANY of / OR)                                                                       │
│       ├── Location == 'BLK-01'                                                                   │
│       └── Location == 'BLK-02'                                                                   │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 Dynamic Rolling Variables
Static date filters (e.g., `Start >= '2026-06-01'`) become obsolete within days. Enterprise project controls require **Dynamic Rolling Variables** that evaluate relative to the schedule's current temporal context:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                 DYNAMIC ROLLING FILTER VARIABLES                                 │
├───────────────────────────┬──────────────────────────────────────────────────────────────────────┤
│ Rolling Variable          │ Dynamic Evaluation Semantics                                         │
├───────────────────────────┼──────────────────────────────────────────────────────────────────────┤
│ `Current Date`            │ System clock date at moment of execution (`NOW()`).                  │
│ `Data Date`               │ The project's active schedule status cutoff date (`project.data_date`)│
│ `Current Week`            │ Beginning of the active calendar week containing Data Date / Clock.  │
│ `Current Month`           │ First day of active calendar month.                                  │
│ `Project Start`           │ Calculated Earliest Start date of the CPM network.                   │
│ `Project Finish`          │ Calculated Latest Early Finish date of the CPM network.              │
└───────────────────────────┴──────────────────────────────────────────────────────────────────────┘
```

#### Rolling Offset Expressions:
Schedulers combine variables with temporal offsets:
* `Start Date is between (Data Date) and (Data Date + 14d)` $\to$ **2-Week Lookahead Filter**
* `Early Finish is between (Current Date - 30d) and (Current Date)` $\to$ **30-Day Progress Audit**

## 6. Production Golang Filter AST & Evaluation Engine

Below is a production-grade filter evaluation engine in Go. It parses declarative JSON filter expressions into an **Abstract Syntax Tree (AST)** and evaluates activities in-memory with sub-millisecond execution.

```go
package layout

import (
	"fmt"
	"strings"
	"time"
)

// LogicalOperator represents boolean combining logic.
type LogicalOperator string

const (
	OpALL LogicalOperator = "ALL" // AND
	OpANY LogicalOperator = "ANY" // OR
)

// ComparisonOperator represents predicate comparison operations.
type ComparisonOperator string

const (
	CompEquals           ComparisonOperator = "EQUALS"
	CompNotEquals        ComparisonOperator = "NOT_EQUALS"
	CompLessThan         ComparisonOperator = "LESS_THAN"
	CompLessThanOrEqual  ComparisonOperator = "LESS_THAN_OR_EQUAL"
	CompGreaterThan      ComparisonOperator = "GREATER_THAN"
	CompGreaterThanOrEqual ComparisonOperator = "GREATER_THAN_OR_EQUAL"
	CompIn               ComparisonOperator = "IN"
	CompBetween          ComparisonOperator = "BETWEEN"
)

// DynamicDateExpression represents a dynamic rolling date variable.
type DynamicDateExpression struct {
	Variable   string `json:"variable"` // "DATA_DATE", "CURRENT_DATE"
	OffsetDays int    `json:"offset_days"`
}

// FilterPredicate represents an individual comparison criteria.
type FilterPredicate struct {
	Field      string                 `json:"field"`
	Operator   ComparisonOperator     `json:"operator"`
	Value      interface{}            `json:"value"`
	HighValue  interface{}            `json:"high_value,omitempty"`
}

// FilterGroup represents a nested boolean conjunction or disjunction node.
type FilterGroup struct {
	Logic      LogicalOperator   `json:"logic"` // ALL or ANY
	Predicates []FilterPredicate `json:"predicates,omitempty"`
	SubGroups  []FilterGroup     `json:"sub_groups,omitempty"`
}

// ActivityModel represents the runtime activity evaluation target.
type ActivityModel struct {
	Code         string                 `json:"code"`
	Name         string                 `json:"name"`
	Type         string                 `json:"activity_type"`
	Status       string                 `json:"status"`
	EarlyStart   time.Time              `json:"early_start"`
	EarlyFinish  time.Time              `json:"early_finish"`
	TotalFloat   int                    `json:"total_float"`
	Codes        map[string]string      `json:"codes"`
	UDFs         map[string]interface{} `json:"udfs"`
}

// FilterContext carries dynamic runtime evaluation variables.
type FilterContext struct {
	CurrentDate time.Time
	DataDate    time.Time
}

// FilterEvaluator executes the AST against an activity collection.
type FilterEvaluator struct {
	ctx FilterContext
}

func NewFilterEvaluator(ctx FilterContext) *FilterEvaluator {
	return &FilterEvaluator{ctx: ctx}
}

// Evaluate checks whether a single activity passes the entire filter group tree.
func (fe *FilterEvaluator) Evaluate(act *ActivityModel, group *FilterGroup) bool {
	// Base case: empty filter permits everything
	if len(group.Predicates) == 0 && len(group.SubGroups) == 0 {
		return true
	}

	if group.Logic == OpALL {
		// Conjunction: All predicates and sub-groups must be TRUE
		for _, pred := range group.Predicates {
			if !fe.evalPredicate(act, pred) {
				return false
			}
		}
		for _, sub := range group.SubGroups {
			if !fe.Evaluate(act, &sub) {
				return false
			}
		}
		return true
	}

	if group.Logic == OpANY {
		// Disjunction: Any predicate or sub-group being TRUE permits the row
		for _, pred := range group.Predicates {
			if fe.evalPredicate(act, pred) {
				return true
			}
		}
		for _, sub := range group.SubGroups {
			if fe.Evaluate(act, &sub) {
				return true
			}
		}
		return false
	}

	return false
}

func (fe *FilterEvaluator) resolveDateValue(val interface{}) (time.Time, bool) {
	if strVal, ok := val.(string); ok {
		t, err := time.Parse("2006-01-02", strVal)
		if err == nil {
			return t, true
		}
	} else if mapVal, ok := val.(map[string]interface{}); ok {
		varExpr := fmt.Sprintf("%v", mapVal["variable"])
		offset := 0
		if oVal, ok := mapVal["offset_days"].(float64); ok {
			offset = int(oVal)
		}

		var base time.Time
		if varExpr == "DATA_DATE" {
			base = fe.ctx.DataDate
		} else {
			base = fe.ctx.CurrentDate
		}
		return base.AddDate(0, 0, offset), true
	}
	return time.Time{}, false
}

func (fe *FilterEvaluator) evalPredicate(act *ActivityModel, pred FilterPredicate) bool {
	switch pred.Field {
	case "total_float":
		return fe.evalNumeric(float64(act.TotalFloat), pred)
	case "activity_type":
		return fe.evalString(act.Type, pred)
	case "status":
		return fe.evalString(act.Status, pred)
	case "early_start":
		targetDate, ok := fe.resolveDateValue(pred.Value)
		if !ok {
			return false
		}
		return fe.evalDate(act.EarlyStart, pred.Operator, targetDate)
	case "early_finish":
		targetDate, ok := fe.resolveDateValue(pred.Value)
		if !ok {
			return false
		}
		return fe.evalDate(act.EarlyFinish, pred.Operator, targetDate)
	default:
		// Check Activity Codes
		if codeVal, exists := act.Codes[pred.Field]; exists {
			return fe.evalString(codeVal, pred)
		}
		return false
	}
}

func (fe *FilterEvaluator) evalString(actual string, pred FilterPredicate) bool {
	switch pred.Operator {
	case CompEquals:
		return strings.EqualFold(actual, fmt.Sprintf("%v", pred.Value))
	case CompNotEquals:
		return !strings.EqualFold(actual, fmt.Sprintf("%v", pred.Value))
	case CompIn:
		if slice, ok := pred.Value.([]interface{}); ok {
			for _, item := range slice {
				if strings.EqualFold(actual, fmt.Sprintf("%v", item)) {
					return true
				}
			}
		}
		return false
	}
	return false
}

func (fe *FilterEvaluator) evalNumeric(actual float64, pred FilterPredicate) bool {
	val, ok := pred.Value.(float64)
	if !ok {
		if intVal, ok := pred.Value.(int); ok {
			val = float64(intVal)
		} else {
			return false
		}
	}

	switch pred.Operator {
	case CompEquals:
		return actual == val
	case CompLessThanOrEqual:
		return actual <= val
	case CompGreaterThanOrEqual:
		return actual >= val
	case CompLessThan:
		return actual < val
	case CompGreaterThan:
		return actual > val
	}
	return false
}

func (fe *FilterEvaluator) evalDate(actual time.Time, op ComparisonOperator, target time.Time) bool {
	switch op {
	case CompLessThanOrEqual:
		return actual.Before(target) || actual.Equal(target)
	case CompGreaterThanOrEqual:
		return actual.After(target) || actual.Equal(target)
	case CompLessThan:
		return actual.Before(target)
	case CompGreaterThan:
		return actual.After(target)
	case CompEquals:
		return actual.Year() == target.Year() && actual.YearDay() == target.YearDay()
	}
	return false
}
```

## 7. Real-World Engineering Pitfalls & Anti-Patterns

### 7.1 Pitfall 1: Timezone Discrepancies with Rolling Variables
* **The Anti-Pattern:** Schedulers in India (IST, UTC+5:30) and Houston (CST, UTC-6:00) open the same layout. The filter uses `Current Date`.
* **Why it Breaks Systems:** Schedulers see different activity counts for the "Today" lookahead because the server evaluates UTC midnight while the site is already half-way through the working day.
* **The Architectural Rule:** Dynamic date filters must evaluate against the **Project's Data Date** or use the **Project's Geographic Timezone**, never the arbitrary UTC system clock of the cloud server.

### 7.2 Pitfall 2: Layout Schema Migration Drift
* **The Anti-Pattern:** A user deletes an Activity Code Type (`Module_Batch`), but 50 saved layouts still reference `Module_Batch` in their `group_by` and `filter` JSON definitions.
* **Why it Breaks Systems:** Opening those layouts throws unhandled JavaScript errors in the Next.js frontend, bricking the user interface.
* **The Architectural Rule:** Implement a **Layout Schema Validator and Sanitizer**. When loading a layout, the backend strips non-existent column IDs and pruning invalid filter predicates, logging a warning rather than crashing.

### 7.3 Pitfall 3: DOM Overload in Next.js Gantt Views
* **The Anti-Pattern:** Rendering 15,000 activity rows and SVG Gantt bars directly into the HTML DOM.
* **Why it Breaks Systems:** Browser memory consumes 3GB of RAM, frame rates drop to 2 FPS, and user interactions lock up.
* **The Architectural Rule:** Mandatory **Virtual Scrolling (Virtualization)** on both table and canvas. Render only the 40 visible rows in the viewport window ($O(1)$ DOM nodes), dynamically recycling elements during scrolling.
