## 🧠 Section A: Conceptual & Architectural Principles

### Solution 1: Decoupling Identity from Organizational Position

#### 1. Why Decouple User Accounts from the OBS
In enterprise project controls:
* **`app_user` represents a physical identity:** A person who logs in with credentials, an email address, and an active session. People change companies, take parental leave, or transfer departments.
* **`obs_node` represents an organizational role and management responsibility:** A permanent operational position (e.g., "Lead Project Manager — Rajasthan", "Civil Construction Superintendent").
* **Decoupling Rationale:**
  1. Projects, EPS branches, and Work Breakdown Structures are assigned to an **OBS node**, never directly to an individual person's user ID.
  2. If assignments were hardcoded to user IDs, replacing a Project Manager would require updating thousands of database foreign keys across projects, activities, WBS nodes, and approval workflows.
  3. Under the OBS model, reassigning responsibility requires updating only **one relationship**: re-binding the new employee's `user_id` to the existing `obs_id`.

#### 2. Administrative Procedure on Employee Turnover
* **Under Direct-Role Model:**
  - Locate all 5,000 activities, 12 projects, and 4 EPS nodes where `responsible_user_id = 'rajesh_uuid'`.
  - Execute massive database updates to change `responsible_user_id` to `new_pm_uuid`.
  - Re-configure all permissions, notifications, and approval workflows individually.
* **Under the P6 OBS Model:**
  - Step 1: Revoke `user_obs_grant` for Rajesh on `OBS-PM-RAJ`.
  - Step 2: Insert a new `user_obs_grant` binding the new PM to `OBS-PM-RAJ` with the `Project Manager` profile.
  - Zero project, WBS, or activity records need to be modified. The new PM instantly inherits access to all projects governed by `OBS-PM-RAJ`.

#### 3. Preservation of Historical Audit Integrity
When Rajesh departs:
* Historical audit logs (e.g., `activity_audit_log.created_by = 'rajesh_uuid'`) remain immutable, preserving contractual and legal records of who authorized schedule changes.
* Current operational ownership transitions cleanly through the OBS node without erasing past audit trails.

### Solution 2: Global Security Profiles vs. Project Security Profiles

#### 1. Profile Type Mapping
```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                         SECURITY PROFILE CLASSIFICATION MAPPING                                  │
├────────────────────────────────────────────────────────┬─────────────────────────────────────────┤
│ Operational Action                                     │ Governing Profile Type                  │
├────────────────────────────────────────────────────────┼─────────────────────────────────────────┤
│ Create new enterprise calendar (desert hours)          │ Global Security Profile                 │
│ Modify Planned Finish date of solar tracker activity   │ Project Security Profile                │
│ Add new global Activity Code ("PV Manufacturer")       │ Global Security Profile                 │
│ Create new Project Baseline (Baseline B01)             │ Project Security Profile                │
│ Run CPM Critical Path calculation (F9 execution)       │ Project Security Profile                │
│ Change system-wide currency exchange rate (USD to INR) │ Global Security Profile                 │
└────────────────────────────────────────────────────────┴─────────────────────────────────────────┘
```

#### 2. The High-Risk Mechanics of "Restore Baseline"
* **Creating a Baseline (`can_create_baseline`):** Takes a read-only snapshot of the current project state and saves it into baseline archive tables. It is non-destructive.
* **Restoring a Baseline (`can_restore_baseline`):** Decouples a baseline snapshot and converts it back into an active, editable project—or overwrites the current live project with historic baseline data.
* **Why Separate Permissions Are Mandatory:**
  If an unauthorized scheduler restores an outdated baseline over the live project, months of real-time actual progress, site status records, and cost accruals could be permanently overwritten. In enterprise governance, project managers may have rights to *create* baselines, but only the Project Controls Director or PMO Lead may *restore* a baseline.

### Solution 3: The Mechanics of Cascading Access in the EPS-OBS Matrix

#### 1. Effective Permissions for User Anita on `PRJ-SOL-050-HAR`
* Anita is assigned to `OBS-VP-SOLAR` with the `Project Manager` profile.
* In the OBS tree, `OBS-VP-SOLAR` is the parent of `OBS-DIR-NORTH`.
* `PRJ-SOL-050-HAR` resides under EPS node `SOLAR-NORTH`, which reports to `OBS-DIR-NORTH`.
* **Result:** Because `OBS-VP-SOLAR` is an ancestor of `OBS-DIR-NORTH`, Anita's `Project Manager` permissions **cascade downwards**. She has full `Project Manager` rights (view, edit, schedule, baseline) on `PRJ-SOL-050-HAR`.

#### 2. Effective Scope for User Tariq (Subcontractor)
* Tariq is assigned to `OBS-PM-RAJ` with profile `Field Statusing`.
* `PRJ-SOL-100-RAJ` is assigned to Responsible Manager `OBS-PM-RAJ`.
* **Result:** Tariq can view `PRJ-SOL-100-RAJ` and update physical progress / actual dates on activities assigned to his scope. He cannot add new activities, change planned baseline dates, modify budgets, or execute F9 schedule calculations.

#### 3. Can Tariq Access `PRJ-SOL-050-HAR`?
* **No.** `PRJ-SOL-050-HAR` is governed by `OBS-DIR-NORTH` (or an independent PM OBS node).
* Tariq's grant is rooted at `OBS-PM-RAJ`. Traversal walks *downward* from grants to resources, never upward to sibling or parent branches. Tariq cannot view or access `PRJ-SOL-050-HAR`.

### Solution 4: Multi-Grant Additive Union vs. Hierarchical Shadowing

#### 1. Outcome for User Rajesh
* **Permit.** Rajesh's action (editing activity dates) is permitted.
* Under the **Additive Union** model, an action is allowed if **at least one** active grant covering the resource explicitly enables that action.
* Even though Grant 1 (`Executive Viewer` at the parent node) has `can_edit_activity_dates = FALSE`, Grant 2 (`Project Manager` at the child node) has `can_edit_activity_dates = TRUE`. The union of `FALSE OR TRUE` evaluates to `TRUE`.

#### 2. Why P6 Uses Additive Union
In enterprise operations, staff frequently hold broad read-only roles across a division while carrying deep operational write roles on specific sub-projects.
If a system enforced "first-match-wins" (evaluating from the root down), the parent read-only grant would shadow and disable the child write grant, preventing the manager from working.

#### 3. Vulnerability of "Least-Privilege-Wins" in Hierarchies
If an authorization engine enforced "most restrictive wins" across hierarchical grants:
* Assigning an executive a global "Auditor / Read-Only" profile at the root node would instantly strip their administrative edit rights across every sub-project they manage!
* Additive union is the only model that allows graceful delegation of responsibilities.

## 🏗️ Section B: Database Design & SQL Implementation

### Solution 5: PostgreSQL Schema & Relational Matrix Grants

```sql
CREATE EXTENSION IF NOT EXISTS ltree;

-- 1. Organizational Breakdown Structure (OBS) Table
CREATE TABLE obs_node (
    obs_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    obs_code VARCHAR(32) NOT NULL UNIQUE,
    obs_name VARCHAR(120) NOT NULL,
    parent_obs_id UUID REFERENCES obs_node(obs_id) ON DELETE RESTRICT,
    obs_path ltree NOT NULL,
    description TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);
CREATE INDEX idx_obs_path_gist ON obs_node USING GIST (obs_path);

-- 2. Project Security Profiles Table
CREATE TABLE project_security_profile (
    profile_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    profile_name VARCHAR(64) NOT NULL UNIQUE,
    description TEXT,
    
    can_view_project BOOLEAN NOT NULL DEFAULT TRUE,
    can_edit_project_details BOOLEAN NOT NULL DEFAULT FALSE,
    can_add_delete_activities BOOLEAN NOT NULL DEFAULT FALSE,
    can_edit_activity_dates BOOLEAN NOT NULL DEFAULT FALSE,
    can_edit_activity_progress BOOLEAN NOT NULL DEFAULT FALSE,
    can_execute_scheduling BOOLEAN NOT NULL DEFAULT FALSE,
    can_create_baseline BOOLEAN NOT NULL DEFAULT FALSE,
    can_restore_baseline BOOLEAN NOT NULL DEFAULT FALSE,
    can_view_costs BOOLEAN NOT NULL DEFAULT FALSE,
    can_edit_costs BOOLEAN NOT NULL DEFAULT FALSE,
    can_edit_udfs BOOLEAN NOT NULL DEFAULT FALSE,
    
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

-- 3. Application Users Table
CREATE TABLE app_user (
    user_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    username VARCHAR(64) NOT NULL UNIQUE,
    email VARCHAR(255) NOT NULL UNIQUE,
    is_super_admin BOOLEAN NOT NULL DEFAULT FALSE,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

-- 4. User-to-OBS Security Matrix Grant Table
CREATE TABLE user_obs_grant (
    grant_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES app_user(user_id) ON DELETE CASCADE,
    obs_id UUID NOT NULL REFERENCES obs_node(obs_id) ON DELETE CASCADE,
    profile_id UUID NOT NULL REFERENCES project_security_profile(profile_id) ON DELETE RESTRICT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    CONSTRAINT uq_user_obs_grant UNIQUE (user_id, obs_id)
);
CREATE INDEX idx_user_obs_grant_lookup ON user_obs_grant(user_id, obs_id);
```

### Solution 6: Dynamic Permission Evaluation Function

```sql
CREATE OR REPLACE FUNCTION fn_check_user_project_permission(
    p_user_id UUID,
    p_project_id UUID,
    p_action VARCHAR
) RETURNS BOOLEAN AS $$
DECLARE
    v_is_super BOOLEAN;
    v_project_obs_path ltree;
    v_has_permission BOOLEAN;
BEGIN
    -- 1. Check Super Admin status
    SELECT is_super_admin INTO v_is_super 
    FROM app_user 
    WHERE user_id = p_user_id AND is_active = TRUE;
    
    IF v_is_super IS TRUE THEN
        RETURN TRUE;
    END IF;

    -- 2. Fetch the project's Responsible Manager OBS path
    SELECT o.obs_path INTO v_project_obs_path
    FROM project p
    JOIN obs_node o ON o.obs_id = p.obs_id
    WHERE p.project_id = p_project_id;

    IF v_project_obs_path IS NULL THEN
        RETURN FALSE;
    END IF;

    -- 3. Evaluate Additive Union across all matching grants
    EXECUTE format('
        SELECT EXISTS (
            SELECT 1
            FROM user_obs_grant g
            JOIN obs_node granted_obs ON granted_obs.obs_id = g.obs_id
            JOIN project_security_profile psp ON psp.profile_id = g.profile_id
            WHERE g.user_id = $1
              AND granted_obs.obs_path @> $2
              AND psp.%I = TRUE
        )', p_action)
    INTO v_has_permission
    USING p_user_id, v_project_obs_path;

    RETURN COALESCE(v_has_permission, FALSE);
END;
$$ LANGUAGE plpgsql STABLE;
```

### Solution 7: PostgreSQL Row-Level Security (RLS) Policy

```sql
-- Enable RLS on the project table
ALTER TABLE project ENABLE ROW LEVEL SECURITY;

-- Transparent read access control policy
CREATE POLICY p_project_select_security ON project
FOR SELECT
USING (
    -- Super Admin bypass
    EXISTS (
        SELECT 1 
        FROM app_user u 
        WHERE u.user_id = NULLIF(current_setting('app.current_user_id', true), '')::UUID 
          AND u.is_super_admin = TRUE
    )
    OR
    -- Evaluates if user has a valid grant at or above the project's OBS node
    EXISTS (
        SELECT 1
        FROM user_obs_grant g
        JOIN obs_node granted_obs ON granted_obs.obs_id = g.obs_id
        JOIN obs_node project_obs ON project_obs.obs_id = project.obs_id
        JOIN project_security_profile psp ON psp.profile_id = g.profile_id
        WHERE g.user_id = NULLIF(current_setting('app.current_user_id', true), '')::UUID
          AND granted_obs.obs_path @> project_obs.obs_path
          AND psp.can_view_project = TRUE
    )
);
```

## 💻 Section C: Golang Authorization Engine & Performance

### Solution 8: High-Performance In-Memory Authorization Engine

```go
package security

import (
	"errors"
	"fmt"
	"strings"
	"sync"
)

type PermissionAction string

const (
	ActionViewProject        PermissionAction = "can_view_project"
	ActionEditProject        PermissionAction = "can_edit_project_details"
	ActionAddDeleteActivity  PermissionAction = "can_add_delete_activities"
	ActionEditActivityDates  PermissionAction = "can_edit_activity_dates"
	ActionUpdateProgress     PermissionAction = "can_edit_activity_progress"
	ActionExecuteScheduling  PermissionAction = "can_execute_scheduling"
	ActionCreateBaseline     PermissionAction = "can_create_baseline"
	ActionRestoreBaseline    PermissionAction = "can_restore_baseline"
	ActionViewCosts          PermissionAction = "can_view_costs"
	ActionEditCosts          PermissionAction = "can_edit_costs"
)

type SecurityProfile struct {
	ID          string
	Name        string
	Permissions map[PermissionAction]bool
}

type OBSNode struct {
	ID   string
	Path string // e.g. "SURYA.SOLAR.RAJASTHAN"
}

type UserGrant struct {
	UserID    string
	OBSID     string
	OBSPath   string
	ProfileID string
	Profile   *SecurityProfile
}

type AuthEngine struct {
	mu          sync.RWMutex
	obsMap      map[string]*OBSNode
	userGrants  map[string][]UserGrant
	superAdmins map[string]bool
}

func NewAuthEngine() *AuthEngine {
	return &AuthEngine{
		obsMap:      make(map[string]*OBSNode),
		userGrants:  make(map[string][]UserGrant),
		superAdmins: make(map[string]bool),
	}
}

func isAncestor(ancestorPath, targetPath string) bool {
	if ancestorPath == targetPath {
		return true
	}
	return strings.HasPrefix(targetPath, ancestorPath+".")
}

func (a *AuthEngine) CanUserPerformAction(userID string, projectOBSID string, action PermissionAction) (bool, error) {
	a.mu.RLock()
	defer a.mu.RUnlock()

	// 1. Super Admin instant permit
	if a.superAdmins[userID] {
		return true, nil
	}

	// 2. Resolve project's OBS node
	projOBS, exists := a.obsMap[projectOBSID]
	if !exists {
		return false, fmt.Errorf("project OBS %s not recognized", projectOBSID)
	}

	// 3. Check user grants (Additive Union)
	grants, found := a.userGrants[userID]
	if !found || len(grants) == 0 {
		return false, nil
	}

	for _, grant := range grants {
		if grant.Profile == nil {
			continue
		}
		if isAncestor(grant.OBSPath, projOBS.Path) {
			if grant.Profile.Permissions[action] {
				return true, nil // Short-circuit on first matching true permission
			}
		}
	}

	return false, nil
}
```

### Solution 9: HTTP API Middleware Enforcement

```go
package security

import (
	"database/sql"
	"encoding/json"
	"net/http"
	"strings"
)

type Middleware struct {
	authEngine *AuthEngine
	db         *sql.DB
}

func NewMiddleware(engine *AuthEngine, db *sql.DB) *Middleware {
	return &Middleware{authEngine: engine, db: db}
}

func (m *Middleware) RequireProjectPermission(action PermissionAction, next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		// 1. Extract User ID from context (injected by Auth/JWT middleware)
		userID, ok := r.Context().Value("current_user_id").(string)
		if !ok || userID == "" {
			http.Error(w, `{"error":"unauthenticated"}`, http.StatusUnauthorized)
			return
		}

		// 2. Extract Project ID from URL path (e.g., /api/v1/projects/{project_id}/...)
		parts := strings.Split(r.URL.Path, "/")
		var projectID string
		for i, part := range parts {
			if part == "projects" && i+1 < len(parts) {
				projectID = parts[i+1]
				break
			}
		}
		if projectID == "" {
			http.Error(w, `{"error":"missing project_id in route"}`, http.StatusBadRequest)
			return
		}

		// 3. Fetch project's OBS ID
		var projectOBSID string
		err := m.db.QueryRowContext(r.Context(), "SELECT obs_id FROM project WHERE project_id = $1", projectID).Scan(&projectOBSID)
		if err != nil {
			http.Error(w, `{"error":"project not found"}`, http.StatusNotFound)
			return
		}

		// 4. Verify permission in-memory with sub-millisecond evaluation
		allowed, err := m.authEngine.CanUserPerformAction(userID, projectOBSID, action)
		if err != nil || !allowed {
			w.Header().Set("Content-Type", "application/json")
			w.WriteHeader(http.StatusForbidden)
			json.NewEncoder(w).Encode(map[string]string{
				"error":   "forbidden",
				"message": "insufficient permissions to perform: " + string(action),
			})
			return
		}

		// 5. Authorized - pass to next handler
		next(w, r)
	}
}
```

### Solution 10: Real-World Incident — The Subcontractor Baseline Leak

#### 1. Security Configuration Flaw Analysis
The leak occurred due to two common enterprise oversights:
1. **Overly Broad Default Profile:** The subcontractor was assigned a profile where `can_view_costs = TRUE` was left enabled by default.
2. **Missing Field-Level Output Masking:** The Next.js frontend fetched the full project JSON object (`GET /api/v1/projects/:id`), which included `budget_at_completion`, `contingency_reserve`, and `baseline_finish_date`. The frontend simply hid the cost tab in the UI using CSS (`display: none`), allowing the subcontractor to inspect the raw API JSON payload via browser Developer Tools.

#### 2. Hardened `Field Statusing` Security Profile
To securely sandbox third-party subcontractors, configure the following profile flags:
```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                   HARDENED FIELD STATUSING SECURITY PROFILE CONFIGURATION                        │
├───────────────────────────────────┬───────────────┬──────────────────────────────────────────────┤
│ Permission Flag                   │ State         │ Security Justification                       │
├───────────────────────────────────┼───────────────┼──────────────────────────────────────────────┤
│ can_view_project                  │ TRUE          │ Necessary to load assigned activities.       │
│ can_edit_activity_progress        │ TRUE          │ Permits updating % complete and actual dates.│
│ can_edit_activity_dates           │ FALSE         │ Blocks tampering with planned/baseline dates.│
│ can_add_delete_activities         │ FALSE         │ Blocks injecting unapproved contract scope.  │
│ can_execute_scheduling (F9)       │ FALSE         │ Blocks recalculating enterprise critical path│
│ can_create_baseline               │ FALSE         │ Prevents overwriting baseline archives.      │
│ can_restore_baseline              │ FALSE         │ Eliminates project restore risk.             │
│ can_view_costs                    │ FALSE         │ Conceals financial rates, budgets, margins.  │
│ can_edit_costs                    │ FALSE         │ Prevents altering commercial values.         │
└───────────────────────────────────┴───────────────┴──────────────────────────────────────────────┘
```

#### 3. Field-Level Masking in Response Serializers
Never rely on client-side CSS to hide confidential enterprise data. In the Go backend serializer:

```go
type ProjectResponse struct {
	ID          string     `json:"id"`
	Code        string     `json:"code"`
	Name        string     `json:"name"`
	DataDate    string     `json:"data_date"`
	BAC         *float64   `json:"budget_at_completion,omitempty"`
	PV          *float64   `json:"planned_value,omitempty"`
	EV          *float64   `json:"earned_value,omitempty"`
	AC          *float64   `json:"actual_cost,omitempty"`
}

func MaskProjectResponse(p *Project, canViewCosts bool) ProjectResponse {
	resp := ProjectResponse{
		ID:       p.ID,
		Code:     p.Code,
		Name:     p.Name,
		DataDate: p.DataDate.Format("2006-01-02"),
	}

	if canViewCosts {
		resp.BAC = &p.BudgetAtCompletion
		resp.PV = &p.PlannedValue
		resp.EV = &p.EarnedValue
		resp.AC = &p.ActualCost
	}

	return resp
}
```
If `canViewCosts` is `false`, cost fields serialize as `null` or are completely omitted from the JSON payload, guaranteeing zero leakage even if the network tab is inspected.
