# Topic 5.3: Global, Project & Resource Calendars — Enterprise Hierarchy & Precedence

## 1. Executive Summary & The Core Mental Model

### 1.1 The Axiom: Enterprise Scheduling Requires Tiered Temporal Governance
In small software task trackers (such as Jira or Trello), a calendar is an afterthought. A sprint is two weeks, weekends are assumed non-working, and everyone shares the same calendar.

In multi-billion-dollar Engineering, Procurement, and Construction (EPC) projects—such as the **Surya 100MW Solar IPP Project** in Rajasthan, India—a single global calendar is impossible. An EPC enterprise simultaneously manages:
1. **Corporate Headquarters & Legal Compliance:** Managing contracts, bank financing, and regulatory filings in New Delhi and Mumbai under statutory national holidays and standard 5-day office hours.
2. **Site Civil Works:** Operating 6 days a week, 10 hours a day in the Thar Desert, constrained by extreme summer heat curfews and local state holidays.
3. **Continuous Chemical & Physical Processes:** 24/7 uninterrupted curing of 220kV transformer foundation pads and continuous substation security operations.
4. **Specialized Capital Equipment & Subcontractor Crews:** High-tonnage hydraulic piling rigs that require weekly scheduled maintenance down-days, and specialized German inverter commissioning technicians working on 4-day, 10-hour compressed shifts.

If a project manager changes a national holiday at the corporate level, should that change immediately wipe out the site contractor's Sunday overtime shift? **No.**  
Conversely, if a project planner creates a custom 6-day desert shift, should that custom calendar leak into the corporate database and corrupt a petrochemical plant project in Gujarat? **Absolutely not.**

To solve this, enterprise scheduling systems like **Oracle Primavera P6** implement a **3-Tier Enterprise Calendar Architecture**:

```text

│                           THE 3-TIER ENTERPRISE CALENDAR HIERARCHY                               │

│   │  • Defines standard statutory holidays, standard corporate 5-day / 40h work weeks       │   │
```

## 2. Activity Type & Calendar Precedence Rules

In Primavera P6 and modern industrial scheduling engines, an activity does not have a single hardcoded duration calculation. The scheduling engine determines which calendar dictates early and late dates based on the **Activity Type**.

The two dominant activity types governing calendar resolution are:
1. **Task Dependent (`TASK_DEPENDENT`)** (Industry standard default)
2. **Resource Dependent (`RESOURCE_DEPENDENT`)**

### 2.1 Task Dependent Activities (`TASK_DEPENDENT`)

#### The Rule:
> **An activity designated as Task Dependent is scheduled strictly according to the Activity's assigned calendar, regardless of the calendars assigned to any resources working on that activity.**

#### Physical Intuition:
Task Dependent activities represent work whose timeline is dictated by **site conditions, contract milestones, or project work windows**, rather than individual human or machine availability.
* If **"Site Grading & Earthworks"** is scheduled on a 6-day project calendar (Monday to Saturday), the activity **will proceed Monday through Saturday**.
* If a surveyor assigned to the task only works Monday to Thursday (on a 4-day resource calendar), the activity **does not stop on Friday or Saturday**.
* What happens to the surveyor? The scheduler reports a **Resource Overallocation / Availability Conflict** (the resource is demanded when their calendar says non-working), but **the activity dates (Start/Finish) remain firmly fixed on the activity calendar**.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                   TASK DEPENDENT SCHEDULING (Activity Calendar Governs)                          │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Activity: Piling Block A (Duration: 30 Working Hours)                                            │
│ Assigned Activity Calendar: Surya Site Civil (6-Day, 10h/day: Mon-Sat 07:00-18:00, 1h lunch)     │
│ Assigned Resource: Crane Operator Ram (Resource Calendar: 5-Day, Mon-Fri 07:00-18:00)           │
│                                                                                                  │
│ Universal Timeline:                                                                              │
│                 Thu (Day 1)          Fri (Day 2)          Sat (Day 3)          Sun (Day 4)       │
│              07:00     18:00      07:00     18:00      07:00     18:00                           │
│ Activity:    ┌──────────────┐     ┌──────────────┐     ┌──────────────┐                          │
│ Site Civil   │   10 Hours   │     │   10 Hours   │     │   10 Hours   │     [Non-Working Day]    │

│                                                        ▲                                         │
│                                                        │ OVERALLOCATION / CONFLICT!              │
```

### 2.2 Resource Dependent Activities (`RESOURCE_DEPENDENT`)

#### The Rule:
> **An activity designated as Resource Dependent is scheduled according to the assigned Resource's calendar. If multiple resources are assigned, the activity is governed by the Primary Resource's calendar (or the joint intersection of all assigned resource calendars). The Activity calendar is completely bypassed for date computation.**

#### Physical Intuition:
Resource Dependent activities represent specialized work whose progress is **entirely constrained by the physical presence of a specific machine or certified specialist**.
* If **"220kV Substation Relay Protection Testing"** requires Dr. Mehta (the sole certified commissioning engineer in western India), the testing can **only happen when Dr. Mehta is on site**.
* If Dr. Mehta works Tuesday through Saturday, testing **cannot take place on Monday**, even though the project site is fully open and active on Monday!
* If Dr. Mehta takes a planned leave from Wednesday to Friday, the activity **stretches across those days**, pushing the finish date out.

Let us contrast the exact same scenario under `RESOURCE_DEPENDENT`:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                 RESOURCE DEPENDENT SCHEDULING (Resource Calendar Governs)                        │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Activity: Piling Block A (Duration: 30 Working Hours)                                            │
│ Assigned Activity Calendar: Surya Site Civil (6-Day: Mon-Sat, 10h/day)                           │
│ Assigned Primary Resource: Bauer Piling Rig 1 (Resource Cal: Mon-Thu 10h/day, Fri-Sun Overhaul)  │
│ Start Date: Thursday 07:00                                                                       │
│                                                                                                  │
│ Universal Timeline:                                                                              │
│             Thu (D1)      Fri (D2)      Sat (D3)      Sun (D4)      Mon (D5)      Tue (D6)       │
│ Activity:   ┌──────────┐  ░░░░░░░░░░░░  ░░░░░░░░░░░░  ░░░░░░░░░░░░  ┌──────────┐  ┌──────────┐   │
│ Progress:   │ 10 Hours │  ░ PAUSED ░░░  ░ PAUSED ░░░  ░ PAUSED ░░░  │ 10 Hours │  │ 10 Hours │   │
│             └──────────┘  ░░░░░░░░░░░░  ░░░░░░░░░░░░  ░░░░░░░░░░░░  └──────────┘  └──────────┘   │
│ Work Total:     10h           10h           10h           10h           20h           30h (DONE) │
│                                                                                                  │
│ Resource    ┌──────────┐  [RIG OVERHAUL MAINTENANCE - NON-WORKING]  ┌──────────┐  ┌──────────┐   │
│ Bauer Rig 1:│  Active  │  ░░░░░░░░░░░░  ░░░░░░░░░░░░  ░░░░░░░░░░░░  │  Active  │  │  Active  │   │
│             └──────────┘                                            └──────────┘  └──────────┘   │
│                                                                                                  │
│ Outcome: Under Resource Dependent, the activity STRETCHES from 3 calendar days (Thu-Sat)         │
│          to 6 calendar days (Thu-Tue) because Friday & Saturday are rig overhaul non-working!    │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **Summary Comparison:**
> - **Task Dependent:** Activity Calendar dictates the timeline. Duration in calendar days is fixed. Resources must adapt or show overallocation.
> - **Resource Dependent:** Primary Resource Calendar dictates the timeline. Duration in calendar days stretches/fragments to fit resource availability.

## 3. Data Modeling & Inheritance Architecture in PostgreSQL

When designing a production scheduling engine in Golang and PostgreSQL, you must solve a critical architectural challenge:  
**How do we model Global, Project, and Resource calendars while supporting overrides without database bloat or race conditions?**

There are two primary architectural patterns:
1. **The Pure Clone (Snapshot) Pattern**
2. **The Prototypal Inheritance (Delta-Override) Pattern**

### 3.1 Pattern Comparison: Clone vs. Prototypal Inheritance

### 3.2 The Enterprise Standard: The Hybrid Prototype-Snapshot Model
In Oracle Primavera P6 and mission-critical engines, **Project Calendars can either link to a Global Calendar base or exist as independent Project-specific calendars**.

Here is the battle-tested PostgreSQL schema implementing this architecture:

```sql
-- Enums for Calendar Tier and Activity Governance
CREATE TYPE calendar_scope AS ENUM ('GLOBAL', 'PROJECT', 'RESOURCE');
CREATE TYPE activity_type_enum AS ENUM (
    'TASK_DEPENDENT', 
    'RESOURCE_DEPENDENT', 
    'LEVEL_OF_EFFORT', 
    'START_MILESTONE', 
    'FINISH_MILESTONE'
);
CREATE TYPE day_override_type AS ENUM ('WORKING', 'NON_WORKING', 'CUSTOM_HOURS');

-- 1. Core Calendars Table
CREATE TABLE calendars (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    enterprise_id UUID NOT NULL,
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    parent_calendar_id UUID REFERENCES calendars(id) ON DELETE RESTRICT,
    scope calendar_scope NOT NULL,
    name VARCHAR(255) NOT NULL,
    description TEXT,
    
    -- Nominal daily conversion factor (e.g., 8.0, 10.0, 24.0)
    hours_per_day NUMERIC(4, 2) NOT NULL DEFAULT 8.00,
    hours_per_week NUMERIC(5, 2) NOT NULL DEFAULT 40.00,
    hours_per_month NUMERIC(6, 2) NOT NULL DEFAULT 172.00,
    hours_per_year NUMERIC(7, 2) NOT NULL DEFAULT 2000.00,
    
    is_default BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    
    -- Constraint: Global calendars MUST NOT have a project_id
    CONSTRAINT chk_global_no_project CHECK (
        (scope = 'GLOBAL' AND project_id IS NULL) OR
        (scope IN ('PROJECT', 'RESOURCE'))
    ),
    -- Constraint: Project calendars MUST have a project_id
    CONSTRAINT chk_project_has_project CHECK (
        (scope = 'PROJECT' AND project_id IS NOT NULL) OR
        (scope IN ('GLOBAL', 'RESOURCE'))
    )
);

CREATE INDEX idx_calendars_scope_proj ON calendars(scope, project_id);
CREATE INDEX idx_calendars_parent ON calendars(parent_calendar_id);

-- 2. Standard 7-Day Weekly Pattern (0 = Sunday, 1 = Monday, ..., 6 = Saturday)
CREATE TABLE calendar_weekly_shifts (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    calendar_id UUID NOT NULL REFERENCES calendars(id) ON DELETE CASCADE,
    day_of_week SMALLINT NOT NULL CHECK (day_of_week BETWEEN 0 AND 6),
    is_working BOOLEAN NOT NULL DEFAULT TRUE,
    
    -- Shift intervals stored as JSONB array of minute ranges: [{"start": 420, "end": 720}, {"start": 780, "end": 1080}]
    -- e.g., 420 = 07:00, 1080 = 18:00
    shifts JSONB NOT NULL DEFAULT '[]'::jsonb,
    total_work_minutes INT NOT NULL DEFAULT 0,
    
    CONSTRAINT uq_cal_day UNIQUE (calendar_id, day_of_week)
);

-- 3. Specific Date Exceptions & Overrides
CREATE TABLE calendar_exceptions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    calendar_id UUID NOT NULL REFERENCES calendars(id) ON DELETE CASCADE,
    exception_date DATE NOT NULL,
    override_type day_override_type NOT NULL,
    description VARCHAR(255),
    
    -- Custom shift intervals if override_type = 'CUSTOM_HOURS'
    custom_shifts JSONB DEFAULT '[]'::jsonb,
    total_work_minutes INT NOT NULL DEFAULT 0,
    
    CONSTRAINT uq_cal_date UNIQUE (calendar_id, exception_date)
);

CREATE INDEX idx_cal_exceptions_date ON calendar_exceptions(calendar_id, exception_date);

-- 4. Activities Table with Calendar & Activity Type
CREATE TABLE activities (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    calendar_id UUID NOT NULL REFERENCES calendars(id) ON DELETE RESTRICT,
    activity_type activity_type_enum NOT NULL DEFAULT 'TASK_DEPENDENT',
    name VARCHAR(255) NOT NULL,
    planned_duration_minutes INT NOT NULL,
    early_start TIMESTAMPTZ,
    early_finish TIMESTAMPTZ,
    late_start TIMESTAMPTZ,
    late_finish TIMESTAMPTZ,
    total_float_minutes INT
);

-- 5. Resources and Resource Assignments
CREATE TABLE resources (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    enterprise_id UUID NOT NULL,
    calendar_id UUID NOT NULL REFERENCES calendars(id) ON DELETE RESTRICT,
    name VARCHAR(255) NOT NULL,
    resource_type VARCHAR(50) NOT NULL -- 'LABOR', 'NON_LABOR', 'MATERIAL'
);

CREATE TABLE activity_resource_assignments (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    activity_id UUID NOT NULL REFERENCES activities(id) ON DELETE CASCADE,
    resource_id UUID NOT NULL REFERENCES resources(id) ON DELETE RESTRICT,
    is_primary BOOLEAN NOT NULL DEFAULT FALSE,
    planned_units_per_hour NUMERIC(5, 2) NOT NULL DEFAULT 1.00,
    
    -- Only one primary resource allowed per activity
    CONSTRAINT uq_act_primary_res UNIQUE (activity_id, is_primary) 
        DEFERRABLE INITIALLY DEFERRED
);
```

### 3.3 Hierarchical SQL Calendar Resolution

When a Project Calendar inherits from a Global Calendar (`parent_calendar_id IS NOT NULL`), an exception defined on the Project Calendar **overrides** an exception on the Global Calendar. If the Project Calendar has no exception for date $D$, it inherits the Global Calendar's exception for date $D$.

Here is the high-performance SQL query using Common Table Expressions (CTEs) to resolve the effective daily exception for any given date:

```sql
WITH RECURSIVE calendar_chain AS (
    -- Base: The target calendar
    SELECT id, parent_calendar_id, 1 AS depth
    FROM calendars
    WHERE id = :target_calendar_id
    
    UNION ALL
    
    -- Recursive Step: Traverse up to parent (Global) calendar
    SELECT c.id, c.parent_calendar_id, cc.depth + 1
    FROM calendars c
    JOIN calendar_chain cc ON c.id = cc.parent_calendar_id
)
SELECT 
    e.exception_date,
    e.override_type,
    e.custom_shifts,
    e.total_work_minutes,
    e.description
FROM calendar_chain cc
JOIN calendar_exceptions e ON e.calendar_id = cc.id
WHERE e.exception_date = :query_date
ORDER BY cc.depth ASC -- Depth 1 (Project) takes precedence over Depth 2 (Global)
LIMIT 1;
```

## 4. Golang Calendar Resolution Engine

Now, let us implement the production Golang resolution engine that:
1. Evaluates an Activity's `ActivityType`.
2. Inspects resource assignments to identify the Primary Resource.
3. Selects the governing calendar.
4. Executes interval walking to compute Start and Finish timestamps.

### 4.1 Domain Structures

```go
package calendar

import (
	"errors"
	"fmt"
	"time"
)

type CalendarScope string

const (
	ScopeGlobal   CalendarScope = "GLOBAL"
	ScopeProject  CalendarScope = "PROJECT"
	ScopeResource CalendarScope = "RESOURCE"
)

type ActivityType string

const (
	TaskDependent     ActivityType = "TASK_DEPENDENT"
	ResourceDependent ActivityType = "RESOURCE_DEPENDENT"
	LevelOfEffort     ActivityType = "LEVEL_OF_EFFORT"
	StartMilestone    ActivityType = "START_MILESTONE"
	FinishMilestone   ActivityType = "FINISH_MILESTONE"
)

// TimeInterval represents minutes from midnight [Start, End).
// E.g., 08:00 - 12:00 is {Start: 480, End: 720}.
type TimeInterval struct {
	StartMinute int `json:"start"`
	EndMinute   int `json:"end"`
}

func (i TimeInterval) DurationMinutes() int {
	return i.EndMinute - i.StartMinute
}

// DaySchedule defines the working windows for a 24-hour day.
type DaySchedule struct {
	IsWorking bool
	Shifts    []TimeInterval
}

// Calendar represents a resolved, in-memory calendar.
type Calendar struct {
	ID             string
	Name           string
	Scope          CalendarScope
	ProjectID      *string
	ParentID       *string
	WeeklyPatterns [7]DaySchedule          // 0 = Sunday, 1 = Monday ... 6 = Saturday
	Exceptions     map[string]DaySchedule  // Key: "YYYY-MM-DD"
	HoursPerDay    float64
}

// Resource represents a worker, crew, or machine.
type Resource struct {
	ID         string
	Name       string
	CalendarID string
}

// ResourceAssignment joins an Activity to a Resource.
type ResourceAssignment struct {
	ResourceID string
	IsPrimary  bool
}

// Activity represents a scheduled CPM node.
type Activity struct {
	ID                     string
	ProjectID              string
	Name                   string
	CalendarID             string
	Type                   ActivityType
	PlannedDurationMinutes int
	EarlyStart             time.Time
	EarlyFinish            time.Time
}
```

### 4.2 The Calendar Resolution Engine

```go
// CalendarResolver inspects activity rules and resolves the governing calendar.
type CalendarResolver struct {
	calendars map[string]*Calendar
	resources map[string]*Resource
}

func NewCalendarResolver(cals map[string]*Calendar, res map[string]*Resource) *CalendarResolver {
	return &CalendarResolver{
		calendars: cals,
		resources: res,
	}
}

// ResolveGoverningCalendar determines which calendar dictates activity scheduling.
func (r *CalendarResolver) ResolveGoverningCalendar(
	act Activity, 
	assignments []ResourceAssignment,
) (*Calendar, error) {
	// Rule 1: Task Dependent activities ALWAYS follow the Activity Calendar
	if act.Type == TaskDependent || act.Type == LevelOfEffort || act.Type == StartMilestone || act.Type == FinishMilestone {
		cal, exists := r.calendars[act.CalendarID]
		if !exists {
			return nil, fmt.Errorf("activity calendar %s not found for activity %s", act.CalendarID, act.ID)
		}
		return cal, nil
	}

	// Rule 2: Resource Dependent activities follow the Primary Resource's Calendar
	if act.Type == ResourceDependent {
		if len(assignments) == 0 {
			// Fallback: If no resource is assigned, fall back to activity calendar with warning
			cal, exists := r.calendars[act.CalendarID]
			if !exists {
				return nil, fmt.Errorf("fallback activity calendar %s not found", act.CalendarID)
			}
			return cal, nil
		}

		// Find the primary resource
		var primaryResID string
		for _, a := range assignments {
			if a.IsPrimary {
				primaryResID = a.ResourceID
				break
			}
		}

		// If no resource is flagged primary, default to the first assigned resource
		if primaryResID == "" {
			primaryResID = assignments[0].ResourceID
		}

		res, exists := r.resources[primaryResID]
		if !exists {
			return nil, fmt.Errorf("primary resource %s not found", primaryResID)
		}

		resCal, exists := r.calendars[res.CalendarID]
		if !exists {
			return nil, fmt.Errorf("resource calendar %s not found for resource %s", res.CalendarID, res.ID)
		}

		return resCal, nil
	}

	return nil, errors.New("unrecognized activity type")
}
```

### 4.3 Interval Walking Forward Pass Engine

Once the governing calendar is resolved, the forward pass computes `EarlyFinish` by walking forward through the active calendar's working intervals:

```go
// AddWorkMinutes walks forward along the given calendar to consume work duration.
func (c *Calendar) AddWorkMinutes(start time.Time, durationMinutes int) (time.Time, error) {
	if durationMinutes <= 0 {
		return start, nil
	}

	remaining := durationMinutes
	curr := start

	// Safety watchdog: prevent infinite loops on broken calendars (e.g., 0 working hours)
	loopCount := 0
	const maxIterations = 3650 // 10 years limit

	for remaining > 0 {
		loopCount++
		if loopCount > maxIterations {
			return time.Time{}, errors.New("calendar forward walk exceeded 10-year limit: calendar may have zero working minutes")
		}

		dateKey := curr.Format("2006-01-02")
		daySchedule := c.getEffectiveDaySchedule(curr, dateKey)

		if !daySchedule.IsWorking || len(daySchedule.Shifts) == 0 {
			// Advance to midnight of the next day
			curr = time.Date(curr.Year(), curr.Month(), curr.Day()+1, 0, 0, 0, 0, curr.Location())
			continue
		}

		// Current minute of the day [0..1439]
		currMin := curr.Hour()*60 + curr.Minute()

		// Walk through daily shifts
		consumedToday := false
		for _, shift := range daySchedule.Shifts {
			if currMin >= shift.EndMinute {
				// We are already past this shift window
				continue
			}

			// If current time is before shift start, snap to shift start
			shiftEffectiveStart := shift.StartMinute
			if currMin > shift.StartMinute {
				shiftEffectiveStart = currMin
			}

			availableInShift := shift.EndMinute - shiftEffectiveStart

			if remaining <= availableInShift {
				// Work completes inside this shift!
				finishMin := shiftEffectiveStart + remaining
				hour := finishMin / 60
				min := finishMin % 60
				return time.Date(curr.Year(), curr.Month(), curr.Day(), hour, min, 0, 0, curr.Location()), nil
			}

			// Consume entire remaining shift
			remaining -= availableInShift
			currMin = shift.EndMinute
			consumedToday = true
		}

		// Advance to midnight of next day
		curr = time.Date(curr.Year(), curr.Month(), curr.Day()+1, 0, 0, 0, 0, curr.Location())
		_ = consumedToday
	}

	return curr, nil
}

// getEffectiveDaySchedule checks date exceptions first, then falls back to weekly pattern.
func (c *Calendar) getEffectiveDaySchedule(t time.Time, dateKey string) DaySchedule {
	if override, exists := c.Exceptions[dateKey]; exists {
		return override
	}
	dayOfWeek := int(t.Weekday())
	return c.WeeklyPatterns[dayOfWeek]
}
```

### 5.1 Scenario 1: The Piling Rig Breakdown & Overhaul (Task vs Resource Dependent)

#### Context:
* **Activity:** `ACT-101: Piling Row B1-B10`
* **Planned Work Content:** 20 Working Hours.
* **Start Time:** Friday, 07:00 AM.
* **Activity Calendar:** `Surya Site Civil` (6-Day: Mon-Sat, 07:00–12:00 & 13:00–18:00, 10h/day).
* **Primary Resource Assigned:** `Bauer Piling Rig #1`.
* **Resource Calendar:** `Bauer Rig Maint` (4-Day: Tue-Fri 10h/day; Sat-Mon Non-working for diesel overhaul).

#### Case A: Activity is Configured as `TASK_DEPENDENT`
1. **Governing Calendar:** `Surya Site Civil` (Activity Calendar).
2. **Friday:**
   - 07:00 to 12:00 = 5h.
   - 13:00 to 18:00 = 5h.
   - Total Friday = 10h. Remaining = 10h.
3. **Saturday:**
   - Site civil calendar is working on Saturday!
   - 07:00 to 12:00 = 5h.
   - 13:00 to 18:00 = 5h.
   - Total Saturday = 10h. Remaining = 0h.
4. **Early Finish Timestamp:** **Saturday at 18:00**.
5. **Contractual Impact:** Activity is legally scheduled to finish Saturday evening.
6. **Field Reality Conflict:** The Bauer Rig maintenance schedule is violated. The scheduler sees a resource overallocation flag for Saturday on Bauer Rig #1.

#### Case B: Activity is Configured as `RESOURCE_DEPENDENT`
1. **Governing Calendar:** `Bauer Rig Maint` (Resource Calendar).
2. **Friday:**
   - 07:00 to 18:00 = 10h consumed. Remaining = 10h.
3. **Saturday:** Non-working on Bauer Rig calendar. Consumed = 0h.
4. **Sunday:** Non-working on Bauer Rig calendar. Consumed = 0h.
5. **Monday:** Non-working on Bauer Rig calendar. Consumed = 0h.
6. **Tuesday:**
   - Rig resumes operations at 07:00!
   - 07:00 to 18:00 = 10h consumed. Remaining = 0h.
7. **Early Finish Timestamp:** **Tuesday at 18:00**.
8. **Contractual Impact:** The activity finish date slips by **3 full calendar days** (from Saturday to Tuesday)!

## 7. Summary & Key Takeaways

1. **The 3-Tier Enterprise Calendar Model** enforces clean separation of concerns:
   - **Global Calendars:** Enterprise-wide standards governed centrally.
   - **Project Calendars:** Project-specific operating shifts and weather curfews.
   - **Resource Calendars:** Machine maintenance cycles and specialist work schedules.
2. **Activity Type governs precedence:**
   - `TASK_DEPENDENT` ignores resource calendars for dates. The activity calendar reigns supreme.
   - `RESOURCE_DEPENDENT` stretches and shifts activity dates to match the primary resource's availability.
3. **Database Architecture:**
   - In production, use a hybrid prototypal snapshot architecture with explicit `calendar_scope` constraints.
   - Store shift windows in normalized minute-resolution intervals (`0..1440`).
4. **Performance:**
   - The Go engine uses interval walking across effective day schedules.
   - Date exceptions take precedence over repeating 7-day cyclical patterns.
