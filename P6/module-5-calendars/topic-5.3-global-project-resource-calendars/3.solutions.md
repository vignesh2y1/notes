## 🧠 Section A: Conceptual & Precedence Foundations

### Solution 1: The 3-Tier Enterprise Calendar Model & Isolation Hazards

#### 1. Three Major Failures of a Flat (Single-Tier) Calendar Model:
* **Failure 1: Unintended Cross-Project Contamination (Cascade Corruption):**  
  In a multi-project enterprise EPC firm, hundreds of active projects share the database. If project-level schedulers can freely edit calendars that other projects rely on, a scheduler adding a local monsoon shutdown to a "Standard 6-Day Calendar" for a desert solar project in Rajasthan will inadvertently halt engineering and procurement schedules for an indoor substation in Mumbai or an offshore wind farm in Gujarat.
* **Failure 2: Destruction of Legal Baseline Integrity & Claims Protection:**  
  In mega-construction projects, contractual disputes (such as delay analysis under FIDIC or NEC4 contracts) require defending an approved Schedule Baseline against owner interference or liquidated damages claims. If enterprise PMO administrators update corporate holidays (e.g., adding an ad-hoc government mourning day) and this silently modifies an already baselined project calendar, the calculated early/late dates and critical path float change without an official change order, destroying the contractor’s legal defense in delay litigation.
* **Failure 3: Conflation of Site Working Rhythms with Resource Asset Constraints:**  
  A project site has an operational rhythm dictated by local labor laws, daylight, and climate (e.g., 6 days/week, 10 hours/day). Specialized assets (e.g., a 250-ton mobile crawler crane or an offshore pipelaying vessel) have independent maintenance overhaul schedules, mobilization windows, or multi-site sharing constraints. Storing them in a single flat tier forces schedulers either to duplicate hundreds of identical site calendars or to distort site calendars to reflect a single machine's downtime.

#### 2. Legal Scenario Where Global Changes Must NOT Alter Active Projects:
* **Case Study:** In an EPC contract for the Surya 100MW Solar IPP, the baseline schedule was approved by the Owner (Rajasthan Rajya Vidyut Utpadan Nigam) on 01-January. The contract stipulates liquidated damages of \$50,000 per calendar day of delay past the Commercial Operation Date (COD).
* In June, the corporate holding company updates its Global Corporate Calendar to observe a newly gazetted state cultural holiday.
* If this global change automatically propagated to the active Surya project calendar:
  - Total Float on the critical substation commissioning path would drop by 1 day.
  - The scheduled completion date would slip by 24 hours.
  - The owner could claim delay or reject monthly milestone billing because the schedule deviates from the contractually baselined schedule without a formal change order.
* Therefore, **Project Calendars must either be deep-copied (cloned) at baseline freeze or maintain an immutable baseline snapshot**.

#### 3. Resource Calendars vs. Project Calendars:
* **Scope:** A Project Calendar is scoped to the physical project boundary (e.g., Bhadla Solar Park). A Resource Calendar is bound to an individual asset (laborer, engineer, subcontractor, crane, rig) that may move across multiple projects.
* **Lifecycle:** A Project Calendar exists for the duration of the project. A Resource Calendar persists across the resource's employment or equipment leasing lifecycle.
* **Scheduling Impact:** A Project Calendar dictates site availability for `TASK_DEPENDENT` activities. A Resource Calendar dictates availability for `RESOURCE_DEPENDENT` activities and resource leveling calculations across the enterprise portfolio.

### Solution 2: Task Dependent vs. Resource Dependent Precedence Mechanics

#### 1. Formal Precedence Rules:
* **Task Dependent (`TASK_DEPENDENT`):**
  $$\text{Governing Calendar} = \mathcal{C}_{\text{Activity}}$$
  The activity's early/late dates and duration are computed exclusively via the Activity Calendar ($\mathcal{C}_{\text{Activity}}$). Assigned resource calendars are completely ignored during forward and backward CPM passes. If an assigned resource is unavailable on an activity work day, the engine flags a **Resource Overallocation**, but does **not** adjust the activity dates.
* **Resource Dependent (`RESOURCE_DEPENDENT`):**
  $$\text{Governing Calendar} = \mathcal{C}_{\text{Primary Resource}}$$
  The activity's early/late dates and duration are computed exclusively via the calendar of the assigned Primary Resource ($\mathcal{C}_{\text{Primary Resource}}$). The Activity Calendar is ignored for date arithmetic. The activity work days stretch, pause, and resume according to the resource's working intervals.

#### 2. Comparative Calculation (40 Working Hours, Starts Monday 08:00):
* **Inputs:**
  - Work Duration: $D = 40\text{ hours}$.
  - Activity Calendar: 6-Day (Mon–Sat, 10h/day: 08:00–18:00).
  - Primary Resource Calendar: 4-Day (Mon–Thu, 10h/day: 08:00–18:00; Fri–Sun Non-working).

* **Case A: `TASK_DEPENDENT`:**
  - Monday: 08:00–18:00 $\rightarrow 10\text{h}$ consumed. Remaining = $30\text{h}$.
  - Tuesday: 08:00–18:00 $\rightarrow 10\text{h}$ consumed. Remaining = $20\text{h}$.
  - Wednesday: 08:00–18:00 $\rightarrow 10\text{h}$ consumed. Remaining = $10\text{h}$.
  - Thursday: 08:00–18:00 $\rightarrow 10\text{h}$ consumed. Remaining = $0\text{h}$.
  - **Early Finish:** **Thursday at 18:00**.
  - **Chronological Days:** 4 days (Mon, Tue, Wed, Thu).
  - **Resource Impact:** Because the activity finishes on Thursday at 18:00, the resource worked within its Mon–Thu shift. No conflict on Friday or Saturday occurs. (If the task were 50 hours, it would work Friday 10h on the Activity Calendar, creating a resource overallocation flag on the 4-day resource).

* **Case B: `RESOURCE_DEPENDENT` (Same duration = 40 hours):**
  - Monday: 10h consumed.
  - Tuesday: 10h consumed.
  - Wednesday: 10h consumed.
  - Thursday: 10h consumed.
  - **Early Finish:** **Thursday at 18:00** (Same finish because 40 hours fits inside Mon–Thu).
  - *What if duration were 50 hours?*
    - Under `TASK_DEPENDENT`: Finishes **Friday at 18:00** (5 calendar days).
    - Under `RESOURCE_DEPENDENT`: Thursday leaves 10h remaining. Fri, Sat, Sun are non-working on Resource Calendar. Work resumes Monday at 08:00 and finishes **Monday at 18:00** (8 calendar days elapsed, a 72-hour delay!).

### Solution 3: The Multi-Resource Dilemma and Primary Resource Governance

#### 1. The "Primary Resource Rule" in Primavera P6:
When an activity requires multiple resources (e.g., a crane, a crane operator, and a rigging engineer), each resource may possess a distinct working calendar. If an activity is `RESOURCE_DEPENDENT`, whose calendar governs?
* Primavera P6 designates exactly **one** resource on the assignment list as the **Primary Resource**.
* The Primary Resource’s calendar becomes the single source of truth for the activity's early/late dates and duration.
* **Why this is necessary:** In construction, one critical asset (e.g., the 150-ton heavy crane) is typically the pacing asset; secondary labor resources (riggers, spotters) are scheduled around it. Choosing a single governing calendar avoids mathematical over-constraint and circular dependencies.

#### 2. Dates Under `Heavy Crane 150T` Governance:
* `Heavy Crane 150T` operates Tue–Sat (08:00–17:00). Monday is non-working maintenance.
* If the rigging activity starts Tuesday morning at 08:00:
  - Tuesday through Saturday are working days.
  - Sunday and Monday are non-working days.
  - The activity will work across Tue–Sat, pause on Sun–Mon, and resume on Tuesday.
  - Secondary resources (`Crane Operator Ashok` who is off on Saturday, and `Rigging Engineer Vijay` who is off on Sunday) will show resource overallocation conflicts on Saturday.

#### 3. Mathematical Intersection Scheduling & The Deadlock Hazard:
* If the engine enforces the **joint intersection** ($\mathcal{C}_{\text{joint}} = \mathcal{C}_{\text{Ashok}} \cap \mathcal{C}_{\text{Vijay}} \cap \mathcal{C}_{\text{Crane}}$):
  - Ashok works: Mon–Fri.
  - Vijay works: Mon–Sat.
  - Crane works: Tue–Sat (Mon is maintenance).
  - **Intersection:** Only days when ALL THREE are working = **Tuesday, Wednesday, Thursday, Friday** (4 days/week).
* **Deadlock / Infinite Duration Hazard:**
  - Suppose Ashok works Monday–Wednesday, and the Crane is only available Thursday–Saturday.
  - The intersection $\mathcal{C}_{\text{Ashok}} \cap \mathcal{C}_{\text{Crane}} = \emptyset$ (empty set: zero overlapping minutes in the entire week!).
  - If the engine attempts an interval walk on an empty intersection calendar:
    $$\int_t^\infty W_{\cap}(\tau) \, d\tau = 0 < D_{\text{work}}$$
    The engine enters an infinite loop or walks to the end of the 10-year planning horizon, resulting in **computational deadlock and schedule explosion**. This is why commercial scheduling engines mandate the Primary Resource Rule rather than blind set intersection!

### Solution 7: Snapshot vs. Delta-Inheritance in PostgreSQL

#### 1. PostgreSQL DDL for Delta-Inheritance:
```sql
CREATE TABLE calendars (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    enterprise_id UUID NOT NULL,
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    parent_calendar_id UUID REFERENCES calendars(id) ON DELETE RESTRICT,

);

CREATE TABLE calendar_weekly_patterns (
    calendar_id UUID REFERENCES calendars(id) ON DELETE CASCADE,
    day_of_week SMALLINT NOT NULL CHECK (day_of_week BETWEEN 0 AND 6),
    is_working BOOLEAN NOT NULL,
    shifts JSONB NOT NULL DEFAULT '[]'::jsonb,
    PRIMARY KEY (calendar_id, day_of_week)
);

CREATE TABLE calendar_exceptions (
    calendar_id UUID REFERENCES calendars(id) ON DELETE CASCADE,
    exception_date DATE NOT NULL,
    override_type VARCHAR(20) NOT NULL CHECK (override_type IN ('WORKING', 'NON_WORKING', 'CUSTOM_HOURS')),
    custom_shifts JSONB DEFAULT '[]'::jsonb,
    PRIMARY KEY (calendar_id, exception_date)
);
```

#### 2. Recursive CTE Query for Effective Day Resolution:
```sql
WITH RECURSIVE cal_hierarchy AS (
    -- Anchor member: Target calendar
    SELECT id, parent_calendar_id, 1 AS depth
    FROM calendars
    WHERE id = 'c0a80123-0000-0000-0000-000000000001' -- cal_site_civil_01
    
    UNION ALL
    
    -- Recursive member: Traverse up to parent (global)
    SELECT c.id, c.parent_calendar_id, ch.depth + 1
    FROM calendars c
    JOIN cal_hierarchy ch ON c.id = ch.parent_calendar_id
)
-- Step 1: Look for date exceptions first (Child overrides Parent)
SELECT 
    e.exception_date,
    e.override_type,
    e.custom_shifts,
    'EXCEPTION' AS source_tier
FROM cal_hierarchy ch
JOIN calendar_exceptions e ON e.calendar_id = ch.id
WHERE e.exception_date = '2026-10-02'
ORDER BY ch.depth ASC
LIMIT 1;
```

#### 3. Architectural Comparison:
* **Query Performance:** Snapshot pattern is $O(1)$ direct lookup; Delta-Inheritance requires recursive CTE joining across hierarchy tiers ($O(K)$ where $K$ is depth).
* **Concurrency & Lock Contention:** Updating a Global calendar in Delta-Inheritance can trigger massive database locks or cascade recalculations across thousands of active activities. Snapshot keeps projects isolated.
* **Auditability:** Snapshot guarantees that a baselined schedule remains exactly as it was when approved by the court or owner.

### Solution 8: Enforcing Primary Resource Constraints in PostgreSQL

#### 1. Why `UNIQUE(activity_id, is_primary)` Fails:
A unique constraint on `(activity_id, is_primary)` allows only **one row** where `is_primary = TRUE` AND only **one row** where `is_primary = FALSE`. If an activity needs 5 non-primary laborers, inserting the second row with `is_primary = FALSE` throws a unique constraint violation!

#### 2. The PostgreSQL Partial Unique Index:
```sql
-- Create a partial unique index that only enforces uniqueness when is_primary IS TRUE
CREATE UNIQUE INDEX uq_single_primary_resource_per_activity
ON activity_resource_assignments (activity_id)
WHERE is_primary = TRUE;
```
* **Why this works:** PostgreSQL partial indexes only index rows satisfying the `WHERE` predicate. Multiple rows with `is_primary = FALSE` are ignored by the index, while a second row with `is_primary = TRUE` for the same `activity_id` is immediately rejected.

#### 3. Validation When `RESOURCE_DEPENDENT` Has Zero Resources:
* **Application Layer:** During validation, if `act.activity_type == 'RESOURCE_DEPENDENT'` and `len(assignments) == 0`:
  1. Emit an explicit validation error if saving/publishing the schedule: `"Cannot schedule Resource Dependent activity without assigned resources."`
  2. If running the CPM engine, fall back gracefully to `act.calendar_id` while logging an `EngineWarning` to the schedule audit log.

## 💻 Section D: Golang Engine & Algorithmic Implementation

### Solution 9: Implementing `ResolveGoverningCalendar`

```go
package calendar

import (
	"errors"
	"fmt"
)

type CalendarRepository interface {
	GetCalendarByID(id string) (*Calendar, error)
}

type ResourceRepository interface {
	GetResourceByID(id string) (*Resource, error)
}

// ResolveGoverningCalendar resolves the governing calendar according to P6 precedence rules.
func ResolveGoverningCalendar(
	act Activity,
	assignments []ResourceAssignment,
	calRepo CalendarRepository,
	resRepo ResourceRepository,
) (*Calendar, error) {
	// Rule 1: Task Dependent activities use Activity Calendar
	if act.Type == TaskDependent || act.Type == LevelOfEffort ||
		act.Type == StartMilestone || act.Type == FinishMilestone {
		cal, err := calRepo.GetCalendarByID(act.CalendarID)
		if err != nil {
			return nil, fmt.Errorf("failed to fetch activity calendar %s: %w", act.CalendarID, err)
		}
		return cal, nil
	}

	// Rule 2: Resource Dependent activities
	if act.Type == ResourceDependent {
		if len(assignments) == 0 {
			// Fallback to activity calendar
			cal, err := calRepo.GetCalendarByID(act.CalendarID)
			if err != nil {
				return nil, fmt.Errorf("fallback activity calendar %s failed: %w", act.CalendarID, err)
			}
			return cal, nil
		}

		// Find primary resource
		var primaryResID string
		for _, a := range assignments {
			if a.IsPrimary {
				primaryResID = a.ResourceID
				break
			}
		}

		// If no primary designated, default to first resource
		if primaryResID == "" {
			primaryResID = assignments[0].ResourceID
		}

		res, err := resRepo.GetResourceByID(primaryResID)
		if err != nil {
			return nil, fmt.Errorf("failed to fetch primary resource %s: %w", primaryResID, err)
		}

		resCal, err := calRepo.GetCalendarByID(res.CalendarID)
		if err != nil {
			return nil, fmt.Errorf("failed to fetch resource calendar %s for resource %s: %w", res.CalendarID, res.ID, err)
		}

		return resCal, nil
	}

	return nil, errors.New("unknown activity type")
}
```

### Solution 10: Multi-Resource Calendar Intersection Engine

#### 1. Mathematical Intersection:
$$S_{\cap} = \{ [s_k, e_k) \mid \forall t \in [s_k, e_k), W_1(t) = 1 \land W_2(t) = 1 \}$$

#### 2. Golang Implementation:
```go
package calendar

// IntersectDaySchedules computes the exact overlapping working windows of two schedules.
func IntersectDaySchedules(s1, s2 DaySchedule) DaySchedule {
	if !s1.IsWorking || !s2.IsWorking || len(s1.Shifts) == 0 || len(s2.Shifts) == 0 {
		return DaySchedule{IsWorking: false, Shifts: nil}
	}

	var overlapping []TimeInterval

	i, j := 0, 0
	for i < len(s1.Shifts) && j < len(s2.Shifts) {
		shift1 := s1.Shifts[i]
		shift2 := s2.Shifts[j]

		// Overlap start is max of starts; overlap end is min of ends
		overlapStart := max(shift1.StartMinute, shift2.StartMinute)
		overlapEnd := min(shift1.EndMinute, shift2.EndMinute)

		if overlapStart < overlapEnd {
			overlapping = append(overlapping, TimeInterval{
				StartMinute: overlapStart,
				EndMinute:   overlapEnd,
			})
		}

		// Advance the interval that ends earlier
		if shift1.EndMinute < shift2.EndMinute {
			i++
		} else {
			j++
		}
	}

	if len(overlapping) == 0 {
		return DaySchedule{IsWorking: false, Shifts: nil}
	}

	return DaySchedule{
		IsWorking: true,
		Shifts:    overlapping,
	}
}

func min(a, b int) int {
	if a < b {
		return a
	}
	return b
}

func max(a, b int) int {
	if a > b {
		return a
	}
	return b
}
```

#### 3. Test Evaluation:
* **Schedule 1:** `[{Start: 420, End: 720}, {Start: 780, End: 1080}]` (07:00–12:00, 13:00–18:00)
* **Schedule 2:** `[{Start: 540, End: 900}]` (09:00–15:00)
* **Step-by-step intersection:**
  - `shift1 = [420, 720]`, `shift2 = [540, 900]`:  
    Overlap: $[\max(420, 540), \min(720, 900)] = [540, 720]$ (09:00 to 12:00 = 180 min).  
    Shift 1 ends first ($720 < 900$), increment $i$.
  - `shift1 = [780, 1080]`, `shift2 = [540, 900]`:  
    Overlap: $[\max(780, 540), \min(1080, 900)] = [780, 900]$ (13:00 to 15:00 = 120 min).  
    Shift 2 ends first ($900 < 1080$), increment $j$. Loop terminates.
* **Resulting Intersected Schedule:**
  `[{Start: 540, End: 720}, {Start: 780, End: 900}]`  
  Total Working Minutes = $180 + 120 = 300\text{ minutes (5.0 hours)}$.

### Solution 11: Detecting Overallocation on Task Dependent Activities

```go
package calendar

import (
	"fmt"
	"time"
)

type ConflictReport struct {
	ResourceID      string
	Date            string
	DemandedMinutes int
	AvailableMinutes int
	ConflictReason  string
}

// DetectResourceConflicts audits an assigned resource against a task-dependent activity schedule.
func DetectResourceConflicts(
	act Activity,
	res Resource,
	actCal Calendar,
	resCal Calendar,
) []ConflictReport {
	var reports []ConflictReport

	// Walk day-by-day from EarlyStart to EarlyFinish
	currDate := time.Date(act.EarlyStart.Year(), act.EarlyStart.Month(), act.EarlyStart.Day(), 0, 0, 0, 0, act.EarlyStart.Location())
	endDate := time.Date(act.EarlyFinish.Year(), act.EarlyFinish.Month(), act.EarlyFinish.Day(), 0, 0, 0, 0, act.EarlyFinish.Location())

	for !currDate.After(endDate) {
		dateKey := currDate.Format("2006-01-02")

		actDay := actCal.getEffectiveDaySchedule(currDate, dateKey)
		resDay := resCal.getEffectiveDaySchedule(currDate, dateKey)

		// Calculate demanded minutes on this day
		demandedMin := 0
		if actDay.IsWorking {
			for _, shift := range actDay.Shifts {
				demandedMin += (shift.EndMinute - shift.StartMinute)
			}
		}

		if demandedMin > 0 {
			availableMin := 0
			if resDay.IsWorking {
				for _, shift := range resDay.Shifts {
					availableMin += (shift.EndMinute - shift.StartMinute)
				}
			}

			if !resDay.IsWorking {
				reports = append(reports, ConflictReport{
					ResourceID:       res.ID,
					Date:             dateKey,
					DemandedMinutes:  demandedMin,
					AvailableMinutes: 0,
					ConflictReason:   fmt.Sprintf("Resource is on NON-WORKING day; activity demands %d min", demandedMin),
				})
			} else if availableMin < demandedMin {
				reports = append(reports, ConflictReport{
					ResourceID:       res.ID,
					Date:             dateKey,
					DemandedMinutes:  demandedMin,
					AvailableMinutes: availableMin,
					ConflictReason:   fmt.Sprintf("Resource capacity deficit: demanded %d min, available %d min", demandedMin, availableMin),
				})
			}
		}

		currDate = currDate.AddDate(0, 0, 1)
	}

	return reports
}
```
