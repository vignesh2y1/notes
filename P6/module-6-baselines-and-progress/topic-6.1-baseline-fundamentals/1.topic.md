# Topic 6.1: Baseline Fundamentals — The Frozen Anchor of Reality

## 1. Executive Summary & The Core Mental Model

### 1.1 The Axiom: The Moving Goalposts Fallacy
In amateur project management, schedules are frequently treated as live, fluid documents where dates update every week to reflect what actually happened on site. When a construction task slips by two weeks, the project coordinator simply drags the Gantt bar forward by two weeks or enters a new planned start date. 

To an uninformed observer, the project looks organized: every activity has a clean date, the CPM forward pass calculates without errors, and no activities appear in the past. 

In enterprise project controls and commercial contracting, this practice is known as **"moving the goalposts."**

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                 THE MOVING GOALPOSTS FALLACY                                     │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  Week 0 (Contract Award):                                                                        │
│  [Target COD: 31-Dec-2026] ◄───────────────────────────────────── Approved Milestone Anchor      │
│  ├── Inverter Foundation [01-May ────► 15-May]                                                   │
│                                                                                                  │
│  Week 20 (Un-baselined Live Schedule after 14-day delay):                                        │
│  Contractor quietly drags foundation dates forward:                                              │
│  ├── Inverter Foundation [15-May ────► 29-May]                                                   │
│  └── Substation Commissioning [01-Dec ────► 14-Jan-2027]                                         │
│                                                                                                  │
│  WITHOUT A FROZEN BASELINE:                                                                      │
│  * The delay is invisible on the live screen because variance = 0 (Current - Current = 0).       │
│  * The Owner cannot prove contractor delay.                                                      │
│  * The Contractor cannot prove owner-caused delay or claim Extension of Time (EOT).             │
│  * Liquidated Damages (LDs) of ₹5,00,000/day cannot be contractually enforced!                   │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

> **The Fundamental Axiom of Project Controls:**  
> A schedule without a frozen baseline is not a control tool; it is merely a dynamic diary of current intentions. You cannot calculate variance, measure slip, evaluate earned value, or adjudicate delay claims without an immutable benchmark.

### 1.2 Plain-English Intuition: The Git Commit Hash Analogy
If you are a software engineer building backend systems in Go, think of a **Baseline** as an immutable **Git Release Tag** or **Frozen Snapshot**:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                 THE GIT BRANCH VS BASELINE MENTAL MODEL                          │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  Git VCS:                                                                                        │
│  ┌────────────────────────┐      git tag v1.0.0 (Frozen Commit Hash: 8f3a9e)                     │
│  │   main (Live Branch)   │ ──► [v1.0.0 Snapshot] ─── (Immutable anchor in git object store)     │
│  └──────────┬─────────────┘                                                                      │
│             │ git commit (daily edits, rebases, bug fixes)                                       │
│             ▼                                                                                    │
│     Working Tree Drift ───► git diff v1.0.0 HEAD (Computes exact line-by-line drift!)            │
│                                                                                                  │
│  Primavera P6:                                                                                   │
│  ┌────────────────────────┐      "Maintain Baselines" (Frozen Project Clone: proj_id = 9021)     │
│  │ Live Working Forecast  │ ──► [Target 1 / B1 Snapshot] ─── (Write-protected deep clone)        │
│  └──────────┬─────────────┘                                                                      │
│             │ F9 Schedule (daily progress, logic changes, duration updates)                      │
│             ▼                                                                                    │
│     Forecast Drift     ───► Variance = Current Early Finish - Baseline Finish                    │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

When you cut a release in Git (`git tag -a v1.0.0`), you don't stop developing on `main`. You keep committing features and bug fixes. However, whenever you want to know what changed, you run `git diff v1.0.0 HEAD`. The tag `v1.0.0` never mutates; it remains frozen in the object store for eternity.

A **Primavera P6 Baseline** is identical in philosophy: it is an immutable, frozen snapshot of the entire project model (WBS, activities, relationships, resources, costs, calendars, and planned dates) captured at a critical contractual junction. As the live schedule moves forward through time, the baseline stays anchored in place, providing the fixed coordinate system against which all drift is calculated.

If monsoon flash floods wash out the desert access roads in July, or if the 220kV power transformer delivery slips from Germany, the project team does **not** erase the baseline. They record progress against the live schedule and use B1 to prove the exact time and cost impact.

## 2. Taxonomy of Baselines in Enterprise Project Controls

In enterprise construction and defense engineering, you never manage just a single baseline over a three-year lifecycle. P6 supports multiple classes of baselines to serve different contractual and internal stakeholders:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                   ENTERPRISE BASELINE TAXONOMY                                   │
├───────────────────────────────┬──────────────────────────────────┬───────────────────────────────┤
│ Baseline Category             │ Primary Stakeholders             │ Governance & Change Rules     │
├───────────────────────────────┼──────────────────────────────────┼───────────────────────────────┤
│ 1. Contract Award Baseline    │ Owner, Lenders, EPC Contractor,  │ Strictly frozen. Can ONLY be  │
│    (Target 1 / Initial B1)    │ Independent Engineer (IE)        │ altered via approved EOT claim│
├───────────────────────────────┼──────────────────────────────────┼───────────────────────────────┤
│ 2. Live Working Forecast      │ Project Controls, Field Supts,   │ Updated weekly/monthly.       │
│    (Current Schedule)         │ Package Managers                 │ Logic and durations fluctuate │
├───────────────────────────────┼──────────────────────────────────┼───────────────────────────────┤
│ 3. Approved Re-Baseline       │ Client Executive Committee,      │ Replaces B1 as the operational│
│    (Revised Target / B2)      │ Bank Consortium, PMO             │ target after formal scope change│
├───────────────────────────────┼──────────────────────────────────┼───────────────────────────────┤
│ 4. What-If Scenario Baselines │ Delay Forensic Experts, Planners,│ Sandboxed clones. Used to test│
│    (Impacted As-Planned)      │ Dispute Adjudication Board       │ mitigation or claims scenarios│
└───────────────────────────────┴──────────────────────────────────┴───────────────────────────────┘
```

### 2.1 Contract Award Baseline (Target 1 / Initial Baseline)
This is the schedule agreed upon at contract signing. It represents the legal commitment between the Owner (Surya Green Energy Ltd.) and the EPC Contractor (Bharat Solar Infrastructure Ltd.).
* **Legal Status:** Admissible in arbitration courts and Dispute Adjudication Boards (DAB).
* **Immutability:** Absolute. No user, not even the Project Director, can edit dates, add relationships, or alter durations in this snapshot without a formal contractual amendment.
* **Liquidated Damages Anchor:** All delay penalties ($LD = \text{Days Overdue} \times ₹5,00,000$) are measured relative to the finish dates in this baseline.

### 2.2 Live Working Forecast (Current Operating Plan)
The live schedule is the dynamic model where project controls engineers perform status updates:
* Field engineers enter Actual Start dates, Actual Finish dates, and Remaining Durations.
* Planners run the CPM scheduling engine (the `F9` key in P6) to push incomplete activities forward past the current **Data Date (Status Date)**.
* Logic ties are adjusted to reflect real-world site workarounds (e.g., fast-tracking civil piling in Block B while waiting for access in Block A).

### 2.3 Approved Re-Baseline (Revised Baseline / B2)
What happens when the Owner issues a formal Change Order adding 20MW of Battery Energy Storage (BESS) to the solar plant, adding 4 months of work and expanding contract value by ₹40 Crore?
* Trying to evaluate performance against the original 100MW B1 baseline would show an artificial 4-month delay across the entire site.
* The Project Steering Committee approves an **Extension of Time (EOT)** and authorizes **Baseline 2 (B2)**.
* Crucially, **B1 is not overwritten**! In P6, B1 is preserved in the archive, while B2 is assigned as the active Project Baseline for forward-looking performance reporting.

### 2.4 What-If / Delay Fragnet Baselines (Forensic Analysis)
When a dispute occurs—for example, when the State Transmission Utility (STU) delays the 220kV grid interconnection substation bay handover by 45 days—the contractor's claims consultant creates a sandboxed baseline clone. They insert the delay event (a "fragnet" of delay activities) into this copy to produce an **Impacted As-Planned** model. This demonstrates the pure causal impact of the Owner delay without polluting the live operating schedule.

### 3.1 Project Baseline: The Enterprise Standard of Record
* **Global Scope:** Set by the Project Director or PMO Lead. When set, every team member, executive dashboard, and external PDF report generated from P6 references this specific baseline.
* **Drives Earned Value Management (EVM):** In P6, **Planned Value (PV / BCWS)** is strictly calculated from the Project Baseline. If an activity in the live schedule has a budget of ₹10,00,000, its planned expenditure curve across time is computed from the Early Start and Early Finish dates stored inside the Project Baseline project.
* **Contractual Milestone Variances:** Official contract milestone compliance columns (`Schedule % Complete`, `Variance - Baseline Project Finish Date`) pull from the Project Baseline.

### 3.2 User Baselines: Multi-Target Analysis
P6 permits each individual user to assign up to three personal baselines:
1. **Primary Baseline (B1):** Commonly set to the Contract Award Baseline.
2. **Secondary Baseline (B2):** Commonly set to the Revised Working Target or Internal Aggressive Contractor Schedule.
3. **Tertiary Baseline (B3):** Commonly set to Last Month's Approved Monthly Update (to calculate month-over-month slip rather than cumulative slip from day one).

## 4. Database Snapshot Mechanics: How P6 Actually Stores Baselines

When software developers first encounter P6, they often assume that creating a baseline simply adds a few date columns to the activity table:
```sql
-- JUNIOR DEVELOPER NAIVE ANTI-PATTERN (DO NOT DO THIS)
ALTER TABLE activities ADD COLUMN baseline_start TIMESTAMP;
ALTER TABLE activities ADD COLUMN baseline_finish TIMESTAMP;
```

This naive approach fails completely in enterprise project management for three critical reasons:
1. **What happens if an activity is deleted in the live project?** If an activity is deleted or its scope is swapped, the naive baseline columns disappear with it! You have lost historical record of what was originally planned.
2. **What happens if logic relationships change?** You cannot perform a retrospective delay analysis because you didn't save the network logic (predecessors, successors, lags) of the baseline.
3. **What happens if resource assignments or budgets change?** Naive date columns cannot preserve the original planned resource loading, man-hour profiles, or cost curves.

### 4.1 The Deep Project Clone Architecture
Primavera P6 solves this with an elegant database design:
> **A Baseline in P6 is not a table column; it is a full, independent, cloned PROJECT record.**

In the P6 database schema (and modern scheduling engines):
* The active project resides in the `PROJECT` table with a primary key `proj_id` (e.g., `1001`).
* When you click **Project -> Maintain Baselines -> Save a copy of the current project as a new baseline**, P6 executes a deep clone transaction.
* It inserts a **new row** into the `PROJECT` table with `proj_id = 9021`, and sets the foreign key `orig_proj_id = 1001`.
* It clones every dependent record associated with that project:
  * Every WBS element in `PROJWBS`
  * Every activity in `TASK`
  * Every logic tie in `TASKPRED`
  * Every resource assignment in `TASKRSRC`
  * Every expense item in `PROJECTEX`
* It sets `is_baseline = true` and writes metadata to a join table `PROJECT_BASELINE` mapping `orig_proj_id -> baseline_proj_id` and tagging its role (`PROJECT`, `B1`, `B2`, `B3`).

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                      P6 DATABASE CLONING ARCHITECTURE (ENTITY RELATIONSHIP)                      │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  TABLE: PROJECT                                                                                  │
│  ┌─────────┬──────────────────────┬──────────────┬──────────────┬──────────────┐                 │
│  │ proj_id │ proj_short_name      │ orig_proj_id │ is_baseline  │ status_code  │                 │
│  ├─────────┼──────────────────────┼──────────────┼──────────────┼──────────────┤                 │
│  │ 1001    │ SURYA-100MW-LIVE     │ NULL         │ FALSE        │ Active       │ ◄── LIVE PLAN   │
│  │ 9021    │ SURYA-100MW-B1-NTP   │ 1001         │ TRUE         │ Inactive     │ ◄── CLONED B1   │
│  │ 9022    │ SURYA-100MW-B2-REVISED│ 1001        │ TRUE         │ Inactive     │ ◄── CLONED B2   │
│  └─────────┴──────────────────────┴──────────────┴──────────────┴──────────────┘                 │
```

### 4.2 Matching Strategy: `task_code` vs Stable `task_uuid`
When the live schedule queries its baseline dates, how does it know which activity in Project `9021` corresponds to an activity in Project `1001`?
* **Legacy P6 Approach:** Matches by `task_code` (e.g., `ACT-CIV-101`). If a user renames an activity ID in the live project, the link breaks!
* **Modern Engine Architecture (Go + Postgres):** Generates a permanent `task_uuid` on creation. When the deep clone runs, the cloned task retains the exact same `task_uuid` (or a `source_task_uuid` foreign key). This guarantees that even if a planner renames an activity ID or moves it to a different WBS node, variance analytics remain 100% stable.

## 5. The Immutability Invariant: Database-Level Protection

In legal disputes involving tens of millions of dollars, schedules submitted in court are scrutinized by forensic delay analysts. If opposing counsel discovers that baseline dates were subtly modified or re-scheduled after contract award, the entire schedule delay claim can be thrown out for spoliation of evidence.

Therefore, an enterprise scheduling engine must enforce the **Immutability Invariant**:
> **Once a project record is flagged as a Baseline (`is_baseline = true`), it must be mathematically and cryptographically impossible for standard application API endpoints or users to modify or delete its rows.**

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                             DATABASE-LEVEL IMMUTABILITY ENFORCEMENT                              │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  Client Request: UPDATE /api/activities/8501  (Target End Date = 2026-05-20)                     │
│                                                                                                  │
│  Application Layer (Go Middleware):                                                              │
│  ┌────────────────────────────────────────────────────────────────────────┐                      │
│  │ CheckProjectRole(proj_id): Is project marked as baseline?              │                      │
│  │ ──► IF is_baseline == true: RETURN 403 Forbidden ("Baseline Immutable")│                      │
│  └───────────────────────────────────┬────────────────────────────────────┘                      │
│                                      │ (Bypassed if rogue admin/DBA runs direct SQL)             │
│                                      ▼                                                           │
│  Database Layer (PostgreSQL Trigger):                                                            │
│  ┌────────────────────────────────────────────────────────────────────────┐                      │
│  │ CREATE TRIGGER trg_enforce_baseline_immutability                       │                      │
│  │ BEFORE UPDATE OR DELETE ON activities                                  │                      │
│  │ FOR EACH ROW EXECUTE FUNCTION check_baseline_lock();                   │                      │
│  │                                                                        │                      │
│  │ IF project.is_baseline THEN                                            │                      │
│  │    RAISE EXCEPTION 'CRITICAL SECURITY VIOLATION: Baseline project %    │                      │
│  │    is write-protected. Modifications strictly prohibited.', proj_id;   │                      │
│  │ END IF;                                                                │                      │
│  └────────────────────────────────────────────────────────────────────────┘                      │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 5.1 The "Restore Baseline" Operation
What if a planner genuinely made a mistake during baseline creation, or needs to open the baseline as an active project to make an approved change?
P6 provides a specific workflow called **"Restore Baseline"**:
1. The user unlinks the baseline from the live project.
2. The database clears the `orig_proj_id` link and sets `is_baseline = false`.
3. The cloned project appears in the main Enterprise Project Structure (EPS) directory as a standard, editable project.
4. The user makes the authorized corrections, logs the audit justification, and runs "Convert to Baseline" to re-freeze and re-attach it.

## 6. Engineering a Scheduling Engine: PostgreSQL & Go Implementation

Let us translate these architectural requirements into production-grade database tables and Go code.

### 6.1 PostgreSQL Schema for Deep Baseline Snapshots

```sql
-- Migration: 006_baselines_architecture.sql

-- 1. Projects table supporting hierarchical parent-child baseline linkage
CREATE TABLE projects (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code VARCHAR(64) NOT NULL UNIQUE,
    name VARCHAR(255) NOT NULL,
    orig_proj_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    is_baseline BOOLEAN NOT NULL DEFAULT FALSE,
    baseline_type VARCHAR(32) CHECK (baseline_type IN ('PROJECT', 'B1', 'B2', 'B3', 'WHAT_IF')),
    data_date TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Index for instant lookup of attached baselines for a live project
CREATE INDEX idx_projects_orig_proj ON projects(orig_proj_id) WHERE is_baseline IS TRUE;

-- 2. Activities table storing planned and calculated dates
CREATE TABLE activities (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    code VARCHAR(64) NOT NULL,
    name VARCHAR(255) NOT NULL,
    original_task_uuid UUID, -- Stable identity across clones
    calendar_id UUID NOT NULL,
    planned_duration_minutes INT NOT NULL,
    target_start TIMESTAMPTZ NOT NULL,
    target_finish TIMESTAMPTZ NOT NULL,
    early_start TIMESTAMPTZ,
    early_finish TIMESTAMPTZ,
    actual_start TIMESTAMPTZ,
    actual_finish TIMESTAMPTZ,
    total_float_minutes INT,
    status VARCHAR(32) NOT NULL DEFAULT 'NOT_STARTED',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_project_activity_code UNIQUE (project_id, code)
);

CREATE INDEX idx_activities_project ON activities(project_id);
CREATE INDEX idx_activities_uuid_lookup ON activities(original_task_uuid);

-- 3. Relationships table for CPM network logic
CREATE TABLE activity_relationships (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    pred_activity_id UUID NOT NULL REFERENCES activities(id) ON DELETE CASCADE,
    succ_activity_id UUID NOT NULL REFERENCES activities(id) ON DELETE CASCADE,
    type VARCHAR(4) NOT NULL CHECK (type IN ('FS', 'SS', 'FF', 'SF')),
    lag_minutes INT NOT NULL DEFAULT 0,
    CONSTRAINT uq_relationship UNIQUE (pred_activity_id, succ_activity_id)
);

-- 4. Database Trigger: Zero-Tolerance Immutability for Baselines
CREATE OR REPLACE FUNCTION check_baseline_immutability()
RETURNS TRIGGER AS $$
DECLARE
    v_is_baseline BOOLEAN;
BEGIN
    SELECT is_baseline INTO v_is_baseline FROM projects WHERE id = OLD.project_id;
    IF v_is_baseline THEN
        RAISE EXCEPTION 'DATABASE INTEGRITY ERROR: Cannot mutate or delete records in frozen baseline project %', OLD.project_id;
    END IF;
    RETURN OLD;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_activities_baseline_lock
BEFORE UPDATE OR DELETE ON activities
FOR EACH ROW EXECUTE FUNCTION check_baseline_immutability();
```

### 6.2 Golang Deep Snapshot Creation Engine

In Go, copying a project with tens of thousands of activities, relationships, and calendars requires a single, atomic database transaction (`sql.Tx`). If any query fails, the entire snapshot rolls back cleanly.

```go
// Package engine/baseline/snapshot.go
package baseline

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	"github.com/google/uuid"
)

type SnapshotRequest struct {
	LiveProjectID uuid.UUID
	BaselineName  string
	BaselineCode  string
	BaselineType  string // "PROJECT", "B1", "B2", "B3"
}

type SnapshotResult struct {
	BaselineProjectID uuid.UUID
	ClonedTasksCount  int64
	ClonedRelsCount   int64
	ExecutionDuration time.Duration
}

// DeepCloneProjectToBaseline creates an immutable snapshot of an active project
func DeepCloneProjectToBaseline(ctx context.Context, db *sql.DB, req SnapshotRequest) (*SnapshotResult, error) {
	startTime := time.Now()

	// 1. Begin atomic transaction with SERIALIZABLE isolation to avoid phantom reads
	tx, err := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelSerializable})
	if err != nil {
		return nil, fmt.Errorf("failed to begin transaction: %w", err)
	}
	defer tx.Rollback()

	// 2. Fetch live project metadata
	var liveDataDate time.Time
	err = tx.QueryRowContext(ctx, `
		SELECT data_date FROM projects WHERE id = $1 AND is_baseline = FALSE
	`, req.LiveProjectID).Scan(&liveDataDate)
	if err != nil {
		return nil, fmt.Errorf("live project %s not found or is already a baseline: %w", req.LiveProjectID, err)
	}

	// 3. Insert child project record
	baselineProjID := uuid.New()
	_, err = tx.ExecContext(ctx, `
		INSERT INTO projects (id, code, name, orig_proj_id, is_baseline, baseline_type, data_date, created_at, updated_at)
		VALUES ($1, $2, $3, $4, TRUE, $5, $6, NOW(), NOW())
	`, baselineProjID, req.BaselineCode, req.BaselineName, req.LiveProjectID, req.BaselineType, liveDataDate)
	if err != nil {
		return nil, fmt.Errorf("failed to create baseline project header: %w", err)
	}

	// 4. Batch deep clone activities with mapping table
	// We preserve original_task_uuid for deterministic joins in Next.js Gantt views
	activityCloneQuery := `
		WITH cloned_tasks AS (
			INSERT INTO activities (
				id, project_id, code, name, original_task_uuid, calendar_id,
				planned_duration_minutes, target_start, target_finish,
				early_start, early_finish, actual_start, actual_finish,
				total_float_minutes, status, created_at, updated_at
			)
			SELECT 
				gen_random_uuid(),
				$1,
				code,
				name,
				COALESCE(original_task_uuid, id), -- guarantee stable tracking UUID
				calendar_id,
				planned_duration_minutes,
				target_start,
				target_finish,
				early_start,
				early_finish,
				actual_start,
				actual_finish,
				total_float_minutes,
				status,
				NOW(),
				NOW()
			FROM activities
			WHERE project_id = $2
			RETURNING id, original_task_uuid
		)
		SELECT count(*) FROM cloned_tasks;
	`
	var clonedTasksCount int64
	err = tx.QueryRowContext(ctx, activityCloneQuery, baselineProjID, req.LiveProjectID).Scan(&clonedTasksCount)
	if err != nil {
		return nil, fmt.Errorf("failed to clone activities: %w", err)
	}

	// 5. Deep clone CPM network relationships
	// Subquery matches predecessor and successor IDs in the newly cloned project
	relCloneQuery := `
		WITH cloned_rels AS (
			INSERT INTO activity_relationships (
				id, project_id, pred_activity_id, succ_activity_id, type, lag_minutes
			)
			SELECT 
				gen_random_uuid(),
				$1,
				cloned_pred.id,
				cloned_succ.id,
				orig_rel.type,
				orig_rel.lag_minutes
			FROM activity_relationships orig_rel
			JOIN activities orig_pred ON orig_rel.pred_activity_id = orig_pred.id
			JOIN activities orig_succ ON orig_rel.succ_activity_id = orig_succ.id
			JOIN activities cloned_pred ON cloned_pred.project_id = $1 
				AND cloned_pred.original_task_uuid = orig_pred.original_task_uuid
			JOIN activities cloned_succ ON cloned_succ.project_id = $1 
				AND cloned_succ.original_task_uuid = orig_succ.original_task_uuid
			WHERE orig_rel.project_id = $2
			RETURNING id
		)
		SELECT count(*) FROM cloned_rels;
	`
	var clonedRelsCount int64
	err = tx.QueryRowContext(ctx, relCloneQuery, baselineProjID, req.LiveProjectID).Scan(&clonedRelsCount)
	if err != nil {
		return nil, fmt.Errorf("failed to clone relationships: %w", err)
	}

	// 6. Commit transaction
	if err := tx.Commit(); err != nil {
		return nil, fmt.Errorf("failed to commit baseline clone transaction: %w", err)
	}

	return &SnapshotResult{
		BaselineProjectID: baselineProjID,
		ClonedTasksCount:  clonedTasksCount,
		ClonedRelsCount:   clonedRelsCount,
		ExecutionDuration: time.Since(startTime),
	}, nil
}
```
