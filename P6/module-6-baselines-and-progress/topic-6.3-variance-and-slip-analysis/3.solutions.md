## 🧠 Section A: Mathematical Foundations & Sign Conventions

### Solution 1: The P6 Sign Convention Proof

#### 1. Why P6 Uses $\text{Baseline} - \text{Current}$
* **Earned Value Management (EVM) Alignment:** In ANSI/EIA-748 EVM standards, **Schedule Variance in Cost ($SV$)** is defined as:
  $$SV = EV - PV \quad (\text{Earned Value} - \text{Planned Value})$$
  In financial accounting and project controls, a **positive number always signifies a favorable condition** (higher earnings, surplus funds, surplus time), while a **negative number signifies an unfavorable condition** (over-budget, schedule delay).
* **Cognitive Consistency:** If variance were defined as $\text{Early Finish} - \text{Baseline Finish}$, a delayed task that slips from May 1 to May 15 would produce $+14\text{ days}$. Executives and project managers naturally interpret positive numbers as positive achievements. Displaying $+14$ on a red delayed bar creates dangerous cognitive dissonance.
* **The P6 Invariant:** By defining $SV_{\text{finish}} = \text{Baseline Finish} - \text{Early Finish}$:
  - Ahead of Schedule $\longrightarrow$ Positive ($+$) $\longrightarrow$ Favorable (Green)
  - Behind Schedule $\longrightarrow$ Negative ($-$) $\longrightarrow$ Unfavorable (Red)

#### 2. Sign Conditions
* $SV_{\text{finish}} > 0$: $\text{Baseline Finish} > \text{Early Finish}$ (The forecast finishes **earlier** than the baseline; the project is ahead of schedule).
* $SV_{\text{finish}} < 0$: $\text{Baseline Finish} < \text{Early Finish}$ (The forecast finishes **later** than the baseline; the project is behind schedule).
* $SV_{\text{finish}} = 0$: $\text{Baseline Finish} = \text{Early Finish}$ (The project is exactly on track).

#### 3. Calculation for `2026-06-15` vs `2026-06-25`
$$SV_{\text{finish}} = \text{15-Jun-2026} - \text{25-Jun-2026} = \mathbf{-10\text{ calendar days}}$$
This represents an **unfavorable schedule slip of 10 days** (Behind Schedule).

### Solution 2: The Calendar-Aware Variance Calculation Flaw

#### 1. Naive vs Calendar-Aware Calculation
* **Given Data:**
  - Baseline Finish: Friday `2026-05-15 17:00:00`
  - Early Finish: Monday `2026-05-18 17:00:00`
  - Calendar: 5-Day Week (Mon–Fri, 8h/day). Saturday & Sunday non-working.
* **Naive Timestamp Formula:**
  $$\Delta t = \frac{\text{unix}(\text{2026-05-15 17:00}) - \text{unix}(\text{2026-05-18 17:00})}{86400} = \frac{-259{,}200}{86400} = \mathbf{-3.0\text{ Days}}$$
  The naive formula reports a delay of **3 days**.
* **Calendar-Aware Working Time Walk:**
  - Friday 17:00 to Monday 08:00 is non-working weekend (0 working hours).
  - Monday 08:00 to Monday 17:00 is 1 working day (8 working hours).
  - Total working delay $= \mathbf{-1.0\text{ Working Day}}$ (8 working hours).

#### 2. Percentage Error
$$\text{Error} = \left| \frac{\text{Naive} - \text{True}}{\text{True}} \right| \times 100 = \left| \frac{-3.0 - (-1.0)}{-1.0} \right| \times 100 = \mathbf{200\% \text{ Error!}}$$
The naive calculation exaggerates the delay by 200%.

#### 3. Compounding Impact Across Mega-Projects
In a multi-year EPC infrastructure project spanning 104 weekends, 30 national public holidays, and 45 days of desert monsoon or summer heat moratoria:
* Calculating variance using raw calendar days erroneously counts non-working rest intervals as delayed production time.
* Subcontractors facing liquidated damage claims will immediately have the claims dismissed in court by showing that the scheduler counted non-working days as lost production days.

### Solution 3: The Four Canonical Variance Dimensions

#### 1. Start Variance ($SV_{\text{start}}$)
$$SV_{\text{start}} = \text{Baseline Start} - \text{Early Start}$$
* **Meaning:** Measures delay or acceleration in the commencement of physical work. Isolates mobilization and predecessor handoff performance.

#### 2. Finish Variance ($SV_{\text{finish}}$)
$$SV_{\text{finish}} = \text{Baseline Finish} - \text{Early Finish}$$
* **Meaning:** Measures the net divergence of activity completion against the benchmark. Represents the cumulative effect of start variance and production speed.

#### 3. Duration Variance ($DV$)
$$DV = \text{Baseline Planned Duration} - \text{At-Completion Duration}$$
* **Meaning:** Measures productivity and execution efficiency. If positive, the crew completed the physical work faster than budgeted, regardless of when they started.

#### 4. Float Variance ($FV$)
$$FV = \text{Current Total Float} - \text{Baseline Total Float}$$
* **Meaning:** Measures the erosion or gain of schedule risk buffer. If negative, the activity is losing flexibility and moving closer to the critical path.

#### 5. Concrete Scenario: Negative Finish Variance with Positive Duration Variance
* **Scenario:** Activity `ACT-TRN-101` (Transformer Installation).
  - Baseline: Start `01-May`, Finish `28-May` (Planned Duration = 20 days).
  - Delay in transport: Early Start slips to `15-May` ($SV_{\text{start}} = -14\text{ days}$).
  - Double shifts mobilized: Work completes in 12 days instead of 20 days!
  - Early Finish = `27-May` + 2 days = `29-May`.
* **Metrics:**
  $$SV_{\text{finish}} = \text{28-May} - \text{29-May} = \mathbf{-1\text{ Day (Negative / Delayed)}}$$
  $$DV = 20\text{ days} - 12\text{ days} = \mathbf{+8\text{ Days (Positive / High Productivity)}}$$
  The crew performed exceptionally well (+8 days faster than planned), but because they started 14 days late, the activity still finished 1 day behind baseline!

## 🏗️ Section B: Float Erosion & Critical Path Migration

### Solution 4: The "Float Consumption" Trap

#### 1. Finish Variance of Activity $A$
$$SV_{\text{finish}} = \text{10-Apr-2026} - \text{24-Apr-2026} = \mathbf{-10\text{ Working Days}}$$

#### 2. New Total Float of Activity $A$
$$\text{New Total Float} = \text{Original Total Float} - \text{Delay} = +25\text{ days} - 10\text{ days} = \mathbf{+15\text{ Working Days}}$$

#### 3. Why the Executive Statement is Dangerous
* Stating that the project is "100% on schedule" because the final milestone date hasn't moved is an illusion known as the **"Static Milestone Fallacy."**
* 10 working days of contingency buffer have been permanently incinerated.
* The schedule's capacity to absorb future unforeseen disruptions (equipment breakdowns, weather delays, permitting freezes) has been reduced by 40% ($10 / 25$).

#### 4. Downstream Risk
Total Float is a **shared path resource**. Any downstream activity sharing that CPM path (e.g., testing, cabling, pre-commissioning) now has 10 fewer days of flexibility. If testing takes 16 days instead of 15 days, it immediately threatens project completion.

### Solution 5: Critical Path Migration Dynamics

#### 1. Initial State
* Path 1 (Civil Switchyard): Finish `15-Aug`, Float = `+15 days`.
* Path 2 (Cabling): Finish `30-Aug`, Float = `0 days` (Critical Path).
* Project Milestone: `30-Aug-2026`.

#### 2. Tracing the 25-Day Delay on Path 1
* **Early Finish of Path 1:**
  $$\text{New Finish} = \text{15-Aug} + 25\text{ days} = \mathbf{09\text{-Sep-2026}}$$
* **Overall Project Completion Date:**
  Since the milestone depends on both Path 1 and Path 2:
  $$\text{Project Finish} = \max(\text{Path 1 Finish}, \text{Path 2 Finish}) = \max(\text{09-Sep}, \text{30-Aug}) = \mathbf{09\text{-Sep-2026}}$$
  The project milestone is delayed by **10 calendar days** (`30-Aug` to `09-Sep`).
* **Total Float of Path 1:**
  Path 1 is now driving project completion.
  $$\text{Total Float (Path 1)} = \mathbf{0\text{ Days (or } -10\text{ days if contractual deadline is 30-Aug)}}$$
* **Total Float of Path 2:**
  Path 2 finishes on `30-Aug`, while the project now finishes on `09-Sep`.
  $$\text{Total Float (Path 2)} = \text{09-Sep} - \text{30-Aug} = \mathbf{+10\text{ Days!}}$$

#### 3. Critical Path Migration Explained

## 💻 Section D: Golang Engine & Frontend Engineering

### Solution 8: Golang Calendar-Aware Variance Function

```go
package variance

import "time"

type Calendar struct {
	// IsWorkingMinute returns true if timestamp falls in a working shift
	IsWorkingMinute func(t time.Time) bool
	// WeeklyWorkingMinutes provides quick lookup for whole week fast-forwarding
	WeeklyWorkingMinutes int
}

// CountWorkingMinutesBetween calculates calendar-aware working time between two timestamps
func (c *Calendar) CountWorkingMinutesBetween(start, end time.Time) int {
	// 1. Normalize order: ensure start <= end
	if start.After(end) {
		start, end = end, start
	}

	totalWorkingMin := 0
	current := start

	// 2. High-Performance Optimization: Fast-Forward Full Weeks (if interval > 14 days)
	daysDiff := int(end.Sub(current).Hours() / 24)
	if daysDiff >= 14 && c.WeeklyWorkingMinutes > 0 {
		fullWeeks := daysDiff / 7
		totalWorkingMin += fullWeeks * c.WeeklyWorkingMinutes
		current = current.AddDate(0, 0, fullWeeks*7)
	}

	// 3. Minute-by-Minute Interval Walk for Remaining Time Boundary
	for current.Before(end) {
		if c.IsWorkingMinute(current) {
			totalWorkingMin++
		}
		current = current.Add(time.Minute)
	}

	return totalWorkingMin
}
```

### Solution 9: Automated Threshold & Issue Engine

```go
package variance

import (
	"context"
	"time"

	"github.com/google/uuid"
)

type ProjectIssue struct {
	ID          uuid.UUID
	ProjectID   uuid.UUID
	ActivityID  uuid.UUID
	Code        string
	Severity    string
	TriggerRule string
	Description string
	CreatedAt   time.Time
}

// ScanProjectThresholds inspects all activity variances against enterprise rules
func ScanProjectThresholds(ctx context.Context, projectID uuid.UUID, evaluatedActivities []ActivityVarianceResult, rawInputs map[uuid.UUID]ActivityComparisonInput) ([]ProjectIssue, error) {
	var issues []ProjectIssue

	for _, act := range evaluatedActivities {
		raw := rawInputs[act.ActivityID]

		// Rule 3: Contractual Milestone Slip (Highest Severity)
		if raw.IsContractualCOD && act.FinishVarianceHours < 0 {
			issues = append(issues, ProjectIssue{
				ID:          uuid.New(),
				ProjectID:   projectID,
				ActivityID:  act.ActivityID,
				Code:        act.Code,
				Severity:    "BREACH",
				TriggerRule: "RULE_3_MILESTONE_BREACH",
				Description: "Contractual milestone delayed past approved baseline target.",
				CreatedAt:   time.Now(),
			})
			continue
		}

		// Rule 1: Critical Path Negative Variance
		if raw.CurrentTotalFloat <= 0 && act.FinishVarianceHours < 0 {
			issues = append(issues, ProjectIssue{
				ID:          uuid.New(),
				ProjectID:   projectID,
				ActivityID:  act.ActivityID,
				Code:        act.Code,
				Severity:    "CRITICAL",
				TriggerRule: "RULE_1_CRITICAL_PATH_SLIP",
				Description: "Activity on critical path has negative finish variance.",
				CreatedAt:   time.Now(),
			})
			continue
		}

		// Rule 2: Near-Critical Float Erosion (> 5 days slip on float < 10 days)
		if raw.CurrentTotalFloat > 0 && raw.CurrentTotalFloat <= 4800 && act.FinishVarianceHours <= -40.0 {
			issues = append(issues, ProjectIssue{
				ID:          uuid.New(),
				ProjectID:   projectID,
				ActivityID:  act.ActivityID,
				Code:        act.Code,
				Severity:    "WARNING",
				TriggerRule: "RULE_2_FLOAT_EROSION",
				Description: "Near-critical path buffer depleted by more than 5 working days.",
				CreatedAt:   time.Now(),
			})
		}
	}

	return issues, nil
}
```

### Solution 10: Next.js Variance Column Formatter

```typescript
// utils/varianceFormatter.ts

export interface VarianceFormatting {
  text: string;
  colorClass: string;
  badge: string;
}

export function formatVarianceCell(hours: number, calendarHoursPerDay: number = 8.0): VarianceFormatting {
  const days = hours / calendarHoursPerDay;
  const absDays = Math.abs(days).toFixed(1);

  // Positive: Ahead of Schedule (Favorable)
  if (days > 0.05) {
    return {
      text: `+${absDays} d`,
      colorClass: 'text-emerald-400 bg-emerald-950/40 border-emerald-800',
      badge: 'AHEAD',
    };
  }

  // Zero: On Target (Within 0.05 days tolerance)
  if (Math.abs(days) <= 0.05) {
    return {
      text: `0.0 d`,
      colorClass: 'text-slate-300 bg-slate-800/40 border-slate-700',
      badge: 'ON TARGET',
    };
  }

  // Minor Negative: -0.1 to -5.0 days (Warning)
  if (days >= -5.0) {
    return {
      text: `-${absDays} d`,
      colorClass: 'text-amber-400 bg-amber-950/40 border-amber-800',
      badge: 'WARNING',
    };
  }

  // Severe Negative: More than 5 days behind (Critical)
  return {
    text: `-${absDays} d`,
    colorClass: 'text-rose-400 bg-rose-950/50 border-rose-800 ring-1 ring-rose-600 animate-pulse',
    badge: 'CRITICAL',
  };
}
```
