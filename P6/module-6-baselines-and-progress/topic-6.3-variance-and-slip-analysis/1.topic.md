## 1. Executive Summary & The Geometry of Schedule Variance

### 1.1 The Axiom: Schedules Drift Long Before Milestones Fail
Projects rarely fail due to a sudden, catastrophic 6-month delay occurring on the final week. Mega-projects fail **one day at a time**, through unnoticed micro-delays that erode schedule contingency buffers until the critical path ruptures.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                             HOW PROJECTS DRIFT: THE FLOAT EROSION CURVE                          │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  Month 1 to 4: Stage 1 (Float Erosion — The "Invisible" Delay)                                   │
│  * Tasks slip by 5, 10, 15 days.                                                                 │
│  * Executive Report: "Project Completion Milestone is 100% on track!" (Green Status)             │
│  * Reality: Total Float dropped from +30 days down to 0 days. Safety buffer is dead!             │
│                                                                                                  │
│  Month 5: Stage 2 (Direct Critical Path Slip — The Crisis)                                       │
│  * A minor 2-day delivery slip hits an activity with 0 float.                                    │
│  * The entire Project COD pushes by 2 days. Total Float turns NEGATIVE (-2 days).                │
│  * Executive Panic: "How did we suddenly get delayed?"                                           │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

> **The Architectural Standard:**  
> **Variance Analysis** is the real-time differential calculus of project controls. It compares the live forward-pass forecast against the frozen baseline coordinates, exposing not only milestone slips, but the upstream **float erosion** that precedes failure.

### 1.2 Sign Conventions: Mathematical Drift vs P6 Project Controls Convention
When writing algorithms for a scheduling engine, developers frequently trip over the **sign convention** (+ / -) of variance.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                             VARIANCE SIGN CONVENTIONS: DUAL PERSPECTIVES                         │
├────────────────────────────┬─────────────────────────────┬───────────────────────────────────────┤
│ Convention                 │ Mathematical Drift          │ Primavera P6 Standard Convention      │
├────────────────────────────┼─────────────────────────────┼───────────────────────────────────────┤
│ Core Question              │ "Did the date move later?"  │ "Is the project ahead or behind?"     │
├────────────────────────────┼─────────────────────────────┼───────────────────────────────────────┤
│ Formula                    │ Early Finish - BL Finish    │ BL Finish - Early Finish              │
├────────────────────────────┼─────────────────────────────┼───────────────────────────────────────┤
│ Positive Value (+)         │ +10d = Finished LATER       │ +10d = AHEAD of Schedule (Favorable!) │
│ Negative Value (-)         │ -10d = Finished EARLIER     │ -10d = BEHIND Schedule (Unfavorable!) │
├────────────────────────────┼─────────────────────────────┼───────────────────────────────────────┤
│ Industry Alignment         │ Standard Software Diffs     │ Earned Value Management ($SV = EV-PV$)│
└────────────────────────────┴─────────────────────────────┴───────────────────────────────────────┘
```

In Primavera P6 and Earned Value Management:
* **Positive ($+$) is ALWAYS Good (Favorable):** You finished earlier than planned, or you have float remaining.
* **Negative ($-$) is ALWAYS Bad (Unfavorable):** You finished later than planned, or you are running behind schedule.

Therefore, the official Primavera P6 formulas are:
$$\text{Variance - Baseline Start Date} = \text{Baseline Start} - \text{Early Start}$$
$$\text{Variance - Baseline Finish Date} = \text{Baseline Finish} - \text{Early Finish}$$
$$\text{Variance - Duration} = \text{Baseline Planned Duration} - \text{At-Completion Duration}$$
$$\text{Variance - Total Float} = \text{Current Total Float} - \text{Baseline Total Float}$$

*Note: In the live database, these differences are measured in calendar working hours using the activity's assigned calendar.*

## 2. Float Erosion vs Schedule Slip: The Two Stages of Delay

A competent project controls architect distinguishes between **Float Consumption** and **Critical Path Slip**.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                               THE TWO PHASES OF SCHEDULE DECAY                                   │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  PHASE 1: FLOAT CONSUMPTION (Total Float > 0, Finish Variance < 0)                               │
│  ┌────────────────────────────────────────────────────────────────────────┐                      │
│  │ Activity slips by 12 days. Finish Variance = -12 Days.                 │                      │
│  │ Total Float drops from +20 Days down to +8 Days.                       │                      │
│  │ COD Completion Milestone does NOT move!                                │                      │
│  │ Consequence: Project resilience decreases. Risk absorption collapses.  │                      │
│  └────────────────────────────────────────────────────────────────────────┘                      │
│                                      │ (Further delays consume remaining 8 days)                 │
│                                      ▼                                                           │
│  PHASE 2: DIRECT CRITICAL PATH SLIP (Total Float ≤ 0, Finish Variance < 0)                       │
│  ┌────────────────────────────────────────────────────────────────────────┐                      │
│  │ Activity slips by an additional 10 days.                               │                      │
│  │ Total Float drops from +8 Days down to -2 Days!                        │                      │
│  │ COD Completion Milestone pushes by 2 Days!                             │                      │
│  │ Consequence: Liquidated Damages (LD) triggered at ₹5,00,000/day!       │                      │
│  └────────────────────────────────────────────────────────────────────────┘                      │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 2.1 Why Float is a Commercial Commodity
Who owns the float? 
* In EPC contracts, "Float belongs to the project" until consumed.
* If a subcontractor carelessly consumes 25 days of float on non-critical civil trenching, they leave zero contingency buffer for subsequent electrical cabling and transformer commissioning.
* If a 2-day rainstorm hits during commissioning, the transformer activity immediately pushes the COD milestone. The subcontractor who consumed the buffer is contractually liable for the resulting delay damages.

Notice how `ACT-CIV-302` slipped by 15 days, but COD only slipped by 5 days. Why?

## 5. Golang Variance Evaluator Engine & Architecture

A naive developer computes variance by subtracting Unix timestamps:
```go
// NAIVE FLAWED SUBTRACTION (IGNORES CALENDARS AND SHIFTS)
varianceSeconds := baselineFinish.Unix() - earlyFinish.Unix()
varianceDays := varianceSeconds / 86400
```
This is incorrect in construction because:
1. Two dates separated by a weekend (Saturday + Sunday) should not count as 2 days of working schedule variance on a 5-day calendar.
2. Schedule variance must be reported in **Working Days** according to the activity's specific calendar!

### 5.1 Calendar-Aware Variance Calculation Engine

```go
// Package engine/variance/evaluator.go
package variance

import (
	"time"

	"github.com/google/uuid"
)

type VarianceAlertLevel string

const (
	AlertNormal   VarianceAlertLevel = "NORMAL"
	AlertWarning  VarianceAlertLevel = "WARNING"
	AlertCritical VarianceAlertLevel = "CRITICAL"
	AlertBreach   VarianceAlertLevel = "BREACH"
)

type ActivityComparisonInput struct {
	ActivityID        uuid.UUID
	Code              string
	Name              string
	IsMilestone       bool
	IsContractualCOD  bool
	CurrentEarlyStart time.Time
	CurrentEarlyFin   time.Time
	CurrentTotalFloat int // in working minutes
	BaselineStart     time.Time
	BaselineFinish    time.Time
	BaselineDuration  int // in working minutes
	CurrentDuration   int // in working minutes
}

type ActivityVarianceResult struct {
	ActivityID          uuid.UUID
	Code                string
	StartVarianceHours  float64 // Positive = Ahead, Negative = Behind
	FinishVarianceHours float64 // Positive = Ahead, Negative = Behind
	DurationVarianceHrs float64
	FloatVarianceHours  float64
	AlertLevel          VarianceAlertLevel
	AlertMessage        string
}

// CalendarFilter represents the activity calendar interface
type CalendarFilter interface {
	CountWorkingMinutesBetween(start, end time.Time) int
}

// EvaluateActivityVariance calculates true calendar-aware schedule variance
func EvaluateActivityVariance(input ActivityComparisonInput, cal CalendarFilter, baselineFloatMin int) ActivityVarianceResult {
	res := ActivityVarianceResult{
		ActivityID: input.ActivityID,
		Code:       input.Code,
	}

	// 1. Calculate Start Variance (BL Start - Early Start)
	// If Early Start is AFTER Baseline Start, result is NEGATIVE (Delay)
	if input.CurrentEarlyStart.After(input.BaselineStart) {
		workingMin := cal.CountWorkingMinutesBetween(input.BaselineStart, input.CurrentEarlyStart)
		res.StartVarianceHours = -float64(workingMin) / 60.0
	} else {
		workingMin := cal.CountWorkingMinutesBetween(input.CurrentEarlyStart, input.BaselineStart)
		res.StartVarianceHours = float64(workingMin) / 60.0
	}

	// 2. Calculate Finish Variance (BL Finish - Early Finish)
	if input.CurrentEarlyFin.After(input.BaselineFinish) {
		workingMin := cal.CountWorkingMinutesBetween(input.BaselineFinish, input.CurrentEarlyFin)
		res.FinishVarianceHours = -float64(workingMin) / 60.0
	} else {
		workingMin := cal.CountWorkingMinutesBetween(input.CurrentEarlyFin, input.BaselineFinish)
		res.FinishVarianceHours = float64(workingMin) / 60.0
	}

	// 3. Duration & Float Variance
	res.DurationVarianceHrs = float64(input.BaselineDuration-input.CurrentDuration) / 60.0
	res.FloatVarianceHours = float64(input.CurrentTotalFloat-baselineFloatMin) / 60.0

	// 4. Automated Alert Rule Evaluation
	totalFloatHours := float64(input.CurrentTotalFloat) / 60.0

	if input.IsContractualCOD && res.FinishVarianceHours < 0 {
		res.AlertLevel = AlertBreach
		res.AlertMessage = "CRITICAL BREACH: Contractual COD Milestone delayed! Liquidated damages active."
	} else if totalFloatHours <= 0 || res.FinishVarianceHours <= -40.0 { // <= -5 days (8h/d)
		res.AlertLevel = AlertCritical
		res.AlertMessage = "CRITICAL ALERT: Critical path delay or severe milestone slip."
	} else if totalFloatHours < 80.0 || res.FinishVarianceHours < 0 { // Float < 10 days
		res.AlertLevel = AlertWarning
		res.AlertMessage = "WARNING: Significant float consumption or minor schedule slip."
	} else {
		res.AlertLevel = AlertNormal
		res.AlertMessage = "Activity on schedule with healthy float buffer."
	}

	return res
}
```

## 6. Next.js Variance Grid & Gantt Visualization

In modern web-based project controls applications, variances are presented in tabular grids and Gantt tooltips with immediate visual cues.

### 6.1 React Variance Badge Component

```tsx
// components/schedule/VarianceBadge.tsx
'use client';

import React from 'react';

interface VarianceBadgeProps {
  varianceHours: number;
  unit?: 'hours' | 'days';
}

export const VarianceBadge: React.FC<VarianceBadgeProps> = ({ varianceHours, unit = 'days' }) => {
  const value = unit === 'days' ? (varianceHours / 8.0).toFixed(1) : varianceHours.toFixed(1);
  const numVal = parseFloat(value);

  if (numVal > 0) {
    return (
      <span className="inline-flex items-center px-2.5 py-0.5 rounded-full text-xs font-semibold bg-emerald-950 text-emerald-400 border border-emerald-800">
        +{value} {unit === 'days' ? 'd' : 'h'} (Ahead)
      </span>
    );
  }

  if (numVal === 0) {
    return (
      <span className="inline-flex items-center px-2.5 py-0.5 rounded-full text-xs font-semibold bg-slate-800 text-slate-300 border border-slate-700">
        0.0 {unit === 'days' ? 'd' : 'h'} (On Target)
      </span>
    );
  }

  if (numVal >= -5.0) {
    return (
      <span className="inline-flex items-center px-2.5 py-0.5 rounded-full text-xs font-semibold bg-amber-950 text-amber-400 border border-amber-800">
        {value} {unit === 'days' ? 'd' : 'h'} (Warning)
      </span>
    );
  }

  return (
    <span className="inline-flex items-center px-2.5 py-0.5 rounded-full text-xs font-semibold bg-rose-950 text-rose-400 border border-rose-800 animate-pulse">
      {value} {unit === 'days' ? 'd' : 'h'} (Critical)
    </span>
  );
};
```
