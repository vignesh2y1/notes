## 1. Executive Summary & The Core Mental Model

### 1.1 The Axiom: Time Passed Is Not Work Performed
In standard agile software project management tools (such as Jira, Linear, or GitHub Projects), tracking progress is often binary or subjective: an issue is moved across columns (`Todo` → `In Progress` → `Done`), or story points are burned down as pull requests merge. If a two-week sprint reaches Day 7, engineers might casually say the sprint is "50% done."

Enterprise capital projects—governed by scheduling engines like **Oracle Primavera P6**, **Safran Project**, and **Asta Powerproject**—reject this casual assumption. 

> **Axiom:** The passage of chronological time bears no guaranteed linear relationship to physical work completion or resource expenditure.

Consider the **Surya 100MW Solar IPP Project** in the Thar Desert of Rajasthan, India. The engineering, procurement, and construction (EPC) contract covers:
* 6,800 tracker foundation piles drilled into hard desert strata.
* 220,000 bifacial monocrystalline photovoltaic (PV) modules mounted on single-axis trackers.
* 45 kilometers of 33kV medium-voltage (MV) underground cabling.
* 40 central inverter station pads with heavy reinforced cement concrete (RCC).
* A 33/220kV Pooling Substation (PSS) with two 60MVA power transformers.

```text

│                                TIME PASSED VS. WORK PERFORMED                                    │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
```

If your scheduling engine automatically assumed that 10 days of elapsed time on a 20-day activity equaled 50% physical completion, project executives would remain blind to the site bottleneck until the original finish date arrived with 90% of the physical piles still uninstalled.

### 1.3 The Data Date (Status Date / Time Now)
Every calculation of progress in an enterprise scheduling engine revolves around a single contractual anchor known as the **Data Date** (abbreviated $DD$, also called *Status Date* or *Time Now*).

The Data Date is a temporal demarcation line that divides the project schedule into two fundamentally distinct universes:
1. **The Past (Historical Domain, $t < DD$):** The realm of facts, immutable records, actual start timestamps, actual finish timestamps, actual duration consumed, and actual labor hours billed. CPM logic does not calculate dates in the past; it records observed reality.
2. **The Future (Forecast Domain, $t \ge DD$):** The realm of deterministic CPM math, remaining durations, early start and finish forecasts, total float, and critical path propagation.

```text
│                                    THE DATA DATE DEMARCATION                                     │

│                     ◄─────────────────────────┼─────────────────────────►                        │
```

## 2. The Three Percent Complete Types in Primavera P6

Primavera P6 provides three distinct calculation engines for activity percent complete:
1. **Duration % Complete**
2. **Physical % Complete**
3. **Units % Complete**

The selection of `Percent_Complete_Type` on an activity fundamentally alters how P6's scheduling engine couples dates, durations, resource units, and Earned Value Management (EVM) metrics.

### 2.1 Duration % Complete

#### Mathematical Formulation
Duration % Complete measures the proportion of an activity's total duration that has been consumed up to the Data Date:

$$\text{Duration \% Complete} = \frac{\text{Actual Duration}}{\text{Actual Duration} + \text{Remaining Duration}} \times 100$$

Where:
* $\text{Actual Duration} \, (AD)$: The working time elapsed between the Activity's Actual Start ($AS$) and the Data Date ($DD$), filtered through the activity's calendar.
* $\text{Remaining Duration} \, (RD)$: The estimated working time required from the Data Date to finish the activity.
* $\text{At Completion Duration} \, (CD) = AD + RD$.

#### Bidirectional Coupling Mechanics
In Primavera P6, when an activity is configured with `Percent_Complete_Type = DURATION`, the engine enforces a strict mathematical link between $\text{Duration \%}$ and $\text{Remaining Duration}$:

$$\text{Remaining Duration} = \text{Original Duration} \times \left(1 - \frac{\text{Duration \% Complete}}{100}\right)$$

If an engineer opens P6 and types `75%` into the Duration % Complete field for an activity with an Original Duration of 20 days:
1. The engine automatically overwrites $\text{Remaining Duration} = 20 \times (1 - 0.75) = 5\text{ days}$.
2. Conversely, if the engineer modifies $\text{Remaining Duration}$ from 5 days to 2 days, P6 instantly recalculates:
   $$\text{Duration \% Complete} = \frac{15}{15 + 2} \times 100 = 88.24\%$$

#### When to Use Duration % Complete
Duration % Complete is appropriate **only** for purely time-driven activities where physical work is continuous and passive, requiring zero manual craftsmanship or variable labor productivity:
* **Concrete Curing:** `ACT-CIV-045: 7-Day Curing of 33kV Substation Transformer Pad`. Concrete strength develops chemically over 168 hours; tracking elapsed calendar hours is an exact physical proxy for progress.
* **Environmental Waiting Periods:** 30-day statutory public consultation periods before desert wildlife clearance.
* **Charter Sea Vessel In-Transit:** Shipping PV inverters across the Indian Ocean from manufacturer to port (assuming normal maritime speed).

#### The Fatal Pitfall: The "90% Complete Syndrome"
In physical construction, Duration % Complete is notoriously treacherous. It causes what construction claims analysts term the **"90% Complete Syndrome"**:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                 THE "90% COMPLETE SYNDROME"                                      │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   Original Duration: 20 Days (Piling Block A)                                                    │
│                                                                                                  │
│   Day 18 Progress Meeting:                                                                       │
│   • Actual Duration Elapsed = 18 Days                                                            │
│   • Naive Duration % Formula = 18 / 20 = 90% COMPLETE                                            │
│   • Client Management is informed: "Piling is almost finished!"                                  │
│                                                                                                  │
│   Physical Reality Audited on Day 19:                                                            │
│   • 3,000 out of 6,800 piles hit hard subsurface granite.                                        │
│   • Drill rigs suffered repeated hydraulic refusal.                                              │

│                                                                                                  │
```

Using Duration % Complete for craft activities creates a dangerous illusion of progress that hides productivity collapse until contractual deadlines are irrecoverably breached.

### 2.2 Physical % Complete

#### The Decoupled Architecture
To eliminate the 90% Complete Syndrome, enterprise capital project standards (such as **AACE International Recommended Practice 28R-03** and **PMI PMBOK**) mandate **Physical % Complete** for all direct construction deliverables.

Under `Percent_Complete_Type = PHYSICAL`:
1. **Physical % Complete is completely decoupled from Remaining Duration.**
2. Changing the Physical % Complete does **not** alter the Remaining Duration.
3. Changing the Remaining Duration does **not** alter the Physical % Complete.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                             PHYSICAL % COMPLETE: DECOUPLED STATE                                 │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│                       ┌──────────────────────────────────────────┐                               │
│                       │        Physical % Complete = 25%         │                               │
│                       │ (Audited: 1,700 / 6,800 Piles Installed) │                               │
│                       └──────────────────────────────────────────┘                               │
│                                             ▲                                                    │
│                                             │ ZERO COUPLING!                                     │
│                                             ▼                                                    │
│                       ┌──────────────────────────────────────────┐                               │
│                       │       Remaining Duration = 28 Days       │                               │
│                       │ (Engineering Estimate of Future Work)    │                               │
│                       └──────────────────────────────────────────┘                               │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### Field Reality on Surya 100MW Solar
Consider Activity `ACT-STR-010: Install Tracker Torque Tubes & Mounting Racks` (Original Duration: 30 days).
* The site team works for 15 working days ($\text{Actual Duration} = 15$).
* A QA/QC physical survey reveals that the erection crews faced windstorms and only completed 30% of the torque tube assemblies ($\text{Physical \% Complete} = 30\%$).
* The field engineer knows that with extra night shifts, the remaining 70% of racks can be completed in 18 days ($\text{Remaining Duration} = 18\text{ days}$).

In P6 under Physical % Complete:
* $\text{Physical \%} = 30.0\%$ (Stored for EVM).
* $\text{Remaining Duration} = 18\text{ days}$ (Used for CPM forward pass).
* $\text{Duration \%} = \frac{15}{15 + 18} \times 100 = 45.45\%$ (Reported for time consumption only).

#### The Earned Value Connection
Physical % Complete is the **sole legitimate driver** for Earned Value Management (EVM) in capital projects. 

$$\text{Earned Value (BCWP)} = \text{Budget At Completion (BAC)} \times \left(\frac{\text{Physical \% Complete}}{100}\right)$$

If an activity has a baseline budget of \$500,000:
* Under Physical % Complete ($30\%$), the project earns:
  $$\text{BCWP} = \$500,000 \times 0.30 = \$150,000$$
* If P6 had naively used Duration % Complete ($45.45\%$), it would have fraudulently reported:
  $$\text{Earned Value} = \$500,000 \times 0.4545 = \$227,250$$
  This represents a \$77,250 phantom progress overstatement.

### 2.3 Units % Complete

#### Mathematical Formulation
Units % Complete calculates progress based on the physical quantities of resources expended (such as labor hours, equipment machine hours, or material units):

$$\text{Units \% Complete} = \frac{\text{Actual Units}}{\text{Actual Units} + \text{Remaining Units}} \times 100 = \frac{\text{Actual Units}}{\text{At Completion Units}} \times 100$$

Where:
* $\text{Actual Units}$: The actual labor man-hours or equipment machine-hours recorded via site timesheets up to the Data Date.
* $\text{Remaining Units}$: The estimated resource units required to finish the scope.
* $\text{At Completion Units} = \text{Actual Units} + \text{Remaining Units}$.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                     UNITS % COMPLETE FLOW                                        │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   Labor Resource: High-Voltage Cable Jointer Crews                                               │
│   • Planned Budget: 1,000 Man-Hours                                                              │
│   • Actual Man-Hours Expended (Timesheets): 400 Man-Hours                                        │
│   • Remaining Man-Hours Forecasted: 600 Man-Hours                                                │
│                                                                                                  │
│   UNITS % COMPLETE = 400 / (400 + 600) * 100 = 40.0%                                             │
│                                                                                                  │
│   Nonlinear Burn Scenario:                                                                       │
│   If jointer crews encounter flooded cable vaults and spend 400 hours doing dewatering work:     │
│   • Actual Units = 400 Man-Hours                                                                 │
│   • Remaining Units to complete actual cable joints = 900 Man-Hours                              │
│   • Revised Units % = 400 / (400 + 900) * 100 = 30.77%                                          │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### Why Units % Differs from Duration %
1. **Nonlinear Crew Sizing:** A 10-day activity might deploy 2 workers on Days 1–3, ramp up to 20 workers on Days 4–8, and taper off to 2 workers on Days 9–10. On Day 5, 50% of the duration has passed, but over 65% of the man-hours have been consumed.
2. **Overtime and Double Shifts:** Adding night shifts doubles the rate of unit consumption per calendar day.

## 3. Activity Steps & Step Weighting

### 3.1 The Granularity Dilemma in Project Scheduling
When modeling a massive EPC project like Surya 100MW, scheduling engineers encounter a classic architectural tradeoff:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                   THE GRANULARITY DILEMMA                                        │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   APPROACH A: HYPER-DECOMPOSITION (Micro-Tasks)       APPROACH B: MONOLITHIC MACRO-TASKS         │
│   ─────────────────────────────────────────────       ──────────────────────────────────         │
│   Break every activity into 20 sub-activities:        Keep 1 activity: "Inverter Station Pad"    │
│   • "Dig Pad Foundation" (2 days)                     Duration: 14 days                          │
│   • "Lay Blinding Concrete" (1 day)                                                              │
│   • "Tie Rebar Cage" (3 days)                         Disadvantages:                             │
│   • "Inspect Rebar" (1 day)                           • Field progress is subjective guesswork.  │
│   • "Pour Concrete" (2 days)...                       • High risk of 90% Complete Syndrome.      │
│                                                       • Hard to prove physical completion.       │
│   Disadvantages:                                                                                 │
│   • Schedule explodes to 50,000+ activities.                                                     │
│   • CPM forward/backward pass memory explodes.                                                   │
│   • Gantt chart becomes unreadable spaghetti.                                                    │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 The Solution: Activity Steps
Primavera P6 resolves this dilemma through **Activity Steps**.

An Activity Step is a discrete, weighted checklist item that exists **inside** an activity node. 
* Steps do **not** have their own CPM relationships, floats, or logic links.
* Steps do **not** bloat the topological sorting graph of the CPM scheduling engine.
* Steps allow an objective, audit-proof, mathematical calculation of **Physical % Complete**.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                   ACTIVITY STEP ARCHITECTURE                                     │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   CPM Network Graph Node: ACT-INV-012 "Construct 2.5MW Inverter Pad #4"                          │
│   Duration: 14 Days | Float: +6 Days | Calendar: 6-Day Construction                              │
│                                                                                                  │
│   INTERNAL ACTIVITY STEPS:                                                                       │
│   ┌──────┬───────────────────────────────────┬────────┬──────────┬──────────────┐                │
│   │ Step │ Step Description                  │ Weight │ % Comp   │ Earned Comp  │                │
│   ├──────┼───────────────────────────────────┼────────┼──────────┼──────────────┤                │
│   │ 01   │ Excavation & Earth Compaction     │ 15.0   │ 100.0%   │ 15.00%       │                │
│   │ 02   │ Rebar Cage & Earthing Grid        │ 30.0   │ 100.0%   │ 30.00%       │                │
│   │ 03   │ Conduit Stub-ups & Formwork       │ 25.0   │  60.0%   │ 15.00%       │                │
│   │ 04   │ RCC Concrete Pour & Finishing     │ 20.0   │   0.0%   │  0.00%       │                │
│   │ 05   │ 7-Day Curing & Cube Strength Test │ 10.0   │   0.0%   │  0.00%       │                │
│   └──────┴───────────────────────────────────┴────────┴──────────┴──────────────┘                │
│                                                                                                  │
│   Total Weight: 100.0                       Activity Physical % Complete = 60.00%                │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.3 The Step Weighting Mathematical Formula
Each step $k \in \{1, \dots, n\}$ is assigned a user-defined non-negative weight $W_k$. The total weight is:

$$W_{\text{total}} = \sum_{k=1}^n W_k$$

Each step possesses an individual completion metric $S_k \in [0, 100]$.

The parent activity's **Physical % Complete** is calculated via the normalized weighted sum:

$$\text{Physical \% Complete} = \sum_{k=1}^n \left( \frac{W_k}{W_{\text{total}}} \times S_k \right)$$

When steps are treated as simple binary checklists ($S_k \in \{0, 100\}$), the formula simplifies to:

$$\text{Physical \% Complete} = \frac{\sum_{k \in \text{Completed}} W_k}{\sum_{k=1}^n W_k} \times 100$$

#### P6 Setting: "Activity % Complete from Steps"
In P6, an activity must have two settings toggled for this automation:
1. `Percent_Complete_Type = PHYSICAL`
2. `Activity_Percent_Complete_Based_On_Activity_Steps = TRUE`

If this flag is enabled, the activity's `Physical_Percent_Complete` field becomes read-only in the UI and is dynamically evaluated from its child steps.

## 4. The Data Date Progress Updating Workflow

Updating a schedule for weekly or monthly reporting requires a deterministic execution pipeline.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                            THE 6-STEP STATUSING WORKFLOW PIPELINE                                │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   [ STEP 1 ] Advance Data Date (DD) to Reporting Cutoff (e.g., 2026-11-15 17:00)                 │
│       │                                                                                          │
│   [ STEP 2 ] For each started task: Record Actual Start Date (AS <= DD)                          │
│       │                                                                                          │
│   [ STEP 3 ] Record Historical Usage (Actual Duration AD or Actual Units Expended)               │
│       │                                                                                          │
│   [ STEP 4 ] Update Step Checklist or Direct Physical % Complete                                 │
│       │                                                                                          │
│   [ STEP 5 ] Field Re-estimation: Update Remaining Duration (RD)                                 │
│       │                                                                                          │
│   [ STEP 6 ] Execute CPM Rescheduling Engine (Forward & Backward Pass)                           │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 Step-by-Step Validation Rules
When designing a backend engine in Go to handle progress updates, you must enforce strict business invariants:

1. **Actual Start Rule:**
   $$\text{Actual Start} \le \text{Data Date}$$
   An activity cannot start in the future.
2. **Actual Finish Rule:**
   $$\text{Actual Start} \le \text{Actual Finish} \le \text{Data Date}$$
   An activity cannot finish before it starts, nor can it finish in the future.
3. **Completion Rule:**
   $$\text{If Actual Finish is set} \implies \text{Remaining Duration} = 0 \land \text{Percent Complete} = 100\%$$
4. **In-Progress Rule:**
   $$\text{If Actual Start is set} \land \text{Actual Finish is NULL} \implies \text{Remaining Duration} > 0$$

### 4.2 The "Out-of-Sequence" Progress Dilemma
In physical construction, crews frequently work around bottlenecks, violating planned schedule logic ties:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                OUT-OF-SEQUENCE PROGRESS DILEMMA                                  │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   Planned Logic:  [ Trenching (Act A) ] ─────FS─────► [ Cable Pulling (Act B) ]                  │
│                                                                                                  │
│   Field Reality:                                                                                 │
│   Trenching hit rock and is only 30% complete.                                                   │
│   However, cable reels arrived on site, and the contractor started pulling cable into            │
│   the completed 30% trench section before Trenching finished!                                    │
│                                                                                                  │
│   Activity B has an Actual Start, but its Predecessor A is NOT Finished!                         │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

When P6 recalculates the schedule with out-of-sequence progress, it offers two primary options:

1. **Retained Logic (Standard Enterprise Best Practice):**
   - The engine respects the remaining logic tie.
   - Even though Activity B has started, its **Remaining Duration** cannot proceed until Predecessor A achieves its Actual Finish.
   - Activity B is split: actual work sits in the past, but remaining work is pushed to after Activity A finishes.

2. **Progress Override:**
   - The engine assumes the predecessor tie was invalid or circumvented.
   - It ignores the relationship for remaining duration calculation and allows Activity B's remaining duration to proceed immediately from the Data Date.

## 5. PostgreSQL Database Schema for Progress Tracking

Below is the production-grade PostgreSQL schema designed to support enterprise progress tracking, activity steps, weighted rollups, and multi-calendar compliance.

```sql
-- Enums for progress tracking
CREATE TYPE percent_complete_type_enum AS ENUM ('DURATION', 'PHYSICAL', 'UNITS');
CREATE TYPE activity_status_enum AS ENUM ('NOT_STARTED', 'IN_PROGRESS', 'COMPLETED');

-- Activities table
CREATE TABLE activities (
    activity_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL REFERENCES projects(project_id) ON DELETE CASCADE,
    activity_code VARCHAR(32) NOT NULL,
    activity_name VARCHAR(255) NOT NULL,
    calendar_id UUID NOT NULL REFERENCES calendars(calendar_id),
    
    -- Status & Progress Configuration
    status activity_status_enum NOT NULL DEFAULT 'NOT_STARTED',
    percent_complete_type percent_complete_type_enum NOT NULL DEFAULT 'PHYSICAL',
    use_steps_for_percent_complete BOOLEAN NOT NULL DEFAULT FALSE,
    
    -- Durations (Stored in Working Seconds to maintain sub-day precision)
    original_duration_seconds BIGINT NOT NULL CHECK (original_duration_seconds >= 0),
    actual_duration_seconds BIGINT NOT NULL DEFAULT 0 CHECK (actual_duration_seconds >= 0),
    remaining_duration_seconds BIGINT NOT NULL CHECK (remaining_duration_seconds >= 0),
```

## 6. Production-Grade Golang Progress Calculator Engine

Here is the clean, idiomatic Go engine implementing progress calculations, state transitions, step weightings, and validation invariants.

```go
package progress

import (
	"errors"
	"fmt"
	"math"
	"time"
)

// PercentCompleteType mirrors P6 calculation behavior.
type PercentCompleteType string

const (
	DurationPercentComplete PercentCompleteType = "DURATION"
	PhysicalPercentComplete PercentCompleteType = "PHYSICAL"
	UnitsPercentComplete    PercentCompleteType = "UNITS"
)

// ActivityStatus represents the lifecycle state of a task.
type ActivityStatus string

const (
	StatusNotStarted ActivityStatus = "NOT_STARTED"
	StatusInProgress ActivityStatus = "IN_PROGRESS"
	StatusCompleted  ActivityStatus = "COMPLETED"
)

// ActivityStep represents a weighted checklist item inside an activity.
type ActivityStep struct {
	ID                  string  `json:"id"`
	SequenceNumber      int     `json:"sequence_number"`
	Name                string  `json:"name"`
	StepWeight          float64 `json:"step_weight"`
	IsCompleted         bool    `json:"is_completed"`
	StepPercentComplete float64 `json:"step_percent_complete"` // 0.0 to 100.0
}

// Activity represents an execution node in the project schedule.
type Activity struct {
	ID                         string              `json:"id"`
	Code                       string              `json:"code"`
	Name                       string              `json:"name"`
	PercentCompleteType        PercentCompleteType `json:"percent_complete_type"`
	UseStepsForPhysicalPercent bool                `json:"use_steps_for_physical_percent"`

	Status ActivityStatus `json:"status"`

	// Durations in working seconds (e.g. 1 day = 8 * 3600 = 28800s)
	OriginalDurationSeconds  int64 `json:"original_duration_seconds"`
	ActualDurationSeconds    int64 `json:"actual_duration_seconds"`
	RemainingDurationSeconds int64 `json:"remaining_duration_seconds"`

	// Resource Units (Man-hours or Machine-hours)
	PlannedUnits   float64 `json:"planned_units"`
	ActualUnits    float64 `json:"actual_units"`
	RemainingUnits float64 `json:"remaining_units"`

	// Percent Completes (0.0 to 100.0)
	DurationPercentComplete float64 `json:"duration_percent_complete"`
	PhysicalPercentComplete float64 `json:"physical_percent_complete"`
	UnitsPercentComplete    float64 `json:"units_percent_complete"`

	ActualStart  *time.Time      `json:"actual_start,omitempty"`
	ActualFinish *time.Time      `json:"actual_finish,omitempty"`
	Steps        []*ActivityStep `json:"steps,omitempty"`
}

// StatusUpdateCommand encapsulates inputs from the site engineer on Data Date.
type StatusUpdateCommand struct {
	DataDate                 time.Time
	ActualStart              *time.Time
	ActualFinish             *time.Time
	ActualDurationSeconds    *int64
	RemainingDurationSeconds *int64
	PhysicalPercentComplete  *float64
	ActualUnits              *float64
	RemainingUnits           *float64
	StepUpdates              map[string]float64 // stepID -> stepPercent (0..100)
}

// CalculateStepPhysicalPercent computes weighted physical percent complete.
func CalculateStepPhysicalPercent(steps []*ActivityStep) (float64, error) {
	if len(steps) == 0 {
		return 0.0, nil
	}

	var totalWeight float64
	var weightedProgress float64

	for _, step := range steps {
		if step.StepWeight < 0 {
			return 0.0, fmt.Errorf("step %s has negative weight: %f", step.ID, step.StepWeight)
		}
		totalWeight += step.StepWeight

		percent := step.StepPercentComplete
		if step.IsCompleted && percent < 100.0 {
			percent = 100.0
		}
		weightedProgress += (step.StepWeight * percent)
	}

	if totalWeight <= 0 {
		return 0.0, errors.New("total weight of steps must be greater than zero")
	}

	result := weightedProgress / totalWeight
	return math.Round(result*10000) / 10000, nil // 4 decimal places
}

// ApplyProgressUpdate applies field updates and recalculates metrics.
func (a *Activity) ApplyProgressUpdate(cmd StatusUpdateCommand) error {
	// 1. Validate Actual Dates against Data Date
	if cmd.ActualStart != nil {
		if cmd.ActualStart.After(cmd.DataDate) {
			return errors.New("actual start date cannot be strictly after the data date")
		}
		a.ActualStart = cmd.ActualStart
		a.Status = StatusInProgress
	}

	if cmd.ActualFinish != nil {
		if a.ActualStart == nil {
			return errors.New("cannot set actual finish without an actual start date")
		}
		if cmd.ActualFinish.Before(*a.ActualStart) {
			return errors.New("actual finish date cannot be before actual start date")
		}
		if cmd.ActualFinish.After(cmd.DataDate) {
			return errors.New("actual finish date cannot be strictly after the data date")
		}
		a.ActualFinish = cmd.ActualFinish
		a.Status = StatusCompleted
		a.RemainingDurationSeconds = 0
		a.RemainingUnits = 0
		a.DurationPercentComplete = 100.0
		a.PhysicalPercentComplete = 100.0
		a.UnitsPercentComplete = 100.0
		return nil
	}

	// 2. Handle In-Progress Activity Updates
	if a.Status == StatusInProgress {
		// Update durations
		if cmd.ActualDurationSeconds != nil {
			if *cmd.ActualDurationSeconds < 0 {
				return errors.New("actual duration cannot be negative")
			}
			a.ActualDurationSeconds = *cmd.ActualDurationSeconds
		}

		if cmd.RemainingDurationSeconds != nil {
			if *cmd.RemainingDurationSeconds <= 0 {
				return errors.New("in-progress activity must have remaining duration > 0")
			}
			a.RemainingDurationSeconds = *cmd.RemainingDurationSeconds
		}

		// Update resource units
		if cmd.ActualUnits != nil {
			a.ActualUnits = *cmd.ActualUnits
		}
		if cmd.RemainingUnits != nil {
			a.RemainingUnits = *cmd.RemainingUnits
		}

		// 3. Compute Duration % Complete: AD / (AD + RD) * 100
		totalDur := a.ActualDurationSeconds + a.RemainingDurationSeconds
		if totalDur > 0 {
			a.DurationPercentComplete = (float64(a.ActualDurationSeconds) / float64(totalDur)) * 100.0
			a.DurationPercentComplete = math.Round(a.DurationPercentComplete*10000) / 10000
		}

		// 4. Compute Units % Complete: ActualUnits / (ActualUnits + RemainingUnits) * 100
		totalUnits := a.ActualUnits + a.RemainingUnits
		if totalUnits > 0 {
			a.UnitsPercentComplete = (a.ActualUnits / totalUnits) * 100.0
			a.UnitsPercentComplete = math.Round(a.UnitsPercentComplete*10000) / 10000
		}

		// 5. Compute Physical % Complete
		if a.UseStepsForPhysicalPercent && len(a.Steps) > 0 {
			// Apply step updates if provided
			for _, step := range a.Steps {
				if val, exists := cmd.StepUpdates[step.ID]; exists {
					step.StepPercentComplete = val
					if val >= 100.0 {
						step.IsCompleted = true
					}
				}
			}
			physPct, err := CalculateStepPhysicalPercent(a.Steps)
			if err != nil {
				return err
			}
			a.PhysicalPercentComplete = physPct
		} else if cmd.PhysicalPercentComplete != nil {
			if *cmd.PhysicalPercentComplete < 0 || *cmd.PhysicalPercentComplete > 100 {
				return errors.New("physical percent complete must be between 0 and 100")
			}
			a.PhysicalPercentComplete = *cmd.PhysicalPercentComplete
		}

		// 6. Handle coupling rule if PercentCompleteType is DURATION
		if a.PercentCompleteType == DurationPercentComplete && cmd.RemainingDurationSeconds == nil {
			// If Duration % was modified directly, recompute RD
			pctRatio := a.DurationPercentComplete / 100.0
			a.RemainingDurationSeconds = int64(float64(a.OriginalDurationSeconds) * (1.0 - pctRatio))
		}
	}

	return nil
}
```

## 8. Summary of Best Practices for Engineering Teams

1. **Mandate Physical % Complete for Work Deliverables:** Never configure physical civil, mechanical, or electrical activities as `Duration % Complete`. Use Duration % only for passive waiting periods.
2. **Decompose via Activity Steps, Not Micro-Activities:** Keep CPM graphs clean and responsive by encapsulating sub-milestone checklists inside activity steps.
3. **Always Decouple Physical % from Remaining Duration:** Allow field superintendents to independently report physical progress and future duration estimates based on actual equipment productivity.
4. **Enforce the Data Date Invariant:** Reject any user input where actual dates occur in the future ($t > DD$) or where remaining work occurs in the past ($t < DD$).
