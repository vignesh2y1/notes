## 1. Executive Summary & Mental Model: What is an Activity in Enterprise CPM?

In modern software engineering, developers are intimately familiar with "tasks" or "issues" as represented in ticketing systems like Jira, GitHub Issues, or Trello. In those tools, a task is fundamentally a **to-do item**: it has a title, an assignee, a status column (e.g., `Todo`, `In Progress`, `Done`), and perhaps an estimated number of story points or a loose due date. If a developer fails to complete an issue by Friday, the sprint backlog rolls over; no mathematical laws of physics are broken.

In industrial capital projects—such as the **Surya 100MW Solar IPP Project in Rajasthan, India**—an **Activity** in Oracle Primavera P6 is fundamentally different. An activity is **not a casual to-do item**. 

> **Mental Model: The CPM Activity as a Deterministic State Machine & Resource Consumer**
> An Activity is an indivisible, mathematically bounded unit of scope within a project network. It consumes **time** (quantified against a specific working calendar), consumes **resources** (labor man-hours, equipment plant-hours, and raw materials), incurs **costs**, and is governed by strict **topological precedence relationships** (CPM edges) and **temporal constraints**.


### The Running Case Study: Surya 100MW Solar IPP Project (Rajasthan, India)
Throughout this topic and the entire module, we anchor every architectural concept to the construction of a utility-scale 100 Megawatt (MW) photovoltaic power plant situated in the Thar Desert near Bhadla, Rajasthan:
* **Scope**: 220,000 bifacial solar modules, 3,200 single-axis trackers, 40 central inverter stations (2.5 MW each), 33 kV underground pooling collector network, and a 220 kV Grid Substation (GSS) with a 132/220 kV step-up transformer feeding into the state grid (RVPNL).
* **Environment**: Extreme ambient temperatures exceeding 48°C in summer, localized dust storms, high soil resistivity requiring chemical earthing, and seasonal monsoon interruptions.
* **Workforce & Equipment**: Multi-tier subcontracting model comprising local civil earthwork crews, specialized German-manufactured hydraulic piling rigs, imported tracker assembly technicians, and government electrical inspectors.

When building an enterprise scheduling engine in **Golang** with a **PostgreSQL** persistence tier and a **Next.js** interactive Gantt client, you cannot model activities as a generic flat table. Primavera P6 defines **6 distinct Activity Types**, each with unique mathematical behaviors in the Critical Path Method (CPM) calculation engine.

## 2. The 6 Core Activity Types in Primavera P6

Primavera P6 classifies activities into 6 distinct behavioral types. The activity type dictates:
1. Which calendar governs the start, finish, and working hours of the task.
2. How the activity interacts with assigned resource calendars.
3. Whether the activity drives CPM logic or is merely an observer (hammock/summary).
4. Whether the activity possesses physical duration or is an instantaneous milestone.

### 2.1 Type 1: Task Dependent (`TT_Task`)

#### Core Architectural Definition
A **Task Dependent** activity is the default workhorse of project scheduling. In a Task Dependent activity:
* The **Activity Calendar** is king.
* The activity’s planned duration, early start ($ES$), early finish ($EF$), late start ($LS$), and late finish ($LF$) are calculated **strictly against the calendar assigned directly to the activity**.
* Any assigned resources (laborers, engineers, equipment) are forced to conform to the activity's calendar during their assignment window, regardless of what personal calendar is assigned to the resource in the enterprise dictionary.

```
Activity Calendar: 6-Day Workweek (Mon - Sat, 10 hrs/day, Sun OFF)
Resource Calendar: 5-Day Workweek (Mon - Fri, 8 hrs/day, Sat-Sun OFF)

┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│ Task Dependent Execution:                                                                        │
│   Activity runs on Monday, Tuesday, Wednesday, Thursday, Friday, AND Saturday!                  │
│   The assigned resource is scheduled to work on Saturday according to the Activity Calendar.     │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### Production EPC Scenario (Surya Solar)
Consider `ACT-CIV-1020: Array Block 1 Ground Leveling & Grading`.
* **Assigned Activity Calendar**: `Rajasthan Site Civil 6D-10H` (Monday through Saturday, 07:00 to 18:00 with 1 hour afternoon heat siesta; Sunday non-working).
* **Assigned Resource**: `Rental Bulldozer BD-01` (whose resource dictionary calendar might be a generic vendor 5-day calendar).
* **Behavior**: Because the activity is **Task Dependent**, earthwork operations proceed on Saturday. The site schedule does not pause just because the rental equipment vendor's administrative office is closed on weekends. The project control manager schedules the site work based on the site work permit calendar.

#### When to Use Task Dependent
Use Task Dependent when work progress is constrained by the **physical project site**, work permits, environmental clearances, or subcontractor work hours, rather than by individual craft availability. If the contract states: *"Civil foundation trenching will occur 6 days a week on site,"* the activity must be Task Dependent.

### 2.2 Type 2: Resource Dependent (`TT_Rsrc`)

#### Core Architectural Definition
In a **Resource Dependent** activity, the duration and scheduled dates of the activity are governed **by the individual working calendars of the assigned resources**.
* The activity does not have an autonomous calendar schedule.
* Instead, work can only occur on dates and time slots when the assigned resource(s) are actively on shift according to their assigned **Resource Calendars**.
* If multiple resources are assigned to the same activity, work can only progress when the resources can work together (or as defined by the scheduling engine's multi-resource driving rules).

```
Activity Calendar: Irrelevant / Overridden
Resource A (Lead Piling Rig): Calendar Mon-Fri (8 hrs/day)
Resource B (NDT Inspection Tech): Calendar Tue-Sat (8 hrs/day)

┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│ Resource Dependent Execution (Driving Resources):                                                │
│   Mon: Resource A available, Resource B OFF  ──► NO PROGRESS (if both required)                 │
│   Tue: Resource A available, Resource B available ──► WORK PROCEEDS (8 hrs)                      │
│   Wed: Resource A available, Resource B available ──► WORK PROCEEDS (8 hrs)                      │
│   Thu: Resource A available, Resource B available ──► WORK PROCEEDS (8 hrs)                      │
│   Fri: Resource A available, Resource B available ──► WORK PROCEEDS (8 hrs)                      │
│   Sat: Resource A OFF, Resource B available  ──► NO PROGRESS (if both required)                 │
│                                                                                                  │
│   Result: The activity duration stretches across calendar days because work only ticks           │
│   during the intersection of the assigned resources' available shifts.                           │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### Production EPC Scenario (Surya Solar)
Consider `ACT-ELE-5020: 220kV GIS Substation Specialized High-Voltage Gas Leak & Flashover Testing`.
* **Site Situation**: The local civil and electrical contractors operate on the standard Rajasthan 6-day calendar. However, the high-voltage testing can only be performed by a certified commissioning specialist flown in from the switchgear OEM (Siemens / ABB Germany).
* **Resource Calendar**: The specialist's contract strictly enforces an expatriate rota: `EU Expat 5D-40H Calendar` (Monday–Friday, 08:00–16:00, strictly 8 hours/day, Saturday and Sunday off, with European public holidays recognized).
* **Behavior**: The activity is designated as **Resource Dependent**. Even though the Rajasthan solar substation site is bustling on Saturday, no testing progress can be made on Saturday because the certified specialist is contractually off-shift. If the testing requires 40 net working hours, the engine spans it over 5 calendar days (Mon–Fri). If it starts on Thursday, it pauses over Saturday and Sunday, completing on the following Tuesday.

#### Engine Fallback Edge Case
> [!WARNING]
> **What happens if a Resource Dependent activity has NO resources assigned?**
> In Primavera P6, if an activity is configured as `Resource Dependent` but no resources are currently assigned to it in the database, the CPM engine falls back to using the **Activity's assigned calendar** to calculate start and finish dates. In your Go engine, you must implement this exact fallback; otherwise, the forward pass will divide by zero or encounter a nil calendar pointer!

### 2.3 Type 3: Level of Effort (LOE / Hammock) (`TT_LOE`)

#### Core Architectural Definition
A **Level of Effort (LOE)** activity—historically referred to as a **Hammock activity**—does not represent a discrete, measurable deliverable with an independent planned duration. Instead, an LOE represents ongoing supervisory, administrative, or operational support work that must exist as long as other execution activities are underway.

* **Dynamic Duration**: An LOE activity has no fixed duration. Its duration is dynamically calculated by the CPM engine based on the scheduled dates of other activities in the network.
* **Precedence Ties**:
  * Its **Start Date** is governed by its driving predecessors (typically through Start-to-Start or Finish-to-Start links).
  * Its **Finish Date** is governed by its driving successors (typically through Finish-to-Finish or Start-to-Finish links).
* **The Golden Axiom of LOE Activities**:
  $$\text{LOE Start} = \min_{p \in \text{Predecessors}} (ES_p \text{ or } EF_p \text{ depending on link type})$$
  $$\text{LOE Finish} = \max_{s \in \text{Successors}} (EF_s \text{ or } ES_s \text{ depending on link type})$$

```
          [ ACT-CIV-1010: Site Grading ]  ──────[FS]──────►  [ ACT-CIV-1040: Piling Execution ]
          ES: 2026-11-02   EF: 2026-11-20                    ES: 2026-11-21   EF: 2026-12-15
                 │                                                                   │
                 │ (SS Predecessor Link)                                             │ (FF Successor Link)
                 ▼                                                                   ▼
       ┌───────────────────────────────────────────────────────────────────────────────────┐
       │ ACT-LOE-0010: Site HSE Officer Supervision & Water Mist Dust Suppression           │
       │ ES: 2026-11-02                                                    EF: 2026-12-15  │
       │ Duration: Dynamically derived = 44 calendar days (38 site working days)           │
       └───────────────────────────────────────────────────────────────────────────────────┘
```

#### Why LOE Activities NEVER Have Float and NEVER Drive the Critical Path
This is one of the most common interview and architectural design questions in enterprise project controls:

1. **Why LOE Cannot Drive**: 
   An LOE is an **observer**, not an actor. If an LOE could drive a successor task with a Finish-to-Start link, it would create an instantaneous circular dependency. If Task A expands, the LOE expands; if the expanded LOE then pushes Task B, which in turn feeds back into the LOE's successors, the network deadlocks. Therefore, the scheduling engine **completely ignores outgoing logic edges from an LOE when calculating standard activities**.
2. **Why LOE Always Has Zero Float (or Inherits Float)**:
   By mathematical definition:
   $$\text{Early Start}_{\text{LOE}} = \text{Earliest Start of Driving Predecessors}$$
   $$\text{Early Finish}_{\text{LOE}} = \text{Latest Finish of Driving Successors}$$
   During the backward pass:
   $$\text{Late Finish}_{\text{LOE}} = \text{Early Finish}_{\text{LOE}}$$
   $$\text{Late Start}_{\text{LOE}} = \text{Early Start}_{\text{LOE}}$$
   $$\text{Total Float} = LF - EF = 0$$
   An LOE cannot be delayed without delaying the underlying scope it supports; conversely, if the underlying scope is delayed, the LOE stretches automatically rather than consuming float. In Primavera P6, LOE activities display a Total Float of `0` (or match the float of the controlling activities depending on specific calculation settings), but **they are never marked with a Critical Path red bar that drives project completion**.

#### Production EPC Scenario (Surya Solar)
* `ACT-HSE-0050: Environmental Dust Suppression & Tanker Water Spraying`.
* This activity must start the day earthworks commence (`ACT-CIV-1010: Site Clearing & Grubbing`) and must continue until civil foundation backfilling finishes (`ACT-CIV-1090: Inverter Foundation Backfill`).
* If civil earthworks finish 14 days ahead of schedule, the dust suppression tanker contract ends 14 days early (saving rental costs). If rock excavation delays civil works by 30 days, the water tanker activity automatically stretches by 30 days, re-budgeting the required water tanker driver man-hours accordingly!

### 2.4 Type 4: WBS Summary (`TT_WBSummary`)

#### Core Architectural Definition
A **WBS Summary** activity is a special activity type whose dates and duration are dynamically calculated from the aggregate of **all activities that share the same WBS code (or WBS sub-branch)**.

* **Automatic Scope Aggregation**: Unlike an LOE activity—which requires explicit predecessor and successor dependency lines drawn to specific boundary tasks—a WBS Summary activity does **not** require relationship links to determine its dates.
* **Date Derivation**:
  $$\text{Early Start}_{\text{WBS Summary}} = \min \{ ES_i \mid i \in \text{Activities}(\text{Current WBS}) \}$$
  $$\text{Early Finish}_{\text{WBS Summary}} = \max \{ EF_i \mid i \in \text{Activities}(\text{Current WBS}) \}$$
* **Why Use a WBS Summary Activity Instead of a WBS Node?**
  In Topic 2.3, we established that a pure WBS node (in the `PROJWBS` table) is a structural scope folder that **cannot have direct resource assignments, cost curves, or progress tracking flags**.
  A **WBS Summary Activity** (living in the `TASK` table), however:
  1. Can have **direct resource assignments** (e.g., assigning a Lead Civil Project Manager's lump-sum salary across all civil works).
  2. Can be loaded with **expenses and overhead budget**.
  3. Can be exported via standard activity API endpoints to external ERPs (SAP S/4HANA or Oracle Fusion).

```
WBS Node: 02.01 Civil Works (Hierarchy Container - Cannot hold resources or logic)
├── ACT-CIV-1010: Grading & Grubbing       (ES: Nov 02, EF: Nov 15) [Task Dependent]
├── ACT-CIV-1020: Piling Foundations       (ES: Nov 16, EF: Dec 10) [Task Dependent]
├── ACT-CIV-1030: Inverter Pad Casting     (ES: Dec 01, EF: Dec 20) [Task Dependent]
└── ACT-CIV-SUMM: Civil Discipline Summary (ES: Nov 02, EF: Dec 20) [WBS Summary]
    └── Loaded with: Civil Project Manager (1 Month Salary = $12,000)
```

### 2.5 & 2.6 Types 5 & 6: Start Milestone (`TT_StartMile`) and Finish Milestone (`TT_FinMile`)

#### Core Architectural Definition
A **Milestone** is an instantaneous reference marker in time. It represents a significant event, a contractual commitment, a legal permitting gate, or a handoff between subcontractors.

* **Strict Invariant**:
  $$\text{Original Duration} \equiv 0, \quad \text{Remaining Duration} \equiv 0$$
* A milestone consumes **zero calendar time** and **zero resources/costs** (though expenses can occasionally be tied to contractual billing milestones in commercial setups).

#### The Subtle Mathematical Distinction: Start Milestone vs Finish Milestone
Many developers ask: *"If both have a duration of 0 hours, why does P6 distinguish between Start Milestone and Finish Milestone?"*

The difference lies in **calendar boundary timestamps** and **relationship logic binding**:

```
                       DAY D (Working Hours: 08:00:00 to 18:00:00)
  08:00:00                                                              18:00:00
  ┌────────────────────────────────────────────────────────────────────────┐
  │                           WORK SHIFT PERIOD                            │
  └────────────────────────────────────────────────────────────────────────┘
  ▲                                                                        ▲
  │                                                                        │
START MILESTONE                                                     FINISH MILESTONE
Timestamp: Day D @ 08:00:00                                         Timestamp: Day D @ 18:00:00
"Marks the opening of the window"                                   "Marks the closure of the window"
```

1. **Start Milestone (`TT_StartMile`)**:
   * Occurs at the **start of the working day/shift** (e.g., `2026-11-02 08:00:00`).
   * When connected to a successor with a Finish-to-Start (FS, lag 0) relationship, the successor starts at `2026-11-02 08:00:00` on the **same day**.
   * Represents the *commencement of a condition* (e.g., "Site Access Handed Over", "Notice to Proceed Issued").
2. **Finish Milestone (`TT_FinMile`)**:
   * Occurs at the **end of the working day/shift** (e.g., `2026-11-02 18:00:00`).
   * When connected to a successor with a Finish-to-Start (FS, lag 0) relationship, the successor cannot start until the **next available working shift** (e.g., `2026-11-03 08:00:00`).
   * Represents the *culmination of an achievement* (e.g., "Civil Foundation Works Approved by Quality Inspector", "Grid Synchronization Approved").

```
Scenario: Task A runs on Monday (Nov 02). 
If Milestone M is connected to Task A via FS (Finish-to-Start):
- If M is a FINISH MILESTONE:
  Task A finishes Nov 02 @ 18:00. Milestone M date = Nov 02 @ 18:00.
  (It records that the milestone was achieved at the close of business Monday).
- If M was modeled as a START MILESTONE:
  Task A finishes Nov 02 @ 18:00. Milestone M date = Nov 03 @ 08:00!
  (It pushes the milestone event to the start of Tuesday, creating a 1-day reporting discrepancy).
```

#### Production EPC Scenarios (Surya Solar)
* **Start Milestone**: `MS-NTP: Commercial Notice to Proceed (NTP) from SECI`.
  * Date: `2026-11-02 08:00:00`.
  * Predecessor to all initial site mobilization and topographic surveying activities.
* **Finish Milestone**: `MS-COD: Commercial Operation Date (COD) & Grid Energization`.
  * Date: `2027-05-31 18:00:00`.
  * The contractual liquidated damages deadline. If this milestone slips past May 31, the project company faces penalties of ₹500,000 INR per day from the state discom.

## 3. Deep Dive: The Scheduling Engine 3-Stage Execution Pipeline

When designing a production-grade CPM scheduling engine in Golang, a fatal architectural mistake is attempting to calculate all activities in a single topological sorting pass. 

If you feed Level of Effort (LOE) activities or WBS Summary activities directly into a standard Kahn’s Algorithm DAG sorter, you will trigger:
1. **Cycle Detection False Positives**: An LOE connected to predecessor A and successor B creates an apparent path $A \to \text{LOE} \to B$. If another relationship exists from $B \to A$ (or feedback loops), the sorter halts.
2. **Float Pollution**: LOE activities will distort the critical path, flagging administrative overhead as the critical bottleneck instead of physical piling or high-voltage cabling.

To mirror Oracle Primavera P6's scheduling engine faithfully, the scheduling calculation must execute in a **Three-Stage Pipeline**:

```
┌─────────────────────────────────────────────────────────────────────────────────────────────────┐
│                      THE 3-STAGE CPM SCHEDULING ENGINE PIPELINE                                 │
├─────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                 │
│   STAGE 1: CORE CPM ENGINE (Physical Execution DAG)                                             │
│   ├── Filter: Exclude TT_LOE and TT_WBSummary activities.                                       │
│   ├── Nodes: Only TT_Task, TT_Rsrc, TT_StartMile, TT_FinMile.                                   │
│   ├── Step 1A: Topological Sort (Kahn's Algorithm). Cycle detection aborts if graph is not DAG. │
│   ├── Step 1B: Forward Pass (ES & EF calculation across Activity/Resource Calendars).           │
│   ├── Step 1C: Backward Pass (LS & LF calculation from project target date or max EF).          │
│   └── Step 1D: Float Calculation (Total Float = LS - ES, Free Float = min(ES_succ - EF)).       │
│                                │                                                                │
│                                ▼ Core Dates Established                                         │
│   STAGE 2: LEVEL OF EFFORT (HAMMOCK) RESOLUTION                                                 │
│   ├── Target: Activities with type = TT_LOE.                                                    │
│   ├── Step 2A: For each LOE activity:                                                           │
│   │   ├── Query all incoming Predecessors (Must be Stage 1 activities).                         │
│   │   │   └── ES_LOE = min(Predecessor Early Boundary Dates)                                    │
│   │   ├── Query all outgoing Successors (Must be Stage 1 activities).                           │
│   │   │   └── EF_LOE = max(Successor Early Boundary Dates)                                      │
│   │   ├── Calculate Planned Duration = WorkHoursBetween(Calendar, ES_LOE, EF_LOE)               │
│   │   └── Set Late Dates: LS_LOE = ES_LOE, LF_LOE = EF_LOE (Total Float = 0).                   │
│                                │                                                                │
│                                ▼ LOE Dates Established                                          │
│   STAGE 3: WBS SUMMARY RESOLUTION                                                               │
│   ├── Target: Activities with type = TT_WBSummary.                                              │
│   ├── Step 3A: For each WBS Summary activity:                                                   │
│   │   ├── Identify WBS Node scope boundary.                                                     │
│   │   ├── Find all child activities (Stage 1 + Stage 2) within that WBS branch.                │
│   │   ├── ES_WBS = min(Child ES), EF_WBS = max(Child EF).                                       │
│   │   └── Calculate Duration = WorkHoursBetween(Calendar, ES_WBS, EF_WBS).                      │
│   │   └── Late Dates rollup: LS_WBS = min(Child LS), LF_WBS = max(Child LF).                    │
│                                │                                                                │
│                                ▼ Complete Schedule State                                        │
│   STAGE 4: PERSISTENCE & BROADCAST                                                              │
│   └── Commit computed date boundaries to PostgreSQL within a single read-committed transaction. │
│                                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### Stage 1: Core Physical CPM Pass
In this stage, only true driving nodes are scheduled:
1. All relationships involving LOE activities are temporarily **pruned** from the graph adjacency list.
2. For **Task Dependent** activities: Durations are mapped against the activity's assigned calendar.
3. For **Resource Dependent** activities: Durations are calculated by stepping forward through the calendar shifts of the assigned driving resource(s).
4. Start Milestones and Finish Milestones evaluate with duration $= 0$.

### Stage 2: LOE (Hammock) Resolution
Once the early and late dates of all Stage 1 activities are frozen:
1. The engine iterates over every LOE activity.
2. Its $ES$ is determined by evaluating all predecessor links:
   * For a Finish-to-Start (FS) link from Task P: $ES_{\text{LOE}} = \min(EF_P + \text{Lag})$.
   * For a Start-to-Start (SS) link from Task P: $ES_{\text{LOE}} = \min(ES_P + \text{Lag})$.
3. Its $EF$ is determined by evaluating all successor links:
   * For a Finish-to-Finish (FF) link to Task S: $EF_{\text{LOE}} = \max(EF_S - \text{Lag})$.
   * For a Start-to-Finish (SF) link to Task S: $EF_{\text{LOE}} = \max(ES_S - \text{Lag})$.
4. Once $ES_{\text{LOE}}$ and $EF_{\text{LOE}}$ are determined, the engine calls the activity calendar's `CalculateWorkingHours(ES, EF)` to compute its scheduled working duration.

### Stage 3: WBS Summary Resolution
After Stage 1 and Stage 2 have fully populated the start and finish timestamps of every physical and support activity:
1. The engine traverses the WBS hierarchy bottom-up or groups activities by `wbs_id`.
2. For every activity of type `WBS Summary`, it sets:
   $$ES = \min_{a \in \text{WBS\_Activities}, a \neq \text{Current}} (ES_a)$$
   $$EF = \max_{a \in \text{WBS\_Activities}, a \neq \text{Current}} (EF_a)$$
3. The activity duration is derived from the span across the WBS summary activity's calendar.

## 4. Activity Duration Types in Primavera P6

Beyond the Activity Type (which governs calendar and engine calculation behavior), every activity in P6 has an **Activity Duration Type**. This setting dictates how the scheduling engine handles the classic **Duration Triangle** when resources are assigned or progress is updated.

### 4.1 The Fundamental Duration Triangle
In project controls mathematics, resource loading and duration are governed by the formula:

$$\text{Planned Work (Units)} = \text{Planned Duration} \times \text{Work Rate (Units / Time)}$$

Or in software units:
$$\text{Man-Hours} = \text{Working Days} \times \left(\frac{\text{Man-Hours}}{\text{Working Day}}\right)$$

```
                                    UNITS (Work / Man-Hours)
                                              ▲
                                             / \
                                            /   \
                                           /     \
                                          /       \
                                         /         \
                                        /           \
               DURATION (Working Time) ◄─────────────► UNITS / TIME (Rate / Day)
```

When an engineer modifies one of these three variables in the software interface, **which of the remaining two variables should the engine hold constant, and which should it recompute?** 

Primavera P6 provides 4 Duration Types to control this behavior:

```
┌─────────────────────────────────────────────────────────────────────────────────────────────────┐
│                           THE 4 ACTIVITY DURATION TYPES IN P6                                   │
├──────────────────────────────┬──────────────────┬─────────────────┬─────────────────────────────┤
│ DURATION TYPE                │ HELD CONSTANT    │ RECALCULATED    │ TYPICAL USE CASE            │
├──────────────────────────────┼──────────────────┼─────────────────┼─────────────────────────────┤
│ 1. Fixed Units / Time        │ Units/Time (Rate)│ Duration or     │ Equipment / standard crew   │
│                              │                  │ Units           │ with a fixed production rate│
├──────────────────────────────┼──────────────────┼─────────────────┼─────────────────────────────┤
│ 2. Fixed Duration &          │ Duration AND     │ Units (Work)    │ Fixed window contracts,     │
│    Units / Time              │ Units/Time       │                 │ security shifts, rentals    │
├──────────────────────────────┼──────────────────┼─────────────────┼─────────────────────────────┤
│ 3. Fixed Units               │ Total Units      │ Duration or     │ Fixed quantity contracts    │
│                              │ (Total Man-Hrs)  │ Units/Time      │ (e.g., 2,400 piles to drill)│
├──────────────────────────────┼──────────────────┼─────────────────┼─────────────────────────────┤
│ 4. Fixed Duration & Units    │ Duration AND     │ Units/Time      │ Fixed-price turnkey packages│
│                              │ Total Units      │ (Burn Rate)     │ with capped total hours     │
└──────────────────────────────┴──────────────────┴─────────────────┴─────────────────────────────┘
```

### 4.2 Detailed Mechanics of the 4 Duration Types

#### 1. Fixed Units / Time (`Fixed Rate`)
* **Philosophy**: The capacity or production rate is constant.
  * Example: A specialized solar pile driving machine operates at a fixed output rate of `10 hours/day` (1.0 Units/Time).
* **Behavior**:
  * If the planner increases the **Duration** from 10 days to 20 days:
    $$\text{Units} = 20 \text{ days} \times 10 \text{ hrs/day} = 200 \text{ Man-Hours (Units increases)}$$
  * If the planner increases the **Units** (work scope) from 100 hrs to 300 hrs:
    $$\text{Duration} = \frac{300 \text{ hrs}}{10 \text{ hrs/day}} = 30 \text{ Days (Duration increases)}$$
* **Best For**: Machine-driven civil works where equipment cannot be sped up arbitrarily.

#### 2. Fixed Duration & Units / Time
* **Philosophy**: Both the calendar window and the daily resource burn rate are strictly fixed.
* **Behavior**:
  * If the user assigns a resource to a 10-day task with a rate of 8 hrs/day, the Total Units are derived:
    $$\text{Units} = 10 \times 8 = 80 \text{ hours}$$
  * If the duration changes to 15 days, the daily rate stays 8 hrs/day, and Units increases to 120 hrs.
  * If the user changes Total Units manually, P6 forces the change to reflect as an overtime/variance factor or rejects it, because both Duration and Rate are locked.
* **Best For**: **Level of Effort activities**, ongoing security guard shifts, site office rental trailers, and environmental monitoring. The guard works 8 hours a day, the task lasts as long as the phase, and the total billable hours simply track the duration.

#### 3. Fixed Units (`Fixed Scope / Quantity`)
* **Philosophy**: The total scope of work is finite and invariant.
  * Example: Installing 2,400 solar tracker torque tubes requires exactly `1,200 craft man-hours`.
* **Behavior**:
  * If you allocate **more crew** (increase Units/Time from 40 hrs/day to 80 hrs/day):
    $$\text{Duration} = \frac{1,200 \text{ hrs}}{80 \text{ hrs/day}} = 15 \text{ Days (Duration compresses!)}$$
  * If bad weather or access delays stretch the **Duration** from 30 days to 60 days:
    $$\text{Units/Time} = \frac{1,200 \text{ hrs}}{60 \text{ days}} = 20 \text{ hrs/day (Daily burn rate slows down)}$$
* **Best For**: Subcontract packages awarded on a lump-sum physical quantity basis. If the subcontractor falls behind, they must add more workers (increase Units/Time) to bring the duration back to target.

#### 4. Fixed Duration & Units
* **Philosophy**: The calendar deadline is contractually immovable, AND the total budgeted labor hours are capped.
  * Example: A 5-day factory acceptance test (FAT) capped at 80 total engineering man-hours.
* **Behavior**:
  * If the planner updates the resource assignment to add more engineers, the system automatically recalculates the required **Units/Time** (burn rate) to fit inside the fixed 5-day window without exceeding the 80-hour budget.
* **Best For**: Regulatory audits, consulting engagements, and fixed-price milestone reviews.

### 5.2 Golang Domain Models & CPM 3-Stage Pipeline Implementation

Below is a complete, production-grade Go package (`cpmengine`) implementing the domain models, calendar arithmetic interface, and the **3-Stage CPM Scheduling Worker**.

```go
// Package cpmengine implements an enterprise-grade Critical Path Method
// scheduling pipeline supporting all 6 Primavera P6 activity types.
package cpmengine

import (
	"context"
	"errors"
	"fmt"
	"time"
)

// ActivityType models the 6 P6 activity types.
type ActivityType string

const (
	TypeTaskDependent     ActivityType = "TASK_DEPENDENT"
	TypeResourceDependent ActivityType = "RESOURCE_DEPENDENT"
	TypeLevelOfEffort     ActivityType = "LEVEL_OF_EFFORT"
	TypeWBSSummary        ActivityType = "WBS_SUMMARY"
	TypeStartMilestone    ActivityType = "START_MILESTONE"
	TypeFinishMilestone   ActivityType = "FINISH_MILESTONE"
)

// DurationType models the 4 P6 duration types.
type DurationType string

const (
	FixedUnitsPerTime              DurationType = "FIXED_UNITS_PER_TIME"
	FixedDurationAndUnitsPerTime   DurationType = "FIXED_DURATION_AND_UNITS_PER_TIME"
	FixedUnits                     DurationType = "FIXED_UNITS"
	FixedDurationAndUnits          DurationType = "FIXED_DURATION_AND_UNITS"
)

// RelationshipType models CPM dependency link types.
type RelationshipType string

const (
	RelFS RelationshipType = "FS"
	RelSS RelationshipType = "SS"
	RelFF RelationshipType = "FF"
	RelSF RelationshipType = "SF"
)

// Relationship represents a directed CPM precedence edge.
type Relationship struct {
	ID             string
	PredActivityID string
	SuccActivityID string
	Type           RelationshipType
	LagMinutes     int
}

// Activity represents the in-memory domain model of an execution node.
type Activity struct {
	ID                       string
	WBSID                    string
	CalendarID               string
	Code                     string
	Name                     string
	Type                     ActivityType
	DurationType             DurationType
	OriginalDurationMinutes  int
	RemainingDurationMinutes int

	// Calculated CPM Dates
	EarlyStart time.Time
	EarlyFinish time.Time
	LateStart   time.Time
	LateFinish  time.Time

	TotalFloatMinutes int
	FreeFloatMinutes  int
	IsCritical        bool

	// Adjacency edges for topological sorting
	Predecessors []*Relationship
	Successors   []*Relationship
}

// CalendarService defines the interface for project calendar arithmetic.
type CalendarService interface {
	AddWorkingDuration(calID string, start time.Time, durationMinutes int) (time.Time, error)
	SubtractWorkingDuration(calID string, finish time.Time, durationMinutes int) (time.Time, error)
	CalculateWorkingMinutes(calID string, start, finish time.Time) (int, error)
	NormalizeStart(calID string, t time.Time) time.Time
	NormalizeFinish(calID string, t time.Time) time.Time
}

// CPMScheduler orchestrates the 3-stage execution pipeline.
type CPMScheduler struct {
	calSvc CalendarService
}

func NewCPMScheduler(calSvc CalendarService) *CPMScheduler {
	return &CPMScheduler{calSvc: calSvc}
}

// ScheduleProject executes the full 3-Stage CPM forward and backward pipeline.
func (s *CPMScheduler) ScheduleProject(
	ctx context.Context,
	projectStartDate time.Time,
	activities map[string]*Activity,
) error {
	// Partition activities by pipeline stage
	stage1Activities := make(map[string]*Activity)
	loeActivities := make(map[string]*Activity)
	wbsSummaryActivities := make(map[string]*Activity)

	for id, act := range activities {
		switch act.Type {
		case TypeTaskDependent, TypeResourceDependent, TypeStartMilestone, TypeFinishMilestone:
			stage1Activities[id] = act
		case TypeLevelOfEffort:
			loeActivities[id] = act
		case TypeWBSSummary:
			wbsSummaryActivities[id] = act
		default:
			return fmt.Errorf("unrecognized activity type: %s", act.Type)
		}
	}

	// -------------------------------------------------------------
	// STAGE 1: CORE CPM PASS (Physical Execution Graph)
	// -------------------------------------------------------------
	order, err := s.topologicalSort(stage1Activities)
	if err != nil {
		return fmt.Errorf("stage 1 topological sort failed: %w", err)
	}

	// Step 1A: Forward Pass
	if err := s.forwardPassStage1(projectStartDate, order, stage1Activities); err != nil {
		return fmt.Errorf("stage 1 forward pass failed: %w", err)
	}

	// Step 1B: Backward Pass
	if err := s.backwardPassStage1(order, stage1Activities); err != nil {
		return fmt.Errorf("stage 1 backward pass failed: %w", err)
	}

	// -------------------------------------------------------------
	// STAGE 2: LEVEL OF EFFORT (HAMMOCK) RESOLUTION
	// -------------------------------------------------------------
	if err := s.resolveLOEStage2(loeActivities, stage1Activities); err != nil {
		return fmt.Errorf("stage 2 LOE resolution failed: %w", err)
	}

	// -------------------------------------------------------------
	// STAGE 3: WBS SUMMARY RESOLUTION
	// -------------------------------------------------------------
	if err := s.resolveWBSSummaryStage3(wbsSummaryActivities, activities); err != nil {
		return fmt.Errorf("stage 3 WBS summary resolution failed: %w", err)
	}

	return nil
}

// topologicalSort performs Kahn's Algorithm on Stage 1 activities only.
func (s *CPMScheduler) topologicalSort(nodes map[string]*Activity) ([]string, error) {
	inDegree := make(map[string]int)
	for id := range nodes {
		inDegree[id] = 0
	}

	// Compute in-degree considering only links between Stage 1 nodes
	for _, act := range nodes {
		for _, succRel := range act.Successors {
			if _, exists := nodes[succRel.SuccActivityID]; exists {
				inDegree[succRel.SuccActivityID]++
			}
		}
	}

	var queue []string
	for id, deg := range inDegree {
		if deg == 0 {
			queue = append(queue, id)
		}
	}

	var sorted []string
	for len(queue) > 0 {
		currID := queue[0]
		queue = queue[1:]
		sorted = append(sorted, currID)

		currAct := nodes[currID]
		for _, succRel := range currAct.Successors {
			if _, exists := nodes[succRel.SuccActivityID]; exists {
				inDegree[succRel.SuccActivityID]--
				if inDegree[succRel.SuccActivityID] == 0 {
					queue = append(queue, succRel.SuccActivityID)
				}
			}
		}
	}

	if len(sorted) != len(nodes) {
		return nil, errors.New("cyclic dependency detected in Stage 1 activities")
	}

	return sorted, nil
}

// forwardPassStage1 computes Early Start and Early Finish for standard activities.
func (s *CPMScheduler) forwardPassStage1(
	projectStart time.Time,
	order []string,
	nodes map[string]*Activity,
) error {
	for _, id := range order {
		act := nodes[id]
		earliestStart := projectStart

		// Evaluate driving predecessors
		for _, predRel := range act.Predecessors {
			pred, exists := nodes[predRel.PredActivityID]
			if !exists {
				continue // Skip LOE or non-Stage 1 predecessors
			}

			var candidate time.Time
			switch predRel.Type {
			case RelFS:
				candidate = pred.EarlyFinish.Add(time.Duration(predRel.LagMinutes) * time.Minute)
			case RelSS:
				candidate = pred.EarlyStart.Add(time.Duration(predRel.LagMinutes) * time.Minute)
			case RelFF:
				// EF = candidate; ES derived backwards
				effCandidate := pred.EarlyFinish.Add(time.Duration(predRel.LagMinutes) * time.Minute)
				esFromFF, err := s.calSvc.SubtractWorkingDuration(act.CalendarID, effCandidate, act.RemainingDurationMinutes)
				if err == nil && esFromFF.After(earliestStart) {
					earliestStart = esFromFF
				}
				continue
			case RelSF:
				effCandidate := pred.EarlyStart.Add(time.Duration(predRel.LagMinutes) * time.Minute)
				esFromSF, err := s.calSvc.SubtractWorkingDuration(act.CalendarID, effCandidate, act.RemainingDurationMinutes)
				if err == nil && esFromSF.After(earliestStart) {
					earliestStart = esFromSF
				}
				continue
			}

			if candidate.After(earliestStart) {
				earliestStart = candidate
			}
		}

		act.EarlyStart = s.calSvc.NormalizeStart(act.CalendarID, earliestStart)

		// Handle Milestones (0 duration)
		if act.Type == TypeStartMilestone || act.Type == TypeFinishMilestone || act.RemainingDurationMinutes == 0 {
			act.EarlyFinish = act.EarlyStart
		} else {
			ef, err := s.calSvc.AddWorkingDuration(act.CalendarID, act.EarlyStart, act.RemainingDurationMinutes)
			if err != nil {
				return err
			}
			act.EarlyFinish = ef
		}
	}
	return nil
}

// backwardPassStage1 computes Late Finish, Late Start, and Floats.
func (s *CPMScheduler) backwardPassStage1(order []string, nodes map[string]*Activity) error {
	if len(order) == 0 {
		return nil
	}

	// Find maximum Early Finish across the project
	var maxProjectEF time.Time
	for _, act := range nodes {
		if act.EarlyFinish.After(maxProjectEF) {
			maxProjectEF = act.EarlyFinish
		}
	}

	// Traverse in reverse topological order
	for i := len(order) - 1; i >= 0; i-- {
		id := order[i]
		act := nodes[id]
		latestFinish := maxProjectEF

		firstSuccessor := true
		for _, succRel := range act.Successors {
			succ, exists := nodes[succRel.SuccActivityID]
			if !exists {
				continue
			}

			var candidate time.Time
			switch succRel.Type {
			case RelFS:
				candidate = succ.LateStart.Add(-time.Duration(succRel.LagMinutes) * time.Minute)
			case RelFF:
				candidate = succ.LateFinish.Add(-time.Duration(succRel.LagMinutes) * time.Minute)
			case RelSS:
				lsCandidate := succ.LateStart.Add(-time.Duration(succRel.LagMinutes) * time.Minute)
				lfFromSS, err := s.calSvc.AddWorkingDuration(act.CalendarID, lsCandidate, act.RemainingDurationMinutes)
				if err == nil && (firstSuccessor || lfFromSS.Before(latestFinish)) {
					latestFinish = lfFromSS
					firstSuccessor = false
				}
				continue
			case RelSF:
				lsCandidate := succ.LateFinish.Add(-time.Duration(succRel.LagMinutes) * time.Minute)
				lfFromSF, err := s.calSvc.AddWorkingDuration(act.CalendarID, lsCandidate, act.RemainingDurationMinutes)
				if err == nil && (firstSuccessor || lfFromSF.Before(latestFinish)) {
					latestFinish = lfFromSF
					firstSuccessor = false
				}
				continue
			}

			if firstSuccessor || candidate.Before(latestFinish) {
				latestFinish = candidate
				firstSuccessor = false
			}
		}

		act.LateFinish = s.calSvc.NormalizeFinish(act.CalendarID, latestFinish)

		if act.Type == TypeStartMilestone || act.Type == TypeFinishMilestone || act.RemainingDurationMinutes == 0 {
			act.LateStart = act.LateFinish
		} else {
			ls, err := s.calSvc.SubtractWorkingDuration(act.CalendarID, act.LateFinish, act.RemainingDurationMinutes)
			if err != nil {
				return err
			}
			act.LateStart = ls
		}

		// Calculate Floats
		floatMinutes, _ := s.calSvc.CalculateWorkingMinutes(act.CalendarID, act.EarlyStart, act.LateStart)
		act.TotalFloatMinutes = floatMinutes
		if act.TotalFloatMinutes <= 0 {
			act.IsCritical = true
		}
	}
	return nil
}

// resolveLOEStage2 resolves Hammock dates from Stage 1 boundaries.
func (s *CPMScheduler) resolveLOEStage2(
	loeActivities map[string]*Activity,
	stage1Activities map[string]*Activity,
) error {
	for _, loe := range loeActivities {
		var earliestStart time.Time
		hasPredecessors := false

		// Find earliest start boundary from predecessors
		for _, predRel := range loe.Predecessors {
			pred, exists := stage1Activities[predRel.PredActivityID]
			if !exists {
				continue
			}
			var cand time.Time
			if predRel.Type == RelSS || predRel.Type == RelSF {
				cand = pred.EarlyStart
			} else {
				cand = pred.EarlyFinish
			}

			if !hasPredecessors || cand.Before(earliestStart) {
				earliestStart = cand
				hasPredecessors = true
			}
		}

		var latestFinish time.Time
		hasSuccessors := false

		// Find latest finish boundary from successors
		for _, succRel := range loe.Successors {
			succ, exists := stage1Activities[succRel.SuccActivityID]
			if !exists {
				continue
			}
			var cand time.Time
			if succRel.Type == RelFF || succRel.Type == RelFS {
				cand = succ.EarlyFinish
			} else {
				cand = succ.EarlyStart
			}

			if !hasSuccessors || cand.After(latestFinish) {
				latestFinish = cand
				hasSuccessors = true
			}
		}

		if hasPredecessors {
			loe.EarlyStart = earliestStart
		}
		if hasSuccessors {
			loe.EarlyFinish = latestFinish
		}

		// Calculate dynamic working duration
		workMinutes, err := s.calSvc.CalculateWorkingMinutes(loe.CalendarID, loe.EarlyStart, loe.EarlyFinish)
		if err == nil {
			loe.OriginalDurationMinutes = workMinutes
			loe.RemainingDurationMinutes = workMinutes
		}

		// Invariant: LOE has zero float and late dates match early dates
		loe.LateStart = loe.EarlyStart
		loe.LateFinish = loe.EarlyFinish
		loe.TotalFloatMinutes = 0
		loe.IsCritical = false // Never drives the critical path
	}
	return nil
}

// resolveWBSSummaryStage3 rolls up boundaries for WBS Summary activities.
func (s *CPMScheduler) resolveWBSSummaryStage3(
	wbsSummaries map[string]*Activity,
	allActivities map[string]*Activity,
) error {
	for _, summary := range wbsSummaries {
		var minStart time.Time
		var maxFinish time.Time
		foundChildren := false

		for _, act := range allActivities {
			// Find siblings in the same WBS branch (excluding the summary itself)
			if act.WBSID == summary.WBSID && act.ID != summary.ID {
				if !foundChildren || act.EarlyStart.Before(minStart) {
					minStart = act.EarlyStart
				}
				if !foundChildren || act.EarlyFinish.After(maxFinish) {
					maxFinish = act.EarlyFinish
				}
				foundChildren = true
			}
		}

		if foundChildren {
			summary.EarlyStart = minStart
			summary.EarlyFinish = maxFinish
			summary.LateStart = minStart
			summary.LateFinish = maxFinish
			summary.TotalFloatMinutes = 0
			summary.IsCritical = false

			workMinutes, err := s.calSvc.CalculateWorkingMinutes(summary.CalendarID, minStart, maxFinish)
			if err == nil {
				summary.OriginalDurationMinutes = workMinutes
				summary.RemainingDurationMinutes = workMinutes
			}
		}
	}
	return nil
}
```

## 6. Industrial Best Practices, Antipatterns & Senior Mentor Pitfalls

When managing or auditing scheduling systems for multi-crore infrastructure projects like the Surya 100MW Solar IPP, senior project controls architects must enforce rigorous standards:

### 1. The LOE Successor Trap (DCMA 14-Point Violation)
* **The Antipattern**: A junior planner draws a Finish-to-Start link from an LOE activity (e.g., `Site Supervision`) to a physical activity (e.g., `Array Block 2 Inverter Testing`).
* **The Disaster**: In naive scheduling engines, this creates an artificial constraint where physical construction waits for administrative supervision. In standard P6 engines, it corrupts the backward pass.
* **The Rule**: **LOE activities must never have outgoing relationships that drive non-LOE activities.** All relationships to normal activities must be incoming Start links or outgoing Finish links that define the LOE's boundaries.

### 2. Misusing Resource Dependent for Common Crew Shortages
* **The Antipattern**: Marking all civil activities as "Resource Dependent" because the project currently only has 2 civil foreman crews.
* **The Solution**: Do **not** use Resource Dependent activity types to solve resource leveling! Activity types govern *working calendar shift alignment* (e.g., expat rotas or tidal construction windows). Resource constraints should be resolved via the **Resource Leveling Algorithm (Heuristic Leveling)**, leaving the activities as Task Dependent.

### 3. Start vs Finish Milestone Confusion in Contractual Handover
* **The Antipattern**: Marking `Commercial Operation Date (COD)` as a Start Milestone.
* **The Consequence**: If COD is set as a Start Milestone on May 31, its timestamp is `08:00:00`. It implies the project was operational at the beginning of May 31, whereas the grid synchronization testing was only certified at 17:30:00 at the end of the day. For contractual completions, warranties, and handover points, **always use Finish Milestones**.
