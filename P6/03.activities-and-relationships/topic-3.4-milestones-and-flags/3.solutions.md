## 🏛️ Section A: Conceptual & Temporal Mechanics

### Solution 1: The Zero-Duration Paradox & The 1-Day Fencepost Error

#### 1. Case A: Finish Milestone Date Assignment
A **Finish Milestone** represents the completion of an activity or phase. By definition in the Critical Path Method (CPM) and Primavera P6:
* Its Early Finish ($EF$) matches the finish moment of its driving predecessor when linked via Finish-to-Start ($FS$, $\text{Lag}=0$).
* Its Early Start ($ES$) is identical to its Early Finish ($ES = EF$) because its planned duration is zero ($OD = 0$).
* It snaps to the **close of the working day** (`17:00:00`).

$$\text{Predecessor Finish} = \text{Friday, 13-Feb-2026 at 17:00:00}$$
$$ES(\text{M-SUB-CIVIL}) = \mathbf{\text{Friday, 13-Feb-2026 at 17:00:00}}$$
$$EF(\text{M-SUB-CIVIL}) = \mathbf{\text{Friday, 13-Feb-2026 at 17:00:00}}$$
$$\text{Display Date} = \mathbf{\text{13-Feb-2026}}$$

---

#### 2. Case B: Start Milestone Date Assignment
A **Start Milestone** marks the *initiation* of work. By definition:
* A Start Milestone timestamps at the **opening moment of a working period** (`08:00:00`).
* When an $FS$ ($\text{Lag}=0$) relationship connects a predecessor task finishing on Friday at 17:00:00 to a Start Milestone, the CPM scheduling engine computes:
  $$\text{Earliest Successor Start} = \text{Next Available Working Instant after } EF(\text{Pred})$$
* On a 6-day calendar (Mon–Sat working, Sunday non-working), the next working instant after Friday 17:00:00 is **Saturday, 14-Feb-2026 at 08:00:00**.

$$ES(\text{M-SUB-CIVIL}) = \mathbf{\text{Saturday, 14-Feb-2026 at 08:00:00}}$$
$$EF(\text{M-SUB-CIVIL}) = \mathbf{\text{Saturday, 14-Feb-2026 at 08:00:00}}$$
$$\text{Display Date} = \mathbf{\text{14-Feb-2026}}$$

---

#### 3. The Calendar Boundary Discrepancy
* **For Friday Finish:**
  * Physical elapsed time: 15 hours of non-working night hours (from Friday 17:00 to Saturday 08:00).
  * Calendar display date difference: **+1 Calendar Day** (13-Feb vs 14-Feb).

* **For Saturday Finish (The Weekend Trap):**
  * If `Act 201` finishes on **Saturday, 14-Feb-2026 at 17:00:00**:
    * **Case A (Finish Milestone):** Snaps to **Saturday, 14-Feb-2026 at 17:00:00**. Display Date = `14-Feb-2026`.
    * **Case B (Start Milestone):** The next available working instant is NOT Sunday (Sunday is non-working in Rajasthan). The engine skips Sunday, 15-Feb, and advances to **Monday, 16-Feb-2026 at 08:00:00**!
    * **Discrepancy:**
      $$\Delta T = \text{Monday 16-Feb} - \text{Saturday 14-Feb} = \mathbf{2\text{ calendar days (or 3 days over a long holiday weekend)}}!$$

```
   FRIDAY 13-FEB           SATURDAY 14-FEB           SUNDAY 15-FEB           MONDAY 16-FEB
┌──────────────────┐    ┌──────────────────┐      ┌──────────────────┐    ┌──────────────────┐
│ 08:00      17:00 │    │ 08:00      17:00 │      │   NON-WORKING    │    │ 08:00      17:00 │
└──────────────┬───┘    └──────────────────┘      └──────────────────┘    └───┬──────────────┘
               ▲                                                              ▲
               │                                                              │
         [Case A Finish MS]                                             [Case B Start MS]
         13-Feb 17:00:00                                                16-Feb 08:00:00
         (On-Time!)                                                     (3 Days Delayed!)
```

---

#### 4. Contractual Failure Mode
Under FIDIC Silver Book / Indian Contract Act:
1. **False Breach of Contract:** The contractor finished 100% of the physical scope on Friday, 13-Feb-2026. However, because the software report displays `14-Feb-2026` (or `16-Feb-2026` if over a weekend), the Owner's Automated Project Management System flags the milestone as **LATE**.
2. **Prejudicial Audit Records:** In contractual arbitrations, automated schedule extracts serve as primary legal evidence. The contractor must expend legal fees and expert testimony proving that software date snapping caused a phantom delay.
3. **Engine Design Rule:** 
   > Completion of scope must **always** be modeled as a **Finish Milestone** ($T_{\text{end}}$), never a Start Milestone.

### Solution 2: CPM Dependency Matrix & Milestone Boundary Permutations

Let predecessor $P$ have $D_P = 5\text{ days}$, $ES = \text{Day 1, 08:00}$, $EF = \text{Day 5, 17:00}$.

#### 1. Predecessor Task $\to$ Successor Milestone ($Lag = 0$)

| Relationship | Successor Type | Governing Date Formula | Resulting Date |
| :--- | :--- | :--- | :--- |
| **FS (0)** | $M_{\text{start}}$ | $\text{NextWorkStart}(EF(P))$ | **Day 6, 08:00** |
| **FS (0)** | $M_{\text{finish}}$ | $EF(P)$ (snaps to predecessor completion instant) | **Day 5, 17:00** |
| **SS (0)** | $M_{\text{start}}$ | $ES(P)$ (snaps to predecessor start instant) | **Day 1, 08:00** |
| **SS (0)** | $M_{\text{finish}}$ | $\text{DayEnd}(ES(P))$ | **Day 1, 17:00** |
| **FF (0)** | $M_{\text{start}}$ | $\text{NextWorkStart}(EF(P))$ | **Day 6, 08:00** |
| **FF (0)** | $M_{\text{finish}}$ | $EF(P)$ | **Day 5, 17:00** |
| **SF (0)** | $M_{\text{start}}$ | $\text{DayStart}(ES(P))$ | **Day 1, 08:00** |
| **SF (0)** | $M_{\text{finish}}$ | $\text{DayEnd}(ES(P))$ | **Day 1, 17:00** |

---

#### 2. Predecessor Milestone $\to$ Successor Task ($D_S = 4\text{ days}$)

* **When $M$ is a Start Milestone (Day 1, 08:00):**
  * **FS (0):** Because $M$ has zero duration, it completes at Day 1, 08:00. The successor $S$ starts immediately at **Day 1, 08:00**.
    $$ES(S) = \text{Day 1, 08:00}, \quad EF(S) = \text{Day 4, 17:00}$$
  * **SS (0):** Aligns the start of $S$ with the start of $M$.
    $$ES(S) = \text{Day 1, 08:00}, \quad EF(S) = \text{Day 4, 17:00}$$
  *(Notice that for a Start Milestone driving a task, $FS(0)$ and $SS(0)$ yield identical dates!)*

* **When $M$ is a Finish Milestone (Day 1, 17:00):**
  * **FS (0):** $M$ finishes at Day 1, 17:00. The successor $S$ starts at the beginning of the next working day:
    $$ES(S) = \text{Day 2, 08:00}, \quad EF(S) = \text{Day 5, 17:00}$$
  * **SS (0):** The start of $S$ is bound to the "start" of the Finish Milestone. Since a Finish Milestone sits at Day 1, 17:00, setting $SS(0)$ forces $S$ to start at Day 1, 17:00 (consuming 0 working hours on Day 1), pushing its effective work into Days 2 through 5.

---

#### 3. The SS Anomaly on Finish Milestones
Using an $SS$ relationship on an incoming Finish Milestone or an $FF$ relationship on an outgoing Start Milestone is an architectural defect:
* A **Finish Milestone** represents the end of an activity. A Start-to-Start link attempts to bind logic to the "beginning" of an activity that has no beginning separate from its end.
* If a planner writes `Task A (SS) -> Finish Milestone`, the Finish Milestone is triggered when `Task A` starts. This means a milestone titled "Inverters Commissioned" would trigger on the day commissioning *begins*, violating common sense and contract semantics.

### Solution 3: Float Propagation and Critical Path Mechanics on Zero-Duration Nodes

```
  [Act 101: Inverter 1 Found] (8d) [ES=1, EF=8, LS=1, LF=8] ───┐ (FS)
                                                                ▼
                                                [◆ M-INV-CIVIL] ──► [Act 103: Skid Placement] (5d)
                                                                │   [ES=9, EF=13, LS=9, LF=13]
  [Act 102: Inverter 2 Found] (6d) [ES=1, EF=6, LS=3, LF=8] ───┘ (FS)
                                                                └──► [Act 104: Trenching] (10d)
                                                                    [ES=9, EF=18, LS=12, LF=21]
```

#### 1. Derivation of Dates and Total Float for `M-INV-CIVIL`
* **Forward Pass (Early Dates):**
  $$EF(M) = \max \Big( EF(\text{Act 101}), EF(\text{Act 102}) \Big) = \max(8, 6) = \mathbf{8}$$
  $$ES(M) \equiv EF(M) = \mathbf{8}$$
* **Backward Pass (Late Dates):**
  Successors: `Act 103` ($LS = 9$), `Act 104` ($LS = 12$).
  Under $FS$ logic, predecessor late finish is bounded by $\min(LS(\text{Succ}) - 1)$:
  $$LF(M) = \min(LS(\text{Act 103}) - 1, LS(\text{Act 104}) - 1) = \min(9 - 1, 12 - 1) = \min(8, 11) = \mathbf{8}$$
  $$LS(M) \equiv LF(M) = \mathbf{8}$$
* **Total Float ($TF$):**
  $$TF(M) = LF(M) - EF(M) = 8 - 8 = \mathbf{0\text{ days (Critical Node)}}$$

---

#### 2. Free Float ($FF$) Calculation
Free Float is the amount of time an activity can slip without delaying the early start of any immediate successor:
$$FF(M) = \min_{S \in \text{Successors}(M)} \Big( ES(S) - 1 \Big) - EF(M)$$
* For `Act 103`: $ES(\text{Act 103}) = 9 \implies 9 - 1 - 8 = 0$.
* For `Act 104`: $ES(\text{Act 104}) = 9 \implies 9 - 1 - 8 = 0$.
$$FF(M) = \min(0, 0) = \mathbf{0\text{ days}}$$

---

#### 3. Network Configuration Where $TF > 0$ and $FF = 0$
Yes, a milestone can easily have $TF > 0$ and $FF = 0$.

**Construction:**
* Let `M-GATE` have $EF = 10$.
* Successor `Task S1` has $ES = 11$, but $LS = 15$ ($TF = 4$).
* Successor `Task S2` has $ES = 11$, but $LS = 18$ ($TF = 7$).
* Then:
  $$LF(\text{M-GATE}) = \min(15 - 1, 18 - 1) = 14$$
  $$TF(\text{M-GATE}) = LF - EF = 14 - 10 = \mathbf{4\text{ days}}$$
  $$FF(\text{M-GATE}) = \min(11 - 1, 11 - 1) - 10 = 10 - 10 = \mathbf{0\text{ days}}$$
* **Operational Meaning:** Any delay to `M-GATE` will immediately delay the Early Start of `Task S1` ($FF = 0$), but will **not** delay the project completion date because there are 4 days of float buffer ($TF = 4$).

---

#### 4. Mandatory Finish Constraint of Day 7
If a **Mandatory Finish = Day 7** constraint is applied to `M-INV-CIVIL`:
* The Late Finish is overridden by the constraint date:
  $$LF(M) = 7, \quad LS(M) = 7$$
* **Total Float of `M-INV-CIVIL`:**
  $$TF(M) = LF(M) - EF(M) = 7 - 8 = \mathbf{-1\text{ working day}}$$
* **Backward Propagation to Predecessor `Act 101`:**
  $$LF(\text{Act 101}) = LS(M) = 7$$
  $$LS(\text{Act 101}) = LF - D + 1 = 7 - 8 + 1 = 0$$
  $$TF(\text{Act 101}) = LF - EF = 7 - 8 = \mathbf{-1\text{ working day}}$$

**Contractual Signification:**
Negative total float ($TF < 0$) is the mathematical signature of a **projected contractual breach**. It proves that even if work proceeds without further delay, the project will breach its contractually committed milestone by 1 working day unless accelerated.

### Solution 4: Historical P3 Flags vs Modern P6 Milestones & UDF Indicators

#### 1. Topological Differences & Graph Traversal
In legacy Primavera P3 (1980s–1990s):
* **Flags** were point events placed on the barchart that did **not** participate in the topological DAG. They could not have predecessor or successor relationship links ($FS, SS, FF, SF$).
* **Mathematical Consequence:**
  * Because a Flag had no edges, it did not participate in the Backward Pass.
  * A Flag had **no computed Late Dates** ($LS, LF$) and **no Total Float**.
  * Delays in activities preceding a flag did not automatically push the flag, and delays in the flag did not push downstream tasks. Planners had to manually align them.

---

#### 2. Comparative Matrix: Modern Architecture

| Feature | Legacy P3 Flag | Modern P6 Milestone | Modern P6 Activity Code / UDF Indicator |
| :--- | :--- | :--- | :--- |
| **CPM DAG Node** | No (Non-network marker) | **Yes** (True zero-duration node) | No (Metadata attribute on task) |
| **Relationships Allowed** | None | Full ($FS, SS, FF, SF$ with lag) | None |
| **Float Calculation** | None (N/A) | Exact ($TF = LF - EF$) | Inherits from parent activity |
| **Resource Loading** | Prohibited | Prohibited (best practice) | Prohibited |
| **Filtering & Grouping** | Limited | Yes (by Activity Type) | **Primary mechanism** for grouping & color coding |
| **Dashboarding Role** | Obsolete | Contractual gates, phase handovers | Categorization (e.g., "Vendor: ABB", "Phase: 1") |

### Solution 5: Tier 1 Contractual Milestones & Liquidated Damages (Surya 100MW Solar IPP)

#### 1. Interim Withholding Penalty for `M-GRID`
* Contractual Target Date: **15-Oct-2026**
* Forecast / Actual Early Finish: **09-Nov-2026**
* Calendar Days of Delay ($\Delta T_{\text{grid}}$):
  * October 15 to October 31 = $31 - 15 = 16\text{ days}$
  * November 01 to November 09 = $9\text{ days}$
  $$\Delta T_{\text{grid}} = 16 + 9 = \mathbf{25\text{ calendar days}}$$
* Interim Penalty Rate: ₹10,00,000 per day.
$$\text{Interim Withheld} = 25 \times ₹10,00,000 = \mathbf{₹2,50,00,000 \text{ (₹2.50 Crore)}}$$

---

#### 2. Final Delay Liquidated Damages for `M-COD`
* Contractual COD Target: **30-Nov-2026**
* Actual COD Achieved: **18-Dec-2026**
* Calendar Days of Delay ($\Delta T_{\text{COD}}$):
  $$\Delta T_{\text{COD}} = 18 - 0 = \mathbf{18\text{ calendar days}}$$
* Daily Delay LD Rate: $0.05\%$ of Contract Price.
  $$V_C = ₹420,00,00,000$$
  $$\text{Daily LD} = ₹420,00,00,000 \times 0.0005 = \mathbf{₹21,00,000 \text{ per day}}$$
* Total Final Delay LD Liability:
  $$\text{Final Delay LD} = 18\text{ days} \times ₹21,00,000 = \mathbf{₹3,78,00,000 \text{ (₹3.78 Crore)}}$$

---

#### 3. Net Financial Settlement
Under FIDIC Clause 8.2 and the contract's reversion provisions:
* The interim penalty of ₹2.50 Crore was a **temporary retention**, not an independent liquidated damage.
* The total ultimate liability of the contractor for delay is governed exclusively by the Final Delay LD amount: ₹3.78 Crore.
* Net deduction from final invoice:
  $$\text{Net Payment Deducted} = \text{Final LD} - \text{Interim Withholding} = ₹3,78,00,000 - ₹2,50,00,000 = \mathbf{₹1,28,00,000 \text{ (₹1.28 Crore Additional)}}$$

---

#### 4. Maximum Delay Cap
* **Maximum LD Cap:** $10.0\%$ of $V_C$:
  $$\text{Max LD Cap} = 10\% \times ₹420,00,00,000 = \mathbf{₹42,00,00,000 \text{ (₹42 Crore)}}$$
* Maximum billable delay days before cap is reached:
  $$\text{Days to Cap} = \frac{₹42,00,00,000}{₹21,00,000/\text{day}} = \mathbf{200\text{ calendar days}}$$
*(Past 200 calendar days of delay, the employer cannot deduct further LDs, but gains the immediate contractual right to terminate for default under FIDIC Clause 15.2).*

---

#### 5. Extension of Time (EoT) Recalculation
* **Approved EoT:** 14 calendar days.
* **Revised Contractual COD Date:**
  $$30\text{-Nov-2026} + 14\text{ calendar days} = \mathbf{14\text{-Dec-2026}}$$
* **Net Unexcused Delay:**
  $$\text{Actual COD (18-Dec)} - \text{Revised Target (14-Dec)} = \mathbf{4\text{ calendar days}}$$
* **Revised Final LD Liability:**
  $$\text{Revised LD} = 4\text{ days} \times ₹21,00,000/\text{day} = \mathbf{₹84,00,000 \text{ (₹84 Lakhs)}}$$
* **Refund to Contractor:**
  Since the Owner had withheld ₹2.50 Crore in interim penalties, the Owner must **refund** ₹1.66 Crore back to the contractor:
  $$\text{Refund} = ₹2,50,00,000 - ₹84,00,000 = \mathbf{₹1,66,00,000 \text{ (₹1.66 Crore)}}$$

### Solution 6: Phase Gate Architecture & Fan-In / Fan-Out Network Design

#### 1. Architecture A: Direct Dependency Mesh
* Number of Predecessors ($M$): 8
* Number of Successors ($N$): 5
$$E_{\text{mesh}} = M \times N = 8 \times 5 = \mathbf{40\text{ relationships}}$$

---

#### 2. Architecture B: Phase Gate Design
* Predecessors fan-in to Phase Gate: 8 links
* Phase Gate fans-out to Successors: 5 links
$$E_{\text{gate}} = M + N = 8 + 5 = \mathbf{13\text{ relationships}}$$

---

#### 3. Generalization and Complexity Comparison
$$\Delta E = (M \times N) - (M + N)$$
For $M=8, N=5$:
$$\Delta E = 40 - 13 = \mathbf{27\text{ fewer relationship edges (67.5% reduction)}}$$

```
  ARCHITECTURE A: Full Mesh (40 Edges)          ARCHITECTURE B: Phase Gate (13 Edges)
  
       [Eng 1] ──┬──┬──┬──┬──► [PO A]               [Eng 1] ───┐
       [Eng 2] ──┼──┼──┼──┼──► [PO B]               [Eng 2] ───┤           ┌──► [PO A]
       [Eng 3] ──┼──┼──┼──┼──► [PO C]               [Eng 3] ───┼──► [◆] ───┼──► [PO B]
       [Eng 4] ──┼──┼──┼──┼──► [PO D]               ...        │    Gate   ├──► [PO C]
       ...     ──┴──┴──┴──┴──► [PO E]               [Eng 8] ───┘           └──► [PO E]
       (Nightmare to audit & maintain)              (Single verification checkpoint)
```

**Operational Advantages:**
1. **Single Point of Sign-off:** The Independent Engineer (IE) inspects and certifies a single milestone `M-GATE-IFC`. If an issue arises, only one node is placed on hold rather than rewiring 40 edges.
2. **Deterministic Governance:** Eliminates accidental logic bypasses where a junior engineer wires 7 out of 8 drawings, allowing a procurement contract to be awarded with missing foundation designs.

---

#### 4. Topological Sort Performance in Golang Engine
* In Kahn's Algorithm for Topological Sort, each edge is traversed once:
  $$\text{Time Complexity} = O(V + E)$$
* By replacing $O(M \cdot N)$ dense bipartite subgraphs with $O(M + N)$ star subgraphs, graph edge density is slashed. In a 5,000-node network with 20 major phase gates, this reduces graph traversal cache misses and slice reallocation overhead in Golang by up to 60%.

### Solution 7: Multi-Contractor Interface Milestones & External Constraints

#### 1. Modeling Parameters for `M-INT-BAY`
* **Activity Type:** **Start Milestone**
  * *Reason:* It marks the moment the Surya EPC team is permitted to *commence* work inside the RVPNL switchyard.
* **Constraint Type:** **Early Start On or After (ESOA)** set to **15-Jul-2026 08:00:00**.

---

#### 2. Risk of "Mandatory Start" vs "Start On or After"
* **"Early Start On or After" (ESOA):**
  * Constrains the **Forward Pass**: $ES \ge \text{Constraint Date}$.
  * Does **not** artificially force the Backward Pass. If successors finish comfortably early, positive total float is preserved.
* **"Mandatory Start" (MS):**
  * Sets **both** $ES = \text{Constraint Date}$ AND $LS = \text{Constraint Date}$, regardless of network logic!
  * **Catastrophic Failure Mode:** It breaks the CPM backward pass. Predecessors are forced to calculate late dates relative to the hard-coded date, destroying the true critical path and creating artificial negative float on upstream activities.

---

#### 3. RVPNL Delay Impact and EoT Claim Mechanics
* When RVPNL delays handover from 15-Jul-2026 to 15-Aug-2026 (31 calendar days delay):
  1. The ESOA constraint on `M-INT-BAY` is updated to 15-Aug-2026.
  2. The forward pass pushes `Act 350` and downstream grid back-feed testing by 31 calendar days.
  3. If this path is critical, `M-COD` slips day-for-day by 31 days.
  4. **EoT Claim Under FIDIC Clause 8.4(b):** The delay is caused by an external authority (RVPNL / Employer's Interconnection Authority). Because `M-INT-BAY` is an explicit contractual Interface Milestone on the approved baseline critical path, the contractor has immediate, indisputable entitlement to 31 days Extension of Time and relief from ₹6.51 Crore in Delay Liquidated Damages!

### Solution 8: Level of Effort (LOE) / Hammock Anchoring between Milestones

#### 1. Dynamic CPM Calculation of LOE Activities
During the Forward Pass:
1. $ES(\text{LOE}) = \min \Big( ES(\text{Start Predecessors}) \Big) = ES(\text{M-NTP}) = \text{01-Jan-2026, 08:00}$.
2. $EF(\text{LOE}) = \max \Big( EF(\text{Finish Predecessors}) \Big) = EF(\text{M-COD}) = \text{28-Nov-2026, 17:00}$.
3. $\text{Planned Duration} = \text{WorkingDaysBetween}(ES(\text{LOE}), EF(\text{LOE}), \text{Calendar})$.

---

#### 2. Baseline Budget for `Act 900`
$$\text{Baseline Working Days} = 285\text{ days}$$
$$\text{Daily Burn Rate} = ₹65,000/\text{day}$$
$$\text{Baseline Budget} = 285 \times ₹65,000 = \mathbf{₹1,85,25,000 \text{ (₹1.85 Crore)}}$$

---

#### 3. Slippage Cost Overrun
* **Additional Working Days:** 41 days.
* **Revised Total Duration:** $285 + 41 = 326\text{ working days}$.
* **Overrun Cost:**
  $$\text{Cost Overrun} = 41\text{ days} \times ₹65,000 = \mathbf{₹26,65,000 \text{ (₹26.65 Lakhs)}}$$
* **Revised Total Overhead Cost:** $₹1,85,25,000 + ₹26,65,000 = \mathbf{₹2,11,90,000 \text{ (₹2.12 Crore)}}$.

---

#### 4. The CPM Circularity Rule & DAG Cycle Error
* **The Rule:** An LOE activity can **never** have successor relationships driving operational tasks or milestones.
* **Mathematical Failure:**
  * If an engineer adds `Act 900 (LOE) --(FS)--> M-COD`:
    1. $EF(\text{Act 900})$ is driven by $EF(\text{M-COD})$.
    2. $EF(\text{M-COD})$ is now driven by $EF(\text{Act 900})$.
    3. The relationship creates a **directed cycle**:
       $$\text{M-COD} \to \text{Act 900} \to \text{M-COD}$$
    4. In a Golang CPM engine, Kahn's algorithm fails with `CyclicDependencyError`, or a naive recursive DFS crashes with `stack overflow` (infinite loop)!

## 💻 Section C: Software Architecture & Engine Design

### Solution 9: PostgreSQL Relational Database Schema Design

```sql
-- ============================================================================
-- TOPIC 3.4: ENTERPRISE MILESTONES & SCHEDULING RELATIONAL SCHEMA
-- ============================================================================

-- 1. Enums for Activity Classification and Contractual Tiers
CREATE TYPE activity_type_enum AS ENUM (
    'TASK_DEPENDENT',
    'RESOURCE_DEPENDENT',
    'LEVEL_OF_EFFORT',
    'START_MILESTONE',
    'FINISH_MILESTONE',
    'WBS_SUMMARY'
);

CREATE TYPE milestone_tier_enum AS ENUM (
    'TIER_1_CONTRACTUAL_KEY',
    'TIER_2_COMMERCIAL_BILLING',
    'TIER_3_OPERATIONAL_GATE',
    'TIER_4_INFORMATIONAL'
);

-- 2. Core Activities Table
CREATE TABLE activities (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL,
    wbs_id UUID NOT NULL,
    activity_code VARCHAR(32) NOT NULL,
    name VARCHAR(255) NOT NULL,
    activity_type activity_type_enum NOT NULL DEFAULT 'TASK_DEPENDENT',
    calendar_id UUID NOT NULL,
    
    -- Duration Columns (Zero for Milestones!)
    planned_duration_days NUMERIC(10, 4) NOT NULL DEFAULT 0.0000,
    remaining_duration_days NUMERIC(10, 4) NOT NULL DEFAULT 0.0000,
    actual_duration_days NUMERIC(10, 4) NOT NULL DEFAULT 0.0000,
    
    -- CPM Computed Early/Late Timestamps
    early_start TIMESTAMPTZ,
    early_finish TIMESTAMPTZ,
    late_start TIMESTAMPTZ,
    late_finish TIMESTAMPTZ,
    actual_start TIMESTAMPTZ,
    actual_finish TIMESTAMPTZ,
    
    -- Float and Criticality
    total_float_days NUMERIC(10, 4),
    free_float_days NUMERIC(10, 4),
    is_critical BOOLEAN NOT NULL DEFAULT FALSE,
    
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- STRICT ZERO-DURATION INTEGRITY CONSTRAINT
    CONSTRAINT chk_milestone_zero_durations CHECK (
        (activity_type IN ('START_MILESTONE', 'FINISH_MILESTONE') 
         AND planned_duration_days = 0.0000 
         AND remaining_duration_days = 0.0000)
        OR
        (activity_type NOT IN ('START_MILESTONE', 'FINISH_MILESTONE'))
    ),

    -- Unique Activity Code per Project
    CONSTRAINT uq_project_activity_code UNIQUE (project_id, activity_code)
);

-- 3. Contractual Milestones Metadata Table
CREATE TABLE project_milestones (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    activity_id UUID NOT NULL UNIQUE REFERENCES activities(id) ON DELETE CASCADE,
    tier milestone_tier_enum NOT NULL DEFAULT 'TIER_3_OPERATIONAL_GATE',
    contractual_target_date TIMESTAMPTZ NOT NULL,
    daily_delay_ld_amount NUMERIC(15, 2) NOT NULL DEFAULT 0.00,
    max_ld_cap_amount NUMERIC(15, 2) NOT NULL DEFAULT 0.00,
    billing_weight_percentage NUMERIC(5, 2) NOT NULL DEFAULT 0.00,
    stakeholder_signoff_role VARCHAR(100) NOT NULL,
    is_phase_gate BOOLEAN NOT NULL DEFAULT FALSE,
    punch_list_required BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT chk_billing_weight CHECK (billing_weight_percentage >= 0.00 AND billing_weight_percentage <= 100.00)
);

-- Indexing for High-Performance Queries
CREATE INDEX idx_activities_project_type ON activities(project_id, activity_type);
CREATE INDEX idx_project_milestones_activity ON project_milestones(activity_id);
CREATE INDEX idx_project_milestones_tier ON project_milestones(tier);

-- 4. Analytical Query: Detect Violated Phase Gates & Financial LD Exposure
SELECT 
    a.activity_code,
    a.name AS milestone_name,
    pm.tier,
    pm.contractual_target_date::DATE AS target_date,
    a.early_finish::DATE AS forecast_date,
    GREATEST(0, EXTRACT(DAY FROM (a.early_finish - pm.contractual_target_date)))::INTEGER AS delay_calendar_days,
    ROUND(
        LEAST(
            pm.max_ld_cap_amount,
            GREATEST(0, EXTRACT(DAY FROM (a.early_finish - pm.contractual_target_date))) * pm.daily_delay_ld_amount
        ), 2
    ) AS accumulated_delay_ld_inr,
    pm.stakeholder_signoff_role
FROM activities a
JOIN project_milestones pm ON a.id = pm.activity_id
WHERE a.project_id = 'a0000000-0000-0000-0000-000000000001'
  AND pm.is_phase_gate = TRUE
  AND a.early_finish > pm.contractual_target_date
ORDER BY accumulated_delay_ld_inr DESC, delay_calendar_days DESC;
```

### Solution 10: Golang Forward Pass & Backward Pass for Zero-Duration Nodes

```go
package cpm

import (
	"math"
	"time"
)

// ForwardPassNode processes a single node in topological order
func ForwardPassNode(n *Node, incomingEdges []*Relationship, nodeMap map[string]*Node, cal *SiteCalendar) {
	if len(incomingEdges) == 0 {
		// Project root node
		if n.Type == StartMilestone {
			n.EarlyStart = cal.SnapToDayStart(n.EarlyStart)
			n.EarlyFinish = n.EarlyStart
		} else if n.Type == FinishMilestone {
			n.EarlyFinish = cal.SnapToDayEnd(n.EarlyFinish)
			n.EarlyStart = n.EarlyFinish
		} else {
			n.EarlyStart = cal.SnapToDayStart(n.EarlyStart)
			n.EarlyFinish = cal.AddWorkingDays(n.EarlyStart, n.DurationWork)
		}
		return
	}

	var maxConstraint time.Time

	for _, rel := range incomingEdges {
		pred := nodeMap[rel.PredecessorID]
		var constraint time.Time

		switch rel.Type {
		case FS:
			if n.Type == StartMilestone {
				// Finish-to-Start to a Start Milestone pushes to start of next working period
				constraint = cal.NextWorkingDayStart(pred.EarlyFinish, rel.LagHours)
			} else {
				// Finish-to-Start to a Finish Milestone or Task snaps to end of predecessor plus lag
				constraint = cal.AddHours(pred.EarlyFinish, rel.LagHours)
			}

		case SS:
			constraint = cal.AddHours(pred.EarlyStart, rel.LagHours)

		case FF:
			constraint = cal.AddHours(pred.EarlyFinish, rel.LagHours)

		case SF:
			constraint = cal.AddHours(pred.EarlyStart, rel.LagHours)
		}

		if constraint.After(maxConstraint) {
			maxConstraint = constraint
		}
	}

	// Apply node duration and zero-duration invariants
	if n.Type == StartMilestone {
		n.EarlyStart = cal.SnapToDayStart(maxConstraint)
		n.EarlyFinish = n.EarlyStart // Zero duration: ES == EF
	} else if n.Type == FinishMilestone {
		n.EarlyFinish = cal.SnapToDayEnd(maxConstraint)
		n.EarlyStart = n.EarlyFinish // Zero duration: ES == EF
	} else {
		n.EarlyStart = cal.SnapToDayStart(maxConstraint)
		n.EarlyFinish = cal.AddWorkingDays(n.EarlyStart, n.DurationWork)
	}
}

// BackwardPassNode processes a single node in reverse topological order
func BackwardPassNode(n *Node, outgoingEdges []*Relationship, nodeMap map[string]*Node, projectEnd time.Time, cal *SiteCalendar) {
	if len(outgoingEdges) == 0 {
		// Terminal node
		if n.Type == StartMilestone || n.Type == FinishMilestone {
			n.LateFinish = n.EarlyFinish
			n.LateStart = n.LateFinish
		} else {
			n.LateFinish = projectEnd
			n.LateStart = cal.SubtractWorkingDays(n.LateFinish, n.DurationWork)
		}
		n.TotalFloat = n.LateFinish.Sub(n.EarlyFinish).Hours() / cal.HoursPerDay
		n.IsCritical = (n.TotalFloat <= 0.0001)
		return
	}

	minConstraint := time.Date(2099, 12, 31, 0, 0, 0, 0, time.UTC)

	for _, rel := range outgoingEdges {
		succ := nodeMap[rel.SuccessorID]
		var constraint time.Time

		switch rel.Type {
		case FS:
			if succ.Type == StartMilestone {
				constraint = cal.PrevWorkingDayEnd(succ.LateStart, rel.LagHours)
			} else {
				constraint = cal.SubtractHours(succ.LateStart, rel.LagHours)
			}

		case SS:
			constraint = cal.SubtractHours(succ.LateStart, rel.LagHours)

		case FF:
			constraint = cal.SubtractHours(succ.LateFinish, rel.LagHours)

		case SF:
			constraint = cal.SubtractHours(succ.LateFinish, rel.LagHours)
		}

		if constraint.Before(minConstraint) {
			minConstraint = constraint
		}
	}

	// Maintain zero-duration equality on backward pass
	if n.Type == StartMilestone {
		n.LateStart = minConstraint
		n.LateFinish = n.LateStart // LS == LF
	} else if n.Type == FinishMilestone {
		n.LateFinish = minConstraint
		n.LateStart = n.LateFinish // LS == LF
	} else {
		n.LateFinish = minConstraint
		n.LateStart = cal.SubtractWorkingDays(n.LateFinish, n.DurationWork)
	}

	// Float arithmetic
	n.TotalFloat = math.Round((n.LateFinish.Sub(n.EarlyFinish).Hours()/cal.HoursPerDay)*10000) / 10000
	n.IsCritical = (n.TotalFloat <= 0.0001)
}
```

### Solution 11: Workday Shift Timestamp Normalization in Golang

```go
package cpm

import (
	"testing"
	"time"
)

type SiteCalendar struct {
	WorkStartHour int // e.g. 8 (08:00)
	WorkEndHour   int // e.g. 17 (17:00)
	HoursPerDay   float64
}

// NormalizeMilestoneTimestamp ensures zero-duration milestones sit precisely on boundary instants
func NormalizeMilestoneTimestamp(t time.Time, mType ActivityType, cal *SiteCalendar) time.Time {
	loc := t.Location()
	year, month, day := t.Date()

	if mType == StartMilestone {
		// If timestamp is on or after work close (17:00), push to next working day morning (08:00)
		if t.Hour() >= cal.WorkEndHour {
			nextDay := t.AddDate(0, 0, 1)
			for nextDay.Weekday() == time.Sunday { // Skip Sundays in Rajasthan
				nextDay = nextDay.AddDate(0, 0, 1)
			}
			return time.Date(nextDay.Year(), nextDay.Month(), nextDay.Day(), cal.WorkStartHour, 0, 0, 0, loc)
		}
		// If during the working day or early morning, snap to start of this working day
		return time.Date(year, month, day, cal.WorkStartHour, 0, 0, 0, loc)
	}

	// FinishMilestone: Always snaps to close of business (17:00:00) of that working day
	return time.Date(year, month, day, cal.WorkEndHour, 0, 0, 0, loc)
}

// Unit Test proving weekend jump from Friday evening to Monday morning
func TestNormalizeMilestoneTimestamp(t *testing.T) {
	cal := &SiteCalendar{WorkStartHour: 8, WorkEndHour: 17, HoursPerDay: 8.0}
	loc := time.UTC

	// Scenario: Task finishes Saturday at 17:00:00
	satFinish := time.Date(2026, time.February, 14, 17, 0, 0, 0, loc)

	// Finish Milestone must stay on Saturday at 17:00
	finMS := NormalizeMilestoneTimestamp(satFinish, FinishMilestone, cal)
	if finMS.Weekday() != time.Saturday || finMS.Hour() != 17 {
		t.Fatalf("Expected Saturday 17:00, got: %v", finMS)
	}

	// Start Milestone driven by Saturday finish must skip Sunday and snap to Monday 08:00
	startMS := NormalizeMilestoneTimestamp(satFinish, StartMilestone, cal)
	if startMS.Weekday() != time.Monday || startMS.Hour() != 8 {
		t.Fatalf("Expected Monday 08:00, got: %v", startMS)
	}
}
```

### Solution 12: Next.js / SVG Diamond Geometry & Milestone Trend Chart (MTC) Math

#### 1. SVG Diamond Geometry Formula
Given center coordinates $(cx, cy)$ and radius $R$:
* Top vertex: $(x_1, y_1) = (cx, cy - R)$
* Right vertex: $(x_2, y_2) = (cx + R, cy)$
* Bottom vertex: $(x_3, y_3) = (cx, cy + R)$
* Left vertex: $(x_4, y_4) = (cx - R, cy)$

In SVG string format:
```tsx
const points = `${cx},${cy - R} ${cx + R},${cy} ${cx},${cy + R} ${cx - R},${cy}`;
```

#### 2. Slippage Velocity ($\nu_{\text{slip}}$) Mathematical Interpretation
$$\nu_{\text{slip}}(k) = \frac{F_k - F_{k-1}}{T_k - T_{k-1}}$$

* **$\nu_{\text{slip}} = 0$ (Stable):** The forecasted achievement date is unchanging. Schedule execution is proceeding exactly in step with time.
* **$\nu_{\text{slip}} = 1.0$ (Critical Day-for-Day Slip):** For every calendar day that elapses, the milestone forecast slips by exactly one calendar day. Zero progress is being made on the driving critical path.
* **$\nu_{\text{slip}} > 1.0$ (Compounding Delay Acceleration):** Catastrophic project condition. For every month that passes, the milestone recedes by more than one month (common in EPC when rework, subcontractor defaults, or stop-work orders occur).
* **$\nu_{\text{slip}} < 0$ (Schedule Compression / Acceleration):** The project is recovering schedule through crashing, fast-tracking, or additional construction crews.

#### 3. TypeScript MTC Analyzer Implementation

```typescript
export interface MilestoneSnapshot {
  updateDate: Date;      // Data Date (T_k)
  forecastDate: Date;    // Calculated Early Finish (F_k)
}

export interface SlippageAnalysis {
  velocity: number;
  isCriticalDanger: boolean;
  projectedBreachDays: number;
  recommendation: string;
}

export function computeMilestoneSlippage(
  snapshots: MilestoneSnapshot[],
  contractualTarget: Date
): SlippageAnalysis {
  if (snapshots.length < 2) {
    return {
      velocity: 0,
      isCriticalDanger: false,
      projectedBreachDays: 0,
      recommendation: "Insufficient history to compute velocity.",
    };
  }

  // Sort chronologically by updateDate
  const sorted = [...snapshots].sort((a, b) => a.updateDate.getTime() - b.updateDate.getTime());
  const prev = sorted[sorted.length - 2];
  const curr = sorted[sorted.length - 1];

  const deltaReportingDays = (curr.updateDate.getTime() - prev.updateDate.getTime()) / (1000 * 60 * 60 * 24);
  const deltaForecastDays = (curr.forecastDate.getTime() - prev.forecastDate.getTime()) / (1000 * 60 * 60 * 24);

  const velocity = deltaReportingDays > 0 ? deltaForecastDays / deltaReportingDays : 0;
  const projectedBreachDays = Math.max(0, (curr.forecastDate.getTime() - contractualTarget.getTime()) / (1000 * 60 * 60 * 24));
  
  const isCriticalDanger = velocity >= 1.0 && curr.forecastDate.getTime() > contractualTarget.getTime();

  let recommendation = "Schedule trajectory is within acceptable tolerance.";
  if (isCriticalDanger) {
    recommendation = `CRITICAL DANGER: Slippage velocity is ${velocity.toFixed(2)}d/d with ${projectedBreachDays.toFixed(0)} days delay. Issue FIDIC Notice of Claim & mobilize recovery shifts immediately!`;
  } else if (velocity > 0) {
    recommendation = `WARNING: Mild slippage detected (${velocity.toFixed(2)}d/d). Monitor subcontractor daily output.`;
  }

  return {
    velocity: Math.round(velocity * 100) / 100,
    isCriticalDanger,
    projectedBreachDays: Math.round(projectedBreachDays),
    recommendation,
  };
}
```
