# Topic 11.2: System Architecture: Building P6 in Go & Next.js

## 1. Executive Summary & Plain-English Analogy

### 1.1 Why Jira and Trello Break at 50,000 Nodes
Imagine building a digital model of the Surya 100MW Solar plant. If an engineer opens an issue tracking tool like Jira or Trello, they are dealing with an **Adjacency Table of Tickets**. Each ticket is an independent document with a status badge (`To Do`, `In Progress`, `Done`). If ticket B depends on ticket A, it is merely a hyperlink. If ticket A is delayed by two weeks, ticket B does not automatically recalculate its start date, shift the schedules of 4,000 downstream activities, recalculate resource leveling across 12 piling rigs, and update early/late finish dates in under 10 milliseconds.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                     ISSUE TRACKER (JIRA) vs. SCHEDULING ENGINE (PRIMAVERA P6)                    │
├───────────────────────────────────┬──────────────────────────────────────────────────────────────┤
│ Issue Tracker / Kanban Board      │ High-Performance Project Controls Engine                    │
├───────────────────────────────────┼──────────────────────────────────────────────────────────────┤
│ * Document / Ticket store.        │ * Mathematical Directed Acyclic Graph (DAG).                 │
│ * Static metadata links.          │ * Dynamic Topological Time Wave Propagation.                │
│ * Eventual consistency is fine.   │ * Strict sub-10ms forward/backward CPM recalculation.        │
│ * 1,000 issues per board max.     │ * 50,000 to 200,000 activities in a single portfolio.        │
│ * Relies on relational DB joins.  │ * Contiguous in-memory cache-aligned graph structures.       │
│ * DOM rendering: 500 cards = lag. │ * 60 FPS virtualized split-pane canvas/DOM Gantt chart.      │
└───────────────────────────────────┴──────────────────────────────────────────────────────────────┘
```

A project controls engine like Oracle Primavera P6 is **not** a CRUD database application. It is a **deterministic, real-time discrete-event graph simulation system**. 

When a scheduler drags an activity bar by 3 days in the Gantt chart, the backend must execute:
1. Cycle detection ($O(V + E)$).
2. Topological ordering ($O(V + E)$).
3. Multi-calendar calendar math and relationship lag evaluation ($O(E)$).
4. Forward Pass early dates calculation ($O(V + E)$).
5. Backward Pass late dates and float calculation ($O(V + E)$).
6. Resource-constrained Parallel Schedule Generation Scheme leveling ($O(V \log V)$).
7. Fan-out state updates over WebSockets to 20 concurrent planners viewing the project.

If this recalculation takes more than 100 milliseconds, the user experience degrades into stuttering, rendering interactive Gantt editing impossible.

The CPM graph traversal requires visiting tens of thousands of adjacent vertices and edges in rapid succession. Crossing process boundaries or HTTP/gRPC network hops inside the traversal loop destroys CPU cache lines and introduces millisecond network latency. 

Therefore, the industry standard for a P6-grade scheduling engine is a **Modular Monolith** in Golang:
- Persistent storage: PostgreSQL 16 for durable transactional records.
- Compute engine: A dedicated in-memory Go core maintaining cache-aligned adjacency lists.
- Boundary: Clean domain packages (`domain/cpm`, `domain/leveling`, `domain/calendar`, `domain/collab`) compiled into a single binary, scaling horizontally via stateful project-sharded worker nodes coordinated by Redis pub/sub.

## 3. Backend (Golang): High-Performance CPM & Leveling Engine

### 3.1 Memory Layout & Cache-Locality Optimization
In Go, standard pointer-heavy structures (`type Node struct { Next *Node }`) lead to memory fragmentation. Pointers scatter nodes across the 64-bit virtual memory heap. When traversing 50,000 nodes, the CPU suffers constant L1/L2/L3 cache misses.

To achieve **sub-10ms recalculation for 50,000 nodes**, we use **Data-Oriented Design (DOD)**:
1. Store all graph nodes in a single flat, contiguous slice: `[]ActivityNode`.
2. Reference predecessors and successors by integer array indices (`uint32`), not 64-bit memory pointers.
3. Keep calendar bitsets in contiguous memory for instant bitwise working-hour evaluation.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                          CACHE-ALIGNED IN-MEMORY GRAPH ARENA                                     │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   POINTER GRAPH (Bad: Cache Misses)             CONTIGUOUS ARENA (Good: L1 Cache Friendly)       │
│                                                                                                  │
│   Heap Memory Address:                          Contiguous CPU Cache Line (64 Bytes):            │
│   0x001A: Node 1 [Ptr: 0x4B2C] ──┐              ┌──────────────────────────────────────────────┐ │
│   ... (Cache Miss: fetch RAM)    │              │ Node 0 (Index 0) | Node 1 (Index 1) | ...    │ │
│   0x4B2C: Node 2 [Ptr: 0x88F0] ──┼──┐           ├──────────────────────────────────────────────┤ │
│   ... (Cache Miss: fetch RAM)    │  │           │ In-degree | Early Start | Early Finish | ... │ │
│   0x88F0: Node 3 [Ptr: 0x12A0] ◄─┘  │           └──────────────────────────────────────────────┘ │
│                                     ▼                                                            │
│                                  RAM Fetch      Sequential pre-fetching loads 4 nodes per cycle! │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 Production Golang CPM Engine Implementation
Below is the complete, high-performance CPM engine implementing Kahn's algorithm for topological sorting and dual-pass early/late date evaluation:

```go
package cpm

import (
	"errors"
	"fmt"
	"time"
)

// RelationshipType defines CPM relationship logic
type RelationshipType uint8

const (
	FinishToStart RelationshipType = iota // FS
	StartToStart                         // SS
	FinishToFinish                       // FF
	StartToFinish                        // SF
)

// RelationshipEdge represents a directed dependency between two activity indices
type RelationshipEdge struct {
	PredecessorIdx uint32
	SuccessorIdx   uint32
	Type           RelationshipType
	LagMinutes     int64 // Lag in working minutes
}

// ActivityNode holds cache-aligned scheduling properties
type ActivityNode struct {
	ID               string
	Index            uint32
	OriginalDuration int64 // Duration in minutes
	RemainingDuration int64
	CalendarID       string

	// Forward Pass Results (Working minutes from project epoch)
	EarlyStart  int64
	EarlyFinish int64

	// Backward Pass Results
	LateStart  int64
	LateFinish int64

	// Float Metrics
	TotalFloat int64
	FreeFloat  int64
	IsCritical bool

	// Graph Adjacency Bookkeeping (Indices in the edges slice)
	PredecessorEdgeIndices []uint32
	SuccessorEdgeIndices   []uint32
}

// CPMGraph encapsulates the in-memory contiguous network
type CPMGraph struct {
	Nodes       []ActivityNode
	Edges       []RelationshipEdge
	NodeIndexMap map[string]uint32
	DataDate    int64 // Project reference epoch in minutes
}

// NewCPMGraph initializes an empty arena with pre-allocated capacity
func NewCPMGraph(capacity int) *CPMGraph {
	return &CPMGraph{
		Nodes:        make([]ActivityNode, 0, capacity),
		Edges:        make([]RelationshipEdge, 0, capacity*2),
		NodeIndexMap: make(map[string]uint32, capacity),
	}
}

// AddActivity registers an activity into the contiguous arena
func (g *CPMGraph) AddActivity(id string, durationMinutes int64, calID string) uint32 {
	idx := uint32(len(g.Nodes))
	node := ActivityNode{
		ID:                     id,
		Index:                  idx,
		OriginalDuration:       durationMinutes,
		RemainingDuration:      durationMinutes,
		CalendarID:             calID,
		PredecessorEdgeIndices: make([]uint32, 0, 4),
		SuccessorEdgeIndices:   make([]uint32, 0, 4),
	}
	g.Nodes = append(g.Nodes, node)
	g.NodeIndexMap[id] = idx
	return idx
}

// AddRelationship establishes a dependency edge between activities
func (g *CPMGraph) AddRelationship(predID, succID string, relType RelationshipType, lagMinutes int64) error {
	predIdx, ok1 := g.NodeIndexMap[predID]
	succIdx, ok2 := g.NodeIndexMap[succID]
	if !ok1 || !ok2 {
		return fmt.Errorf("invalid activity IDs: %s -> %s", predID, succID)
	}

	edgeIdx := uint32(len(g.Edges))
	edge := RelationshipEdge{
		PredecessorIdx: predIdx,
		SuccessorIdx:   succIdx,
		Type:           relType,
		LagMinutes:     lagMinutes,
	}
	g.Edges = append(g.Edges, edge)

	g.Nodes[predIdx].SuccessorEdgeIndices = append(g.Nodes[predIdx].SuccessorEdgeIndices, edgeIdx)
	g.Nodes[succIdx].PredecessorEdgeIndices = append(g.Nodes[succIdx].PredecessorEdgeIndices, edgeIdx)
	return nil
}

// Recalculate executes Kahn's topological sort, Forward Pass, and Backward Pass
func (g *CPMGraph) Recalculate() error {
	numNodes := len(g.Nodes)
	if numNodes == 0 {
		return nil
	}

	// 1. Calculate In-Degrees for Topological Ordering
	inDegree := make([]int, numNodes)
	for i := 0; i < len(g.Edges); i++ {
		inDegree[g.Edges[i].SuccessorIdx]++
	}

	// 2. Queue for zero in-degree nodes (Roots)
	queue := make([]uint32, 0, numNodes/4)
	for i := 0; i < numNodes; i++ {
		if inDegree[i] == 0 {
			queue = append(queue, uint32(i))
		}
	}

	topoOrder := make([]uint32, 0, numNodes)

	// 3. Kahn's Algorithm
	for len(queue) > 0 {
		currIdx := queue[0]
		queue = queue[1:]
		topoOrder = append(topoOrder, currIdx)

		for _, edgeIdx := range g.Nodes[currIdx].SuccessorEdgeIndices {
			succIdx := g.Edges[edgeIdx].SuccessorIdx
			inDegree[succIdx]--
			if inDegree[succIdx] == 0 {
				queue = append(queue, succIdx)
			}
		}
	}

	if len(topoOrder) != numNodes {
		return errors.New("circular dependency detected in CPM network")
	}

	// 4. FORWARD PASS (Early Dates Calculation)
	for _, nodeIdx := range topoOrder {
		node := &g.Nodes[nodeIdx]
		maxEarlyStart := g.DataDate

		for _, edgeIdx := range node.PredecessorEdgeIndices {
			edge := g.Edges[edgeIdx]
			pred := &g.Nodes[edge.PredecessorIdx]
			var candidateStart int64

			switch edge.Type {
			case FinishToStart:
				candidateStart = pred.EarlyFinish + edge.LagMinutes
			case StartToStart:
				candidateStart = pred.EarlyStart + edge.LagMinutes
			case FinishToFinish:
				candidateStart = pred.EarlyFinish + edge.LagMinutes - node.RemainingDuration
			case StartToFinish:
				candidateStart = pred.EarlyStart + edge.LagMinutes - node.RemainingDuration
			}

			if candidateStart > maxEarlyStart {
				maxEarlyStart = candidateStart
			}
		}

		node.EarlyStart = maxEarlyStart
		node.EarlyFinish = maxEarlyStart + node.RemainingDuration
	}

	// Determine Project Finish Date
	var projectFinishDate int64 = g.DataDate
	for i := 0; i < numNodes; i++ {
		if g.Nodes[i].EarlyFinish > projectFinishDate {
			projectFinishDate = g.Nodes[i].EarlyFinish
		}
	}

	// 5. BACKWARD PASS (Late Dates Calculation)
	for i := 0; i < numNodes; i++ {
		g.Nodes[i].LateFinish = projectFinishDate
		g.Nodes[i].LateStart = projectFinishDate - g.Nodes[i].RemainingDuration
	}

	// Iterate in reverse topological order
	for i := len(topoOrder) - 1; i >= 0; i-- {
		nodeIdx := topoOrder[i]
		node := &g.Nodes[nodeIdx]

		if len(node.SuccessorEdgeIndices) > 0 {
			minLateFinish := int64(1<<62 - 1)

			for _, edgeIdx := range node.SuccessorEdgeIndices {
				edge := g.Edges[edgeIdx]
				succ := &g.Nodes[edge.SuccessorIdx]
				var candidateFinish int64

				switch edge.Type {
				case FinishToStart:
					candidateFinish = succ.LateStart - edge.LagMinutes
				case StartToStart:
					candidateFinish = succ.LateStart - edge.LagMinutes + node.RemainingDuration
				case FinishToFinish:
					candidateFinish = succ.LateFinish - edge.LagMinutes
				case StartToFinish:
					candidateFinish = succ.LateFinish - edge.LagMinutes + node.RemainingDuration
				}

				if candidateFinish < minLateFinish {
					minLateFinish = candidateFinish
				}
			}

			node.LateFinish = minLateFinish
			node.LateStart = minLateFinish - node.RemainingDuration
		}

		// 6. TOTAL FLOAT & CRITICAL PATH EVALUATION
		node.TotalFloat = node.LateStart - node.EarlyStart
		node.IsCritical = node.TotalFloat <= 0
	}

	return nil
}
```

### 3.3 Resource Leveling Engine: Parallel Schedule Generation Scheme (SGS)
While CPM assumes unlimited resources, physical projects have finite resource limits (e.g., 12 piling rigs, 450 civil laborers). Resource leveling delays non-critical tasks to resolve resource overallocation without violating precedence constraints.

The **Parallel Schedule Generation Scheme (SGS)** iterates through discrete time steps $t$. At each time step:
1. Identify all activities whose predecessors have finished by time $t$ (The **Eligible Set**).
2. Rank eligible activities using a priority rule:
   $$\text{Priority} = \text{Total Float (Ascending)} \longrightarrow \text{Early Start (Ascending)} \longrightarrow \text{Duration (Descending)}$$
3. Evaluate available resource capacity. If capacity is sufficient, allocate resources and schedule the activity at time $t$.
4. If resources are insufficient, defer the activity with higher float to a future time step.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                   PARALLEL SCHEDULE GENERATION SCHEME (SGS) TIME-STEPPING                        │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   Time t = 0: Available Rigs = 12                                                                │
│   Eligible Set:                                                                                  │
│   ├── Task A: Piling Array Block 1 (Demands 6 Rigs, Float = 0d) ──► SCHEDULED AT t=0 (6 Rigs Left)│
│   ├── Task B: Piling Array Block 2 (Demands 6 Rigs, Float = 0d) ──► SCHEDULED AT t=0 (0 Rigs Left)│
│   └── Task C: Perimeter Fence Foundations (Demands 2 Rigs, Float = 15d) ──► DEFERRED!           │
│                                                                                                  │
│            │                                                                                     │
│            ▼ Advance time t to earliest completion of active task (e.g., t = 20)                 │
│                                                                                                  │
│   Time t = 20: Task A Completes ──► 6 Rigs Released! Available Rigs = 6                          │
│   Eligible Set:                                                                                  │
│   ├── Task C: Perimeter Fence (Demands 2 Rigs, Float = 5d) ──► SCHEDULED AT t=20 (4 Rigs Left)  │
│   └── Task D: Inverter Skid Foundations (Demands 4 Rigs)  ──► SCHEDULED AT t=20 (0 Rigs Left)  │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

Below is the Go priority queue implementation for resource leveling:

```go
package leveling

import (
	"container/heap"
)

type SchedActivity struct {
	ID         string
	Index      uint32
	Duration   int64
	Demand     int64
	EarlyStart int64
	TotalFloat int64
	Priority   int64 // Composite priority score
	heapIndex  int
}

type PriorityQueue []*SchedActivity

func (pq PriorityQueue) Len() int           { return len(pq) }
func (pq PriorityQueue) Less(i, j int) bool { return pq[i].Priority < pq[j].Priority }
func (pq PriorityQueue) Swap(i, j int) {
	pq[i], pq[j] = pq[j], pq[i]
	pq[i].heapIndex = i
	pq[j].heapIndex = j
}
func (pq *PriorityQueue) Push(x any) {
	n := len(*pq)
	item := x.(*SchedActivity)
	item.heapIndex = n
	*pq = append(*pq, item)
}
func (pq *PriorityQueue) Pop() any {
	old := *pq
	n := len(old)
	item := old[n-1]
	old[n-1] = nil
	item.heapIndex = -1
	*pq = old[0 : n-1]
	return item
}
```

### 3.4 Multi-User Real-Time Collaboration & Optimistic Locking
When multiple project planners edit the Surya 100MW schedule simultaneously, the system must prevent race conditions and schedule corruption:
1. **Optimistic Locking via Revision Vectors:**
   Every project entity maintains an atomic `revision_id` (`BIGINT`). When a user updates an activity duration, the API requires:
   ```sql
   UPDATE activities 
   SET duration = $1, revision_id = revision_id + 1 
   WHERE id = $2 AND revision_id = $3;
   ```
   If another user recalculated the schedule in between, the query updates 0 rows, triggering an HTTP 409 Conflict.
2. **WebSocket Pub/Sub Broadcast:**
   The Go backend hosts a persistent WebSocket hub. When an activity change commits, the diff is published to Redis channel `project:PRJ-SUR-100:events`, fan-out broadcasting to all connected Next.js browser clients in $< 15\text{ms}$.

#### The Industry Standard: The Virtualized Hybrid Architecture
The optimal architecture chosen by modern high-end tools is a **Hybrid Virtualized Architecture**:
1. **Split Pane Left (Tree Table):** Virtualized DOM windowing (`@tanstack/react-virtual`). Only the 30 rows currently visible in the viewport are mounted into the DOM. This provides native keyboard navigation, screen reader accessibility, inline text editing, and clean CSS styling.
2. **Split Pane Right (Gantt Timeline):**
   - **Background Grid & Bars:** Virtualized DOM row bars mapped to relative CSS positioning (`transform: translateX(...)`).
   - **Relationship Dependency Lines:** A synchronized HTML5 2D Canvas overlay that renders bezier connectors connecting visible predecessor and successor bars during animation frames.

### 4.2 Client-Side State Management: Zustand & TanStack Query
To achieve zero-latency UI responses when dragging task dates:
1. **Optimistic Updates:** When the user drags a Gantt bar, the client-side Zustand store immediately recalculates local dates and renders the bar at the new position within the same frame (0ms latency).
2. **Server CPM Re-sync:** In the background, a debounced mutation is dispatched to the Go backend (`POST /api/v1/projects/:id/recalculate`).
3. **Rollback on Error:** If the Go backend rejects the change (e.g., circular dependency or optimistic lock conflict), TanStack Query automatically rolls back the local Zustand store to the server snapshot and renders a toast notification.
