## 🧠 Section A: Conceptual & Architectural Principles

### Solution 1: Modular Monolith vs. Microservices for Graph Engines

#### 1. Latency & Throughput Analysis of Distributed Microservices
If CPM recalculation is split across distributed microservices (`activity-service`, `calendar-service`, `cpm-calculation-engine`):
1. **Network Overhead:** In a 50,000-activity schedule with 95,000 relationships, a CPM pass requires traversing every node and relationship multiple times (Topological sort + Forward Pass + Backward Pass).
   - If the CPM engine makes gRPC or HTTP calls to fetch or validate calendar shift intervals for 50,000 tasks:
     $$\text{Total RPC Latency} = 50,000 \times 0.2\text{ ms (fast local VPC)} = 10.0\text{ SECONDS}$$
   - Even with batching (e.g., sending chunks of 1,000 tasks per RPC), serialization/deserialization (JSON or Protobuf) and context switches across 3 services add 400–800ms of CPU overhead.
2. **Throughput Collapse:** In-memory traversal in a single process takes **3 to 8 milliseconds**. A distributed microservice setup increases latency by 1,000x to 3,000x, rendering interactive real-time Gantt editing impossible.

#### 2. CPU Cache Locality Degradation
When graph traversal crosses process boundaries:
- In a single process, sequential nodes in a contiguous array reside in the CPU's L1/L2 cache (retrieval time: ~1–4 nanoseconds).
- Crossing an IPC socket or network stack flushes the CPU cache lines, triggers OS kernel context switches, and incurs TCP/IP stack overhead (retrieval time: ~200,000 to 2,000,000 nanoseconds).
- The engine transitions from CPU memory-bus bandwidth (40–80 GB/sec) to network socket bandwidth (1–10 Gbps), a 100x drop in throughput.

#### 3. Modular Monolith Architecture
To achieve high performance with clean architecture:
- Build a **single Go binary** structured into isolated domain packages:
  ```text
  cmd/scheduler/main.go
  internal/
    ├── domain/
    │   ├── cpm/         // In-memory topological sort, forward/backward pass
    │   ├── leveling/    // Parallel SGS priority queue scheduler
    │   ├── calendar/    // Bitset-based working shift calculations
    │   └── collab/      // WebSocket hub and optimistic locking
    ├── repository/      // PostgreSQL 16 pgx/v5 persistence
    └── transport/       // gRPC and HTTP/REST OpenAPI endpoints
  ```
- Communication between domains occurs via direct in-memory Go method calls (`func (s *CPMService) Recalculate(...)`), avoiding all network hops while preserving clean interface boundaries.

### Solution 2: Memory Layout & Cache Locality in Golang

#### 1. Go Garbage Collector (GC) Behavior
* **Approach A (Pointer Graph):**
  Each `ActivityNode` has pointer slices (`[]*ActivityNode`). For 100,000 nodes with 200,000 relationships, the Go heap contains over 300,000 independent pointer references. During Go GC stop-the-world and concurrent mark phases, the GC must scan every individual pointer to verify reachability. This causes GC pause times of **15–40ms** and high CPU consumption.
* **Approach B (Contiguous Flat Arena):**
  Nodes and edges are stored in two contiguous slices: `[]ActivityNode` and `[]RelationshipEdge`. Because `ActivityNode` contains primitive integers (`uint32`) and no pointers, the Go GC marks the entire backing memory slice in a single pass as a contiguous block with **zero pointer dereferences**. GC overhead drops to $< 1\text{ms}$.

#### 2. CPU Hardware Cache Line Analysis (64 Bytes)
Modern x86_64 and ARM64 CPUs fetch memory from RAM in **64-byte cache lines**:
- **Under Approach A:** Nodes are allocated on the heap at arbitrary memory addresses. Reading Node 1 pulls 64 bytes containing only Node 1. To read its successor Node 2, the CPU must dereference a pointer to an entirely different memory page, causing an L1/L2 cache miss.
- **Under Approach B:** Nodes are aligned sequentially in memory. If an `ActivityNode` struct is packed into 64 bytes, sequential iteration through the topological order allows the CPU hardware pre-fetcher to stream contiguous cache lines into L1 cache before the loop even requests them, maximizing instruction pipelining.

#### 3. Spatial Overhead Difference
- **64-bit Pointer:** Takes 8 bytes. For 200,000 edges with bidirectional links (predecessors + successors = 400,000 references):
  $$\text{Pointer Memory} = 400,000 \times 8\text{ bytes} = 3,200,000\text{ bytes (3.20 MB)}$$
- **`uint32` Array Index:** Takes 4 bytes:
  $$\text{Index Memory} = 400,000 \times 4\text{ bytes} = 1,600,000\text{ bytes (1.60 MB)}$$
Using `uint32` indices cuts edge indexing memory consumption exactly in half (50% reduction) and allows addressing up to $2^{32} - 1 \approx 4.29\text{ billion}$ activities—far exceeding any industrial project controls requirement.

### Solution 3: Cycle Detection & Topological Ordering Complexity

#### 1. Why Topological Ordering is Mandatory for CPM Forward Pass
The Forward Pass calculates an activity's Early Start ($ES$) as:
$$ES_j = \max_{i \in \text{Pred}(j)} (EF_i + \text{Lag}_{ij})$$
To compute $ES_j$, **all predecessors of activity $j$ must already have their Early Finish ($EF_i$) permanently calculated**. 
If activities are processed in arbitrary database order, calculating activity $j$ before predecessor $i$ results in an uncalculated or stale $ES_j$. Topological sorting arranges the Directed Acyclic Graph (DAG) such that for every directed edge $u \to v$, node $u$ appears before node $v$ in the linear sequence.

#### 2. Kahn's Algorithm vs. Depth-First Search (DFS)
```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                           KAHN'S ALGORITHM vs. DFS TOPOLOGICAL SORT                              │
├──────────────────────────┬───────────────────────────────────┬───────────────────────────────────┤
│ Dimension                │ Kahn's Algorithm (In-Degree Queue)│ Tarjan's DFS Algorithm            │
├──────────────────────────┼───────────────────────────────────┼───────────────────────────────────┤
│ Iteration Style          │ Breadth-first iterative with queue│ Recursive stack traversal         │
│ Stack Overflow Risk      │ Zero (Uses flat slice queue)      │ High risk on deep linear chains   │
│ Cycle Detection          │ Instant (`len(topo) != numNodes`) │ Requires 3-color node marking     │
│ Parallelization Potential│ High (Nodes with in-degree 0 can   │ Difficult to parallelize          │
│                          │ be evaluated concurrently)        │ recursively                       │
└──────────────────────────┴───────────────────────────────────┴───────────────────────────────────┘
```
For a production Go engine, **Kahn's Algorithm** is vastly superior because it avoids recursion (preventing Go call-stack growth on deep 1,000-activity linear pipeline chains) and naturally processes independent project branches in parallel.

#### 3. Kahn's Cycle Detection Mechanics & Complexity
- **Algorithm:**
  1. Compute the in-degree of all vertices $V$ by scanning edges $E$.
  2. Enqueue all vertices with in-degree 0.
  3. Dequeue vertex $u$, append to `topoOrder`, and decrement in-degree of all successors $v$.
  4. If in-degree of $v$ reaches 0, enqueue $v$.
- **Detection:** If a cycle exists (e.g., $A \to B \to C \to A$), none of the nodes in the cycle ever reach in-degree 0. They are never enqueued. At termination:
  $$\text{len}(\text{topoOrder}) < |V| \implies \text{Cycle Detected!}$$
- **Complexity:** $O(|V| + |E|)$ time and $O(|V|)$ space. For 50,000 nodes and 95,000 edges, cycle detection runs in under **4 milliseconds**.

### Solution 4: Leveling Schemes: Serial SGS vs. Parallel SGS

#### 1. Definitions of Serial vs. Parallel SGS
* **Serial Schedule Generation Scheme (Serial SGS):**
  - **Activity-oriented.** It iterates through an ordered list of activities (1 to $N$).
  - For each activity, it searches for the earliest valid calendar start time $t$ where all predecessors have finished AND sufficient resource capacity exists for the entire duration of the activity.
* **Parallel Schedule Generation Scheme (Parallel SGS):**
  - **Time-oriented.** It iterates through discrete points in time $t_0, t_1, \dots, t_k$.
  - At each time step $t$, it forms an "Eligible Set" of all activities whose predecessors have finished.
  - It prioritizes and schedules activities until available resource capacity at time $t$ is exhausted. Remaining tasks are deferred to the next completion time step.

#### 2. Resource Limit Compliance Guarantee
**Parallel SGS** strictly guarantees that resource limits are never breached at any discrete instant in time. Because it steps through time $t$ and tracks a global available resource capacity vector $R_k(t)$, it allocates only what is available. Serial SGS can leave resource gaps because it schedules individual tasks across the entire time horizon one at a time.

#### 3. Computational Complexity: Min-Heap vs. Naive Scan
At each time step $t$ in Parallel SGS:
- A naive array scan inspects all uncompleted tasks to find eligible candidates, costing $O(V)$. Over $V$ scheduling steps, this yields **$O(V^2)$** complexity (for 50,000 tasks, $50,000^2 = 2.5 \times 10^9$ operations $\approx 30\text{ seconds}$).
- A **Min-Heap Priority Queue (`container/heap`)** maintains only the active eligible tasks. Extracting the highest-priority task (lowest float) takes $O(\log |E_{\text{eligible}}|)$. Over all tasks, total runtime is **$O(V \log V)$** (for 50,000 tasks, $50,000 \log_2(50,000) \approx 780,000$ operations $\approx 5\text{ milliseconds}$).

### Solution 5: Go CPM Forward Pass with SS and FF Lags

#### 1. Mathematical Equations for Candidate Early Start ($ES_{\text{cand}}$)
Given predecessor Early Start ($ES_p$), Early Finish ($EF_p$), remaining duration ($D_{\text{rem}}$), and lag ($L$):
1. **Finish-to-Start (FS):**
   $$ES_{\text{cand}} = EF_p + L$$
2. **Start-to-Start (SS):**
   $$ES_{\text{cand}} = ES_p + L$$
3. **Finish-to-Finish (FF):**
   $$EF_{\text{cand}} = EF_p + L \implies ES_{\text{cand}} = EF_p + L - D_{\text{rem}}$$
4. **Start-to-Finish (SF):**
   $$EF_{\text{cand}} = ES_p + L \implies ES_{\text{cand}} = ES_p + L - D_{\text{rem}}$$

#### 2. Production Go Function Implementation
```go
package cpm

import "fmt"

func computeCandidateEarlyStart(pred *ActivityNode, edge RelationshipEdge, remDuration int64) (int64, error) {
	var candidateStart int64

	switch edge.Type {
	case FinishToStart:
		candidateStart = pred.EarlyFinish + edge.LagMinutes
	case StartToStart:
		candidateStart = pred.EarlyStart + edge.LagMinutes
	case FinishToFinish:
		// Successor Early Finish cannot precede pred.EarlyFinish + Lag
		candidateFinish := pred.EarlyFinish + edge.LagMinutes
		candidateStart = candidateFinish - remDuration
	case StartToFinish:
		candidateFinish := pred.EarlyStart + edge.LagMinutes
		candidateStart = candidateFinish - remDuration
	default:
		return 0, fmt.Errorf("unsupported relationship type: %v", edge.Type)
	}

	return candidateStart, nil
}
```

#### 3. Negative Lag (Lead) Validation
If a scheduler specifies a negative lag ($L < 0$, a lead), `candidateStart` can mathematically evaluate to a date earlier than the project **Data Date** ($T_{\text{data}}$):
- The CPM engine must clamp:
  $$\text{Effective Early Start} = \max(T_{\text{data}}, \text{candidateStart})$$
- Under strict AACE/DCMA 14-Point schedule health standards, negative lags are flagged with a lint warning because they model an impossible physical condition (e.g., claiming a task can start before its prerequisite begins).

### Solution 6: Goroutine Worker Pool for Multi-Project Parallel Scheduling

#### 1. Production Go Worker Pool Implementation
```go
package scheduler

import (
	"context"
	"sync"
	"time"
)

type ProjectJob struct {
	ProjectID string
	DataDate  int64
	Graph     *CPMGraph
}

type ProjectResult struct {
	ProjectID   string
	DurationMs  int64
	Error       error
	FinishDate  int64
}

type PortfolioScheduler struct {
	numWorkers int
}

func NewPortfolioScheduler(workers int) *PortfolioScheduler {
	return &PortfolioScheduler{numWorkers: workers}
}

func (ps *PortfolioScheduler) SchedulePortfolio(ctx context.Context, jobs []ProjectJob) []ProjectResult {
	jobsChan := make(chan ProjectJob, len(jobs))
	resultsChan := make(chan ProjectResult, len(jobs))

	var wg sync.WaitGroup

	// Spawn Goroutine Workers
	for w := 0; w < ps.numWorkers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for job := range jobsChan {
				select {
				case <-ctx.Done():
					resultsChan <- ProjectResult{
						ProjectID: job.ProjectID,
						Error:     ctx.Err(),
					}
					return
				default:
					start := time.Now()
					err := job.Graph.Recalculate()
					elapsed := time.Since(start).Milliseconds()

					var projFinish int64
					if err == nil && len(job.Graph.Nodes) > 0 {
						projFinish = job.Graph.Nodes[len(job.Graph.Nodes)-1].EarlyFinish
					}

					resultsChan <- ProjectResult{
						ProjectID:  job.ProjectID,
						DurationMs: elapsed,
						Error:      err,
						FinishDate: projFinish,
					}
				}
			}
		}()
	}

	// Enqueue Jobs
	for _, job := range jobs {
		jobsChan <- job
	}
	close(jobsChan)

	// Close results channel once all workers finish
	go func() {
		wg.Wait()
		close(resultsChan)
	}()

	// Collect Results
	results := make([]ProjectResult, 0, len(jobs))
	for res := range resultsChan {
		results = append(results, res)
	}

	return results
}
```

#### 2. Intra-Project vs. Multi-Project Concurrency
- **Intra-Project CPM:** Inside a single project DAG, the topological steps have strict sequential data dependencies (Step $N$ depends on outputs of Step $N-1$). Spawning goroutines across adjacent nodes within a single pass causes mutex lock contention and channel communication overhead that is 10x slower than sequential execution.
- **Multi-Project Portfolio:** Independent projects (e.g., Surya 100MW, Haryana 50MW, Gujarat 200MW) share zero internal precedence edges. They can be scheduled on separate CPU cores with embarrassingly parallel efficiency.

#### 3. Preventing Deadlocks & Goroutine Leakage
- Pass a `context.WithTimeout(parentCtx, 30*time.Second)` to every job.
- Inside the worker loop, verify `ctx.Done()`. If a calculation exceeds the deadline, the worker immediately aborts and returns a timeout error.

### Solution 7: Real-Time Optimistic Concurrency Control (OCC) in Go

#### 1. Atomic Revision ID Mechanism
Every project row has `revision_id BIGINT NOT NULL DEFAULT 1`. 
When User 1 and User 2 fetch the schedule, both read `revision_id = 42`.
- When User 1 updates duration, the SQL query checks `WHERE revision_id = 42` and increments `revision_id` to `43`. The database locks the single row, performs the update, and returns `1 row affected`.
- When User 2 attempts to add a relationship checking `WHERE revision_id = 42`, the row's current revision is now `43`. The query matches 0 rows.

#### 2. Go Handler with `pgx/v5` Handling `ErrNoRows`
```go
package repository

import (
	"context"
	"errors"
	"fmt"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgxpool"
)

var ErrOptimisticLockConflict = errors.New("schedule was modified by another user; please refresh")

type ActivityRepository struct {
	pool *pgxpool.Pool
}

func (r *ActivityRepository) UpdateActivityDuration(
	ctx context.Context,
	projectID string,
	activityID string,
	newDurationMinutes int64,
	clientRevisionID int64,
) (int64, error) {
	tx, err := r.pool.Begin(ctx)
	if err != nil {
		return 0, err
	}
	defer tx.Rollback(ctx)

	// 1. Update Project Revision atomically with OCC check
	var newRevisionID int64
	projectQuery := `
		UPDATE projects
		SET revision_id = revision_id + 1, updated_at = NOW()
		WHERE project_id = $1 AND revision_id = $2
		RETURNING revision_id;
	`
	err = tx.QueryRow(ctx, projectQuery, projectID, clientRevisionID).Scan(&newRevisionID)
	if err != nil {
		if errors.Is(err, pgx.ErrNoRows) {
			return 0, ErrOptimisticLockConflict
		}
		return 0, fmt.Errorf("failed to increment project revision: %w", err)
	}

	// 2. Update the activity record
	activityQuery := `
		UPDATE activities
		SET original_duration = $1, remaining_duration = $1, updated_at = NOW()
		WHERE activity_id = $2 AND project_id = $3;
	`
	tag, err := tx.Exec(ctx, activityQuery, newDurationMinutes, activityID, projectID)
	if err != nil {
		return 0, fmt.Errorf("failed to update activity: %w", err)
	}
	if tag.RowsAffected() == 0 {
		return 0, errors.New("activity not found")
	}

	if err := tx.Commit(ctx); err != nil {
		return 0, err
	}

	return newRevisionID, nil
}
```

#### 3. Client Resolution Flow
1. Go backend returns HTTP `409 Conflict` with JSON payload `{ "error": "OCC_CONFLICT", "latest_revision": 43 }`.
2. Next.js client catches the 409 status code in TanStack Query's `onError`.
3. Client silently refetches the updated CPM schedule state (`GET /api/v1/projects/:id/schedule`).
4. Zustand store updates the viewport and surfaces a non-intrusive toast: *"Schedule was updated by another team member. Your changes were merged."*

### Solution 8: Parallel SGS Priority Queue Implementation in Go

#### 1. Data Structure Definitions
```go
package leveling

import "container/heap"

type ActivityItem struct {
	Index             uint32
	ID                string
	TotalFloatMinutes int64
	EarlyStartMinutes int64
	RemainingDuration int64
	ResourceDemand    int64
	heapIndex         int
}

type PriorityQueue []*ActivityItem

func (pq PriorityQueue) Len() int { return len(pq) }
```

#### 2. Multi-Factor Comparison Function (`Less`)
Standard P6 leveling prioritizes:
1. Lowest Total Float (Ascending)
2. Earliest Early Start Date (Ascending)
3. Longest Remaining Duration (Descending)

```go
func (pq PriorityQueue) Less(i, j int) bool {
	// Factor 1: Lowest Total Float
	if pq[i].TotalFloatMinutes != pq[j].TotalFloatMinutes {
		return pq[i].TotalFloatMinutes < pq[j].TotalFloatMinutes
	}
	// Factor 2: Earliest Early Start
	if pq[i].EarlyStartMinutes != pq[j].EarlyStartMinutes {
		return pq[i].EarlyStartMinutes < pq[j].EarlyStartMinutes
	}
	// Factor 3: Longest Remaining Duration (Tie-breaker)
	return pq[i].RemainingDuration > pq[j].RemainingDuration
}

func (pq PriorityQueue) Swap(i, j int) {
	pq[i], pq[j] = pq[j], pq[i]
	pq[i].heapIndex = i
	pq[j].heapIndex = j
}

func (pq *PriorityQueue) Push(x any) {
	item := x.(*ActivityItem)
	item.heapIndex = len(*pq)
	*pq = append(*pq, item)
}

func (pq *PriorityQueue) Pop() any {
	old := *pq
	n := len(old)
	item := old[n-1]
	old[n-1] = nil
	item.heapIndex = -1
	*pq = old[0 : n-1]
	return item
}
```

#### 3. Trace of Heap Operations with 4 Available Rigs
Suppose at time $t = 50$, 4 piling rigs are available. Three tasks are eligible:
- **Task A (Perimeter Piling):** Demand = 2 rigs, Float = 15d, Start = Day 50, Duration = 20d
- **Task B (Main Array Block 1):** Demand = 4 rigs, Float = 0d (Critical), Start = Day 50, Duration = 40d
- **Task C (Inverter Plinths):** Demand = 2 rigs, Float = 5d, Start = Day 50, Duration = 15d

1. Tasks are pushed into the Min-Heap:
   - Root of heap is **Task B** (Float = 0d).
   - Second item is **Task C** (Float = 5d).
   - Third item is **Task A** (Float = 15d).
2. Leveler calls `heap.Pop()`:
   - Extracts **Task B** (Demand = 4 rigs).
   - Available rigs = $4 - 4 = 0$ rigs remaining.
   - Task B is scheduled at $t = 50$.
3. Leveler inspects **Task C** (Demand = 2 rigs):
   - Available rigs = 0. Demand (2) exceeds available (0).
   - Task C cannot be scheduled at $t = 50$. It is deferred until the earliest completion of active tasks ($t = 50 + 40 = 90$).
4. Leveler inspects **Task A** (Demand = 2 rigs):
   - Deferred to $t = 90$.

### Solution 9: Virtualized Split-Pane Bi-Directional Scroll Synchronization

#### 1. Why Naive React State Causes Scroll Jitter
If scroll position is managed via React state (`const [scrollTop, setScrollTop] = useState(0)`):
- Every mousewheel scroll event dispatches a state update.
- React queues a component re-render, runs reconciliation, and updates DOM attributes.
- Because browser scroll events fire up to 120 times per second, the JavaScript thread becomes saturated. Re-renders lag behind the hardware scroll position by 3 to 5 frames, producing visible stutter, frame drops (15 FPS), and rubber-banding.

#### 2. Unmanaged DOM Refs & `requestAnimationFrame`
To achieve silky-smooth 60 FPS synchronization:
- Avoid React state entirely during scrolling.
- Attach native scroll listeners to unmanaged DOM refs (`leftPaneRef.current`, `rightPaneRef.current`).
- Read and assign `element.scrollTop` directly within a `requestAnimationFrame` callback.

#### 3. Preventing Infinite Scroll Loops
To prevent Pane A from triggering Pane B which re-triggers Pane A:
Maintain an active scrolling flag (`isScrollingRef = 'left' | 'right' | null`):

```typescript
let activeScroller: 'left' | 'right' | null = null;
let rafId: number | null = null;

const handleLeftScroll = () => {
  if (activeScroller === 'right') return;
  activeScroller = 'left';

  if (rafId) cancelAnimationFrame(rafId);
  rafId = requestAnimationFrame(() => {
    if (rightPaneRef.current && leftPaneRef.current) {
      rightPaneRef.current.scrollTop = leftPaneRef.current.scrollTop;
    }
    activeScroller = null;
  });
};

const handleRightScroll = () => {
  if (activeScroller === 'left') return;
  activeScroller = 'right';

  if (rafId) cancelAnimationFrame(rafId);
  rafId = requestAnimationFrame(() => {
    if (leftPaneRef.current && rightPaneRef.current) {
      leftPaneRef.current.scrollTop = rightPaneRef.current.scrollTop;
    }
    activeScroller = null;
  });
};
```

### Solution 10: Canvas Overlay for 20,000 Relationship Bezier Connectors

#### 1. Architecture of Canvas Dependency Layer
Instead of mounting 20,000 DOM SVG nodes:
- Place a single HTML5 `<canvas>` element over the Gantt grid, styled with `pointer-events: none; position: absolute; top: 0; left: 0;`.
- On every scroll or zoom event, clear the canvas (`ctx.clearRect(0, 0, width, height)`).
- Query the virtualizer for the currently visible row range (e.g., indices 40 to 75).
- Filter the relationship list to only those where **either the predecessor or the successor is within the visible range**.
- Draw cubic bezier curves directly using the 2D context.

#### 2. Coordinate Math for Finish-to-Start (FS) Relationship
For an FS link from Task A to Task B:
- **Predecessor End Coordinate:**
  $$x_1 = \text{computeBarLeft}(\text{Task A}) + \text{computeBarWidth}(\text{Task A})$$
  $$y_1 = \text{virtualRowIndex}(A) \times \text{rowHeight} + \frac{\text{rowHeight}}{2}$$
- **Successor Start Coordinate:**
  $$x_2 = \text{computeBarLeft}(\text{Task B})$$
  $$y_2 = \text{virtualRowIndex}(B) \times \text{rowHeight} + \frac{\text{rowHeight}}{2}$$
- **Bezier Path:**
  ```typescript
  ctx.beginPath();
  ctx.moveTo(x1, y1);
  const controlOffset = Math.min(40, Math.abs(x2 - x1) / 2);
  ctx.bezierCurveTo(x1 + controlOffset, y1, x2 - controlOffset, y2, x2, y2);
  ctx.strokeStyle = isCritical ? '#ef4444' : '#64748b';
  ctx.lineWidth = 1.5;
  ctx.stroke();

  // Draw arrow head at (x2, y2)
  ctx.beginPath();
  ctx.moveTo(x2, y2);
  ctx.lineTo(x2 - 6, y2 - 4);
  ctx.lineTo(x2 - 6, y2 + 4);
  ctx.fillStyle = isCritical ? '#ef4444' : '#64748b';
  ctx.fill();
  ```

#### 3. Handling Off-Screen Coordinates
If Task A is scrolled off the top ($y_1 < 0$) and Task B is visible ($y_2 > 0$):
- The Canvas 2D engine naturally clips any coordinates outside the canvas viewport dimensions.
- The bezier curve starts cleanly at the clipped top boundary of the canvas ($y = 0$) and sweeps down smoothly to terminate at $(x_2, y_2)$ of Task B.

import { useMutation, useQueryClient } from '@tanstack/react-query';
import { useGanttStore } from './useGanttStore';

export function useUpdateActivityMutation(projectId: string) {
  const queryClient = useQueryClient();
  const { updateTaskOptimistic, setTasks } = useGanttStore();

  return useMutation({
    mutationFn: async ({ taskId, durationDays }: { taskId: string; durationDays: number }) => {
      const res = await fetch(`/api/v1/projects/${projectId}/activities/${taskId}`, {
        method: 'PATCH',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ durationDays }),
      });
      if (!res.ok) {
        const errorData = await res.json();
        throw new Error(errorData.message || 'Failed to update schedule');
      }
      return res.json();
    },

    onMutate: async (newActivity) => {
      // 1. Cancel in-flight queries
      await queryClient.cancelQueries({ queryKey: ['schedule', projectId] });

      // 2. Snapshot current state for rollback
      const previousSchedule = queryClient.getQueryData(['schedule', projectId]);

      // 3. Apply optimistic update to local store immediately
      updateTaskOptimistic(newActivity.taskId, new Date().toISOString(), newActivity.durationDays);

      return { previousSchedule };
    },

    onError: (err, newActivity, context) => {
      // Rollback to snapshot on error
      if (context?.previousSchedule) {
        queryClient.setQueryData(['schedule', projectId], context.previousSchedule);
        setTasks((context.previousSchedule as any).tasks);
      }
      alert(`Schedule Error: ${err.message}`);
    },

    onSettled: () => {
      // Refetch authoritative schedule from Go engine
      queryClient.invalidateQueries({ queryKey: ['schedule', projectId] });
    },
  });
}

### Solution 12: Performance Profiling: 50,000 Tasks at 60 FPS

#### 1. Browser Memory & Rendering Limits
- If 50,000 HTML elements are mounted directly into the DOM:
  - The DOM tree consumes over **600 MB of RAM**.
  - Style calculation and layout passes take **4,000 to 8,000 ms**.
  - Garbage collection pauses lock the main UI thread.
- Virtual windowing resolves this by keeping only **~30 to 40 DOM nodes** mounted at any instant, consuming under **35 MB of RAM**.

#### 2. Role of `overscan` in TanStack Virtual
- `overscan: 10` instructs the virtualizer to render 10 extra rows above and 10 extra rows below the visible viewport boundary.
- **Why it matters:** When the user scrolls rapidly via mousewheel or page down, the browser immediately reveals the pre-rendered overscan buffer.
- If `overscan: 0`, the browser scrolls into empty unmounted space before the virtualizer can calculate indices, creating an ugly **white flashing** artifact.
- If `overscan` is set too high (e.g., 200), too many rows mount, degrading frame rates back down to 30 FPS. `overscan: 10 to 15` is the optimal sweet spot.

#### 3. CSS Hardware Acceleration Optimizations
To achieve 60 FPS on high-DPI (Retina) displays:
1. `transform: translateY(${virtualRow.start}px)`: Moves rows using GPU compositor hardware without triggering expensive CSS layout or repaint passes.
2. `will-change: transform`: Promotes the virtual row container to its own dedicated GPU compositing layer.
3. `contain: strict`: Informs the browser layout engine that the element's subtree is completely isolated. Changes inside a row bar do not invalidate the layout of the parent container or neighboring elements.
4. `content-visibility: auto`: Bypasses layout and painting for off-screen canvas elements until they approach the viewport boundary.
