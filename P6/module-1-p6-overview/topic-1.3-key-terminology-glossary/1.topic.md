## 1. Introduction & Theoretical Foundation

To build a high-performance Primavera P6 clone (a Golang microservices backend with a Next.js front-end) or to master enterprise project controls on multi-hundred-million-dollar capital infrastructure, you must master the specialized vocabulary of project scheduling.

In consumer task-management software (Jira, Trello, Asana), a "task" is an isolated row with a date picker and a status string. In **Oracle Primavera P6**, scheduling is a rigorous **mathematical graph optimization problem**. An activity is a node in a **Directed Acyclic Graph (DAG)** governed by topological constraints, non-linear calendars, calendar bitmasks, resource availability vectors, and earned-value financial integration.

This document serves as the **Master Dictionary and Architectural Specification**. It defines **65 core terms** across seven functional domains. For each term, you will find:
1. **Formal Definition & Intuition** (The controls engineer's understanding + the software engineer's graph mental model).
2. **Mathematical Formulation & Algorithms** (CPM equations, boundary conditions, float formulas, EVM metrics).
3. **Real-World Solar EPC Case Example** (From our running case study: the *Surya 100MW Grid-Connected Solar IPP* in Rajasthan, India).
4. **PostgreSQL Schema & Golang Struct Representation** (How data is modeled in production tables and in-memory engine heaps).

### 1.1 Enterprise Project Structure (EPS)
* **Formal Definition:** A multi-level hierarchical tree structure representing the company-wide organization of all projects. It defines the ownership, grouping, and executive portfolio visibility across an entire enterprise.
* **Intuition:** Think of the EPS as the root directory tree on a file system (`/company/renewables/solar/india/`). Every project must live inside an EPS container.
* **100MW Solar Example:** `EPS: CleanEnergy Corp -> Ground-Mount Solar Division -> Rajasthan Cluster -> Surya 100MW IPP (Project ID: PRJ-SOL-001)`.
* **Database Representation:**
```sql
CREATE TABLE enterprise_project_structures (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    parent_id UUID REFERENCES enterprise_project_structures(id) ON DELETE CASCADE,
    code VARCHAR(32) NOT NULL UNIQUE,
    name VARCHAR(255) NOT NULL,
    description TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```
* **Golang Model:**
```go
type EPSNode struct {
    ID          uuid.UUID  `json:"id" db:"id"`
    ParentID    *uuid.UUID `json:"parent_id" db:"parent_id"`
    Code        string     `json:"code" db:"code"`
    Name        string     `json:"name" db:"name"`
    Children    []*EPSNode `json:"children,omitempty"`
}
```

### 1.2 Organizational Breakdown Structure (OBS)
* **Formal Definition:** A hierarchical model representing the enterprise's management reporting structure, departments, project managers, and leadership roles.
* **Intuition:** The OBS answers *"Who is responsible?"* whereas the WBS answers *"What is being delivered?"*. In P6, OBS nodes are mapped to EPS nodes and WBS nodes to enforce Role-Based Access Control (RBAC) and accountability.
* **100MW Solar Example:** `OBS: VP EPC Operations -> Solar Project Director (Rajesh Sharma) -> Site Civil Lead (Anand Verma)`. Anand Verma is mapped to the "Civil & Piling Works" WBS node.
* **Database Representation:**
```sql
CREATE TABLE organizational_breakdown_structures (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    parent_id UUID REFERENCES organizational_breakdown_structures(id),
    name VARCHAR(128) NOT NULL,
    manager_email VARCHAR(255) NOT NULL,
    user_id UUID -- links to auth user
);
```

### 1.3 Work Breakdown Structure (WBS)
* **Formal Definition:** A 100% deliverable-oriented hierarchical decomposition of the total project scope to be executed by the project team.
* **Intuition:** The WBS is a tree of pure summary nodes. It contains no direct execution dates, no assignees, and no dependency links of its own. All dates, costs, and progress in a WBS node are calculated dynamically by aggregating (rolling up) its child activities.
* **100MW Solar Example:** 
  * WBS Level 1: `WBS-03: Substation & Grid Interconnection (33/220kV)`
  * WBS Level 2: `WBS-03.01: Main Power Transformer (MPT) Bay`
  * WBS Level 3: `WBS-03.01.02: Transformer Foundation Civil Pours`
* **Database Representation:**
```sql
CREATE TABLE wbs_nodes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    parent_id UUID REFERENCES wbs_nodes(id) ON DELETE CASCADE,
    code VARCHAR(64) NOT NULL,
    name VARCHAR(255) NOT NULL,
    obs_id UUID REFERENCES organizational_breakdown_structures(id),
    path LTREE NOT NULL, -- PostgreSQL hierarchical tree extension
    CONSTRAINT uq_project_wbs_code UNIQUE (project_id, code)
);
CREATE INDEX idx_wbs_path ON wbs_nodes USING GIST (path);
```

### 1.4 Work Package
* **Formal Definition:** The lowest level node of a WBS branch that contains one or more terminal activities. It represents the smallest discrete deliverable for which cost, time, and responsibility can be reliably managed.
* **Intuition:** A Work Package is the boundary where the WBS stops decomposing deliverables and hands off to the scheduling engine to model the actual network of activities.
* **100MW Solar Example:** `WP-CIV-04: Tracker Foundation Piling - Block A (Contains 1,200 driven steel posts)`.
* **Database Representation:** In P6, a Work Package is simply a terminal `wbs_node` (a leaf node in the WBS tree where `has_children = false`).

### 1.5 Activity (Task)
* **Formal Definition:** The fundamental executable unit of work in a project schedule. It has a quantifiable duration, consumes time and resources, is governed by calendars, and connects to other activities via precedence relationships.
* **Intuition:** In the database, the activity is the primary graph node. It stores early dates, late dates, actual dates, duration fields, and assigned resource links.
* **100MW Solar Example:** `ACT-1040: Drill & Cast Foundation for Inverter Station #4 (Duration: 6 Work Days)`.
* **Database Representation:**
```sql
CREATE TYPE activity_type_enum AS ENUM (
    'task_dependent',
    'resource_dependent',
    'level_of_effort',
    'start_milestone',
    'finish_milestone',
    'wbs_summary'
);

CREATE TABLE activities (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    wbs_id UUID NOT NULL REFERENCES wbs_nodes(id) ON DELETE RESTRICT,
    activity_id VARCHAR(32) NOT NULL, -- User visible code, e.g., 'ACT-1040'
    name VARCHAR(255) NOT NULL,
    activity_type activity_type_enum NOT NULL DEFAULT 'task_dependent',
    calendar_id UUID NOT NULL REFERENCES calendars(id),
    original_duration_seconds BIGINT NOT NULL, -- Stored in seconds or hours!
    remaining_duration_seconds BIGINT NOT NULL,
    actual_duration_seconds BIGINT NOT NULL DEFAULT 0,
    planned_start_date TIMESTAMPTZ,
    planned_finish_date TIMESTAMPTZ,
    early_start_date TIMESTAMPTZ,
    early_finish_date TIMESTAMPTZ,
    late_start_date TIMESTAMPTZ,
    late_finish_date TIMESTAMPTZ,
    actual_start_date TIMESTAMPTZ,
    actual_finish_date TIMESTAMPTZ,
    free_float_seconds BIGINT NOT NULL DEFAULT 0,
    total_float_seconds BIGINT NOT NULL DEFAULT 0,
    is_critical BOOLEAN NOT NULL DEFAULT FALSE,
    percent_complete_type VARCHAR(16) NOT NULL DEFAULT 'duration',
    percent_complete NUMERIC(5,2) NOT NULL DEFAULT 0.00,
    CONSTRAINT uq_proj_activity_id UNIQUE(project_id, activity_id)
);
```

### 1.6 Task Dependent (Activity Type)
* **Formal Definition:** An activity whose scheduled duration and working dates are strictly determined by the **activity's assigned calendar**, regardless of the individual work calendars of the resources assigned to it.
* **Intuition:** 90% of construction tasks are Task Dependent. If the concrete pouring activity is scheduled on a 6-day site calendar, the pour occurs on Saturday even if a specific engineer assigned to it normally works a 5-day week.
* **100MW Solar Example:** `ACT-CIV-200: PV Module Table Assembly (Block 1)` assigned to `6-Day Construction Site Calendar`.

### 1.7 Resource Dependent (Activity Type)
* **Formal Definition:** An activity whose duration and work execution schedule are determined by the **assigned resource's individual calendar** rather than the activity calendar. If multiple resources are assigned, the activity only works when the primary or coordinating resources are on working shifts.
* **Intuition:** Used for tasks constrained by specialized labor or specialized machinery.
* **100MW Solar Example:** `ACT-TST-101: 220kV Transformer High-Voltage Dielectric Testing`. Driven entirely by the availability calendar of the third-party government testing inspector (who only works Tuesdays and Thursdays).

### 1.8 Level of Effort (LOE) (Activity Type)
* **Formal Definition:** An activity whose duration is dynamically calculated by the scheduling engine based on the start date of its earliest predecessor and the finish date of its latest successor. It has no independent duration.
* **Intuition:** LOE activities represent overhead or ongoing supervisory support. They must **never** be on the critical path, must **never** drive the dates of other tasks, and must have **zero Total Float**.
* **100MW Solar Example:** `ACT-MGT-01: Health & Safety Environmental (HSE) Field Supervision during Inverter Civil Works`. 
  * Predecessor: `Inverter Civil Start` (SS)
  * Successor: `Inverter Civil Handover` (FF)
  * Duration stretches or shrinks dynamically if civil works take 30 days or 60 days.
* **Mathematical Rule:**
$$\text{Early Start}_{LOE} = \min_{p \in Pred} (\text{Early Start}_p)$$
$$\text{Early Finish}_{LOE} = \max_{s \in Succ} (\text{Early Finish}_s)$$

### 1.9 Start Milestone & Finish Milestone
* **Formal Definition:** Zero-duration markers in time that designate major contractual, legal, or physical events.
  * **Start Milestone:** Marks the official beginning of a project phase or deliverable. Has an Early Start date; Early Finish is equal to Early Start.
  * **Finish Milestone:** Marks the formal completion or handover of a deliverable. Has an Early Finish date; Early Start is equal to Early Finish.
* **Intuition:** Milestones consume zero work and zero resources; they are timestamps used for contractual billing, progress gates, and delay analysis.
* **100MW Solar Example:**
  * Start Milestone: `MS-NTP: Notice to Proceed Issued by Offtaker (Duration: 0d)`.
  * Finish Milestone: `MS-COD: Commercial Operation Date & Grid Synchronization (Duration: 0d)`.
* **Database Representation:** `duration_seconds = 0`, `early_start = early_finish`.

### 1.10 WBS Summary (Activity Type)
* **Formal Definition:** An activity whose duration and scheduled dates roll up dynamically to reflect all activities sharing the same WBS branch.
* **Intuition:** Similar to an LOE activity, but its boundary predecessors are automatically derived from the activities enclosed within its parent WBS band.
* **100MW Solar Example:** `ACT-SUM-CIV: Summary of Piling & Civil Block 1`.

## 4. Section 2: Scheduling & Logic Terminology

```
Finish-to-Start (FS):     [Predecessor A] ───► [Successor B]
Start-to-Start (SS):      [Predecessor A]
                          │ (SS + Lag)
                          └──► [Successor B]
Finish-to-Finish (FF):    [Predecessor A] ───┐
                                             │ (FF + Lag)
                          [Successor B]   ◄──┘
Start-to-Finish (SF):     [Predecessor A] ───┐ (Predecessor start controls
                                             └──► [Successor B] finish)
```

### 2.1 Predecessor & Successor
* **Formal Definition:** 
  * **Predecessor:** An activity whose start or finish date logically controls and drives the start or finish date of another activity.
  * **Successor:** An activity whose start or finish date is logically determined or constrained by another activity.
* **Graph Theory Perspective:** In a DAG $G = (V, E)$, an activity is a vertex $v \in V$. A directed edge $e = (u, v) \in E$ denotes that $u$ is the predecessor of $v$, and $v$ is the successor of $u$.
* **100MW Solar Example:** `Excavate Inverter Trench (ACT-01)` is Predecessor to `Pour Inverter Mud Mat (ACT-02)`.

### 2.2 Relationship Types (Dependencies)
P6 supports four distinct precedence logic edge types:

#### Finish-to-Start (FS)
* **Definition:** The successor cannot start until the predecessor finishes. This represents 90% of real-world construction logic.
* **Mathematical Formula:**
$$\text{Early Start}_{Succ} \ge \text{Early Finish}_{Pred} + \text{Lag}$$
* **Solar Example:** You cannot erect the mounting tracker structure until the driven pile foundation has finished curing.

#### Start-to-Start (SS)
* **Definition:** The successor cannot start until the predecessor has started. Used to model overlapping, fast-tracked activities.
* **Mathematical Formula:**
$$\text{Early Start}_{Succ} \ge \text{Early Start}_{Pred} + \text{Lag}$$
* **Solar Example:** Laying DC string cables (`ACT-CBL-01`) can start 3 days after trench excavation (`ACT-TRN-01`) starts. (SS with +3 day lag).

#### Finish-to-Finish (FF)
* **Definition:** The successor cannot finish until the predecessor has finished. Used when the tail end of two activities must align.
* **Mathematical Formula:**
$$\text{Early Finish}_{Succ} \ge \text{Early Finish}_{Pred} + \text{Lag}$$
* **Solar Example:** Backfilling inverter cable trenches cannot finish until the final QA testing of laid cables finishes (FF with 0 day lag).

#### Start-to-Finish (SF)
* **Definition:** The successor cannot finish until the predecessor has started. This is the rarest dependency in project controls (<0.1% of links).
* **Mathematical Formula:**
$$\text{Early Finish}_{Succ} \ge \text{Early Start}_{Pred} + \text{Lag}$$
* **Solar Example:** A temporary diesel generator providing construction site power cannot finish operation until the permanent 33kV auxiliary power transformer starts commissioning.

### 2.3 Lag & Lead
* **Formal Definition:**
  * **Lag:** A positive offset of non-working or working time applied to a relationship link, forcing a delay between predecessor and successor.
  * **Lead (Negative Lag):** A negative offset applied to a relationship, pulling the successor backward in time to overlap with the predecessor.
* **Industry Pitfall:** Major auditing standards (e.g., DCMA 14-Point Assessment) strictly prohibit negative lags because they create confusing, non-physical logic (predicting the future before work starts). Lags should generally be converted into distinct activities (e.g., concrete curing should be an explicit activity, not an invisible lag).
* **100MW Solar Example:** `Pour Inverter Foundation` -> `FS + 7 days curing lag` -> `Erect Inverter Enclosure`.
* **Database Representation:**
```sql
CREATE TYPE relationship_type_enum AS ENUM ('FS', 'SS', 'FF', 'SF');

CREATE TABLE project_relationships (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    predecessor_id UUID NOT NULL REFERENCES activities(id) ON DELETE CASCADE,
    successor_id UUID NOT NULL REFERENCES activities(id) ON DELETE CASCADE,
    relationship_type relationship_type_enum NOT NULL DEFAULT 'FS',
    lag_seconds BIGINT NOT NULL DEFAULT 0, -- Positive for lag, negative for lead
    is_driving BOOLEAN NOT NULL DEFAULT FALSE, -- Computed by CPM engine
    CONSTRAINT chk_no_self_dependency CHECK (predecessor_id <> successor_id),
    CONSTRAINT uq_pred_succ UNIQUE (predecessor_id, successor_id)
);
```

### 2.4 Driving vs. Non-Driving Relationship
* **Formal Definition:**
  * **Driving Relationship:** A predecessor dependency link that is the active mathematical constraint determining the successor’s Early Start or Early Finish date.
  * **Non-Driving Relationship:** A dependency link where other incoming predecessors push the successor further out, rendering this link non-binding.
* **Mathematical Evaluation (for FS relationship):**
  If activity $B$ has predecessors $A_1, A_2, \dots, A_n$:
  $$\text{Early Start}_B = \max_{i} (\text{Early Finish}_{A_i} + \text{Lag}_i)$$
  A link $(A_k, B)$ is **driving** if and only if:
  $$\text{Early Finish}_{A_k} + \text{Lag}_k = \text{Early Start}_B$$
* **Solar Example:** Inverter installation requires both (1) Concrete foundation cured (Ready Day 20) and (2) Inverter hardware delivered to site (Ready Day 35). The hardware delivery link is **driving**; the concrete foundation link is **non-driving** (it has 15 days of slack).

```go
// Driving relationship check in Golang CPM engine
func IsDrivingFS(predEF time.Time, lag time.Duration, succES time.Time) bool {
    effectiveFinish := predEF.Add(lag)
    return effectiveFinish.Equal(succES)
}
```

### 2.5 Data Date (Status Date / As-Of Date)
* **Formal Definition:** The impenetrable temporal boundary line that separates historical project execution (the past) from forecasted CPM calculations (the future).
* **Engine Rules:**
  * Activities completed before the Data Date must have `actual_start_date` and `actual_finish_date`.
  * Activities currently in-progress span across the Data Date; remaining duration is scheduled forward from the Data Date.
  * Future planned activities can never have calculated early dates earlier than the Data Date.
* **Solar Example:** Project status update meeting on Month 4, Day 15 (`Data Date = 2026-04-15 17:00:00 UTC`). All 45,000 tracker posts driven prior to this date are frozen actuals; all electrical work is forecasted from this boundary.

```
PAST (Actuals Recorded)                  FUTURE (CPM Scheduled)
────────────────────────────────┼──────────────────────────────►
                                ▲
                            DATA DATE
                       (e.g., Apr 15, 2026)
```

### 2.6 Forward Pass
* **Formal Definition:** The algorithmic phase of the Critical Path Method that traverses the activity graph in topological order from the Project Start / Data Date to the Project Finish, computing the **Early Start (ES)** and **Early Finish (EF)** dates for every node.
* **Algorithm Steps:**
  1. For each source node $v$ (in-degree = 0):
     $$\text{Early Start}_v = \text{Data Date}$$
     $$\text{Early Finish}_v = \text{CalculateCalendarFinish}(\text{Early Start}_v, \text{Duration}_v)$$
  2. For every successor $u$ traversed in topological order:
     $$\text{Early Start}_u = \max_{p \in Pred(u)} (\text{ResolveEarlyStartConstraint}(p, u))$$
     $$\text{Early Finish}_u = \text{CalculateCalendarFinish}(\text{Early Start}_u, \text{Duration}_u)$$

### 2.7 Backward Pass
* **Formal Definition:** The algorithmic phase of the Critical Path Method that traverses the activity graph in reverse topological order from the Project Finish back to the Data Date, computing the **Late Finish (LF)** and **Late Start (LS)** dates.
* **Algorithm Steps:**
  1. For terminal nodes $w$ (out-degree = 0):
     $$\text{Late Finish}_w = \text{Early Finish}_w \quad (\text{or Contractual Finish Milestone})$$
     $$\text{Late Start}_w = \text{CalculateCalendarStart}(\text{Late Finish}_w, \text{Duration}_w)$$
  2. For every predecessor $v$ traversed in reverse topological order:
     $$\text{Late Finish}_v = \min_{s \in Succ(v)} (\text{ResolveLateFinishConstraint}(v, s))$$
     $$\text{Late Start}_v = \text{CalculateCalendarStart}(\text{Late Finish}_v, \text{Duration}_v)$$

### 2.8 Early Start (ES) & Early Finish (EF)
* **Early Start (ES):** The earliest possible calendar timestamp an activity can start based on predecessor network logic and constraints.
* **Early Finish (EF):** The earliest possible calendar timestamp an activity can finish.
  $$\text{EF} = \text{ES} \oplus \text{Remaining Duration (using activity calendar)}$$
  *(Note: $\oplus$ denotes calendar-aware date addition honoring shift intervals).*

### 2.9 Late Start (LS) & Late Finish (LF)
* **Late Finish (LF):** The latest possible calendar timestamp an activity can finish without delaying the overall project completion date (or a contractual finish constraint).
* **Late Start (LS):** The latest possible calendar timestamp an activity can start without delaying project completion.
  $$\text{LS} = \text{LF} \ominus \text{Remaining Duration (using activity calendar)}$$

### 2.10 Free Float (FF)
* **Formal Definition:** The amount of time an activity can slip without delaying the **Early Start** of any immediate successor activity.
* **Mathematical Formula:**
$$\text{Free Float}_i = \min_{j \in Succ(i)} \left( \text{ES}_j - \text{Lag}_{ij} \right) - \text{EF}_i$$
* **Intuition:** Free float belongs exclusively to that specific activity. Delaying an activity within its Free Float does not impact any other task in the entire company schedule.
* **Solar Example:** Activity `Order Auxiliary Fence Paint (Duration: 2d)` finishes on Day 10. Successor `Paint Fencing` cannot start until Day 25 when fence installation completes. Free Float = 15 days.

### 2.11 Total Float (TF) & Negative Float
* **Formal Definition:** The total duration an activity can be delayed from its Early Start without delaying the **Project Contractual Completion Date** (or violating a mandatory finish milestone).
* **Mathematical Formula:**
$$\text{Total Float}_i = \text{Late Finish}_i - \text{Early Finish}_i = \text{Late Start}_i - \text{Early Start}_i$$
* **Negative Float:** Occurs when an external hard constraint or mandatory deadline is earlier than the calculated CPM Early Finish date ($LF < EF$).
  $$\text{Total Float} < 0 \implies \text{Project is in critical delay!}$$
* **Solar Example:** Grid Synchronization deadline is locked to Day 300. Major substation transformer explosion delays calculated early finish to Day 320. Substation tasks now show **Total Float = -20 days**.

### 2.12 Critical Path vs. Longest Path
* **Critical Path:** Classically defined as the sequence of activities where **Total Float $\le 0$** (or $\le$ user-defined threshold, e.g., $\text{TF} \le 0$).
* **Longest Path:** The continuous, unbroken chain of driving relationships from the project start/Data Date to the project finish milestone that dictates the total schedule duration.
* **The Crucial P6 Distinction:**
  * When a schedule contains multiple calendars (e.g., 5-day office engineering vs. 7-day concrete curing) or artificial hard constraints, an activity can have negative float or float of 1 day while not actually being on the continuous driving chain to completion.
  * **Longest Path** traces purely driving dependencies ($IsDriving = true$) from start to finish. In legal dispute analysis and delay forensics, courts prefer the **Longest Path** method to prevent false critical paths caused by constraint manipulation.

### 3.1 Calendar
* **Formal Definition:** A configurable schedule template that specifies the working and non-working days, work shifts (working hours per day), and holiday exceptions across a project timeline.
* **Intuition:** A calendar acts as a time-dilation lens. In a 5-day, 8-hr/day calendar, 40 hours of work requires 7 calendar days. In a 7-day 24-hr calendar, 40 hours of work requires 1.67 calendar days.

### 3.2 Calendar Work Pattern & Shifts
* **Formal Definition:** The recurring weekly pattern of working days and intraday shift blocks.
* **Shift Interval:** Defined by start and end minute offsets within a 24-hour day (e.g., Shift 1: 08:00–12:00, Shift 2: 13:00–17:00).
* **Database Representation:**
```sql
CREATE TYPE calendar_type_enum AS ENUM ('global', 'project', 'resource');

CREATE TABLE calendars (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE, -- NULL if global
    name VARCHAR(128) NOT NULL,
    calendar_type calendar_type_enum NOT NULL DEFAULT 'project',
    hours_per_day NUMERIC(4,2) NOT NULL DEFAULT 8.00,
    hours_per_week NUMERIC(5,2) NOT NULL DEFAULT 40.00,
    hours_per_month NUMERIC(6,2) NOT NULL DEFAULT 160.00,
    hours_per_year NUMERIC(7,2) NOT NULL DEFAULT 1920.00
);

CREATE TABLE calendar_weekly_shifts (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    calendar_id UUID NOT NULL REFERENCES calendars(id) ON DELETE CASCADE,
    day_of_week SMALLINT NOT NULL, -- 0 = Sunday, 1 = Monday ... 6 = Saturday
    start_time_seconds INT NOT NULL, -- Seconds from midnight (e.g., 28800 = 08:00)
    end_time_seconds INT NOT NULL,   -- Seconds from midnight (e.g., 61200 = 17:00)
    CONSTRAINT chk_shift_time CHECK (start_time_seconds < end_time_seconds)
);
```

### 3.3 Calendar Exceptions (Holidays & Weather)
* **Formal Definition:** Specific non-recurring dates or date intervals that override the standard weekly shift pattern (e.g., national holidays, plant turnarounds, scheduled monsoon/extreme summer shutdown periods).
* **100MW Solar Example:** Thar Desert extreme heat shutdown: No afternoon outdoor piling allowed between June 01 and June 30 from 12:00 to 16:00.
* **Database Representation:**
```sql
CREATE TABLE calendar_exceptions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    calendar_id UUID NOT NULL REFERENCES calendars(id) ON DELETE CASCADE,
    start_timestamp TIMESTAMPTZ NOT NULL,
    end_timestamp TIMESTAMPTZ NOT NULL,
    is_working_override BOOLEAN NOT NULL DEFAULT FALSE, -- Usually false (holiday)
    description VARCHAR(255)
);
```

### 3.4 Global Calendar vs. Project Calendar vs. Resource Calendar
* **Global Calendar:** Enterprise-wide calendar accessible to all projects across the EPS (e.g., `Corporate 5-Day Standard`, `National Statutory Holidays`).
* **Project Calendar:** Private to a specific project. Edits made by the project planner do not impact other enterprise projects (e.g., `Surya 100MW 6-Day Site Work Calendar`).
* **Resource Calendar:** Assigned to a specific human or machine resource reflecting personal vacations, rotation schedules, or maintenance overhauls (e.g., `Rig-01 Hydraulic Overhaul Calendar`).

### 3.5 Calendar Mask (Bitmask Engine Architecture)
* **Formal Definition:** An in-memory data structure where time is discretized into discrete slices (e.g., 1-hour or 15-minute bits) where `1` represents working time and `0` represents non-working time.
* **Golang Implementation:** Enables ultra-fast calendar arithmetic via bitwise operations rather than slow database queries.

```go
type MinuteWorkMask struct {
    // 1440 bits per day represented as slice of 23 uint64 words
    Bits [23]uint64
}

func (m *MinuteWorkMask) IsWorking(minuteOfDay int) bool {
    word := minuteOfDay / 64
    bit := minuteOfDay % 64
    return (m.Bits[word] & (1 << bit)) != 0
}
```

## 6. Section 4: Date Constraints

Constraints in P6 are classified into **Soft Constraints** (which respect network logic) and **Hard Constraints** (which forcibly override mathematical CPM logic).

```
                      ┌──────────────────────────────┐
                      │    DATE CONSTRAINT TYPES     │
                      └──────────────┬───────────────┘
                     ┌───────────────┴───────────────┐
                     ▼                               ▼
          [Soft / Logic-Preserving]        [Hard / Logic-Breaking]
          • As Soon As Possible (ASAP)     • Mandatory Start
          • As Late As Possible (ALAP)     • Mandatory Finish
          • Start On or After (SOA)
          • Finish On or Before (FOB)
```

### 4.1 As Soon As Possible (ASAP)
* **Definition:** The default, natural state of CPM scheduling. The activity begins on its calculated Early Start date as soon as all predecessors are satisfied.

### 4.2 As Late As Possible (ALAP)
* **Definition:** Forces an activity to consume all of its available float and schedule its Early Start equal to its Late Start ($ES = LS$), without pushing the overall project finish.
* **100MW Solar Example:** `Procure PV Cleaning Robots`. The developer delays procurement to the absolute latest possible week before commissioning to minimize warranty expiry during construction.

### 4.3 Start On (Must Start On) & Finish On (Must Finish On)
* **Definition:** Soft constraints that pin the activity's Early and Late dates to a specific calendar date, but may allow backward push depending on calculation settings.
* **Impact:** Compresses float to zero at that point in the network.

### 4.4 Start On or After (SOA) & Start On or Before (SOB)
* **Start On or After (Early Start Constraint):** Specifies that the activity cannot start earlier than date $D$, even if predecessors finish earlier.
  $$\text{Early Start} = \max(\text{Calculated ES}, D)$$
  * **Solar Example:** `Delivery of 33kV Transformers (SOA: Sept 01, 2026)` because the supplier factory cannot ship before that date.
* **Start On or Before:** Sets an upper bound on late start dates.

### 4.5 Finish On or After (FOA) & Finish On or Before (FOB)
* **Finish On or Before (Late Finish Constraint):** Specifies that the activity must complete by date $D$ or earlier.
  $$\text{Late Finish} = \min(\text{Calculated LF}, D)$$
  * **Solar Example:** `Complete River Crossing Transmission Tower Foundations (FOB: June 15)` to beat the annual river flooding season.

### 4.6 Mandatory Start & Mandatory Finish (Hard Constraints)
* **Formal Definition:** An uncompromising constraint that forcibly overrides all predecessor and successor network logic, fixing the activity start or finish to an exact date regardless of whether predecessors are completed.
* **Why It Is Toxic to CPM Engines:**
  * If a predecessor slips past the Mandatory Start date, the engine will schedule the activity to start **before its predecessor finishes**, creating physically impossible reality.
  * Generates large negative floats that distort the true critical path.
* **Database Representation:**
```sql
CREATE TYPE constraint_type_enum AS ENUM (
    'asap',
    'alap',
    'start_on',
    'finish_on',
    'start_on_or_after',
    'start_on_or_before',
    'finish_on_or_after',
    'finish_on_or_before',
    'mandatory_start',
    'mandatory_finish'
);

ALTER TABLE activities ADD COLUMN primary_constraint_type constraint_type_enum DEFAULT 'asap';
ALTER TABLE activities ADD COLUMN primary_constraint_date TIMESTAMPTZ;
```

## 7. Section 5: Baselines & Progress Tracking

```
LIVE SCHEDULE:     [Act 1 (Actual: Jan 1-15)] ───► [Act 2 (Forecast: Jan 16-30)]
                                                         │ (+5d Slippage)
                                                         ▼
PROJECT BASELINE:  [Act 1 (Planned: Jan 1-10)] ───► [Act 2 (Planned: Jan 11-25)]
```

### 5.1 Current Schedule (Live Project)
* **Formal Definition:** The active, mutable working schedule reflecting field realities, daily updates, actual dates recorded, remaining durations, and live CPM calculations.

### 5.2 Baseline (Project Baseline B1, Secondary B2, What-If)
* **Formal Definition:** A frozen, immutable copy of the project schedule approved by stakeholders at contract award (Notice to Proceed). It serves as the benchmark against which performance, cost, and schedule variances are measured.
* **P6 Multi-Baseline Hierarchy:**
  * **Project Baseline (B1):** The contractual master schedule (Target 1).
  * **User Baseline (B2):** An internal target used by project managers for aggressive site pacing.
  * **What-If Baseline:** A scenario model used to evaluate the impact of change orders or delay claims before committing them.
* **Database Representation:**
```sql
CREATE TABLE project_baselines (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    baseline_type VARCHAR(32) NOT NULL, -- 'project_baseline', 'user_baseline', 'what_if'
    name VARCHAR(255) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    snapshot_data JSONB NOT NULL -- Full serialized graph of WBS, activities, dates
);
```

### 5.3 Schedule Variance (Time Slippage)
* **Formal Definition:** The difference in days or hours between the live forecasted finish date and the baseline finish date.
$$\text{Schedule Finish Variance} = \text{Baseline Finish Date} - \text{Current Early Finish Date}$$
* A negative value indicates project slippage (behind schedule).

### 5.4 Percent Complete Types
P6 provides three distinct ways to measure progress on an activity. Choosing the wrong type is the most common beginner error in project controls:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                               PERCENT COMPLETE TYPES                                   │
├──────────────────────────┬──────────────────────────────┬──────────────────────────────┤
│ 1. Duration % Complete   │ 2. Physical % Complete       │ 3. Units % Complete          │
├──────────────────────────┼──────────────────────────────┼──────────────────────────────┤
│ • Pure mathematical     │ • Independent manual entry   │ • Purely resource-driven     │
│   function of time.      │   representing actual work.  │   calculation.               │
│ • Tied to Remaining      │ • Decoupled from Remaining   │ • Tied to Work Hours or      │
│   Duration!              │   Duration!                  │   Financial Quantities.      │
│ • Formula:               │ • Used for Earned Value      │ • Formula:                   │
│   (OD - RD) / OD         │   (EV = BAC * Phys%)         │   Actual Units / Total Units │
└──────────────────────────┴──────────────────────────────┴──────────────────────────────┘
```

#### 5.4.1 Duration % Complete
* **Formula:**
$$\text{Duration \% Complete} = \frac{\text{Original Duration} - \text{Remaining Duration}}{\text{Original Duration}} \times 100$$
* **Behavior:** When the user edits Duration %, P6 automatically overrides `Remaining Duration`.
* **Danger:** If an activity takes 5 days of an allocated 10 days, Duration % is 50%. But what if workers only completed 10% of the physical wall? Duration % gives a dangerously false picture of progress.

#### 5.4.2 Physical % Complete
* **Formula:** User or field engineer enters an audited percentage (e.g., $32.5\%$) based on actual physical deliverables (e.g., cubic meters of concrete poured, miles of cable laid).
* **Crucial Property:** Entering Physical % Complete **does not** automatically recalculate `Remaining Duration`. If a task is 80% physically complete but unexpected rock formations mean it will take another 20 days to finish, the planner can enter `Physical % = 80%` and `Remaining Duration = 20 days` independently.
* **Standard:** Mandated for all ANSI/EIA-748 Earned Value Management systems.

#### 5.4.3 Units % Complete (Labor / Cost % Complete)
* **Formula:**
$$\text{Units \% Complete} = \frac{\text{Actual Labor Units}}{\text{Actual Labor Units} + \text{Remaining Labor Units}} \times 100$$
* **Behavior:** Directly tied to the resource timesheets and man-hour consumption.

## 8. Section 6: Resources, Roles & Leveling

```
[Role: Certified High-Voltage Cable Jointer]  <-- Abstract Skill Requirement
                     ▲
                     │ (Staffed by)
[Resource: Anand Kumar, Jointer Tech #4]       <-- Concrete Entity (Calendar, Pay Rate)
```

### 6.1 Role vs. Resource
* **Role:** An abstract skill set, trade, or title required to perform work, without naming a specific individual or piece of equipment (e.g., `Civil Surveyor`, `200-Ton Crane`, `Piling Rig`).
* **Resource:** A concrete, named entity assigned to execute work, possessing an individual calendar, unit cost rates, and maximum capacity limits (e.g., `Rig-Bauer-BG28`, `John Smith`).
* **Engineering Flow:** In early engineering phases, activities have **Roles** assigned. During mobilization, Roles are substituted with specific **Resources**.

### 6.2 Max Units / Time (Capacity)
* **Formal Definition:** The maximum capacity of a resource expressed in units per work period (e.g., $8.0\text{ h/d}$ or $100\%$ for one full-time worker; $40\text{ h/d}$ or $500\%$ for a crew of 5 electricians).

### 6.3 Primary Resource
* **Formal Definition:** The principal resource among multiple assignments designated as the driver of the activity’s progress, status updates, and calendar (when the activity type is *Resource Dependent*).

### 6.4 Resource Allocation & Overallocation
* **Resource Allocation:** The sum of assigned resource units across all overlapping activities active on a given calendar day.
* **Overallocation:** Occurs whenever the total demand for a resource exceeds its `Max Units / Time` on that day.
$$\sum_{k \in Active(t)} \text{Assigned Rate}_k(t) > \text{Max Available Capacity}(t)$$
* **100MW Solar Example:** 5 different inverter blocks all schedule transformer pad excavation on Day 45. Each pad requires 1 excavator. The site only has 2 excavators mobilized. Peak demand = 5 excavators; Capacity = 2 excavators. **Overallocation = 3 excavators**.

```
Units
  6 ┌───┐
  5 │   │  <--- OVERALLOCATION (Deficit: 3 Units)
  4 │   │
────┼───┴─────── Max Capacity Limit = 2 Units
  2 │   │
  1 │   │
  0 └───┴───────
     Day 45
```

### 6.5 Resource Leveling (Heuristic Smoothing)
* **Formal Definition:** An algorithmic scheduling procedure that resolves resource overallocations by delaying activities within their available float (or pushing the project end date) based on priority heuristics.
* **Leveling Heuristics:**
  1. Earliest Late Start (least float first).
  2. Total Float ascending.
  3. Activity ID / User Priority code.
* **Database Representation:**
```sql
CREATE TABLE resources (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code VARCHAR(32) NOT NULL UNIQUE,
    name VARCHAR(128) NOT NULL,
    resource_type VARCHAR(16) NOT NULL, -- 'labor', 'non_labor', 'material'
    unit_of_measure VARCHAR(16),        -- 'hours', 'tons', 'm3'
    calendar_id UUID NOT NULL REFERENCES calendars(id),
    default_cost_per_unit NUMERIC(12,2) NOT NULL DEFAULT 0.00,
    max_units_per_day NUMERIC(6,2) NOT NULL DEFAULT 8.00 -- 1 person = 8 hrs/day
);

CREATE TABLE resource_assignments (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    activity_id UUID NOT NULL REFERENCES activities(id) ON DELETE CASCADE,
    resource_id UUID NOT NULL REFERENCES resources(id) ON DELETE CASCADE,
    planned_units NUMERIC(12,2) NOT NULL,
    actual_units NUMERIC(12,2) NOT NULL DEFAULT 0.00,
    remaining_units NUMERIC(12,2) NOT NULL,
    planned_cost NUMERIC(14,2) NOT NULL,
    actual_cost NUMERIC(14,2) NOT NULL DEFAULT 0.00,
    is_primary_resource BOOLEAN NOT NULL DEFAULT FALSE
);
```

### 6.6 Resource Curves / Profiles (Spread Distribution)
* **Formal Definition:** Mathematical algorithms that distribute resource hours and costs across an activity’s duration.
* **Curve Types:**
  * **Linear:** Even distribution ($\text{Units}/day = \text{Total} / \text{Duration}$).
  * **Front-Loaded:** Heavy effort at the beginning (e.g., site mobilization, planning).
  * **Back-Loaded:** Heavy effort at the end (e.g., commissioning, punch-listing).
  * **Bell-Shaped:** Normal distribution representing gradual ramp-up, peak execution, and ramp-down.
  * **S-Curve:** Cumulative integration of the Bell curve over time.

## 9. Section 7: Cost & Earned Value Management (EVM)

```
$ Cost
 ▲                                      BAC (Budget At Completion)
 │                                        ┌─────────
 │                                     ▲  │   EAC (Forecasted Cost)
 │                                     │  ▼
 │                                ┌────┼───────── PV (Planned Value)
 │                            ┌───┘    │
 │                       ┌────┘   ▲    │   EV (Earned Value)
 │                   ┌───┘        │ SV │
 │             ┌─────┘            ▼    │
 │       ┌─────┘  ▲ ───────────────────┘
 │   ┌───┘        │ CV
 │ ┌─┘            ▼
 └─┴───────────────────────────────► Time
                ▲
            DATA DATE
```

Earned Value Management (EVM) is the international standard (ANSI/EIA-748) for integrating scope, schedule, and cost performance.

### 7.1 Budget at Completion (BAC)
* **Formal Definition:** The total authorized baseline budget for the project, WBS branch, or activity.
* **Formula:** Sum of all baseline planned costs.
$$\text{BAC} = \sum_{k} \text{Planned Cost}_k$$
* **100MW Solar Example:** Total Turnkey EPC Contract Value = **$68,000,000 USD**.

### 7.2 Planned Value (PV / BCWS)
* **Formal Definition:** **Budgeted Cost of Work Scheduled**. The authorized budget assigned to scheduled work expected to be completed up to the Data Date according to the baseline schedule.
* **Formula:**
$$\text{PV} = \text{BAC} \times \text{Baseline Planned \% Complete}$$

### 7.3 Earned Value (EV / BCWP)
* **Formal Definition:** **Budgeted Cost of Work Performed**. The measure of work physically performed expressed in terms of the budget authorized for that work.
* **Formula:**
$$\text{EV} = \text{BAC} \times \text{Physical \% Complete}$$
* **Golden Rule:** Earned Value cares only about physical progress achieved, never about how much money was actually spent!

### 7.4 Actual Cost (AC / ACWP)
* **Formal Definition:** **Actual Cost of Work Performed**. The total realized cost incurred and recorded in accounting in executing the work completed up to the Data Date.

### 7.5 Schedule Variance (SV) & SV %
* **Formal Definition:** The financial monetization of schedule advancement or slippage.
* **Formula:**
$$\text{SV} = \text{EV} - \text{PV}$$
$$\text{SV \%} = \frac{\text{SV}}{\text{PV}} \times 100$$
* **Interpretation:**
  * $\text{SV} > 0$: Ahead of schedule.
  * $\text{SV} = 0$: Exactly on schedule.
  * $\text{SV} < 0$: Behind schedule (loss of budgeted value).

### 7.6 Cost Variance (CV) & CV %
* **Formal Definition:** The financial difference between earned earned deliverable value and actual cash spent.
* **Formula:**
$$\text{CV} = \text{EV} - \text{AC}$$
$$\text{CV \%} = \frac{\text{CV}}{\text{EV}} \times 100$$
* **Interpretation:**
  * $\text{CV} > 0$: Under budget (cost savings).
  * $\text{CV} = 0$: Exactly on budget.
  * $\text{CV} < 0$: Over budget (cost overrun).

### 7.7 Schedule Performance Index (SPI)
* **Formal Definition:** A metric of schedule efficiency representing the ratio of work earned to work planned.
* **Formula:**
$$\text{SPI} = \frac{\text{EV}}{\text{PV}}$$
* **Interpretation:** $\text{SPI} = 0.85$ means the project is progressing at only 85% of the planned schedule speed.
* **Boundary Condition in Code:** If $\text{PV} = 0$, $\text{SPI} = 1.00$ (by definition before work starts).

### 7.8 Cost Performance Index (CPI)
* **Formal Definition:** A metric of financial cost efficiency representing the ratio of work earned to actual funds expended.
* **Formula:**
$$\text{CPI} = \frac{\text{EV}}{\text{AC}}$$
* **Interpretation:** $\text{CPI} = 0.80$ means that for every \$1.00 spent on site, the contractor earns only \$0.80 worth of tangible solar plant deliverables (\$0.20 wasted).

### 7.9 Estimate to Complete (ETC)
* **Formal Definition:** The expected additional cost required to finish all remaining scope from the Data Date onward.
* **Standard Formula (assuming future work continues at current CPI efficiency):**
$$\text{ETC} = \frac{\text{BAC} - \text{EV}}{\text{CPI}}$$

### 7.10 Estimate at Completion (EAC)
* **Formal Definition:** The expected total ultimate cost of the project upon completion.
* **Formula:**
$$\text{EAC} = \text{AC} + \text{ETC} = \text{AC} + \frac{\text{BAC} - \text{EV}}{\text{CPI}} = \frac{\text{BAC}}{\text{CPI}}$$

### 7.11 Variance at Completion (VAC) & To-Complete Performance Index (TCPI)
* **Variance at Completion (VAC):** Projected budget surplus or deficit at final project handover.
$$\text{VAC} = \text{BAC} - \text{EAC}$$
* **To-Complete Performance Index (TCPI):** The cost efficiency that must be achieved on remaining work to complete within the original authorized budget (BAC).
$$\text{TCPI}_{BAC} = \frac{\text{BAC} - \text{EV}}{\text{BAC} - \text{AC}}$$

## 10. Comprehensive Database Schema & Golang Engine Architecture

To build a high-performance P6 scheduling engine in Golang with PostgreSQL, model the relationships as an adjacency list graph and compute CPM passes using topological sorting:

```go
package cpmengine

import (
	"time"
	"github.com/google/uuid"
	"github.com/shopspring/decimal"
)

type ActivityType string
const (
	TaskDependent     ActivityType = "task_dependent"
	ResourceDependent ActivityType = "resource_dependent"
	LevelOfEffort     ActivityType = "level_of_effort"
	StartMilestone    ActivityType = "start_milestone"
	FinishMilestone   ActivityType = "finish_milestone"
	WBSSummary        ActivityType = "wbs_summary"
)

type RelationType string
const (
	RelFS RelationType = "FS"
	RelSS RelationType = "SS"
	RelFF RelationType = "FF"
	RelSF RelationType = "SF"
)

// GraphActivity represents an in-memory CPM activity node
type GraphActivity struct {
	ID                uuid.UUID
	Code              string
	Type              ActivityType
	CalendarID        uuid.UUID
	OriginalDuration  time.Duration
	RemainingDuration time.Duration
	ActualDuration    time.Duration

	// Dates
	EarlyStart  time.Time
	EarlyFinish time.Time
	LateStart   time.Time
	LateFinish  time.Time
	ActualStart *time.Time
	ActualFinish *time.Time

	// Floats
	FreeFloat  time.Duration
	TotalFloat time.Duration
	IsCritical bool

	// Adjacency edges
	Predecessors []*GraphDependency
	Successors   []*GraphDependency

	// EVM Fields
	BAC          decimal.Decimal
	PhysicalPct  decimal.Decimal
	ActualCost   decimal.Decimal
}

type GraphDependency struct {
	ID            uuid.UUID
	PredecessorID uuid.UUID
	SuccessorID   uuid.UUID
	Type          RelationType
	Lag           time.Duration
	IsDriving     bool
}

// CalculateEVM performs Earned Value math for an activity
func (a *GraphActivity) CalculateEVM(plannedPct decimal.Decimal) (ev, sv, cv, spi, cpi decimal.Decimal) {
	// EV = BAC * Physical%
	ev = a.BAC.Mul(a.PhysicalPct)
	pv := a.BAC.Mul(plannedPct)

	sv = ev.Sub(pv)
	cv = ev.Sub(a.ActualCost)

	if !pv.IsZero() {
		spi = ev.Div(pv)
	} else {
		spi = decimal.NewFromInt(1)
	}

	if !a.ActualCost.IsZero() {
		cpi = ev.Div(a.ActualCost)
	} else {
		cpi = decimal.NewFromInt(1)
	}

	return ev, sv, cv, spi, cpi
}
```

## 12. Summary & Engineering Takeaways

1. **A P6 activity is not a database row with two dates:** It is a node in a mathematical network governed by forward/backward passes, calendar bitmasks, and driving relationships.
2. **Never mix progress types:** Always use **Physical % Complete** for engineering/construction deliverables to decouple actual progress from estimated remaining duration.
3. **Guard the Critical Path:** Distinguish between **Total Float $\le 0$** and the true **Longest Path** to prevent schedule distortions caused by constraints and disparate calendars.
4. **Earned Value is the single source of truth:** Project controls integrates cost and time through $EV = BAC \times Physical\%$, allowing algorithmic detection of project distress long before physical deadlines are missed.
