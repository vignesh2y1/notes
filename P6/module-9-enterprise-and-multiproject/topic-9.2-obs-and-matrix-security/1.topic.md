In software engineering terms:
* **EPS (Enterprise Project Structure)** is the **Resource Hierarchy** (the target objects being protected).
* **OBS (Organizational Breakdown Structure)** is the **Subject/Role Hierarchy** (the management chain and organizational entities).
* **Security Profiles** are the **Permission Sets** (the granular ACLs defining read, write, delete, baselining, and scheduling execution rights).

The **EPS-OBS Security Matrix** connects these three primitives. Without understanding this matrix, an engineering team attempting to build an enterprise scheduling platform will either hardcode brittle user roles (`is_admin`, `is_pm`) or suffer massive security breaches where third-party contractors can read corporate financial baselines.

## 2. Conceptual Foundations: The Organizational Breakdown Structure (OBS)

### 2.1 What is the OBS?
The **Organizational Breakdown Structure (OBS)** represents the people, departments, management reporting chains, and corporate hierarchy of an organization. Unlike standard user accounts, which represent individual logins, the OBS represents **positions and management roles** (e.g., "VP Solar Operations", "Civil Project Engineer", "Electrical Commissioning Lead").

Key characteristics of the OBS:
1. **Hierarchical Management Chain:** An OBS tree models reporting relationships from executive leadership down to project managers and discipline leads.
2. **Decoupled from User Identity:** Users are assigned to OBS nodes. If a Project Manager leaves the company, a new user account is simply assigned to that existing OBS node, preserving all historical project governance associations.
3. **Decoupled from Project Scope:** OBS represents *who is responsible*, whereas WBS represents *what work is being done*. A single OBS node (e.g., "Civil Engineering Lead") may be responsible for WBS elements across multiple independent projects.

## 3. The EPS-OBS Security Matrix: Mechanics of Cascading Access

### 3.1 The Responsible Manager Assignment
In enterprise P6 architecture, every EPS node and every Project record contains a mandatory foreign key: **`obs_id` (Responsible Manager)**.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                            CASCADING ACCESS CONTROL VIA EPS & OBS                                │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   EPS Hierarchy                                   Assigned Responsible Manager (OBS)             │
│   ═════════════                                   ══════════════════════════════════             │
│   [EPS] SURYA-SOLAR (Utility Solar) ─────────────► [OBS] VP Solar Operations                     │
│     │                                                                                            │
│     ├── [EPS] SOLAR-NORTH (North Region) ────────► [OBS] Senior Regional Director (North)        │
│     │     │                                                                                      │
│     │     └── [PRJ] PRJ-SOL-100 (100MW Solar) ───► [OBS] Lead Project Manager (Rajasthan)        │
│     │                                                                                            │
│     └── [EPS] SOLAR-WEST (West Region) ──────────► [OBS] Senior Regional Director (West)         │
│           │                                                                                      │
│           └── [PRJ] PRJ-SOL-200 (200MW Khavda) ──► [OBS] Lead Project Manager (Gujarat)          │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 Cascading Inheritance Rules
1. **Top-Down Privilege Inheritance:** If user **Anita** is granted access to the OBS node `VP Solar Operations` with the Project Profile `Project Manager`, Anita automatically inherits `Project Manager` permissions across:
   - The EPS node `SURYA-SOLAR`;
   - All descendant EPS nodes (`SOLAR-NORTH`, `SOLAR-WEST`);
   - All projects within those nodes (`PRJ-SOL-100`, `PRJ-SOL-200`).
2. **Explicit Override at Lower Tiers:** If a project or child EPS node specifies a different Responsible Manager, a user whose access is granted only at that child node has privileges restricted to that subtree.
3. **Third-Party Contractor Sandboxing:** A third-party EPC contractor assigned to `Lead Project Manager (Rajasthan)` with a `Field Statusing` profile can *only* see and update progress for `PRJ-SOL-100`. They cannot see `PRJ-SOL-200` or the parent division.

## 5. Enterprise Database Architecture (PostgreSQL)

### 5.1 Relational Schema for OBS, Profiles, and Matrix Grants

```sql
-- 1. Organizational Breakdown Structure (OBS) Table
CREATE TABLE obs_node (
    obs_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    obs_code VARCHAR(32) NOT NULL UNIQUE,
    obs_name VARCHAR(120) NOT NULL,
    parent_obs_id UUID REFERENCES obs_node(obs_id) ON DELETE RESTRICT,
    obs_path ltree NOT NULL,
    description TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);
CREATE INDEX idx_obs_path ON obs_node USING GIST (obs_path);

-- 2. Project Security Profiles Table
CREATE TABLE project_security_profile (
    profile_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    profile_name VARCHAR(64) NOT NULL UNIQUE,
    description TEXT,
    
    -- Granular Permission Flags
    can_view_project BOOLEAN NOT NULL DEFAULT TRUE,
    can_edit_project_details BOOLEAN NOT NULL DEFAULT FALSE,
    can_add_delete_activities BOOLEAN NOT NULL DEFAULT FALSE,
    can_edit_activity_dates BOOLEAN NOT NULL DEFAULT FALSE,
    can_edit_activity_progress BOOLEAN NOT NULL DEFAULT FALSE,
    can_execute_scheduling BOOLEAN NOT NULL DEFAULT FALSE, -- F9 Execute
    can_create_baseline BOOLEAN NOT NULL DEFAULT FALSE,
    can_restore_baseline BOOLEAN NOT NULL DEFAULT FALSE,
    can_view_costs BOOLEAN NOT NULL DEFAULT FALSE,
    can_edit_costs BOOLEAN NOT NULL DEFAULT FALSE,
    can_edit_udfs BOOLEAN NOT NULL DEFAULT FALSE,
    
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

-- 3. Application Users Table
CREATE TABLE app_user (
    user_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    username VARCHAR(64) NOT NULL UNIQUE,
    email VARCHAR(255) NOT NULL UNIQUE,
    is_super_admin BOOLEAN NOT NULL DEFAULT FALSE,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

-- 4. User-to-OBS Security Matrix Grant Table
CREATE TABLE user_obs_grant (
    grant_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES app_user(user_id) ON DELETE CASCADE,
    obs_id UUID NOT NULL REFERENCES obs_node(obs_id) ON DELETE CASCADE,
    profile_id UUID NOT NULL REFERENCES project_security_profile(profile_id) ON DELETE RESTRICT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    CONSTRAINT uq_user_obs_grant UNIQUE (user_id, obs_id)
);
CREATE INDEX idx_user_obs_grant_user ON user_obs_grant(user_id);
CREATE INDEX idx_user_obs_grant_obs ON user_obs_grant(obs_id);
```

### 5.2 Dynamic Permission Resolution Function
To determine whether a specific user has permission to perform an action on a specific project:

```sql
CREATE OR REPLACE FUNCTION fn_check_user_project_permission(
    p_user_id UUID,
    p_project_id UUID,
    p_required_permission VARCHAR
) RETURNS BOOLEAN AS $$
DECLARE
    v_is_super BOOLEAN;
    v_project_obs_path ltree;
    v_has_permission BOOLEAN;
BEGIN
    -- 1. Super Admin bypass
    SELECT is_super_admin INTO v_is_super FROM app_user WHERE user_id = p_user_id;
    IF v_is_super IS TRUE THEN
        RETURN TRUE;
    END IF;

    -- 2. Lookup the project's Responsible Manager OBS path
    SELECT o.obs_path INTO v_project_obs_path
    FROM project p
    JOIN obs_node o ON o.obs_id = p.obs_id
    WHERE p.project_id = p_project_id;

    IF v_project_obs_path IS NULL THEN
        RETURN FALSE;
    END IF;

    -- 3. Check if user has an OBS grant at or above the project's OBS node
    -- Uses ltree ancestor operator (@>)
    EXECUTE format('
        SELECT EXISTS (
            SELECT 1
            FROM user_obs_grant g
            JOIN obs_node o ON o.obs_id = g.obs_id
            JOIN project_security_profile psp ON psp.profile_id = g.profile_id
            WHERE g.user_id = $1
              AND o.obs_path @> $2
              AND psp.%I = TRUE
        )', p_required_permission)
    INTO v_has_permission
    USING p_user_id, v_project_obs_path;

    RETURN COALESCE(v_has_permission, FALSE);
END;
$$ LANGUAGE plpgsql STABLE;
```

### 5.3 PostgreSQL Row-Level Security (RLS) Implementation
To transparently enforce security so that users can *only* query projects and activities they have permission to see:

```sql
-- Enable RLS on the project table
ALTER TABLE project ENABLE ROW LEVEL SECURITY;

-- Create policy leveraging JWT session variable for user identity
CREATE POLICY p_project_access_control ON project
FOR SELECT
USING (
    EXISTS (
        SELECT 1 FROM app_user u WHERE u.user_id = NULLIF(current_setting('app.current_user_id', true), '')::UUID AND u.is_super_admin = TRUE
    )
    OR
    EXISTS (
        SELECT 1
        FROM user_obs_grant g
        JOIN obs_node granted_obs ON granted_obs.obs_id = g.obs_id
        JOIN obs_node project_obs ON project_obs.obs_id = project.obs_id
        JOIN project_security_profile psp ON psp.profile_id = g.profile_id
        WHERE g.user_id = NULLIF(current_setting('app.current_user_id', true), '')::UUID
          AND granted_obs.obs_path @> project_obs.obs_path
          AND psp.can_view_project = TRUE
    )
);
```

## 6. Production Golang Authorization Engine

In high-concurrency Go web servers powering Next.js applications, running a database function on every single HTTP API call introduces unacceptable latency. Instead, permissions must be evaluated via an in-memory authorization engine with microsecond latency, backed by thread-safe caching and Pub/Sub invalidation.

```go
package security

import (
	"context"
	"errors"
	"fmt"
	"strings"
	"sync"
	"time"
)

// PermissionAction represents a discrete securable action in the scheduling engine.
type PermissionAction string

const (
	ActionViewProject        PermissionAction = "can_view_project"
	ActionEditProject        PermissionAction = "can_edit_project_details"
	ActionAddDeleteActivity  PermissionAction = "can_add_delete_activities"
	ActionEditActivityDates  PermissionAction = "can_edit_activity_dates"
	ActionUpdateProgress     PermissionAction = "can_edit_activity_progress"
	ActionExecuteScheduling  PermissionAction = "can_execute_scheduling"
	ActionCreateBaseline     PermissionAction = "can_create_baseline"
	ActionRestoreBaseline    PermissionAction = "can_restore_baseline"
	ActionViewCosts          PermissionAction = "can_view_costs"
	ActionEditCosts          PermissionAction = "can_edit_costs"
	ActionEditUDFs           PermissionAction = "can_edit_udfs"
)

// SecurityProfile encapsulates fine-grained permission flags.
type SecurityProfile struct {
	ID          string                     `json:"id"`
	Name        string                     `json:"name"`
	Permissions map[PermissionAction]bool  `json:"permissions"`
}

// OBSNode represents a node in the organizational tree.
type OBSNode struct {
	ID       string     `json:"id"`
	Code     string     `json:"code"`
	Path     string     `json:"path"` // e.g. "MD.VP_SOLAR.PM_RAJ"
	ParentID string     `json:"parent_id,omitempty"`
	Children []*OBSNode `json:"children,omitempty"`
}

// UserGrant represents an explicit assignment in the security matrix.
type UserGrant struct {
	UserID    string
	OBSID     string
	OBSPath   string
	ProfileID string
	Profile   *SecurityProfile
}

// AuthEngine provides sub-millisecond RBAC evaluation across the enterprise tree.
type AuthEngine struct {
	mu           sync.RWMutex
	obsMap       map[string]*OBSNode
	profileMap   map[string]*SecurityProfile
	userGrants   map[string][]UserGrant // key: UserID
	superAdmins  map[string]bool
}

// NewAuthEngine initializes the memory-backed authorization engine.
func NewAuthEngine() *AuthEngine {
	return &AuthEngine{
		obsMap:      make(map[string]*OBSNode),
		profileMap:  make(map[string]*SecurityProfile),
		userGrants:  make(map[string][]UserGrant),
		superAdmins: make(map[string]bool),
	}
}

// RegisterSuperAdmin flags a user as having unconditional bypass rights.
func (a *AuthEngine) RegisterSuperAdmin(userID string) {
	a.mu.Lock()
	defer a.mu.Unlock()
	a.superAdmins[userID] = true
}

// LoadConfiguration atomically loads OBS hierarchy, profiles, and user grants.
func (a *AuthEngine) LoadConfiguration(obsNodes []*OBSNode, profiles []*SecurityProfile, grants []UserGrant) {
	a.mu.Lock()
	defer a.mu.Unlock()

	a.obsMap = make(map[string]*OBSNode)
	for _, n := range obsNodes {
		a.obsMap[n.ID] = n
	}

	a.profileMap = make(map[string]*SecurityProfile)
	for _, p := range profiles {
		a.profileMap[p.ID] = p
	}

	a.userGrants = make(map[string][]UserGrant)
	for _, g := range grants {
		if profile, exists := a.profileMap[g.ProfileID]; exists {
			g.Profile = profile
			if node, ok := a.obsMap[g.OBSID]; ok {
				g.OBSPath = node.Path
			}
			a.userGrants[g.UserID] = append(a.userGrants[g.UserID], g)
		}
	}
}

// IsAncestorPath checks if ancestorPath is an ancestor or identical to targetPath.
// Uses dot-separated ltree semantics (e.g., "MD.VP_SOLAR" is ancestor of "MD.VP_SOLAR.PM_RAJ").
func IsAncestorPath(ancestorPath, targetPath string) bool {
	if ancestorPath == targetPath {
		return true
	}
	prefix := ancestorPath + "."
	return strings.HasPrefix(targetPath, prefix)
}

// CanUserPerformAction evaluates the security matrix in O(K) where K is number of grants assigned to user.
func (a *AuthEngine) CanUserPerformAction(userID string, projectOBSID string, action PermissionAction) (bool, error) {
	a.mu.RLock()
	defer a.mu.RUnlock()

	// 1. Super Admin check: Instant permit
	if a.superAdmins[userID] {
		return true, nil
	}

	// 2. Resolve Project's Responsible Manager OBS
	projectOBS, exists := a.obsMap[projectOBSID]
	if !exists {
		return false, fmt.Errorf("project responsible manager OBS %s not found", projectOBSID)
	}

	// 3. Retrieve User's assigned grants
	grants, found := a.userGrants[userID]
	if !found || len(grants) == 0 {
		return false, nil // No permissions assigned
	}

	// 4. Evaluate cascading inheritance: does any grant cover this OBS node or its ancestors?
	for _, grant := range grants {
		if grant.Profile == nil {
			continue
		}

		// Check if the grant is at or above the project's OBS node in the hierarchy
		if IsAncestorPath(grant.OBSPath, projectOBS.Path) {
			if allowed := grant.Profile.Permissions[action]; allowed {
				return true, nil // Short-circuit permit
			}
		}
	}

	return false, nil
}

// EnforcePermission returns an error if permission is denied, suitable for API middleware.
func (a *AuthEngine) EnforcePermission(ctx context.Context, userID, projectOBSID string, action PermissionAction) error {
	allowed, err := a.CanUserPerformAction(userID, projectOBSID, action)
	if err != nil {
		return err
	}
	if !allowed {
		return errors.New("access denied: insufficient enterprise project permissions")
	}
	return nil
}
```

## 7. Real-World Engineering Pitfalls & Anti-Patterns

### 7.1 Pitfall 1: Root OBS Privilege Escalation
* **The Anti-Pattern:** A new junior scheduler joins the company and is assigned the `Managing Director (Root)` OBS node because "they need to view all projects."
* **Why it Breaks Systems:** The user accidentally receives rights to edit baselines, modify project preferences, and delete activities across every project in the enterprise.
* **The Architectural Rule:** Create explicit **Read-Only / Executive Viewer** project security profiles. Never assign high-privilege profiles at the root OBS node unless the user is an enterprise administrator.

### 7.2 Pitfall 2: The "Inheritance Shadowing" Paradox
* **The Anti-Pattern:** A user has a restricted profile at a parent OBS node, but is granted full Project Manager rights at a child OBS node. A naïve authorization engine checks the first match and denies access.
* **Why it Breaks Systems:** The user is blocked from managing their own assigned project because an ancestor grant shadowed their specific project-level grant.
* **The Architectural Rule:** Security matrices in P6 evaluate permissions **additively across all matching grants** (Union of Permissions). If any valid grant covering the target project permits the action, access is granted.

### 7.3 Pitfall 3: Unindexed Recursive Permission Checks in API Handlers
* **The Anti-Pattern:** The frontend makes a request: `GET /api/v1/activities?project_id=XYZ`. The backend executes a recursive CTE querying the entire OBS tree to verify permissions on every single activity row.
* **Why it Breaks Systems:** Database CPU spikes to 100%, and query latency jumps from 15ms to 2,500ms when fetching 5,000 activities.
* **The Architectural Rule:** **Check permissions at the Project Boundary once per request**, not on every individual activity record. Once project access is validated in middleware, activities within that project inherit the validated permission scope.
