## 🧠 Section A: Conceptual & Architectural Principles

### Solution 1: EPS vs. WBS Structural Invariants

#### 1. Three Fundamental Architectural Differences
Merging `eps_node` and `wbs_node` into a single polymorphic `hierarchy_node` table violates several fundamental database and domain design invariants:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                            EPS vs. WBS DATABASE DESIGN COMPARISON                                │
├───────────────────────┬──────────────────────────────────┬───────────────────────────────────────┤
│ Dimension             │ Enterprise Project Structure     │ Work Breakdown Structure              │
├───────────────────────┼──────────────────────────────────┼───────────────────────────────────────┤
│ Scope & Cardinality   │ Multi-project, enterprise-wide.  │ Strictly scoped to 1 Project entity.  │
│ Leaf Entity Type      │ Leaf children are `project` rows.│ Leaf children are `activity` rows.    │
│ Security Coupling     │ Binds to OBS for RBAC policies.  │ Inherits permissions from Project/EPS.│
│ Lifecycle & Versioning│ Permanent corporate taxonomy.    │ Baseline-versioned per project run.   │
└───────────────────────┴──────────────────────────────────┴───────────────────────────────────────┘
```

1. **Entity Relationships & Cardinality:** An EPS node contains other EPS nodes or `project` records. A WBS node exists strictly *inside* a single project and contains other WBS nodes or `activity` records. Merging them creates polymorphic foreign keys (`child_type = 'PROJECT' | 'ACTIVITY' | 'NODE'`), disabling relational foreign key constraints and referential integrity.
2. **Access Control & Domain Boundaries:** Security matrices (OBS mapping) attach directly to EPS nodes to govern portfolio visibility. WBS elements inherit security from their parent project. Unifying them complicates Row-Level Security (RLS) queries, as every activity query would have to distinguish whether an ancestor node is an enterprise container or a project deliverable.
3. **Baselining & Versioning Lifecycles:** When a project baseline is created (e.g., Baseline B01), the entire WBS tree of that project is cloned into a historical snapshot table (`project_baseline_wbs`). EPS nodes are never baselined—they represent the permanent corporate organization. Merging them would force baselining logic to handle partial trees and recursive branch exclusions.

#### 2. CPM Logic and Date Rollup Mechanics
* **WBS Nodes participate directly in schedule execution:** A WBS node summarizes the activities below it. Its Early Start is the minimum Early Start of its children; its Early Finish is the maximum Early Finish of its children. Furthermore, WBS milestones (Start/Finish milestones) directly participate in CPM topological sorting and forward/backward passes.
* **EPS Nodes do not participate in CPM runs:** An EPS node cannot have a predecessor or successor relationship with another EPS node. Projects inside an EPS branch may run on completely different calendars, different Data Dates, and independent status periods. CPM calculations are strictly scoped to the topological network of activities within projects.

#### 3. Security Assignment Differences
* **EPS Security:** Mapped explicitly via the **OBS-EPS Matrix**. A user assigned to an EPS node with a "Project Manager" profile inherits rights to view and manage all current and future projects provisioned under that EPS branch.
* **WBS Security:** WBS nodes do not have independent OBS mappings in standard P6 architecture; permissions are inherited uniformly from the parent Project entity.

### Solution 2: Tree Storage Pattern Trade-offs in PostgreSQL

#### 1. Pattern Comparison Matrix

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                        EVALUATION OF TREE STORAGE ARCHITECTURES                                  │
├───────────────────┬─────────────────┬──────────────────┬─────────────────┬───────────────────────┤
│ Pattern           │ Read Subtree    │ Insert Leaf      │ Reparent Branch │ Storage & Indexing    │
├───────────────────┼─────────────────┼──────────────────┼─────────────────┼───────────────────────┤
│ Adjacency List    │ O(Depth) via CTE│ O(1) Instant     │ O(1) Instant    │ Minimal (parent_id)   │
│ Nested Sets       │ O(1) Fast range │ O(N) Rewrites    │ O(N) Rewrites   │ Heavy write lock contention│
│ PostgreSQL ltree  │ O(log N) GiST   │ O(1) Fast        │ O(Subtree) Fast │ Compact GiST index    │
│ Closure Table     │ O(1) Fast join  │ O(Depth) Fast    │ O(Subtree × D)  │ High row multiplication│
└───────────────────┴─────────────────┴──────────────────┴─────────────────┴───────────────────────┘
```

* **Adjacency List:** Requires recursive Common Table Expressions (`WITH RECURSIVE`). For depth 5 across 50,000 projects, recursive query latency climbs to 15–35ms under concurrency.
* **Nested Sets:** Reading a branch is a fast range query (`WHERE lft BETWEEN parent.lft AND parent.rgt`). However, inserting or reparenting requires updating every `lft` and `rgt` integer across the entire table, taking exclusive table locks and paralyzing concurrent project creation.
* **PostgreSQL `ltree`:** Encodes the hierarchy as a materialized path (`SURYA.SOLAR.NORTH.PRJ_100`). Subtree lookup uses GiST indexes and runs in under 1ms. Reparenting requires updating only the descendant paths via string prefix replacement.
* **Closure Table:** Stores every ancestor-descendant pair. Provides ultra-fast $O(1)$ joins for permissions, but introduces $O(\text{Depth} \times N)$ storage growth.

#### 2. PostgreSQL GiST Index Mechanics on `ltree`
The query:
```sql
SELECT * FROM project WHERE eps_path <@ 'SURYA.SOLAR.NORTH';
```
uses the GiST (Generalized Search Tree) index on the `ltree` column. GiST indexes `ltree` paths using signature bitmasks representing path prefixes. When evaluating the `<@` (is-descendant-of) operator:
1. The query planner skips scanning individual rows and traverses the balanced GiST index tree.
2. It prunes entire index pages whose path signatures do not match the prefix `SURYA.SOLAR.NORTH`.
3. It resolves the matching project IDs in logarithmic time ($O(\log N)$), converting an expensive full-table scan of 50,000 projects into a sub-millisecond index lookup.

#### 3. Justification for Hybrid `ltree` + Closure Table Architecture
A hybrid approach is justified when building enterprise authorization matrices (OBS-EPS security). 
* Use **`ltree`** for frontend folder navigation, path displays, and hierarchical project rollups.
* Use a **Closure Table (`eps_closure`)** to compute user permissions via inner joins in Row-Level Security (RLS) policies. Joins against integer/UUID foreign keys in a closure table are faster for the SQL query planner than evaluating dynamic string regexes or path expressions inside high-throughput RLS filters.

### Solution 3: Enterprise Default Inheritance & Override Lifecycle

#### 1. Static vs. Dynamic Inheritance
* **Static Inheritance (Snapshot Copy):**
  - **Mechanics:** When a project is created, properties from the parent EPS node (e.g., `default_calendar_id`, `currency_code`, `activity_id_prefix`) are copied directly into the project's own database columns.
  - **Applied To:** Calendars, Activity ID autonumbering, and financial settings. Projects need immutable, autonomous configurations that do not alter unexpectedly when enterprise defaults are modified.
* **Dynamic Inheritance (Cascading Lookup):**
  - **Mechanics:** The project stores a `NULL` value for a configuration field. At runtime, the application queries up the EPS tree until it encounters the first non-null setting.
  - **Applied To:** Corporate fiscal year boundaries, global currency exchange rate tables, and security policy rules.

#### 2. Behavioral Impact of Modifying Parent EPS Calendar
If an administrator changes the default calendar at `SOLAR-NORTH` from a 5-day to a 6-day workweek:
1. **Existing Active Projects:** Must **not** change automatically. Active projects have already committed baseline schedules, subcontractor commitments, and CPM dates based on their assigned calendar. Modifying their calendar would cause unapproved date shifts, distorting contractual Float and Earned Value metrics.
2. **Future Projects:** New projects created under `SOLAR-NORTH` will inherit the new 6-day calendar default.

#### 3. Preventing Inheritance Cache Stampedes
To prevent cascading recalculation storms:
* Decouple administrative defaults from active project calculation engines.
* Enforce explicit user-driven re-baselining: If an enterprise calendar is updated, the system marks affected projects with a notification flag (`calendar_update_available`), requiring the Project Manager to review impact analysis before manually applying changes.

### Solution 4: Multi-Tiered Portfolio Aggregation Semantics

#### 1. Handling Project Lifecycle States in Rollups
* **`ACTIVE`:** Included in all operational, financial, and earned value portfolio metrics ($BAC$, $PV$, $EV$, $AC$).
* **`PLANNED`:** Included in portfolio capital expenditure forecasts and resource capacity planning, but excluded from Earned Value calculations ($EV=0$, $AC=0$) because physical execution has not started.
* **`WHAT_IF`:** Strictly excluded from official enterprise rollups. Kept in isolated sandboxes for scenario modeling.
* **`ARCHIVED` / `INACTIVE`:** Preserved for historical financial accounting, but excluded from real-time operational schedule health and active variance tracking.

#### 2. Multi-Currency Normalization
If Project A is in INR and Project B is in USD:
1. Define a corporate base reporting currency at the root EPS node (e.g., INR).
2. Maintain an enterprise exchange rate table with effective date ranges.
3. Convert all project financial values ($BAC_i$, $PV_i$, $EV_i$, $AC_i$) to the base corporate currency at the active Data Date exchange rate before performing portfolio-level summation:
   $$\text{Portfolio } EV = \sum \left( EV_i \times \text{ExchangeRate}(i \to \text{Base}) \right)$$
   $$\text{Portfolio } AC = \sum \left( AC_i \times \text{ExchangeRate}(i \to \text{Base}) \right)$$
4. Compute the portfolio $CPI$ exclusively using normalized values:
   $$\text{Portfolio } CPI = \frac{\text{Normalized } EV}{\text{Normalized } AC}$$

#### 3. Why Total Float Cannot Be Summed or Averaged
**Total Float is not an additive metric.** 
* Summing float ($\sum TF$) is mathematically meaningless. If Project 1 has $+40$ days float and Project 2 has $-40$ days float, summing them yields $0$, hiding a severe schedule delay.
* Averaging float hides critical path risks: a project delayed by 180 days would be masked by ten small projects with 20 days of positive float.
* **Correct Portfolio Schedule Risk Representation:**
  1. **Minimum Float (Worst Float):** Report the minimum Total Float across all active projects within the EPS node ($\min(TF)$).
  2. **Critical Project Ratio:** Track the percentage of projects within the portfolio having $TF \le 0$.
  3. **Milestone Slip Variance:** Measure milestone slip on key contractual interface dates.

### Solution 5: PostgreSQL Schema & ltree Maintenance Triggers

#### 1. PostgreSQL DDL for `eps_node`

```sql
CREATE EXTENSION IF NOT EXISTS ltree;

CREATE TABLE eps_node (
    eps_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    eps_code VARCHAR(32) NOT NULL UNIQUE,
    eps_name VARCHAR(255) NOT NULL,
    parent_eps_id UUID REFERENCES eps_node(eps_id) ON DELETE RESTRICT,
    node_path ltree NOT NULL,
    obs_id UUID NOT NULL REFERENCES obs_node(obs_id) ON DELETE RESTRICT,
    
    default_calendar_id UUID,
    default_currency_code VARCHAR(3) NOT NULL DEFAULT 'INR',
    activity_id_prefix VARCHAR(10) NOT NULL DEFAULT 'ACT-',
    activity_id_suffix INT NOT NULL DEFAULT 1000,
    activity_id_increment INT NOT NULL DEFAULT 10,
    
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

CREATE INDEX idx_eps_path_gist ON eps_node USING GIST (node_path);
CREATE INDEX idx_eps_parent_id ON eps_node(parent_eps_id);
```

#### 2. Trigger Function for Automatic Path Generation on INSERT
```sql
CREATE OR REPLACE FUNCTION trg_fn_maintain_eps_path_insert()
RETURNS TRIGGER AS $$
DECLARE
    parent_path ltree;
    clean_code text;
BEGIN
    -- Replace hyphens and illegal characters with underscores for valid ltree labels
    clean_code := regexp_replace(NEW.eps_code, '[^a-zA-Z0-9_]', '_', 'g');

    IF NEW.parent_eps_id IS NULL THEN
        NEW.node_path := text2ltree(clean_code);
    ELSE
        SELECT node_path INTO parent_path FROM eps_node WHERE eps_id = NEW.parent_eps_id;
        IF parent_path IS NULL THEN
            RAISE EXCEPTION 'Parent EPS node ID % does not exist', NEW.parent_eps_id;
        END IF;
        NEW.node_path := parent_path || text2ltree(clean_code);
    END IF;

    NEW.updated_at := clock_timestamp();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_eps_path_insert
BEFORE INSERT ON eps_node
FOR EACH ROW EXECUTE FUNCTION trg_fn_maintain_eps_path_insert();
```

#### 3. UPDATE Trigger for Reparenting and Descendant Path Cascading
```sql
CREATE OR REPLACE FUNCTION trg_fn_maintain_eps_path_update()
RETURNS TRIGGER AS $$
DECLARE
    old_path ltree;
    new_path ltree;
    parent_path ltree;
    clean_code text;
BEGIN
    -- Check if either parent or code changed
    IF (OLD.parent_eps_id IS DISTINCT FROM NEW.parent_eps_id) OR (OLD.eps_code <> NEW.eps_code) THEN
        clean_code := regexp_replace(NEW.eps_code, '[^a-zA-Z0-9_]', '_', 'g');
        
        IF NEW.parent_eps_id IS NULL THEN
            new_path := text2ltree(clean_code);
        ELSE
            SELECT node_path INTO parent_path FROM eps_node WHERE eps_id = NEW.parent_eps_id;
            IF parent_path IS NULL THEN
                RAISE EXCEPTION 'Parent EPS node ID % does not exist', NEW.parent_eps_id;
            END IF;
            -- Prevent circular parent assignment
            IF parent_path <@ OLD.node_path THEN
                RAISE EXCEPTION 'Cannot reparent node % under its own descendant %', NEW.eps_code, parent_path;
            END IF;
            new_path := parent_path || text2ltree(clean_code);
        END IF;

        old_path := OLD.node_path;
        NEW.node_path := new_path;
        NEW.updated_at := clock_timestamp();

        -- Cascade new path to all descendant EPS nodes
        UPDATE eps_node
        SET node_path = new_path || subpath(node_path, nlevel(old_path)),
            updated_at = clock_timestamp()
        WHERE node_path <@ old_path AND eps_id <> NEW.eps_id;
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_eps_path_update
BEFORE UPDATE OF eps_code, parent_eps_id ON eps_node
FOR EACH ROW EXECUTE FUNCTION trg_fn_maintain_eps_path_update();
```

### Solution 6: Hierarchical Portfolio EVM Rollup Query

```sql
WITH target_scope AS (
    SELECT eps_id, eps_code, eps_name, node_path
    FROM eps_node
    WHERE eps_code = 'SURYA-SOLAR'
),
descendants AS (
    SELECT 
        ts.eps_code AS root_scope_code,
        ts.eps_name AS root_scope_name,
        p.project_id,
        p.budget_at_completion,
        p.planned_value,
        p.earned_value,
        p.actual_cost
    FROM target_scope ts
    JOIN eps_node e ON e.node_path <@ ts.node_path
    JOIN project p ON p.eps_id = e.eps_id
    WHERE p.status = 'ACTIVE'
)
SELECT 
    d.root_scope_code AS eps_code,
    d.root_scope_name AS eps_name,
    COUNT(d.project_id) AS active_project_count,
    COALESCE(SUM(d.budget_at_completion), 0.00) AS total_bac,
    COALESCE(SUM(d.planned_value), 0.00) AS total_pv,
    COALESCE(SUM(d.earned_value), 0.00) AS total_ev,
    COALESCE(SUM(d.actual_cost), 0.00) AS total_ac,
    COALESCE(SUM(d.earned_value) - SUM(d.actual_cost), 0.00) AS cost_variance,
    COALESCE(SUM(d.earned_value) - SUM(d.planned_value), 0.00) AS schedule_variance,
    CASE 
        WHEN SUM(d.actual_cost) > 0 THEN ROUND(SUM(d.earned_value) / SUM(d.actual_cost), 3)
        ELSE 1.000 
    END AS portfolio_cpi,
    CASE 
        WHEN SUM(d.planned_value) > 0 THEN ROUND(SUM(d.earned_value) / SUM(d.planned_value), 3)
        ELSE 1.000 
    END AS portfolio_spi
FROM descendants d
GROUP BY d.root_scope_code, d.root_scope_name;
```

### Solution 7: Preventing Cycle Formation & Integrity Protection

#### 1. Cycle Prevention via Database Check
As implemented in the `trg_fn_maintain_eps_path_update` trigger:
```sql
IF parent_path <@ OLD.node_path THEN
    RAISE EXCEPTION 'Cannot reparent node % under its own descendant %', NEW.eps_code, parent_path;
END IF;
```
Because the `node_path` encodes the full lineage, checking if the intended new parent's path is a descendant (`parent_path <@ OLD.node_path`) detects circular references instantly before the database write occurs.

#### 2. Integrity Protection & `ON DELETE RESTRICT`
* **Why `ON DELETE RESTRICT` is mandatory:** If an EPS node used `ON DELETE CASCADE`, deleting a top-level node (e.g., `SURYA-SOLAR`) would recursively delete all child projects, their baselines, and contractual audit records.
* **Decommissioning Protocol:**
  1. Verify all projects in the branch are marked `ARCHIVED` or `INACTIVE`.
  2. Reparent active projects to an active branch or archive container (`ARCHIVE-EPS`).
  3. Mark the EPS node `is_active = FALSE`.
  4. Only if the node has zero child projects and zero child EPS nodes can a physical deletion be executed by a Super Administrator.

### Solution 8: In-Memory Tree Construction & Cycle Detection

```go
package eps

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

type Project struct {
	ID                 string    `json:"id"`
	Code               string    `json:"code"`
	Name               string    `json:"name"`
	EPSID              string    `json:"eps_id"`
	Status             string    `json:"status"`
	BudgetAtCompletion float64   `json:"budget_at_completion"`
	PlannedValue       float64   `json:"planned_value"`
	EarnedValue        float64   `json:"earned_value"`
	ActualCost         float64   `json:"actual_cost"`
}

type EPSNode struct {
	ID                string            `json:"id"`
	Code              string            `json:"code"`
	Name              string            `json:"name"`
	ParentID          string            `json:"parent_id,omitempty"`
	NodePath          string            `json:"node_path"`
	Children          []*EPSNode        `json:"children"`
	Projects          []*Project        `json:"projects"`
	AggregatedMetrics PortfolioMetrics  `json:"aggregated_metrics"`
	mu                sync.RWMutex
}

type TreeBuilder struct {
	nodes map[string]*EPSNode
	roots []*EPSNode
}

func NewTreeBuilder() *TreeBuilder {
	return &TreeBuilder{
		nodes: make(map[string]*EPSNode),
		roots: make([]*EPSNode, 0),
	}
}

func (tb *TreeBuilder) BuildTree(flatNodes []*EPSNode, projects []*Project) ([]*EPSNode, error) {
	// Step 1: Index nodes
	for _, n := range flatNodes {
		n.Children = make([]*EPSNode, 0)
		n.Projects = make([]*Project, 0)
		tb.nodes[n.ID] = n
	}

	// Step 2: Establish hierarchy
	for _, n := range flatNodes {
		if n.ParentID == "" {
			tb.roots = append(tb.roots, n)
		} else {
			parent, exists := tb.nodes[n.ParentID]
			if !exists {
				return nil, fmt.Errorf("node %s references non-existent parent %s", n.Code, n.ParentID)
			}
			parent.Children = append(parent.Children, n)
		}
	}

	// Step 3: Attach projects
	for _, p := range projects {
		node, exists := tb.nodes[p.EPSID]
		if !exists {
			return nil, fmt.Errorf("project %s references non-existent EPS node %s", p.Code, p.EPSID)
		}
		node.Projects = append(node.Projects, p)
	}

	// Step 4: Validate Acyclic Graph via DFS
	visited := make(map[string]bool)
	recStack := make(map[string]bool)

	for _, root := range tb.roots {
		if err := tb.detectCycleDFS(root, visited, recStack); err != nil {
			return nil, err
		}
	}

	return tb.roots, nil
}

func (tb *TreeBuilder) detectCycleDFS(curr *EPSNode, visited, recStack map[string]bool) error {
	visited[curr.ID] = true
	recStack[curr.ID] = true

	for _, child := range curr.Children {
		if !visited[child.ID] {
			if err := tb.detectCycleDFS(child, visited, recStack); err != nil {
				return err
			}
		} else if recStack[child.ID] {
			return fmt.Errorf("cycle detected: node %s (%s) is an ancestor of itself", child.Code, child.ID)
		}
	}

	recStack[curr.ID] = false
	return nil
}
```

### Solution 9: Concurrent Post-Order Metric Rollup Engine

```go
package eps

import (
	"sync"
)

type PortfolioMetrics struct {
	TotalProjects    int     `json:"total_projects"`
	ActiveProjects   int     `json:"active_projects"`
	TotalBAC         float64 `json:"total_bac"`
	TotalPV          float64 `json:"total_pv"`
	TotalEV          float64 `json:"total_ev"`
	TotalAC          float64 `json:"total_ac"`
	CostVariance     float64 `json:"cost_variance"`
	ScheduleVariance float64 `json:"schedule_variance"`
	CPI              float64 `json:"cpi"`
	SPI              float64 `json:"spi"`
}

// RollupSubtree performs concurrent post-order traversal to calculate metrics bottom-up.
func RollupSubtree(node *EPSNode) PortfolioMetrics {
	var metrics PortfolioMetrics

	// Step 1: Accumulate directly assigned projects
	for _, p := range node.Projects {
		metrics.TotalProjects++
		if p.Status == "ACTIVE" {
			metrics.ActiveProjects++
			metrics.TotalBAC += p.BudgetAtCompletion
			metrics.TotalPV += p.PlannedValue
			metrics.TotalEV += p.EarnedValue
			metrics.TotalAC += p.ActualCost
		}
	}

	// Step 2: Recursively aggregate child EPS nodes concurrently
	if len(node.Children) > 0 {
		var wg sync.WaitGroup
		childMetrics := make([]PortfolioMetrics, len(node.Children))

		for i, child := range node.Children {
			wg.Add(1)
			go func(idx int, target *EPSNode) {
				defer wg.Done()
				childMetrics[idx] = RollupSubtree(target)
			}(i, child)
		}
		wg.Wait()

		for _, cm := range childMetrics {
			metrics.TotalProjects += cm.TotalProjects
			metrics.ActiveProjects += cm.ActiveProjects
			metrics.TotalBAC += cm.TotalBAC
			metrics.TotalPV += cm.TotalPV
			metrics.TotalEV += cm.TotalEV
			metrics.TotalAC += cm.TotalAC
		}
	}

	// Step 3: Compute derived performance indicators
	metrics.CostVariance = metrics.TotalEV - metrics.TotalAC
	metrics.ScheduleVariance = metrics.TotalEV - metrics.TotalPV

	if metrics.TotalAC > 0 {
		metrics.CPI = metrics.TotalEV / metrics.TotalAC
	} else {
		metrics.CPI = 1.000
	}

	if metrics.TotalPV > 0 {
		metrics.SPI = metrics.TotalEV / metrics.TotalPV
	} else {
		metrics.SPI = 1.000
	}

	node.mu.Lock()
	node.AggregatedMetrics = metrics
	node.mu.Unlock()

	return metrics
}
```

### Solution 10: Real-World Incident — The Reparenting Cache Outage

#### 1. Root Cause Analysis
1. **Next.js Dashboard Showing Old Hierarchy (50% Split):**
   - The frontend reads from both Redis-cached tree payloads and direct read-replica SQL queries. When the branch reparenting occurred, the database write succeeded, but the Redis cache key `eps_tree_root` was not purged. Furthermore, client browser WebSocket connections were not notified of the hierarchical mutation.
2. **Background Jobs Failing with Foreign Key Violations:**
   - Background jobs were running concurrent project inserts pointing to old, cached EPS paths that were mid-mutation or locked by table triggers.
3. **Redis Memory Spike to 100%:**
   - Naïve cache invalidation triggered an uncontrolled loop where every concurrent user request that missed cache began re-querying and caching 50,000 projects under separate user-scoped keys, exhausting Redis memory.

#### 2. Robust Reparenting & Invalidation Architecture

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                   TRANSACTIONAL REPARENTING & CACHE INVALIDATION WORKFLOW                        │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  1. Client Requests Move Branch(SourceEPS, TargetEPS)                                            │
│     │                                                                                            │
│  2. Acquire Distributed Redis Mutex: Lock("eps_mutation_lock", TTL=10s)                          │
│     │                                                                                            │
│  3. Begin PostgreSQL Transaction (SERIALIZABLE):                                                 │
│     ├── Validate target is not a descendant of source                                            │
│     ├── Execute UPDATE eps_node SET parent_eps_id = TargetID WHERE eps_id = SourceID             │
│     ├── Path triggers update all descendant ltree paths atomically                               │
│     └── COMMIT Transaction                                                                       │
│                                                                                                  │
│  4. Atomic Cache Eviction:                                                                       │
│     ├── Invalidate root cache keys: DEL eps_tree:*                                               │
│     └── Publish Redis Pub/Sub Event: PUBLISH eps_events '{"event":"TREE_MUTATED"}'               │
│                                                                                                  │
│  5. Release Distributed Lock                                                                     │
│                                                                                                  │
│  6. Next.js WebSocket Gateway broadcasts 'TREE_REFRESH' to all connected clients                 │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### Go Implementation:
```go
package eps

import (
	"context"
	"database/sql"
	"encoding/json"
	"fmt"
	"time"

	"github.com/go-redis/redis/v8"
)

type HierarchyService struct {
	db    *sql.DB
	rdb   *redis.Client
}

func (s *HierarchyService) ReparentBranch(ctx context.Context, sourceID, targetID string) error {
	// Step 1: Distributed Lock to prevent concurrent mutations
	lockKey := "lock:eps_mutation"
	acquired, err := s.rdb.SetNX(ctx, lockKey, "locked", 10*time.Second).Result()
	if err != nil || !acquired {
		return fmt.Errorf("another hierarchy mutation is in progress: %w", err)
	}
	defer s.rdb.Del(ctx, lockKey)

	// Step 2: Transactional database update
	tx, err := s.db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelSerializable})
	if err != nil {
		return err
	}
	defer tx.Rollback()

	query := `UPDATE eps_node SET parent_eps_id = $1 WHERE eps_id = $2;`
	if _, err := tx.ExecContext(ctx, query, targetID, sourceID); err != nil {
		return fmt.Errorf("failed to reparent EPS node in postgres: %w", err)
	}

	if err := tx.Commit(); err != nil {
		return fmt.Errorf("transaction commit failed: %w", err)
	}

	// Step 3: Atomic cache invalidation using pattern scan
	iter := s.rdb.Scan(ctx, 0, "eps_tree:*", 0).Iterator()
	for iter.Next(ctx) {
		s.rdb.Del(ctx, iter.Val())
	}
	if err := iter.Err(); err != nil {
		return fmt.Errorf("redis cache purge error: %w", err)
	}

	// Step 4: Broadcast real-time refresh message to Next.js clients via Redis PubSub
	payload, _ := json.Marshal(map[string]string{
		"event":    "EPS_TREE_MUTATED",
		"sourceId": sourceID,
		"targetId": targetID,
	})
	s.rdb.Publish(ctx, "eps_updates_channel", payload)

	return nil
}
```
