# Topic 9.5: Multi-Project Scheduling & Cross-Project Relationships

## 1. Executive Summary & Plain-English Analogy

### 1.1 The Interlocking Gear Trains Analogy
Imagine two massive industrial factories located five miles apart. Factory A manufactures high-speed electric trains, while Factory B manufactures heavy-duty lithium traction batteries.
* Each factory operates independently: its own factory manager, its own assembly line, its own daily shift workers, and its own internal production schedule.
* However, on Day 120, Factory A's assembly line reaches the step: *"Install Traction Battery Pack."* Factory A cannot proceed until Factory B delivers the finished battery!
* If Factory B suffers a 30-day delay in lithium cell procurement, Factory A's entire train assembly line halts, even though Factory A's internal workers did everything perfectly on time.

In software engineering terms:
* A single project's CPM schedule is a **Local Directed Acyclic Graph (DAG)**.
* Multi-project scheduling is **Global Graph Unification**: stitching multiple independent sub-graphs together via **Cross-Project Interface Edges** into a single unified enterprise DAG.
* If an engineer does not understand multi-project DAG unification, cross-project dependencies will create hidden circular loops, corrupt critical path floats, and paralyze multi-million-dollar infrastructure investments.

A **Cross-Project Relationship** occurs when an activity in Project A is linked to an activity in Project B.

#### What Happens When Only One Project is Open?
1. **If Project A is opened alone:** P6 preserves the external link. It reads the cached Early Finish date of `B2040` from the database and uses it as the Early Start constraint for `A1040`.
2. **If Project B is updated and scheduled alone:** If `B2040` slips by 45 days, Project B recalculates its dates. However, Project A will not reflect this slip until Project A is re-opened and scheduled (`F9`), or until both projects are scheduled together in a **Unified Multi-Project Run**.

### 3.1 Data Date Synchronization Dilemma
When scheduling multiple projects simultaneously, how should the scheduling engine handle mismatched Data Dates?

### 3.2 Total Float Propagation Across Enterprise Boundaries
The most powerful (and dangerous) characteristic of multi-project scheduling is **Total Float Propagation**:
* If `B2040` (Substation Energization) is delayed, its late dates compress.
* The backward pass starts at the contractual delivery milestone of Project A and flows backward across the cross-project relationship into Project B!
* If Project A has a mandatory completion deadline of 31-Dec-2026, a delay in Project B will cause Project B's activities to exhibit **Negative Float driven by Project A's contractual finish date**!

## 4. Graph Theory & The Cross-Project Cycle Hazard

### 4.1 The Circular Dependency Catastrophe
In single-project scheduling, schedulers rarely create circular dependencies because the entire CPM network is visible. 
In multi-project scheduling across different organizational divisions, circular dependencies occur with alarming frequency:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                              THE CROSS-PROJECT CIRCULAR LOOP DISASTER                            │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│       [PROJECT A: Solar Farm]                           [PROJECT B: Grid Substation]             │
│       ┌──────────────────────┐                          ┌──────────────────────┐                 │
│       │ Act A1020: Piling    │                          │ Act B2010: Earthwork │                 │
│       └──────────┬───────────┘                          └──────────┬───────────┘                 │
│                  │                                                 │                             │
│                  ▼                                                 ▼                             │
│       ┌──────────────────────┐    CROSS-PROJECT LINK 1  ┌──────────────────────┐                 │
│       │ Act A1040: COD       │◄─────────────────────────┤ Act B2040: Energize  │                 │
│       └──────────┬───────────┘                          └──────────────────────┘                 │
│                  │                                                 ▲                             │
│                  │                CROSS-PROJECT LINK 2             │                             │
│                  └─────────────────────────────────────────────────┘                             │
│                     (Substation Engineer links B2040 Predecessor = Act A1040!)                   │
│                                                                                                  │
│   TOPOLOGICAL RESULT: A1040 depends on B2040, which depends on A1040!                            │
│   THE GRAPH IS NO LONGER A DAG. CPM ENGINE ENTERING AN INFINITE LOOP!                            │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

To prevent the scheduling engine from locking up or crashing, a production scheduling platform must execute **Cycle Detection** across the unified multi-project graph before running topological sorting.

### 4.2 Tarjan's Strongly Connected Components (SCC) Algorithm
The most efficient algorithm for detecting cycles in directed graphs is **Tarjan's Strongly Connected Components (SCC)** algorithm, running in linear time $O(V + E)$ where $V$ is total activities and $E$ is total dependencies.
* A graph is a Directed Acyclic Graph (DAG) **if and only if** every strongly connected component consists of a single isolated vertex.
* Any strongly connected component containing 2 or more vertices represents an **illegal circular dependency loop**!

## 5. Enterprise Database Architecture (PostgreSQL)

### 5.1 Cross-Project Relationship Schema

```sql
-- Unified Relationship Table Supporting Intra-Project and Cross-Project Edges
CREATE TABLE project_relationship (
    relationship_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- Predecessor Identification
    predecessor_project_id UUID NOT NULL REFERENCES project(project_id) ON DELETE CASCADE,
    predecessor_activity_id UUID NOT NULL REFERENCES activity(activity_id) ON DELETE CASCADE,
    
    -- Successor Identification
    successor_project_id UUID NOT NULL REFERENCES project(project_id) ON DELETE CASCADE,
    successor_activity_id UUID NOT NULL REFERENCES activity(activity_id) ON DELETE CASCADE,
    
    -- CPM Dependency Type & Lag
    dependency_type VARCHAR(2) NOT NULL DEFAULT 'FS'
        CHECK (dependency_type IN ('FS', 'SS', 'FF', 'SF')),
    lag_duration_hours INT NOT NULL DEFAULT 0,
    
    -- Cross-Project Classification Flag
    is_cross_project BOOLEAN GENERATED ALWAYS AS (predecessor_project_id <> successor_project_id) STORED,
    
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    
    -- Prevent Duplicate Edges Between Same Activities
    CONSTRAINT uq_activity_relationship UNIQUE (predecessor_activity_id, successor_activity_id),
    -- Prevent Self-Loops
    CONSTRAINT chk_no_self_relationship CHECK (predecessor_activity_id <> successor_activity_id)
);

CREATE INDEX idx_rel_predecessor_lookup ON project_relationship(predecessor_activity_id);
CREATE INDEX idx_rel_successor_lookup ON project_relationship(successor_activity_id);
CREATE INDEX idx_rel_cross_project ON project_relationship(is_cross_project) WHERE is_cross_project = TRUE;
CREATE INDEX idx_rel_projects_pair ON project_relationship(predecessor_project_id, successor_project_id);
```

### 5.2 Fast Multi-Project Graph Extraction Query
To extract the complete unified graph when a user opens multiple projects:

```sql
-- Extract all internal and boundary relationships for an open project set
WITH open_projects AS (
    SELECT UNNEST(ARRAY[
        'c4b8b6e2-7634-4a25-a1c2-3e2b20465590'::UUID, -- Surya 100MW Solar
        'e8f1b2c3-9821-4d76-b5e1-8f9a0c1d2e3f'::UUID  -- 220kV Grid Substation
    ]) AS project_id
)
SELECT 
    r.relationship_id,
    r.predecessor_project_id,
    p_pred.project_code AS pred_project_code,
    r.predecessor_activity_id,
    a_pred.activity_code AS pred_activity_code,
    r.successor_project_id,
    p_succ.project_code AS succ_project_code,
    r.successor_activity_id,
    a_succ.activity_code AS succ_activity_code,
    r.dependency_type,
    r.lag_duration_hours,
    r.is_cross_project
FROM project_relationship r
JOIN open_projects op1 ON op1.project_id = r.predecessor_project_id
JOIN open_projects op2 ON op2.project_id = r.successor_project_id
JOIN project p_pred ON p_pred.project_id = r.predecessor_project_id
JOIN project p_succ ON p_succ.project_id = r.successor_project_id
JOIN activity a_pred ON a_pred.activity_id = r.predecessor_activity_id
JOIN activity a_succ ON a_succ.activity_id = r.successor_activity_id;
```

## 6. Production Golang Multi-Project CPM & Cycle Detection Engine

Below is an enterprise-grade Golang engine that:
1. Unifies multiple projects into a single global directed graph.
2. Runs **Tarjan's Strongly Connected Components (SCC)** algorithm to verify that the multi-project graph is strictly acyclic ($O(V + E)$).
3. Executes a multi-project forward pass and backward pass to calculate Early Dates, Late Dates, and Total Float across project boundaries.

```go
package multiproject

import (
	"errors"
	"fmt"
	"math"
	"time"
)

type DependencyType string

const (
	TypeFS DependencyType = "FS"
	TypeSS DependencyType = "SS"
	TypeFF DependencyType = "FF"
	TypeSF DependencyType = "SF"
)

type ActivityNode struct {
	ID          string
	Code        string
	ProjectID   string
	Duration    int // in hours
	EarlyStart  time.Time
	EarlyFinish time.Time
	LateStart   time.Time
	LateFinish  time.Time
	TotalFloat  int // in hours
}

type Edge struct {
	PredecessorID string
	SuccessorID   string
	Type          DependencyType
	LagHours      int
	IsCrossProject bool
}

type MultiProjectGraph struct {
	Activities map[string]*ActivityNode
	Successors map[string][]Edge
	Predecessors map[string][]Edge
	DataDates   map[string]time.Time
}

func NewMultiProjectGraph() *MultiProjectGraph {
	return &MultiProjectGraph{
		Activities:   make(map[string]*ActivityNode),
		Successors:   make(map[string][]Edge),
		Predecessors: make(map[string][]Edge),
		DataDates:    make(map[string]time.Time),
	}
}

func (g *MultiProjectGraph) AddActivity(act *ActivityNode) {
	g.Activities[act.ID] = act
}

func (g *MultiProjectGraph) AddRelationship(edge Edge) {
	g.Successors[edge.PredecessorID] = append(g.Successors[edge.PredecessorID], edge)
	g.Predecessors[edge.SuccessorID] = append(g.Predecessors[edge.SuccessorID], edge)
}

// DetectCyclesTarjan executes Tarjan's SCC algorithm. Returns error if circular loops exist.
func (g *MultiProjectGraph) DetectCyclesTarjan() error {
	index := 0
	indices := make(map[string]int)
	lowlink := make(map[string]int)
	onStack := make(map[string]bool)
	stack := make([]string, 0)
	var sccs [][]string

	var strongConnect func(v string)
	strongConnect = func(v string) {
		indices[v] = index
		lowlink[v] = index
		index++
		stack = append(stack, v)
		onStack[v] = true

		for _, edge := range g.Successors[v] {
			w := edge.SuccessorID
			if _, visited := indices[w]; !visited {
				strongConnect(w)
				if lowlink[w] < lowlink[v] {
					lowlink[v] = lowlink[w]
				}
			} else if onStack[w] {
				if indices[w] < lowlink[v] {
					lowlink[v] = indices[w]
				}
			}
		}

		// Root of an SCC identified
		if lowlink[v] == indices[v] {
			var scc []string
			for {
				w := stack[len(stack)-1]
				stack = stack[:len(stack)-1]
				onStack[w] = false
				scc = append(scc, w)
				if w == v {
					break
				}
			}
			if len(scc) > 1 {
				sccs = append(sccs, scc)
			}
		}
	}

	for id := range g.Activities {
		if _, visited := indices[id]; !visited {
			strongConnect(id)
		}
	}

	if len(sccs) > 0 {
		msg := "circular dependencies detected across projects:"
		for i, scc := range sccs {
			msg += fmt.Sprintf(" [Cycle %d: ", i+1)
			for _, actID := range scc {
				msg += fmt.Sprintf("%s ", g.Activities[actID].Code)
			}
			msg += "]"
		}
		return errors.New(msg)
	}

	return nil
}

// TopologicalSort returns activity IDs in CPM execution order.
func (g *MultiProjectGraph) TopologicalSort() ([]string, error) {
	inDegree := make(map[string]int)
	for id := range g.Activities {
		inDegree[id] = 0
	}
	for _, edges := range g.Successors {
		for _, edge := range edges {
			inDegree[edge.SuccessorID]++
		}
	}

	queue := make([]string, 0)
	for id, deg := range inDegree {
		if deg == 0 {
			queue = append(queue, id)
		}
	}

	sorted := make([]string, 0, len(g.Activities))
	for len(queue) > 0 {
		curr := queue[0]
		queue = queue[1:]
		sorted = append(sorted, curr)

		for _, edge := range g.Successors[curr] {
			inDegree[edge.SuccessorID]--
			if inDegree[edge.SuccessorID] == 0 {
				queue = append(queue, edge.SuccessorID)
			}
		}
	}

	if len(sorted) != len(g.Activities) {
		return nil, errors.New("graph contains cycles; topological sort failed")
	}

	return sorted, nil
}

// CalculateCPM executes unified multi-project forward and backward passes.
func (g *MultiProjectGraph) CalculateCPM() error {
	// 1. Cycle Verification
	if err := g.DetectCyclesTarjan(); err != nil {
		return err
	}

	// 2. Topological Sort
	sorted, err := g.TopologicalSort()
	if err != nil {
		return err
	}

	// 3. Forward Pass (Early Dates)
	for _, id := range sorted {
		act := g.Activities[id]
		dataDate := g.DataDates[act.ProjectID]

		earliestStart := dataDate
		for _, predEdge := range g.Predecessors[id] {
			pred := g.Activities[predEdge.PredecessorID]
			var candidateStart time.Time

			switch predEdge.Type {
			case TypeFS:
				candidateStart = pred.EarlyFinish.Add(time.Duration(predEdge.LagHours) * time.Hour)
			case TypeSS:
				candidateStart = pred.EarlyStart.Add(time.Duration(predEdge.LagHours) * time.Hour)
			}

			if candidateStart.After(earliestStart) {
				earliestStart = candidateStart
			}
		}

		act.EarlyStart = earliestStart
		act.EarlyFinish = earliestStart.Add(time.Duration(act.Duration) * time.Hour)
	}

	// Determine Global Project Finish
	var globalFinish time.Time
	for _, act := range g.Activities {
		if act.EarlyFinish.After(globalFinish) {
			globalFinish = act.EarlyFinish
		}
	}

	// 4. Backward Pass (Late Dates & Total Float)
	for i := len(sorted) - 1; i >= 0; i-- {
		id := sorted[i]
		act := g.Activities[id]

		latestFinish := globalFinish
		if len(g.Successors[id]) > 0 {
			latestFinish = time.Unix(math.MaxInt64, 0)
			for _, succEdge := range g.Successors[id] {
				succ := g.Activities[succEdge.SuccessorID]
				var candidateFinish time.Time

				switch succEdge.Type {
				case TypeFS:
					candidateFinish = succ.LateStart.Add(-time.Duration(succEdge.LagHours) * time.Hour)
				case TypeFF:
					candidateFinish = succ.LateFinish.Add(-time.Duration(succEdge.LagHours) * time.Hour)
				}

				if candidateFinish.Before(latestFinish) {
					latestFinish = candidateFinish
				}
			}
		}

		act.LateFinish = latestFinish
		act.LateStart = latestFinish.Add(-time.Duration(act.Duration) * time.Hour)
		act.TotalFloat = int(act.LateStart.Sub(act.EarlyStart).Hours())
	}

	return nil
}
```

## 7. Real-World Engineering Pitfalls & Anti-Patterns

### 7.1 Pitfall 1: The "Invisible Float Vampire"
* **The Anti-Pattern:** A scheduler on Project B links an internal civil task to Project A's commercial COD milestone as a predecessor. Project B falls 90 days behind schedule.
* **Why it Breaks Systems:** Project A's scheduler opens their project and discovers that their Critical Path has collapsed to **-90 days of Total Float**, triggering lender penalties and executive panic, with zero explanation visible within Project A's internal network.
* **The Architectural Rule:** **Mandatory Interface Milestones (Handoff Buffers)**. Never link arbitrary operational tasks directly across projects. Force cross-project links to route through explicit, contractually governed **Interface Milestones** owned by designated Project Directors.

### 7.2 Pitfall 2: The Data Date Asynchrony Paradox
* **The Anti-Pattern:** Running a unified multi-project schedule when Project A was updated yesterday (Data Date: 30-Jun-2026), but Project B has not been updated in two months (Data Date: 30-Apr-2026).
* **Why it Breaks Systems:** Uncompleted activities from May in Project B calculate past early start dates that distort successor logic in Project A, corrupting resource histograms and cash flow forecasts.
* **The Architectural Rule:** Enforce an **Enterprise Schedule Harmonization Gate**. Before executing unified multi-project scheduling, the backend validates that all open projects have Data Dates within an approved 7-day synchronization window.

### 7.3 Pitfall 3: Dangling External Relationships
* **The Anti-Pattern:** Project B is deleted or archived, leaving dangling foreign keys in `project_relationship` where `predecessor_project_id` references a non-existent project.
* **Why it Breaks Systems:** The scheduling engine encounters null pointer exceptions during topological sorting, or converts the external predecessor into a hard fixed constraint date without notifying the PM.
* **The Architectural Rule:** Use database `ON DELETE RESTRICT` or maintain an explicit archival cleanup trigger that converts dangling external links into documented user-visible constraints (`Start-On-Or-After` fixed constraint) with an automated audit warning.
