## 🧠 Section A: Conceptual & Architectural Principles

### Solution 1: Orthogonal Multi-Dimensional Slicing vs. WBS Churn

#### 1. Why Altering the WBS for Ad-Hoc Views is a Fatal Error
Modifying the approved Work Breakdown Structure (WBS) to satisfy temporary or contractor-specific reporting needs is a critical project governance failure:
* **Contractual Scope Baseline Destruction:** The WBS represents the contractually approved 100% scope baseline agreed upon with project owners, financiers, and auditors. Changing the WBS changes the contractual deliverables tree and invalidates previously approved progress baselines.
* **Loss of Historical Variance Tracking:** Earned Value ($EV$) and schedule variance calculations compare the current schedule against baseline snapshots (e.g., Baseline B01). If the current WBS nodes no longer match the baseline WBS nodes, historical Earned Value comparisons become invalid.
* **Single-Hierarchy Limitation:** A tree can only have **one** parent-child structure. If you restructure the WBS by Contractor, you lose the ability to view it by System. Tomorrow, when the environmental auditor asks to see work by Environmental Impact Zone, you would have to rewrite the entire project tree again!

#### 2. How Activity Codes Solve the Problem
Activity Codes treat classification as **orthogonal faceted metadata**.
* The underlying WBS remains 100% intact and untouched.
* Each activity is tagged with independent codes (`Contractor = 'Sterling & Wilson'`, `Location = 'Block 01'`).
* The scheduling UI simply sorts, groups, and summarizes activities on the fly using these tags without altering CPM logic, dates, or contractual baseline structures.

#### 3. Cardinality Rules Between Activities and Activity Codes
In Primavera P6:
* An activity can have **at most ONE value** assigned per **Activity Code Type**.
* If the code type is `Discipline`, an activity cannot be simultaneously assigned `Civil` and `Electrical`.
* **Database Modeling:** This is enforced via a unique constraint:
  `UNIQUE(activity_id, code_type_id)`.
* If a task involves multiple disciplines, the task must either be decomposed into distinct sub-activities (e.g., "Inverter Civil Pad" vs "Inverter Cabling") or tagged with a composite code value (`Civil/Electrical Hybrid`).

### Solution 2: Activity Code Scoping & Enterprise Governance

#### 1. Optimal Scope Classification
```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                            ACTIVITY CODE SCOPE CLASSIFICATION                                    │
├──────────────────────────────────────────┬───────────────────┬───────────────────────────────────┤
│ Attribute                                │ Recommended Scope │ Architectural Justification       │
├──────────────────────────────────────────┼───────────────────┼───────────────────────────────────┤
│ Corporate Discipline (Civil, Elec, etc.) │ Global            │ Universal across all projects.    │
│ Solar Inverter Station ID (INV-01..32)   │ Project-level     │ Local to Surya 100MW site layout. │
│ PV Module Technology (Bifacial/Mono)     │ EPS-level         │ Shared by all Solar SBU projects. │
│ Concrete Pour Trench (TR-A104-EAST)      │ Project-level     │ Micro-workfront specific to site. │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 2. Consequences of Schedulers Creating Global Codes
Allowing project schedulers to create Global Activity Codes leads to **Global Dictionary Pollution**:
* Within months, hundreds of duplicate, inconsistent codes are created (`Vendor`, `Subcontractor`, `Subcon`, `Contractor_Name`).
* Global drop-down lists become bloated and unmanageable.
* Corporate-wide rollups fail because half the projects use one spelling and half use another.
* Database index size expands with redundant metadata.

#### 3. EPS-level Scope Visibility Boundary
An EPS-level code created at `SURYA-SOLAR` is **invisible** to projects under `SURYA-GRID`.
* **Reason:** EPS codes are scoped strictly to the declaring EPS node and its descendants (`node_path <@ 'SURYA_SOLAR'`).
* This provides divisional sandboxing: the Solar division can define solar-specific codes without cluttering the dictionaries of the Transmission Grid or Wind divisions.

### Solution 3: Hierarchical Code Values

#### 1. Hierarchical Values vs. Flat Tag Strings
* Flat tag strings are isolated values (`"Block 01"`, `"Rajasthan"`). The database has no inherent knowledge that Block 01 is physically located inside Rajasthan.
* Hierarchical code values model tree relationships within the code dictionary using parent-child links or materialized paths (`IND -> RAJ -> JOD -> BLK01`).

#### 2. Visual Banding at Level 2 vs. Level 4
* **Grouped at Level 2 (`RAJ`):** The Gantt chart creates a single summary band for Rajasthan. All 2,500 activities across all districts and blocks are aggregated together.
* **Grouped at Level 4 (`BLK01`):** The Gantt chart creates 32 distinct summary bands (one per Inverter Block), allowing granular inspection of local workfronts.

#### 3. Summary Metric Calculation Mechanics
At each band tier:
* **Budget at Completion ($BAC$):** Direct sum of all child activities ($\sum BAC$).
* **Earliest Start:** Minimum Early Start across all child activities ($\min(ES)$).
* **Latest Finish:** Maximum Early Finish across all child activities ($\max(EF)$).
* **Worst Float:** Minimum Total Float across all child activities ($\min(TF)$). (A summary band is critical if *any* task within it is critical).

### Solution 4: User Defined Fields (UDFs) vs. Activity Codes

#### 1. Operational Distinction
* **Use Activity Codes when:** You need to **group, sort, filter, or summarize** activities into visual bands on the Gantt chart or generate categorical breakdown reports.
* **Use UDFs when:** You need to store **discrete data attributes** (such as a purchase order number, physical quantity, contractual warranty date, or calculated monetary penalty) that do not represent grouping categories.

#### 2. Primary Primitive Data Types in UDFs
```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                   UDF PRIMITIVE DATA TYPES                                       │
├───────────────┬───────────────────────────────┬──────────────────────────────────────────────────┤
│ Data Type     │ Internal Database Type        │ Real-World Solar Infrastructure Example          │
├───────────────┼───────────────────────────────┼──────────────────────────────────────────────────┤
│ Text          │ VARCHAR / TEXT                │ SAP Purchase Order: "PO-2026-IND-9912"           │
│ Integer       │ INT                           │ Number of Piles Driven: 450                      │
│ Cost          │ NUMERIC(16,2)                 │ Liquidated Damages Exposure: ₹45,00,000.00       │
│ Number        │ DOUBLE PRECISION / NUMERIC    │ Concrete Volume Poured: 125.75 m³                │
│ Date          │ TIMESTAMPTZ                   │ Factory Acceptance Test (FAT) Date: 2026-08-15   │
│ Indicator     │ VARCHAR(16) (Enum)            │ Environmental Clearance Status: GREEN            │
└───────────────┴───────────────────────────────┴──────────────────────────────────────────────────┘
```

#### 3. Static UDFs vs. Formula UDFs
* **Static UDF:** Persisted directly in the database row. Modified only by user input, API integrations, or scheduled batch jobs.
* **Formula UDF:** Dynamically evaluated expression computed in-memory or at query time based on other project fields. It is never statically persisted, ensuring it is always synchronized with schedule calculations.

## 🏗️ Section B: Database Design & SQL Implementation

### Solution 5: Database Architecture: The EAV Dilemma vs. Hybrid JSONB

#### 1. Performance Impact of Pure EAV Tables
Querying 2,500 activities with 15 custom attributes in pure EAV:
```sql
SELECT a.id, eav1.val AS po_no, eav2.val AS volume, ...
FROM activity a
LEFT JOIN activity_eav eav1 ON eav1.activity_id = a.id AND eav1.key = 'po_no'
LEFT JOIN activity_eav eav2 ON eav2.activity_id = a.id AND eav2.key = 'volume'
... -- 15 total joins!
WHERE a.project_id = '...';
```
* **Consequences:** 15 self-joins generate massive nested loop iterations, ballooning query memory and causing query latency of 4 to 12 seconds for a single table view.

#### 2. Benefits of the Hybrid Pattern
* **Normalized Tables for Codes:** Enforces referential integrity, supports hierarchical `ltree` indexing, and allows fast relational joins for grouping.
* **JSONB with GIN for UDFs:** Consolidates all dynamic attributes into a single document column per activity row. Zero joins required to retrieve 50 custom attributes. GIN indexing allows sub-millisecond filtering (`WHERE udf_values @> '{"permit_status": "APPROVED"}'`).

#### 3. Production PostgreSQL DDL
```sql
CREATE EXTENSION IF NOT EXISTS ltree;

-- 1. Activity Code Type
CREATE TABLE activity_code_type (
    code_type_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code_type_name VARCHAR(64) NOT NULL,
    scope VARCHAR(16) NOT NULL CHECK (scope IN ('GLOBAL', 'EPS', 'PROJECT')),
    eps_id UUID REFERENCES eps_node(eps_id) ON DELETE CASCADE,
    project_id UUID REFERENCES project(project_id) ON DELETE CASCADE,
    is_secure BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    
    CONSTRAINT chk_code_type_scope CHECK (
        (scope = 'GLOBAL' AND eps_id IS NULL AND project_id IS NULL) OR
        (scope = 'EPS' AND eps_id IS NOT NULL AND project_id IS NULL) OR
        (scope = 'PROJECT' AND project_id IS NOT NULL)
    )
);

-- 2. Activity Code Values (Hierarchical)
CREATE TABLE activity_code_value (
    value_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code_type_id UUID NOT NULL REFERENCES activity_code_type(code_type_id) ON DELETE CASCADE,
    code_value VARCHAR(32) NOT NULL,
    description VARCHAR(255) NOT NULL,
    parent_value_id UUID REFERENCES activity_code_value(value_id) ON DELETE RESTRICT,
    value_path ltree NOT NULL,
    sort_order INT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    CONSTRAINT uq_code_type_value UNIQUE (code_type_id, code_value)
);
CREATE INDEX idx_code_val_path ON activity_code_value USING GIST (value_path);
CREATE INDEX idx_code_val_type ON activity_code_value(code_type_id);

-- 3. Activity Code Assignments
CREATE TABLE activity_code_assignment (
    assignment_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    activity_id UUID NOT NULL,
    code_type_id UUID NOT NULL REFERENCES activity_code_type(code_type_id) ON DELETE CASCADE,
    value_id UUID NOT NULL REFERENCES activity_code_value(value_id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    CONSTRAINT uq_activity_code_type_assign UNIQUE (activity_id, code_type_id)
);
CREATE INDEX idx_assign_activity ON activity_code_assignment(activity_id);
CREATE INDEX idx_assign_value ON activity_code_assignment(value_id);
```

### Solution 6: Automated PostgreSQL JSONB Type Validation Trigger

```sql
CREATE OR REPLACE FUNCTION trg_fn_validate_activity_udfs()
RETURNS TRIGGER AS $$
DECLARE
    def RECORD;
    val_type text;
    field_val jsonb;
BEGIN
    FOR def IN 
        SELECT field_key, data_type 
        FROM udf_field_definition 
        WHERE subject_area = 'ACTIVITY' AND is_active = TRUE 
    LOOP
        IF NEW.udf_values ? def.field_key THEN
            field_val := NEW.udf_values -> def.field_key;
            val_type := jsonb_typeof(field_val);

            IF val_type <> 'null' THEN
                CASE def.data_type
                    WHEN 'COST', 'NUMBER' THEN
                        IF val_type <> 'number' THEN
                            RAISE EXCEPTION 'Field % must be numeric, got %', def.field_key, val_type;
                        END IF;
                    WHEN 'INTEGER' THEN
                        IF val_type <> 'number' OR (field_val::text)::numeric % 1 <> 0 THEN
                            RAISE EXCEPTION 'Field % must be integer, got %', def.field_key, field_val;
                        END IF;
                    WHEN 'INDICATOR' THEN
                        IF val_type <> 'string' OR NOT (field_val#>>'{}' IN ('RED', 'YELLOW', 'GREEN', 'BLUE')) THEN
                            RAISE EXCEPTION 'Field % must be RED, YELLOW, GREEN, or BLUE; got %', def.field_key, field_val;
                        END IF;
                    WHEN 'DATE' THEN
                        BEGIN
                            PERFORM (field_val#>>'{}')::timestamptz;
                        EXCEPTION WHEN OTHERS THEN
                            RAISE EXCEPTION 'Field % must be ISO8601 timestamp string, got %', def.field_key, field_val;
                        END;
                    WHEN 'TEXT' THEN
                        IF val_type <> 'string' THEN
                            RAISE EXCEPTION 'Field % must be text string, got %', def.field_key, val_type;
                        END IF;
                END CASE;
            END IF;
        END IF;
    END LOOP;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_validate_activity_udfs
BEFORE INSERT OR UPDATE OF udf_values ON activity
FOR EACH ROW EXECUTE FUNCTION trg_fn_validate_activity_udfs();
```

### Solution 7: Complex Multi-Dimensional Slicing SQL Query

```sql
WITH contractor_assignments AS (
    SELECT 
        aca.activity_id,
        acv.code_value AS contractor_name
    FROM activity_code_assignment aca
    JOIN activity_code_type act ON act.code_type_id = aca.code_type_id
    JOIN activity_code_value acv ON acv.value_id = aca.value_id
    WHERE act.code_type_name = 'Contractor'
),
discipline_assignments AS (
    SELECT 
        aca.activity_id,
        acv.code_value AS discipline_name
    FROM activity_code_assignment aca
    JOIN activity_code_type act ON act.code_type_id = aca.code_type_id
    JOIN activity_code_value acv ON acv.value_id = aca.value_id
    WHERE act.code_type_name = 'Discipline'
)
SELECT 
    COALESCE(ca.contractor_name, 'UNASSIGNED') AS contractor,
    COALESCE(da.discipline_name, 'UNASSIGNED') AS discipline,
    COUNT(a.activity_id) AS total_activities,
    COALESCE(SUM(a.budget_at_completion), 0.00) AS total_bac,
    COALESCE(SUM(a.earned_value), 0.00) AS total_ev,
    COALESCE(SUM(a.actual_cost), 0.00) AS total_ac,
    COALESCE(SUM(a.earned_value) - SUM(a.actual_cost), 0.00) AS cost_variance,
    COALESCE(MIN(a.total_float), 0) AS worst_float
FROM activity a
LEFT JOIN contractor_assignments ca ON ca.activity_id = a.activity_id
LEFT JOIN discipline_assignments da ON da.activity_id = a.activity_id
WHERE a.project_id = 'c4b8b6e2-7634-4a25-a1c2-3e2b20465590'
GROUP BY 
    COALESCE(ca.contractor_name, 'UNASSIGNED'),
    COALESCE(da.discipline_name, 'UNASSIGNED')
ORDER BY contractor, discipline;
```

## 💻 Section C: Golang Dynamic Slicing & Grouping Engine

### Solution 8: Dynamic Multi-Dimensional Slicing Algorithm

```go
package grouping

import (
	"fmt"
	"sort"
)

type Activity struct {
	ID                 string                 `json:"id"`
	Code               string                 `json:"code"`
	Name               string                 `json:"name"`
	BudgetAtCompletion float64                `json:"budget_at_completion"`
	PlannedValue       float64                `json:"planned_value"`
	EarnedValue        float64                `json:"earned_value"`
	ActualCost         float64                `json:"actual_cost"`
	TotalFloat         int                    `json:"total_float"`
	Codes              map[string]string      `json:"codes"` // Type -> Value
	UDFs               map[string]interface{} `json:"udf_values"`
}

type GroupSummary struct {
	GroupKey      string          `json:"group_key"`
	GroupValue    string          `json:"group_value"`
	ActivityCount int             `json:"activity_count"`
	TotalBAC      float64         `json:"total_bac"`
	TotalEV       float64         `json:"total_ev"`
	TotalAC       float64         `json:"total_ac"`
	WorstFloat    int             `json:"worst_float"`
	SubGroups     []*GroupSummary `json:"sub_groups,omitempty"`
	Activities    []*Activity     `json:"activities,omitempty"`
}

func SliceActivities(activities []*Activity, groupByFields []string) *GroupSummary {
	root := &GroupSummary{
		GroupKey:   "ROOT",
		GroupValue: "All Activities",
		WorstFloat: 999999,
	}
	buildSubTree(root, activities, groupByFields, 0)
	return root
}

func buildSubTree(current *GroupSummary, items []*Activity, fields []string, depth int) {
	if len(items) == 0 {
		return
	}

	// Calculate metrics at current node
	current.ActivityCount = len(items)
	current.WorstFloat = 999999
	for _, act := range items {
		current.TotalBAC += act.BudgetAtCompletion
		current.TotalEV += act.EarnedValue
		current.TotalAC += act.ActualCost
		if act.TotalFloat < current.WorstFloat {
			current.WorstFloat = act.TotalFloat
		}
	}

	// Leaf level reached
	if depth >= len(fields) {
		current.Activities = items
		return
	}

	currentField := fields[depth]
	partitions := make(map[string][]*Activity)

	for _, act := range items {
		val := "UNASSIGNED"
		if codeVal, exists := act.Codes[currentField]; exists && codeVal != "" {
			val = codeVal
		} else if udfVal, exists := act.UDFs[currentField]; exists && udfVal != nil {
			val = fmt.Sprintf("%v", udfVal)
		}
		partitions[val] = append(partitions[val], act)
	}

	// Sort group keys for determinism
	sortedKeys := make([]string, 0, len(partitions))
	for k := range partitions {
		sortedKeys = append(sortedKeys, k)
	}
	sort.Strings(sortedKeys)

	current.SubGroups = make([]*GroupSummary, 0, len(sortedKeys))
	for _, k := range sortedKeys {
		sub := &GroupSummary{
			GroupKey:   currentField,
			GroupValue: k,
			WorstFloat: 999999,
		}
		buildSubTree(sub, partitions[k], fields, depth+1)
		current.SubGroups = append(current.SubGroups, sub)
	}
}
```

### Solution 9: High-Performance Formula UDF Evaluator

```go
package grouping

import (
	"errors"
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
	"strconv"
)

// EvaluateFormula safely evaluates arithmetic expressions over activity variables.
func EvaluateFormula(expression string, activity *Activity) (float64, error) {
	expr, err := parser.ParseExpr(expression)
	if err != nil {
		return 0, fmt.Errorf("invalid formula syntax: %w", err)
	}

	return evalAST(expr, activity)
}

func evalAST(node ast.Expr, act *Activity) (float64, error) {
	switch n := node.(type) {
	case *ast.BasicLit:
		if n.Kind == token.INT || n.Kind == token.FLOAT {
			return strconv.ParseFloat(n.Value, 64)
		}
		return 0, fmt.Errorf("unsupported literal type: %s", n.Value)

	case *ast.Ident:
		switch n.Name {
		case "budget_at_completion", "bac":
			return act.BudgetAtCompletion, nil
		case "planned_value", "pv":
			return act.PlannedValue, nil
		case "earned_value", "ev":
			return act.EarnedValue, nil
		case "actual_cost", "ac":
			return act.ActualCost, nil
		case "total_float", "tf":
			return float64(act.TotalFloat), nil
		default:
			// Check UDFs
			if val, ok := act.UDFs[n.Name]; ok {
				if fVal, ok := val.(float64); ok {
					return fVal, nil
				}
			}
			return 0, fmt.Errorf("unknown variable: %s", n.Name)
		}

	case *ast.BinaryExpr:
		left, err := evalAST(n.X, act)
		if err != nil {
			return 0, err
		}
		right, err := evalAST(n.Y, act)
		if err != nil {
			return 0, err
		}

		switch n.Op {
		case token.ADD:
			return left + right, nil
		case token.SUB:
			return left - right, nil
		case token.MUL:
			return left * right, nil
		case token.QUO:
			if right == 0 {
				return 0, errors.New("division by zero in formula")
			}
			return left / right, nil
		default:
			return 0, fmt.Errorf("unsupported operator: %s", n.Op)
		}

	case *ast.ParenExpr:
		return evalAST(n.X, act)

	default:
		return 0, fmt.Errorf("unsupported expression node: %T", node)
	}
}
```

### Solution 10: Real-World Incident — The Corrupted SAP Sync Outage

#### 1. Architectural Flaws Analysis
1. **Blind Payload Persistence:** The integration script inserted raw SAP JSON payloads directly into `udf_values` without schema validation or type checks.
2. **Missing Currency Normalization:** SAP exported numbers as localized strings with comma separators (`"1,450,000.00"`), which cannot be parsed as IEEE 754 floating-point numbers.
3. **ERP Sentinel Codes Misinterpreted:** SAP sent `-9999` (a sentinel error value indicating "Pending Procurement Approval") which was stored as a legitimate cost number, corrupting earned value metrics.

#### 2. Defensive Ingestion & Sanitization Layer in Go

```go
package grouping

import (
	"fmt"
	"strconv"
	"strings"
)

type SAPPayload struct {
	ActivityCode string `json:"activity_code"`
	PONumber     string `json:"po_number"`
	CommittedAmt string `json:"committed_amt"` // e.g. "1,450,000.00" or "-9999"
}

type SanitizedUDFs struct {
	SAP_PO       string   `json:"sap_po"`
	CommittedCost *float64 `json:"committed_cost,omitempty"`
}

func SanitizeSAPRecord(raw SAPPayload) (*SanitizedUDFs, error) {
	sanitized := &SanitizedUDFs{
		SAP_PO: strings.TrimSpace(raw.PONumber),
	}

	// 1. Strip commas and spaces
	cleanAmtStr := strings.ReplaceAll(raw.CommittedAmt, ",", "")
	cleanAmtStr = strings.TrimSpace(cleanAmtStr)

	// 2. Parse numeric value
	val, err := strconv.ParseFloat(cleanAmtStr, 64)
	if err != nil {
		return nil, fmt.Errorf("invalid currency format from SAP: %s", raw.CommittedAmt)
	}

	// 3. Catch SAP sentinel error codes
	if val < 0 {
		// Log warning, treat pending approval as null cost rather than negative financial value
		sanitized.CommittedCost = nil
	} else {
		sanitized.CommittedCost = &val
	}

	return sanitized, nil
}
```
This defensive layer ensures only valid numbers are stored, preventing corrupted ERP inputs from ever reaching the database or scheduling calculation engine.
