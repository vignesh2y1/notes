# Topic 9.3: Activity Codes & User Defined Fields (UDFs)

## 1. Executive Summary & Plain-English Analogy

### 1.1 The Multi-Dimensional Rubik's Cube vs. The Rigid Bookshelf Analogy
Imagine you have a library of 10,000 engineering and construction documents. If you organize them on physical bookshelves strictly by **System Architecture** (Inverters, PV Modules, Transmission Lines), you have created a single, rigid Work Breakdown Structure (WBS).

Now, three different stakeholders walk into your library:
1. The **Site Subcontractor** says: *"I only care about work assigned to Sterling & Wilson across all systems."*
2. The **Civil Quality Inspector** says: *"I only care about Concrete Foundations in Block 4, regardless of whether it's for an inverter or a switchyard."*
3. The **Chief Procurement Officer** says: *"I need to see all imported equipment with Long Lead Times across every division."*

In software engineering terms:
* **WBS** is the **Canonical Hierarchy** (the single parent-child tree defining project scope ownership).
* **Activity Codes** are **Categorical Metadata / Faceted Tags** (enabling multi-dimensional OLAP slicing, grouping, filtering, and reporting across orthogonal business dimensions).
* **User Defined Fields (UDFs)** are **Dynamic Custom Attributes** (arbitrary typed properties—such as warranty dates, vendor purchase order numbers, environmental permits, or calculated metrics—attached to project entities).

## 3. Conceptual Foundations: User Defined Fields (UDFs)

### 3.1 Subject Areas & Supported Data Types
While Activity Codes provide categorical grouping and filtering, **User Defined Fields (UDFs)** allow organizations to capture custom structured data without modifying core database schemas.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                               UDF SUBJECT AREAS & DATA TYPES MATRIX                              │
├───────────────────────┬───────────────────────────────────┬──────────────────────────────────────┤
│ Subject Area          │ Supported Data Types              │ Real-World Infrastructure Use Case   │
├───────────────────────┼───────────────────────────────────┼──────────────────────────────────────┤
│ Project UDF           │ Text, Integer, Cost, Number,      │ • EPC Contract Number (Text)         │
│                       │ Date, Indicator (Traffic Light)   │ • Liquidated Damages Daily Rate (Cost│
│                       │                                   │ • Land Acquisition Clear (Indicator) │
├───────────────────────┼───────────────────────────────────┼──────────────────────────────────────┤
│ WBS UDF               │ Text, Integer, Cost, Number, Date │ • Sub-system Commissioning Date (Date│
│                       │                                   │ • Weightage Percentage (Number)      │
├───────────────────────┼───────────────────────────────────┼──────────────────────────────────────┤
│ Activity UDF          │ Text, Integer, Cost, Number,      │ • SAP Purchase Order Number (Text)   │
│                       │ Date, Indicator, Formula          │ • Concrete Volume Poured (m³) (Number│
│                       │                                   │ • Environmental Clearance OK (Indic.)│
├───────────────────────┼───────────────────────────────────┼──────────────────────────────────────┤
│ Resource UDF          │ Text, Number, Cost, Date          │ • Safety Certification Expiry (Date) │
│                       │                                   │ • Union Pay Grade Level (Integer)    │
└───────────────────────┴───────────────────────────────────┴──────────────────────────────────────┘
```

### 3.2 Static UDFs vs. Dynamic Formula Fields
1. **Static UDFs:** User-entered or API-synchronized values stored directly in the database (e.g., entering an equipment serial number).
2. **Formula UDFs:** Dynamically evaluated expressions computed at runtime. For example:
   $$\text{Liquidated Damages Exposure} = \max(0, (\text{Current Early Finish} - \text{Contract Finish})) \times \text{Daily LD Rate}$$

## 5. Enterprise Database Architecture (PostgreSQL)

### 5.1 The Architectural Dilemma: EAV Anti-Pattern vs. Hybrid JSONB
When designing custom attribute storage for enterprise scheduling systems:
* **Pure Entity-Attribute-Value (EAV):**
  - Stores every attribute as a separate row (`entity_id, attribute_key, value_string`).
  - **The Disaster:** Querying an activity table with 2,500 activities and 20 custom fields requires **20 self-joins**, destroying query performance and overwhelming the PostgreSQL query planner.
* **Pure JSONB Document Column:**
  - Fast writes, no schema migrations required.
  - **The Hazard:** Lacks referential integrity, allows corrupt data types (e.g., storing `"hello"` in a cost field), and makes cross-project aggregate rollups slow without GIN indexes.

#### The Enterprise Hybrid Pattern:
1. **Activity Codes:** Model with normalized relational tables (`code_type`, `code_value`, `code_assignment`) because codes require strict referential integrity, hierarchical trees, and indexed foreign keys.
2. **User Defined Fields (UDFs):** Model with a **Metadata Dictionary Table** defining field types, coupled with a validated **`jsonb` column** on the entity table indexed via GIN.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                         ENTERPRISE HYBRID STORAGE ARCHITECTURE                                   │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   RELATIONAL ACTIVITY CODES (Normalized)           DYNAMIC UDF VALUES (Hybrid JSONB)             │
│                                                                                                  │
│   ┌───────────────────────────┐                    ┌───────────────────────────────┐             │
│   │ activity_code_type        │                    │ udf_field_definition          │             │
│   │  (Discipline, Contractor) │                    │  (SAP_PO, Soil_Permit, Volume)│             │
│   └─────────────┬─────────────┘                    └───────────────┬───────────────┘             │
│                 │ 1:N                                              │ Validates                   │
│   ┌─────────────▼─────────────┐                                    ▼                             │
│   │ activity_code_value       │                    ┌───────────────────────────────┐             │
│   │  (Civil, Elec, S&W, L&T)  │                    │ activity                      │             │
│   └─────────────┬─────────────┘                    │  ...                          │             │
│                 │ 1:N                              │  udf_values JSONB             │             │
│   ┌─────────────▼─────────────┐                    │   {"sap_po": "PO-9912",       │             │
│   │ activity_code_assignment  │                    │    "concrete_m3": 450.5,      │             │
│   │  (activity_id, value_id)  │                    │    "permit_ok": true}         │             │
```

### 5.2 PostgreSQL DDL Implementation

```sql
CREATE EXTENSION IF NOT EXISTS ltree;

-- 1. Activity Code Type (Definition)
CREATE TABLE activity_code_type (
    code_type_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code_type_name VARCHAR(64) NOT NULL,
    scope VARCHAR(16) NOT NULL CHECK (scope IN ('GLOBAL', 'EPS', 'PROJECT')),
    eps_id UUID REFERENCES eps_node(eps_id) ON DELETE CASCADE,
    project_id UUID REFERENCES project(project_id) ON DELETE CASCADE,
    is_secure BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    
    -- Integrity Check: EPS scope requires eps_id; PROJECT scope requires project_id
    CONSTRAINT chk_code_type_scope CHECK (
        (scope = 'GLOBAL' AND eps_id IS NULL AND project_id IS NULL) OR
        (scope = 'EPS' AND eps_id IS NOT NULL AND project_id IS NULL) OR
        (scope = 'PROJECT' AND project_id IS NOT NULL)
    )
);
CREATE INDEX idx_code_type_scope ON activity_code_type(scope);

-- 2. Activity Code Values (Hierarchical Tree)
CREATE TABLE activity_code_value (
    value_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code_type_id UUID NOT NULL REFERENCES activity_code_type(code_type_id) ON DELETE CASCADE,
    code_value VARCHAR(32) NOT NULL,
    description VARCHAR(255) NOT NULL,
    parent_value_id UUID REFERENCES activity_code_value(value_id) ON DELETE RESTRICT,
    value_path ltree NOT NULL,
    sort_order INT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    CONSTRAINT uq_code_type_value UNIQUE (code_type_id, code_value)
);
CREATE INDEX idx_code_val_path ON activity_code_value USING GIST (value_path);
CREATE INDEX idx_code_val_type ON activity_code_value(code_type_id);

-- 3. Activity Code Assignments Table
CREATE TABLE activity_code_assignment (
    assignment_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    activity_id UUID NOT NULL, -- references activity(activity_id)
    code_type_id UUID NOT NULL REFERENCES activity_code_type(code_type_id) ON DELETE CASCADE,
    value_id UUID NOT NULL REFERENCES activity_code_value(value_id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    CONSTRAINT uq_activity_code_type_assign UNIQUE (activity_id, code_type_id)
);
CREATE INDEX idx_assign_activity ON activity_code_assignment(activity_id);
CREATE INDEX idx_assign_value ON activity_code_assignment(value_id);

-- 4. UDF Field Metadata Dictionary
CREATE TABLE udf_field_definition (
    field_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    field_key VARCHAR(64) NOT NULL UNIQUE,
    field_name VARCHAR(120) NOT NULL,
    subject_area VARCHAR(32) NOT NULL 
        CHECK (subject_area IN ('PROJECT', 'WBS', 'ACTIVITY', 'RESOURCE', 'STEP')),
    data_type VARCHAR(16) NOT NULL 
        CHECK (data_type IN ('TEXT', 'INTEGER', 'COST', 'NUMBER', 'DATE', 'INDICATOR')),
    formula_expression TEXT, -- If non-null, field is calculated dynamically
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

-- 5. Activity Entity with JSONB UDF Storage & GIN Index
ALTER TABLE activity ADD COLUMN IF NOT EXISTS udf_values JSONB NOT NULL DEFAULT '{}'::jsonb;
CREATE INDEX idx_activity_udf_gin ON activity USING GIN (udf_values);
```

### 5.3 Automated JSONB Type Validation Trigger
To guarantee that users do not write invalid types (e.g., text strings into a `COST` or `DATE` UDF):

```sql
CREATE OR REPLACE FUNCTION trg_fn_validate_activity_udfs()
RETURNS TRIGGER AS $$
DECLARE
    def RECORD;
    val_type text;
    field_val jsonb;
BEGIN
    FOR def IN SELECT field_key, data_type FROM udf_field_definition WHERE subject_area = 'ACTIVITY' LOOP
        IF NEW.udf_values ? def.field_key THEN
            field_val := NEW.udf_values -> def.field_key;
            val_type := jsonb_typeof(field_val);

            -- Validate nulls are permitted
            IF val_type <> 'null' THEN
                CASE def.data_type
                    WHEN 'COST', 'NUMBER' THEN
                        IF val_type <> 'number' THEN
                            RAISE EXCEPTION 'UDF field % must be numeric, got %', def.field_key, val_type;
                        END IF;
                    WHEN 'INTEGER' THEN
                        IF val_type <> 'number' OR (field_val::text)::numeric % 1 <> 0 THEN
                            RAISE EXCEPTION 'UDF field % must be integer, got %', def.field_key, field_val;
                        END IF;
                    WHEN 'INDICATOR' THEN
                        IF val_type <> 'string' OR NOT (field_val#>>'{}' IN ('RED', 'YELLOW', 'GREEN', 'BLUE')) THEN
                            RAISE EXCEPTION 'UDF field % must be valid indicator (RED, YELLOW, GREEN, BLUE)', def.field_key;
                        END IF;
                    WHEN 'DATE' THEN
                        -- Attempt to parse ISO8601 date string
                        BEGIN
                            PERFORM (field_val#>>'{}')::timestamptz;
                        EXCEPTION WHEN OTHERS THEN
                            RAISE EXCEPTION 'UDF field % must be ISO8601 date string, got %', def.field_key, field_val;
                        END;
                    WHEN 'TEXT' THEN
                        IF val_type <> 'string' THEN
                            RAISE EXCEPTION 'UDF field % must be text string, got %', def.field_key, val_type;
                        END IF;
                END CASE;
            END IF;
        END IF;
    END LOOP;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_validate_activity_udf_types
BEFORE INSERT OR UPDATE OF udf_values ON activity
FOR EACH ROW EXECUTE FUNCTION trg_fn_validate_activity_udfs();
```

## 6. Production Golang Dynamic Slicing & Grouping Engine

When building a high-speed scheduling engine, the backend must group and summarize thousands of activities along arbitrary dimensions in milliseconds.

Below is an enterprise Go implementation that:
1. Dynamically slices an activity collection across an ordered slice of grouping keys (`[Contractor, Discipline, Location]`).
2. Builds a hierarchical summary tree in memory.
3. Aggregates Duration, Budget, Earned Value, and Float metrics at every grouping band.

```go
package grouping

import (
	"fmt"
	"sort"
	"strings"
	"time"
)

// Activity represents an individual scheduled task.
type Activity struct {
	ID                 string                 `json:"id"`
	Code               string                 `json:"code"`
	Name               string                 `json:"name"`
	PlannedDuration    int                    `json:"planned_duration"` // hours or days
	BudgetAtCompletion float64                `json:"budget_at_completion"`
	PlannedValue       float64                `json:"planned_value"`
	EarnedValue        float64                `json:"earned_value"`
	ActualCost         float64                `json:"actual_cost"`
	TotalFloat         int                    `json:"total_float"`
	Codes              map[string]string      `json:"codes"`      // CodeTypeName -> CodeValue
	UDFs               map[string]interface{} `json:"udf_values"` // FieldKey -> Value
}

// GroupSummary aggregates performance metrics for an arbitrary slice of activities.
type GroupSummary struct {
	GroupKey           string          `json:"group_key"`
	GroupValue         string          `json:"group_value"`
	ActivityCount      int             `json:"activity_count"`
	TotalBAC           float64         `json:"total_bac"`
	TotalPV            float64         `json:"total_pv"`
	TotalEV            float64         `json:"total_ev"`
	TotalAC            float64         `json:"total_ac"`
	MinFloat           int             `json:"min_float"`
	SubGroups          []*GroupSummary `json:"sub_groups,omitempty"`
	Activities         []*Activity     `json:"activities,omitempty"`
}

// MultiDimensionalSlicer organizes flat activities into an N-tier hierarchical grouping tree.
type MultiDimensionalSlicer struct {
	groupByFields []string // e.g. ["Contractor", "Discipline", "Location"]
}

// NewMultiDimensionalSlicer creates a new slicing engine with specified grouping order.
func NewMultiDimensionalSlicer(groupByFields []string) *MultiDimensionalSlicer {
	return &MultiDimensionalSlicer{groupByFields: groupByFields}
}

// Slice builds a hierarchical summary tree from flat activities.
func (s *MultiDimensionalSlicer) Slice(activities []*Activity) *GroupSummary {
	root := &GroupSummary{
		GroupKey:   "ROOT",
		GroupValue: "All Activities",
		MinFloat:   999999,
	}

	s.buildHierarchy(root, activities, 0)
	return root
}

func (s *MultiDimensionalSlicer) buildHierarchy(currentGroup *GroupSummary, items []*Activity, depth int) {
	if len(items) == 0 {
		return
	}

	// Base Case: We have partitioned through all grouping dimensions
	if depth >= len(s.groupByFields) {
		currentGroup.Activities = items
		s.aggregateMetrics(currentGroup, items)
		return
	}

	currentField := s.groupByFields[depth]

	// Partition items by the current grouping field
	partitions := make(map[string][]*Activity)
	for _, act := range items {
		val := "Unassigned"
		if codeVal, exists := act.Codes[currentField]; exists && codeVal != "" {
			val = codeVal
		} else if udfVal, exists := act.UDFs[currentField]; exists && udfVal != nil {
			val = fmt.Sprintf("%v", udfVal)
		}
		partitions[val] = append(partitions[val], act)
	}

	// Sort keys for deterministic output
	sortedKeys := make([]string, 0, len(partitions))
	for k := range partitions {
		sortedKeys = append(sortedKeys, k)
	}
	sort.Strings(sortedKeys)

	// Recursively build child group nodes
	currentGroup.SubGroups = make([]*GroupSummary, 0, len(sortedKeys))
	for _, key := range sortedKeys {
		subGroup := &GroupSummary{
			GroupKey:   currentField,
			GroupValue: key,
			MinFloat:   999999,
		}
		s.buildHierarchy(subGroup, partitions[key], depth+1)
		currentGroup.SubGroups = append(currentGroup.SubGroups, subGroup)
	}

	// Aggregate metrics for this group from all child items
	s.aggregateMetrics(currentGroup, items)
}

func (s *MultiDimensionalSlicer) aggregateMetrics(group *GroupSummary, items []*Activity) {
	group.ActivityCount = len(items)
	group.TotalBAC = 0
	group.TotalPV = 0
	group.TotalEV = 0
	group.TotalAC = 0
	group.MinFloat = 999999

	for _, act := range items {
		group.TotalBAC += act.BudgetAtCompletion
		group.TotalPV += act.PlannedValue
		group.TotalEV += act.EarnedValue
		group.TotalAC += act.ActualCost
		if act.TotalFloat < group.MinFloat {
			group.MinFloat = act.TotalFloat
		}
	}

	if len(items) == 0 {
		group.MinFloat = 0
	}
}
```

## 7. Real-World Engineering Pitfalls & Anti-Patterns

### 7.1 Pitfall 1: Global Code Pollution
* **The Anti-Pattern:** Allowing standard schedulers to create global activity codes. Within 12 months, the global dictionary contains 1,200 redundant codes (`Subcon`, `Subcontractor`, `Sub_Contractor`, `Vendor_Name`, `Temp_Code_Bob`).
* **Why it Breaks Systems:** Global drop-down lists become unusable, corporate aggregation queries break, and database memory expands with fragmented string indices.
* **The Architectural Rule:** Enforce strict RBAC on `activity_code_type`. Only Enterprise PMO Administrators can create **Global Codes**. Project Schedulers are strictly sandboxed to creating **Project-level Codes**.

### 7.2 Pitfall 2: The EAV Performance Trap
* **The Anti-Pattern:** Storing all custom attributes in a generic `entity_attribute_values` table (`entity_id, key, value_string`).
* **Why it Breaks Systems:** Querying 5,000 activities with 15 UDFs requires joining `entity_attribute_values` 15 times in SQL. Query latency exceeds 8 seconds, locking database tables and crashing the Next.js API.
* **The Architectural Rule:** Use **JSONB with GIN indexing** for dynamic fields. Store all UDF values in a single document column per row, avoiding relational self-joins entirely.

### 7.3 Pitfall 3: String Typing in Numeric and Financial UDFs
* **The Anti-Pattern:** Storing financial numbers as raw unvalidated strings (`"12,500.00 INR"`, `"$15000"`, `"N/A"`) inside custom fields.
* **Why it Breaks Systems:** When the aggregation engine runs `SUM(udf_values->>'custom_cost')`, the SQL cast throws a fatal runtime syntax error (`invalid input syntax for type numeric: "$15000"`), crashing portfolio dashboards.
* **The Architectural Rule:** Enforce strict typing via database `CHECK` constraints or validation triggers. Strip currency symbols and formatting; store numbers strictly as numeric floating-point values or integers.
