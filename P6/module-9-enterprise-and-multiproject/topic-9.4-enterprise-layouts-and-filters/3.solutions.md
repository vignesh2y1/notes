## 🧠 Section A: Conceptual & Architectural Principles

### Solution 1: Declarative Layouts vs. Data Mutations

#### 1. Why Mutating Entity Columns is a Fatal Anti-Pattern
Adding `is_visible` or `highlight_color` columns to the `activity` table introduces critical concurrency and data integrity breakdowns:
* **Multi-User State Pollution:** In an enterprise environment, dozens of engineers view the same project simultaneously. If User A filters for "Civil Activities" and sets `is_visible = false` on electrical activities, User B (an electrical engineer) immediately loses visibility of their own work!
* **Transactional Overhead & Lock Thrashing:** Filtering or changing bar colors would trigger thousands of SQL `UPDATE` queries, taking row-level write locks on the `activity` table and blocking background CPM schedule calculations and ERP syncs.
* **Loss of Determinism:** A project's database representation should reflect physical reality (scope, durations, dependencies, progress). Visual preferences are purely client-side projection concerns.

#### 2. The Relationship Between CPM State and Declarative Layouts
* The **CPM Schedule State** is the single source of truth: topological network graphs, baseline dates, actual dates, float values, and progress percentages.
* A **Declarative Layout** is a stateless, pure functional projection:
  $$\text{Rendered View} = \text{Layout}(\text{Project State})$$
  The layout specifies *what* to display (visible columns, sort order, color bands, timescale) and *what subset* to display (boolean filter predicates).

#### 3. Isolating Concurrent User View States
* **Zero Backend Mutex on Views:** The backend stores the project entities as read-only state during query execution.
* **Per-Session Layout State:** Each user's browser session transmits its active `layout_id` or transient filter parameters in the request headers or query parameters (`GET /api/v1/projects/:id/activities?layout_id=exec-30d`).
* The backend evaluates the filter against the data in-memory or in a parameterized SQL `WHERE` clause, returning an isolated, user-specific JSON response without mutating database state.

#### 1. Layout Scope Comparison

#### 2. Risks of Schedulers Overwriting Global Layouts
If individual schedulers can overwrite Global Layouts:
* Schedulers will modify corporate executive views to suit local daily needs (e.g., removing variance columns or adding local custom fields).
* C-suite dashboards and board reports will break or display inconsistent formats across business units.
* Enterprise reporting standards are destroyed.

#### 3. Handling Concurrent Active Sessions on Global Layout Updates
* When an administrator saves changes to a Global Layout, the server issues a cache invalidation event over Redis Pub/Sub: `PUBLISH layout_updates '{"layout_id": "lay-global-01", "version": 2}'`.
* Active Next.js client sessions receive a WebSocket notification: *"The corporate layout has been updated by the PMO."*
* The client provides a non-intrusive prompt: *"Update View"* to cleanly fetch the new column configuration without discarding unsaved user field edits.

### Solution 3: The Anatomy of Gantt Bar Necking

#### 1. What is Bar Necking?
**Bar Necking** is a visual representation technique on a Gantt chart where an activity's horizontal bar visually narrows or splits into a thin wire during calendar non-working intervals (weekends, holidays, severe weather downtime, seasonal shutdowns).

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                  GANTT BAR NECKING VISUALIZATION                                 │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   STANDARD UN-NECKED BAR (Appears continuous, conceals non-working delays):                      │
│   [██████████████████████████████████████████████████████████████████████████████████]           │
│                                                                                                  │
│   NECKED BAR (Visualizes calendar non-working periods clearly):                                  │
│   [██████████████████]──────────────────[████████████████████]──────────────────[████████]       │
│      Working Days      Monsoon Shutdown       Working Days         Sunday Break   Work Days      │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 2. How the Rendering Engine Calculates Necking
The Gantt rendering engine intersects the activity's span `[EarlyStart, EarlyFinish]` with the assigned **Calendar Workweek & Exception Intervals**. Whenever an interval corresponds to zero working hours (`hours == 0`), the bar height is reduced to 2 pixels or drawn as a dashed guideline.

#### 3. Operational Hazard of Disabling Necking
If necking is disabled:
* A 10-day concrete foundation task spanning a 30-day monsoon shutdown appears as a massive 40-day continuous effort.
* Site executives will mistakenly assume the crew is working during heavy rain or accuse the contractor of an inflated labor budget.
* Necking provides visual proof that duration extensions are caused by calendar shutdowns, not contractor inefficiency.

### Solution 4: Dynamic Rolling Variables vs. Static Temporal Filters

#### 1. Behavior Comparison: Filter A vs. Filter B
* **Filter A (Static Dates):** Hardcodes `2026-06-01` to `2026-06-15`. When the project advances to Month 2 (Data Date: 01-Jul-2026), Filter A still returns past June activities, rendering it completely useless for forward-looking operational planning.
* **Filter B (Dynamic Rolling Variable):** `Data Date` to `Data Date + 14d`. When the schedule is updated and the Data Date moves to 01-Jul-2026, the filter automatically shifts its evaluation window to `2026-07-01` through `2026-07-15`. It remains permanently accurate without manual edits.

#### 2. `Data Date` vs. `Current Date`
* **`Data Date`:** The official schedule status cutoff date up to which progress has been certified and recorded. In infrastructure projects, Data Date typically lags the real-world clock by several days or weeks while progress is compiled and audited.
* **`Current Date`:** The real-time system clock (`NOW()`).
* **Context for `Current Date`:** Used for **Daily Field Dispatch and Site Mobilization** (e.g., *"Show me all tasks that crews should be working on today according to the baseline plan, regardless of whether last month's formal billing schedule has been updated"*).

#### 3. Timezone Normalization
* If the server runs in UTC and the project is in Jodhpur, India (UTC+5:30):
* At 4:00 AM IST on July 1st, UTC is still 10:30 PM on June 30th.
* An un-normalized query using `CURRENT_DATE` would evaluate against June 30th, omitting tasks starting on July 1st.
* **Solution:** Always convert date boundaries to the project's explicit timezone before generating SQL intervals:
  `SET timezone = 'Asia/Kolkata';` or compute dates using the project's calendar offset.

### Solution 6: Compiling Filter AST to Parameterized PostgreSQL SQL

#### 1 & 2. SQL AST Compiler with SQL Injection Protection
To prevent SQL injection, field names must be whitelisted against known database columns, and all values must be passed as parameterized positional arguments (`$1`, `$2`, etc.):

```go
package layout

import (
	"errors"
	"fmt"
	"strings"
)

var allowedFields = map[string]string{
	"discipline":    "aca_disc.code_value",
	"status":        "a.status",
	"total_float":   "a.total_float",
	"early_start":   "a.early_start_date",
	"early_finish":  "a.early_finish_date",
	"activity_type": "a.activity_type",
}

type SQLCompiler struct {
	argIndex int
	args     []interface{}
}

func (c *SQLCompiler) Compile(group *FilterGroup) (string, []interface{}, error) {
	c.argIndex = 1
	c.args = make([]interface{}, 0)
	sqlClause, err := c.compileGroup(group)
	if err != nil {
		return "", nil, err
	}
	return "WHERE " + sqlClause, c.args, nil
}

func (c *SQLCompiler) compileGroup(group *FilterGroup) (string, error) {
	clauses := make([]string, 0)

	for _, pred := range group.Predicates {
		colName, allowed := allowedFields[pred.Field]
		if !allowed {
			return "", fmt.Errorf("unsupported or malicious field: %s", pred.Field)
		}

		// Handle Dynamic Date Arithmetic
		if mapVal, ok := pred.Value.(map[string]interface{}); ok {
			varName := fmt.Sprintf("%v", mapVal["variable"])
			offset := int(mapVal["offset_days"].(float64))

			var baseCol string
			if varName == "DATA_DATE" {
				baseCol = "p.data_date"
			} else {
				baseCol = "CURRENT_DATE"
			}

			var opSQL string
			switch pred.Operator {
			case CompLessThanOrEqual:
				opSQL = "<="
			case CompGreaterThanOrEqual:
				opSQL = ">="
			default:
				opSQL = "="
			}

			clauses = append(clauses, fmt.Sprintf("(%s %s (%s + INTERVAL '%d days'))", colName, opSQL, baseCol, offset))
			continue
		}

		// Standard parameterized predicate
		var opSQL string
		switch pred.Operator {
		case CompEquals:
			opSQL = "="
		case CompNotEquals:
			opSQL = "<>"
		case CompLessThanOrEqual:
			opSQL = "<="
		case CompGreaterThanOrEqual:
			opSQL = ">="
		default:
			return "", errors.New("unsupported operator")
		}

		clauses = append(clauses, fmt.Sprintf("(%s %s $%d)", colName, opSQL, c.argIndex))
		c.args = append(c.args, pred.Value)
		c.argIndex++
	}

	joinWord := " AND "
	if group.Logic == OpANY {
		joinWord = " OR "
	}

	return "(" + strings.Join(clauses, joinWord) + ")", nil
}
```

## 💻 Section C: Golang Filter AST Engine & Performance

### Solution 7: In-Memory Boolean AST Evaluation Engine

```go
package layout

import (
	"strings"
	"time"
)

type ActivityModel struct {
	Code        string
	Name        string
	Status      string
	EarlyStart  time.Time
	EarlyFinish time.Time
	TotalFloat  int
	Discipline  string
}

type FilterContext struct {
	CurrentDate time.Time
	DataDate    time.Time
}

func (fe *FilterEvaluator) EvaluateAST(act *ActivityModel, group *FilterGroup) bool {
	if len(group.Predicates) == 0 && len(group.SubGroups) == 0 {
		return true
	}

	if group.Logic == OpALL {
		for _, pred := range group.Predicates {
			if !fe.evalPredicate(act, pred) {
				return false // Short-circuit AND
			}
		}
		for _, sub := range group.SubGroups {
			if !fe.EvaluateAST(act, &sub) {
				return false
			}
		}
		return true
	}

	if group.Logic == OpANY {
		for _, pred := range group.Predicates {
			if fe.evalPredicate(act, pred) {
				return true // Short-circuit OR
			}
		}
		for _, sub := range group.SubGroups {
			if fe.EvaluateAST(act, &sub) {
				return true
			}
		}
		return false
	}

	return false
}
```

### Solution 8: Dynamic Variable Temporal Resolver

```go
package layout

import (
	"errors"
	"fmt"
	"time"
)

func ResolveDateValue(val interface{}, ctx FilterContext) (time.Time, error) {
	// Case 1: ISO8601 String
	if strVal, ok := val.(string); ok {
		t, err := time.Parse("2006-01-02", strVal)
		if err != nil {
			return time.Time{}, fmt.Errorf("failed to parse date string: %w", err)
		}
		return time.Date(t.Year(), t.Month(), t.Day(), 0, 0, 0, 0, time.UTC), nil
	}

	// Case 2: Dynamic Rolling Map
	if mapVal, ok := val.(map[string]interface{}); ok {
		varName, ok := mapVal["variable"].(string)
		if !ok {
			return time.Time{}, errors.New("missing variable in date expression")
		}

		offset := 0
		if oVal, ok := mapVal["offset_days"].(float64); ok {
			offset = int(oVal)
		}

		var base time.Time
		switch varName {
		case "DATA_DATE":
			base = ctx.DataDate
		case "CURRENT_DATE":
			base = ctx.CurrentDate
		default:
			return time.Time{}, fmt.Errorf("unsupported rolling variable: %s", varName)
		}

		res := base.AddDate(0, 0, offset)
		return time.Date(res.Year(), res.Month(), res.Day(), 0, 0, 0, 0, base.Location()), nil
	}

	return time.Time{}, errors.New("unsupported date representation")
}
```

### Solution 9: Layout Sanitizer & Schema Drift Protection

```go
package layout

type ColumnConfig struct {
	ID    string `json:"id"`
	Title string `json:"title"`
}

type GroupConfig struct {
	Field string `json:"field"`
}

type LayoutConfig struct {
	Columns []ColumnConfig `json:"columns"`
	GroupBy []GroupConfig  `json:"group_by"`
	Filter  FilterGroup    `json:"filter"`
}

func SanitizeLayout(layout *LayoutConfig, activeCodes, activeUDFs []string) *LayoutConfig {
	validFields := make(map[string]bool)
	for _, c := range activeCodes {
		validFields[c] = true
	}
	for _, u := range activeUDFs {
		validFields[u] = true
	}
	// Add core immutable fields
	validFields["code"] = true
	validFields["name"] = true
	validFields["early_start"] = true
	validFields["early_finish"] = true
	validFields["total_float"] = true
	validFields["status"] = true

	// 1. Sanitize Columns
	sanitizedCols := make([]ColumnConfig, 0)
	for _, col := range layout.Columns {
		if validFields[col.ID] {
			sanitizedCols = append(sanitizedCols, col)
		}
	}
	layout.Columns = sanitizedCols

	// 2. Sanitize GroupBy
	sanitizedGroups := make([]GroupConfig, 0)
	for _, g := range layout.GroupBy {
		if validFields[g.Field] {
			sanitizedGroups = append(sanitizedGroups, g)
		}
	}
	layout.GroupBy = sanitizedGroups

	// 3. Sanitize Filters
	layout.Filter = sanitizeFilterGroup(layout.Filter, validFields)

	return layout
}

func sanitizeFilterGroup(g FilterGroup, valid map[string]bool) FilterGroup {
	sanitizedPreds := make([]FilterPredicate, 0)
	for _, p := range g.Predicates {
		if valid[p.Field] {
			sanitizedPreds = append(sanitizedPreds, p)
		}
	}
	g.Predicates = sanitizedPreds

	sanitizedSubs := make([]FilterGroup, 0)
	for _, sub := range g.SubGroups {
		cleaned := sanitizeFilterGroup(sub, valid)
		if len(cleaned.Predicates) > 0 || len(cleaned.SubGroups) > 0 {
			sanitizedSubs = append(sanitizedSubs, cleaned)
		}
	}
	g.SubGroups = sanitizedSubs

	return g
}
```

### Solution 10: Real-World Incident — The Crashing 20,000-Row Next.js Gantt

#### 1. Next.js Virtualized Viewport Architecture
Rendering 20,000 activity DOM elements crashes browser tabs because of DOM node tree thrashing and excessive memory consumption.
* **Virtualization (Windowing) Solution:**
  1. Calculate the total scrollable height: $\text{Total Height} = \text{Row Height (32px)} \times 20,000 = 640,000\text{px}$.
  2. Maintain a scroll listener on the viewport container (e.g., container height 800px displays 25 rows).
  3. Calculate the active index range:
     $$\text{Start Index} = \max(0, \lfloor \text{scrollTop} / \text{rowHeight} \rfloor - \text{overscan})$$
     $$\text{End Index} = \min(N, \text{Start Index} + \text{visibleCount} + 2 \times \text{overscan})$$
  4. Render only the $\approx 40$ active rows positioned absolutely inside the 640,000px container using CSS `transform: translateY(index * 32px)`.
  5. The DOM holds exactly 40 elements at all times ($O(1)$ memory), guaranteeing silky smooth 60 FPS scrolling across 100,000 activities.

#### 2. Backend Streaming Pagination in Go
Instead of serializing a 20,000-row JSON array into a single 15MB HTTP response string:
* Implement **Cursor-based Keyspace Pagination**:
  `GET /api/v1/projects/:id/activities?limit=100&cursor=ACT_1050`
* Or stream chunks using HTTP/2 Server-Sent Events (SSE) or chunked JSON arrays:

```go
func StreamActivities(w http.ResponseWriter, r *http.Request, db *sql.DB) {
	w.Header().Set("Content-Type", "application/x-ndjson")
	w.WriteHeader(http.StatusOK)

	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "streaming unsupported", http.StatusInternalServerError)
		return
	}

	rows, _ := db.QueryContext(r.Context(), "SELECT json_build_object('id', id, 'code', code) FROM activity ORDER BY sort_order")
	defer rows.Close()

	for rows.Next() {
		var jsonChunk []byte
		rows.Scan(&jsonChunk)
		w.Write(jsonChunk)
		w.Write([]byte("\n"))
		flusher.Flush()
	}
}
```
This reduces server memory allocation to near zero and allows the Next.js client to begin rendering the first 50 rows within 15 milliseconds.
