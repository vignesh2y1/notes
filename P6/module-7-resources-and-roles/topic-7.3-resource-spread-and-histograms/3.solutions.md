## 🧠 Section A: Conceptual & Analytical Principles

### Solution 1: The Fallacy of Average Allocation

#### 1. The Fatal Mathematical Flaw
The project director divided total man-hours ($144,000$) uniformly across the total project duration ($360\text{ days}$):
$$\text{Average Demand} = \frac{144,000\text{ hrs}}{360\text{ days} \times 8\text{ hrs/day}} = 50\text{ electricians}$$
This calculation assumes a flat, horizontal demand curve from Day 1 to Day 360. In industrial engineering, resource requirements follow a bell-shaped distribution:
* Early months (site preparation, access roads): Minimal electrical work ($\approx 5\text{ to } 10\text{ electricians}$).
* Peak construction months (DC string cabling, inverter skid termination): High concurrent demand ($\approx 120\text{ to } 150\text{ electricians}$).
* Closeout months (testing and punch-listing): Tapering demand ($\approx 15\text{ to } 20\text{ electricians}$).

#### 2. Consequences During Peak Cabling Phase (Months 6 to 8)
When demand reaches 130 electricians in Month 7, the 60-bed camp can only house less than half the required workforce. The contractor faces a severe dilemma:
* Refuse additional workers $\rightarrow$ Cabling falls 50% behind schedule, triggering critical path delay.
* House workers in unauthorized, unsafe off-site conditions $\rightarrow$ Safety and regulatory violations, worker strikes, health hazards in 48°C desert summer.

#### 3. Highway Bridge Weight Limit Analogy
A bridge designed for an average annual traffic weight of 10 tons per hour will collapse if a single 80-ton crane drives across it. In civil engineering and project controls, systems are sized to withstand **peak instantaneous loading**, never average loads.

### Solution 2: The Early vs Late Date Envelope (The Banana Curve)

#### 1. Definitions
* **Early Resource Profile:** The time-phased distribution of resource hours/costs assuming every activity starts at the earliest possible instant allowed by network logic (**Early Start - ES**).
* **Late Resource Profile:** The time-phased distribution assuming every activity is deferred to its latest possible instant (**Late Start - LS**) without postponing the contractual project completion date.

#### 2. Why It Forms a "Banana Curve"
* Both early and late cumulative curves start at $(0, 0\%)$ on Day 1 and converge to $(T_{\text{finish}}, 100\%)$ at project completion.
* Because early dates execute work sooner, the Early S-curve sits above and to the left.
* The Late S-curve sits below and to the right.
* The physical space between them is created by **Total Float** across non-critical paths, forming the characteristic curved silhouette of a banana.

#### 3. Interpretation of Actual Progress Relative to the Envelope
* **To the Left of Early Curve:** **Super-optimal / Ahead of Plan.** Work is being accomplished faster than the most aggressive theoretical schedule.
* **Inside the Envelope:** **Healthy & Feasible.** Non-critical tasks are absorbing available float, but the project is contractually on schedule.
* **To the Right of Late Curve:** **Critical Delay.** Activities have exceeded all allowable total float. The contractual completion milestone has slipped, exposing the contractor to Delay Damages.

### Solution 3: Stacked Histograms vs Composite Curves

#### 1. Fundamental Difference
* **Stacked Histogram:** A bar chart showing **period-by-period (discrete) resource burn rates** (units/day or units/month), broken down by trade.
* **Cumulative S-Curve:** A continuous line chart showing **accumulated work or spend** from Day 0 to the current status date ($\sum \text{Units}$).

#### 2. Identifying Trade-Specific Bottlenecks
An aggregated man-hour curve might show 250 total men/day against a 350-man camp limit, suggesting zero issues. However, a stacked histogram reveals:
* Civil: 30 men
* Mechanical: 40 men
* Electrical: **180 men** (against an electrical trade subcontract limit of 100 certified cable technicians).
The total is safe, but the electrical discipline has exceeded its capacity by 80 men, creating an invisible fatal bottleneck.

### Solution 4: The Mathematical Over-Allocation Threshold

#### 1. Daily Demand Equation
$$\text{Daily Demand}_R(t) = \sum_{i=1}^{N} \text{Units}_{i, R}(t)$$

#### 2. Over-Allocation Equation
$$\text{OverAllocation}_R(t) = \max\left(0, \; \text{Daily Demand}_R(t) - \text{Max Availability}_R(t)\right)$$

#### 3. Operational Consequences of Crane Over-Allocation
If an over-allocation of 2 heavy crawler cranes is ignored:
* Both subcontractor crews mobilize to their respective inverter stations expecting a crane.
* Only one crane is physically on site. One crew stands idle while the crane works elsewhere.
* Subcontractors log daily standing-time claims (₹1,50,000/day per idle crew).
* CPM calculations in the computer assume parallel execution, but field work executes sequentially—causing unexpected schedule slips.

#### 2. Peak Demand and Over-Allocation
* **Peak Demand:** **5 Rigs** on 03-May, 04-May, and 05-May.
* **Over-Allocation:** **1 Rig over capacity** on each of those 3 days ($5 - 4 = 1\text{ rig}$).

#### 3. Commercial Financial Risk Analysis
* If Task B cannot start without the 2nd rig, 1 crew stands idle for 3 days:
  $$\text{Idle Standing Cost} = 3\text{ days} \times ₹75,000 = ₹2,25,000$$
* If the delay pushes the overall substation connection date past COD by 3 days:
  $$\text{Liquidated Damages} = 3\text{ days} \times ₹5,00,000/\text{day} = ₹15,00,000$$
* **Total Exposure:** **₹17,25,000**. Running resource leveling to delay Task B to 06-May (if it has float) eliminates this risk at zero cost!

### Solution 6: Labor Camp Capacity Breaches

#### 1. Aggregate Daily Labor Demand in Month 6
$$\text{Total Demand} = 80\text{ (Civil)} + 140\text{ (Tracker)} + 60\text{ (Inverter)} + 110\text{ (Cabling)} = 390\text{ workers}$$

#### 2. Camp Deficit
$$\text{Deficit} = 390\text{ workers} - 350\text{ camp capacity} = 40\text{ workers over capacity}$$

#### 3. Two Scheduling Interventions Without Extending COD
1. **Shift Floating Non-Critical Activities:**
   Check total float on `33kV Cable Trenching` (110 workers). If it possesses $\ge 30\text{ days}$ of total float, delay its start to Month 7 when Civil Foundations (80 workers) finish and demobilize.
2. **Compress Daily Shift & Add Night Shift for Off-Peak Tasks:**
   If permitted, split the 140 tracker assembly workers into two non-overlapping 70-worker shifts (Morning and Late Evening), allowing hot-bunking or shared facility rotation if sanitation permits allow.

### Solution 7: Zero-Duration Milestone Material Delivery Spreading

#### 1. Runtime Error
$$\text{DailyRate} = \frac{\text{TotalUnits}}{\text{Duration}} = \frac{40,000}{0} \rightarrow \text{Division by Zero!}$$
In Go, this results in a runtime panic (`divide by zero` in integer arithmetic) or `+Inf` in floating-point operations.

#### 2. Engine Mitigation
The spreading engine must check if `Duration == 0`:
```go
if task.Duration == 0 || task.Type == FinishMilestone {
    // Allocate 100% of material units directly to the milestone date timestamp
    buckets[milestoneDateIndex].MaterialUnits += assignment.TotalUnits
    return
}
```

## 💻 Section C: SQL & Backend Engine Engineering

### Solution 8: PostgreSQL Daily Bucketization with `generate_series`

```sql
WITH dates AS (
    SELECT generate_series(
        '2026-06-01'::DATE, 
        '2026-06-30'::DATE, 
        '1 day'::INTERVAL
    )::DATE AS cal_date
)
SELECT 
    d.cal_date,
    r.rsrc_code,
    r.rsrc_name,
    SUM(tr.target_qty / NULLIF(tr.target_drtn_hr / 8.0, 0)) AS daily_hours,
    8.0 AS max_capacity_hours,
    ROUND(SUM(tr.target_qty / NULLIF(tr.target_drtn_hr / 8.0, 0)) - 8.0, 2) AS over_allocated_hours
FROM task_rsrc tr
JOIN rsrc r ON tr.rsrc_id = r.rsrc_id
CROSS JOIN dates d
WHERE r.rsrc_code = 'R-EQP-CRANE-100T'
  AND d.cal_date >= tr.target_start::DATE
  AND d.cal_date <= tr.target_end::DATE
GROUP BY d.cal_date, r.rsrc_code, r.rsrc_name
HAVING SUM(tr.target_qty / NULLIF(tr.target_drtn_hr / 8.0, 0)) > 8.0
ORDER BY d.cal_date;
```

### Solution 9: Multi-Trade Stacked Aggregation Query

```sql
WITH project_days AS (
    SELECT generate_series(
        '2026-01-01'::DATE, 
        '2026-12-31'::DATE, 
        '1 day'::INTERVAL
    )::DATE AS calendar_date
)
SELECT 
    pd.calendar_date,
    COALESCE(SUM(CASE WHEN r.rsrc_type = 'RT_Labor' THEN tr.target_qty / (tr.target_drtn_hr / 8.0) END), 0) AS labor_hours,
    COALESCE(SUM(CASE WHEN r.rsrc_type = 'RT_NonLabor' THEN tr.target_qty / (tr.target_drtn_hr / 8.0) END), 0) AS non_labor_hours,
    COALESCE(SUM(CASE WHEN r.rsrc_type = 'RT_Mat' THEN tr.target_qty / (tr.target_drtn_hr / 8.0) END), 0) AS material_units
FROM project_days pd
LEFT JOIN task_rsrc tr 
  ON pd.calendar_date >= tr.target_start::DATE 
 AND pd.calendar_date <= tr.target_end::DATE
LEFT JOIN rsrc r ON tr.rsrc_id = r.rsrc_id
GROUP BY pd.calendar_date
ORDER BY pd.calendar_date;
```

### Solution 10: Next.js JSON API Time-Phased Formatter in Go

```go
package main

import (
	"encoding/json"
	"fmt"
)

type ResourceAllocationBucket struct {
	Date            string  `json:"date"`
	EarlyUnits      float64 `json:"early_units"`
	LateUnits       float64 `json:"late_units"`
	CumEarlyUnits   float64 `json:"cum_early_units"`
	CumLateUnits    float64 `json:"cum_late_units"`
	MaxCapacity     float64 `json:"max_capacity"`
	IsOverAllocated bool    `json:"is_over_allocated"`
	OverAllocation  float64 `json:"over_allocation"`
}

type ChartPayload struct {
	TotalEarlyUnits float64                    `json:"total_early_units"`
	PeakDemand      float64                    `json:"peak_demand"`
	PeakDate        string                     `json:"peak_date"`
	HasOverAlloc    bool                       `json:"has_over_allocation"`
	TimeSeries      []ResourceAllocationBucket `json:"time_series"`
}

// FormatResourceHistogramJSON serializes buckets for Next.js frontend charts.
func FormatResourceHistogramJSON(buckets []ResourceAllocationBucket) ([]byte, error) {
	payload := ChartPayload{
		TimeSeries: buckets,
	}

	for _, b := range buckets {
		if b.EarlyUnits > payload.PeakDemand {
			payload.PeakDemand = b.EarlyUnits
			payload.PeakDate = b.Date
		}
		if b.IsOverAllocated {
			payload.HasOverAlloc = true
		}
	}
	if len(buckets) > 0 {
		payload.TotalEarlyUnits = buckets[len(buckets)-1].CumEarlyUnits
	}

	return json.MarshalIndent(payload, "", "  ")
}

func main() {
	sampleBuckets := []ResourceAllocationBucket{
		{
			Date:            "2026-05-01",
			EarlyUnits:      24.0,
			LateUnits:       16.0,
			CumEarlyUnits:   24.0,
			CumLateUnits:    16.0,
			MaxCapacity:     32.0,
			IsOverAllocated: false,
			OverAllocation:  0.0,
		},
		{
			Date:            "2026-05-02",
			EarlyUnits:      40.0,
			LateUnits:       24.0,
			CumEarlyUnits:   64.0,
			CumLateUnits:    40.0,
			MaxCapacity:     32.0,
			IsOverAllocated: true,
			OverAllocation:  8.0,
		},
	}

	output, err := FormatResourceHistogramJSON(sampleBuckets)
	if err != nil {
		panic(err)
	}
	fmt.Println(string(output))
}
```
