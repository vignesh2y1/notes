## 1. Executive Summary & The Core Mental Model

### 1.1 The Fallacy of Average Allocation
In novice project management, resource requirements are computed using simple project-wide averages:
* *"We have 120,000 man-hours of electrical installation across a 10-month (300-day) construction period."*
* *"Therefore, we need an average of $\frac{120,000}{300 \times 8} = 50\text{ electricians}$ on site."*

In industrial project controls, this mathematical simplification is known as the **Fallacy of Average Allocation**:


> **The Capacity Axiom:**  
> A bridge does not collapse under the *average* weight of traffic over a year; it collapses under the *peak axle load* during rush hour. Similarly, a project does not fail on *average* man-hours; it fails when peak daily demand exceeds camp capacity, crane availability, or site physical space.

### 1.2 Plain-English Intuition: The Water Reservoir & Spillway
To understand time-phasing intuitively:
* **Total Units (Work):** The total volume of water stored behind a dam (e.g., 100,000 acre-feet).
* **Duration:** The number of days the reservoir release gates are opened.
* **Histogram (Daily Spread):** The water flow rate (cubic feet per second) discharging through the spillway on each individual day.
* **Capacity Limit:** The maximum riverbank capacity downstream before flooding occurs.

If you release the entire reservoir uniformly, the downstream river handles the flow comfortably. But if you open all sluice gates simultaneously during Week 24 because multiple activities are scheduled concurrently, the river floods its banks—creating site congestion, safety violations, labor accommodation shortages, and equipment gridlock.

## 2. Time-Phased Resource Distribution Algorithms

Time-phasing is the computational process of taking discrete activity assignments and projecting them across uniform temporal slices (daily, weekly, or monthly buckets).

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                             TIME-PHASED BUCKETIZATION WORKFLOW                                   │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  1. CPM Early/Late Dates Calculation ──► Early Start (ES), Early Finish (EF), Late Dates         │
│                                                                                                  │
│  2. Daily Working Slot Identification ──► Intersect with Resource / Activity Working Shifts      │
│                                                                                                  │
│  3. Spread Profile Application        ──► Apply Linear Rate or 21-Point Curve (Topic 7.2)        │
│                                                                                                  │
│  4. Bucket Aggregation                ──► Sum across all active assignments for Day t:           │
│                                           Total_Demand(t) = ∑ Resource_Usage_i(t)                │
│                                                                                                  │
│  5. Cumulative Profile Generation     ──► Cum_Demand(T) = ∑ Total_Demand(t) (t = 1 to T)         │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 2.1 The Daily Bucketization Formula
For any single resource $R$ across $N$ overlapping activities on calendar day $t$:

$$\text{Daily Demand}_R(t) = \sum_{i=1}^{N} \text{Units}_{i, R}(t)$$

Where $\text{Units}_{i, R}(t)$ is zero if day $t$ is non-working for activity $i$ or falls outside the interval $[\text{Start}_i, \text{Finish}_i]$.

### 3.2 The Early vs Late Envelope (The Resource Banana Curve)
Every project with positive total float has two distinct resource deployment schedules:
1. **Early Resource Profile:** Assumes all activities start on their **Early Start (ES)** dates.
   * Work starts aggressively as soon as possible.
   * Cash burn and resource mobilization happen early.
2. **Late Resource Profile:** Assumes all activities are delayed to their **Late Start (LS)** dates.
   * Work is deferred until the last possible moment without delaying the contractual finish date.
   * Cash burn and resource mobilization are back-loaded.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                         THE RESOURCE BANANA CURVE (EARLY VS LATE ENVELOPE)                       │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  Cumulative % Units (S-Curve)                                                                    │
│  100% ┼                                                  ╭──────────────── Early Curve (ES)      │
│       │                                         ╭────────╯                                       │
│   80% ┼                                 ╭───────╯          ╭────────────── Late Curve (LS)       │
```

## 4. Peak Demand Analysis & Over-Allocation Detection

### 4.1 Identifying Threshold Breaches
An over-allocation occurs when the aggregate demand for a resource exceeds its declared maximum capacity during any working time bucket:

$$\text{OverAllocation}_R(t) = \max\left(0, \; \text{Daily Demand}_R(t) - \text{Max Availability}_R(t)\right)$$

```text

│                            OVER-ALLOCATION THRESHOLD IDENTIFICATION                              │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤

│  Piling Rigs                                                                                     │
│    6 ┼                                 ┌───┐                                                     │
│    5 ┼                                 │ ! │ ◄── OVER-ALLOCATION: 2 Rigs Over Capacity!          │
```

## 5. Enterprise PostgreSQL Time-Bucket Aggregation Query

The following SQL query demonstrates how to generate a complete daily time-phased resource histogram using PostgreSQL's `generate_series`, handling calendar workdays, daily rate distribution, and flagging over-allocations.

```sql
-- ============================================================================
-- MODULE 7.3: TIME-PHASED DAILY RESOURCE HISTOGRAM QUERY
-- ============================================================================

WITH RECURSIVE 
-- 1. Generate Daily Calendar Grid for Project Lifecycle
project_dates AS (
    SELECT generate_series(
        '2026-05-01'::DATE, 
        '2026-05-31'::DATE, 
        '1 day'::INTERVAL
    )::DATE AS calendar_date
),

-- 2. Expand Task Resource Assignments Across Their Working Intervals
assignment_spread AS (
    SELECT 
        tr.task_rsrc_id,
        tr.task_id,
        tr.rsrc_id,
        r.rsrc_code,
        r.rsrc_name,
        r.rsrc_type,
        r.max_qty_per_hr * 8.0 AS daily_capacity, -- Max 8-hr day capacity
        pd.calendar_date,
        -- Check if day is non-working (e.g. Sunday = 0)
        CASE 
            WHEN EXTRACT(DOW FROM pd.calendar_date) = 0 THEN 0.0
            ELSE (tr.target_qty / NULLIF(tr.target_drtn_hr / 8.0, 0)) -- Linear Daily Spread
        END AS daily_allocated_units
    FROM task_rsrc tr
    JOIN rsrc r ON tr.rsrc_id = r.rsrc_id
    CROSS JOIN project_dates pd
    WHERE pd.calendar_date >= tr.target_start::DATE
      AND pd.calendar_date <= tr.target_end::DATE
)

-- 3. Aggregate Daily Demand and Detect Over-Allocations
SELECT 
    asgn.calendar_date,
    TO_CHAR(asgn.calendar_date, 'Dy, DD-Mon-YYYY') AS formatted_date,
    asgn.rsrc_code,
    asgn.rsrc_name,
    asgn.rsrc_type,
    asgn.daily_capacity,
    ROUND(SUM(asgn.daily_allocated_units), 2) AS total_daily_demand,
    CASE 
        WHEN SUM(asgn.daily_allocated_units) > asgn.daily_capacity 
        THEN ROUND(SUM(asgn.daily_allocated_units) - asgn.daily_capacity, 2)
        ELSE 0.00 
    END AS over_allocated_units,
    CASE 
        WHEN SUM(asgn.daily_allocated_units) > asgn.daily_capacity THEN 'OVER_ALLOCATED'
        WHEN SUM(asgn.daily_allocated_units) = 0 THEN 'IDLE'
        ELSE 'OPTIMAL'
    END AS allocation_status
FROM assignment_spread asgn
GROUP BY 
    asgn.calendar_date, 
    asgn.rsrc_code, 
    asgn.rsrc_name, 
    asgn.rsrc_type, 
    asgn.daily_capacity
ORDER BY 
    asgn.rsrc_code, 
    asgn.calendar_date;
```

## 6. Production Go Time-Phased Aggregator Engine

Below is a complete, production-grade Go engine that:
1. Bucketizes multiple overlapping activities into daily temporal buckets.
2. Generates both **Early Dates** and **Late Dates** cumulative curves.
3. Identifies peak resource demand and over-allocations.
4. Serializes the payload into clean JSON for Next.js charts.

```go
package main

import (
	"encoding/json"
	"fmt"
	"math"
	"time"
)

// ResourceAllocationBucket represents one time-slice bucket in the histogram.
type ResourceAllocationBucket struct {
	Date            string  `json:"date"`
	EarlyUnits      float64 `json:"early_units"`
	LateUnits       float64 `json:"late_units"`
	CumEarlyUnits   float64 `json:"cum_early_units"`
	CumLateUnits    float64 `json:"cum_late_units"`
	MaxCapacity     float64 `json:"max_capacity"`
	IsOverAllocated bool    `json:"is_over_allocated"`
	OverAllocation  float64 `json:"over_allocation"`
}

// AssignmentDetail defines task schedule boundaries and resource demand.
type AssignmentDetail struct {
	TaskCode   string
	EarlyStart time.Time
	EarlyEnd   time.Time
	LateStart  time.Time
	LateEnd    time.Time
	TotalUnits float64
}

// ResourceProfileEngine computes time-phased distributions.
type ResourceProfileEngine struct {
	MaxDailyCapacity float64
}

func NewResourceProfileEngine(maxCapacity float64) *ResourceProfileEngine {
	return &ResourceProfileEngine{MaxDailyCapacity: maxCapacity}
}

// GenerateProfile computes daily buckets and cumulative S-curves.
func (e *ResourceProfileEngine) GenerateProfile(
	startDate time.Time,
	endDate time.Time,
	assignments []AssignmentDetail,
) ([]ResourceAllocationBucket, error) {

	numDays := int(endDate.Sub(startDate).Hours()/24) + 1
	buckets := make([]ResourceAllocationBucket, numDays)

	// Initialize buckets
	curr := startDate
	for i := 0; i < numDays; i++ {
		buckets[i] = ResourceAllocationBucket{
			Date:        curr.Format("2006-01-02"),
			MaxCapacity: e.MaxDailyCapacity,
		}
		curr = curr.AddDate(0, 0, 1)
	}

	// Helper to spread units linearly across a working date range
	spreadUnits := func(asgn AssignmentDetail, start, end time.Time, isEarly bool) {
		taskDays := int(end.Sub(start).Hours()/24) + 1
		if taskDays <= 0 {
			return
		}
		dailyRate := asgn.TotalUnits / float64(taskDays)

		offset := int(start.Sub(startDate).Hours() / 24)
		for d := 0; d < taskDays; d++ {
			idx := offset + d
			if idx >= 0 && idx < numDays {
				if isEarly {
					buckets[idx].EarlyUnits += dailyRate
				} else {
					buckets[idx].LateUnits += dailyRate
				}
			}
		}
	}

	// Process all assignments
	for _, asgn := range assignments {
		spreadUnits(asgn, asgn.EarlyStart, asgn.EarlyEnd, true)
		spreadUnits(asgn, asgn.LateStart, asgn.LateEnd, false)
	}

	// Calculate cumulative values and flag over-allocations
	cumEarly := 0.0
	cumLate := 0.0

	for i := 0; i < numDays; i++ {
		b := &buckets[i]
		b.EarlyUnits = math.Round(b.EarlyUnits*100) / 100
		b.LateUnits = math.Round(b.LateUnits*100) / 100

		cumEarly += b.EarlyUnits
		cumLate += b.LateUnits

		b.CumEarlyUnits = math.Round(cumEarly*100) / 100
		b.CumLateUnits = math.Round(cumLate*100) / 100

		if b.EarlyUnits > e.MaxDailyCapacity {
			b.IsOverAllocated = true
			b.OverAllocation = math.Round((b.EarlyUnits-e.MaxDailyCapacity)*100) / 100
		}
	}

	return buckets, nil
}

func main() {
	// Surya Solar: Piling Rig Fleet (Max Capacity = 4 Rigs = 32 machine-hrs/day)
	engine := NewResourceProfileEngine(32.0)

	start := time.Date(2026, time.May, 1, 0, 0, 0, 0, time.UTC)
	end := time.Date(2026, time.May, 10, 0, 0, 0, 0, time.UTC)

	// Two overlapping piling tasks
	tasks := []AssignmentDetail{
		{
			TaskCode:   "PILE-BLOCK-01",
			EarlyStart: time.Date(2026, time.May, 1, 0, 0, 0, 0, time.UTC),
			EarlyEnd:   time.Date(2026, time.May, 5, 0, 0, 0, 0, time.UTC),
			LateStart:  time.Date(2026, time.May, 3, 0, 0, 0, 0, time.UTC),
			LateEnd:    time.Date(2026, time.May, 7, 0, 0, 0, 0, time.UTC),
			TotalUnits: 120.0, // 24 hrs/day (3 rigs)
		},
		{
			TaskCode:   "PILE-BLOCK-02",
			EarlyStart: time.Date(2026, time.May, 3, 0, 0, 0, 0, time.UTC),
			EarlyEnd:   time.Date(2026, time.May, 8, 0, 0, 0, 0, time.UTC),
			LateStart:  time.Date(2026, time.May, 5, 0, 0, 0, 0, time.UTC),
			LateEnd:    time.Date(2026, time.May, 10, 0, 0, 0, 0, time.UTC),
			TotalUnits: 96.0, // 16 hrs/day (2 rigs)
		},
	}

	profile, _ := engine.GenerateProfile(start, end, tasks)

	fmt.Println("--- TIME-PHASED RESOURCE HISTOGRAM & PEAK ANALYSIS ---")
	for _, b := range profile {
		status := "OK "
		if b.IsOverAllocated {
			status = "OVER-ALLOCATED!"
		}
		fmt.Printf("Date: %s | Early: %5.1f hrs | CumEarly: %6.1f | Capacity: %4.1f | Status: %s\n",
			b.Date, b.EarlyUnits, b.CumEarlyUnits, b.MaxCapacity, status)
	}

	// Serialize to JSON for Next.js Recharts
	jsonData, _ := json.MarshalIndent(profile[:3], "", "  ")
	fmt.Printf("\nSample JSON Output for Next.js UI:\n%s\n", string(jsonData))
}
```

## 7. Real-World Pitfalls & Production Edge Cases

### 7.1 The "End-of-Month Spike" Artifact
* **The Cause:** When aggregating daily time-spread data into monthly reporting buckets, calendar months have varying lengths (28, 30, 31 days). 
* **The Artifact:** A 31-day month appears to have higher resource demand than a 28-day month even if the daily work intensity was identical.
* **Remedy:** Normalize monthly reporting by displaying **Average Units per Working Day** rather than raw monthly sums when comparing month-over-month performance.

### 7.2 Zero-Duration Milestones with Material Deliveries
* **The Bug:** A scheduler assigns 40,000 PV modules to a zero-duration milestone `ACT-DELIV-01` (*"Delivery of Batch 1 Modules"*).
* **Division by Zero:** When a daily spreading algorithm executes `DailyRate = TotalUnits / Duration`, dividing by $D = 0$ causes a panic or `NaN`.
* **Fix:** The spreading engine must detect milestones ($D = 0$) and allocate 100% of material units directly to the milestone date timestamp without dividing by duration.
