# Topic 7.1: Roles vs Resources — The Enterprise Staffing & Allocation Engine

## 1. Executive Summary & The Core Mental Model

### 1.1 The Planning Phase Fallacy: The Named-Individual Trap
In naive project management and consumer-grade scheduling tools (such as basic kanban boards or spreadsheets), schedulers assign specific named individuals to activities months or years before construction begins:
* *"Arun Kumar will conduct 220kV Bay Pre-Commissioning on 12-Nov-2026."*
* *"Hydraulic Piling Rig #02 will drill Foundation Holes in Inverter Block 04 on 15-May-2026."*

On a multi-year industrial megaproject—such as the **Surya 100MW Solar IPP Project in Rajasthan, India**—this practice is catastrophic:
1. **Attrition & Turnover:** Over an 18-month engineering, procurement, and construction (EPC) cycle, engineers resign, subcontractors change, and specific machinery undergoes unscheduled maintenance.
2. **Premature Commitment:** Committing named individuals during the tender/bid stage inflates administrative overhead and creates false precision.
3. **Capacity Obfuscation:** You cannot answer the fundamental executive question: *"Do we have the organizational trade capability (e.g., certified High-Voltage Testing Engineers) to take on a second 100MW solar park next quarter?"* when all assignments are hardcoded to specific employee IDs.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                 THE NAMED-INDIVIDUAL TRAP                                        │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  TENDER / FEASIBILITY PHASE (Day -180):                                                          │
│  Naively assigned: "Arun Kumar" (Lead Commissioning Engineer)                                    │
│  [Activity: 220kV Transformer Testing ── 15-Nov-2026]                                            │
│                                                                                                  │
│  EXECUTION PHASE (Day +240):                                                                     │
│  * Arun Kumar resigned in Month 4 to join a green hydrogen developer.                            │
│  * Project database has 450 activities hardcoded to Arun Kumar's user ID.                        │
│  * Global resource queries fail: System shows negative capacity for an employee no longer there. │
│  * Executive capacity planning breaks across all concurrent bids.                                │
│                                                                                                  │
│  ENTERPRISE SEPARATION (The Solution):                                                           │
│  1. Plan with ROLES (Generic Skill Pools / Trades) during Phase 1-3.                             │
│  2. Staff with RESOURCES (Named Humans, Rigs, Materials) during Lookahead / Mobilization.        │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

> **The Enterprise Axiom:**  
> A **Role** represents **demand for a capability** (what trade, skill level, or equipment classification is required). A **Resource** represents the **supply of capacity** (who or what specific asset delivers the work). You must decouple the *demand contract* from the *fulfillment entity*.

### 1.2 Plain-English Intuition: Interfaces vs Concrete Implementations
If you are a software engineer building backend systems in Go, the separation between Roles and Resources is identical to the separation between an **interface** and a **concrete struct**:

```text

│                             INTERFACES VS CONCRETE IMPLEMENTATIONS                               │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤

│  ┌───────────────────────────────────────────────────┐                                           │
│  │ type TransformerTester interface {                │  ◄─── THE ROLE (Contract/Demand)          │
│  │     ExecuteHiPotTest(kv float64) (Result, error)  │       Generic capability requirement      │
│  │ }                                                 │                                           │
│  └─────────────────────────┬─────────────────────────┘                                           │
│                            │ Implemented By                                                      │

│             ▼                             ▼                                                      │
│  ┌───────────────────────┐   ┌────────────────────────┐                                          │
│  │ type ArunKumar struct │   │ type PriyaNair struct  │ ◄─── THE RESOURCES (Supply/Instances)    │
│  │ Rate: ₹3,500/hr       │   │ Rate: ₹4,200/hr        │      Named, instantiated actors          │
│  └───────────────────────┘   └────────────────────────┘                                          │

│  │ Standard Rate: ₹3,000/hr                          │       Used for early estimation           │
│  └─────────────────────────┬─────────────────────────┘                                           │
│                            │ Staffed By                                                          │
│             ┌──────────────┴──────────────┐                                                      │
│             ▼                             ▼                                                      │
│  ┌───────────────────────┐   ┌────────────────────────┐                                          │
│  │ Resource: Arun Kumar  │   │ Resource: Priya Nair   │ ◄─── THE RESOURCES (Named Entities)      │
│  │ Resource ID: R-ENG-09 │   │ Resource ID: R-ENG-14  │      Assigned when mobilizing            │
│  └───────────────────────┘   └────────────────────────┘                                          │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

When writing clean Go code, your high-level business logic accepts an interface (`TransformerTester`). You do not care whether the runtime injects `ArunKumar` or `PriyaNair`, so long as the contract is satisfied. Only when you wire up dependency injection at startup do you bind the concrete instance.

Similarly, in Primavera P6:
* **Roles** allow engineering and project controls teams to schedule and cost activities without knowing which specific humans or subcontractor machines will be on site.
* **Resources** bind real-world humans, heavy equipment, or materials to those roles when mobilization dates approach.

## 2. The Taxonomy of Roles in Primavera P6

### 2.1 Role Hierarchies and Skill Pools
Roles are organized in an enterprise-level tree structure (Enterprise Project Structure / EPS style). Every role has:
1. **Role ID & Role Name:** Unique identifier (e.g., `CIVIL-PILING-OP`, `Civil Piling Rig Operator`).
2. **Parent Role:** Hierarchical roll-up for organizational reporting.
3. **Default Role Rate:** A baseline commercial cost (e.g., ₹2,500/hr) used for budget cost estimation before specific individuals or vendors are assigned.
4. **Competency Levels:** P6 supports 5 competency levels (1-Master, 2-Expert, 3-Proficient, 4-Competent, 5-Novice), allowing matching based on technical capability.

### 2.2 Primary Role Assignment and Role-to-Resource Mapping
In Primavera P6, a resource can possess multiple roles, and an activity can be staffed through a structured assignment workflow:
* **Resource Multi-Role Assignment:** Arun Kumar might be qualified as both `ENG-ELEC-HV` (Primary Role) and `ENG-ELEC-SCADA` (Secondary Role).
* **The Primary Role Flag:** When calculating project-wide role usage curves, P6 checks the `is_primary` flag on the resource-role relationship to avoid double-counting corporate headcount.
* **Role Staffing Workflow:**
  1. **Phase 1 (Baseline Schedule):** The activity `ACT-SUB-102` (*"Pre-Commissioning Testing of 220kV GIS Switchgear"*) is assigned the role `ENG-ELEC-HV` with 80 Budgeted Units (hours). Cost = $80 \times ₹4,500 = ₹3,60,000$.
  2. **Phase 2 (Two-Week Lookahead):** The Project Controls Manager runs the "Assign Resource by Role" wizard. P6 filters the resource pool for active resources matching `ENG-ELEC-HV` with Competency $\ge 2$.
  3. **Phase 3 (Binding):** Arun Kumar (`R-ENG-09`, actual rate ₹4,800/hr) is selected. The role remains attached as the design intent, but Arun Kumar is now the active driving resource. The forecast cost recalculates to $80 \times ₹4,800 = ₹3,84,000$, producing an immediate ₹24,000 rate variance!

## 3. The Three Resource Types in Primavera P6

Primavera P6 classifies all physical, operational, and material inputs into exactly **three fundamental resource types**. This classification dictates how the scheduling engine applies calendars, calculates costs, and accumulates units.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                         THE THREE PRIMAVERA P6 RESOURCE TYPES                                    │
├──────────────────────────┬──────────────────────────┬────────────────────────────────────────────┤
│ Resource Type            │ Unit of Measure (UOM)    │ Driving Calendars & Engine Behavior        │
├──────────────────────────┼──────────────────────────┼────────────────────────────────────────────┤
│ 1. LABOR                 │ Time / Hours             │ Bound to working shifts & human limits.    │
│    (Trades, Engineers,   │ (e.g., Man-hours,        │ Subject to overtime rates, labor laws.     │
│     Operators, Helpers)  │  Person-days)            │ Drives activity duration if Resource-Dep.  │
├──────────────────────────┼──────────────────────────┼────────────────────────────────────────────┤
│ 2. NON-LABOR             │ Time / Hours             │ Bound to mechanical shifts & maintenance.  │
│    (Cranes, Rigs,        │ (e.g., Machine-hours,    │ Hourly wear/tear, fuel & operator costs.   │
│     Excavators, Gensets) │  Equipment-days)         │ Distinct from the humans operating them.   │
├──────────────────────────┼──────────────────────────┼────────────────────────────────────────────┤
│ 3. MATERIAL              │ Physical Quantity Units  │ NO CALENDAR DURATION. Consumed in physical │
│    (Solar Panels, Steel, │ (e.g., Watts, Pieces,    │ units (m³, metric tons, units). Time-      │
│     Concrete, Inverters) │  m³, MT, Linear Meters)  │ spread driven strictly by activity dates.  │
└──────────────────────────┴──────────────────────────┴────────────────────────────────────────────┘
```

### 3.1 Labor Resources: The Human Factor
Labor resources represent human physical and intellectual effort:
* **Calendar Dependency:** Humans cannot work 24/7. In Rajasthan, peak summer temperatures force a split shift: 06:00 to 11:00, and 16:00 to 19:00 (8 hours total), avoiding the 11:00–16:00 extreme heat window.
* **Overtime Rules:** P6 provides distinct parameters for `Cost per Unit` (Standard Rate) and `Overtime Cost per Unit` (`cost_per_qty_ot`). Overtime hours can be tracked against separate budgets.
* **Max Units / Time:** Defines availability. If Surya Solar has a crew of 10 certified DC string electricians, the resource pool limit is $10 \times 8\text{ h/d} = 80\text{ h/d}$ (or 1000% in P6 percentage notation).

### 3.2 Non-Labor Resources: Heavy Plant & Machinery
Non-Labor resources represent capital equipment, mobile plants, and heavy machinery:
* **The "Machine vs Operator" Separation:** A common anti-pattern is combining a crane and its driver into one labor resource. In professional controls, they are strictly separated:
  * Crane: Non-Labor (`R-EQP-CRANE-100T`, ₹12,000/hr machine lease + fuel).
  * Crane Operator: Labor (`R-OPR-CRANE-SR`, ₹1,500/hr certified master rigger).
* **Maintenance Windows:** Non-Labor assets possess distinct calendars. A hydraulic piling rig may operate on a 6-day, 10-hour work calendar, with every alternate Sunday blocked for hydraulic oil changes and engine overhauls.

### 3.3 Material Resources: Physical Consumables & Capital Equipment
Material resources represent tangible physical items consumed, installed, or erected:
* **Unit of Measure (UOM):** Unlike Labor and Non-Labor (which are locked to units of time: hours), Material resources require an explicit unit of measure:
  * Solar PV Modules: `EA` (Each) or `Wp` (Watts peak).
  * Ready-Mix Concrete: `M3` (Cubic Meters).
  * High-Tensile Steel Piles: `MT` (Metric Tonnes).
  * 33kV Underground Cable: `KM` (Kilometers).
* **Rate Multiplier:** Cost is expressed as `Price / Unit` (e.g., ₹25,000 per MT of steel, ₹8,500 per $m^3$ of M35 grade concrete).
* **Scheduling Impact:** Material resources **never drive activity duration**. An activity requiring $1,200\text{ m}^3$ of concrete does not take 1,200 hours; its duration is determined by the civil pouring crew (Labor) and the concrete boom placer (Non-Labor).

## 4. Calendar Interplay: Resource Calendars vs Activity Calendars

One of the most complex subsystems when architecting a P6-compliant scheduling engine in Go is the interaction between **Activity Calendars** and **Resource Calendars**.

### 4.1 Activity Types: Task Dependent vs Resource Dependent
Every activity in P6 has an `activity_type`. The two most critical for resource scheduling are:

1. **Task Dependent (`TT_Task`):**
   * The activity's schedule is governed **strictly by the Activity Calendar**.
   * Assigned resources work only during the working hours defined by the activity's calendar, regardless of their own base calendar.
   * If a resource is unavailable during those hours, the resource becomes **over-allocated**, but the **activity dates do NOT slip**.

2. **Resource Dependent (`TT_Rsrc`):**
   * The activity's schedule is governed by the **Primary Driving Resource's Calendar** (or the intersection of all assigned driving resource calendars).
   * If the activity calendar says Saturday is a working day, but Arun Kumar's calendar says Saturday is a holiday, **the activity will NOT work on Saturday**.
   * Activity duration expands to accommodate resource non-working time!

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                   CALENDAR INTERPLAY: TASK DEPENDENT VS RESOURCE DEPENDENT                       │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  SCENARIO: Activity "Transformer Testing". Duration: 2 Days (16 Hours).                         │
│  * Activity Calendar: 6-Day Work Week (Mon - Sat, 8 hrs/day).                                    │
│  * Assigned Resource: Arun Kumar. Resource Calendar: 5-Day Work Week (Mon - Fri, 8 hrs/day).    │
│  * Status Date / Start: Friday Morning (08:00).                                                  │
│                                                                                                  │
│  CASE 1: Activity is TASK DEPENDENT                                                              │
│  ┌──────────────┬──────────────┬──────────────┬──────────────┐                                   │
│  │ Friday       │ Saturday     │ Sunday       │ Monday       │                                   │
│  ├──────────────┼──────────────┼──────────────┼──────────────┤                                   │
│  │ 8 hrs (Work) │ 8 hrs (Work) │ Non-Working  │              │                                   │
│  └──────────────┴──────────────┴──────────────┴──────────────┘                                   │
│  Calculated Finish: Saturday 17:00 (Duration = 2 Days).                                          │
│  Resource Impact: Arun Kumar is forced to work on Saturday -> OVER-ALLOCATION FLAGGED!           │
│                                                                                                  │
│  CASE 2: Activity is RESOURCE DEPENDENT                                                          │
│  ┌──────────────┬──────────────┬──────────────┬──────────────┐                                   │
│  │ Friday       │ Saturday     │ Sunday       │ Monday       │                                   │
│  ├──────────────┼──────────────┼──────────────┼──────────────┤                                   │
│  │ 8 hrs (Work) │ Non-Working  │ Non-Working  │ 8 hrs (Work) │                                   │
│  └──────────────┴──────────────┴──────────────┴──────────────┘                                   │
│  Calculated Finish: Monday 17:00 (Duration = 4 Calendar Days, 2 Working Days).                   │
│  Schedule Impact: Activity slipped by 2 days because the human was not available!               │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 Driving vs Non-Driving Resources
When multiple resources are assigned to a single activity:
* **Driving Resource:** A resource whose specific availability calendar and allocation directly determine the start and finish dates of the activity assignment.
* **Non-Driving Resource:** A resource that performs auxiliary work (e.g., an apprentice shadowing a master engineer). Even if the apprentice is absent, the activity proceeds on the master's schedule.

## 5. Enterprise PostgreSQL Database Schema

To support industrial-scale resource and role allocation, the relational model must support recursive role trees, multi-tier rate histories, and composite assignment tracking.

```sql
-- ============================================================================
-- MODULE 7.1: ENTERPRISE RESOURCE & ROLE SCHEMA
-- ============================================================================

CREATE TYPE rsrc_type_enum AS ENUM ('RT_Labor', 'RT_NonLabor', 'RT_Mat');
CREATE TYPE activity_type_enum AS ENUM ('TT_Task', 'TT_Rsrc', 'TT_Mile', 'TT_LOE', 'TT_WBS');

-- 1. ROLES TABLE (Generic Capability & Skill Tree)
CREATE TABLE roles (
    role_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    role_code VARCHAR(32) NOT NULL UNIQUE,
    role_name VARCHAR(128) NOT NULL,
    parent_role_id UUID REFERENCES roles(role_id) ON DELETE SET NULL,
    def_cost_qty NUMERIC(12, 4) NOT NULL DEFAULT 0.0000, -- Default Price/Unit (₹/hr)
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_roles_parent ON roles(parent_role_id);

-- 2. RESOURCES TABLE (Named Humans, Equipment, Materials)
CREATE TABLE rsrc (
    rsrc_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    rsrc_code VARCHAR(32) NOT NULL UNIQUE,
    rsrc_name VARCHAR(128) NOT NULL,
    rsrc_type rsrc_type_enum NOT NULL,
    parent_rsrc_id UUID REFERENCES rsrc(rsrc_id) ON DELETE SET NULL,
    clndr_id UUID NOT NULL, -- FK to enterprise calendar table
    unit_of_measure VARCHAR(16) DEFAULT 'HR', -- 'HR', 'EA', 'M3', 'MT', 'Wp'
    def_cost_qty NUMERIC(12, 4) NOT NULL DEFAULT 0.0000,
    cost_per_qty_ot NUMERIC(12, 4) DEFAULT 0.0000, -- Overtime rate
    max_qty_per_hr NUMERIC(8, 4) NOT NULL DEFAULT 1.0000, -- 1.0 = 100% (1 person)
    active_flag BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_rsrc_type ON rsrc(rsrc_type);
CREATE INDEX idx_rsrc_parent ON rsrc(parent_rsrc_id);

-- 3. RESOURCE-ROLE CROSS REFERENCE (Multi-Skill Qualifications)
CREATE TABLE rsrc_role (
    rsrc_role_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    rsrc_id UUID NOT NULL REFERENCES rsrc(rsrc_id) ON DELETE CASCADE,
    role_id UUID NOT NULL REFERENCES roles(role_id) ON DELETE CASCADE,
    skill_level INT NOT NULL CHECK (skill_level BETWEEN 1 AND 5), -- 1=Master, 5=Novice
    is_primary BOOLEAN NOT NULL DEFAULT FALSE,
    CONSTRAINT uq_rsrc_role UNIQUE (rsrc_id, role_id)
);

CREATE INDEX idx_rsrc_role_lookup ON rsrc_role(role_id, skill_level);

-- 4. RESOURCE TIME-PHASED RATE TIERS (Escalation & Rate Tables)
CREATE TABLE rsrc_rates (
    rate_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    rsrc_id UUID REFERENCES rsrc(rsrc_id) ON DELETE CASCADE,
    role_id UUID REFERENCES roles(role_id) ON DELETE CASCADE,
    rate_type INT NOT NULL DEFAULT 1 CHECK (rate_type BETWEEN 1 AND 5), -- 5 P6 Rate Tiers
    start_date TIMESTAMPTZ NOT NULL, -- Effective start date
    cost_per_qty NUMERIC(12, 4) NOT NULL, -- Standard rate
    cost_per_qty_ot NUMERIC(12, 4) NOT NULL DEFAULT 0.0000,
    CONSTRAINT chk_rsrc_or_role CHECK (
        (rsrc_id IS NOT NULL AND role_id IS NULL) OR 
        (rsrc_id IS NULL AND role_id IS NOT NULL)
    )
);

CREATE INDEX idx_rsrc_rates_effective ON rsrc_rates(rsrc_id, rate_type, start_date);

-- 5. TASK RESOURCE ASSIGNMENTS (The Binding Table)
CREATE TABLE task_rsrc (
    task_rsrc_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    task_id UUID NOT NULL, -- FK to tasks/activities table
    rsrc_id UUID REFERENCES rsrc(rsrc_id) ON DELETE RESTRICT,
    role_id UUID REFERENCES roles(role_id) ON DELETE RESTRICT,
    is_driving BOOLEAN NOT NULL DEFAULT TRUE,
    rate_type INT NOT NULL DEFAULT 1 CHECK (rate_type BETWEEN 1 AND 5),
    target_qty NUMERIC(12, 4) NOT NULL DEFAULT 0.0000, -- Planned Units (hours or qty)
    remain_qty NUMERIC(12, 4) NOT NULL DEFAULT 0.0000, -- Remaining Units
    act_qty NUMERIC(12, 4) NOT NULL DEFAULT 0.0000,    -- Actual Units
    target_lag_drtn_hr INT NOT NULL DEFAULT 0,         -- Assignment lag
    target_start TIMESTAMPTZ,
    target_end TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT chk_assignment_entity CHECK (rsrc_id IS NOT NULL OR role_id IS NOT NULL)
);

CREATE INDEX idx_task_rsrc_task ON task_rsrc(task_id);
CREATE INDEX idx_task_rsrc_rsrc ON task_rsrc(rsrc_id);
```

## 6. Production Go Implementation

Here is the production-ready Go scheduling engine subsystem demonstrating:
1. Role-to-Resource substitution and rate variance calculation.
2. Calendar intersection for `Resource Dependent` vs `Task Dependent` activities.
3. Driving resource start and finish calculation.

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

// ResourceType represents Labor, Non-Labor, or Material.
type ResourceType string

const (
	Labor    ResourceType = "RT_Labor"
	NonLabor ResourceType = "RT_NonLabor"
	Material ResourceType = "RT_Mat"
)

// ActivityType determines calendar dependency.
type ActivityType string

const (
	TaskDependent     ActivityType = "TT_Task"
	ResourceDependent ActivityType = "TT_Rsrc"
)

// Calendar defines working days (0 = Sunday, 1 = Monday, ... 6 = Saturday).
type Calendar struct {
	ID          string
	Name        string
	WorkingDays map[time.Weekday]bool
	HoursPerDay float64
}

// IsWorkingDay checks if a given date is working in this calendar.
func (c *Calendar) IsWorkingDay(t time.Time) bool {
	return c.WorkingDays[t.Weekday()]
}

// Role represents a generic capability pool.
type Role struct {
	ID          string
	Code        string
	Name        string
	DefaultRate float64 // ₹/hr
}

// Resource represents a named entity, machine, or material.
type Resource struct {
	ID           string
	Code         string
	Name         string
	Type         ResourceType
	Calendar     *Calendar
	StandardRate float64 // ₹/hr or ₹/UOM
	UOM          string  // "HR", "M3", "MT", "Wp"
}

// ResourceAssignment binds a role or resource to an activity.
type ResourceAssignment struct {
	ID           string
	TaskID       string
	Role         *Role
	Resource     *Resource
	IsDriving    bool
	TargetUnits  float64 // Budgeted Hours or Material Units
	CalculatedCost float64
}

// Activity represents a project task with calendar and assignments.
type Activity struct {
	ID           string
	Code         string
	Type         ActivityType
	Calendar     *Calendar
	EarlyStart   time.Time
	DurationDays int
	EarlyFinish  time.Time
	Assignments  []*ResourceAssignment
}

// Engine performs resource management and scheduling calculations.
type Engine struct{}

// NewEngine creates a new scheduling engine instance.
func NewEngine() *Engine {
	return &Engine{}
}

// StaffRoleWithResource replaces a generic role with a concrete resource and computes cost variance.
func (e *Engine) StaffRoleWithResource(
	assignment *ResourceAssignment,
	rsrc *Resource,
) (costVariance float64, err error) {
	if assignment == nil || rsrc == nil {
		return 0, errors.New("assignment and resource cannot be nil")
	}

	// Calculate preliminary cost under Role rate
	var baselineCost float64
	if assignment.Role != nil {
		baselineCost = assignment.TargetUnits * assignment.Role.DefaultRate
	}

	// Assign concrete resource
	assignment.Resource = rsrc
	assignment.CalculatedCost = assignment.TargetUnits * rsrc.StandardRate

	// Variance = Actual Assigned Cost - Baseline Role Cost
	costVariance = assignment.CalculatedCost - baselineCost
	return costVariance, nil
}

// CalculateActivityDates evaluates early start and finish based on activity type and calendars.
func (e *Engine) CalculateActivityDates(act *Activity) (time.Time, time.Time, error) {
	if act.DurationDays <= 0 {
		return act.EarlyStart, act.EarlyStart, nil
	}

	currDate := act.EarlyStart
	daysCounted := 0

	// Determine which calendar to evaluate against
	var evalCalendar *Calendar
	if act.Type == TaskDependent {
		evalCalendar = act.Calendar
	} else if act.Type == ResourceDependent {
		// Find driving labor/non-labor resource calendar
		for _, assign := range act.Assignments {
			if assign.IsDriving && assign.Resource != nil && assign.Resource.Calendar != nil {
				evalCalendar = assign.Resource.Calendar
				break
			}
		}
		if evalCalendar == nil {
			// Fallback to activity calendar if no driving resource calendar found
			evalCalendar = act.Calendar
		}
	}

	// Advance calendar day-by-day
	for daysCounted < act.DurationDays {
		if evalCalendar.IsWorkingDay(currDate) {
			daysCounted++
			if daysCounted == act.DurationDays {
				break
			}
		}
		currDate = currDate.AddDate(0, 0, 1)
	}

	act.EarlyFinish = currDate
	return act.EarlyStart, act.EarlyFinish, nil
}
```

## 7. Real-World Pitfalls & Production Edge Cases

### 7.1 The "Double-Calendar Gridlock"
* **Failure Mode:** On industrial sites, subcontractors frequently work 7-day weeks (to meet tight deadlines), while the Owner's inspection engineers follow a 5-day government/corporate calendar.
* **Symptom in P6:** When an activity is marked `Resource Dependent` and assigned both the subcontractor rig (7-day calendar) and the Owner's QA Inspector (5-day calendar), the scheduling engine pauses work entirely across Saturday and Sunday. 
* **Remedy:** Ensure the contractor's field task is marked `Task Dependent` on the site 7-day calendar, with the QA sign-off created as a separate successor milestone or discrete dependent inspection activity.

### 7.2 The Material "Hours vs Units" Corruption
* **Failure Mode:** A scheduler creates a resource called `PV-MODULE-540W` and forgets to set `rsrc_type = RT_Mat`, leaving it as default `RT_Labor`.
* **Disaster:** When they assign 240,000 units to the activity, P6 calculates $240,000\text{ labor hours}$. In the project resource histogram, the site appears to require **30,000 electricians working simultaneously**, causing panic in executive staffing reviews!
* **Architectural Rule:** Enforce strict validation in the API layer: any resource with a `unit_of_measure != 'HR'` MUST have `rsrc_type = RT_Mat`.

### 7.3 Role De-linking During XER Export/Import
* **Failure Mode:** When exporting schedules across different P6 enterprise databases (e.g., Subcontractor DB to EPC Master DB), Role IDs are frequently mapped improperly if the global Role Dictionary is not synchronized.
* **Result:** Assignments lose their role binding, converting planned role allocations into orphaned strings or throwing unmapped foreign key errors during DB ingestion. Always implement a deterministic code-matching fallback (`role_code` instead of internal `UUID`/`role_id`).
