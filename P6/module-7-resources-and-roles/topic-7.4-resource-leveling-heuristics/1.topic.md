# Topic 7.4: Resource Leveling Heuristics — The RCPSP Engine & Conflict Resolution

## 1. Executive Summary & The Core Mental Model

### 1.1 The Infinite Capacity Illusion of Traditional CPM
The Critical Path Method (CPM), developed by DuPont in 1957, is built upon a fundamental physical falsehood:
**It assumes that resources are infinitely available at all times.**

When a traditional forward pass executes, it calculates the Early Start ($ES$) of an activity based solely on when its logical predecessors finish. If ten massive activities all finish their predecessors on the same Friday, CPM schedules all ten to start concurrently on Monday morning—even if that requires:
* 50 heavy cranes when the contractor only owns 2.
* 400 certified high-voltage electricians when only 30 exist in the state.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                THE INFINITE CAPACITY ILLUSION                                    │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  CPM VIEW (Assumes Infinite Resources):                                                          │
│  Task A (Needs 1 Crane) ────► [01-Jun ──────► 15-Jun]                                            │
│  Task B (Needs 1 Crane) ────► [01-Jun ──────► 15-Jun]  ◄── CPM says both start Monday!           │
│  Task C (Needs 1 Crane) ────► [01-Jun ──────► 15-Jun]                                            │
│                                                                                                  │
│  CPM Verdict: Project finishes on 15-Jun. Total Float = 14 days. Management is happy.             │
│                                                                                                  │
│  ──────────────────────────────────────────────────────────────────────────────────────────────  │
│                                                                                                  │
│  PHYSICAL SITE REALITY (Only 1 Crane Exists):                                                    │
│  * The 3 tasks CANNOT run in parallel.                                                           │
│  * They MUST execute sequentially:                                                               │
│    Task A: [01-Jun ──► 15-Jun] ──► Releases Crane                                                │
│    Task B: [16-Jun ──► 30-Jun] ──► Releases Crane                                                │
│    Task C: [01-Jul ──► 15-Jul]                                                                   │
│                                                                                                  │
│  REALITY VERDICT: Project finishes on 15-Jul (1 MONTH LATE!). CPM was a dangerous fiction.        │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

> **The Leveling Axiom:**  
> A CPM schedule that ignores resource limits is not a plan; it is a wish list. **Resource Leveling** is the algorithmic process of resolving over-allocations by shifting activities across time, transforming an unachievable theoretical network into an executable operational reality.

### 1.2 Plain-English Intuition: The Single-Track Railway
Imagine a railway network with a single track running through a mountain pass:
* **CPM Schedule:** Two express trains traveling in opposite directions are both scheduled to enter the single-track mountain section at 10:00 AM because their previous stations were cleared.
* **The Collision:** Without an external dispatcher, a head-on collision occurs.
* **The Dispatcher (The Leveling Engine):**
  1. The dispatcher evaluates train priority: Train #1 is a high-speed passenger train with 0 minutes of delay allowance; Train #2 is a freight train with 45 minutes of scheduled buffer.
  2. Train #2 is directed to a siding (delayed by 30 minutes) to allow Train #1 to pass.
  3. Both trains proceed safely without physical collision.

In Primavera P6, the **Resource Leveling Engine** acts as that railway dispatcher. It identifies resource collisions and shifts lower-priority activities into available time slots or float buffers.

### 1.3 Running Case Study Context: Surya 100MW Solar IPP
On the Surya Solar Project in Bhadla, Rajasthan:
* **The Bottleneck:** Only **1 Heavy Crawler Crane (100T)** is mobilized on site for erecting the main 120MVA Generator Step-Up (GSU) Power Transformer and setting 40 Central Inverter Skids.
* **The Conflict:** In Month 5, the mechanical contractor schedules the erection of Inverter Skid #01 through #04 concurrently with the main Substation GSU Transformer Gantry Erection. Both operations demand the 100T Crane simultaneously.
* **The Solution:** The P6 Leveling Engine must analyze total float, activity priorities, and network logic to sequence the crane's movements across the 480-acre solar park without breaching the 31-Dec-2026 Commercial Operation Date (COD).

## 2. The RCPSP Formulation (Resource-Constrained Project Scheduling)

The problem Primavera P6 solves during leveling is known in computer science and operations research as the **Resource-Constrained Project Scheduling Problem (RCPSP)**.

### 2.1 Formal Mathematical Model
Given:
* A set of activities $V = \{1, 2, \dots, n\}$.
* Duration $d_i$ for each activity $i$.
* Precedence relations $(i, j) \in E$ meaning activity $j$ cannot start until $i$ finishes:
  $$S_j \ge S_i + d_i \quad \forall (i, j) \in E$$
* A set of renewable resources $K$. Each resource $k \in K$ has a constant capacity limit $R_k$.
* Resource demand $r_{i, k}$ for activity $i$ on resource $k$.

**Objective:** Minimize project completion time (makespan $S_n$):

$$\min S_n$$

**Subject to the Resource Capacity Constraint:**
For every time instant $t$ and every resource $k \in K$:

$$\sum_{i \in A(t)} r_{i, k} \le R_k \quad \forall t, \forall k$$

Where $A(t) = \{i \in V \mid S_i \le t < S_i + d_i\}$ is the set of activities actively executing at time $t$.

### 2.2 Computational Complexity: Why Heuristics Are Mandatory
The RCPSP is **NP-hard in the strong sense**. 
* For a tiny network of 20 activities, an exact Integer Linear Programming (ILP) solver or Branch-and-Bound algorithm can find the mathematically optimal schedule in seconds.
* For a real-world enterprise EPC schedule (such as the Surya Solar project with **8,500 activities** and 15 constrained resources), finding the globally optimal schedule would take $10^{40}$ compute years!
* Therefore, commercial project controls engines like Primavera P6 use **Heuristic Schedule Generation Schemes (SGS)** to compute near-optimal, legally defensible leveled dates in milliseconds.

## 3. Schedule Generation Schemes: Parallel SGS vs Serial SGS

The operations research community classifies heuristic scheduling engines into two primary architectures:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                       SERIAL SGS VS PARALLEL SGS ARCHITECTURAL COMPARISON                        │
├──────────────────────────┬─────────────────────────────┬─────────────────────────────────────────┤
│ Dimension                │ Serial SGS (Activity-Based) │ Parallel SGS (Time-Based - P6 DEFAULT)  │
├──────────────────────────┼─────────────────────────────┼─────────────────────────────────────────┤
│ Iteration Loop           │ Loops through ACTIVITIES:   │ Loops through TIME TICKS (Clock):       │
│                          │ For act in PriorityList ... │ For t = 0; t <= ProjectFinish; t++ ...  │
├──────────────────────────┼─────────────────────────────┼─────────────────────────────────────────┤
│ Placement Decision       │ Takes next activity and     │ At current clock time t, identifies all │
│                          │ schedules it at earliest    │ eligible ready tasks. Allocates         │
│                          │ resource-feasible slot.     │ available resources by priority.        │
├──────────────────────────┼─────────────────────────────┼─────────────────────────────────────────┤
│ Resource Shifting        │ Can insert activities into  │ Strictly moves forward in time. Tasks   │
│                          │ earlier holes ("gaps").     │ cannot be backfilled behind clock t.    │
├──────────────────────────┼─────────────────────────────┼─────────────────────────────────────────┤
│ Real-World Behavior      │ Unrealistic in the field    │ Mirrors site execution: decisions are   │
│                          │ (schedules future before    │ made daily based on who is standing     │
│                          │ resolving today).           │ on site and what equipment is free.     │
└──────────────────────────┴─────────────────────────────┴─────────────────────────────────────────┘
```

### 3.1 Parallel Schedule Generation Scheme (P6 Engine Default)
Primavera P6 uses the **Parallel SGS**:
1. Initialize clock $t = 0$.
2. Maintain three sets of activities:
   * **Complete ($C$):** Activities finished prior to $t$.
   * **Active ($A$):** Activities currently running at time $t$.
   * **Eligible ($E$):** Activities whose logic predecessors are all in $C$, but have not yet started.
3. Sort eligible activities $E$ according to the **P6 Leveling Priority Rules**.
4. For each activity $i \in E$:
   * Check if available resource capacity at $t$ satisfies $r_{i, k} \le R_k - \sum_{j \in A} r_{j, k}$ for all resources $k$.
   * If **YES**: Start activity $i$ at time $t$, move $i$ from $E$ to $A$, and deduct its resources.
   * If **NO**: Activity $i$ cannot start at time $t$. It remains delayed.
5. Advance clock $t$ to the earliest completion time of any active activity in $A$.
6. Repeat until all activities are in $C$.

│  [Eligible Tasks Competing for Scarce Crane]                                                     │
│        │                                                                                         │
│        ▼                                                                                         │

## 6. Resource-Constrained Critical Path & Resource Float

One of the most profound revelations for a scheduling engineer is that **Resource Leveling breaks classical CPM float calculations**:

### 6.1 Phantom Dependencies (Resource Links)
Consider two completely unrelated activities:
* Activity 1: Substation GSU Transformer Placement (0 float).
* Activity 2: Inverter Skid 04 Placement (14 days float).
There is **no logic link** (FS, SS, FF) connecting them.
However, because both require the single 100T Crane, Activity 2 cannot start until Activity 1 releases the crane.
The crane creates a **Phantom Resource Link** between them:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                   THE PHANTOM RESOURCE LINK                                      │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  Logical Network:   [Activity 1: Transformer Lift]      [Activity 2: Inverter Skid Lift]          │
│                     (No Relationship Exists!)                                                    │
│                                                                                                  │
│  Resource Network:  [Activity 1] ─── (100T Crane Transfer) ───► [Activity 2]                     │
│                                                                                                  │
│  CONSEQUENCE:                                                                                    │
│  If Activity 1 is delayed by 2 days due to wind, Activity 2 is automatically delayed by 2 days,  │
│  even though CPM logic shows zero relationship between them!                                     │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 6.2 Resource Float ($RF$)
In classical CPM, Total Float is:
$$TF = LF - EF$$
In a leveled schedule, a task may have $TF = 14\text{ days}$ according to logic, but its **Resource Float** is $0\text{ days}$ because delaying it by even 1 day will collide with another task's crane reservation!
This creates the **Resource-Constrained Critical Path**: the sequence of activities that dictates project completion, bound together by a mixture of logical relationships and resource contentions.

## 7. Production Go Resource Leveling Engine

Below is a complete, production-grade Go leveling engine implementing the **Parallel Schedule Generation Scheme**:

```go
package main

import (
	"container/heap"
	"fmt"
	"sort"
)

// LevelingPriority defines user priority tiers.
type LevelingPriority int

const (
	PriorityTop LevelingPriority = iota
	PriorityHigh
	PriorityNormal
	PriorityLow
	PriorityLowest
)

// Task represents an activity in the leveling engine.
type Task struct {
	ID           string
	Code         string
	Duration     int
	DemandCrane  int // Required 100T cranes
	TotalFloat   int
	EarlyStart   int
	EarlyFinish  int
	LeveledStart int
	LeveledEnd   int
	Priority     LevelingPriority
	Predecessors []*Task
}

// TaskPriorityQueue implements heap.Interface for the Parallel SGS tie-breaker.
type TaskPriorityQueue []*Task

func (pq TaskPriorityQueue) Len() int { return len(pq) }

func (pq TaskPriorityQueue) Less(i, j int) bool {
	// 1. User Priority (Top beats High)
	if pq[i].Priority != pq[j].Priority {
		return pq[i].Priority < pq[j].Priority
	}
	// 2. Minimum Total Float (0 beats 10)
	if pq[i].TotalFloat != pq[j].TotalFloat {
		return pq[i].TotalFloat < pq[j].TotalFloat
	}
	// 3. Early Start (Earlier beats later)
	if pq[i].EarlyStart != pq[j].EarlyStart {
		return pq[i].EarlyStart < pq[j].EarlyStart
	}
	// 4. Lexicographical ID fallback
	return pq[i].ID < pq[j].ID
}

func (pq TaskPriorityQueue) Swap(i, j int) { pq[i], pq[j] = pq[j], pq[i] }
func (pq *TaskPriorityQueue) Push(x interface{}) { *pq = append(*pq, x.(*Task)) }
func (pq *TaskPriorityQueue) Pop() interface{} {
	old := *pq
	n := len(old)
	item := old[n-1]
	*pq = old[0 : n-1]
	return item
}

// ParallelLeveler executes time-stepped parallel leveling.
type ParallelLeveler struct {
	MaxCranes int
}

func NewParallelLeveler(maxCranes int) *ParallelLeveler {
	return &ParallelLeveler{MaxCranes: maxCranes}
}

func (l *ParallelLeveler) Level(tasks []*Task) int {
	completed := make(map[string]bool)
	active := make([]*Task, 0)
	clock := 0

	for len(completed) < len(tasks) {
		// 1. Clean up tasks that finished at or before current clock
		newActive := make([]*Task, 0)
		for _, t := range active {
			if t.LeveledEnd <= clock {
				completed[t.ID] = true
			} else {
				newActive = append(newActive, t)
			}
		}
		active = newActive

		// Check termination
		if len(completed) == len(tasks) {
			break
		}

		// 2. Calculate currently consumed cranes
		usedCranes := 0
		for _, t := range active {
			usedCranes += t.DemandCrane
		}

		// 3. Find eligible tasks (all predecessors completed, not yet started)
		eligiblePQ := &TaskPriorityQueue{}
		heap.Init(eligiblePQ)

		for _, t := range tasks {
			if completed[t.ID] || t.LeveledStart > 0 || (t.LeveledEnd > 0 && t.LeveledEnd > clock) {
				continue
			}
			// Check if already active
			isActive := false
			for _, act := range active {
				if act.ID == t.ID {
					isActive = true
					break
				}
			}
			if isActive {
				continue
			}

			// Predecessors satisfied?
			predsSatisfied := true
			for _, pred := range t.Predecessors {
				if !completed[pred.ID] {
					predsSatisfied = false
					break
				}
			}

			if predsSatisfied && clock >= t.EarlyStart {
				heap.Push(eligiblePQ, t)
			}
		}

		// 4. Allocate resources according to priority queue
		for eligiblePQ.Len() > 0 {
			candidate := heap.Pop(eligiblePQ).(*Task)
			if usedCranes+candidate.DemandCrane <= l.MaxCranes {
				// Allocate and start task at clock
				candidate.LeveledStart = clock
				candidate.LeveledEnd = clock + candidate.Duration
				usedCranes += candidate.DemandCrane
				active = append(active, candidate)
			}
		}

		// 5. Advance clock to next earliest event
		nextClock := clock + 1
		if len(active) > 0 {
			earliestFinish := 999999
			for _, act := range active {
				if act.LeveledEnd < earliestFinish {
					earliestFinish = act.LeveledEnd
				}
			}
			nextClock = earliestFinish
		}
		clock = nextClock
	}

	return clock
}

func main() {
	// Surya Solar 100T Crane Leveling Scenario: Capacity = 1 Crane
	leveler := NewParallelLeveler(1)

	// Task 1: 120MVA GSU Transformer Placement (Critical Path, 0 float)
	task1 := &Task{
		ID:          "T1",
		Code:        "GSU-TRANS-LIFT",
		Duration:    5,
		DemandCrane: 1,
		TotalFloat:  0,
		EarlyStart:  0,
		EarlyFinish: 5,
		Priority:    PriorityTop,
	}

	// Task 2: Inverter Skid 01 Placement (Non-critical, 10 days float)
	task2 := &Task{
		ID:          "T2",
		Code:        "INVERTER-SKID-01",
		Duration:    4,
		DemandCrane: 1,
		TotalFloat:  10,
		EarlyStart:  0,
		EarlyFinish: 4,
		Priority:    PriorityNormal,
	}

	// Task 3: Inverter Skid 02 Placement (Non-critical, 12 days float)
	task3 := &Task{
		ID:          "T3",
		Code:        "INVERTER-SKID-02",
		Duration:    4,
		DemandCrane: 1,
		TotalFloat:  12,
		EarlyStart:  0,
		EarlyFinish: 4,
		Priority:    PriorityNormal,
	}

	taskList := []*Task{task1, task2, task3}

	fmt.Println("--- PRE-LEVELING STATE (CPM UNCONSTRAINED) ---")
	for _, t := range taskList {
		fmt.Printf("Task %-18s: ES=%2d, EF=%2d, Float=%2d, Crane Demand=%d\n",
			t.Code, t.EarlyStart, t.EarlyFinish, t.TotalFloat, t.DemandCrane)
	}

	makespan := leveler.Level(taskList)

	fmt.Println("\n--- POST-LEVELING STATE (PARALLEL SGS CONSTRAINED) ---")
	sort.Slice(taskList, func(i, j int) bool {
		return taskList[i].LeveledStart < taskList[j].LeveledStart
	})

	for _, t := range taskList {
		delay := t.LeveledStart - t.EarlyStart
		fmt.Printf("Task %-18s: LeveledStart=%2d, LeveledEnd=%2d (Delayed %2d days by Crane Contention)\n",
			t.Code, t.LeveledStart, t.LeveledEnd, delay)
	}
	fmt.Printf("\nProject Leveled Completion (Makespan): Day %d\n", makespan)
}
```

## 8. Real-World Pitfalls & Production Edge Cases

### 8.1 The Circular Leveling Deadlock
* **The Glitch:** Activity A and Activity B both require Crane 1 and Electrician Crew 1. A requires Crane first, then Crew; B requires Crew first, then Crane. If activity splitting is enabled, the leveling engine splits A waiting for Crew, and splits B waiting for Crane—locking both tasks in a perpetual deadlock (the classic operating system "Dining Philosophers" problem).
* **Fix:** Disable activity splitting on multi-resource interdependent craft tasks.

### 8.2 Levelling Only Within Float vs Commercial Ruin
* **Contractor Hazard:** If a planner enables "Level only within Total Float", P6 leaves over-allocations unresolved when float reaches zero. If the contractor submits this schedule to the Owner, the Owner's engineer will approve it because the milestone dates didn't move. But when construction starts, the missing equipment physically halts work, and the contractor cannot claim delay because they submitted an un-levelled schedule with unresolved over-allocations!
