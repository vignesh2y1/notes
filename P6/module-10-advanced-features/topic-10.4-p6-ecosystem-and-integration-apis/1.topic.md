### 2.1 The Modern Choice: P6 EPPM REST API
For modern cloud-native architectures (such as building custom dashboards in Next.js or high-speed processing in Golang), the **P6 EPPM REST API** is the enterprise standard:
* **Endpoints:** Exposes standard resources (`/p6ws/restapi/project`, `/activity`, `/baseline`, `/wbs`, `/resource`).
* **Format:** Clean JSON payloads.
* **Authentication:** HTTP Basic, Cookie-based Session Leasing, or OAuth2 / SAML Bearer Tokens.
* **Bulk Capabilities:** Supports batch operations to minimize network round-trips.

## 3. Authentication & Session Management in P6 REST API

Unlike stateless public APIs, Oracle Primavera P6 EPPM was originally architected as a stateful enterprise application. When integrating via Go, handling authentication lifecycle correctly is paramount.

### 3.1 Cookie-Based Session Leasing vs. Stateless Tokens

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                         P6 EPPM REST API SESSION LEASING LIFECYCLE                               │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   [Golang Integration Service]                          [P6 EPPM REST Gateway]                   │
│                │                                                   │                             │
│                │─── 1. POST /login (Credentials / DB Instance) ───>│ (Validates against P6 OBS)  │
│                │<── 2. 200 OK + Set-Cookie: JSESSIONID=xyz... ────│ (Allocates session lease)    │
│                │                                                   │                             │
│                │─── 3. GET /activity (Cookie: JSESSIONID=xyz) ────>│ (Fast in-memory cache lookup│
│                │<── 4. 200 OK (Activity JSON Array) ───────────────│                             │
│                │                                                   │                             │
│                │    [... 50 subsequent API requests ...]           │                             │
│                │                                                   │                             │
│                │─── 5. POST /logout (Terminate lease) ────────────>│ (Frees database session pool│
│                │<── 6. 200 OK ─────────────────────────────────────│                             │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **The Session Exhaustion Bug:**
> If your Go service logs in on *every* HTTP request without logging out, P6's WebLogic application server will exhaust its licensed concurrent user pool within minutes, throwing HTTP `500 Internal Server Error` and locking out human schedulers!
> Modern Go integration clients must implement **Session Pooling with Keep-Alive Heartbeats**.

### 4.1 The Billing Milestone Trigger Flow
1. Milestone `ACT-500` (*Commercial Operation Date*) achieves `ActualFinish = 15-Dec-2026` in P6.
2. The Go sync service captures the change event via P6 Webhook.
3. The service maps P6 activity `ACT-500` to SAP WBS Element `SU-100-M500`.
4. The service posts an RFC/OData call to SAP PS: `/sap/opu/odata/sap/API_PROJECT_MILESTONE/ConfirmMilestone`.
5. SAP PS immediately unlocks the contractual payment milestone, releasing ₹450,000,000 in owner invoice billing.

## 5. Synchronization Patterns & Resilience Architectures

When syncing thousands of activities across enterprise boundaries, three architectural patterns prevent data corruption:

### 5.1 Pattern 1: Batch Chunking and Keyset Pagination
Fetching 50,000 activities in a single REST request results in HTTP `504 Gateway Timeout` or OOM crashes.
* P6 REST API uses offset pagination or keyset filtering (`ObjectId > lastSeenId`).
* Chunk requests into batches of **500 to 1,000 records**.

### 5.2 Pattern 2: Exponential Backoff & Circuit Breaking
Enterprise P6 servers undergo nightly database maintenance, baseline copying, and scheduling recalculations, during which API response times degrade.
* The Go HTTP client must implement **Exponential Backoff with Full Jitter**:
$$t_{\text{sleep}} = \min(t_{\text{max}},\; t_{\text{base}} \times 2^{\text{attempt}}) \times \text{Uniform}(0.5, 1.5)$$

### 5.3 Pattern 3: Bidirectional Idempotency & Conflict Resolution
What happens if a scheduler updates the activity name in P6 while an ERP accountant simultaneously updates the WBS name in SAP?
* **Golden Rule of Enterprise Integration:** Designate a **Single Source of Truth (SSOT)** for every field!
  - SAP is SSOT for *Budget, Actual Cost, and Vendor Names*.
  - P6 is SSOT for *Durations, Precedence Logic, Dates, and Physical % Complete*.
* Never permit bidirectional writes on the same field!

## 6. Production-Grade Golang P6 REST Client

Below is a complete, concurrent, thread-safe Go client for the Primavera P6 EPPM REST API, featuring session pooling, automatic re-authentication, pagination, and retry backoff.

```go
package p6client

import (
	"bytes"
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"io"
	"math/rand"
	"net/http"
	"net/http/cookiejar"
	"net/url"
	"sync"
	"time"
)

// Config encapsulates connection details for P6 EPPM.
type Config struct {
	BaseURL    string
	DatabaseID string
	Username   string
	Password   string
	Timeout    time.Duration
}

// ActivityDTO models the P6 REST activity resource.
type ActivityDTO struct {
	ObjectId               int        `json:"ObjectId"`
	Id                     string     `json:"Id"`
	Name                   string     `json:"Name"`
	ProjectId              string     `json:"ProjectId"`
	WBSObjectId            int        `json:"WBSObjectId"`
	Status                 string     `json:"Status"` // 'Not Started', 'In Progress', 'Completed'
	PlannedDuration        float64    `json:"PlannedDuration"`
	RemainingDuration      float64    `json:"RemainingDuration"`
	ActualStartDate        *time.Time `json:"ActualStartDate,omitempty"`
	ActualFinishDate       *time.Time `json:"ActualFinishDate,omitempty"`
	PlannedStartDate       time.Time  `json:"PlannedStartDate"`
	PlannedFinishDate      time.Time  `json:"PlannedFinishDate"`
	PercentComplete        float64    `json:"PercentComplete"`
	PrimaryConstraintType  string     `json:"PrimaryConstraintType,omitempty"`
	PrimaryConstraintDate  *time.Time `json:"PrimaryConstraintDate,omitempty"`
}

// Client manages authenticated communication with P6 EPPM.
type Client struct {
	cfg        Config
	httpClient *http.Client
	mu         sync.RWMutex
	isLoggedIn bool
	lastActive time.Time
}

// NewClient constructs an initialized P6 client with cookie jar.
func NewClient(cfg Config) (*Client, error) {
	jar, err := cookiejar.New(nil)
	if err != nil {
		return nil, fmt.Errorf("failed to create cookie jar: %w", err)
	}

	return &Client{
		cfg: cfg,
		httpClient: &http.Client{
			Jar:     jar,
			Timeout: cfg.Timeout,
		},
	}, nil
}

// Login establishes an authenticated session with P6 EPPM.
func (c *Client) Login(ctx context.Context) error {
	c.mu.Lock()
	defer c.mu.Unlock()

	loginURL := fmt.Sprintf("%s/p6ws/restapi/login", c.cfg.BaseURL)
	payload := map[string]string{
		"UserName": c.cfg.Username,
		"Password": c.cfg.Password,
		"Database": c.cfg.DatabaseID,
	}

	bodyBytes, _ := json.Marshal(payload)
	req, err := http.NewRequestWithContext(ctx, http.MethodPost, loginURL, bytes.NewReader(bodyBytes))
	if err != nil {
		return err
	}
	req.Header.Set("Content-Type", "application/json")

	resp, err := c.httpClient.Do(req)
	if err != nil {
		return fmt.Errorf("login request failed: %w", err)
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		b, _ := io.ReadAll(resp.Body)
		return fmt.Errorf("login rejected (status %d): %s", resp.StatusCode, string(b))
	}

	c.isLoggedIn = true
	c.lastActive = time.Now()
	return nil
}

// Logout releases the server-side session lease.
func (c *Client) Logout(ctx context.Context) error {
	c.mu.Lock()
	defer c.mu.Unlock()

	if !c.isLoggedIn {
		return nil
	}

	logoutURL := fmt.Sprintf("%s/p6ws/restapi/logout", c.cfg.BaseURL)
	req, _ := http.NewRequestWithContext(ctx, http.MethodPost, logoutURL, nil)
	resp, err := c.httpClient.Do(req)
	if err == nil {
		resp.Body.Close()
	}

	c.isLoggedIn = false
	return nil
}

// ensureSession validates session freshness and re-authenticates if expired (> 20 min idle).
func (c *Client) ensureSession(ctx context.Context) error {
	c.mu.RLock()
	needLogin := !c.isLoggedIn || time.Since(c.lastActive) > 20*time.Minute
	c.mu.RUnlock()

	if needLogin {
		return c.Login(ctx)
	}
	return nil
}

// FetchActivitiesByProject retrieves all activities for a project using chunked pagination.
func (c *Client) FetchActivitiesByProject(ctx context.Context, projectObjectId int) ([]ActivityDTO, error) {
	if err := c.ensureSession(ctx); err != nil {
		return nil, err
	}

	allActivities := make([]ActivityDTO, 0)
	pageSize := 500
	offset := 0

	for {
		chunk, err := c.fetchActivityPageWithRetry(ctx, projectObjectId, pageSize, offset)
		if err != nil {
			return nil, err
		}

		allActivities = append(allActivities, chunk...)
		if len(chunk) < pageSize {
			break // Reached final page
		}
		offset += pageSize
	}

	c.mu.Lock()
	c.lastActive = time.Now()
	c.mu.Unlock()

	return allActivities, nil
}

// fetchActivityPageWithRetry executes an API call with exponential retry backoff.
func (c *Client) fetchActivityPageWithRetry(ctx context.Context, projectID, limit, offset int) ([]ActivityDTO, error) {
	maxAttempts := 4
	baseDelay := 500 * time.Millisecond

	var lastErr error
	for attempt := 1; attempt <= maxAttempts; attempt++ {
		endpoint := fmt.Sprintf("%s/p6ws/restapi/activity?Filter=ProjectObjectId%%20eq%%20%d&Fields=ObjectId,Id,Name,ProjectId,Status,PlannedDuration,RemainingDuration,PercentComplete&Range=%d,%d",
			c.cfg.BaseURL, projectID, offset, limit)

		req, err := http.NewRequestWithContext(ctx, http.MethodGet, endpoint, nil)
		if err != nil {
			return nil, err
		}
		req.Header.Set("Accept", "application/json")

		resp, err := c.httpClient.Do(req)
		if err == nil && resp.StatusCode == http.StatusOK {
			defer resp.Body.Close()
			var result struct {
				Activities []ActivityDTO `json:"Activity"`
			}
			if err := json.NewDecoder(resp.Body).Decode(&result); err != nil {
				return nil, fmt.Errorf("failed to decode JSON response: %w", err)
			}
			return result.Activities, nil
		}

		if resp != nil {
			resp.Body.Close()
			if resp.StatusCode == http.StatusUnauthorized {
				// Session expired; re-login and retry
				_ = c.Login(ctx)
			}
		}

		lastErr = err
		// Calculate jittered backoff
		jitter := time.Duration(rand.Float64() * float64(baseDelay))
		sleepDur := (baseDelay * time.Duration(1<<attempt)) + jitter
		select {
		case <-time.After(sleepDur):
		case <-ctx.Done():
			return nil, ctx.Err()
		}
	}

	return nil, fmt.Errorf("failed after %d attempts: %w", maxAttempts, lastErr)
}
```

## 7. Industry Pitfalls & Anti-Patterns

### 7.1 Pitfall 1: Session Leakage Paralyzing WebLogic
* **The Anti-Pattern:** A microservice instantiates a new HTTP client, sends `/login`, fetches one activity, and closes the TCP socket without invoking `/logout`.
* **Why it Breaks Systems:** WebLogic holds the HTTP session in memory for 30 minutes. Under continuous polling, 1,000 leaked sessions consume all licensed P6 user seats and exhaust JVM heap memory, causing the P6 application server to crash.
* **The Rule:** Maintain a long-lived, persistent HTTP client with cookie leasing, heartbeats, and graceful `/logout` on process shutdown.

### 7.2 Pitfall 2: Bidirectional Race Conditions on Dates
* **The Anti-Pattern:** Schedulers change dates in P6 while project engineers simultaneously adjust milestone dates in SAP. A bidirectional sync runs every 15 minutes, ping-ponging dates back and forth.
* **Why it Breaks Systems:** The two systems oscillate indefinitely, flooding database audit logs and corrupting project baselines.
* **The Rule:** Enforce strict unilateral ownership. P6 owns all schedule dates; SAP owns all financial amounts.

### 7.3 Pitfall 3: Synchronous Blocking HTTP Calls in Webhook Handlers
* **The Anti-Pattern:** A webhook receiver in Go receives an event: "Activity ACT-100 Updated", and immediately triggers a synchronous 45-second CPM recalculation before returning HTTP 200 OK.
* **Why it Breaks Systems:** The P6 webhook publisher times out after 5 seconds, assumes failure, and retries the webhook 10 times, triggering 10 simultaneous CPM runs and crashing the server.
* **The Rule:** Webhook endpoints must quickly enqueue the event onto a message broker (RabbitMQ/Kafka) and immediately respond with `202 Accepted` or `200 OK` in < 20ms.
