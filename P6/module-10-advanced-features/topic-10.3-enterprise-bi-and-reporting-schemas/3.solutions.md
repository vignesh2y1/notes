## 🧠 Section A: Conceptual & Architectural Principles

### Solution 1: OLTP 3NF vs. OLAP Dimensional Warehousing

#### 1. Why Operational P6 Schemas Fail for Dashboards
The native operational relational schema of P6 is designed for **transactional integrity (ACID)**. Tables like `TASK`, `PROJWBS`, `TASKPRED`, and `TASKRSRC` are heavily normalized (Third Normal Form, 3NF):
* Operational queries modify a single row at a time (e.g., updating `remain_drtn_hr_cnt` for Activity `ACT-100`).
* In contrast, an executive dashboard requires calculating portfolio-wide aggregates across time: "Sum Planned Value and Earned Value across all 250 projects over 36 months, grouped by Business Unit and Contractor."
* Executing this on the operational DB requires joining 8 to 12 normalized tables, traversing recursive WBS trees, and computing dynamic calendar spreads on millions of rows. This causes high CPU spikes, locks the transaction tables, and causes timeouts for planners saving updates.

#### 2. Time-Phased Cost Curves in Operational P6
* In the P6 user interface, planners view smooth daily, weekly, or monthly Planned Value and Earned Value S-curves.
* However, **P6 does not physically store daily time-phased cost records in tables**.
* Instead, it stores the total budgeted cost and the activity calendar. When a user requests a profile or curve, the P6 application server **dynamically computes** the daily spread on the fly by iterating through every working hour of the calendar between Early Start and Early Finish. Doing this dynamically for 50,000 activities on every dashboard refresh is computationally impossible.

#### 3. Grain Difference
* **Operational Transaction Grain:** An individual mutation or state of an entity (e.g., a single activity record in `TASK` representing its current remaining duration and early dates).
* **Analytical Snapshot Grain:** **One row per activity per calendar date per baseline snapshot** in `fact_daily_activity_snapshot`. This enables point-in-time time-series analysis without dynamic recalculations.

### Solution 2: Star Schema Design & WBS Hierarchy Flattening

#### 1. Concurrency Bottleneck of Recursive CTEs
In 3NF, the WBS table uses an adjacency list (`wbs_id`, `parent_wbs_id`). To rollup metrics to Level 2 (e.g., "Civil Works"), the database must execute a recursive query:
```sql
WITH RECURSIVE wbs_tree AS (...)
```
For a 7-level tree across 250 projects, this requires repeated index scans, temporary spooling in memory/disk, and cannot easily leverage pre-computed index scans. Under 100 concurrent dashboard requests, PostgreSQL's memory (`work_mem`) is exhausted.

#### 2. Flattened Dimension Pattern for `dim_wbs`
In dimensional modeling, we pre-flatten the hierarchy into explicit level columns:

```sql
CREATE TABLE dim_wbs (
    wbs_key         INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    wbs_id_uuid     UUID NOT NULL,
    project_key     INT NOT NULL,
    wbs_code        VARCHAR(100) NOT NULL,
    wbs_name        VARCHAR(255) NOT NULL,
    wbs_level       SMALLINT NOT NULL,
    
    -- Pre-flattened hierarchy attributes
    wbs_l1_code     VARCHAR(50),
    wbs_l1_name     VARCHAR(255),
    wbs_l2_code     VARCHAR(50),
    wbs_l2_name     VARCHAR(255),
    wbs_l3_code     VARCHAR(50),
    wbs_l3_name     VARCHAR(255),
    wbs_l4_code     VARCHAR(50),
    wbs_l4_name     VARCHAR(255),
    
    is_work_package BOOLEAN NOT NULL DEFAULT FALSE
);
```

To filter by Subsystem (Level 2), the BI tool issues an instantaneous, non-recursive query:
```sql
SELECT wbs_l2_name, SUM(ev_cumulative)
FROM fact_daily_activity_snapshot f
JOIN dim_wbs w ON f.wbs_key = w.wbs_key
WHERE w.wbs_l1_name = 'Solar Array Works'
GROUP BY wbs_l2_name;
```

#### 3. Star Schema vs. Snowflake Schema
* A **Snowflake schema** normalizes dimension tables (e.g., separating `dim_wbs_level1`, `dim_wbs_level2` into separate joined tables).
* Modern analytical data warehouses strongly prefer **Star schemas** because disk storage is cheap, and eliminating table joins drastically improves query throughput and allows columnar vector engines to scan contiguous memory.

### Solution 3: Slowly Changing Dimensions (SCD Type 2) in Project Controls

#### 1. Why SCD Type 1 Destroys Audit Trails
If SCD Type 1 (in-place overwrite) is used:
* Updating `budgeted_cost` from ₹15M to ₹22M modifies the existing row.
* When historical reports are generated for Month 1 through Month 3, the query multiplies physical progress against ₹22M instead of ₹15M.
* Past Earned Value payments and statutory investor filings are retroactively altered, failing statutory financial audits and invalidating earned value metrics.

#### 2. Row Mutations Under SCD Type 2
When Scope Change B01 is approved on 2026-04-01:
1. **Expire Existing Current Record:**
```sql
UPDATE dim_activity
SET effective_to = '2026-03-31 23:59:59+00',
    is_current = FALSE
WHERE activity_id_uuid = 'e8b1d923-...' AND is_current = TRUE;
```
2. **Insert New Version Record:**
```sql
INSERT INTO dim_activity (
    activity_id_uuid, project_key, wbs_key, activity_code, activity_name,
    activity_type, constraint_type, original_duration_days, budgeted_cost,
    effective_from, effective_to, is_current, revision_reason
) VALUES (
    'e8b1d923-...', 1, 14, 'ACT-STR', 'Tracker Mounting',
    'Task Dependent', 'NONE', 45, 22000000.00,
    '2026-04-01 00:00:00+00', '9999-12-31 23:59:59+00', TRUE, 'Scope Change B01 Approved'
);
```

#### 3. Integrity via Surrogate Primary Key
The new row receives a new unique surrogate key (e.g., `activity_key = 102`), while the expired row retains `activity_key = 101`.
* All snapshot fact rows generated in January, February, and March reference `activity_key = 101`.
* All snapshot fact rows generated from April onwards reference `activity_key = 102`.
* Past reports query `activity_key = 101` and accurately reflect the ₹15M baseline!

### Solution 4: Row-Oriented (PostgreSQL) vs. Columnar (ClickHouse) Storage

#### 1. PostgreSQL Row-Oriented Execution
In PostgreSQL, table storage is organized into 8KB disk pages holding complete tuples (rows):
`[DateKey, ProjKey, WbsKey, ActKey, PVDaily, PVCum, EVDaily, EVCum, ACDaily, ACCum, RemDur, Float, Crit]`
* To calculate `SUM(ev_cumulative)`, the query executor must load every 8KB page containing all 13 columns from disk into buffer cache.
* For 54.7 million rows (~6.5 GB of raw data), PostgreSQL must read the entire 6.5 GB from disk, extracting the 8-byte `ev_cumulative` field from each row.

#### 2. ClickHouse Columnar Execution
In ClickHouse, each column is stored as an independent, contiguous file on disk (`ev_cumulative.bin`):
* The engine loads **only** the `ev_cumulative` file off disk. All other columns are completely bypassed.
* The query executor uses SIMD (Single Instruction Multiple Data, e.g. AVX-512) vectorized CPU instructions to sum 8 floating-point numbers per CPU cycle.
* Read volume drops from 6.5 GB to ~430 MB (uncompressed), and memory scan throughput reaches 30+ GB/sec, returning in **5–15 milliseconds**.

#### 3. Why Columnar Compression Exceeds 85%
* **Homogeneous Data Types:** Consecutive entries in `ev_cumulative` are similar numbers or slowly incrementing monotonic sequences.
* **DoubleDelta / T64 Encoding:** Instead of storing raw numbers, ClickHouse stores the second derivative (the change in the change) between successive daily cumulative numbers, compressing long series of identical daily increments into bits.
* **Dictionary Encoding:** Categorical keys (`project_key`, `wbs_key`) repeat millions of times and compress down to 1–2 bytes.

### Solution 5: Star Schema DDL for Resource Time-Phased Spreads

```sql
-- 1. Dimension Table: Resources
CREATE TABLE dim_resource (
    resource_key     INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    resource_id_uuid UUID NOT NULL,
    resource_code    VARCHAR(32) NOT NULL,
    resource_name    VARCHAR(255) NOT NULL,
    resource_type    VARCHAR(32) NOT NULL, -- 'LABOR', 'NON_LABOR', 'MATERIAL'
    trade_category   VARCHAR(64) NOT NULL, -- 'CIVIL', 'ELECTRICAL', 'MECHANICAL'
    contractor_name  VARCHAR(150) NOT NULL,
    hourly_rate      NUMERIC(10, 2) NOT NULL,
    is_active        BOOLEAN NOT NULL DEFAULT TRUE
);

-- 2. Fact Table: Daily Resource Spread
CREATE TABLE fact_resource_daily_spread (
    date_key          INT NOT NULL REFERENCES dim_calendar_date(date_key),
    project_key       INT NOT NULL REFERENCES dim_project(project_key),
    activity_key      INT NOT NULL REFERENCES dim_activity(activity_key),
    resource_key      INT NOT NULL REFERENCES dim_resource(resource_key),
    
    budgeted_hours    NUMERIC(10, 2) NOT NULL DEFAULT 0.00,
    actual_hours      NUMERIC(10, 2) NOT NULL DEFAULT 0.00,
    remaining_hours   NUMERIC(10, 2) NOT NULL DEFAULT 0.00,
    earned_hours      NUMERIC(10, 2) NOT NULL DEFAULT 0.00,
    
    actual_cost       NUMERIC(12, 2) NOT NULL DEFAULT 0.00,
    earned_cost       NUMERIC(12, 2) NOT NULL DEFAULT 0.00,
    
    PRIMARY KEY (date_key, activity_key, resource_key)
) PARTITION BY RANGE (date_key);

-- 3. Labor Burn Rate Query for Civil Piling Crew (Last 30 Days)
SELECT
    r.resource_code,
    r.resource_name,
    r.contractor_name,
    SUM(f.actual_hours) AS total_actual_hours,
    SUM(f.earned_hours) AS total_earned_hours,
    CASE 
        WHEN SUM(f.earned_hours) > 0 
        THEN ROUND(SUM(f.actual_hours) / SUM(f.earned_hours), 2)
        ELSE NULL 
    END AS labor_burn_rate_ratio
FROM fact_resource_daily_spread f
JOIN dim_resource r ON f.resource_key = r.resource_key
JOIN dim_calendar_date d ON f.date_key = d.date_key
WHERE r.trade_category = 'CIVIL'
  AND d.full_date >= CURRENT_DATE - INTERVAL '30 days'
GROUP BY r.resource_key, r.resource_code, r.resource_name, r.contractor_name
ORDER BY labor_burn_rate_ratio DESC NULLS LAST;
```

### Solution 6: Materialized Views and Rollup Acceleration in ClickHouse

```sql
-- 1. ClickHouse Fact Table
CREATE TABLE fact_daily_activity_snapshot_ch (
    snapshot_date Date,
    project_key UInt32,
    wbs_key UInt32,
    activity_key UInt32,
    pv_daily Float64,
    pv_cumulative Float64,
    ev_daily Float64,
    ev_cumulative Float64,
    ac_daily Float64,
    ac_cumulative Float64,
    remaining_duration_hours Int32,
    total_float_hours Int32,
    is_critical UInt8
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(snapshot_date)
ORDER BY (project_key, wbs_key, snapshot_date, activity_key);

-- 2. Materialized View backed by SummingMergeTree
CREATE MATERIALIZED VIEW mv_weekly_earned_value
ENGINE = SummingMergeTree()
PRIMARY KEY (project_key, week_start_date)
AS SELECT
    project_key,
    toMonday(snapshot_date) AS week_start_date,
    sum(pv_daily) AS weekly_pv,
    sum(ev_daily) AS weekly_ev,
    sum(ac_daily) AS weekly_ac
FROM fact_daily_activity_snapshot_ch
GROUP BY project_key, week_start_date;
```

#### 3. How SummingMergeTree Consolidates Metrics
* When new rows are inserted into the source table, the materialized view trigger calculates the aggregates and writes them into temporary sorted data parts.
* In the background, ClickHouse executes asynchronous merge passes (`MergeTree` engine). During a merge, any rows with identical primary keys (`project_key, week_start_date`) are collapsed into a single row, summing all numeric metric columns (`weekly_pv`, `weekly_ev`, `weekly_ac`).

### Solution 7: Monthly Executive EVM Reporting SQL

```sql
WITH latest_monthly_snapshots AS (
    SELECT
        f.project_key,
        TO_CHAR(d.full_date, 'YYYY-MM') AS report_month,
        d.full_date,
        f.pv_cumulative,
        f.ev_cumulative,
        f.ac_cumulative,
        f.total_float_hours,
        f.is_critical,
        ROW_NUMBER() OVER (
            PARTITION BY f.project_key, TO_CHAR(d.full_date, 'YYYY-MM'), f.activity_key
            ORDER BY d.full_date DESC
        ) AS rn
    FROM fact_daily_activity_snapshot f
    JOIN dim_calendar_date d ON f.snapshot_date_key = d.date_key
)
SELECT
    p.project_code,
    p.project_name,
    s.report_month,
    ROUND(SUM(s.pv_cumulative), 2) AS cumulative_pv,
    ROUND(SUM(s.ev_cumulative), 2) AS cumulative_ev,
    ROUND(SUM(s.ac_cumulative), 2) AS cumulative_ac,
    
    -- Cost & Schedule Variance
    ROUND(SUM(s.ev_cumulative) - SUM(s.ac_cumulative), 2) AS cost_variance,
    ROUND(SUM(s.ev_cumulative) - SUM(s.pv_cumulative), 2) AS schedule_variance,
    
    -- Performance Indices with zero-guarding
    CASE 
        WHEN SUM(s.ac_cumulative) > 0 THEN ROUND(SUM(s.ev_cumulative) / SUM(s.ac_cumulative), 3)
        ELSE 1.000 
    END AS cpi,
    
    CASE 
        WHEN SUM(s.pv_cumulative) > 0 THEN ROUND(SUM(s.ev_cumulative) / SUM(s.pv_cumulative), 3)
        ELSE 1.000 
    END AS spi,
    
    -- Count of Critical Activities in Delay (Negative Float)
    COUNT(*) FILTER (WHERE s.is_critical = TRUE AND s.total_float_hours < 0) AS critical_activities_delayed

FROM latest_monthly_snapshots s
JOIN dim_project p ON s.project_key = p.project_key
WHERE s.rn = 1 -- Only the final snapshot of each month
  AND p.project_code = 'PRJ-SURYA-100'
GROUP BY p.project_code, p.project_name, s.report_month
ORDER BY s.report_month;
```

## 💻 Section C: ETL Pipelines & Golang Implementation

### Solution 8: High-Throughput Ingestion with PostgreSQL Binary Protocol

#### 1. Why `INSERT` Statements Fail Under High Volumes
Executing standard SQL `INSERT` statements requires the server to parse SQL text, plan the statement, serialize results, and flush WAL logs for each network transaction. Even multi-value batch inserts require parsing megabytes of SQL text, topping out at ~5,000–8,000 rows/second.

#### 2. PostgreSQL Binary `COPY` Protocol
PostgreSQL's `COPY ... FROM STDIN WITH (FORMAT binary)` stream sends pre-serialized binary representations of datatypes directly into the storage engine. It bypasses the SQL parser, statement re-writing, and query planner, achieving write speeds exceeding **250,000 rows/second**.

#### 3. Production Golang `pgx.CopyFrom` Implementation

```go
package bi

import (
	"context"
	"fmt"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgxpool"
)

type Snapshot struct {
	DateKey             int
	ProjectKey          int
	WBSKey              int
	ActivityKey         int
	PVDaily             float64
	PVCumulative        float64
	EVDaily             float64
	EVCumulative        float64
	ACDaily             float64
	ACCumulative        float64
	RemainingDurationHrs int
	TotalFloatHrs       int
	FreeFloatHrs        int
	IsCritical          bool
}

// IngestSnapshotsBinary streams bulk snapshots directly into PostgreSQL via binary COPY.
func IngestSnapshotsBinary(ctx context.Context, pool *pgxpool.Pool, records []Snapshot) error {
	conn, err := pool.Acquire(ctx)
	if err != nil {
		return fmt.Errorf("failed to acquire connection: %w", err)
	}
	defer conn.Release()

	// Convert slice to pgx.CopyFromRows format
	rows := make([][]interface{}, len(records))
	for i, r := range records {
		rows[i] = []interface{}{
			r.DateKey, r.ProjectKey, r.WBSKey, r.ActivityKey,
			r.PVDaily, r.PVCumulative, r.EVDaily, r.EVCumulative,
			r.ACDaily, r.ACCumulative, r.RemainingDurationHrs,
			r.TotalFloatHrs, r.FreeFloatHrs, r.IsCritical,
		}
	}

	cols := []string{
		"snapshot_date_key", "project_key", "wbs_key", "activity_key",
		"pv_daily", "pv_cumulative", "ev_daily", "ev_cumulative",
		"ac_daily", "ac_cumulative", "remaining_duration_hours",
		"total_float_hours", "free_float_hours", "is_critical",
	}

	count, err := conn.CopyFrom(
		ctx,
		pgx.Identifier{"fact_daily_activity_snapshot"},
		cols,
		pgx.CopyFromRows(rows),
	)
	if err != nil {
		return fmt.Errorf("binary copy failed: %w", err)
	}

	if int(count) != len(records) {
		return fmt.Errorf("mismatched row count: copied %d of %d", count, len(records))
	}

	return nil
}
```

### Solution 9: Golang SCD Type 2 Key Resolver Service

```go
package bi

import (
	"errors"
	"sync"
	"time"
)

type SCDRecord struct {
	ActivityKey   int
	EffectiveFrom time.Time
	EffectiveTo   time.Time
}

type SCDKeyResolver struct {
	mu    sync.RWMutex
	cache map[string][]SCDRecord // ActivityUUID -> Sorted slice of versions
}

func NewSCDKeyResolver() *SCDKeyResolver {
	return &SCDKeyResolver{
		cache: make(map[string][]SCDRecord),
	}
}

// ResolveActivityKey looks up the surrogate key active at snapshotTime in O(log V) or O(1).
func (r *SCDKeyResolver) ResolveActivityKey(activityUUID string, snapshotTime time.Time) (int, error) {
	r.mu.RLock()
	defer r.mu.RUnlock()

	versions, exists := r.cache[activityUUID]
	if !exists || len(versions) == 0 {
		return 0, errors.New("activity UUID not found in SCD cache")
	}

	// Linear scan across version history (typically 1-3 revisions per activity)
	for _, v := range versions {
		if !snapshotTime.Before(v.EffectiveFrom) && snapshotTime.Before(v.EffectiveTo) {
			return v.ActivityKey, nil
		}
	}

	return 0, errors.New("no matching SCD version valid for snapshot timestamp")
}

// UpdateRevision atomically invalidates and updates the cache.
func (r *SCDKeyResolver) UpdateRevision(activityUUID string, updatedVersions []SCDRecord) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.cache[activityUUID] = updatedVersions
}
```

### Solution 10: Event-Driven Schedule CDC Pipeline Architecture

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                      EVENT-DRIVEN SCHEDULE CDC PIPELINE ARCHITECTURE                             │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   [Next.js App / Go Engine]                                                                      │
│             │                                                                                    │
│             ▼ (ACID Writes)                                                                      │
│   [PostgreSQL Operational DB]                                                                    │
│             │                                                                                    │
│             ▼ (WAL Replication)                                                                  │
│   [Debezium CDC Connector] ──> Extracts row before/after states from Postgres WAL                │
│             │                                                                                    │
│             ▼ (JSON / Avro Messages)                                                             │
│   [Apache Kafka Cluster]                                                                         │
│     Topic: p6.operational.tasks (Key: activity_id)                                               │
│             │                                                                                    │
│             ▼                                                                                    │
│   [Go ETL Consumer Service]                                                                      │
│     1. Resolves SCD Type 2 surrogate keys via in-memory cache.                                   │
│     2. Computes time-phased daily spread arrays.                                                 │
│     3. Batches records into micro-batches of 10,000.                                             │
│             │                                                                                    │
│             ▼ (Vectorized Ingestion)                                                             │
│   [ClickHouse OLAP Warehouse] ──> Power BI / Next.js Executive Dashboards (< 15ms)               │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

1. **Idempotency & Out-of-Order Handling:**
   - Messages in Kafka use `activity_id` as the message key, ensuring all state changes for an activity route to the same Kafka partition in strict sequential order.
   - ClickHouse uses the `ReplacingMergeTree` engine with a monotonic version/timestamp column. If a retry event arrives late, ClickHouse automatically deduplicates and replaces older states.
2. **Schema Evolution:**
   - Debezium registers event schemas in the Confluent Schema Registry (using Avro or Protobuf).
   - Adding a new UDF column uses backward-compatible default values, allowing consumer services to consume both legacy and updated records without pipeline stoppage.
