# Topic 10.3: Enterprise BI & Reporting Schemas

## 1. Executive Summary & Plain-English Analogy

### 1.1 The Cash Register vs. The Executive Balance Sheet
Imagine running a massive retail conglomerate with 500 supermarkets across the country. 
* At the store checkout counter, a **Point of Sale (POS) Cash Register** records individual barcode scans: one bottle of milk, one loaf of bread, one pack of batteries. It must read and write single records in microseconds, update store inventory, and handle 10,000 cashier checkouts simultaneously. This is **OLTP (Online Transaction Processing)**, traditionally modeled using Third Normal Form (3NF).
* At corporate headquarters, the **Chief Financial Officer (CFO)** asks: *"What was our gross margin trend on organic dairy across the northern region over the past three fiscal years, grouped by store square footage and supplier contract type?"*

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                   OLTP (OPERATIONAL P6) vs. OLAP (ENTERPRISE BI WAREHOUSE)                       │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   OPERATIONAL TRANSACTIONAL SYSTEM (OLTP - 3NF)    ENTERPRISE ANALYTICAL DATA WAREHOUSE (OLAP)   │
│   (Oracle Primavera P6 Operational Database)       (Star Schema / ClickHouse / BigQuery)         │
│                                                                                                  │
│   ┌────────────────────────────────────────┐       ┌─────────────────────────────────────────┐   │
│   │ TASK, PROJWBS, TASKPRED, TASKRSRC      │       │ FACT_DAILY_ACTIVITY_SNAPSHOT            │   │
│   │ Highly normalized (3NF).               │       │ Star Schema / Columnar storage.         │   │
│   │ Optimized for row-level ACID writes:   │       │ Optimized for aggregate range scans:    │   │
│   │ "Update remaining duration of Act 42." │       │ "Sum EV across 50,000 tasks over 2 yrs."│   │
│   │                                        │       │                                         │   │
│   │ Running an EVM trend query requires    │       │ Analytical queries scan pre-flattened   │   │
│   │ joining 14 tables with recursive CTEs. │       │ facts and dimensions in < 15ms.         │   │
│   │ Database CPU hits 100%, locking users! │       │ Zero locking on operational database.   │   │
│   └────────────────────────────────────────┘       └─────────────────────────────────────────┘   │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

In software engineering terms:
* **Operational P6 databases** (Oracle or SQL Server running under P6 EPPM) prioritize **transaction integrity, row locks, and minimal data redundancy**.
* **Enterprise BI Systems** (Power BI, Tableau, Looker, Next.js executive portals) require **denormalized Star Schemas or columnar data warehouses** optimized for multi-dimensional aggregation across time, WBS, EPS, and resource domains.

Attempting to run real-time executive portfolio dashboards directly against a live P6 3NF operational database will crash the production scheduling engine.

## 2. Why Operational 3NF Schemas Fail Analytical Reporting

In Oracle Primavera P6 operational schemas, scheduling data is decomposed across dozens of relational tables: `PROJECT`, `PROJWBS`, `TASK`, `TASKPRED`, `TASKRSRC`, `RSRC`, `CALENDAR`, `UDFVALUE`.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                       THE OPERATIONAL 3NF QUERY PERFORMANCE BOTTLENECK                           │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   [PROJECT] ──(1:N)──> [PROJWBS] ──(1:N)──> [TASK] ──(1:N)──> [TASKRSRC] ──(N:1)──> [RSRC]      │
│                            │                   │                                                 │
│                            └──(Recursive)      ├──(1:N)──> [TASKPRED]                            │
│                                                └──(1:N)──> [UDFVALUE] ──(N:1)──> [UDFTYPE]       │
│                                                                                                  │
│   To compute a simple Monthly Earned Value curve by Contractor across 50 projects:               │
│   1. The SQL engine must perform a 9-way table join.                                             │
│   2. The WBS tree requires a RECURSIVE Common Table Expression (CTE).                            │
│   3. P6 does NOT store daily time-phased cost spreads in tables; it calculates them DYNAMICALLY  │
│      in memory using calendar workweek matrices!                                                 │
│   4. Result: A single dashboard refresh scans 20,000,000 rows, taking 45 seconds!                │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

Three critical architectural limitations make live 3NF querying unacceptable for BI:
1. **Dynamic Time-Phasing:** Operational P6 stores total budget and remaining duration, but **does not store historical daily planned value curves**. Daily spreads are synthesized on the fly by traversing calendar working hours.
2. **Loss of Historical State:** Operational tables store current state. When an engineer updates an activity's duration from 30 days to 45 days, the old value is overwritten. Without dedicated snapshot warehousing, tracking historical baseline drift is impossible.
3. **Lock Contention:** Heavy analytical aggregations take read locks across `TASK` and `TASKRSRC`, blocking concurrent schedulers from saving updates.

## 3. Dimensional Modeling: The Enterprise Scheduling Star Schema

To achieve sub-second analytical reporting, we model project schedules using a **Kimball Star Schema**.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                           THE ENTERPRISE SCHEDULING STAR SCHEMA                                  │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│       ┌──────────────────────┐                    ┌──────────────────────┐                       │
│       │     DIM_PROJECT      │                    │       DIM_WBS        │                       │
│       ├──────────────────────┤                    ├──────────────────────┤                       │
│       │ project_key (PK)     │                    │ wbs_key (PK)         │                       │
│       │ project_code         │                    │ wbs_code             │                       │
│       │ eps_path             │                    │ wbs_level            │                       │
│       │ business_unit        │                    │ parent_wbs_code      │                       │
│       └──────────┬───────────┘                    └──────────┬───────────┘                       │
│                  │                                           │                                   │
│                  │           ┌──────────────────────┐        │                                   │
│                  └──────────>│      FACT_DAILY_     │<───────┘                                   │
│                              │   ACTIVITY_SNAPSHOT  │                                            │
│                  ┌──────────>│                      │<───────┐                                   │
│                  │           ├──────────────────────┤        │                                   │
│                  │           │ snapshot_date_key(FK)│        │                                   │
│       ┌──────────┴───────────┤ project_key (FK)     ├────────┴───────────┐                       │
│       │     DIM_ACTIVITY     │ wbs_key (FK)         │  DIM_CALENDAR_DATE │                       │
│       ├──────────────────────┤ activity_key (FK)    ├────────────────────┤                       │
│       │ activity_key (PK)    │ planned_value_cum    │ date_key (PK)      │                       │
│       │ activity_code        │ earned_value_cum     │ full_date          │                       │
│       │ activity_name        │ actual_cost_cum      │ fiscal_year        │                       │
│       │ constraint_type      │ remaining_duration   │ fiscal_quarter     │                       │
│       │ is_critical          │ total_float_days     │ is_working_day     │                       │
│       └──────────────────────┴──────────────────────┴────────────────────┘                       │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.1 Core Fact Tables

#### 1. `fact_daily_activity_snapshot`
Captures the cumulative and daily incremental progress metrics for every active activity on every calendar day:
* **Grain:** One row per activity per calendar date per baseline snapshot.
* **Measures:**
  - `planned_value_daily` / `planned_value_cumulative` ($PV$)
  - `earned_value_daily` / `earned_value_cumulative` ($EV$)
  - `actual_cost_daily` / `actual_cost_cumulative` ($AC$)
  - `remaining_duration_hours`
  - `total_float_hours`
  - `free_float_hours`
  - `is_critical` (0 or 1)

#### 2. `fact_earned_value_monthly`
Aggregated rollup table for executive portfolio dashboards:
* **Grain:** One row per WBS work package per calendar month.
* **Measures:** Monthly $PV$, $EV$, $AC$, Cost Variance ($CV = EV - AC$), Schedule Variance ($SV = EV - PV$), $CPI$, $SPI$, Estimate at Completion ($EAC$).

#### 3. `fact_resource_daily_spread`
Tracks labor hours, equipment quantities, and costs time-phased by day:
* **Grain:** One row per activity-resource assignment per calendar date.
* **Measures:** `budgeted_hours_spread`, `actual_hours_spread`, `remaining_hours_spread`, `budgeted_cost_spread`, `actual_cost_spread`.

### 3.2 Core Dimension Tables

#### 1. `dim_project`
Contains project metadata, EPS hierarchy path, contract type (EPC, BoP, Turnkey), target COD, and current status.

#### 2. `dim_wbs`
Pre-flattens the hierarchical WBS tree up to 8 levels deep (`wbs_l1_name`, `wbs_l2_name`, `wbs_l3_name`), eliminating recursive CTEs during report rendering.

#### 3. `dim_activity`
Descriptive activity attributes: activity code, name, primary constraint, activity type (Task Dependent, Resource Dependent, Start Milestone, Finish Milestone), calendar reference.

#### 4. `dim_resource`
Resource attributes: resource code, resource name, trade/craft classification (Civil, Mechanical, Electrical), hourly billing rate, contracting firm.

#### 5. `dim_calendar_date`
Enterprise date dimension: date key (`20261010`), calendar date, fiscal year, fiscal quarter, week number, working day flag per project calendar.

## 4. Tracking Schedule Drift with Slowly Changing Dimensions (SCD Type 2)

In enterprise scheduling, projects undergo contractual revisions:
* Baseline B00 (Original Contract Award)
* Baseline B01 (Approved Scope Change: Addition of 20MW Inverter Block)
* Baseline B02 (Monsoon Extension Claim)

If `dim_activity` only stored current state, historical reports would apply the *new* budget retroactively to past performance periods, distorting audited Earned Value metrics.

### 4.1 SCD Type 2 Architecture
We implement **Slowly Changing Dimensions Type 2 (SCD2)** on `dim_activity` and `dim_wbs`:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                           SLOWLY CHANGING DIMENSION TYPE 2 (SCD2)                                │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   DIM_ACTIVITY TABLE:                                                                            │
│   ┌──────┬──────────┬─────────────┬─────────────┬─────────────┬────────────┬───────────┐         │
│   │SK_ID │ Act_Code │ Original_Dur│ Budgeted_Cost│ Effective_From│ Expire_Date │ Is_Current│         │
│   ├──────┼──────────┼─────────────┼─────────────┼─────────────┼────────────┼───────────┤         │
│   │101   │ ACT-100  │ 20 days     │ $50,000     │ 01-Jan-2026 │ 30-Mar-2026│ FALSE     │(Rev B00)│
│   │102   │ ACT-100  │ 28 days     │ $65,000     │ 31-Mar-2026 │ 99-99-9999 │ TRUE      │(Rev B01)│
│   └──────┴──────────┴─────────────┴─────────────┴─────────────┴────────────┴───────────┘         │
│                                                                                                  │
│   FACT RECORDS LINK TO SURROGATE KEY (SK_ID):                                                    │
│   * January snapshots point to SK 101. Past reports accurately reflect the $50,000 budget!       │
│   * April snapshots point to SK 102. Current reports accurately reflect the $65,000 budget!      │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

## 5. Production Database Schemas: PostgreSQL Star Schema

Below is the production DDL for deploying the scheduling data warehouse in PostgreSQL.

```sql
-- ============================================================================
-- 1. DIMENSION TABLES
-- ============================================================================

CREATE TABLE dim_calendar_date (
    date_key         INT PRIMARY KEY, -- Format: YYYYMMDD (e.g. 20261010)
    full_date        DATE NOT NULL UNIQUE,
    day_of_week      SMALLINT NOT NULL,
    day_name         VARCHAR(10) NOT NULL,
    calendar_month   SMALLINT NOT NULL,
    month_name       VARCHAR(10) NOT NULL,
    calendar_year    SMALLINT NOT NULL,
    fiscal_quarter   VARCHAR(6) NOT NULL,
    fiscal_year      SMALLINT NOT NULL,
    is_weekend       BOOLEAN NOT NULL
);

CREATE TABLE dim_project (
    project_key      INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    project_id_uuid  UUID NOT NULL,
    project_code     VARCHAR(32) NOT NULL,
    project_name     VARCHAR(255) NOT NULL,
    eps_path         VARCHAR(500) NOT NULL,
    business_unit    VARCHAR(100) NOT NULL,
    contract_type    VARCHAR(50) NOT NULL,
    baseline_code    VARCHAR(32) NOT NULL DEFAULT 'CURRENT',
    planned_cod      DATE,
    created_at       TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE dim_wbs (
    wbs_key          INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    wbs_id_uuid      UUID NOT NULL,
    project_key      INT REFERENCES dim_project(project_key),
    wbs_code         VARCHAR(100) NOT NULL,
    wbs_name         VARCHAR(255) NOT NULL,
    wbs_level        SMALLINT NOT NULL,
    wbs_l1_name      VARCHAR(255),
    wbs_l2_name      VARCHAR(255),
    wbs_l3_name      VARCHAR(255),
    is_work_package  BOOLEAN NOT NULL DEFAULT FALSE
);

-- SCD Type 2 Dimension for Activity
CREATE TABLE dim_activity (
    activity_key     INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    activity_id_uuid UUID NOT NULL,
    project_key      INT REFERENCES dim_project(project_key),
    wbs_key          INT REFERENCES dim_wbs(wbs_key),
    activity_code    VARCHAR(32) NOT NULL,
    activity_name    VARCHAR(255) NOT NULL,
    activity_type    VARCHAR(32) NOT NULL,
    constraint_type  VARCHAR(32) NOT NULL,
    original_duration_days INT NOT NULL,
    budgeted_cost    NUMERIC(14, 2) NOT NULL,
    
    -- SCD Type 2 Metadata
    effective_from   TIMESTAMP WITH TIME ZONE NOT NULL,
    effective_to     TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT '9999-12-31 23:59:59+00',
    is_current       BOOLEAN NOT NULL DEFAULT TRUE,
    revision_reason  VARCHAR(255)
);

CREATE INDEX idx_dim_act_scd2 ON dim_activity (activity_id_uuid, is_current);

-- ============================================================================
-- 2. FACT TABLES
-- ============================================================================

CREATE TABLE fact_daily_activity_snapshot (
    snapshot_date_key INT NOT NULL REFERENCES dim_calendar_date(date_key),
    project_key       INT NOT NULL REFERENCES dim_project(project_key),
    wbs_key           INT NOT NULL REFERENCES dim_wbs(wbs_key),
    activity_key      INT NOT NULL REFERENCES dim_activity(activity_key),
    
    -- Earned Value Measures (Monetary Units)
    pv_daily          NUMERIC(14, 2) NOT NULL DEFAULT 0.00,
    pv_cumulative     NUMERIC(14, 2) NOT NULL DEFAULT 0.00,
    ev_daily          NUMERIC(14, 2) NOT NULL DEFAULT 0.00,
    ev_cumulative     NUMERIC(14, 2) NOT NULL DEFAULT 0.00,
    ac_daily          NUMERIC(14, 2) NOT NULL DEFAULT 0.00,
    ac_cumulative     NUMERIC(14, 2) NOT NULL DEFAULT 0.00,
    
    -- Duration and Float Measures
    remaining_duration_hours INT NOT NULL,
    total_float_hours        INT NOT NULL,
    free_float_hours         INT NOT NULL,
    is_critical              BOOLEAN NOT NULL,
    
    PRIMARY KEY (snapshot_date_key, activity_key)
) PARTITION BY RANGE (snapshot_date_key);

-- Sample Partition for 2026 Q4
CREATE TABLE fact_daily_snapshot_2026_q4 PARTITION OF fact_daily_activity_snapshot
    FOR VALUES FROM (20261001) TO (20270101);

CREATE INDEX idx_fact_daily_proj ON fact_daily_activity_snapshot (project_key, snapshot_date_key);
```

## 6. Analytical Warehouses: ClickHouse Columnar Optimization

While PostgreSQL supports partitioned star schemas, multi-gigabyte enterprise schedules with 100,000 activities tracked daily generate **36,500,000 rows per year**. Under such volumes, columnar engines such as **ClickHouse** or **DuckDB** deliver 50x–100x query speedups.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                         ROW-ORIENTED (POSTGRES) vs. COLUMNAR (CLICKHOUSE)                        │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   ROW-ORIENTED (POSTGRESQL):                                                                     │
│   [Date, Proj, Act, PV_cum, EV_cum, AC_cum, Float] ──> [Date, Proj, Act, PV_cum, EV_cum, ...]    │
│   To sum EV_cum across 10 million rows, Postgres MUST load ALL 7 columns off disk into RAM.      │
│                                                                                                  │
│   COLUMNAR STORAGE (CLICKHOUSE):                                                                 │
│   Column 1 (Date):   [20261001, 20261001, ...] (Compressed with DoubleDelta)                     │
│   Column 2 (EV_cum): [12000.50, 12400.00, ...] (Compressed with Gorilla / ZSTD)                 │
│   ClickHouse loads ONLY Column 2 into L3 CPU cache using SIMD vectorized AVX-512 instructions.   │
│   10 Million rows aggregated in 4.2 milliseconds!                                                │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 6.1 ClickHouse DDL & Materialized View
```sql
CREATE TABLE fact_daily_activity_snapshot_ch (
    snapshot_date Date,
    project_key UInt32,
    wbs_key UInt32,
    activity_key UInt32,
    pv_daily Float64,
    pv_cumulative Float64,
    ev_daily Float64,
    ev_cumulative Float64,
    ac_daily Float64,
    ac_cumulative Float64,
    remaining_duration_hours Int32,
    total_float_hours Int32,
    is_critical UInt8
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(snapshot_date)
ORDER BY (project_key, wbs_key, snapshot_date, activity_key);

-- Pre-aggregated Materialized View for instant monthly portfolio rollups
CREATE MATERIALIZED VIEW mv_monthly_project_evm
ENGINE = SummingMergeTree()
PRIMARY KEY (project_key, year_month)
AS SELECT
    project_key,
    toStartOfMonth(snapshot_date) AS year_month,
    sum(pv_daily) AS total_pv_month,
    sum(ev_daily) AS total_ev_month,
    sum(ac_daily) AS total_ac_month,
    max(ev_cumulative) AS month_ending_ev
FROM fact_daily_activity_snapshot_ch
GROUP BY project_key, year_month;
```

## 7. Real-World Case Study: Surya 100MW Solar IPP Dashboard Queries

Let us observe the power of the dimensional star schema in answering real-world executive queries for the Surya 100MW project.

### 7.1 Real-Time Portfolio S-Curve Query
Generate the cumulative Planned Value, Earned Value, and Actual Cost curve over time:

```sql
SELECT
    d.full_date,
    SUM(f.pv_cumulative) AS portfolio_pv,
    SUM(f.ev_cumulative) AS portfolio_ev,
    SUM(f.ac_cumulative) AS portfolio_ac,
    ROUND(SUM(f.ev_cumulative) / NULLIF(SUM(f.ac_cumulative), 0), 2) AS portfolio_cpi,
    ROUND(SUM(f.ev_cumulative) / NULLIF(SUM(f.pv_cumulative), 0), 2) AS portfolio_spi
FROM fact_daily_activity_snapshot f
JOIN dim_calendar_date d ON f.snapshot_date_key = d.date_key
JOIN dim_project p ON f.project_key = p.project_key
WHERE p.project_code = 'PRJ-SURYA-100'
  AND d.full_date BETWEEN '2026-01-01' AND '2026-10-10'
GROUP BY d.full_date
ORDER BY d.full_date;
```
Execution time: **8ms** on ClickHouse, **32ms** on PostgreSQL partitioned table.

## 8. High-Performance Golang ETL Snapshot Pipeline

This Go service extracts daily scheduling metrics from the operational engine, resolves SCD Type 2 dimension keys, and streams batch inserts into the data warehouse using `pgx.CopyFrom`.

```go
package bi

import (
	"context"
	"fmt"
	"time"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgxpool"
)

// DailyActivityRecord represents the daily snapshot grain.
type DailyActivityRecord struct {
	DateKey             int
	ProjectKey          int
	WBSKey              int
	ActivityKey         int
	PVDaily             float64
	PVCumulative        float64
	EVDaily             float64
	EVCumulative        float64
	ACDaily             float64
	ACCumulative        float64
	RemainingDurationHrs int
	TotalFloatHrs       int
	FreeFloatHrs        int
	IsCritical          bool
}

// SnapshotBatchPipeline handles bulk streaming ETL.
type SnapshotBatchPipeline struct {
	pool *pgxpool.Pool
}

func NewSnapshotBatchPipeline(pool *pgxpool.Pool) *SnapshotBatchPipeline {
	return &SnapshotBatchPipeline{pool: pool}
}

// BulkStreamSnapshots streams 50,000+ daily snapshots using PostgreSQL binary COPY.
func (p *SnapshotBatchPipeline) BulkStreamSnapshots(ctx context.Context, records []DailyActivityRecord) error {
	conn, err := p.pool.Acquire(ctx)
	if err != nil {
		return fmt.Errorf("failed to acquire db connection: %w", err)
	}
	defer conn.Release()

	rows := make([][]interface{}, len(records))
	for i, r := range records {
		rows[i] = []interface{}{
			r.DateKey,
			r.ProjectKey,
			r.WBSKey,
			r.ActivityKey,
			r.PVDaily,
			r.PVCumulative,
			r.EVDaily,
			r.EVCumulative,
			r.ACDaily,
			r.ACCumulative,
			r.RemainingDurationHrs,
			r.TotalFloatHrs,
			r.FreeFloatHrs,
			r.IsCritical,
		}
	}

	columnNames := []string{
		"snapshot_date_key", "project_key", "wbs_key", "activity_key",
		"pv_daily", "pv_cumulative", "ev_daily", "ev_cumulative",
		"ac_daily", "ac_cumulative", "remaining_duration_hours",
		"total_float_hours", "free_float_hours", "is_critical",
	}

	copySource := pgx.CopyFromRows(rows)
	count, err := conn.CopyFrom(
		ctx,
		pgx.Identifier{"fact_daily_activity_snapshot"},
		columnNames,
		copySource,
	)
	if err != nil {
		return fmt.Errorf("bulk copy failed: %w", err)
	}

	fmt.Printf("Successfully loaded %d daily snapshot rows into warehouse in %v\n", count, time.Now())
	return nil
}
```

## 9. Industry Pitfalls & Anti-Patterns

### 9.1 Pitfall 1: Querying the Operational 3NF DB for Next.js Dashboards
* **The Anti-Pattern:** A Next.js API route performs a 10-table join against live P6 tables every time an executive refreshes their browser.
* **Why it Breaks Systems:** Executive dashboards refresh every morning at 09:00 AM. 50 project directors opening dashboards simultaneously trigger hundreds of table scans, exhausting connection pools and causing transaction rollbacks for field schedulers.
* **The Rule:** Strictly decouple operational scheduling from reporting via an ETL pipeline to an isolated analytical data warehouse or read-replica.

### 9.2 Pitfall 2: Overwriting Baseline Budgets (SCD Type 1 Anti-Pattern)
* **The Anti-Pattern:** When an activity's budget is revised from \$100k to \$150k, the ETL simply executes `UPDATE dim_activity SET budgeted_cost = 150000`.
* **Why it Breaks Systems:** Past monthly snapshots recalculate against \$150k, causing historical Planned Value to artificially surge retroactively. When statutory auditors examine Q1 filings, historical Earned Value charts no longer match past progress payments!
* **The Rule:** Always use **SCD Type 2** for scope-bearing dimensions. Close out the previous record (`is_current = FALSE`) and insert a new record with a new surrogate key.

### 9.3 Pitfall 3: Storing Floats as Text or Performing Dynamic Calendar Parsing
* **The Anti-Pattern:** An ETL attempts to compute working-day time spreads in Python or JavaScript dynamically inside the BI tool.
* **Why it Breaks Systems:** Calculating working calendar shifts across 100,000 activities in client-side JavaScript crashes the browser with out-of-memory errors.
* **The Rule:** Pre-calculate daily spreads in the Golang ETL engine and persist them as clean physical rows in the fact table.
