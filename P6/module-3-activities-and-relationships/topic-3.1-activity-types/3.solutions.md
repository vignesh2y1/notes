## 🏛️ Section A: Conceptual & Topological Foundations

### Solution 1: The Multi-Stage CPM Pipeline & LOE Isolation Proof

#### 1. Mathematical Proof of LOE Cycle Detection Hazard and Critical Path Corruption
Let the execution network be modeled as a directed graph $G = (V, E)$, where $V$ is the set of all activities and $E$ is the set of precedence relationships. 

Suppose we divide $V$ into two disjoint subsets:
* $V_{\text{core}}$: Physical execution activities (`Task Dependent`, `Resource Dependent`, `Milestones`).
* $V_{\text{loe}}$: Level of Effort (Hammock) activities.

An LOE activity $L \in V_{\text{loe}}$ derives its start from a set of predecessor boundary tasks $P(L) \subset V_{\text{core}}$ and its finish from a set of successor boundary tasks $S(L) \subset V_{\text{core}}$. In standard CPM modeling:
$$ES(L) = \min_{p \in P(L)} (EF_p \text{ or } ES_p)$$
$$EF(L) = \max_{s \in S(L)} (EF_s \text{ or } ES_s)$$

Now suppose a scheduler includes $L$ directly into a single-pass topological sort (such as Kahn's Algorithm):
1. **The Cycle Hazard**:
   To determine $EF(L)$, the engine requires the early dates of all tasks in $S(L)$. Thus, directed edges must exist from each $s \in S(L)$ into $L$ (to compute $EF(L)$), or from $L$ into each $s \in S(L)$ (if the user modeled them as outgoing successors).
   If the relationship is represented as $L \to s$ (an outgoing finish-to-finish tie), then in a topological ordering, $L$ must precede $s$. However, $L$ cannot calculate its finish until $s$ has finished! This creates an immediate circular dependency in the scheduling graph:
   $$\text{Dependency: } L \text{ requires } s \implies s \prec L$$
   $$\text{Graph Edge: } L \to s \implies L \prec s$$
   $$\implies s \prec L \prec s \quad \text{💥 Directed Cycle (Topological Deadlock)}$$

2. **The Critical Path Corruption**:
   If $L$ were allowed to participate in the backward pass as a standard driving node, its Late Dates would be computed as:
   $$LF(L) = \min_{(L, j) \in E} (LS_j - \text{Lag})$$
   If $L$ is connected to an activity with negative or near-zero float, $L$ would back-propagate late dates to its start predecessors $P(L)$, artificially constraining them. A support task (like daily site water misting) would dictate the early start of civil earthwork grading! This violates the physical reality of construction engineering.

#### 3. Mathematical Proof of LOE Total Float
By definition, an LOE activity does not have an independent calendar duration that constrains the project. In Primavera P6's Stage 2 hammock resolution:

1. **Early Dates**:
   $$ES_{\text{LOE}} = \min_{p \in P} (ES_p + \text{Lag}_{p})$$
   $$EF_{\text{LOE}} = \max_{s \in S} (EF_s + \text{Lag}_{s})$$
2. **Late Dates**:
   Because an LOE does not drive any independent project completion milestones, its Late Dates are bounded strictly by the latest acceptable completion of the activities it supports:
   $$LF_{\text{LOE}} = EF_{\text{LOE}}$$
   $$LS_{\text{LOE}} = ES_{\text{LOE}}$$
3. **Total Float ($TF$)**:
   $$\text{Total Float} = LF_{\text{LOE}} - EF_{\text{LOE}} = EF_{\text{LOE}} - EF_{\text{LOE}} \equiv 0$$
   Or equivalently:
   $$\text{Total Float} = LS_{\text{LOE}} - ES_{\text{LOE}} = ES_{\text{LOE}} - ES_{\text{LOE}} \equiv 0$$

**Why LOE Must NEVER Be Displayed as Critical:**
In CPM theory, an activity is critical if its delay directly delays the project completion date. An LOE activity has $TF = 0$ not because it is an inflexible bottleneck, but because its boundaries expand or contract dynamically to match the project's physical activities. If physical piling finishes 5 days late, the LOE automatically expands by 5 days. Marking an LOE in red as a critical activity is an industry antipattern because:
1. It confuses project executives by showing administrative overhead as the critical path driver.
2. It distorts Earned Value critical path indices.
3. In DCMA 14-point schedule compliance audits, LOE activities on the critical path trigger immediate audit failure.

### Solution 2: Calendar Resolution & Resource Dependent Multi-Resource Collisions

#### 1. Task Dependent vs Resource Dependent Forward Pass Evaluation
* **Task Dependent (`TT_Task`)**:
  The CPM engine evaluates the forward pass strictly against the **Activity's assigned calendar**. The assigned resources' personal calendars are ignored. If the activity calendar specifies Saturday as a 10-hour working day, work ticks forward for 10 hours on Saturday regardless of whether an assigned engineer's contract says Monday–Friday.
* **Resource Dependent (`TT_Rsrc`)**:
  The CPM engine evaluates the forward pass across the **calendars of the assigned driving resources**. The activity's own calendar is disregarded (except for the zero-resource fallback). Time only advances when the assigned resources are simultaneously available to perform work.

#### 2. Surya 100MW 220kV GIS Testing: Multi-Resource Working Time Intersection
The activity `ACT-ELE-5020 (220kV GIS Testing)` has three driving resources:
* **Resource 1 (Lead German Engineer)**: Mon–Fri, 08:00–16:00 (8 hrs/day, Sat–Sun off).
* **Resource 2 (Local Rigging Foreman)**: Mon–Sat, 07:00–18:00 with heat siesta 12:00–15:00 (10 hrs/day, Sun off).
* **Resource 3 (High-Voltage Injection Test Rig)**: Mon–Sun, 24 hrs/day.

To find when work can progress, the Go scheduling engine must compute the **set intersection of working intervals**:

$$\text{Valid Work Window} = \text{Calendar}_1 \cap \text{Calendar}_2 \cap \text{Calendar}_3$$

Let us analyze each day of the week:
1. **Sunday**:
   * Resource 1: Non-working.
   * Resource 2: Non-working.
   * Resource 3: Working.
   * **Intersection: 0 Working Hours.**
2. **Saturday**:
   * Resource 1: Non-working.
   * Resource 2: Working (10 hrs).
   * Resource 3: Working (24 hrs).
   * **Intersection: 0 Working Hours** (German engineer is off-shift).
3. **Monday through Friday**:
   * Resource 1 works: `[08:00, 16:00]`
   * Resource 2 works: `[07:00, 12:00]` and `[15:00, 18:00]` (Desert heat break between 12:00 and 15:00)
   * Resource 3 works: `[00:00, 24:00]`

Now compute the intraday intersection for Monday–Friday:
* Morning overlap:
  $$\text{Interval 1} = [08:00, 16:00] \cap [07:00, 12:00] = [08:00, 12:00] \implies 4 \text{ hours}$$
* Afternoon heat siesta: `[12:00, 15:00]` $\implies$ Resource 2 is off $\implies 0$ hours.
* Afternoon overlap:
  $$\text{Interval 2} = [08:00, 16:00] \cap [15:00, 18:00] = [15:00, 16:00] \implies 1 \text{ hour}$$
* Evening period: After 16:00, Resource 1 is off $\implies 0$ hours.

**Net Intersection Result:**
* The team can only achieve **5 effective working hours per calendar day** (08:00–12:00 and 15:00–16:00), strictly Monday through Friday.
* If the testing scope requires **40 net working hours**, the activity will consume:
  $$\frac{40 \text{ hours}}{5 \text{ hrs/day}} = 8 \text{ working days}$$
* Across real calendar time, 8 working days spans **12 calendar days** (Mon–Fri = 5 days, Sat–Sun pause = 2 days, Mon–Wed = 3 days).

#### 3. Engine Fallback Edge Case: Zero Resources Assigned
If an activity is marked as `Resource Dependent` in the database, but its `activity_resource_assignments` relation is empty:
* **The Mathematical Dilemma**: Without assigned resources, the set intersection of resource calendars is either undefined or the empty set ($\emptyset$), which would yield an infinite duration or division by zero.
* **The Primavera P6 Rule**: The scheduling engine automatically falls back to the **Activity's assigned calendar** (`activities.calendar_id`).
* **Implementation in Go**:
```go
func (s *CPMScheduler) resolveActivityCalendar(act *Activity) string {
    if act.Type == TypeResourceDependent && len(act.ResourceAssignments) > 0 {
        return act.ResourceAssignments[0].CalendarID // Or multi-resource intersection calendar
    }
    // Fallback to activity calendar
    return act.CalendarID
}
```

### Solution 3: Milestone Boundary Semantics & Next-Day Shift Push

#### 1. Timestamp Differences Relative to Shift Boundaries
In a professional CPM scheduling engine operating at minute-level resolution:
* **Start Milestone (`TT_StartMile`)**: Anchors to the **start of a working shift** (e.g., `08:00:00`). It represents the opening of a gate.
* **Finish Milestone (`TT_FinMile`)**: Anchors to the **end of a working shift** (e.g., `18:00:00`). It represents the closure or achievement of an event.

---

#### 2. Detailed Scenario Analysis: `ACT-CIV-1010` Finishing Friday at 18:00:00
* `ACT-CIV-1010: Site Boundary Fencing` finishes on **Friday, November 13, 2026, at 18:00:00**.
* Precedence tie: `ACT-CIV-1010` $\xrightarrow{FS, \text{lag}=0}$ `MS-CIV-COMP`.
* Successor task: `MS-CIV-COMP` $\xrightarrow{FS, \text{lag}=0}$ `ACT-CIV-1020: Piling Rig Mobilization`.
* Calendar: 6-Day week (Mon–Sat, 08:00 to 18:00; Sunday OFF).

```
Friday Nov 13                  Saturday Nov 14                Monday Nov 16
08:00                  18:00   08:00                  18:00   08:00                  18:00
┌──────────────────────────┐   ┌──────────────────────────┐   ┌──────────────────────────┐
│   ACT-CIV-1010 Work      │   │                          │   │   ACT-CIV-1020 Work      │
└──────────────────────────┘   └──────────────────────────┘   └──────────────────────────┘
                           ▲   ▲
                           │   │
             FINISH MILESTONE  START MILESTONE
             Nov 13 @ 18:00    Nov 14 @ 08:00 (Shift Boundary Push)
```

##### Case A: `MS-CIV-COMP` is a Finish Milestone
* **Calculated Early Date**: `2026-11-13 18:00:00` (Friday evening).
* **Successor Start (`ACT-CIV-1020`)**:
  * An FS link from a Finish Milestone at Friday 18:00:00 looks for the next available working minute on the successor's calendar.
  * The successor's next working shift opens on **Saturday, November 14, 2026, at 08:00:00**.
* **Integrity**: The milestone accurately records that civil fencing was completed on **Friday, Nov 13**.

##### Case B: `MS-CIV-COMP` is a Start Milestone
* **Calculated Early Date**:
  * A Start Milestone represents the start of work. Since `ACT-CIV-1010` finishes Friday at 18:00:00 (the end of working time), the Start Milestone cannot occur on Friday at 18:00:00 because non-working time begins immediately.
  * The engine normalizes the Start Milestone to the **beginning of the next working shift**: **Saturday, November 14, 2026, at 08:00:00**.
* **Successor Start (`ACT-CIV-1020`)**:
  * Starts Saturday, Nov 14, at 08:00:00.

---

#### 3. Reporting Distortion Over Weekends
Suppose the project operated on a **5-Day Calendar (Sat–Sun OFF)**:
* Under **Case A (Finish Milestone)**: The milestone timestamp is **Friday, Nov 13 @ 18:00:00**. The monthly progress report submitted to the lenders (SECI / State Bank of India) correctly records that Milestone 1 was achieved within the second week of November.
* Under **Case B (Start Milestone)**: The milestone is pushed over the weekend to **Monday, November 16 @ 08:00:00**!
* **Consequence**: The monthly report shows that the milestone was achieved in Week 3 rather than Week 2. If Friday Nov 13 was a contractual milestone cutoff date with a liquidated damages clause, this 1-day calendar push erroneously triggers a penalty audit!

#### 2. Surya 100MW Operational Scenario Requiring WBS Summary
In the Surya 100MW project, under `WBS 02.01 (Civil Balance of Plant)`, there are **140 individual execution activities** (grading, trenching, road compaction, inverter foundations across 40 inverter stations).

The EPC Contractor assigns a **Lead Civil Construction Manager** whose contract is a fixed monthly retainer of ₹250,000 INR. 
* **Why LOE Fails Here**:
  To use an LOE activity, the planner would need to identify the exact earliest starting civil activity (out of 140 tasks) and link it via `SS`, and identify the exact latest finishing civil activity and link it via `FF`. If a different civil activity later slips and becomes the latest finisher, the planner must manually delete and re-wire the LOE successor links!
* **Why WBS Summary Succeeds**:
  The planner creates a single activity `ACT-CIV-MGT: Civil Discipline Site Oversight` of type `WBS Summary` inside `WBS 02.01`.
  * The CPM engine automatically scans all 140 activities in `WBS 02.01`, finds the earliest start date and latest finish date, and sets the span of `ACT-CIV-MGT`.
  * If the inverter pad casting slips past road compaction, `ACT-CIV-MGT` automatically adjusts its finish date without needing any logic links re-drawn.
  * The Civil Manager's labor cost is assigned directly to this WBS Summary activity, allowing monthly cash flow curves to be calculated accurately in SAP S/4HANA.

### Solution 7: High-Voltage Transformer Transport & Heavy Haul Window (Resource Dependent)

#### 1. Why a Single Task Dependent Activity Fails
A single activity cannot span two contradictory calendars simultaneously. 
* If you assign the `Night Transport Calendar (22:00–06:00)` to a single activity, the crane unloading will be scheduled in the dark at 03:00 AM, which violates industrial site safety regulations (OSHA / CEA India safety rules prohibit heavy 145-tonne transformer rigging at night without special floodlit permits).
* If you assign the `Day Shift Calendar (07:00–17:00)`, the heavy-haul multi-axle trailer will be scheduled to drive during the day, which violates the State Highway Police permit.

---

#### 2. Compliant Network Architecture
To model this operation faithfully, divide the scope into two discrete activities linked by a milestone:

```
[ Calendar: Night Transit (22:00 - 06:00, 7D) ]
ACT-LOG-1010: 100MVA Transformer Vadodara-to-Bhadla Heavy Haul Transit
Duration: 40 Working Hours (5 Night Shifts)
Start: Sunday 2026-11-15 @ 22:00:00 ──► Finish: Friday 2026-11-20 @ 06:00:00
       │
       │ FS (lag 0)
       ▼
MS-LOG-1020: Transformer Arrived at Bhadla Substation Gate [FINISH MILESTONE]
Date: Friday 2026-11-20 @ 06:00:00
       │
       │ FS (lag 0) -> Steps into Day Shift Calendar
       ▼
[ Calendar: Site Substation Day Shift (07:00 - 17:00, Mon-Sat) ]
ACT-ELE-1030: Heavy Crane Offloading & Transformer Plinth Jacking-Down
Duration: 20 Working Hours (2 Day Shifts)
Start: Friday 2026-11-20 @ 07:00:00 (1 hour after site arrival gate opening)
```

**Key Architectural Insight**:
By placing the `Finish Milestone` at `06:00:00`, the scheduling engine transitions between the Night Highway Transit Calendar and the Day Substation Civil Calendar seamlessly. The crane rigging crew clocks in at 07:00:00, exactly 1 hour after the convoy arrives.

### Solution 8: Contractual Liquidated Damages Gate & Negative Float Mechanics

#### 1. Total Float Calculation with Mandatory Finish
* Project Baseline COD: **May 31, 2027 @ 18:00:00**.
* Constraint on `MS-COD`: **Mandatory Finish = 2027-05-31 18:00:00**.
* Due to ROW delays, the forward pass calculates Early Finish:
  $$EF(\text{MS-COD}) = \text{2027-06-20 18:00:00}$$

In standard CPM:
* Late Finish ($LF$) without constraints is set equal to the project maximum Early Finish ($LF = EF_{\max} = \text{June 20}$).
* However, a **Mandatory Finish** constraint overrides the backward pass completely, forcing:
  $$LF(\text{MS-COD}) \equiv \text{Constraint Date} = \text{2027-05-31 18:00:00}$$

Now compute Total Float ($TF$):
$$\text{Total Float} = LF - EF = \text{May 31, 2027} - \text{June 20, 2027} = -20 \text{ Calendar Days}$$

Converting to working days on a 6-day site calendar:
$$\text{Total Float} = -17 \text{ Working Days (-170 Working Hours)}$$

---

#### 2. Negative Float Backward Propagation
During the backward pass:
$$LS_i = LF_i - \text{Duration}_i$$
$$LF_{\text{pred}} = \min (LS_{\text{succ}} - \text{Lag})$$

Because $LF(\text{MS-COD})$ is negative relative to $EF$, this **negative float propagates backwards along the entire driving critical path** all the way to the current Data Date. Every activity on the path to grid synchronization will display `Total Float = -17 days`.

#### 3. DCMA 14-Point Audit Penalty
The US Defense Contract Management Agency (DCMA) guidelines penalize Mandatory constraints because:
1. **Mathematical Distortion**: Hard constraints break the fundamental CPM axiom that late dates are derived from network logic.
2. **False Precedence**: If upstream activities finish early, the schedule cannot pull forward past a hard constraint.
3. **Recommended Alternative**: Instead of a Mandatory Finish constraint, best practice is to assign a **Finish On or Before** soft constraint, or use a floating milestone measured against a fixed baseline target line.

#### 3. Why Store Durations as Integer Minutes vs Floating-Point Days?
1. **IEEE 754 Floating-Point Comparison Hazards**:
   In binary floating-point representation, $0.1 + 0.2 \neq 0.3$. If durations are stored as `float8` days:
   $$\text{Day } 0.125 \text{ (3 hours)} + \text{Day } 0.25 \text{ (6 hours)} = 0.37500000000000006$$
   When the engine executes `if earlyFinish == lateFinish`, the check evaluates to `false` due to precision noise, causing critical path detection to fail!
2. **Cumulative Rounding Drift Across Deep Graphs**:
   In a solar plant with 50,000 activities, a 20-node serial path can accumulate small rounding discrepancies. Converting to minutes ($60 \times 8 = 480$ minutes per day) guarantees exact integer arithmetic where $A + B - B \equiv A$ is always preserved.

### Solution 10: Golang Calendar Service & Working Time Normalization

Below is the complete, idiomatic Go implementation of the `CalendarService`:

```go
package cpmengine

import (
	"errors"
	"time"
)

// TimeInterval represents a continuous working shift on a given day.
type TimeInterval struct {
	StartMinutesFromMidnight int // e.g. 08:00 = 480
	EndMinutesFromMidnight   int // e.g. 18:00 = 1080
}

// DayOfWeekProfile defines working shifts for a standard weekday.
type DayOfWeekProfile struct {
	IsWorkDay bool
	Shifts    []TimeInterval
}

// WorkCalendar represents a project work calendar.
type WorkCalendar struct {
	ID        string
	Name      string
	Weekdays  [7]DayOfWeekProfile // Index 0 = Sunday, 1 = Monday ... 6 = Saturday
	Holidays  map[string]bool     // "YYYY-MM-DD" -> true
}

type DefaultCalendarService struct {
	calendars map[string]*WorkCalendar
}

func NewCalendarService(cals map[string]*WorkCalendar) *DefaultCalendarService {
	return &DefaultCalendarService{calendars: cals}
}

// NormalizeStart projects a timestamp forward to the nearest opening working minute.
func (s *DefaultCalendarService) NormalizeStart(calID string, t time.Time) time.Time {
	cal, exists := s.calendars[calID]
	if !exists {
		return t
	}

	curr := t
	for {
		dateStr := curr.Format("2006-01-02")
		weekday := int(curr.Weekday())
		profile := cal.Weekdays[weekday]

		if profile.IsWorkDay && !cal.Holidays[dateStr] {
			currMin := curr.Hour()*60 + curr.Minute()
			for _, shift := range profile.Shifts {
				if currMin < shift.StartMinutesFromMidnight {
					// Snap to start of this upcoming shift today
					return time.Date(curr.Year(), curr.Month(), curr.Day(),
						shift.StartMinutesFromMidnight/60, shift.StartMinutesFromMidnight%60, 0, 0, curr.Location())
				}
				if currMin >= shift.StartMinutesFromMidnight && currMin < shift.EndMinutesFromMidnight {
					// Currently inside a valid shift
					return curr
				}
			}
		}

		// Advance to midnight of the next day
		curr = time.Date(curr.Year(), curr.Month(), curr.Day()+1, 0, 0, 0, 0, curr.Location())
	}
}

// NormalizeFinish projects a timestamp backward to the nearest valid closing working minute.
func (s *DefaultCalendarService) NormalizeFinish(calID string, t time.Time) time.Time {
	cal, exists := s.calendars[calID]
	if !exists {
		return t
	}

	curr := t
	for {
		dateStr := curr.Format("2006-01-02")
		weekday := int(curr.Weekday())
		profile := cal.Weekdays[weekday]

		if profile.IsWorkDay && !cal.Holidays[dateStr] {
			currMin := curr.Hour()*60 + curr.Minute()
			for i := len(profile.Shifts) - 1; i >= 0; i-- {
				shift := profile.Shifts[i]
				if currMin > shift.EndMinutesFromMidnight {
					return time.Date(curr.Year(), curr.Month(), curr.Day(),
						shift.EndMinutesFromMidnight/60, shift.EndMinutesFromMidnight%60, 0, 0, curr.Location())
				}
				if currMin > shift.StartMinutesFromMidnight && currMin <= shift.EndMinutesFromMidnight {
					return curr
				}
			}
		}

		// Retreat to 23:59 of the previous day
		curr = time.Date(curr.Year(), curr.Month(), curr.Day()-1, 23, 59, 0, 0, curr.Location())
	}
}

// AddWorkingDuration steps forward through calendar shifts to calculate Early Finish.
func (s *DefaultCalendarService) AddWorkingDuration(calID string, start time.Time, durationMinutes int) (time.Time, error) {
	cal, exists := s.calendars[calID]
	if !exists {
		return time.Time{}, errors.New("calendar not found")
	}

	if durationMinutes <= 0 {
		return start, nil
	}

	curr := s.NormalizeStart(calID, start)
	rem := durationMinutes

	for rem > 0 {
		dateStr := curr.Format("2006-01-02")
		profile := cal.Weekdays[int(curr.Weekday())]

		if profile.IsWorkDay && !cal.Holidays[dateStr] {
			currMin := curr.Hour()*60 + curr.Minute()
			for _, shift := range profile.Shifts {
				if currMin < shift.EndMinutesFromMidnight {
					effectiveStart := currMin
					if effectiveStart < shift.StartMinutesFromMidnight {
						effectiveStart = shift.StartMinutesFromMidnight
					}
					avail := shift.EndMinutesFromMidnight - effectiveStart
					if rem <= avail {
						finalMin := effectiveStart + rem
						return time.Date(curr.Year(), curr.Month(), curr.Day(),
							finalMin/60, finalMin%60, 0, 0, curr.Location()), nil
					}
					rem -= avail
					currMin = shift.EndMinutesFromMidnight
				}
			}
		}

		// Advance to start of next day
		curr = time.Date(curr.Year(), curr.Month(), curr.Day()+1, 0, 0, 0, 0, curr.Location())
		curr = s.NormalizeStart(calID, curr)
	}

	return curr, nil
}

// SubtractWorkingDuration steps backward through shifts to calculate Late Start.
func (s *DefaultCalendarService) SubtractWorkingDuration(calID string, finish time.Time, durationMinutes int) (time.Time, error) {
	cal, exists := s.calendars[calID]
	if !exists {
		return time.Time{}, errors.New("calendar not found")
	}

	if durationMinutes <= 0 {
		return finish, nil
	}

	curr := s.NormalizeFinish(calID, finish)
	rem := durationMinutes

	for rem > 0 {
		dateStr := curr.Format("2006-01-02")
		profile := cal.Weekdays[int(curr.Weekday())]

		if profile.IsWorkDay && !cal.Holidays[dateStr] {
			currMin := curr.Hour()*60 + curr.Minute()
			for i := len(profile.Shifts) - 1; i >= 0; i-- {
				shift := profile.Shifts[i]
				if currMin > shift.StartMinutesFromMidnight {
					effectiveEnd := currMin
					if effectiveEnd > shift.EndMinutesFromMidnight {
						effectiveEnd = shift.EndMinutesFromMidnight
					}
					avail := effectiveEnd - shift.StartMinutesFromMidnight
					if rem <= avail {
						finalMin := effectiveEnd - rem
						return time.Date(curr.Year(), curr.Month(), curr.Day(),
							finalMin/60, finalMin%60, 0, 0, curr.Location()), nil
					}
					rem -= avail
					currMin = shift.StartMinutesFromMidnight
				}
			}
		}

		// Move to previous day
		curr = time.Date(curr.Year(), curr.Month(), curr.Day()-1, 23, 59, 0, 0, curr.Location())
		curr = s.NormalizeFinish(calID, curr)
	}

	return curr, nil
}

// CalculateWorkingMinutes computes the total working minutes between two timestamps.
func (s *DefaultCalendarService) CalculateWorkingMinutes(calID string, start, finish time.Time) (int, error) {
	if finish.Before(start) {
		return 0, nil
	}
	// Simplified accumulator for illustration
	cal, exists := s.calendars[calID]
	if !exists {
		return 0, errors.New("calendar not found")
	}

	total := 0
	curr := s.NormalizeStart(calID, start)
	for curr.Before(finish) {
		dateStr := curr.Format("2006-01-02")
		profile := cal.Weekdays[int(curr.Weekday())]
		if profile.IsWorkDay && !cal.Holidays[dateStr] {
			currMin := curr.Hour()*60 + curr.Minute()
			for _, shift := range profile.Shifts {
				if currMin < shift.EndMinutesFromMidnight {
					startM := currMin
					if startM < shift.StartMinutesFromMidnight {
						startM = shift.StartMinutesFromMidnight
					}
					endM := shift.EndMinutesFromMidnight
					limitM := finish.Hour()*60 + finish.Minute()
					if curr.Format("2006-01-02") == finish.Format("2006-01-02") && limitM < endM {
						endM = limitM
					}
					if endM > startM {
						total += (endM - startM)
					}
				}
			}
		}
		curr = time.Date(curr.Year(), curr.Month(), curr.Day()+1, 0, 0, 0, 0, curr.Location())
		curr = s.NormalizeStart(calID, curr)
	}
	return total, nil
}
```

### Solution 11: 3-Stage Pipeline Concurrency & Parallel Execution in Go

#### 1. Stage 1 Linear Complexity $O(V + E)$ in Go
By utilizing in-degree arrays and adjacency lists stored in contiguous slices rather than nested DB queries, Kahn's algorithm runs in strictly $O(V_{\text{core}} + E_{\text{core}})$ time. Memory allocations are minimized by pre-allocating slices with `make([]string, 0, len(nodes))`.

---

#### 2. Dependency Proof: Can Stage 2 and Stage 3 Run Concurrently?
* **Question**: Can LOE Resolution (Stage 2) and WBS Summary Resolution (Stage 3) run concurrently?
* **Proof**:
  * Let $\text{Scope}(W)$ be the set of all activities in WBS node $W$.
  * If $\text{Scope}(W) \cap V_{\text{loe}} \neq \emptyset$ (i.e., a WBS container contains an LOE activity, such as `ACT-LOE-DUST` inside `WBS 02.01 Civil Works`):
  * Then the WBS Summary Early Finish is defined as:
    $$EF(W) = \max_{a \in \text{Scope}(W)} EF(a)$$
  * If Stage 3 runs concurrently with Stage 2, $EF(W)$ may read $EF(\text{LOE})$ before the LOE's boundaries are resolved from Stage 1!
  * **Conclusion**: **Stage 3 MUST wait for Stage 2 to complete.** The pipeline is strictly serial across stages:
    $$\text{Stage 1 (Core)} \longrightarrow \text{Stage 2 (LOE)} \longrightarrow \text{Stage 3 (WBS Summary)}$$

---

#### 3. Parallel Worker Pool for Stage 3 (WBS Summaries)
While Stage 3 must follow Stage 2, **individual WBS summaries can be calculated in parallel** across Goroutines because each WBS summary only writes to its own struct:

```go
package cpmengine

import (
	"context"
	"sync"
	"time"
)

// ParallelResolveWBSSummaries resolves WBS Summary activities concurrently.
func (s *CPMScheduler) ParallelResolveWBSSummaries(
	ctx context.Context,
	wbsSummaries []*Activity,
	allActivities map[string]*Activity,
	concurrencyLimit int,
) error {
	jobs := make(chan *Activity, len(wbsSummaries))
	for _, summary := range wbsSummaries {
		jobs <- summary
	}
	close(jobs)

	var wg sync.WaitGroup
	for i := 0; i < concurrencyLimit; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for summary := range jobs {
				var minStart time.Time
				var maxFinish time.Time
				foundChildren := false

				for _, act := range allActivities {
					if act.WBSID == summary.WBSID && act.ID != summary.ID {
						if !foundChildren || act.EarlyStart.Before(minStart) {
							minStart = act.EarlyStart
						}
						if !foundChildren || act.EarlyFinish.After(maxFinish) {
							maxFinish = act.EarlyFinish
						}
						foundChildren = true
					}
				}

				if foundChildren {
					summary.EarlyStart = minStart
					summary.EarlyFinish = maxFinish
					summary.LateStart = minStart
					summary.LateFinish = maxFinish
					summary.TotalFloatMinutes = 0
					summary.IsCritical = false

					workMin, _ := s.calSvc.CalculateWorkingMinutes(summary.CalendarID, minStart, maxFinish)
					summary.OriginalDurationMinutes = workMin
					summary.RemainingDurationMinutes = workMin
				}
			}
		}()
	}

	wg.Wait()
	return nil
}
```

   ```typescript
   function onTaskDragOptimistic(draggedId: string, deltaDays: number) {
     setScheduleState((prev) => {
       const updated = { ...prev };
       const target = updated.activities[draggedId];
       target.earlyStart = addDays(target.earlyStart, deltaDays);

       }
       return updated;
     });
   ```
