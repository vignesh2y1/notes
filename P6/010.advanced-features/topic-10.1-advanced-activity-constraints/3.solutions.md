### Solution 1: Soft vs. Hard Constraint Topological Invariants

#### 1. Mathematical Difference During Forward and Backward Passes
The difference lies in whether precedence logic can override the constraint date during the forward pass:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                   SOFT CONSTRAINT vs. HARD CONSTRAINT PASS LOGIC                                 │
├────────────────────┬──────────────────────────────────────┬──────────────────────────────────────┤
│ Metric / Pass      │ Soft Constraint (FOB)                │ Hard Constraint (MF)                 │
├────────────────────┼──────────────────────────────────────┼──────────────────────────────────────┤
│ Forward Pass       │ Preserves Precedence Logic           │ DESTROYS Precedence Logic            │
│ Calculation        │ EF = max(Predecessors) + Duration    │ EF = ConstraintDate (Overwrites EF)  │
│ Backward Pass      │ Clamps Late Dates                    │ Clamps Late Dates                    │
│ Calculation        │ LF = min(Successors, ConstraintDate) │ LF = ConstraintDate (Overwrites LF)  │
│ Relationship Check │ Invariant ES_succ >= EF_pred holds   │ Invariant ES_succ >= EF_pred broken! │
└────────────────────┴──────────────────────────────────────┴──────────────────────────────────────┘
```

* **Soft Constraint (e.g., Finish On or Before):**
  - **Forward Pass:** The engine respects predecessor driving dates: $ES_B = EF_A$. The constraint does *not* alter early dates if predecessors push past it.
  - **Backward Pass:** The engine enforces a ceiling on late dates: $LF_B = \min(\text{Successors Late Start},\; CD)$.
* **Hard Constraint (e.g., Mandatory Finish):**
  - **Forward Pass:** The engine forcefully clamps the early finish: $EF_B = CD$ and $ES_B = CD - D_B$, completely ignoring whether $EF_A > ES_B$.
  - **Backward Pass:** The engine forcefully clamps the late finish: $LF_B = CD$ and $LS_B = CD - D_B$.

#### 2. Network Calculation for $A \xrightarrow{FS=0} B$ ($D_A = 10\text{d}, D_B = 5\text{d}$)

##### Case 1: Soft Constraint (Finish On or Before Day 12 on Activity B)
1. **Forward Pass:**
   - Activity A: $ES_A = 0$, $EF_A = 10$.
   - Activity B: $ES_B = EF_A = 10$.
   - Activity B: $EF_B = ES_B + D_B = 10 + 5 = 15$.
   *(Note: Predecessor pushes EF past Day 12. Soft constraint yields to topological reality).*
2. **Backward Pass:**
   - Activity B has FOB = Day 12.
   - $LF_B = \min(\text{Project Finish},\; CD) = 12$.
   - $LS_B = LF_B - D_B = 12 - 5 = 7$.
   - Activity A: $LF_A = LS_B = 7$.
   - $LS_A = LF_A - D_A = 7 - 10 = -3$.
3. **Float Analysis:**
   - $TF_B = LF_B - EF_B = 12 - 15 = -3\text{ days}$.
   - $TF_A = LF_A - EF_A = 7 - 10 = -3\text{ days}$.
   - Both activities have $-3$ days Total Float, signaling that the network is delayed by 3 days relative to the target ceiling of Day 12, **yet physical logic is preserved** ($EF_B = 15$).

##### Case 2: Hard Constraint (Mandatory Finish Day 12 on Activity B)
1. **Forward Pass:**
   - Activity A: $ES_A = 0$, $EF_A = 10$.
   - Activity B: Mandatory Finish forces $EF_B = 12$.
   - $ES_B = EF_B - D_B = 12 - 5 = 7$.
   - **Notice the impossible physical anomaly:** Activity B starts on Day 7, even though its predecessor Activity A does not finish until Day 10 ($ES_B < EF_A$)!
2. **Backward Pass:**
   - Activity B: $LF_B = 12$, $LS_B = 7$.
   - Activity A: $LF_A = LS_B = 7$, $LS_A = 7 - 10 = -3$.
3. **Float Analysis:**
   - $TF_B = LF_B - EF_B = 12 - 12 = 0\text{ days}$!
   - $TF_A = LF_A - EF_A = 7 - 10 = -3\text{ days}$.

> [!WARNING]
> **The Critical Finding:**
> Under Mandatory Finish, Activity B shows $TF = 0$ (falsely indicating that B is on track), while predecessor Activity A shows $TF = -3$. The hard constraint masks Activity B's negative float and breaks topological relationship integrity!

### Solution 2: The Emergence of Negative Float and Float Overrides

#### 1. Mathematical Condition for Negative Float
Total Float is defined as:
$$TF = LF - EF = LS - ES$$
Negative float ($TF < 0$) occurs if and only if:
$$EF > LF \iff ES > LS$$
This condition represents physical or contractual **infeasibility**: the earliest possible time work can realistically finish ($EF$) is *later* than the latest allowable time it is permitted to finish ($LF$) to satisfy a contract milestone.

#### 2. Two Distinct Mechanisms in Oracle Primavera P6
1. **Project Must Finish By Date:**
   - In P6 Project Preferences, setting a `Must Finish By` date establishes a project-wide backward pass boundary.
   - If the forward pass completes and the unconstrained project finish $EF_{\text{final}} > \text{Must Finish By}$, the engine sets $LF_{\text{final}} = \text{Must Finish By}$.
   - The negative difference ($LF - EF$) propagates backward across every predecessor on the driving path.
2. **Late Constraint Imposition (SOB, FOB, MS, MF):**
   - Placing a *Finish On or Before* or *Mandatory Finish* on an intermediate deliverable where actual field progress has pushed the forecasted $EF$ past that constraint date.

#### 3. Impact on the Critical Path Definition
* **Traditional Definition:** "The longest path of zero-float activities through the network."
* **In Constrained Reality:** When negative float exists, the Critical Path is **the path of least Total Float** (e.g., the path with float equal to $-42$ days, not $0$ days).
* In P6 scheduling preferences, the administrator must configure whether critical activities are defined by:
  - `Total Float <= 0` (default standard), or
  - `Longest Path` (which traces the pure driving relationship path to the final project deliverable, regardless of constraint-induced float).

### Solution 3: As Late As Possible (ALAP) and Free Float Dynamics

#### 1. Engine Pass Sequence for ALAP
To compute ALAP dates, the scheduling engine executes a three-phase procedure:
1. **Standard Forward Pass:** Calculate all unconstrained early dates ($ES, EF$) for all nodes.
2. **Standard Backward Pass:** From the project end date (or contractual milestone), propagate late dates ($LF, LS$) back through all nodes.
3. **ALAP Clamp Pass:** For each node where $\text{Constraint} == \text{ALAP}$:
   $$ES_i^{\text{ALAP}} = LS_i$$
   $$EF_i^{\text{ALAP}} = LF_i$$
   If this activity has successors, the forward pass for its downstream successors must be verified to ensure no successor Early Start is violated.

#### 2. Impact on Activity Metrics
* **Early Start:** Shifts forward in time from its earliest topological date to equal Late Start: $ES \to LS$.
* **Late Start:** Remains unchanged.
* **Free Float ($FF$):** Driven to exactly **0**. By definition, Free Float is the delay an activity can tolerate without delaying the Early Start of any successor. By shifting the activity to its latest limit, it abuts against its successors' early start dates.
* **Total Float ($TF$):** For the activity itself, $TF = LS - ES = 0$. (Unless predecessor/successor networks introduce negative float).

#### 3. Operational Risk in Construction / EPC
While ALAP minimizes inventory carrying costs (e.g., purchasing expensive solar transformers only when immediately needed):
* **Elimination of Absorptive Buffers:** Every non-critical task becomes **instantaneously critical**.
* **Zero Shock Tolerance:** A single rainy day, flat tire on a delivery truck, or labor dispute on an ALAP task creates an immediate day-for-day project delay.
* **Resource Clumping:** Pushing non-critical tasks to their late dates bunches multiple parallel trades together near milestones, creating unsustainable resource bottlenecks and site congestion.

### Solution 4: Expected Finish vs. Remaining Duration Semantics

#### 1. Expected Finish vs. Constraints
* A **Constraint** (e.g., Finish On or Before) imposes a boundary on Late Dates (or Early Dates) during CPM pass calculation. It does not alter the remaining effort or estimated duration.
* An **Expected Finish Date** is an **estimating override tool for In-Progress tasks**. It instructs the engine to dynamically recalculate the activity's **Remaining Duration** based on the project's Data Date:
$$RD = \text{WorkingDaysBetween}(\text{Data Date},\; \text{Expected Finish Date})$$

#### 2. Active Lifecycle Status
The `Expected Finish Date` field is active **strictly when the activity is `In-Progress`** ($ActualStart \ne \text{nil}$ and $ActualFinish == \text{nil}$). For `Not Started` tasks, it has no effect in standard P6 logic. For `Completed` tasks, the `Actual Finish Date` governs.

#### 3. Calculation Walkthrough
* Original Duration ($OD$) = 20 days.
* Actual Start = Day 5.
* Data Date ($DD$) = Day 15.
* Expected Finish = Day 30.
* Calendar: 7-day continuous work.

1. **Remaining Duration Calculation:**
   $$RD = \text{Expected Finish} - \text{Data Date} = 30 - 15 = 15\text{ days}$$
2. **Duration % Complete:**
   $$\text{Actual Duration} = \text{Data Date} - \text{Actual Start} = 15 - 5 = 10\text{ days}$$
   $$\text{Duration \% Complete} = \frac{OD - RD}{OD} \times 100 = \frac{20 - 15}{20} \times 100 = \frac{5}{20} \times 100 = 25\%$$
   *(Alternatively, using Actual Duration: $\frac{10}{10+15} \times 100 = 40\%$, depending on P6 Duration % Complete calculation settings).*
3. **Reconciling with 40% Physical % Complete:**
   In P6, when Percent Complete Type is set to **Physical**:
   - **Physical % Complete (40%)** governs Earned Value ($EV = BAC \times 0.40$).
   - **Remaining Duration (15 days)** governs CPM forward pass and critical path scheduling.
   - P6 completely decouples physical work accomplished from calendar days remaining. The engineer reports: "We have poured 40% of the foundations, but due to rocky ground, we need 15 more working days from the Data Date."

### Solution 5: Surya 100MW Solar IPP — The Grid Substation Outage Conflict

#### 1. Baseline Schedule Calculation (Data Date = Day 0)
Logic: $ACT\text{-}100 (20\text{d}) \xrightarrow{FS=0} ACT\text{-}200 (15\text{d}) \xrightarrow{FS=0} ACT\text{-}300 (5\text{d})$.
Constraint: $ACT\text{-}300$ has `Finish On or Before Day 35`.

1. **Forward Pass:**
   - $ACT\text{-}100$: $ES = 0$, $EF = 20$.
   - $ACT\text{-}200$: $ES = 20$, $EF = 20 + 15 = 35$.
   - $ACT\text{-}300$: $ES = 35$, $EF = 35 + 5 = 40$.
2. **Backward Pass:**
   - $ACT\text{-}300$ has FOB = Day 35 $\implies LF_{300} = 35$.
   - $LS_{300} = LF_{300} - D_{300} = 35 - 5 = 30$.
   - $ACT\text{-}200$: $LF_{200} = LS_{300} = 30 \implies LS_{200} = 30 - 15 = 15$.
   - $ACT\text{-}100$: $LF_{100} = LS_{200} = 15 \implies LS_{100} = 15 - 20 = -5$.
3. **Float Analysis:**
   - $TF_{300} = LF - EF = 35 - 40 = -5\text{ days}$.
   - $TF_{200} = LF - EF = 30 - 35 = -5\text{ days}$.
   - $TF_{100} = LF - EF = 15 - 20 = -5\text{ days}$.
   - Even in baseline planning, the team has planned 40 days of work against a 35-day window! There is an initial $-5$ days negative float defect.

#### 2. Progress Update: Excavation Delays ($ACT\text{-}100$ Duration = 28 days)
1. **Forward Pass:**
   - $ACT\text{-}100$: $ES = 0$, $EF = 28$.
   - $ACT\text{-}200$: $ES = 28$, $EF = 28 + 15 = 43$.
   - $ACT\text{-}300$: $ES = 43$, $EF = 43 + 5 = 48$.
2. **Backward Pass:**
   - $ACT\text{-}300$: $LF = 35$, $LS = 30$.
   - $ACT\text{-}200$: $LF = 30$, $LS = 15$.
   - $ACT\text{-}100$: $LF = 15$, $LS = 15 - 28 = -13$.
3. **Float Analysis:**
   - $TF_{300} = 35 - 48 = -13\text{ days}$.
   - $TF_{200} = 30 - 43 = -13\text{ days}$.
   - $TF_{100} = 15 - 28 = -13\text{ days}$.
   - Total negative float has expanded to $-13$ days.

#### 3. Replacing FOB with Mandatory Finish Day 35
If the planner changes $ACT\text{-}300$ to **Mandatory Finish Day 35**:
* Forward pass forces $EF_{300} = 35$, $ES_{300} = 30$.
* But $ACT\text{-}200$ finishes on Day 43!
* $ACT\text{-}300$ now displays $TF = 0$ ($LF_{300} - EF_{300} = 35 - 35 = 0$).

> [!CAUTION]
> **Forensic Tribunal Danger:**

The schedule depicts $ACT\text{-}300$ occurring between Day 30 and Day 35, before the GIS Switchgear ($ACT\text{-}200$) is even physically erected! It fraudulently hides the true 13-day delay on the milestone by breaking causality.

### Solution 6: Dual Constraint Feasibility Validation

#### 1. Mathematical Inequality
For an activity with a Start-bound constraint and a Finish-bound constraint:
$$\text{ConstraintDate}_{\text{Finish}} - \text{ConstraintDate}_{\text{Start}} \ge \text{RemainingDuration}$$
If this inequality is violated, the activity cannot physically complete within the constrained window, resulting in immediate artificial negative float during forward/backward pass execution.

#### 2. PostgreSQL Validation Trigger
```sql
CREATE OR REPLACE FUNCTION trg_fn_validate_activity_constraints()
RETURNS TRIGGER AS $$
DECLARE
    v_start_boundary  TIMESTAMP WITH TIME ZONE;
    v_finish_boundary TIMESTAMP WITH TIME ZONE;
    v_window_seconds  NUMERIC;
    v_required_seconds NUMERIC;
BEGIN
    -- Determine start boundary
    IF NEW.primary_constraint_type IN ('START_ON', 'START_ON_OR_AFTER') THEN
        v_start_boundary := NEW.primary_constraint_date;
    END IF;

    -- Determine finish boundary
    IF NEW.secondary_constraint_type IN ('FINISH_ON', 'FINISH_ON_OR_BEFORE') THEN
        v_finish_boundary := NEW.secondary_constraint_date;
    ELSIF NEW.primary_constraint_type IN ('FINISH_ON', 'FINISH_ON_OR_BEFORE') THEN
        v_finish_boundary := NEW.primary_constraint_date;
    END IF;

    -- If both boundaries exist, validate duration feasibility
    IF v_start_boundary IS NOT NULL AND v_finish_boundary IS NOT NULL THEN
        IF v_finish_boundary < v_start_boundary THEN
            RAISE EXCEPTION 'Constraint Error: Finish constraint % cannot precede start constraint %',
                v_finish_boundary, v_start_boundary;
        END IF;

        v_window_seconds := EXTRACT(EPOCH FROM (v_finish_boundary - v_start_boundary));
        v_required_seconds := NEW.remaining_duration_days * 86400;

        IF v_window_seconds < v_required_seconds THEN
            RAISE EXCEPTION 'Constraint Conflict: Window of % days is smaller than remaining duration of % days',
                ROUND(v_window_seconds / 86400, 2), NEW.remaining_duration_days;
        END IF;
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_check_activity_constraints
BEFORE INSERT OR UPDATE ON cpm_activity
FOR EACH ROW
EXECUTE FUNCTION trg_fn_validate_activity_constraints();
```

### Solution 8: Implementing SOA and FOB with Calendar Awareness in Go

```go
package cpm

import (
	"time"
)

// ApplyStartOnOrAfter clamps Early Start to the constraint date if it occurs later.
func ApplyStartOnOrAfter(act *Activity, constraintDate time.Time, cal *WorkCalendar) {
	// If constraint date falls on non-working period, roll forward to next working minute
	effectiveDate := cal.AdjustToNextWorkingTime(constraintDate)

	if effectiveDate.After(act.EarlyStart) {
		act.EarlyStart = effectiveDate
		act.EarlyFinish = cal.AddWorkingDuration(act.EarlyStart, act.RemainingDurationHours)
	}
}

// ApplyFinishOnOrBefore clamps Late Finish to the constraint date if it occurs earlier.
func ApplyFinishOnOrBefore(act *Activity, constraintDate time.Time, cal *WorkCalendar) {
	// If constraint date falls on non-working period, roll back to prior working minute
	effectiveDate := cal.AdjustToPrevWorkingTime(constraintDate)

	if effectiveDate.Before(act.LateFinish) {
		act.LateFinish = effectiveDate
		act.LateStart = cal.SubtractWorkingDuration(act.LateFinish, act.RemainingDurationHours)
	}
}
```

*Calendar Interaction:* If a `Start On or After` constraint is set to Sunday at 08:00 AM on a 5-day Monday–Friday calendar, work cannot physically begin on Sunday. The engine rolls the effective constraint date forward to **Monday at 08:00 AM**.

### Solution 9: Mandatory Finish Backward Pass Cascade in Go

#### 1. Step-by-Step Backward Pass Trace
Network: $A (10\text{d}) \xrightarrow{FS} B (10\text{d}) \xrightarrow{FS} C (10\text{d}) \xrightarrow{FS} D (10\text{d})$. Data Date = Day 0.
* Forward Pass:
  - $A: [0, 10]$
  - $B: [10, 20]$
  - $C: [20, 25]$ (Mandatory Finish locked to Day 25 $\implies ES = 15$)
  - $D: [25, 35]$ (Successor begins at EF of C)
  - Project Early Finish = Day 35.
* Backward Pass:
  - Activity $D$: $LF_D = 35$, $LS_D = 25$.
  - Activity $C$: Has `Mandatory Finish Day 25` $\implies LF_C = 25$, $LS_C = 25 - 10 = 15$.
  - Activity $B$: $LF_B = LS_C = 15 \implies LS_B = 15 - 10 = 5$.
  - Activity $A$: $LF_A = LS_B = 5 \implies LS_A = 5 - 10 = -5$.

#### 2. Total Float Values
* $TF_D = LF_D - EF_D = 35 - 35 = 0\text{ days}$.
* $TF_C = LF_C - EF_C = 25 - 25 = 0\text{ days}$.
* $TF_B = LF_B - EF_B = 15 - 20 = -5\text{ days}$.
* $TF_A = LF_A - EF_A = 5 - 10 = -5\text{ days}$.

#### 3. Criticality Flag Evaluation
With critical threshold defined as $\text{Total Float} \le 0$:
* Activity A: $TF = -5 \implies \text{IsCritical} = \mathbf{true}$
* Activity B: $TF = -5 \implies \text{IsCritical} = \mathbf{true}$
* Activity C: $TF = 0 \implies \text{IsCritical} = \mathbf{true}$
* Activity D: $TF = 0 \implies \text{IsCritical} = \mathbf{true}$
* All four activities are flagged as critical. Activities A and B represent the sub-critical negative float path causing the contractual delay.

### Solution 10: Cycle and Infeasible Constraint Detection Service

```go
package cpm

import (
	"errors"
	"fmt"
	"time"
)

// ValidateConstraintSanity executes defensive checks before scheduling.
func (e *NetworkEngine) ValidateConstraintSanity(act *Activity) error {
	// Rule 1: ALAP cannot have a constraint date
	if act.PrimaryConstraint == ConstraintAsLateAsPossible && act.PrimaryDate != nil {
		return fmt.Errorf("activity %s: ALAP constraint cannot specify a date", act.Code)
	}

	// Rule 2: Non-ALAP constraints must have dates
	if act.PrimaryConstraint != ConstraintNone && act.PrimaryConstraint != ConstraintAsLateAsPossible && act.PrimaryDate == nil {
		return fmt.Errorf("activity %s: constraint %s requires a constraint date", act.Code, act.PrimaryConstraint)
	}

	// Rule 3: Expected finish only allowed for in-progress activities
	if act.ExpectedFinish != nil && act.ActualStart == nil {
		return fmt.Errorf("activity %s: expected finish only valid for in-progress tasks", act.Code)
	}

	// Rule 4: Dual constraint span validation
	if act.PrimaryConstraint != ConstraintNone && act.SecondaryConstraint != ConstraintNone {
		var startBound, finishBound *time.Time

		if act.PrimaryConstraint == ConstraintStartOn || act.PrimaryConstraint == ConstraintStartOnOrAfter {
			startBound = act.PrimaryDate
		}
		if act.SecondaryConstraint == ConstraintFinishOn || act.SecondaryConstraint == ConstraintFinishOnOrBefore {
			finishBound = act.SecondaryDate
		}

		if startBound != nil && finishBound != nil {
			if finishBound.Before(*startBound) {
				return fmt.Errorf("activity %s: secondary finish date precedes primary start date", act.Code)
			}
			durationSpan := finishBound.Sub(*startBound)
			reqDuration := time.Duration(act.RemainingDurationHours) * time.Hour
			if durationSpan < reqDuration {
				return fmt.Errorf("activity %s: dual constraint window (%v) is less than required duration (%v)",
					act.Code, durationSpan, reqDuration)
			}
		}
	}

	return nil
}
```
