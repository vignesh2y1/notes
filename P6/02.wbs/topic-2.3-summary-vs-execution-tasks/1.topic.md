# Topic 2.3: Summary Nodes vs Execution Tasks — Hierarchy vs Network Dynamics

---

## 1. Executive Summary: The Strict Boundary Between Hierarchy and Network

In the engineering of enterprise project controls software (such as Oracle Primavera P6), no architectural decision is more critical—or more frequently violated by inexperienced software engineers—than the strict, immutable boundary between the **Scope Hierarchy (Work Breakdown Structure)** and the **Activity Network (Precedence Diagramming Method / Critical Path Method)**.

In lightweight project management applications (e.g., Trello, Asana, Monday.com, or simplistic Kanban boards), work items are typically modeled as a homogeneous flat list or a shallow parent-child task list where any item can be given dates, checkmarks, dependencies, and assignees. When junior developers build a project scheduling engine, they frequently carry this mental model forward, creating a single "tasks" table with an `is_summary` boolean flag or an optional `parent_task_id`, allowing users to draw dependency arrows between summary folders and leaf activities alike.

In industrial capital projects—such as the **100MW Solar IPP Project in Rajasthan, India**—this homogeneous modeling leads to mathematical collapse. It produces cyclic dependency deadlocks in the scheduling engine, date propagation paradoxes during forward/backward passes, corrupt Earned Value rollups, and unmaintainable database locks across multi-tier subcontractor supply chains.


### The Dual-Topology Rule
A production-grade scheduling engine operates on two orthogonal mathematical structures:
1. **The Scope Tree ($T$):** A rooted tree where every non-root node has exactly one parent. This tree organizes the deliverables of the contract under the **100% Rule** (the sum of children represents 100% of the scope of the parent, mutually exclusive and collectively exhaustive).
2. **The Execution Graph ($G$):** A directed acyclic graph where nodes are discrete execution activities and directed edges represent physical, technical, or contractual precedence relationships.

**The Golden Axiom of Primavera P6 Architecture:**
> **Precedence logic edges ($E_{logic}$) exist exclusively between execution activities ($V_{act}$). Summary nodes ($V_{wbs}$) must NEVER be endpoints of precedence edges.**

Summary nodes are observers and aggregators of state; execution activities are actors that generate state. Conflating the observer with the actor destroys the mathematical validity of the Critical Path Method (CPM).

## 2. The Fundamental Dichotomy: Summary Node vs Execution Task

To implement a robust backend in Golang and an interactive Gantt client in Next.js, we must formally define the structural, operational, and mathematical differences between these two entities.

```
┌────────────────────────────────────────────────────────────────────────────────────────────────┐
│                          SUMMARY NODE (WBS) vs EXECUTION TASK (ACTIVITY)                       │
├─────────────────────────────────────────────────┬──────────────────────────────────────────────┤
│ ATTRIBUTE / CAPABILITY                          │ SUMMARY NODE (WBS)   │ EXECUTION TASK (ACT)  │
├─────────────────────────────────────────────────┼──────────────────────┼──────────────────────┤
│ Independent Planned Duration                    │ ❌ Strictly No       │ ✅ Yes (e.g., 12 d)   │
│ Assigned Working Calendar (Shifts/Holidays)     │ ❌ No (Derived)      │ ✅ Yes (6d-Single)    │
│ Explicit Execution Status (User Toggled)        │ ❌ Strictly No       │ ✅ Yes (In-Progress)  │
│ Direct Labor / Material Loading                 │ ❌ Strictly No       │ ✅ Yes (Hrs, Qty, $)  │
│ Precedence Relationship Target (FS, SS, etc.)   │ ❌ Strictly Banned   │ ✅ Yes (CPM Edges)    │
│ Responsible Entity Assignment                   │ ✅ OBS Manager Node  │ ✅ Resource / Crew    │
│ Early Start ($ES$) / Early Finish ($EF$)        │ 🔄 Derived Rollup    │ 🧮 CPM Engine Pass    │
│ Total Float / Free Float Calculation            │ 🔄 Derived Span      │ 🧮 Late - Early Dates │
│ Physical Percent Complete Source                │ 🔄 Rollup / Rules    │ 📝 Field Update / Qty │
└─────────────────────────────────────────────────┴──────────────────────┴──────────────────────┘
```

### 2.1 The Summary Node (WBS Element)
A Summary Node (represented in P6 by the `PROJWBS` table) is a pure organizational container and rollup aggregator. It represents a deliverable milestone or work package boundary in the project scope.

#### 1. No Independent Duration
A summary node does not possess an autonomous duration. You cannot set a WBS node's duration to "45 days." Instead, its start date, finish date, and calendar span are derived purely from the extreme boundaries of its leaf descendants:
$$\text{Summary Start} = \min_{i \in \text{Children}} (\text{Start}_i)$$
$$\text{Summary Finish} = \max_{i \in \text{Children}} (\text{Finish}_i)$$
$$\text{Calendar Duration (Span)} = \text{DateDiff}(\text{Summary Start}, \text{Summary Finish})$$

If an engineer re-sequences a cable-pulling activity inside `WBS 02.2.1` so that it finishes 10 days later, the Early Finish of `WBS 02.2.1`, `WBS 02.2`, and `WBS 02` automatically expands without any user intervention.

#### 2. No Direct Labor or Equipment Loading
You cannot assign a 50-ton hydraulic crane or 10 structural welders directly to `WBS 02.1 (Civil Works)`. Resources require specific production rates, daily working calendars, overtime rules, and activity curves. Placing a resource directly on a summary node breaks cost allocation: over which days of the 6-month civil span should the crane hours be distributed? 
Instead, resources are assigned to specific leaf activities (e.g., `ACT-102: Inverter Pad Concrete Pour`). The summary node simply sums the resulting cost and unit curves:
$$\text{Planned Cost}_{\text{WBS}} = \sum_{a \in \text{Leaf}(WBS)} \text{Planned Cost}_a$$
$$\text{Actual Cost}_{\text{WBS}} = \sum_{a \in \text{Leaf}(WBS)} \text{Actual Cost}_a$$

#### 3. No Status Toggling
A user cannot open the UI and click "Mark as Completed" on `WBS 02.1 (Civil Works)`. The execution status of a WBS node is a deterministic function of its children's statuses:
* **Not Started:** If $100\%$ of its leaf activities are `Not Started`.
* **In Progress:** If at least one leaf activity is `In Progress` or `Completed`, but at least one leaf activity is not yet `Completed`.
* **Completed:** If and only if $100\%$ of its leaf activities have achieved `Completed` status ($Actual Finish \neq \text{null}$).

```go
// DeriveWBSStatus calculates the deterministic state of a WBS container
func DeriveWBSStatus(leafActivities []Activity) TaskStatus {
    if len(leafActivities) == 0 {
        return StatusNotStarted
    }
    completedCount := 0
    inProgressCount := 0
    for _, a := range leafActivities {
        switch a.Status {
        case StatusCompleted:
            completedCount++
        case StatusInProgress:
            inProgressCount++
        }
    }
    if completedCount == len(leafActivities) {
        return StatusCompleted
    }
    if completedCount > 0 || inProgressCount > 0 {
        return StatusInProgress
    }
    return StatusNotStarted
}
```

### 2.2 The Execution Task (Activity)
An Execution Task (represented in P6 by the `TASK` table) is the fundamental, indivisible unit of work scheduled by the CPM engine.

#### 1. Discrete Planned Duration and Calendar
An activity has a definite Planned Duration (e.g., `Original Duration = 14 days`). This duration is interpreted strictly through its assigned **Work Calendar** (e.g., `Rajasthan Site Civil Calendar - 6 Days/Week, 10 Hours/Day, Major Indian Holidays Excluded, Extreme Summer Afternoon Siesta Applied`).

#### 2. Execution State Lifecycle
An execution task moves through a formal state machine:
```
               ┌────────────────────────┐
               │      NOT STARTED       │
               │  Actual Start: NULL    │
               │  Actual Finish: NULL   │
               └───────────┬────────────┘
                           │
                           │ Field Foreman Posts Actual Start Date
                           │ (e.g., 2026-11-02 08:00:00)
                           ▼
               ┌────────────────────────┐
               │      IN PROGRESS       │
               │  Actual Start: SET     │
               │  Actual Finish: NULL   │
               │  Remaining Duration > 0│
               └───────────┬────────────┘
                           │
                           │ Progress achieves 100%, Remaining Duration = 0
                           │ Field Foreman Posts Actual Finish Date
                           │ (e.g., 2026-11-18 17:30:00)
                           ▼
               ┌────────────────────────┐
               │       COMPLETED        │
               │  Actual Start: SET     │
               │  Actual Finish: SET    │
               │  Remaining Duration = 0│
               └────────────────────────┘
```

#### 3. Network Precedence Participation
An activity participates in the CPM graph through directed relationships:
* Predecessor Activity $\to$ Successor Activity
* Relationship Types:
  * **Finish-to-Start (FS):** Successor cannot start until Predecessor finishes.
  * **Start-to-Start (SS):** Successor cannot start until Predecessor starts.
  * **Finish-to-Finish (FF):** Successor cannot finish until Predecessor finishes.
  * **Start-to-Finish (SF):** Successor cannot finish until Predecessor starts (rare).
* Each relationship may include a signed **Lag** (+/- duration in working hours/days).

## 3. Why Summary Nodes MUST NOT Have Precedence Relationships (The "No Links on WBS" Rule)

In amateur project management software, users are frequently permitted to click a WBS parent bar on a Gantt chart and drag a dependency line to another WBS parent bar (e.g., linking `WBS 02.1 Civil Works` $\to$ `WBS 02.2 Electrical BOP` with an FS link). 

In professional CPM engines, **this operation is strictly illegal**. Allowing relationships between summary nodes introduces fatal mathematical paradoxes, topological cycles, and schedule instability.

### 3.1 Mathematical and Topological Hazards

#### 1. Semantic Ambiguity & The Resolution Dilemma
When an edge is drawn between two sets of activities ($S_1 \to S_2$), what is the mathematical mapping?
* Does it mean: $\forall a \in S_1, \forall b \in S_2: a \to b$? (Every activity in $S_2$ waits for every activity in $S_1$). This creates massive false network rigidity, artificially inflating float and pushing the completion date out by months.
* Does it mean: $\max_{a \in S_1}(EF_a) \le \min_{b \in S_2}(ES_b)$?
If so, what if $S_2$ contains independent preparatory work (e.g., procurement of copper grounding cables) that can occur concurrently with civil grading? The schedule engine cannot guess engineering intent.

#### 2. Mutual Recursion and Forward/Backward Pass Collapse
The CPM calculation requires topologically sorting the graph $G = (V, E)$ into a sequence where every predecessor appears before its successor.
* In a valid CPM pass, the Early Dates of activity $v$ are determined strictly by its predecessors:
  $$ES_v = \max_{(u, v) \in E} (EF_u + \text{Lag}_{u,v})$$
* However, the dates of a summary node $W$ are defined as:
  $$ES_W = \min_{c \in \text{Children}(W)} (ES_c), \quad EF_W = \max_{c \in \text{Children}(W)} (EF_c)$$
* If $W$ is allowed to be an endpoint in $E$, then:
  $$ES_c = f(ES_W) = f(\min_{k \in \text{Children}(W)} (ES_k))$$
This creates a **circular mutual dependency** between an entity and its own constituent parts. The forward pass becomes an unresolved system of recursive algebraic constraints rather than a deterministic single-pass DAG traversal ($O(V + E)$).

#### 3. Hidden Cyclic Deadlocks
In construction, disciplines interlock. Civil works and Electrical works do not happen in sequential monolithic silos:
1. `ACT-101 (Civil Grading)` finishes.
2. `ACT-201 (Electrical Earthing Grid Trenching)` starts.
3. Earthing grid copper is laid.
4. `ACT-102 (Civil Foundation Concrete Pour)` encases the grounding conductors.
5. `ACT-202 (Electrical Transformer Inverter Mounting)` takes place on the cured concrete pads.

The real-world activity precedence is:
$$\text{ACT-101} \xrightarrow{FS} \text{ACT-201} \xrightarrow{FS} \text{ACT-102} \xrightarrow{FS} \text{ACT-202}$$
Notice that this activity network alternates cleanly between Civil ($02.1$) and Electrical ($02.2$). If a user links `WBS 02.1` $\to$ `WBS 02.2`, an unresolvable cycle is guaranteed.

### 3.2 The Special P6 "WBS Summary" Activity Type: The Safe Hammock Alternative

Planners frequently ask: *"If I cannot link WBS nodes, how do I model project management overhead, site security, or temporary dewatering that must span the exact duration of a WBS branch?"*

Primavera P6 solves this need cleanly through the **WBS Summary Activity**.

```
┌─────────────────────────────────────────────────────────────────────────────────────────────────┐
│                           HOW P6 "WBS SUMMARY" ACTIVITIES OPERATE                               │
├─────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                 │
│   WBS 02.1: Solar Block 1 Civil Foundations                                                     │
│   ├── ACT-1010: Site Clearing & Grading (Duration: 10d, 01-Jan to 10-Jan)                      │
│   ├── ACT-1020: Piling & Pullout Testing (Duration: 20d, 11-Jan to 31-Jan)                     │
│   ├── ACT-1030: Inverter Pad Casting (Duration: 15d, 20-Jan to 04-Feb)                         │
│   │                                                                                             │
│   └── ACT-1000 [Type: WBS Summary]: "Civil Discipline Supervision & QA"                        │
│       * Early Start = min(ES of ACT-1010, ACT-1020, ACT-1030) = 01-Jan                          │
│       * Early Finish = max(EF of ACT-1010, ACT-1020, ACT-1030) = 04-Feb                        │
│       * Calculated Duration = 35 Calendar Days                                                  │
│       * Resource Loading: 1x Lead Civil Inspector (Charged across active span)                  │
│                                                                                                 │
│   CRITICAL ENGINE RULE:                                                                         │
│   A "WBS Summary" activity is a passive receiver. It is NEVER an active CPM driver.             │
│   It calculates its dates AFTER the main forward/backward CPM pass completes.                   │
│   It CANNOT drive the Early Start of other activities via FS links.                             │
│                                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### How WBS Summary Activities Differ from Normal Tasks:
1. **Activity Type Classification:** In the `TASK` table, the column `task_type` is set to `'TT_WBSummary'` (as opposed to `'TT_Task'` [Task Dependent], `'TT_Rsrc'` [Resource Dependent], or `'TT_LOE'` [Level of Effort]).
2. **Hammock Date Computation:** During scheduling execution, the CPM engine partitions the graph:
   * **Pass 1:** Normal activities (`Task Dependent`, `Resource Dependent`, `Milestones`) are scheduled via standard topological forward and backward passes.
   * **Pass 2:** `WBS Summary` activities inspect their assigned WBS branch:
     $$ES_{\text{WBSummary}} = \min_{a \in \text{WBS Branch}, a \ne \text{WBSummary}} (ES_a)$$
     $$EF_{\text{WBSummary}} = \max_{a \in \text{WBS Branch}, a \ne \text{WBSummary}} (EF_a)$$
3. **No Driving Relationships:** A WBS Summary activity cannot act as a driving predecessor to an execution activity. Its float is either derived or inherited, preventing feedback loops into the core CPM calculations.

## 4. Database Schema Architecture: Two-Table vs Single-Table Debate

When architecting a high-performance scheduling engine backend in PostgreSQL and Go, developers face a classic architectural fork: **The Two-Table Model vs The Single-Table Polymorphic Model**.

```
┌────────────────────────────────────────────────────────────────────────────────────────────────┐
│                             DATABASE ARCHITECTURAL COMPARISON                                  │
├─────────────────────────────────────────────────┬──────────────────────────────────────────────┤
│ METRIC / DESIGN CRITERIA                        │ TWO-TABLE MODEL      │ SINGLE-TABLE MODEL    │
│                                                 │ (PROJWBS & TASK)     │ (NODES / IS_SUMMARY)  │
├─────────────────────────────────────────────────┼──────────────────────┼──────────────────────┤
│ Strict Relational Integrity                     │ ⭐️⭐️⭐️⭐️⭐️ (Flawless)   │ ⭐️ (Requires Triggers)│
│ Sparse Column Overhead (Nullable Pollution)     │ ⭐️⭐️⭐️⭐️⭐️ (Zero)       │ ⭐️ (Massive: 60+ cols)│
│ CPM Engine Query Performance                    │ ⭐️⭐️⭐️⭐️⭐️ (High Speed) │ ⭐️⭐️ (Filter overhead)│
│ Accidental Node Demotion Prevention             │ ⭐️⭐️⭐️⭐️⭐️ (Type Safe)  │ ⭐️ (Prone to bugs)    │
│ Schema Migration Complexity                     │ ⭐️⭐️⭐️ (2 Tables)     │ ⭐️⭐️⭐️⭐️ (1 Table)    │
│ Tree Hierarchy Traversal                        │ ⭐️⭐️⭐️⭐️ (Dedicated)   │ ⭐️⭐️⭐️⭐️ (Single tree)│
│ Production Standard (Primavera P6, Asta Power)  │ ✅ Enterprise Standard│ ❌ Amateur PM Apps    │
└─────────────────────────────────────────────────┴──────────────────────┴──────────────────────┘
```

### 4.1 The Flawed Single-Table "Polymorphic" Model
In naive designs, a developer creates:
```sql
-- ANTI-PATTERN: DO NOT USE IN PRODUCTION SCHEDULING ENGINES
CREATE TABLE schedule_nodes (
    id UUID PRIMARY KEY,
    project_id UUID NOT NULL,
    parent_id UUID REFERENCES schedule_nodes(id),
    name VARCHAR(255) NOT NULL,
    is_summary BOOLEAN NOT NULL DEFAULT FALSE,
    
    -- Execution fields (NULL for 80% of rows if summary!)
    calendar_id UUID REFERENCES calendars(id),
    early_start TIMESTAMPTZ,
    early_finish TIMESTAMPTZ,
    late_start TIMESTAMPTZ,
    late_finish TIMESTAMPTZ,
    total_float_hours NUMERIC(10,2),
    free_float_hours NUMERIC(10,2),
    original_duration_hours NUMERIC(10,2),
    remaining_duration_hours NUMERIC(10,2),
    actual_start TIMESTAMPTZ,
    actual_finish TIMESTAMPTZ,
    activity_type VARCHAR(32),
    physical_percent_complete NUMERIC(5,2),
    status VARCHAR(20)
);
```

#### Why the Single-Table Model Fails in Enterprise PPM:
1. **Severe Nullable Column Pollution:**
   Execution tasks in an enterprise scheduler require over 60 discrete attributes (e.g., `free_float`, `total_float`, `late_start`, `suspend_date`, `resume_date`, `act_work_qty`, `target_work_qty`, `driving_path_flag`, `primary_resource_id`). In a 50,000-node schedule with 5,000 WBS summary nodes, every summary row has 50+ empty/NULL columns, wasting memory, degrading cache efficiency, and cluttering data models.
2. **Broken Foreign Key Integrity:**
   If precedence relationships are stored as:
   ```sql
   CREATE TABLE dependencies (
       pred_id UUID REFERENCES schedule_nodes(id),
       succ_id UUID REFERENCES schedule_nodes(id)
   );
   ```
   The database foreign key allows users or buggy API payloads to insert links pointing to summary nodes! To prevent this, you must write complex `BEFORE INSERT OR UPDATE` PL/pgSQL triggers that query `schedule_nodes.is_summary`. Triggers add latency to bulk CPM updates.
3. **The "Accidental Demotion" Edge Case:**
   If a user deletes all child activities under a summary node, what happens to that summary node in a single-table system? If the frontend code determines "summary-ness" by `SELECT count(*) FROM schedule_nodes WHERE parent_id = self.id`, the summary node suddenly turns into an execution task with 0 duration and no calendar! In a multi-user environment, this causes silent data corruption.

### 4.2 The Enterprise Two-Table Model: `wbs_nodes` and `activities`

This model mirrors the architectural foundation of Oracle Primavera P6 (where `PROJWBS` is completely separate from `TASK`).

```

│   │ parent_wbs_id: UUID (FK, Self)      │      │     │ wbs_id: UUID (FK -> wbs_nodes)       │───┘
│   │ wbs_code: VARCHAR(50) (e.g. "02.1") │      │     │ activity_code: VARCHAR(30)           │
│   │ wbs_name: VARCHAR(255)              │      │     │ activity_name: VARCHAR(255)          │
│   │ responsible_obs_id: UUID (FK)       │      │     │ calendar_id: UUID (FK -> calendars)  │

│                                                │     │ late_start / late_finish: TIMESTAMPTZ│
│                                                │     │ total_float / free_float: NUMERIC    │
│                                                │     │ actual_start / actual_finish: ...    │

│                                                │                        │                       │
```

#### Key Relational Benefits:
1. **Ironclad Precedence Integrity at the DDL Level:**
   `activity_relationships.predecessor_id` and `successor_id` point directly to `activities.activity_id`. It is mathematically and relationally impossible to attach a CPM logic link to a `wbs_node`. No triggers required.
2. **High-Speed In-Memory CPM Cache Loading:**
   When the scheduling engine runs, it executes:
   ```sql
   SELECT activity_id, calendar_id, planned_duration_hours, status 
   FROM activities WHERE project_id = $1;
   
   SELECT predecessor_id, successor_id, link_type, lag_hours 
   FROM activity_relationships WHERE project_id = $1;
   ```
   The engine reads pure execution structs into Go slices without wasting memory or CPU cycles filtering out hierarchy folders.
3. **Hierarchical Path Optimization with PostgreSQL `ltree`:**
   By indexing `wbs_nodes.path` using GiST, subtree rollup queries execute in sub-millisecond time across 100,000+ nodes.

### 6.2 The Hierarchical WBS Rollup Engine (`rollup.go`)

After the CPM engine completes forward and backward passes across all execution activities, the WBS Rollup Engine runs a bottom-up post-order traversal to aggregate dates, costs, and progress to parent containers.

```go
package scheduling

import (
	"sort"
	"strings"
	"time"
)

// RollupProjectWBS aggregates dates, costs, and statuses from leaf activities up through the WBS tree.
func RollupProjectWBS(wbsNodes []*WBSNode, activities []*Activity) error {
	// 1. Group leaf activities by WBSID
	actsByWBS := make(map[string][]*Activity)
	for _, act := range activities {
		actsByWBS[act.WBSID] = append(actsByWBS[act.WBSID], act)
	}

	// 2. Sort WBS nodes by path length descending (bottom-up post-order processing)
	// A deeper node in the tree will have more segments in its materialized path (e.g., "A.B.C" before "A.B")
	sortedWBS := make([]*WBSNode, len(wbsNodes))
	copy(sortedWBS, wbsNodes)
	sort.Slice(sortedWBS, func(i, j int) bool {
		depthI := strings.Count(sortedWBS[i].Path, ".")
		depthJ := strings.Count(sortedWBS[j].Path, ".")
		return depthI > depthJ
	})

	// Map for quick lookup
	wbsMap := make(map[string]*WBSNode)
	for _, node := range wbsNodes {
		wbsMap[node.ID] = node
		// Reset rollup accumulators
		node.EarlyStart = nil
		node.EarlyFinish = nil
		node.ActualStart = nil
		node.ActualFinish = nil
		node.PlannedCost = 0
		node.ActualCost = 0
		node.EarnedValueCost = 0
		node.PhysicalPercent = 0
	}

	// 3. Bottom-up accumulation
	for _, node := range sortedWBS {
		directActs := actsByWBS[node.ID]

		// Accumulate direct leaf activities first
		var (
			minES    *time.Time
			maxEF    *time.Time
			minAS    *time.Time
			maxAF    *time.Time
			allComp  = len(directActs) > 0
			anyStart = false
			totalPlanCost float64
			totalActCost  float64
			totalEV       float64
		)

		for _, act := range directActs {
			// Early Dates Rollup
			if act.EarlyStart != nil && (minES == nil || act.EarlyStart.Before(*minES)) {
				minES = act.EarlyStart
			}
			if act.EarlyFinish != nil && (maxEF == nil || act.EarlyFinish.After(*maxEF)) {
				maxEF = act.EarlyFinish
			}

			// Actual Dates Rollup
			if act.ActualStart != nil {
				anyStart = true
				if minAS == nil || act.ActualStart.Before(*minAS) {
					minAS = act.ActualStart
				}
			}
			if act.ActualFinish != nil {
				if maxAF == nil || act.ActualFinish.After(*maxAF) {
					maxAF = act.ActualFinish
				}
			}

			if act.Status != StatusCompleted {
				allComp = false
			}
			if act.Status == StatusInProgress || act.Status == StatusCompleted {
				anyStart = true
			}

			// Financials
			totalPlanCost += act.PlannedCost
			totalActCost += act.ActualCost
			ev := act.PlannedCost * (act.PhysicalPercent / 100.0)
			totalEV += ev
		}

		node.PlannedCost += totalPlanCost
		node.ActualCost += totalActCost
		node.EarnedValueCost += totalEV
		node.EarlyStart = minES
		node.EarlyFinish = maxEF
		node.ActualStart = minAS

		// Status determination
		if allComp && len(directActs) > 0 {
			node.Status = StatusCompleted
			node.ActualFinish = maxAF
		} else if anyStart {
			node.Status = StatusInProgress
		} else {
			node.Status = StatusNotStarted
		}

		// Calculate Earned Value Physical % Complete for the WBS
		if node.PlannedCost > 0 {
			node.PhysicalPercent = (node.EarnedValueCost / node.PlannedCost) * 100.0
		}

		// 4. Propagate this node's values to its immediate parent WBS
		if node.ParentWBSID != nil {
			parent, exists := wbsMap[*node.ParentWBSID]
			if exists {
				parent.PlannedCost += node.PlannedCost
				parent.ActualCost += node.ActualCost
				parent.EarnedValueCost += node.EarnedValueCost

				if node.EarlyStart != nil && (parent.EarlyStart == nil || node.EarlyStart.Before(*parent.EarlyStart)) {
					parent.EarlyStart = node.EarlyStart
				}
				if node.EarlyFinish != nil && (parent.EarlyFinish == nil || node.EarlyFinish.After(*parent.EarlyFinish)) {
					parent.EarlyFinish = node.EarlyFinish
				}
				if node.ActualStart != nil && (parent.ActualStart == nil || node.ActualStart.Before(*parent.ActualStart)) {
					parent.ActualStart = node.ActualStart
				}
			}
		}
	}

	return nil
}
```

### 6.3 The DAG Network Validator: Enforcing the "No Links on WBS" Rule (`validator.go`)

When an external user or API client imports a schedule or creates a relationship, this validator guarantees that:
1. Neither predecessor nor successor is a WBS node.
2. Both entities exist in the activity pool.
3. The graph remains strictly acyclic (using Kahn's algorithm or Depth First Search cycle detection).

```go
package scheduling

import (
	"fmt"
)

// NetworkValidator verifies graph integrity and enforces strict WBS-Activity separation
type NetworkValidator struct {
	wbsIDs      map[string]bool
	activityIDs map[string]bool
}

func NewNetworkValidator(wbsNodes []*WBSNode, activities []*Activity) *NetworkValidator {
	v := &NetworkValidator{
		wbsIDs:      make(map[string]bool),
		activityIDs: make(map[string]bool),
	}
	for _, w := range wbsNodes {
		v.wbsIDs[w.ID] = true
	}
	for _, a := range activities {
		v.activityIDs[a.ID] = true
	}
	return v
}

// ValidateRelationships verifies that no summary links exist and no cycles are introduced
func (v *NetworkValidator) ValidateRelationships(rels []*Relationship) error {
	adj := make(map[string][]string)
	inDegree := make(map[string]int)

	// Initialize all activities in inDegree map
	for actID := range v.activityIDs {
		inDegree[actID] = 0
	}

	for _, r := range rels {
		// Rule 1: Predecessor must not be a WBS node
		if v.wbsIDs[r.PredecessorID] {
			return fmt.Errorf("INVALID_RELATIONSHIP: Predecessor %s is a WBS Summary Node. "+
				"Relationships cannot target WBS elements", r.PredecessorID)
		}
		// Rule 2: Successor must not be a WBS node
		if v.wbsIDs[r.SuccessorID] {
			return fmt.Errorf("INVALID_RELATIONSHIP: Successor %s is a WBS Summary Node. "+
				"Relationships cannot target WBS elements", r.SuccessorID)
		}

		// Rule 3: Entities must exist in activity register
		if !v.activityIDs[r.PredecessorID] {
			return fmt.Errorf("ENTITY_NOT_FOUND: Predecessor activity %s does not exist", r.PredecessorID)
		}
		if !v.activityIDs[r.SuccessorID] {
			return fmt.Errorf("ENTITY_NOT_FOUND: Successor activity %s does not exist", r.SuccessorID)
		}

		// Self-loop check
		if r.PredecessorID == r.SuccessorID {
			return fmt.Errorf("CYCLE_DETECTED: Activity %s has a self-referencing relationship", r.PredecessorID)
		}

		adj[r.PredecessorID] = append(adj[r.PredecessorID], r.SuccessorID)
		inDegree[r.SuccessorID]++
	}

	// Rule 4: Cycle detection via Kahn's Algorithm (Topological Sort)
	queue := make([]string, 0)
	for actID, deg := range inDegree {
		if deg == 0 {
			queue = append(queue, actID)
		}
	}

	visitedCount := 0
	for len(queue) > 0 {
		curr := queue[0]
		queue = queue[1:]
		visitedCount++

		for _, neighbor := range adj[curr] {
			inDegree[neighbor]--
			if inDegree[neighbor] == 0 {
				queue = append(queue, neighbor)
			}
		}
	}

	if visitedCount != len(v.activityIDs) {
		return errors.New("CYCLE_DETECTED: A circular precedence relationship exists in the activity network")
	}

	return nil
}
```

### 7.1 Tree-Table Flattening Hook (`useScheduleFlatTree.ts`)

```typescript
import { useMemo } from 'react';

export interface WBSNodeUI {
  id: string;
  parentWbsId: string | null;
  code: string;
  name: string;
  path: string;
  earlyStart: string | null;
  earlyFinish: string | null;
  status: 'NOT_STARTED' | 'IN_PROGRESS' | 'COMPLETED';
  physicalPercent: number;
}

export interface ActivityUI {
  id: string;
  wbsId: string;
  code: string;
  name: string;
  earlyStart: string | null;
  earlyFinish: string | null;
  status: 'NOT_STARTED' | 'IN_PROGRESS' | 'COMPLETED';
  plannedDurationHours: number;
  totalFloatHours: number;
  isCritical: boolean;
  physicalPercent: number;
}

export type FlatRowType = 'WBS_SUMMARY' | 'ACTIVITY';

export interface FlatRow {
  rowId: string;
  type: FlatRowType;
  depth: number;
  isExpanded?: boolean;
  data: WBSNodeUI | ActivityUI;
}

export function useScheduleFlatTree(
  wbsNodes: WBSNodeUI[],
  activities: ActivityUI[],
  expandedWBSIds: Set<string>
): FlatRow[] {
  return useMemo(() => {
    const flatRows: FlatRow[] = [];

    // Group child WBS by parent ID
    const wbsByParent = new Map<string | null, WBSNodeUI[]>();
    for (const w of wbsNodes) {
      const parent = w.parentWbsId ?? null;
      if (!wbsByParent.has(parent)) wbsByParent.set(parent, []);
      wbsByParent.get(parent)!.push(w);
    }

    // Group activities by WBS ID
    const actsByWBS = new Map<string, ActivityUI[]>();
    for (const a of activities) {
      if (!actsByWBS.has(a.wbsId)) actsByWBS.set(a.wbsId, []);
      actsByWBS.get(a.wbsId)!.push(a);
    }

    // Recursive traversal
    function traverse(parentWbsId: string | null, depth: number) {
      const children = wbsByParent.get(parentWbsId) || [];
      for (const wbs of children) {
        const isExpanded = expandedWBSIds.has(wbs.id);
        flatRows.push({
          rowId: `wbs-${wbs.id}`,
          type: 'WBS_SUMMARY',
          depth,
          isExpanded,
          data: wbs,
        });

        if (isExpanded) {
          // 1. Render leaf activities under this WBS first
          const directActs = actsByWBS.get(wbs.id) || [];
          for (const act of directActs) {
            flatRows.push({
              rowId: `act-${act.id}`,
              type: 'ACTIVITY',
              depth: depth + 1,
              data: act,
            });
          }

          // 2. Recurse down child WBS sub-nodes
          traverse(wbs.id, depth + 1);
        }
      }
    }

    traverse(null, 0);
    return flatRows;
  }, [wbsNodes, activities, expandedWBSIds]);
}
```

### 7.2 Gantt Bar Visual Rendering: Summary Hammock vs Execution Bar (`GanttRowBar.tsx`)

In the visual Gantt timeline:
* A **Summary Node** is rendered as an architectural "hammock" bar with downward triangular brackets at its start and finish. It has **no dependency connector handles** (preventing users from dragging connection wires to it).
* An **Execution Activity** is rendered as a solid pill bar with color-coded critical status, physical % complete fill, and circular connector anchor points at its start and finish.

```tsx
import React from 'react';
import { FlatRow, WBSNodeUI, ActivityUI } from './useScheduleFlatTree';

interface GanttRowBarProps {
  row: FlatRow;
  xStart: number;
  width: number;
  y: number;
  height: number;
  onStartConnectionDrag?: (activityId: string, anchor: 'START' | 'FINISH') => void;
}

export const GanttRowBar: React.FC<GanttRowBarProps> = ({
  row,
  xStart,
  width,
  y,
  height,
  onStartConnectionDrag,
}) => {
  if (row.type === 'WBS_SUMMARY') {
    const wbs = row.data as WBSNodeUI;
    const bracketSize = 6;

    // Render Primavera-style Summary Hammock Bar with Start/Finish Brackets
    return (
      <g className="wbs-summary-bar group select-none">
        {/* Main top bar */}
        <rect
          x={xStart}
          y={y + 4}
          width={Math.max(width, 2)}
          height={height / 2.5}
          fill="#1e293b"
          rx={1}
        />
        {/* Start Downward Bracket */}
        <polygon
          points={`${xStart},${y + 4} ${xStart + bracketSize},${y + 4} ${xStart},${y + 4 + bracketSize * 1.5}`}
          fill="#1e293b"
        />
        {/* Finish Downward Bracket */}
        <polygon
          points={`${xStart + width},${y + 4} ${xStart + width - bracketSize},${y + 4} ${xStart + width},${y + 4 + bracketSize * 1.5}`}
          fill="#1e293b"
        />
        {/* Summary progress fill overlay */}
        <rect
          x={xStart}
          y={y + 5}
          width={Math.max(width * (wbs.physicalPercent / 100.0), 0)}
          height={height / 2.5 - 2}
          fill="#3b82f6"
          opacity={0.8}
        />
        {/* WBS Summary nodes DO NOT render connection handles! */}
      </g>
    );
  }

  // Otherwise, render an Execution Activity Bar
  const act = row.data as ActivityUI;
  const isCritical = act.isCritical;
  const barColor = isCritical ? '#ef4444' : '#10b981'; // Red for critical, emerald for non-critical

  return (
    <g className="activity-execution-bar group select-none">
      {/* Background Total Duration Bar */}
      <rect
        x={xStart}
        y={y + 3}
        width={Math.max(width, 4)}
        height={height - 6}
        fill={barColor}
        opacity={0.35}
        rx={3}
      />
      {/* Progress Fill */}
      <rect
        x={xStart}
        y={y + 3}
        width={Math.max(width * (act.physicalPercent / 100.0), 0)}
        height={height - 6}
        fill={barColor}
        rx={3}
      />

      {/* Predecessor Connector Anchor (Start) */}
      <circle
        cx={xStart}
        cy={y + height / 2}
        r={4}
        className="opacity-0 group-hover:opacity-100 transition-opacity cursor-crosshair fill-white stroke-slate-800"
        strokeWidth={2}
        onMouseDown={(e) => {
          e.stopPropagation();
          onStartConnectionDrag?.(act.id, 'START');
        }}
      />

      {/* Successor Connector Anchor (Finish) */}
      <circle
        cx={xStart + width}
        cy={y + height / 2}
        r={4}
        className="opacity-0 group-hover:opacity-100 transition-opacity cursor-crosshair fill-white stroke-slate-800"
        strokeWidth={2}
        onMouseDown={(e) => {
          e.stopPropagation();
          onStartConnectionDrag?.(act.id, 'FINISH');
        }}
      />
    </g>
  );
};
```

## 8. Summary & Architectural Principles Checklist

Before moving to the exercises, review this production checklist when designing or maintaining a scheduling engine:

| Rule | Description | Architectural Check |
| :--- | :--- | :--- |
| **1. The Two-Table Separation** | Scope folders live in `wbs_nodes`; execution tasks live in `activities`. | DDL enforces separate tables; foreign keys on relationships target `activities` only. |
| **2. Zero Precedence on WBS** | WBS nodes must never participate in CPM dependency graphs. | API and DAG validators reject any edge where an endpoint is in `wbs_nodes`. |
| **3. Passive Date Derivation** | Summary node dates are strictly $\min(ES)$ and $\max(EF)$ of children. | CPM forward/backward passes ignore WBS nodes; WBS rollup executes in post-order traversal. |
| **4. Pure Status Rollup** | Summary status is derived deterministically from child activity statuses. | No UI mechanism exists to toggle `status` on a WBS row. |
| **5. WBS Summary Task Isolation** | If a hammock task is required, use `activity_type = 'WBS_SUMMARY'`. | Hammock dates are calculated in Pass 2; they never drive successor critical paths. |
| **6. Staged Progressive Elaboration** | High-level WBS packages can be created without leaf activities on Day 1. | System allows empty WBS nodes without triggering division-by-zero or CPM errors. |
