## 1. Executive Summary & The Core Mental Model

### 1.1 The Axiom: A Project Schedule Is a Living Contract, Not Static Code
In modern Git-based software development, code repositories evolve continuously through pull requests. When a release tag (such as `v1.0.0`) is published, it represents an immutable snapshot of source code at that specific commit hash. If new features are added in `v1.1.0` or a bugfix branch is spun off in `v1.0.1`, developers compare branches and tags using `git diff v1.0.0..HEAD`.

Enterprise capital projects—governed by engines like **Oracle Primavera P6**, **Safran Project**, and **Asta Powerproject**—manage project schedules under a similar, yet contractually enforced paradigm:

> **Axiom:** Mega-projects operate across multiple parallel realities. A single baseline is mathematically and contractually incapable of capturing initial commitments, approved scope changes, and physical recovery plans simultaneously.

Consider the **Surya 100MW Solar IPP Project** in Rajasthan, India. Over its 18-month execution lifecycle, the project experiences three distinct baseline realities:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                 THE MULTI-BASELINE REALITY MATRIX                                │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   BASELINE LEVEL       NAME & DESIGNATION               CONTRACTUAL PURPOSE                      │
│   ──────────────       ──────────────────               ───────────────────                      │
│   Baseline 0 (B0)      Original Contract Award          • Immutable benchmark signed at award.   │
│                        (Initial Sanction / As-Planned)  • Dictates Liquidated Damages liability. │
│                                                         • Never modified, overwritten, or deleted│
│                                                                                                  │
│   Baseline 1 (B1)      Approved Scope Variation         • Captures client-directed additions     │
│                        (+20MW Expansion Order)          (e.g., Rajasthan DISCOM adds 20MW).      │
│                                                         • Entitles contractor to Time Extension  │
│                                                                                                  │
│   Baseline 2 (B2)      Recovery Acceleration Plan       • Internal aggressive target to catch    │
│                        (Post-Monsoon Recovery Target)   up after 45 days of flash flood delays.  │
│                                                         • Mobilizes 24/7 piling & overtime.      │
│                                                                                                  │
│   Current Schedule     Active Execution Graph           • Forecasts physical completion based    │
```

If the scheduling engine allowed the contractor to simply overwrite the Original Contract Baseline (B0) every time they fell behind, the developer would lose the legal right to claim delay damages, and the contractor would lose the legal right to claim time extensions for owner-caused delays.

### 2.1 Project Baseline vs. User Baselines
In P6, a project can have hundreds of archived baseline snapshots in its database, but at any given time, an active project binds up to **four concurrent baseline targets**:

1. **Project Baseline (Target 0):**
   - The authoritative benchmark for the entire project team.
   - Typically locked to the **Original Contract Award Baseline (B0)** or the **Approved Current Budget Baseline (B1)**.
   - Used for corporate reporting, monthly executive dashboards, and contractual client submissions.
2. **Primary User Baseline (Target 1):**
   - Assigned per user session or project role.
   - Commonly mapped to the active Scope Change baseline.
3. **Secondary User Baseline (Target 2):**
   - Commonly mapped to an internal contractor target or recovery schedule.
4. **Tertiary User Baseline (Target 3):**
   - Commonly used for "what-if" risk scenario comparisons or previous month-end snapshots.

### 2.2 Deep Clone vs. Shadow Records: How P6 Internally Stores Baselines
In traditional database design, one might assume a baseline is just a date column on the activity table (`baseline_start`, `baseline_finish`). 
**Primavera P6 does not do this.**

In P6's underlying database schema (`PMDB`):
* When you click **Project → Maintain Baselines → Add (Convert another project or copy current)**, P6 creates a **complete, independent deep clone of the entire project graph**!
* The cloned project is stored in the exact same table: `PROJECT`.
* The child clone's `orig_proj_id` column points back to the active project's `proj_id`.
* Every single activity (`TASK`), relationship (`TASKPRED`), resource assignment (`TASKRSRC`), activity step (`TASKACTV`), and calendar assignment is duplicated into separate database rows.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                   P6 DEEP-CLONE SNAPSHOT MODEL                                   │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   `PROJECT` Table:                                                                               │
│   proj_id: 101 | proj_short_name: "SURYA-LIVE"  | orig_proj_id: NULL  ◄── Active Project         │
│   proj_id: 102 | proj_short_name: "SURYA-BL0"   | orig_proj_id: 101   ◄── Deep-Clone Baseline 0  │
│   proj_id: 103 | proj_short_name: "SURYA-BL1"   | orig_proj_id: 101   ◄── Deep-Clone Baseline 1  │
│                                                                                                  │
│   `TASK` (Activity) Table:                                                                       │
│   task_id: 5001 | proj_id: 101 | task_code: "ACT-INV-001" | target_start: 2026-11-01 (Live)     │
│   task_id: 9001 | proj_id: 102 | task_code: "ACT-INV-001" | target_start: 2026-09-01 (B0 Snap) │
│   task_id: 9501 | proj_id: 103 | task_code: "ACT-INV-001" | target_start: 2026-10-15 (B1 Snap) │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### Why Deep Cloning Is Architectural Genius for Project Controls
1. **Unlinkable Immutability:** An engineer editing relationships in the active project cannot accidentally corrupt the baseline logic graph.
2. **Re-restorable Historical Worlds:** Because the baseline contains its own independent dependency ties and calendars, a planner can detach a baseline, open it as a standalone live project, and re-run CPM forward/backward passes to simulate "what we knew back in January."

## 3. Contractual Re-baselining Governance: FIDIC Clause 8.3 & NEC4

In enterprise construction disputes, billions of dollars hinge on whether a schedule update was a **legitimate contractual re-baseline** or an **unauthorized attempt to erase contractor culpability**.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                   THE DELAY ERASURE CONTROVERSY                                  │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   SCENARIO: Contractor falls 60 days behind on Piling due to slow crew mobilization.             │
│   CONTRACTUAL LIABILITY: Liquidated Damages (LD) = $50,000 / day = $3,000,000!                   │
│                                                                                                  │
│   FRAUDULENT CONTRACTOR MANEUVER:                                                                │
│   • Contractor unilaterally creates a "New Baseline" that shifts the completion date out by 60d. │
│   • Negative float (-60 days) magically resets to 0.0 days!                                      │
│   • Contractor claims: "Look, our new baseline has 0 float; we are on schedule!"                 │
│                                                                                                  │
│   FIDIC & FORENSIC PRINCIPLE:                                                                    │
│   Resetting the baseline does NOT wipe out delay liability unless the Employer formally grants   │
│   an Extension of Time (EoT) under FIDIC Clause 8.4 / 20.1!                                      │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.1 FIDIC (International Federation of Consulting Engineers) Framework

Under the **FIDIC Red Book / Yellow Book (1999 / 2017 Editions)**:
* **Clause 8.3 (Programme):**
  - The Contractor must submit an initial time programme within 28 days of receiving the Notice to Commence.
  - The Contractor must submit a **revised programme** whenever the previous programme is inconsistent with actual progress or with the Contractor's obligations.
  - **Critical Legal Nuance:** The Engineer's approval or non-rejection of a revised programme under Clause 8.3 **does NOT relieve the Contractor of any liability**, nor does it automatically grant an Extension of Time (EoT).
* **Clause 8.4 (Extension of Time for Completion):**
  - An extension of the contractual completion date is granted **only** for specific employer risks:
    1. Variations / Scope changes directed by the Engineer.
    2. Exceptionally adverse climatic conditions (e.g. 100-year Rajasthan flood).
    3. Unforeseeable shortages of personnel or goods caused by epidemics or government shutdown.
    4. Any delay or impediment caused by the Employer.
* **The Rule of Governance:**
  A revised schedule submitted under Clause 8.3 becomes an updated **Operating Target**, but the **Original Baseline (B0)** remains legally binding until a formal Variation and EoT determination is issued.

### 3.2 NEC4 (New Engineering Contract) Framework
Under **NEC4 Engineering and Construction Contract (ECC)**:
* **Clause 31 & 32 (The Accepted Programme):**
  - Unlike FIDIC, NEC4 operates on the concept of the **Accepted Programme**.
  - Every month, the contractor submits an updated programme. Once the Project Manager accepts it, it becomes the new contractual benchmark against which future **Compensation Events (CEs)** are assessed.
  - If a contractor delay occurs, it must be shown in the programme. The contractor cannot reset target dates without compensation events approved by the Project Manager.

### 3.3 The Three Legitimate Triggers for Re-baselining
An enterprise scheduling engine must enforce a governance workflow where re-baselining is restricted to three verified criteria:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                               LEGITIMATE RE-BASELINING CRITERIA                                  │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
```

## 4. Multi-Baseline Variance Tracking & Triangulation

When tracking an active project against multiple baselines, P6 calculates variances across time, duration, and cost.

### 4.1 Variance Formulations
Let $t_{\text{start}}$ and $t_{\text{finish}}$ be the forecasted early dates of an activity in the active schedule, and let $t_{\text{start}}^{(B_k)}$ and $t_{\text{finish}}^{(B_k)}$ be the scheduled dates in baseline $B_k$.

#### 1. Start Variance to Baseline $k$ ($\text{SV}_{B_k}$)
$$\text{SV}_{B_k} = t_{\text{start}} - t_{\text{start}}^{(B_k)}$$
* In P6 convention:
  - $\text{SV} > 0$ (Positive Variance): Activity is **delayed** (starting later than baseline).
  - $\text{SV} < 0$ (Negative Variance): Activity is **ahead of schedule** (starting earlier than baseline).
  *(Note: In Gantt table displays, P6 expresses variance in working days filtered through the activity's calendar).*

#### 2. Finish Variance to Baseline $k$ ($\text{FV}_{B_k}$)
$$\text{FV}_{B_k} = t_{\text{finish}} - t_{\text{finish}}^{(B_k)}$$
This is the single most critical variance for critical path activities, directly quantifying potential delay to downstream milestones.

#### 3. Variance at Completion ($\text{VAC}$)
In cost and labor tracking:
$$\text{VAC} = \text{BAC} - \text{EAC}$$
Where:
* $\text{BAC}$: Budget At Completion in Baseline.
* $\text{EAC}$: Estimate At Completion in Active Schedule ($\text{ACWP} + \text{ETC}$).
* A negative $\text{VAC}$ indicates an anticipated cost overrun.

### 4.2 Multi-Baseline Triangulation Analysis
By comparing the active schedule simultaneously against Baseline 0, Baseline 1, and Baseline 2, project controllers perform **Delay Attribution Triangulation**:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                 DELAY ATTRIBUTION TRIANGULATION                                  │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   Activity: ACT-SUB-010 "Energize 220kV Pooling Substation"                                      │
│   Original Baseline (B0) Finish:     15-Oct-2026                                                 │
│   Scope Variation Baseline (B1) Finish: 30-Nov-2026 (+46 days due to DISCOM Grid Line delay)    │
│   Recovery Target Baseline (B2) Finish: 15-Nov-2026 (Internal target)                           │
│   Current Live Forecast Finish:      15-Dec-2026                                                 │
│                                                                                                  │
│   TRIANGULATION CALCULATIONS:                                                                    │
│   • Total Delay vs Original Contract (B0): 15-Dec minus 15-Oct = +61 Days Delayed                │
│   • Excusable / Compensable Delay (B1 - B0): 30-Nov minus 15-Oct = +46 Days (Owner Responsibility)│
│   • Contractor Culpable Delay (Live - B1):  15-Dec minus 30-Nov = +15 Days (Contractor LD Risk)  │
│   • Recovery Slippage (Live - B2):          15-Dec minus 15-Nov = +30 Days Missed Recovery       │
│                                                                                                  │
│   LEGAL AUDIT CONCLUSION:                                                                        │
│   The contractor is liable for Liquidated Damages on ONLY 15 days, not 61 days!                  │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

Without multi-baseline tracking, a court or dispute adjudication board (DAB) would see 61 days of delay and could improperly penalize the contractor for delays caused by the owner's grid interconnection delays.

## 5. Modern Database Architecture for Multi-Baseline Engines

When architecting a web-based scheduling platform in **Golang + PostgreSQL**, replicating P6's deep-cloning model requires careful consideration of storage amplification, query latency, and referential integrity.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                              DATABASE STORAGE PATTERNS FOR BASELINES                             │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   PATTERN A: FULL TABLE CLONE (P6 Legacy Style)                                                  │
│   • Duplicate all activity & dependency rows into `activities` with new `project_id`.            │
│   • Pros: Complete isolation; baseline can be opened and recalculated as a standalone graph.     │
│   • Cons: 100,000 activities * 10 baselines = 1,000,000 rows. DB bloat.                          │
│                                                                                                  │
│   PATTERN B: SHADOW SNAPSHOT TABLES (Modern Relational Architecture)                             │
│   • Live activities live in `activities`.                                                        │
│   • Baseline snapshots live in `activity_baselines` keyed by `(baseline_id, activity_code)`.     │
│   • Pros: Highly optimized for multi-column Gantt queries; clean indexing; immutable.           │
│   • Cons: Cannot run CPM forward/backward passes directly inside the snapshot table.              │
│                                                                                                  │
│   PATTERN C: COPY-ON-WRITE DELTA ENGINE (Git Tree / Merkle DAG)                                  │
│   • Store immutable activity versions; baselines are arrays of activity version hashes.          │
│   • Pros: Zero storage duplication.                                                              │
│   • Cons: Extreme SQL query complexity; high JOIN overhead for real-time Gantt canvas.           │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

For high-performance web applications, **Pattern B (Shadow Snapshot Tables)** provides the optimal balance: sub-millisecond multi-baseline joins for Next.js Gantt canvas rendering, combined with absolute immutability.

### 5.1 PostgreSQL Schema for Multi-Baseline Architecture

```sql
-- Project Baselines Metadata Table
CREATE TYPE baseline_category_enum AS ENUM (
    'CONTRACT_AWARD_B0', 
    'APPROVED_VARIATION_B1', 
    'RECOVERY_TARGET_B2', 
    'INTERNAL_WHAT_IF_B3'
);

CREATE TABLE project_baselines (
    baseline_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL REFERENCES projects(project_id) ON DELETE CASCADE,
    baseline_code VARCHAR(32) NOT NULL,
    baseline_name VARCHAR(255) NOT NULL,
    category baseline_category_enum NOT NULL,
    is_active_project_baseline BOOLEAN NOT NULL DEFAULT FALSE,
    is_locked BOOLEAN NOT NULL DEFAULT TRUE,
    
    -- Snapshot metadata
    data_date_at_capture TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CLOCK_TIMESTAMP(),
    created_by_user_id UUID,
    approved_by_user_id UUID,
    approval_reference VARCHAR(128), -- e.g., "FIDIC Engineer Determination EoT #2"
    
    UNIQUE (project_id, baseline_code)
);

CREATE INDEX idx_project_baselines_proj ON project_baselines(project_id);

-- Activity Baseline Snapshot Table (Immutable Historical Data)
CREATE TABLE activity_baselines (
    snapshot_id BIGSERIAL PRIMARY KEY,
    baseline_id UUID NOT NULL REFERENCES project_baselines(baseline_id) ON DELETE CASCADE,
    activity_id UUID NOT NULL, -- Logical link to live activity
    activity_code VARCHAR(32) NOT NULL,
    activity_name VARCHAR(255) NOT NULL,
    wbs_id UUID NOT NULL,
    
    -- Scheduled Durations & Dates at Snapshot Time
    duration_seconds BIGINT NOT NULL,
    planned_start_date TIMESTAMPTZ NOT NULL,
    planned_finish_date TIMESTAMPTZ NOT NULL,
    early_start_date TIMESTAMPTZ NOT NULL,
    early_finish_date TIMESTAMPTZ NOT NULL,
    late_start_date TIMESTAMPTZ NOT NULL,
    late_finish_date TIMESTAMPTZ NOT NULL,
    
    -- Float & Criticality
    total_float_seconds BIGINT NOT NULL,
    free_float_seconds BIGINT NOT NULL,
    is_critical BOOLEAN NOT NULL,
    
    -- Cost & Units
    budgeted_cost NUMERIC(15, 2) NOT NULL DEFAULT 0.00,
    budgeted_units NUMERIC(12, 4) NOT NULL DEFAULT 0.0000,
    
    UNIQUE (baseline_id, activity_code)
);

CREATE INDEX idx_activity_baselines_lookup ON activity_baselines(baseline_id, activity_code);
CREATE INDEX idx_activity_baselines_live ON activity_baselines(activity_id);
```

### 5.2 Ultra-Fast Multi-Baseline Gantt View Query
Using this schema, your Next.js frontend can query an activity with its live forecast and both Baseline 0 and Baseline 1 dates in a single indexed query:

```sql
SELECT 
    a.activity_code,
    a.activity_name,
    a.early_start_date AS live_start,
    a.early_finish_date AS live_finish,
    a.total_float_seconds / 28800.0 AS live_float_days,
    
    -- Baseline 0 (Contract Award)
    b0.planned_start_date AS b0_start,
    b0.planned_finish_date AS b0_finish,
    ROUND(EXTRACT(EPOCH FROM (a.early_finish_date - b0.planned_finish_date)) / 86400.0, 1) AS b0_finish_variance_days,
    
    -- Baseline 1 (Scope Variation)
    b1.planned_start_date AS b1_start,
    b1.planned_finish_date AS b1_finish,
    ROUND(EXTRACT(EPOCH FROM (a.early_finish_date - b1.planned_finish_date)) / 86400.0, 1) AS b1_finish_variance_days

FROM activities a
LEFT JOIN activity_baselines b0 
    ON b0.activity_code = a.activity_code 
    AND b0.baseline_id = (SELECT baseline_id FROM project_baselines WHERE project_id = a.project_id AND category = 'CONTRACT_AWARD_B0' LIMIT 1)
LEFT JOIN activity_baselines b1 
    ON b1.activity_code = a.activity_code 
    AND b1.baseline_id = (SELECT baseline_id FROM project_baselines WHERE project_id = a.project_id AND category = 'APPROVED_VARIATION_B1' LIMIT 1)
WHERE a.project_id = '11111111-2222-3333-4444-555555555555'
ORDER BY a.early_start_date ASC;
```

## 6. High-Performance Golang Multi-Baseline Diffing & Variance Engine

In a cloud scheduling engine, users frequently request a **Schedule Delta / Variance Report**.
The Go engine must diff the active schedule against any target baseline, categorizing:
1. **Added Activities:** Activities present in Live but missing from Baseline (scope creep).
2. **Deleted Activities:** Activities present in Baseline but deleted from Live (unapproved scope deletion).
3. **Date & Float Shifts:** Activities whose start/finish or total float shifted.
4. **Critical Path Migration:** Activities that transitioned from non-critical to critical or vice versa.

```go
package baseline

import (
	"fmt"
	"math"
	"time"
)

// ActivitySnapshot represents an immutable activity record in a baseline.
type ActivitySnapshot struct {
	ActivityCode      string    `json:"activity_code"`
	ActivityName      string    `json:"activity_name"`
	PlannedStart      time.Time `json:"planned_start"`
	PlannedFinish     time.Time `json:"planned_finish"`
	DurationSeconds   int64     `json:"duration_seconds"`
	TotalFloatSeconds int64     `json:"total_float_seconds"`
	IsCritical        bool      `json:"is_critical"`
	BudgetedCost      float64   `json:"budgeted_cost"`
}

// LiveActivity represents the current state of an activity in the active project.
type LiveActivity struct {
	ActivityCode      string    `json:"activity_code"`
	ActivityName      string    `json:"activity_name"`
	EarlyStart        time.Time `json:"early_start"`
	EarlyFinish       time.Time `json:"early_finish"`
	DurationSeconds   int64     `json:"duration_seconds"`
	TotalFloatSeconds int64     `json:"total_float_seconds"`
	IsCritical        bool      `json:"is_critical"`
	EstimateAtComp    float64   `json:"estimate_at_completion"`
}

// ActivityVariance encapsulates computed deltas for a single task.
type ActivityVariance struct {
	ActivityCode         string    `json:"activity_code"`
	ActivityName         string    `json:"activity_name"`
	LiveFinish           time.Time `json:"live_finish"`
	BaselineFinish       time.Time `json:"baseline_finish"`
	
	// Variances in Working Days (8 hours = 28,800 seconds)
	StartVarianceDays    float64   `json:"start_variance_days"`
	FinishVarianceDays   float64   `json:"finish_variance_days"`
	DurationVarianceDays float64   `json:"duration_variance_days"`
	FloatVarianceDays    float64   `json:"float_variance_days"`
	
	CostVariance         float64   `json:"cost_variance"` // BAC - EAC
	CriticalPathChanged  bool      `json:"critical_path_changed"`
	Status               string    `json:"status"`        // "UNMODIFIED", "SHIFTED", "CRITICAL_SLIP"
}

// ProjectScheduleDiff encapsulates the full diff report between Live and Baseline.
type ProjectScheduleDiff struct {
	BaselineID        string              `json:"baseline_id"`
	BaselineCode      string              `json:"baseline_code"`
	ComparedAt        time.Time           `json:"compared_at"`
	AddedActivities   []LiveActivity      `json:"added_activities"`
	DeletedActivities []ActivitySnapshot  `json:"deleted_activities"`
	Variances         []ActivityVariance  `json:"variances"`
	TotalProjectSlipDays float64          `json:"total_project_slip_days"`
}

const SecondsPerWorkingDay = 28800.0 // Standard 8-hour shift

// ComputeScheduleDiff performs high-speed graph diffing between live and baseline.
func ComputeScheduleDiff(
	baselineID, baselineCode string,
	baselineActivities map[string]ActivitySnapshot,
	liveActivities map[string]LiveActivity,
) (*ProjectScheduleDiff, error) {

	diff := &ProjectScheduleDiff{
		BaselineID:        baselineID,
		BaselineCode:      baselineCode,
		ComparedAt:        time.Now().UTC(),
		AddedActivities:   make([]LiveActivity, 0),
		DeletedActivities: make([]ActivitySnapshot, 0),
		Variances:         make([]ActivityVariance, 0),
	}

	var maxProjectSlip float64

	// 1. Detect Deleted Activities and Evaluate Matching Activities
	for code, baseAct := range baselineActivities {
		liveAct, exists := liveActivities[code]
		if !exists {
			diff.DeletedActivities = append(diff.DeletedActivities, baseAct)
			continue
		}

		// Calculate calendar chronological delta in days
		startDeltaSec := liveAct.EarlyStart.Sub(baseAct.PlannedStart).Seconds()
		finishDeltaSec := liveAct.EarlyFinish.Sub(baseAct.PlannedFinish).Seconds()
		durDeltaSec := float64(liveAct.DurationSeconds - baseAct.DurationSeconds)
		floatDeltaSec := float64(liveAct.TotalFloatSeconds - baseAct.TotalFloatSeconds)

		startVarDays := math.Round((startDeltaSec/86400.0)*10.0) / 10.0
		finishVarDays := math.Round((finishDeltaSec/86400.0)*10.0) / 10.0
		durVarDays := math.Round((durDeltaSec/SecondsPerWorkingDay)*10.0) / 10.0
		floatVarDays := math.Round((floatDeltaSec/SecondsPerWorkingDay)*10.0) / 10.0

		costVariance := baseAct.BudgetedCost - liveAct.EstimateAtComp
		critChanged := liveAct.IsCritical != baseAct.IsCritical

		status := "UNMODIFIED"
		if finishVarDays > 0.0 && liveAct.IsCritical {
			status = "CRITICAL_SLIP"
		} else if math.Abs(finishVarDays) > 0.1 || math.Abs(startVarDays) > 0.1 {
			status = "SHIFTED"
		}

		if liveAct.IsCritical && finishVarDays > maxProjectSlip {
			maxProjectSlip = finishVarDays
		}

		diff.Variances = append(diff.Variances, ActivityVariance{
			ActivityCode:         code,
			ActivityName:         liveAct.ActivityName,
			LiveFinish:           liveAct.EarlyFinish,
			BaselineFinish:       baseAct.PlannedFinish,
			StartVarianceDays:    startVarDays,
			FinishVarianceDays:   finishVarDays,
			DurationVarianceDays: durVarDays,
			FloatVarianceDays:    floatVarDays,
			CostVariance:         costVariance,
			CriticalPathChanged:  critChanged,
			Status:               status,
		})
	}

	// 2. Detect Added Activities (Present in Live, missing in Baseline)
	for code, liveAct := range liveActivities {
		if _, exists := baselineActivities[code]; !exists {
			diff.AddedActivities = append(diff.AddedActivities, liveAct)
		}
	}

	diff.TotalProjectSlipDays = maxProjectSlip
	return diff, nil
}
```

## 8. Summary of Re-baselining Governance Rules for Engineering Teams

1. **Baseline 0 Is Contractually Sacred:** Never allow any user, administrator, or database migration to overwrite or delete Baseline 0. It is the legal baseline against which all forensic delay claims are judged.
2. **Re-baselining Requires Dual Sign-Off:** Implement an approval workflow in your API (`POST /projects/:id/baselines/approve`) requiring cryptographic or role-based verification from both the Project Manager and Commercial Contracts Director.
3. **Never Re-baseline to Hide Delays:** An internal recovery schedule must be captured as an auxiliary User Baseline (B2), never by modifying the contractual baseline.
4. **Use Deep-Clone or Shadow Records for Integrity:** Do not store baselines as flat date columns on the live activity table. Use dedicated shadow snapshot tables to guarantee historical immutability.
