## 🧠 Section A: Conceptual & Algorithmic Foundations

### Solution 1: The Three Percent Complete Types & Coupling Behavior

#### 1. Mathematical Formulas
* **Duration % Complete:**
  $$\text{Duration \% Complete} = \frac{\text{Actual Duration}}{\text{Actual Duration} + \text{Remaining Duration}} \times 100 = \frac{AD}{AD + RD} \times 100$$
* **Physical % Complete:**
  $$\text{Physical \% Complete} = \sum_{k=1}^n \left( \frac{W_k}{\sum_{j=1}^n W_j} \times S_k \right)$$
  Where $W_k$ is the weight of step $k$ and $S_k \in [0, 100]$ is the measured completion of step $k$ (or entered directly by the field engineer based on physical work measured in place).
* **Units % Complete:**
  $$\text{Units \% Complete} = \frac{\text{Actual Units}}{\text{Actual Units} + \text{Remaining Units}} \times 100 = \frac{AU}{AU + RU} \times 100$$
  Where $AU$ is actual labor man-hours or equipment machine-hours and $RU$ is remaining estimated hours.

#### 2. Coupling Behavior in P6's Scheduling Engine
```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                 COUPLING ARCHITECTURE COMPARISON                                 │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   PERCENT COMPLETE TYPE      COUPLED TO REMAINING DURATION?     EVM INTEGRITY                    │
│   ─────────────────────      ──────────────────────────────     ─────────────                    │
│   Duration % Complete        YES (Bidirectional Coupling)       DANGEROUS (Conflates time with   │
│                              • Modifying % recalculates RD.     earned physical output).         │
│                              • Modifying RD recalculates %.                                      │
│                                                                                                  │
│   Physical % Complete        NO (Completely Decoupled)          GOLD STANDARD (Mandated by PMI   │
│                              • Modifying % leaves RD intact.    & AACE for BCWP calculations).   │
│                              • Modifying RD leaves % intact.                                     │
│                                                                                                  │
│   Units % Complete           NO to RD, but YES to Units         RESOURCE-FOCUSED (Tracks burn    │
│                              • Modifying % recalculates RU.     rate, not physical scope).       │
│                              • Modifying RU recalculates %.                                      │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```
* **Duration % Complete:** If an activity has an Original Duration ($OD$) of 10 days and the user enters `80%`, P6 forces $\text{Remaining Duration} = OD \times (1 - 0.80) = 2\text{ days}$. If the user types $\text{Remaining Duration} = 5\text{ days}$ (with $\text{Actual Duration} = 5\text{ days}$), P6 mutates $\text{Duration \%} = \frac{5}{5 + 5} \times 100 = 50\%$.
* **Physical % Complete:** There is zero coupling to Remaining Duration. If an engineer enters $\text{Physical \%} = 95\%$, the Remaining Duration remains untouched. If the engineer discovers that finishing the last 5% requires specialized cranes arriving in 20 days, they can set $\text{Remaining Duration} = 20\text{ days}$ without disturbing the verified 95% physical completion.

#### 3. The "90% Complete Syndrome"
In physical construction, Duration % Complete creates the catastrophic illusion that an activity is nearly finished simply because 90% of its budgeted calendar days have elapsed.
* **The Mechanism:** On a 20-day tracker installation task, 18 calendar days elapse ($\text{Actual Duration} = 18$). The naive formula calculates $\frac{18}{20} \times 100 = 90\%$.
* **The Concealed Reality:** The crew hit hard subsurface rock and only installed 20% of the tracker tables.
* **The Collapse:** When Day 20 arrives, the contractor cannot finish. They reveal that 30 more days are needed ($\text{Remaining Duration} = 30$). P6 instantly recalculates Duration % as $\frac{20}{20 + 30} \times 100 = 40\%$. The schedule reports a bizarre negative progress or progress collapse, destroying executive trust and hiding delays from CPM downstream paths.

### Solution 2: The Data Date Demarcation Axiom

#### 1. The Four Fundamental Chronological Validation Rules
For any activity node $A$ evaluated at Data Date $DD$:
1. **Rule of Historical Inception (Actual Start):**
   $$AS \le DD$$
   No actual event can occur in the future.
2. **Rule of Chronological Order & Historical Completion (Actual Finish):**
   $$AF \implies (AS \le AF \le DD)$$
   An activity cannot finish before it starts, and it cannot complete after the Data Date.
3. **Rule of Terminal Completion (Zero Remaining Work):**
   $$AF \ne \text{NULL} \implies (RD = 0 \land \text{Physical \%} = 100.0 \land \text{Status} = \text{COMPLETED})$$
   A completed activity cannot have remaining work or fractional progress.
4. **Rule of Active Execution (In-Progress Boundary):**
   $$(AS \ne \text{NULL} \land AF = \text{NULL}) \implies (RD > 0 \land \text{Status} = \text{IN\_PROGRESS})$$
   An in-progress activity must have remaining duration extending strictly forward into the future domain ($t \ge DD$).

#### 2. Downstream Scheduling Paradoxes & EVM Distortions
If a user submits $AS = \text{2026-11-20}$ when $DD = \text{2026-11-15}$:
* **CPM Graph Violation:** CPM forward pass algorithms expect actual dates to be boundary conditions in the past. If an actual date sits in the future, the forward pass scheduler encounters an activity that claims to have "actually happened" before the simulation timeline has even reached it.
* **Float Corruption:** P6's backward pass calculates Total Float as $\text{Late Finish} - \text{Early Finish}$. Injecting an actual date into the future can force Early Finish earlier than Data Date, producing artificial positive float or negative float spikes.
* **EVM Billing Fraud:** In Earned Value reporting, Earned Value ($\text{EV}$) is recognized up to the Data Date. Recognizing actual progress in the future enables fraudulent contractors to claim contractor progress billing for work that has not yet occurred on site.

### Solution 3: Out-of-Sequence Logic Resolution

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                            OUT-OF-SEQUENCE CPM SCHEDULE RESOLUTION                               │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   Network Logic: [ Act A: Trenching (RD=6d) ] ───FS───► [ Act B: Cable Pull (RD=7d) ]            │
│   Status at DD:  Act A has 6d remaining. Act B has started early (AD=1d, RD=7d).                 │
│                                                                                                  │
│   MODE 1: RETAINED LOGIC (Standard / Contractual Best Practice)                                  │
│   DD                                                                                             │
│    │◄─── Act A (RD=6d) ───►                                                                      │
│    │                       │ (FS tie enforced on remaining duration!)                            │
│    │                       ▼                                                                     │
│    │                       ◄─────── Act B Remaining (RD=7d) ───────►                             │
│   [Act B is split: Actual work is in past; Remaining work waits for Act A to finish].            │
│                                                                                                  │
│   MODE 2: PROGRESS OVERRIDE (Aggressive / Optimistic)                                            │
│   DD                                                                                             │
│    │◄─── Act A (RD=6d) ───►                                                                      │
│    │◄─────── Act B Remaining (RD=7d) ───────►  (FS tie ignored for remaining duration!)          │
│   [Act B proceeds in parallel from Data Date, ignoring predecessor constraint].                  │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. Retained Logic Handling
Under **Retained Logic**, the CPM engine respects the physical network logic ties despite the early out-of-sequence start.
* Activity B's Actual Duration ($1\text{ day}$) remains in the historical past ($t < DD$).
* However, Activity B's **Remaining Duration** ($7\text{ days}$) cannot be scheduled at the Data Date. It is constrained by the Finish-to-Start dependency with Activity A.
* The Early Start of Activity B's remaining duration is held until Activity A's Early Finish ($\text{Early Finish}_A = DD + 6\text{ days}$).
* Therefore, Activity B is split, finishing at $DD + 6 + 7 = DD + 13\text{ days}$.

#### 2. Progress Override Handling
Under **Progress Override**, the engine assumes that because the contractor succeeded in starting Activity B early, the original Finish-to-Start dependency was false, obsolete, or circumvented.
* The engine overrides the FS tie for remaining work.
* Activity B's Remaining Duration begins immediately at the Data Date ($ES_B = DD$).
* Activity B finishes at $DD + 7\text{ days}$, running completely in parallel with Activity A.

#### 3. Contractual Mandate
International contracts (such as **FIDIC Clause 8.3** and **US Army Corps of Engineers ER 1-1-11**) strictly mandate **Retained Logic**.
* **Reason:** In physical construction, partial out-of-sequence work (e.g., pulling cables into a partially dug trench) does not mean the entire remaining cable scope can be completed without the rest of the trench being dug. Progress Override conceals the reality that remaining cable pulling will stall as soon as the cable crew catches up to the stalled trenching crew.

### Solution 4: Micro-Activities vs. Activity Steps

#### 1. Three Major Drawbacks of Hyper-Decomposition (Micro-Tasks)
1. **Computational & Memory Explosion in Graph Traversal:** 
   A project with 40 inverter stations ballooning from 40 activities to 600 activities with 1,200 relationships increases the adjacency list size and memory cache misses. Topological sorting, forward pass, backward pass, and free float calculations scale with $O(V + E)$.
2. **Logic Tie Maintenance Overhead & Artificial Rigidity:** 
   Managing 1,200 micro-relationships creates fragile schedules. If an engineer accidentally adds a circular tie or incorrect lag between "Formwork Inverter 3" and "Rebar Inverter 3," the entire project network locks up.
3. **Gantt Chart Visual Clutter & Cognitive Overload:** 
   Field superintendents and executive boards cannot parse a Gantt chart with 600 micro-bars for concrete pours. They need to see macro deliverables.

#### 2. How Activity Steps Solve the Problem
Activity Steps keep the CPM graph lean ($V=40$) while delegating granular milestone verification to internal child checklists:
```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                              COMPLEXITY & PERFORMANCE COMPARISON                                │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   METRIC                     APPROACH A: 600 MICRO-ACTIVITIES    APPROACH B: 40 ACTIVITIES + STEPS│
│   ────────────────────────   ────────────────────────────────    ─────────────────────────────────│
│   CPM Graph Vertices (|V|)   600 nodes                           40 nodes                         │
│   CPM Graph Edges (|E|)      ~1,200 logic ties                   ~70 macro ties                   │
│   CPM Forward Pass Cycles    O(600 + 1200) = 1,800 operations    O(40 + 70) = 110 operations      │
│   Speedup Factor             Baseline (1.0x)                     ~16.3x faster graph evaluation   │
│   Float Calculations         600 total floats computed           40 total floats computed         │
│   Progress Tracking          Manual date updates on 600 nodes    Weighted checkmarks on 15 steps  │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```
Steps provide high-resolution Earned Value without polluting the critical path network.

* Step S4: $\text{Weight} = 20.0$, $\text{Progress} = 0\%$
* Step S5: $\text{Weight} = 10.0$, $\text{Progress} = 0\%$

Total Weight:
$$W_{\text{total}} = 15.0 + 30.0 + 25.0 + 20.0 + 10.0 = 100.0$$

Weighted Earned Progress:
$$\text{Earned}_1 = 15.0 \times 1.00 = 15.0$$
$$\text{Earned}_2 = 30.0 \times 1.00 = 30.0$$
$$\text{Earned}_3 = 25.0 \times 0.60 = 15.0$$
$$\text{Earned}_4 = 20.0 \times 0.00 = 0.0$$

Sum of Earned Progress:

$$\text{Physical \% Complete} = \frac{60.0}{100.0} \times 100 = \mathbf{60.00\%}$$

* Duration % Complete:
  $$\text{Duration \% Complete} = \frac{AD}{AD + RD} \times 100 = \frac{8}{8 + 9} \times 100 = \frac{8}{17} \times 100 = \mathbf{47.06\%}$$

### Solution 6: The Earned Value Distortion Trap

#### 1. Activity X (Using Duration % Complete)
* $AD = 15$, $RD = 5 \implies \text{Duration \%} = \frac{15}{15 + 5} \times 100 = 75.00\%$.
* Earned Value:
  $$\text{EV}_X = \text{BAC} \times \text{Duration \%} = \$100,000 \times 0.75 = \mathbf{\$75,000}$$
* Schedule Variance:
  $$\text{SV}_X = \text{EV}_X - \text{PV} = \$75,000 - \$75,000 = \mathbf{\$0.00}$$
  *(Activity X falsely reports that it is perfectly on schedule!)*

#### 2. Activity Y (Using Physical % Complete)
* Physical % Complete = $20.00\%$ (500m / 2,500m).
* Earned Value:
  $$\text{EV}_Y = \text{BAC} \times \text{Physical \%} = \$100,000 \times 0.20 = \mathbf{\$20,000}$$
* Schedule Variance:
  $$\text{SV}_Y = \text{EV}_Y - \text{PV} = \$20,000 - \$75,000 = \mathbf{-\$55,000}$$
  *(Activity Y reveals a massive \$55,000 schedule delay!)*

#### 3. Magnitude of Financial Distortion & CPI Impact
* **False Financial Overstatement:**
  $$\Delta \text{EV} = \text{EV}_X - \text{EV}_Y = \$75,000 - \$20,000 = \mathbf{\$55,000}$$
* **Cost Performance Index ($\text{CPI} = \frac{\text{EV}}{\text{AC}}$) with Actual Cost $\text{AC} = \$85,000$:**
  * Under Duration % Complete (Activity X):
    $$\text{CPI}_X = \frac{\$75,000}{\$85,000} = \mathbf{0.882}$$
    *(Falsely suggests a mild, manageable 12% cost overrun).*
  * Under Physical % Complete (Activity Y):
    $$\text{CPI}_Y = \frac{\$20,000}{\$85,000} = \mathbf{0.235}$$
    *(Reveals a catastrophic project failure: spending \$85,000 to earn only \$20,000 of value!).*

### Solution 8: Robust Step Weighting Normalizer in Go

```go
package progress

import (
	"errors"
	"fmt"
	"math"
)

type ActivityStep struct {
	ID                  string  `json:"id"`
	Name                string  `json:"name"`
	StepWeight          float64 `json:"step_weight"`
	IsCompleted         bool    `json:"is_completed"`
	StepPercentComplete float64 `json:"step_percent_complete"`
}

// CalculateActivityPhysicalPercent normalizes and computes physical progress.
func CalculateActivityPhysicalPercent(steps []ActivityStep) (float64, error) {
	// Edge Case 1: Empty slice
	if len(steps) == 0 {
		return 0.0, nil
	}

	var totalWeight float64
	var weightedProgress float64

	for _, step := range steps {
		// Edge Case 3: Negative weight validation
		if step.StepWeight < 0 {
			return 0.0, fmt.Errorf("step %q has invalid negative weight: %.4f", step.ID, step.StepWeight)
		}
		totalWeight += step.StepWeight

		// Edge Case 5: Handle IsCompleted = true with zero or low percent
		pct := step.StepPercentComplete
		if step.IsCompleted && pct < 100.0 {
			pct = 100.0
		} else if !step.IsCompleted && pct > 100.0 {
			pct = 100.0
		} else if pct < 0.0 {
			pct = 0.0
		}

		weightedProgress += (step.StepWeight * pct)
	}

	// Edge Case 4: Total weight zero validation
	if totalWeight <= 0.000001 {
		return 0.0, errors.New("total weight of all activity steps must be strictly greater than zero")
	}

	// Edge Case 2 & 6: Clean normalization and 4-decimal place rounding
	normalizedPercent := weightedProgress / totalWeight
	rounded := math.Round(normalizedPercent*10000.0) / 10000.0

	return rounded, nil
}
```

### Solution 9: Statusing State Machine & Invariant Validator in Go

```go
package progress

import (
	"errors"
	"fmt"
	"math"
	"time"
)

type StatusUpdateInput struct {
	DataDate                 time.Time
	ActualStart              *time.Time
	ActualFinish             *time.Time
	ActualDurationSeconds    *int64
	RemainingDurationSeconds *int64
	PhysicalPercentComplete  *float64
	ActualUnits              *float64
	RemainingUnits           *float64
}

// ValidateAndApplyStatus enforces P6 business invariants during statusing.
func (a *Activity) ValidateAndApplyStatus(cmd StatusUpdateInput) error {
	if cmd.DataDate.IsZero() {
		return errors.New("data date must be specified for any status update")
	}

	// 1. Completion Transition
	if cmd.ActualFinish != nil {
		if a.ActualStart == nil && cmd.ActualStart == nil {
			return errors.New("cannot complete activity without an actual start date")
		}
		actStart := a.ActualStart
		if cmd.ActualStart != nil {
			actStart = cmd.ActualStart
		}

		if cmd.ActualFinish.Before(*actStart) {
			return fmt.Errorf("actual finish (%v) cannot be before actual start (%v)", cmd.ActualFinish, actStart)
		}
		if cmd.ActualFinish.After(cmd.DataDate) {
			return fmt.Errorf("actual finish (%v) cannot be after data date (%v)", cmd.ActualFinish, cmd.DataDate)
		}

		// Apply completion state
		a.ActualStart = actStart
		a.ActualFinish = cmd.ActualFinish
		a.Status = StatusCompleted
		a.RemainingDurationSeconds = 0
		a.RemainingUnits = 0
		a.DurationPercentComplete = 100.0
		a.PhysicalPercentComplete = 100.0
		a.UnitsPercentComplete = 100.0
		if cmd.ActualDurationSeconds != nil {
			a.ActualDurationSeconds = *cmd.ActualDurationSeconds
		}
		return nil
	}

	// 2. In-Progress Transition
	if cmd.ActualStart != nil || a.Status == StatusInProgress {
		if cmd.ActualStart != nil {
			if cmd.ActualStart.After(cmd.DataDate) {
				return fmt.Errorf("actual start (%v) cannot be strictly after data date (%v)", cmd.ActualStart, cmd.DataDate)
			}
			a.ActualStart = cmd.ActualStart
			a.Status = StatusInProgress
		}

		if cmd.RemainingDurationSeconds != nil {
			if *cmd.RemainingDurationSeconds <= 0 {
				return errors.New("in-progress activity must have remaining duration strictly greater than zero")
			}
			a.RemainingDurationSeconds = *cmd.RemainingDurationSeconds
		} else if a.RemainingDurationSeconds <= 0 {
			return errors.New("remaining duration must be greater than zero for in-progress activity")
		}

		if cmd.ActualDurationSeconds != nil {
			if *cmd.ActualDurationSeconds < 0 {
				return errors.New("actual duration cannot be negative")
			}
			a.ActualDurationSeconds = *cmd.ActualDurationSeconds
		}

		// Calculate Duration %: AD / (AD + RD) * 100
		totalDur := a.ActualDurationSeconds + a.RemainingDurationSeconds
		if totalDur > 0 {
			a.DurationPercentComplete = math.Round((float64(a.ActualDurationSeconds)/float64(totalDur))*1000000) / 10000
		}

		// Bidirectional coupling check for Duration % Complete type
		if a.PercentCompleteType == DurationPercentComplete && cmd.RemainingDurationSeconds == nil {
			durPctRatio := a.DurationPercentComplete / 100.0
			a.RemainingDurationSeconds = int64(float64(a.OriginalDurationSeconds) * (1.0 - durPctRatio))
		}

		// Physical % Complete update
		if cmd.PhysicalPercentComplete != nil {
			if *cmd.PhysicalPercentComplete < 0.0 || *cmd.PhysicalPercentComplete > 100.0 {
				return errors.New("physical percent complete must be in range [0, 100]")
			}
			a.PhysicalPercentComplete = *cmd.PhysicalPercentComplete
		}
	}

	return nil
}
```

### Solution 10: PostgreSQL Schema & Auditing Triggers

```sql
-- Audit log table to capture immutable progress history
CREATE TABLE activity_progress_audit_log (
    audit_id BIGSERIAL PRIMARY KEY,
    activity_id UUID NOT NULL REFERENCES activities(activity_id) ON DELETE CASCADE,
    project_id UUID NOT NULL REFERENCES projects(project_id) ON DELETE CASCADE,
    data_date TIMESTAMPTZ NOT NULL,
    changed_at TIMESTAMPTZ NOT NULL DEFAULT CLOCK_TIMESTAMP(),
    changed_by_user_id UUID,
    
    -- Previous and New States
    old_status activity_status_enum NOT NULL,
    new_status activity_status_enum NOT NULL,
    
    old_physical_percent NUMERIC(7, 4),
    new_physical_percent NUMERIC(7, 4),
    
    old_remaining_duration_seconds BIGINT,
    new_remaining_duration_seconds BIGINT,
    
    old_actual_start TIMESTAMPTZ,
    new_actual_start TIMESTAMPTZ,
    
    old_actual_finish TIMESTAMPTZ,
    new_actual_finish TIMESTAMPTZ
);

CREATE INDEX idx_progress_audit_activity ON activity_progress_audit_log(activity_id, data_date);

-- Trigger function
CREATE OR REPLACE FUNCTION trg_audit_progress_changes()
RETURNS TRIGGER AS $$
DECLARE
    v_project_data_date TIMESTAMPTZ;
BEGIN
    -- Fetch the active Data Date from the project record
    SELECT data_date INTO v_project_data_date 
    FROM projects 
    WHERE project_id = NEW.project_id;
    
    IF v_project_data_date IS NULL THEN
        RAISE EXCEPTION 'Cannot update progress on activity % without an established project data date', NEW.activity_id;
    END IF;

    -- Detect if progress-related columns were altered
    IF (OLD.physical_percent_complete IS DISTINCT FROM NEW.physical_percent_complete) OR
       (OLD.remaining_duration_seconds IS DISTINCT FROM NEW.remaining_duration_seconds) OR
       (OLD.actual_start_date IS DISTINCT FROM NEW.actual_start_date) OR
       (OLD.actual_finish_date IS DISTINCT FROM NEW.actual_finish_date) OR
       (OLD.status IS DISTINCT FROM NEW.status) THEN
       
        INSERT INTO activity_progress_audit_log (
            activity_id,
            project_id,
            data_date,
            changed_at,
            changed_by_user_id,
            old_status,
            new_status,
            old_physical_percent,
            new_physical_percent,
            old_remaining_duration_seconds,
            new_remaining_duration_seconds,
            old_actual_start,
            new_actual_start,
            old_actual_finish,
            new_actual_finish
        ) VALUES (
            NEW.activity_id,
            NEW.project_id,
            v_project_data_date,
            CLOCK_TIMESTAMP(),
            NULL, -- Populate from session context e.g. current_setting('app.current_user_id')
            OLD.status,
            NEW.status,
            OLD.physical_percent_complete,
            NEW.physical_percent_complete,
            OLD.remaining_duration_seconds,
            NEW.remaining_duration_seconds,
            OLD.actual_start_date,
            NEW.actual_start_date,
            OLD.actual_finish_date,
            NEW.actual_finish_date
        );
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_activities_progress_audit
AFTER UPDATE ON activities
FOR EACH ROW
EXECUTE FUNCTION trg_audit_progress_changes();
```

#### 1. High-Throughput Batch Update Strategy
Instead of executing 2,500 separate `UPDATE` queries in a loop:
1. Parse the uploaded JSON or CSV into sliced Go arrays (`activityIDs`, `actualStarts`, `remainingSeconds`, `physicalPercents`).
2. Execute a single parameterized PostgreSQL query using `unnest($1::uuid[], $2::timestamptz[], $3::bigint[], $4::numeric[])`.
3. This executes in a single round-trip database query within a single transaction boundary, reducing lock acquisition time from seconds to ~15 milliseconds.

#### 2. Non-Blocking CPM Rescheduling Strategy
* Recomputing a 10,000-activity CPM network with topological sort, early date calculation, backward pass, and float re-derivation takes 200–500ms of CPU time.
* If run synchronously inside the HTTP request thread, concurrent users will experience thread pool starvation and timeout errors.
* **Architecture Solution:** 
  1. Commit the batch update transaction to PostgreSQL.
  2. Emit an event to an in-memory channel or Redis queue (`project:reschedule`).
  3. Respond immediately to the client with `202 Accepted` and a Job ID.
  4. The background worker consumes the job, loads the project graph, executes the CPM engine, updates the database with new early/late dates, and publishes a WebSocket event to the Next.js frontend (`PROJECT_SCHEDULED`).
  5. The Next.js frontend automatically refetches the updated Gantt bars via TanStack Query invalidation.
