## 1. Executive Summary & The Date Pair Mental Model

### 1.1 Why Simple Tools Fail: The 2-Date Fallacy
In lightweight productivity tools like Jira, Asana, or Trello, a task typically possesses only two date attributes:
```typescript
// JUNIOR DEVELOPER MENTAL MODEL (NAIVE / LIGHTWEIGHT PM TOOLS)
interface SimpleTask {
  startDate: Date;
  dueDate: Date;
}
```
If an electrical contractor is assembling the 220kV Main Power Transformer for the Surya 100MW Solar Project, what does `startDate` mean?
* Does it mean the date we **hoped** to start when the contract was signed in January?
* Does it mean the date the CPM engine **forecasts** we can start based on German shipping delays?
* Does it mean the latest date we **must** start before delaying the entire Rajasthan grid interconnection?
* Does it mean the actual date the rigging crew physically bolted the radiator banks to the core?

In industrial engineering, treating time as a single start/finish pair causes catastrophic confusion. You cannot simultaneously track **where you were supposed to be**, **where you can earliest be**, **where you must latest be**, and **where you actually were**.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                             THE 5 TEMPORAL DIMENSIONS OF AN ACTIVITY                             │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│   DIMENSION 1: PLANNED (TARGET) DATES                                                            │
│   "What was our original scope intention before any work began?"                                 │
│   [Target Start: 01-Jun] ──────────────────────────────► [Target Finish: 20-Jun]                 │
│                                                                                                  │
│   DIMENSION 2: BASELINE DATES                                                                    │
│   "What is our frozen, legally binding contractual commitment?" (From Baseline Snapshot)         │

│                                                                                                  │
│   DIMENSION 3: EARLY DATES (FORWARD PASS FORECAST)                                               │

│                     [Early Start: 15-Jun] ──────────────────────────────► [Early Finish: 05-Jul] │

```

> **The Architectural Standard:**  
> In Oracle Primavera P6 and enterprise CPM engines, every activity maintains **5 distinct Date Pairs (10 total date fields)**. Each pair answers a fundamentally different question in project controls governance.

## 2. Exhaustive Breakdown of the 5 Date Pairs

Let us inspect the mathematical definition, calculation rules, and database behavior of each date pair.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                  THE 5 DATE PAIRS: DEEP DIVE                                     │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  1. PLANNED DATES (target_start, target_end)                                                     │
│     * Populated during initial schedule creation before any progress is logged.                  │
│     * Once progress begins (Status = In Progress or Completed), Planned Dates FREEZE.            │
│     * Serves as the "as-planned" reference for duration estimation.                             │
│                                                                                                  │
│  2. BASELINE DATES (bl_start, bl_end)                                                            │
│     * Sourced dynamically via SQL JOIN from the attached baseline project snapshot.              │
│     * Completely independent of the live schedule's forward/backward pass.                       │
│     * Used for all variance calculations: Variance = Early Finish - Baseline Finish.             │
│                                                                                                  │
│  3. EARLY DATES (early_start, early_finish)                                                      │
│     * Calculated by the Forward Pass CPM algorithm.                                              │
│     * If Not Started: ES = max(EF_preds + lag); EF = ES + Planned Duration.                     │
│     * If In Progress: ES = Actual Start; EF = max(Data Date, Actual Start) + Remaining Duration. │
│     * If Completed:   ES = Actual Start; EF = Actual Finish.                                     │
│                                                                                                  │
│  4. LATE DATES (late_start, late_finish)                                                         │
│     * Calculated by the Backward Pass CPM algorithm.                                             │
│     * LF = min(LS_succs - lag); LS = LF - Remaining Duration.                                   │
│     * Determines Total Float: Total Float = Late Finish - Early Finish.                          │
│     * If Completed: Late Dates collapse onto Actual Dates (Total Float = 0).                     │
│                                                                                                  │
│  5. ACTUAL DATES (act_start, act_finish)                                                         │
│     * Actual Start: Entered when physical work commences on site. Freezes early start.           │
│     * Actual Finish: Entered when physical work is 100% complete. Freezes early finish.          │
│     * Must strictly occur ON or BEFORE the Data Date (History Boundary).                         │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 2.1 Planned Dates (Original Target Plan)
* **P6 Terminology:** `Planned Start` (`target_start_date`), `Planned Finish` (`target_end_date`).
* **Definition:** The dates established during initial scope definition and work package breakdown.
* **The Freezing Rule:** Before progress is applied (`Status = Not Started`), Planned Dates mirror Early Dates. However, the instant an activity begins (`Status = In Progress`), P6 freezes `Planned Start` and `Planned Finish`. Even if the activity is delayed by 6 months, Planned Dates retain the original pre-progress targets.

### 2.2 Baseline Dates (Benchmark Snapshot Reference)
* **P6 Terminology:** `BL Project Start`, `BL Project Finish`, `BL1 Start`, `BL1 Finish`.
* **Definition:** The dates stored inside the frozen clone project designated as the baseline.
* **Engine Relationship:** The scheduling calculation engine (`F9`) **never touches** baseline dates. They are purely read-only reference coordinates fetched via foreign key relationships.

### 2.3 Early Dates (Forward Pass Dynamic Forecast)
* **P6 Terminology:** `Early Start`, `Early Finish`.
* **Definition:** The earliest calendar timestamps an activity can start and finish, driven by:
  1. The completion of all predecessor dependencies.
  2. The activity's assigned calendar working intervals.
  3. The current **Data Date (Status Date)**.
* **The Living Forecast:** As predecessors experience delays, the Forward Pass pushes Early Start to the right. Early Finish is the primary operational forecast used by procurement, subcontractors, and logistics coordinators.

### 2.4 Late Dates (Backward Pass Contractual Boundaries)
* **P6 Terminology:** `Late Start`, `Late Finish`.
* **Definition:** The latest calendar timestamps an activity can start and finish without:
  1. Delaying the project's overall contractual completion date (COD).
  2. Violating a mandatory milestone constraint (e.g., "Must Finish By 15-Oct-2026").
* **Total Float Derivation:** The gap between Late and Early dates determines schedule flexibility:
  $$\text{Total Float} = \text{Late Finish} - \text{Early Finish} = \text{Late Start} - \text{Early Start}$$
  If $\text{Early Finish} > \text{Late Finish}$, $\text{Total Float} < 0$ (Negative Float / Contractual Delay).

### 2.5 Actual Dates (Historical Physical Ground Truth)
* **P6 Terminology:** `Actual Start`, `Actual Finish`.
* **Definition:** The real-world timestamps recorded by field engineers when physical work commenced and concluded.
* **The Invariant of History:** Once `Actual Start` is entered, `Early Start` is locked to equal `Actual Start`. Once `Actual Finish` is entered, both `Early Finish` and `Late Finish` collapse onto `Actual Finish`.

## 3. Phase-by-Phase Date Pair Behavior & State Machine

How do these 10 date fields change as an activity moves through its lifecycle? The table below illustrates the state machine transitions:

```text

├──────────────────────┬─────────────────────────┬─────────────────────────┬───────────────────────┤
│ Date Field           │ State 1: NOT STARTED    │ State 2: IN PROGRESS    │ State 3: COMPLETED    │
├──────────────────────┼─────────────────────────┼─────────────────────────┼───────────────────────┤
│ Planned Start        │ = Early Start           │ FROZEN (Pre-progress)   │ FROZEN (Pre-progress) │
│ Planned Finish       │ = Early Finish          │ FROZEN (Pre-progress)   │ FROZEN (Pre-progress) │
│ Baseline Start       │ Frozen from B1 Snapshot │ Frozen from B1 Snapshot │ Frozen from B1        │
│ Baseline Finish      │ Frozen from B1 Snapshot │ Frozen from B1 Snapshot │ Frozen from B1        │
│ Early Start          │ Calculated Forward Pass │ = Actual Start (Locked) │ = Actual Start (Locked│
│ Early Finish         │ = ES + Planned Duration │ = Data Date + Rem Dur   │ = Actual Finish       │
│ Late Start           │ Calculated Backward Pass│ Calculated Backward Pass│ = Actual Start        │
```

### 3.1 The Temporal Horizon: The Data Date Boundary
The **Data Date ($\tau_{DD}$)** (also called the **Status Date**) divides universal project time into two mutually exclusive regimes:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                 THE DATA DATE TEMPORAL BOUNDARY                                  │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│                 PAST (Historical Reality)       │     FUTURE (CPM Forward/Backward Forecast)     │
│                 t < Data Date (τ_DD)            │     t ≥ Data Date (τ_DD)                       │
│  ───────────────────────────────────────────────┼──────────────────────────────────────────────► │
│                                                 │                                                │
│  * Immutable historical facts.                  │  * Dynamic mathematical forecasts.             │
│  * Only ACTUAL dates permitted.                 │  * EARLY and LATE dates calculated by engine.  │
│  * No remaining work allowed in the past!       │  * Remaining Durations consume calendar time.  │
│                                                 │                                                │
│  INVARIANT RULE:                                                                                 │
│  For any incomplete activity (Remaining Duration > 0):                                           │
│  Early Finish ≥ Data Date                                                                        │
│  (You cannot finish uncompleted work in yesterday's time!)                                       │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 Pixel Coordinate Calculation for Next.js Canvas/SVG
When developing a custom Gantt chart component in Next.js, each bar layer is calculated using a linear or calendar-aware projection function:
$$X(t) = \frac{t - t_{\text{view\_start}}}{t_{\text{view\_end}} - t_{\text{view\_start}}} \times W_{\text{viewport}}$$

For an In-Progress activity:
* **Actual Segment:**
  - $X_{\text{start}} = X(\text{Actual Start})$
  - $\text{Width}_{\text{actual}} = X(\text{Data Date}) - X(\text{Actual Start})$
  - Fill Color: `#2563EB` (Tailwind `blue-600`)
* **Remaining Segment:**
  - $X_{\text{start}} = X(\text{Data Date})$
  - $\text{Width}_{\text{remaining}} = X(\text{Early Finish}) - X(\text{Data Date})$
  - Fill Color: $\text{Total Float} \le 0 \ ? \ \text{`#DC2626` (Red)} : \text{`#16A34A` (Green)}$
* **Baseline Bar:**
  - $X_{\text{start}} = X(\text{Baseline Start})$
  - $\text{Width}_{\text{baseline}} = X(\text{Baseline Finish}) - X(\text{Baseline Start})$
  - Fill Color: `#F59E0B` (Tailwind `amber-500` / Gold)

## 5. PostgreSQL Database Schema & Query Optimization

To achieve microsecond query latencies when rendering thousands of activities across multiple date pairs, the database schema must index bounding timestamps efficiently.

```sql
-- Migration: 007_date_pairs_and_views.sql

-- 1. Activities table storing all operational date pairs
CREATE TABLE activities (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    code VARCHAR(64) NOT NULL,
    name VARCHAR(255) NOT NULL,
    original_task_uuid UUID NOT NULL,
    calendar_id UUID NOT NULL,
    status VARCHAR(32) NOT NULL DEFAULT 'NOT_STARTED' 
        CHECK (status IN ('NOT_STARTED', 'IN_PROGRESS', 'COMPLETED')),
    
    -- Pair 1: Planned Dates (Target scope)
    planned_start TIMESTAMPTZ NOT NULL,
    planned_finish TIMESTAMPTZ NOT NULL,
    planned_duration_min INT NOT NULL,

    -- Pair 3: Early Dates (Forward pass forecast)
    early_start TIMESTAMPTZ NOT NULL,
    early_finish TIMESTAMPTZ NOT NULL,
    remaining_duration_min INT NOT NULL,

    -- Pair 4: Late Dates (Backward pass boundaries)
    late_start TIMESTAMPTZ,
    late_finish TIMESTAMPTZ,
    total_float_min INT,

    -- Pair 5: Actual Dates (Ground truth)
    actual_start TIMESTAMPTZ,
    actual_finish TIMESTAMPTZ,

    CONSTRAINT uq_proj_activity UNIQUE (project_id, code)
);

-- Bounding Box Viewport Index for ultra-fast Gantt viewport queries:
-- Allows fetching only activities visible within [viewport_start, viewport_end]
CREATE INDEX idx_activities_gantt_viewport ON activities (
    project_id,
    early_start,
    early_finish
);

-- 2. High-Performance SQL View: Merging Live 5 Date Pairs with Active Baseline
CREATE OR REPLACE VIEW v_activity_date_pairs AS
SELECT 
    live.id AS activity_id,
    live.project_id AS live_project_id,
    live.code AS activity_code,
    live.name AS activity_name,
    live.status,
    
    -- 1. Planned
    live.planned_start,
    live.planned_finish,
    
    -- 2. Baseline (Joined from assigned baseline project clone)
    bl.early_start AS baseline_start,
    bl.early_finish AS baseline_finish,
    
    -- 3. Early
    live.early_start,
    live.early_finish,
    
    -- 4. Late
    live.late_start,
    live.late_finish,
    live.total_float_min,
    
    -- 5. Actual
    live.actual_start,
    live.actual_finish,
    
    -- Fast SQL Variances (in hours)
    ROUND(EXTRACT(EPOCH FROM (live.early_start - bl.early_start)) / 3600.0, 2) AS start_variance_hours,
    ROUND(EXTRACT(EPOCH FROM (bl.early_finish - live.early_finish)) / 3600.0, 2) AS finish_variance_hours

FROM activities live
JOIN projects p ON live.project_id = p.id
-- Find active baseline clone attached to this project
LEFT JOIN projects bl_proj ON bl_proj.orig_proj_id = p.id AND bl_proj.baseline_type = 'PROJECT'
LEFT JOIN activities bl ON bl.project_id = bl_proj.id AND bl.original_task_uuid = live.original_task_uuid;
```

## 6. Golang Scheduling Engine: Date Pair State Machine & Calculation

Here is how the Golang CPM scheduling engine maintains and transitions the 5 date pairs during status updates.

```go
// Package engine/schedule/date_pairs.go
package schedule

import (
	"errors"
	"time"

	"github.com/google/uuid"
)

type ActivityStatus string

const (
	StatusNotStarted ActivityStatus = "NOT_STARTED"
	StatusInProgress ActivityStatus = "IN_PROGRESS"
	StatusCompleted  ActivityStatus = "COMPLETED"
)

// DatePairs holds the 10 canonical date fields for an activity
type DatePairs struct {
	// Pair 1: Planned
	PlannedStart  time.Time
	PlannedFinish time.Time

	// Pair 2: Baseline (Read-only reference)
	BaselineStart  *time.Time
	BaselineFinish *time.Time

	// Pair 3: Early
	EarlyStart  time.Time
	EarlyFinish time.Time

	// Pair 4: Late
	LateStart  *time.Time
	LateFinish *time.Time

	// Pair 5: Actual
	ActualStart  *time.Time
	ActualFinish *time.Time
}

type Activity struct {
	ID                   uuid.UUID
	Code                 string
	Status               ActivityStatus
	PlannedDurationMin   int
	RemainingDurationMin int
	TotalFloatMinutes    int
	Dates                DatePairs
}

// UpdateActivityProgress applies real-world progress to an activity and updates date pairs
func (a *Activity) UpdateActivityProgress(dataDate time.Time, actualStart *time.Time, actualFinish *time.Time, remainingMin int) error {
	// Rule 1: Validate Actual Start logic
	if actualStart != nil {
		if actualStart.After(dataDate) {
			return errors.New("actual start cannot be in the future (after Data Date)")
		}
		a.Dates.ActualStart = actualStart
		a.Status = StatusInProgress
		// Invariant: Once started, Early Start locks onto Actual Start
		a.Dates.EarlyStart = *actualStart
	}

	// Rule 2: Validate Actual Finish logic
	if actualFinish != nil {
		if a.Dates.ActualStart == nil {
			return errors.New("cannot have actual finish without actual start")
		}
		if actualFinish.Before(*a.Dates.ActualStart) {
			return errors.New("actual finish cannot precede actual start")
		}
		if actualFinish.After(dataDate) {
			return errors.New("actual finish cannot be in the future (after Data Date)")
		}

		a.Dates.ActualFinish = actualFinish
		a.Status = StatusCompleted
		a.RemainingDurationMin = 0
		// Invariant: Once completed, Early and Late collapse onto Actual Finish
		a.Dates.EarlyFinish = *actualFinish
		a.Dates.LateStart = a.Dates.ActualStart
		a.Dates.LateFinish = actualFinish
		a.TotalFloatMinutes = 0
		return nil
	}

	// Rule 3: In-Progress handling
	if a.Status == StatusInProgress {
		a.RemainingDurationMin = remainingMin
		// Note: The forward pass will calculate EarlyFinish = walkCalendar(dataDate, remainingMin)
	}

	return nil
}
```

## 7. Next.js Multi-Layer Gantt Bar Rendering Component

```tsx
// components/gantt/MultiLayerGanttBar.tsx
'use client';

import React from 'react';

interface MultiLayerGanttBarProps {
  // Viewport projection function: maps ISO timestamp string to pixel X coordinate
  scaleX: (dateStr: string) => number;
  rowY: number; // Top Y coordinate of the current activity row
  rowHeight: number; // Row height (e.g., 40px)
  dataDateStr: string;

  // Dates
  actualStart?: string;
  actualFinish?: string;
  earlyStart: string;
  earlyFinish: string;
  baselineStart?: string;
  baselineFinish?: string;
  
  totalFloatHours: number;
}

export const MultiLayerGanttBar: React.FC<MultiLayerGanttBarProps> = ({
  scaleX,
  rowY,
  rowHeight,
  dataDateStr,
  actualStart,
  actualFinish,
  earlyStart,
  earlyFinish,
  baselineStart,
  baselineFinish,
  totalFloatHours,
}) => {
  const currentBarHeight = 14;
  const baselineBarHeight = 6;
  const currentBarY = rowY + 6;
  const baselineBarY = rowY + 23;

  const isCritical = totalFloatHours <= 0;
  const remainingColor = isCritical ? '#EF4444' : '#10B981'; // Red if critical, Green if float > 0

  const dataDateX = scaleX(dataDateStr);

  return (
    <g className="gantt-activity-bar-group">
      {/* 1. BASELINE BAR (Bottom Lane, Amber/Gold) */}
      {baselineStart && baselineFinish && (
        <rect
          x={scaleX(baselineStart)}
          y={baselineBarY}
          width={Math.max(2, scaleX(baselineFinish) - scaleX(baselineStart))}
          height={baselineBarHeight}
          rx={2}
          fill="#F59E0B"
          opacity={0.8}
        >
          <title>{`Baseline: ${new Date(baselineStart).toLocaleDateString()} -> ${new Date(baselineFinish).toLocaleDateString()}`}</title>
        </rect>
      )}

      {/* 2. CURRENT BAR: ACTUAL PORTION (Blue) */}
      {actualStart && (
        <rect
          x={scaleX(actualStart)}
          y={currentBarY}
          width={Math.max(2, (actualFinish ? scaleX(actualFinish) : dataDateX) - scaleX(actualStart))}
          height={currentBarHeight}
          rx={3}
          fill="#3B82F6"
        >
          <title>{`Actual Progress: Started ${new Date(actualStart).toLocaleDateString()}`}</title>
        </rect>
      )}

      {/* 3. CURRENT BAR: REMAINING FORECAST PORTION (Green or Red) */}
      {!actualFinish && (
        <rect
          x={actualStart ? dataDateX : scaleX(earlyStart)}
          y={currentBarY}
          width={Math.max(2, scaleX(earlyFinish) - (actualStart ? dataDateX : scaleX(earlyStart)))}
          height={currentBarHeight}
          rx={3}
          fill={remainingColor}
        >
          <title>{`Forecast: Early Finish ${new Date(earlyFinish).toLocaleDateString()} (Float: ${totalFloatHours}h)`}</title>
        </rect>
      )}
    </g>
  );
};
```
