### Solution 2: The "Planned Date Freeze" Invariant

#### 1. Why Dynamic Planned Dates Destroy Scheduling Integrity
If `Planned Start = Early Start` and `Planned Finish = Early Finish` at all times:
* Every time an activity slips and its forward pass early dates push into the future, the planned dates would push with it.
* The original scope definition—the target date established when the work package was budgeted and approved—is permanently overwritten.
* You lose the ability to answer: *"What was our original schedule intent before site disturbances occurred?"*

#### 2. Values During In-Progress Delay
Suppose an activity originally had Planned Start = `01-May` and Planned Finish = `15-May` (Duration: 14 days).
It actually starts on `15-May` (2 weeks late) and field conditions double the required duration to 28 days (Early Finish = `12-Jun`).
While **In Progress**:
* `Planned Start` = **`01-May`** (Strictly Frozen!)
* `Planned Finish` = **`15-May`** (Strictly Frozen!)
* `Early Start` = **`15-May`** (= Actual Start)
* `Early Finish` = **`12-Jun`** (Data Date + Remaining Duration)

#### 3. Planned Dates vs Baseline Dates
* **Planned Dates (`target_start`, `target_end`):** Internal to the current active project table. They represent the un-progressed target of the current live schedule.
* **Baseline Dates (`bl_start`, `bl_end`):** Stored inside an external, write-protected snapshot project clone. A project can have multiple baselines (B1, B2, B3), while an activity has exactly one pair of Planned Dates.

### Solution 3: The Data Date Boundary Invariant

#### 1. The Mathematical Invariant
Let universal project time be discretized onto a timeline, and let $\tau_{DD}$ be the Data Date (Status Date).
For any activity $A$ with non-zero Remaining Duration ($D_{\text{rem}}(A) > 0$):
$$\text{Early Finish}(A) \ge \tau_{DD}$$
Furthermore, if work has not started ($\text{Status} = \text{NOT\_STARTED}$):
$$\text{Early Start}(A) \ge \tau_{DD}$$
**Proof:** The Data Date represents the boundary of the present. Work that has not yet occurred cannot be performed in the past. Therefore, all uncompleted duration must be consumed at or after $\tau_{DD}$.

#### 2. Why Future Actual Dates Must Be Rejected
If $\tau_{DD} = \text{2026-06-15 08:00}$ and an engineer inputs $\text{Actual Start} = \text{2026-06-22 08:00}$:
* The entered date claims that physical work began 7 days in the future relative to the status horizon.
* This is a logical and physical impossibility. If the project status is being reported as of June 15, the engineer cannot have verified physical work that takes place on June 22.
* A robust scheduling engine must enforce:
  $$\text{Actual Start} \le \tau_{DD} \quad \text{and} \quad \text{Actual Finish} \le \tau_{DD}$$

#### 3. In-Progress Remaining Work Origin
If an activity started on `2026-06-01` and is 50% complete as of Data Date `2026-06-15 08:00`:
* The completed portion (50%) sits in the past: `[2026-06-01 to 2026-06-15]`.
* The remaining duration begins execution **exactly at $\tau_{DD}$ (`2026-06-15 08:00`)**, walking forward through the activity calendar's working intervals.

### Solution 4: Float Collapse upon Completion

#### 1. Date Behavior upon Completion
When an activity transitions to `COMPLETED` with an `Actual Finish`:
* `Early Start` locks to `Actual Start`.
* `Early Finish` locks to `Actual Finish`.
* `Late Start` collapses to `Actual Start`.
* `Late Finish` collapses to `Actual Finish`.
* **Total Float:**
  $$TF = \text{Late Finish} - \text{Early Finish} = \text{Actual Finish} - \text{Actual Finish} = 0$$

#### 2. Why Total Float is Meaningless for Completed Tasks
Float represents **future schedule flexibility**—the number of days an incomplete activity can slip without delaying downstream milestones or project completion. Once an activity is completed, its timeline is an unchangeable historical fact. It can no longer slip, nor can it provide flexibility to future activities.

#### 3. Historical Slip vs Current Float
* If an activity completed 10 days after its baseline finish, it suffered **10 days of historical schedule slip** ($FV = -10\text{ days}$).
* However, it has **0 days of Total Float today**.
* Conflating historical slip with current float is a common error. Float describes the future capacity for delay; variance measures past divergence from a benchmark.

### Solution 5: Tracing Activity `ACT-TRN-101` Across Lifecycle States

Let us trace the 20 working day activity on a 5-day week (Mon–Fri, 8h/day).
* **Update 0 (01-Jan-2026 NTP, Data Date = 01-Jan-2026):**
  - Planned: `01-May-2026` to `28-May-2026` (20 working days).
  - Baseline B1: `01-May-2026` to `28-May-2026`.
  - Early: `01-May-2026` to `28-May-2026`.
  - Late: Late Finish = `15-Jun-2026`. Subtracting 20 working days backward lands on Late Start = `19-May-2026`.
  - Total Float $= \text{Late Finish} - \text{Early Finish} = \text{15-Jun} - \text{28-May} = 12\text{ working days}$ (or 18 calendar days).
  - Actuals: `NULL`.

* **Update 1 (25-May-2026 Data Date, Status = IN_PROGRESS):**
  - Actual Start = `18-May-2026`.
  - 5 days completed (Mon 18-May to Fri 22-May).
  - Remaining duration = 15 working days.
  - Forward pass walks 15 working days from Data Date Monday `25-May-2026`:
    - Week 1 (25-May to 29-May): 5 days (10 remaining).
    - Week 2 (01-Jun to 05-Jun): 5 days (5 remaining).
    - Week 3 (08-Jun to 12-Jun): 5 days (0 remaining).
    - Early Finish = `12-Jun-2026`.
  - Early Start locks to `Actual Start` = `18-May-2026`.
  - Late Finish remains `15-Jun-2026`.
  - Total Float $= \text{Late Finish (15-Jun)} - \text{Early Finish (12-Jun)} = 1\text{ working day}$.
  - Planned and Baseline dates remain frozen.

* **Update 2 (15-Jun-2026 Data Date, Status = COMPLETED):**
  - Actual Start = `18-May-2026`.
  - Actual Finish = `12-Jun-2026`.
  - Early and Late dates collapse onto Actuals.
  - Total Float = `0`.

### Solution 6: Out-of-Sequence Progress & Date Pair Distortion

#### 1. Definition of Out-of-Sequence Progress
Out-of-Sequence progress occurs when work begins on a successor activity before one or more of its designated predecessor logic constraints have been fully satisfied. Here, `ACT-MOD-01` started on `10-Jul` despite its predecessor `ACT-STR-01` being incomplete until `25-Jul`.

#### 2. Retained Logic vs Progress Override in P6
* **Retained Logic:** P6 respects the network logic for all remaining work. Even though `ACT-MOD-01` has started, its **remaining duration cannot proceed** until the predecessor `ACT-STR-01` finishes on `25-Jul`. The remaining duration is split and pushed to start on `25-Jul`.
* **Progress Override:** P6 assumes the network logic was incorrect or bypassed. It ignores the predecessor relationship and schedules the remaining duration immediately from the Data Date.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                             RETAINED LOGIC VS PROGRESS OVERRIDE                                  │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│  Predecessor: ACT-STR-01 (Piling)       [Started 01-Jul ───────────────► Finishes 25-Jul]        │
│                                                                                                  │
│  RETAINED LOGIC:                                                                                 │
│  Successor:   ACT-MOD-01 (Modules)      [Act: 10-Jul..] ─── (Frozen) ───► [Rem: 25-Jul..05-Aug]  │
│  * Remaining work waits for Piling to complete!                                                  │
│                                                                                                  │
│  PROGRESS OVERRIDE:                                                                              │
│  Successor:   ACT-MOD-01 (Modules)      [Act: 10-Jul..] ───► [Rem: 15-Jul..28-Jul]               │
│  * Logic tie is completely ignored for remaining duration!                                      │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 3. Contractual Standards
**Retained Logic** is mandatory under virtually all major EPC contracts (FIDIC, NEC4, US DoD). Progress Override creates an artificial, un-constructible illusion that work can finish before its physical prerequisites are complete, distorting the true critical path.

### Solution 8: Viewport Bounding Box Query & SQL Optimization

#### 1. Optimized PostgreSQL Bounding Box Query
```sql
SELECT 
    id, code, name, status, early_start, early_finish, actual_start, total_float_min
FROM activities
WHERE project_id = $1
  AND early_start <= '2026-08-31 23:59:59Z'
  AND early_finish >= '2026-06-01 00:00:00Z';
```

#### 2. Why Checking Only `early_start` Fails
If you write `WHERE early_start BETWEEN '2026-06-01' AND '2026-08-31'`:
* Any long-duration activity that started in May 2026 and continues through July 2026 will be **completely excluded**, because its `early_start` is before June 1!
* A Gantt bar is a 1-dimensional bounding box. An activity intersects interval $[A, B]$ if and only if:
  $$\text{Start} \le B \quad \text{AND} \quad \text{Finish} \ge A$$

#### 3. Composite Index Design
```sql
CREATE INDEX idx_activities_gantt_viewport ON activities (
    project_id,
    early_start,
    early_finish
);
```
This multi-column index allows PostgreSQL to perform an `Index Scan` utilizing range conditions on both dimensions, filtering 80,000 activities down to the 200 visible rows in less than 4 milliseconds.

#### 2. Calendar Forward-Walk for In-Progress Task
```go
// CalculateInProgressEarlyFinish walks the activity calendar from Data Date
func CalculateInProgressEarlyFinish(dataDate time.Time, remainingMin int, cal *schedule.Calendar) time.Time {
	current := dataDate
	minutesConsumed := 0

	for minutesConsumed < remainingMin {
		// If current minute falls within a calendar work interval, consume it
		if cal.IsWorkingMinute(current) {
			minutesConsumed++
		}
		current = current.Add(time.Minute)
	}

	return current
}
```

#### 3. Why Completed Late Dates Must Not Be Overwritten
If an activity is completed, its timeline is historically frozen. The backward pass determines the latest allowable schedule for *future incomplete* tasks. Overwriting a completed task's late dates would erase its historical as-built timeline and distort retrospective delay claims.

### Solution 10: Milestones and Date Pairs

#### 1. Relationship Between Early Start and Early Finish for Milestones
* **Duration:** $\text{Duration} = 0$.
* **Start Milestone:** Marks the commencement of a phase.
  $$\text{Early Start} = \text{Early Finish} = \text{Date of Occurrence}$$
* **Finish Milestone:** Marks the completion of a phase.
  $$\text{Early Start} = \text{Early Finish} = \text{Date of Occurrence}$$
In Primavera P6, both Start and Finish milestones have identical Start and Finish timestamps.

#### 2. Actuals for a Start Milestone
If a Start Milestone occurs on `2026-04-15 08:00`:
* $\text{Actual Start} = \text{2026-04-15 08:00}$.
* $\text{Actual Finish} = \text{2026-04-15 08:00}$ (collapses automatically upon completion).
