## 🏛️ Section A: Conceptual & Topological Foundations

### Solution 1: Mathematical Hazards of Summary-to-Summary Precedence

#### 1. Mathematical Proof of Circular Mutual Dependency
Let a schedule be defined by:
* A set of summary nodes $V_{wbs}$ organized as a rooted scope tree $T = (V_{wbs}, E_{tree})$.
* A set of leaf execution activities $V_{act}$.
* A function $\text{Leaf}(W) \subset V_{act}$ returning all execution activities descending from summary node $W \in V_{wbs}$.

In standard CPM forward pass logic, the Early Dates of a summary node $W$ are defined as:
$$ES(W) = \min_{a \in \text{Leaf}(W)} ES(a), \quad EF(W) = \max_{a \in \text{Leaf}(W)} EF(a)$$

Now suppose the system permits a Finish-to-Start precedence edge between two summary nodes:
$$e = (W_1, W_2) \in E_{logic} \implies ES(W_2) \ge EF(W_1)$$

If $ES(W_2)$ is constrained by $EF(W_1)$, then every child activity $b \in \text{Leaf}(W_2)$ inherits this constraint:
$$ES(b) \ge ES(W_2) \ge EF(W_1) = \max_{a \in \text{Leaf}(W_1)} EF(a)$$

Now, evaluate what happens if a child activity $a_k \in \text{Leaf}(W_1)$ has its Early Dates calculated. If the network contains any indirect relationship or shared resource constraint from a task in $W_2$ to $a_k$, we get:
$$ES(a_k) = f(EF(b_j)), \quad \text{where } b_j \in \text{Leaf}(W_2)$$

Substituting the earlier inequality yields:
$$ES(b_j) \ge \max_{a \in \text{Leaf}(W_1)} EF(a) \ge EF(a_k) > ES(a_k) \ge EF(b_j) > ES(b_j)$$
$$\implies ES(b_j) > ES(b_j) \quad \text{💥 Contradiction (Strict Algebraic Paradox)}$$

Thus, treating summary nodes as active CPM network nodes creates a circular mutual dependency: the summary node's dates are determined by its children, while its children's dates are determined by the summary node. CPM collapses from an $O(V + E)$ single-pass topological sort into an unsolvable algebraic fixed-point problem.

### Solution 2: The Semantics of P6 "WBS Summary" Activity vs True WBS Nodes

#### 1. Operational & Mathematical Distinction

| Dimension | WBS Node (`PROJWBS` Table) | Activity of Type WBS Summary (`TASK` Table) |
| :--- | :--- | :--- |
| **Identity & Storage** | Primary entity in `PROJWBS`. Parent in scope hierarchy. | Row in `TASK` table with `task_type = 'TT_WBSummary'`. |
| **Hierarchy Role** | Structural scope container / folder. | Executable network node living *inside* a WBS folder. |
| **Duration Semantics** | Has no duration field; calendar span is dynamically derived. | Has duration fields (`target_durn_hr_cnt`), computed like a hammock. |
| **Logic Edges** | **Strictly prohibited** from having predecessors or successors. | Can have predecessors/successors (used for reporting/hammock triggers). |
| **Resource Loading** | Cannot be directly resource loaded. | **Can have direct resource assignments** (e.g., QA inspector cost). |
| **Driving Nature** | Never participates in CPM forward/backward passes. | Calculated in Pass 2; **cannot drive** normal task critical paths. |

#### 2. CPM Engine Two-Pass Calculation Mechanics
To prevent recursion and critical path corruption, the scheduling engine processes `WBS Summary` activities in two separate stages:

1. **Pass 1: Core Network CPM Pass (Topological Traversal)**
   * All normal activities (`Task Dependent`, `Resource Dependent`, `Milestones`) are evaluated.
   * Forward pass computes $ES$ and $EF$. Backward pass computes $LS$ and $LF$.
   * `WBS Summary` activities are **completely omitted** from this pass. Any outgoing relationship from a WBS Summary activity is treated as non-driving.
2. **Pass 2: WBS Summary Evaluation (Hammock Resolution)**
   * For each activity $A$ where $A.\text{type} = \text{WBS\_SUMMARY}$:
     $$ES_A = \min \{ ES_i \mid i \in \text{Activities}(\text{WBS}_A), i.\text{type} \neq \text{WBS\_SUMMARY} \}$$
     $$EF_A = \max \{ EF_i \mid i \in \text{Activities}(\text{WBS}_A), i.\text{type} \neq \text{WBS\_SUMMARY} \}$$
     $$\text{PlannedDuration}_A = \text{CalendarWorkTime}(A.\text{calendar\_id}, ES_A, EF_A)$$
   * Total Float of $A$ is derived from its assigned WBS boundary:
     $$TF_A = \min \{ TF_i \mid i \in \text{Activities}(\text{WBS}_A), i.\text{type} \neq \text{WBS\_SUMMARY} \}$$

Because Pass 2 happens strictly *after* Pass 1 is finalized, the WBS Summary activity can never feed dates back into the core CPM network.

#### 3. Real-World 100MW Solar IPP Operational Example
On the Rajasthan site, the EPC contractor employs a Senior Quality Assurance & HSE Inspector who oversees all activities in `WBS 03.1.2 Tracker Piling Works` (clearing, ramming, pullout testing).
* If modeled as an individual activity with a fixed duration (e.g., 30 days), whenever piling is delayed by 15 days, the QA activity would not stretch automatically, underestimating supervision labor costs.

* **The Solution:** The planner creates `ACT-1000: Piling QA/HSE Supervision` of type `WBS Summary` inside `WBS 03.1.2`. Assigned Resource: `QA Lead ($45/hr)`.

### Solution 3: Status and Date Rollup Mechanics: Multi-Calendar Anomalies

#### 1. Derived Early Start and Early Finish for `WBS 03.1`
* **Activity A (`ACT-101`)**:
  * Early Start: Monday, 2026-11-02 08:00
  * Early Finish: Saturday, 2026-11-07 18:00
* **Activity B (`ACT-102`)**:
  * Early Start: Thursday, 2026-11-05 08:00
  * Early Finish: Wednesday, 2026-11-11 17:00

The parent summary node dates are derived from the absolute timestamps:
$$\text{Summary Early Start} = \min(\text{2026-11-02 08:00}, \text{2026-11-05 08:00}) = \mathbf{\text{2026-11-02 08:00}}$$
$$\text{Summary Early Finish} = \max(\text{2026-11-07 18:00}, \text{2026-11-11 17:00}) = \mathbf{\text{2026-11-11 17:00}}$$

#### 2. Why "Working Days Duration" is Mathematically Ill-Defined
If an engineer attempts to express `WBS 03.1`'s duration as a single "working days" number:
* Under Activity A's calendar (6-day site calendar), Saturday is a working day, but Sunday is not. Working days between Nov 2 and Nov 11 = 9 working days.
* Under Activity B's calendar (5-day lab calendar), both Saturday and Sunday are non-working days. Working days between Nov 2 and Nov 11 = 8 working days.
* Summing working durations ($6\text{ days} + 5\text{ days} = 11\text{ days}$) is meaningless because the activities executed concurrently from Thursday to Saturday.

Because a WBS container does not own an independent working calendar, there is no unambiguous base calendar against which working days can be evaluated.

#### 3. Enterprise Reporting Standard
Professional PPM systems handle summary duration using two standard metrics:
1. **Calendar Days Span (Elapsed Duration):**
   $$\text{Calendar Span} = \text{DateDiffInDays}(\text{Summary ES}, \text{Summary EF}) + 1 = 10 \text{ Elapsed Calendar Days}$$
   This metric is calendar-independent and reflects real-world project duration.
2. **Project Default Calendar Working Span:**
   The elapsed span is evaluated against the global project default calendar (e.g., standard 5-day or 6-day project calendar) to provide an executive estimate of working days.

### Solution 4: Earned Value Calculation & Percent Complete Weighting at the WBS Boundary

#### 1. Activity-Level and Summary-Level EV Calculations
Formulas:
* $\text{Earned Value } (EV) = \text{Planned Cost } (PV) \times \left(\frac{\text{Physical } \% \text{ Complete}}{100}\right)$
* $\text{Actual Cost } (AC) = \text{Reported actual expenditure}$

| Activity | Planned Value ($PV$) | Physical % Complete | Earned Value ($EV$) | Actual Cost ($AC$) |
| :--- | :--- | :--- | :--- | :--- |
| **ACT-1010 (Block 1 Piling)** | \$200,000 | 100% | \$200,000 | \$220,000 |
| **ACT-1020 (Block 2 Piling)** | \$200,000 | 40% | \$80,000 | \$90,000 |
| **ACT-1030 (Block 3 Piling)** | \$100,000 | 0% | \$0 | \$0 |
| **WBS 03.1.2 TOTAL** | **\$500,000** | — | **\$280,000** | **\$310,000** |

#### 2. Earned Value Physical % Complete for `WBS 03.1.2`
$$\text{WBS Physical } \% = \frac{\sum EV}{\sum PV} \times 100 = \frac{\$280,000}{\$500,000} \times 100 = \mathbf{56.0\%}$$

Cost Variance ($CV$) and Schedule Performance Index ($SPI$) for executive reporting:
$$CV = EV - AC = \$280,000 - \$310,000 = -\$30,000 \quad (\text{Cost Overrun})$$

#### 3. Contrast with Naive Duration % Complete
Suppose the planned durations were:
* `ACT-1010`: 10 days (100% complete $\to$ 10 days progress)
* `ACT-1020`: 10 days (40% complete $\to$ 4 days progress)
* `ACT-1030`: 30 days (0% complete $\to$ 0 days progress)
Total planned duration sum = 50 days. Completed duration sum = 14 days.
$$\text{Duration } \% = \frac{14}{50} \times 100 = \mathbf{28.0\%}$$

**Why Duration % Complete Fails in Industrial Construction:**
`ACT-1030` might be a low-effort curing or monitoring activity that takes 30 days but requires almost zero capital expenditure (\$100k vs \$400k for heavy mechanical ramming). Weighting progress by duration gives disproportionate influence to long, inexpensive tasks, misinforming lenders and clients that the project is only 28% complete when 56% of physical work value has already been delivered.

## 💾 Section B: Relational Database Modeling & Schema Tradeoffs

### Solution 5: Two-Table vs Single-Table Polymorphism Audit

#### 1. Architectural Audit of the Single-Table Model (`tasks` with `is_summary`)

##### A. Relational Constraint Integrity Failure
When dependencies are modeled as:
```sql
CREATE TABLE task_dependencies (
    pred_id UUID REFERENCES tasks(id),
    succ_id UUID REFERENCES tasks(id)
);
```
Foreign key constraints validate only that `pred_id` exists in `tasks`. They cannot inspect whether `tasks.is_summary` is `TRUE`. 
To prevent links to summary rows, the database requires an expensive procedural trigger on every insert/update:
```sql
CREATE OR REPLACE FUNCTION trg_check_not_summary() RETURNS TRIGGER AS $$
BEGIN
    IF EXISTS (SELECT 1 FROM tasks WHERE id IN (NEW.pred_id, NEW.succ_id) AND is_summary = TRUE) THEN
        RAISE EXCEPTION 'Precedence relationships cannot target summary nodes';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```
In a 50,000-activity project, bulk-inserting 80,000 dependencies fires this trigger 80,000 times, performing 160,000 index lookups and causing import bottlenecks.

##### B. Storage and Memory Footprint in PostgreSQL
* **PostgreSQL Tuple Layout:** Every row in a PostgreSQL heap page includes a 23-byte `HeapTupleHeader`, an optional NULL bitmap, and column data.
* If a table has 70 columns and 50 of them are NULL for summary rows, PostgreSQL must allocate an 8-byte NULL bitmask per row.
* More critically, query cache efficiency is severely impaired: when PostgreSQL loads heap pages for execution tasks during CPM passes, memory buffers are polluted with empty columns from interspersed summary nodes.

##### C. Query Planner Degradation
When the Go CPM engine queries executable nodes, it must run:
```sql
SELECT * FROM tasks WHERE project_id = $1 AND is_summary = FALSE;
```
Without a partial index (`CREATE INDEX ... WHERE is_summary = FALSE`), PostgreSQL must perform index scans filtering out summary rows. As the project evolves, planner statistics (histogram bounds and selectivity estimates) can diverge, causing sudden plan flips from index scans to full table scans.

---

#### 2. The Two-Table Architecture Advantage
In the Two-Table design (`wbs_nodes` and `activities`):
1. **Precedence Integrity by Design:**
   `activity_relationships.predecessor_id REFERENCES activities(activity_id)` guarantees at the relational engine level that a relationship can never reference a `wbs_node`. Zero triggers required.
2. **Dense Memory Packing:**
   `activities` contains only execution attributes. `wbs_nodes` contains only hierarchy attributes. Buffer hit ratios in PostgreSQL shared buffers remain near 100%.
3. **Optimized Engine Queries:**
   Querying the execution graph requires a simple scan of `activities` and `activity_relationships`, without conditional filtering on node types.

### Solution 6: Relational Cascade Rules and The "Accidental Demotion" Bug

#### 1. Why `ON DELETE CASCADE` is Disastrous on `activities.wbs_id`
If `activities.wbs_id` is configured with `ON DELETE CASCADE`:
* A planning engineer intends to delete an empty duplicate WBS folder `WBS 03.1.9 Temporary Sheds`.
* Due to an accidental UI click or incorrect API call, the engineer deletes `WBS 03.1 Civil Balance of Plant`.
* PostgreSQL immediately executes a recursive cascade, permanently deleting 8,000 execution activities, their historical actual costs, subcontractor progress logs, and CPM relationship links!

**The Mandatory Rule:**
`activities.wbs_id` must be configured with `ON DELETE RESTRICT` (or `ON DELETE NO ACTION`). If an engineer attempts to delete a WBS node that still contains activities, PostgreSQL rejects the transaction:
```
ERROR: update or delete on table "wbs_nodes" violates foreign key constraint "fk_act_wbs"
DETAIL: Key (wbs_id)=(...) is still referenced from table "activities".
```
The user must explicitly move or reassign the execution tasks before deleting the organizational container.

---

#### 2. The "Accidental Demotion" Bug in Single-Table Models
In systems where summary-ness is computed dynamically:
```sql
-- Dynamic determination in naive ORM code
is_summary := (SELECT count(*) FROM tasks WHERE parent_id = self.id) > 0;
```
Consider `WBS 03.2.1 Inverter Stations`:
1. On Friday, it contains 3 execution tasks. Because child count is 3, the application treats it as a summary container.
2. On Monday, a scheduler decides to move those 3 tasks to a different work package.
3. Once the 3 children are moved, `child_count` becomes 0.
4. The system now treats `WBS 03.2.1` as a **leaf execution task**!
5. When the CPM scheduler runs, it attempts to schedule `WBS 03.2.1`:
   * It has no assigned calendar $\to$ Engine crashes or defaults to generic calendar.
   * It has 0 planned duration $\to$ Engine turns it into a milestone.
   * It has no logic relationships $\to$ It floats to the Project Start date.

The organizational container has accidentally demoted itself into a phantom activity, corrupting the schedule.

### Solution 7: Materialized Paths with PostgreSQL `ltree` vs Recursive Adjacency Lists

#### 1. Comparison of Adjacency List vs `ltree`

| Feature | Adjacency List (`parent_wbs_id`) | Materialized Path (`ltree`) |
| :--- | :--- | :--- |
| **Query Mechanism** | `WITH RECURSIVE` CTE | GiST index on `path` using `<@` operator |
| **Query Complexity** | Multi-join iterative CTE execution | Single indexed range scan ($O(\log N)$) |
| **Execution Speed (50k rows)** | 35ms – 120ms (CPU & memory join intensive) | **0.8ms – 2.5ms (Instant index scan)** |
| **Write Cost (Move Branch)** | Updates 1 row (`parent_wbs_id = new_id`) | Updates all descendant paths (`O(k)`) |
| **Max Depth Limit** | Stack limit in PostgreSQL recursion | Up to 65,535 labels (unlimited in practice) |

For read-heavy scheduling engines where millions of rollup queries execute daily, `ltree` offers vastly superior performance.

#### 2. SQL Query to Retrieve All Descendant Activities Using `ltree`

```sql
-- Retrieve all leaf execution activities under WBS 03.1 Civil Balance of Plant
-- including any deeply nested children (e.g., 03.1.1, 03.1.2.1, etc.)
SELECT 
    a.activity_id,
    a.activity_code,
    a.activity_name,
    a.status,
    a.planned_duration_hours,
    a.early_start,
    a.early_finish,
    a.total_float_hours,
    w.wbs_code,
    w.path::text AS wbs_path
FROM activities a
JOIN wbs_nodes w ON a.wbs_id = w.wbs_id
WHERE w.path <@ (
    SELECT path 
    FROM wbs_nodes 
    WHERE project_id = 'c0a80123-0000-0000-0000-000000000001'::uuid 
      AND wbs_code = '03.1'
)
ORDER BY w.sequence_num, a.activity_code;
```

## ⚙️ Section C: Software Engineering & Go Backend

### Solution 8: High-Throughput Post-Order Tree Rollup Engine in Go

#### 1. Algorithmic Traversal Strategy: Post-Order
A tree aggregation engine must process child nodes before parent nodes. In tree theory:
* **Pre-order (Root $\to$ Children):** Fails because when the root is evaluated, child metrics have not yet been aggregated.
* **Post-order (Children $\to$ Parent):** Guarantees that when parent node $P$ is processed, all children $C_1, C_2, \dots, C_k$ have already calculated their complete dates, costs, and progress.

#### 2. $O(N \log N)$ Sorting Strategy by Path Depth Descending
By sorting WBS nodes by the number of segments in their materialized path descending (e.g., `"ROOT.03.01_2"` before `"ROOT.03"`), we guarantee strict bottom-up post-order evaluation without building complex recursive pointer graphs.

#### 3. Complete Go Production Implementation (`rollup_engine.go`)

```go
package scheduling

import (
	"errors"
	"sort"
	"strings"
	"time"
)

// WBSNodeDTO models the WBS record for rollups
type WBSNodeDTO struct {
	ID               string
	ParentWBSID      *string
	Path             string // e.g. "ROOT.03.01"
	EarlyStart       *time.Time
	EarlyFinish      *time.Time
	ActualStart      *time.Time
	ActualFinish     *time.Time
	Status           TaskStatus
	PlannedCost      float64
	ActualCost       float64
	EarnedValueCost  float64
	PhysicalPercent  float64
	DirectActivities []*Activity
}

// ExecuteWBSRollup performs a robust post-order aggregation across the WBS tree
func ExecuteWBSRollup(nodes []*WBSNodeDTO, activities []*Activity) error {
	if len(nodes) == 0 {
		return nil
	}

	// 1. Index WBS nodes and associate leaf activities
	nodeMap := make(map[string]*WBSNodeDTO, len(nodes))
	for _, n := range nodes {
		nodeMap[n.ID] = n
		n.DirectActivities = nil
		// Reset rollup accumulators
		n.EarlyStart = nil
		n.EarlyFinish = nil
		n.ActualStart = nil
		n.ActualFinish = nil
		n.PlannedCost = 0
		n.ActualCost = 0
		n.EarnedValueCost = 0
		n.PhysicalPercent = 0
		n.Status = StatusNotStarted
	}

	for _, a := range activities {
		if parent, ok := nodeMap[a.WBSID]; ok {
			parent.DirectActivities = append(parent.DirectActivities, a)
		} else {
			return errors.New("ORPHAN_ACTIVITY: activity references non-existent WBS ID: " + a.WBSID)
		}
	}

	// 2. Sort by path depth descending
	sortedNodes := make([]*WBSNodeDTO, len(nodes))
	copy(sortedNodes, nodes)
	sort.Slice(sortedNodes, func(i, j int) bool {
		depthI := strings.Count(sortedNodes[i].Path, ".")
		depthJ := strings.Count(sortedNodes[j].Path, ".")
		if depthI == depthJ {
			return len(sortedNodes[i].Path) > len(sortedNodes[j].Path)
		}
		return depthI > depthJ
	})

	// 3. Process bottom-up
	for _, node := range sortedNodes {
		hasDirect := len(node.DirectActivities) > 0
		allCompleted := hasDirect
		anyStarted := false

		// Aggregate from direct leaf activities
		for _, act := range node.DirectActivities {
			// Date rollup with nil-safety
			if act.EarlyStart != nil && (node.EarlyStart == nil || act.EarlyStart.Before(*node.EarlyStart)) {
				t := *act.EarlyStart
				node.EarlyStart = &t
			}
			if act.EarlyFinish != nil && (node.EarlyFinish == nil || act.EarlyFinish.After(*node.EarlyFinish)) {
				t := *act.EarlyFinish
				node.EarlyFinish = &t
			}
			if act.ActualStart != nil {
				anyStarted = true
				if node.ActualStart == nil || act.ActualStart.Before(*node.ActualStart) {
					t := *act.ActualStart
					node.ActualStart = &t
				}
			}
			if act.ActualFinish != nil {
				if node.ActualFinish == nil || act.ActualFinish.After(*node.ActualFinish) {
					t := *act.ActualFinish
					node.ActualFinish = &t
				}
			}

			if act.Status != StatusCompleted {
				allCompleted = false
			}
			if act.Status == StatusInProgress || act.Status == StatusCompleted {
				anyStarted = true
			}

			// Costs
			node.PlannedCost += act.PlannedCost
			node.ActualCost += act.ActualCost
			node.EarnedValueCost += act.PlannedCost * (act.PhysicalPercent / 100.0)
		}

		// Determine status
		if allCompleted && hasDirect {
			node.Status = StatusCompleted
		} else if anyStarted {
			node.Status = StatusInProgress
		} else {
			node.Status = StatusNotStarted
		}

		// Compute Earned Value Physical % Complete
		if node.PlannedCost > 0 {
			node.PhysicalPercent = (node.EarnedValueCost / node.PlannedCost) * 100.0
		}

		// Propagate to immediate parent WBS container
		if node.ParentWBSID != nil {
			if parent, exists := nodeMap[*node.ParentWBSID]; exists {
				parent.PlannedCost += node.PlannedCost
				parent.ActualCost += node.ActualCost
				parent.EarnedValueCost += node.EarnedValueCost

				if node.EarlyStart != nil && (parent.EarlyStart == nil || node.EarlyStart.Before(*parent.EarlyStart)) {
					t := *node.EarlyStart
					parent.EarlyStart = &t
				}
				if node.EarlyFinish != nil && (parent.EarlyFinish == nil || node.EarlyFinish.After(*parent.EarlyFinish)) {
					t := *node.EarlyFinish
					parent.EarlyFinish = &t
				}
				if node.ActualStart != nil && (parent.ActualStart == nil || node.ActualStart.Before(*parent.ActualStart)) {
					t := *node.ActualStart
					parent.ActualStart = &t
				}
				if node.Status == StatusInProgress || node.Status == StatusCompleted {
					parent.Status = StatusInProgress
				}
			}
		}
	}

	return nil
}
```

### Solution 9: Precedence Boundary Enforcement & Kahn's Algorithm in Go

#### 1. Specification & Algorithmic Flow
The validator takes two sets:
* $V_{wbs}$ (IDs of all WBS containers).
* $V_{act}$ (IDs of all execution activities).
* $E_{rel}$ (List of requested relationships).

It runs two verification stages:
1. **Entity Boundary Validation:** Ensure neither predecessor nor successor belongs to $V_{wbs}$.
2. **Kahn's Topological Sort:** Detect direct and multi-tier cycles in $O(|V| + |E|)$ time.

#### 2. Complete Go Implementation (`dag_validator.go`)

```go
package scheduling

import (
	"fmt"
)

type RelationshipPayload struct {
	PredecessorID string
	SuccessorID   string
	Type          string
	LagHours      float64
}

type ScheduleGraphValidator struct {
	wbsIDSet map[string]struct{}
	actIDSet map[string]struct{}
}

func NewScheduleGraphValidator(wbsIDs []string, activityIDs []string) *ScheduleGraphValidator {
	wSet := make(map[string]struct{}, len(wbsIDs))
	for _, id := range wbsIDs {
		wSet[id] = struct{}{}
	}
	aSet := make(map[string]struct{}, len(activityIDs))
	for _, id := range activityIDs {
		aSet[id] = struct{}{}
	}
	return &ScheduleGraphValidator{wbsIDSet: wSet, actIDSet: aSet}
}

// ValidateGraphEnforcement verifies WBS isolation and cycle freedom
func (v *ScheduleGraphValidator) ValidateGraphEnforcement(rels []RelationshipPayload) error {
	adjacency := make(map[string][]string)
	inDegree := make(map[string]int)

	// Initialize inDegree for all known activities
	for actID := range v.actIDSet {
		inDegree[actID] = 0
	}

	for idx, r := range rels {
		// Rule 1: No Predecessor on WBS Node
		if _, isWBS := v.wbsIDSet[r.PredecessorID]; isWBS {
			return fmt.Errorf("RULE_VIOLATION at index %d: Predecessor '%s' is a WBS Summary Node. "+
				"Relationships must link execution activities only", idx, r.PredecessorID)
		}
		// Rule 2: No Successor on WBS Node
		if _, isWBS := v.wbsIDSet[r.SuccessorID]; isWBS {
			return fmt.Errorf("RULE_VIOLATION at index %d: Successor '%s' is a WBS Summary Node. "+
				"Relationships must link execution activities only", idx, r.SuccessorID)
		}

		// Rule 3: Must exist in activity set
		if _, exists := v.actIDSet[r.PredecessorID]; !exists {
			return fmt.Errorf("NOT_FOUND at index %d: Predecessor '%s' is not a registered activity", idx, r.PredecessorID)
		}
		if _, exists := v.actIDSet[r.SuccessorID]; !exists {
			return fmt.Errorf("NOT_FOUND at index %d: Successor '%s' is not a registered activity", idx, r.SuccessorID)
		}

		// Rule 4: Disallow self-loops
		if r.PredecessorID == r.SuccessorID {
			return fmt.Errorf("CYCLE_ERROR: Self-referencing link on activity '%s'", r.PredecessorID)
		}

		adjacency[r.PredecessorID] = append(adjacency[r.PredecessorID], r.SuccessorID)
		inDegree[r.SuccessorID]++
	}

	// Rule 5: Kahn's Algorithm for Cycle Detection
	queue := make([]string, 0, len(v.actIDSet))
	for actID, deg := range inDegree {
		if deg == 0 {
			queue = append(queue, actID)
		}
	}

	visitedCount := 0
	for len(queue) > 0 {
		curr := queue[0]
		queue = queue[1:]
		visitedCount++

		for _, succ := range adjacency[curr] {
			inDegree[succ]--
			if inDegree[succ] == 0 {
				queue = append(queue, succ)
			}
		}
	}

	if visitedCount != len(v.actIDSet) {
		return fmt.Errorf("DEADLOCK_DETECTED: Network contains circular dependencies. Visited %d of %d activities",
			visitedCount, len(v.actIDSet))
	}

	return nil
}
```

#### 3. Complexity Analysis
* **Time Complexity:** $O(|V_{act}| + |E_{logic}|)$. Initializing in-degrees takes $O(|V|)$, edge accumulation takes $O(|E|)$, and queue processing touches each vertex and edge exactly once.
* **Space Complexity:** $O(|V_{act}| + |E_{logic}|)$ to store the adjacency lists and in-degree maps in memory.

#### 2. Go Progressive Elaboration Budget Validation

```go
package scheduling

import (
	"fmt"
)

// ValidateProgressiveElaboration ensures child elaboration stays within approved container budget
func ValidateProgressiveElaboration(
	wbsID string,
	baselineBudget float64,
	elaboratedActivities []*Activity,
) error {
	var totalElaboratedCost float64
	for _, act := range elaboratedActivities {
		if act.WBSID != wbsID {
			continue
		}
		if act.PlannedCost < 0 {
			return fmt.Errorf("INVALID_COST: Activity '%s' cannot have negative planned cost", act.ActivityCode)
		}
		totalElaboratedCost += act.PlannedCost
	}

	// Enforce 100% Scope Budget Reconciliation
	if totalElaboratedCost > baselineBudget {
		variance := totalElaboratedCost - baselineBudget
		return fmt.Errorf("BUDGET_OVERRUN: Elaborated activities sum to $%.2f, exceeding baseline budget of $%.2f by $%.2f",
			totalElaboratedCost, baselineBudget, variance)
	}

	return nil
}
```

### Solution 11: Tree Flattening for Virtualized Gantt Rendering

#### 1. Tree Flattening Strategy
In enterprise PPM web clients, rendering 15,000 nested DOM nodes degrades performance. 
The flattening hook performs a Depth-First Search (DFS) traversal over the WBS tree. If a parent WBS node's ID is in the `expandedNodeIds` set, the traversal emits its direct activities and recurses into its child WBS nodes.

#### 2. `expandedNodeIds: Set<string>` State Management
Storing expanded IDs in an immutable `Set<string>` guarantees $O(1)$ lookup time:
```typescript
const [expandedNodeIds, setExpandedNodeIds] = useState<Set<string>>(new Set(['ROOT', '03']));

const toggleExpand = (wbsId: string) => {
  setExpandedNodeIds(prev => {
    const next = new Set(prev);
    if (next.has(wbsId)) {
      next.delete(wbsId);
    } else {
      next.add(wbsId);
    }
    return next;
  });
};
```
When a node collapses, all its descendants disappear from the resulting array in a single render pass without layout thrashing.

#### 3. Dynamic Row Heights in `@tanstack/react-virtual`
In Gantt charts, summary rows are visually more compact than execution bars. `@tanstack/react-virtual` natively supports dynamic sizing via its `estimateSize` callback:
