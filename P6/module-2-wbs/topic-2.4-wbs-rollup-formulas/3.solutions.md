### Solution 1: The Non-Continuous Spanned Duration Paradox

#### 1. Direct Mathematical Sum of Durations
$$\sum_{i=1}^3 D_i = D_{101} + D_{102} + D_{103} = 6 + 8 + 4 = \mathbf{18\text{ working days}}$$

#### 2. Rolled-Up Early Start ($ES$) and Early Finish ($EF$)
Under Primavera P6 set aggregation rules:
$$ES(\text{WBS 1.3}) = \min(ES_{101}, ES_{102}, ES_{103}) = \min(\text{05-Jan-2026}, \text{19-Jan-2026}, \text{09-Feb-2026}) = \mathbf{\text{Mon 05-Jan-2026}}$$
$$EF(\text{WBS 1.3}) = \max(EF_{101}, EF_{102}, EF_{103}) = \max(\text{10-Jan-2026}, \text{27-Jan-2026}, \text{12-Feb-2026}) = \mathbf{\text{Thu 12-Feb-2026}}$$

#### 3. Spanned Calendar Days
The total spanned calendar duration is the inclusive elapsed calendar days between $ES$ and $EF$:
* January 05 to January 31 = $31 - 5 + 1 = 27\text{ days}$.
* February 01 to February 12 = $12\text{ days}$.
$$\text{Spanned Calendar Days} = 27 + 12 = \mathbf{39\text{ calendar days}}$$

#### 4. Effective Working Duration (6-Day Rajasthan Site Calendar)
In a 6-day work week (Monday–Saturday working, Sunday non-working):
* Total calendar days in window: 39 days.
* Number of Sundays between 05-Jan-2026 and 12-Feb-2026:
  * 11-Jan-2026 (Sunday)
  * 18-Jan-2026 (Sunday)
  * 25-Jan-2026 (Sunday)
  * 01-Feb-2026 (Sunday)
  * 08-Feb-2026 (Sunday)
  * Total Sundays = 5 days.
$$\text{Effective Working Duration} = 39 - 5 = \mathbf{34\text{ working days}}$$

#### 5. Why Scheduling Engines Must Never Display $\sum D_i$ for WBS Nodes
$$\text{Effective Working Duration (34 days)} \neq \sum D_i\ (18\text{ days})$$

```
Timeline: Jan 05 ────── Jan 10        Jan 19 ───────── Jan 27        Feb 09 ──── Feb 12
Work:     [=== Act 101 ===]           [=== Act 102 ===]              [=== Act 103 ===]
Idle:                      [─────────]                 [────────────]
                           Gap 1: 7 days               Gap 2: 12 days
Summary:  [==========================================================================]
          Spanned Window: 39 Calendar Days (34 Working Days)
          Actual Physical Labor: Only 18 Days
```

* **The Mathematical Reality:** WBS elements represent **temporal envelopes**, not physical activities. The time between 05-Jan and 12-Feb contains **16 non-working or unallocated working days** (gaps where no work is scheduled under this WBS).
* **Operational & Resource False Assumptions:**
  1. **Phantom Resource Allocation:** If an executive divides total budgeted labor (e.g., ₹18 Lakhs) by the spanned duration (34 days), the calculated daily burn rate appears as ₹52,941/day. In reality, during active work days, the burn rate is ₹100,000/day ($18\text{ Lakh} / 18\text{ days}$), while during gap periods it is ₹0/day.
  2. **False Equipment Utilization:** Heavy machinery (such as concrete boom pumps or cranes) scheduled across the summary window would be billed or reserved for 34 days instead of the 18 days actually needed, leading to massive mobilization cost overruns.

### Solution 3: Mathematical Proof of Weighting Skew (Duration vs Cost)

#### 1. Duration-Weighted Progress
$$\%_{\text{Duration}} = \frac{(5 \times 0.0) + (95 \times 0.80)}{5 + 95} = \frac{0 + 76}{100} = \mathbf{76.0\%}$$

#### 2. Cost-Weighted Progress (Earned Value Rollup)
* $BAC_A = ₹18,00,00,000$ (₹18 Crore)
* $BAC_B = ₹2,00,000$ (₹2 Lakh)
* Total $BAC = ₹18,00,00,000 + ₹2,00,000 = ₹18,02,00,000$
* $EV_A = ₹18,00,00,000 \times 0.0 = ₹0$
* $EV_B = ₹2,00,000 \times 0.80 = ₹1,60,000$
$$\%_{\text{Cost}} = \frac{EV_A + EV_B}{BAC_{\text{Total}}} = \frac{₹1,60,000}{₹18,02,00,000} \approx \mathbf{0.008879\% \ (0.0089\%)}$$

#### 3. Algebraic Proof of Equivalence Condition
Let $p_i \in [0, 1]$ be the progress percentage of activity $i$, $D_i > 0$ be the planned duration, and $C_i > 0$ be the baseline cost ($BAC$).

$$\%_{\text{Duration}} = \frac{\sum_{i=1}^n D_i p_i}{\sum_{i=1}^n D_i}, \quad \%_{\text{Cost}} = \frac{\sum_{i=1}^n C_i p_i}{\sum_{i=1}^n C_i}$$

Equating the two expressions for all possible progress vectors $\vec{p} = (p_1, \dots, p_n)$:
$$\sum_{i=1}^n \left( \frac{D_i}{\sum_{k=1}^n D_k} \right) p_i = \sum_{i=1}^n \left( \frac{C_i}{\sum_{k=1}^n C_k} \right) p_i$$

For this linear identity to hold universally for any arbitrary progress vector $\vec{p} \in [0, 1]^n$, the coefficients of each $p_i$ must be identically equal:
$$\frac{D_i}{\sum_{k=1}^n D_k} = \frac{C_i}{\sum_{k=1}^n C_k} \quad \forall i \in \{1, \dots, n\}$$

Dividing by $D_i$ and multiplying by $\sum C_k$:
$$\frac{C_i}{D_i} = \frac{\sum_{k=1}^n C_k}{\sum_{k=1}^n D_k} = \kappa \quad (\text{constant})$$

**Conclusion:** 
$$\%_{\text{Duration}} \equiv \%_{\text{Cost}} \iff \frac{C_i}{D_i} = \kappa \quad \forall i$$
Duration weighting equals Cost weighting **if and only if every single activity in the work package possesses the exact same daily burn rate (cost per day)**.

#### 4. Duration Skew Factor and Contractual Rejection
$$\Delta = |\%_{\text{Duration}} - \%_{\text{Cost}}| = |76.0\% - 0.0089\%| = \mathbf{75.9911\%}$$

* **Why EPC Contracts Prohibit Duration Weighting:**
  A contractor billing against duration-weighted progress would invoice the owner for $76\%$ of the ₹18.02 Crore package—demanding payment of **₹13.7 Crore**—while delivering only ₹1.6 Lakhs of physical work. 
  Contractors could intentionally inflate durations on passive, low-cost activities (permits, curing, monitoring) to front-load cash flow, creating massive unearned financial liabilities for project owners.

### Solution 4: Procurement Inflation Distortion & Labor-Units Rollup

* Project Baseline $BAC = ₹450\text{ Crore}$.
* Earned Value:

  * Civil Piling: $EV_2 = ₹60\text{ Crore} \times 0.05 = ₹3\text{ Crore}$.
  * Total $EV = 240 + 3 = ₹243\text{ Crore}$.
$$\%_{\text{Cost}} = \frac{₹243\text{ Crore}}{₹450\text{ Crore}} = \mathbf{54.00\%}$$

#### 2. Overall Project Labor-Units Percent Complete ($\%_{\text{Labor}}$)
* Budgeted Labor Hours:
  * Module Supply: $1,000\text{ hours}$.
  * Civil Piling: $150,000\text{ hours}$.
  * Total Budgeted Labor = $1,000 + 150,000 = 151,000\text{ hours}$.
* Earned Labor Hours:
  * Module Supply: $1,000 \times 1.00 = 1,000\text{ hours}$.
  * Civil Piling: $150,000 \times 0.05 = 7,500\text{ hours}$.
  * Total Earned Labor = $1,000 + 7,500 = 8,500\text{ hours}$.
$$\%_{\text{Labor}} = \frac{8,500\text{ hours}}{151,000\text{ hours}} \approx \mathbf{5.629\% \ (5.63\%)}$$

#### 3. Material Risk Hidden from Bank Lenders
* **The Illusion:** The developer reports $54\%$ progress, claiming that more than half the solar plant is built, and draws down $54\%$ of the ₹350 Crore project debt facility.
* **The Site Reality:** Only $5.6\%$ of the physical field erection has been executed. The solar panels are sitting in cardboard boxes in the desert heat, vulnerable to dust, thermal degradation, and warranty expiration, while the civil contractor has encountered impenetrable bedrock. 
* If the civil contractor goes bankrupt or the piling delays extend past the monsoon, the lender has disbursed $54\%$ of the capital with almost zero operational infrastructure deployed in the field.

#### 4. Primavera P6 Percent Complete Type Configuration
Primavera P6 provides three options for the **Percent Complete Type** on each activity:
1. **Duration % Complete:** Driven strictly by remaining duration: $\% = \frac{OD - RD}{OD}$.
2. **Units % Complete:** Driven strictly by resource units consumed vs remaining: $\% = \frac{\text{Actual Units}}{\text{Actual Units} + \text{Remaining Units}}$.
3. **Physical % Complete:** Set manually by field engineers based on physical deliverables (e.g., piles driven, meters of cable pulled), independent of time or labor hours.

To eliminate procurement distortion, enterprise schedulers configure:
* Procurement activities as **Physical % Complete** tied to strict material inspection gates.
* Construction activities as **Units % Complete** (labor-weighted).
* Project dashboards report **Labor Units Rollup** alongside Cost Rollup so executive committees can track sweat-equity productivity vs cash flow.

### Solution 5: The Float Fallacy — Mathematical Counterexample

#### 1. Compute $EF_{\text{WBS}}$ and $LF_{\text{WBS}}$
* Activity 1: $ES_1 = 0, EF_1 = 15, LS_1 = 0, LF_1 = 15 \implies TF_1 = 15 - 15 = 0$.
* Activity 2: $ES_2 = 20, EF_2 = 35, LS_2 = 35, LF_2 = 50 \implies TF_2 = 50 - 35 = 15$.

Under WBS date rollup rules:
$$EF_{\text{WBS}} = \max(EF_1, EF_2) = \max(15, 35) = \mathbf{35}$$
$$LF_{\text{WBS}} = \max(LF_1, LF_2) = \max(15, 50) = \mathbf{50}$$

#### 2. Evaluate Naive Float Formula
$$TF_{\text{naive}} = LF_{\text{WBS}} - EF_{\text{WBS}} = 50 - 35 = \mathbf{15\text{ days}}$$

#### 3. Evaluate True P6 Rollup Formula
$$TF_{\text{P6}} = \min(TF_1, TF_2) = \min(0, 15) = \mathbf{0\text{ days}}$$

#### 4. Why the Naive Formula Fails & The Mathematical Equivalence Condition
* **The Failure:** $TF_{\text{naive}} = 15$ masks the zero-float critical path activity (Activity 1). If Activity 1 delays by 5 days, the overall project finish date slips by 5 days, yet the naive WBS float calculation claimed there were 15 days of buffer!
* **General Condition for Equivalence:**
  $$LF_{\text{WBS}} - EF_{\text{WBS}} == \min_{i} (LF_i - EF_i)$$
  Let $k$ be the activity that determines the WBS Early Finish ($EF_k = \max_i EF_i$), and let $m$ be the activity that determines the WBS Late Finish ($LF_m = \max_i LF_i$).
  Then:
  $$LF_{\text{WBS}} - EF_{\text{WBS}} = LF_m - EF_k$$
  For this to equal $\min_i (LF_i - EF_i)$:
  1. Activity $k$ and Activity $m$ must be the **exact same activity** ($k = m$). That is, the activity with the latest Early Finish must also have the latest Late Finish.
  2. That single activity must also have the **minimum total float** across all activities in the work package.
  In real-world networks with parallel paths and varying floats, this condition is almost never satisfied.

### Solution 6: Empty WBS Node Invariant & Null-Safety Contract

#### 1. Algebraic Properties of the Empty Set $\emptyset$
* $ES(\emptyset) = \min(\emptyset) = +\infty \implies \mathbf{\text{NULL}}$
* $EF(\emptyset) = \max(\emptyset) = -\infty \implies \mathbf{\text{NULL}}$
* $BAC(\emptyset) = \sum_{a \in \emptyset} BAC(a) = \mathbf{0.0}$
* $TF(\emptyset) = \min(\emptyset) = +\infty \implies \mathbf{\text{NULL}}$ (or undefined)
* $\%(\emptyset) = \frac{0}{0} \implies \mathbf{0.0}$ (by convention, empty scope has $0\%$ progress)

#### 2. Aggregation Operator $f(B, C)$
Given $B$ is empty and $C$ is populated:
$$ES(A) = \min(\{ ES(c) \mid c \in \{B, C\}, ES(c) \neq \text{NULL} \}) = ES(C) = \mathbf{\text{2026-03-01}}$$
$$EF(A) = \max(\{ EF(c) \mid c \in \{B, C\}, EF(c) \neq \text{NULL} \}) = EF(C) = \mathbf{\text{2026-04-15}}$$
$$BAC(A) = BAC(B) + BAC(C) = 0 + ₹5\text{ Cr} = \mathbf{₹5\text{ Crore}}$$
$$TF(A) = \min(\{ TF(c) \mid c \in \{B, C\}, TF(c) \neq \text{NULL} \}) = TF(C) = \mathbf{+10\text{ days}}$$

* $AS = \text{10-Jan-2026} \implies x_{\text{start}} = X(AS)$
* $DD = \text{31-Jan-2026} \implies x_{\text{dd}} = X(DD)$
* $EF = \text{28-Feb-2026} \implies x_{\text{finish}} = X(EF)$

The summary bar is vectorized into two contiguous SVG `<rect>` elements:
1. **Segment 1 (Historical Actuals / Completed Work):**
   * $\text{Start } x = x_{\text{start}}$
   * $\text{Width } w_1 = x_{\text{dd}} - x_{\text{start}}$

3. **Progress Fill Indicator:**
   A solid inner progress stripe of width $w_{\text{prog}} = (x_{\text{finish}} - x_{\text{start}}) \times (\%_{\text{Prog}} / 100)$.

   x_start (10-Jan)               x_dd (31-Jan)                      x_finish (28-Feb)
          │                              │                                  │
          ▼                              ▼                                  ▼
          ┌──────────────────────────────┬──────────────────────────────────┐

#### 2. Handling Out-of-Sequence Actual Dates Past the Data Date
If an activity records an actual start or actual finish past the Data Date:
* The CPM engine flags an **Out-of-Sequence (OOS) violation**.
* In P6, depending on calculation options:
  * **Retained Logic:** Remaining duration cannot start until predecessors finish; remaining work is pushed past $DD$.
  * **Progress Override:** Remaining duration starts immediately at $DD$.
* In summary bar vectorization: The engine clamps the actual segment to $\min(DD, \text{Max Child Actual})$ and renders a distinct warning icon or amber hatching across the invalid temporal span.

### Solution 8: Time and Space Complexity Analysis: Post-Order vs Recursive CTE

#### 1. In-Memory Iterative Post-Order Traversal (Golang)
* **Time Complexity: $O(N + M)$**
  * Building the two stacks visits each of the $M$ WBS nodes exactly twice ($O(M)$).
  * In the reverse loop, every WBS node processes its direct child nodes ($k$) and its direct leaf activities ($L_m$).
  * Since each activity belongs to exactly one direct parent WBS node:
    $$\sum_{m=1}^M (\text{len}(\text{ChildNodes}_m) + \text{len}(\text{Activities}_m)) = (M - 1) + N$$
  * Thus, total operations $= O(N + M) \approx \mathbf{O(N)}$.
* **Space Complexity: $O(M)$**
  * Two slice stacks storing pointers to $M$ nodes. Peak auxiliary memory for 2,400 activities and 200 WBS nodes is less than $50\text{ KB}$.

#### 2. PostgreSQL Recursive CTE
* **Join Complexity & Memory:**
  * The recursive CTE constructs paths using `ARRAY[id] || child.id`.
  * The self-join `ancestor.id = ANY(descendant.path)` executes an $O(M^2)$ ancestor-descendant Cartesian product closure.
  * Grouping and aggregating activities across the closure table requires hashing/sorting $M \times N_{\text{descendant}}$ row combinations.
  * For $N = 10,000$ activities and $M = 1,000$ nodes, the query generates intermediate working sets of $500,000+$ rows in Postgres memory (`work_mem`).
* **Concurrent Execution:**
  When 100 users execute this query concurrently, PostgreSQL allocates $100 \times \text{work\_mem}$ (often hundreds of megabytes), saturating CPU cores with hash joins and disk spills (`temp_files`).

#### 3. Scale Breakdown Threshold
* **Threshold:** Approach 2 breaks down at **$N \ge 5,000$ activities** under concurrent load ($> 10$ concurrent readers), resulting in query latencies spiking from $50\text{ ms}$ to $> 2,500\text{ ms}$.
* In contrast, Golang in-memory post-order traversal executes across $100,000$ activities in **$< 4\text{ ms}$**.

### Solution 9: Incremental Ancestor Walk vs Delta Invalidation

#### 1. Why Incremental Walk is Superior
In an $N = 10,000$ project with tree depth $h = 5$ and average child branching factor $k = 8$:
* A full project rollup recalculates all 10,000 activities and all 1,250 WBS nodes ($O(N)$ operations).
* An incremental ancestor walk visits **only 5 nodes** ($h = 5$). At each node, it evaluates only its direct children ($k = 8$ children).
* Total operations $= 5 \times 8 = 40\text{ operations}$ vs $11,250\text{ operations}$.
$$\text{Speedup Factor} = \frac{11,250}{40} \approx \mathbf{281\times\text{ faster}}$$

#### 2. Why Linear Metrics Support Delta Updates, but Min/Max Do Not
Let $W$ have children $\{c_1, c_2, \dots, c_k\}$.
* **Linear Metric ($EV$):**
  $$EV_{\text{new}}(W) = \sum_{i=1}^k EV(c_i) = EV_{\text{old}}(W) + (EV_{\text{new}}(c_1) - EV_{\text{old}}(c_1)) = EV_{\text{old}}(W) + \Delta EV$$
  A single subtraction and addition updates the parent without inspecting siblings $c_2, \dots, c_k$.
* **Extrema Metric ($ES = \min(ES_i)$):**
  Suppose $ES(W) = \min(10, 15, 20) = 10$ (driven by $c_1$).
  If $c_1$ delays so that $ES_{\text{new}}(c_1) = 25$:
  $$\min(\{10, 15, 20\} \setminus \{10\} \cup \{25\}) = \min(25, 15, 20) = 15$$
  The minimum value changed from $10$ to $15$. **There is no mathematical operator $\Delta$ that can deduce the number 15 without inspecting the remaining sibling values.** 
  Hence, delta updates for dates and float are impossible without maintaining priority queues or re-scanning direct children.

#### 3. Early-Exit Optimization Condition in Golang
An ancestor walk can safely terminate before reaching the root if:
1. The newly computed $ES, EF, LS, LF$ match the node's prior dates:
   $$ES_{\text{new}} == ES_{\text{old}} \quad \text{and} \quad EF_{\text{new}} == EF_{\text{old}}$$
2. The newly computed $TotalFloat$ matches the node's prior float:
   $$TF_{\text{new}} == TF_{\text{old}}$$
3. The newly computed $EarnedValue$ matches the prior $EV$ (or the change is below floating-point epsilon):
   $$|EV_{\text{new}} - EV_{\text{old}}| < 10^{-6}$$

If all three conditions are satisfied, none of the inputs to the parent node have altered. The engine executes `return` immediately, saving upstream traversal steps.

### Solution 10: Concurrency Control & Hierarchical Deadlock Prevention

#### 1. Deadlock Sequence Diagram (Unordered / Top-Down vs Bottom-Up Locking)

```
Engineer A (Act 101 -> Node 1.1.1)               Engineer B (Act 102 -> Node 1.1.2)
──────────────────────────────────               ──────────────────────────────────
1. Acquires Lock(Node 1.1.1)                     1. Acquires Lock(Node 1.1.2)
2. Traverses up: Requests Lock(Node 1.1)         2. Traverses up: Requests Lock(Node 1.1)
   [Node 1.1 is LOCKED by A]                        [Node 1.1 is contested]
   
IF A holds Node 1.1 and attempts to read         IF B holds Node 1.1 and attempts to read
down into 1.1.2 while B holds 1.1.2:              down into 1.1.1 while A holds 1.1.1:
   Wait for Node 1.1.2... (Held by B)                Wait for Node 1.1.1... (Held by A)
   
                     ★ CIRCULAR DEADLOCK DETECTED! ★
```

#### 2. The Hierarchical Lock Ordering Rule
To guarantee deadlock freedom without a global lock:
1. **Never hold locks during upward navigation.** 
2. When aggregating a node $W$:
   * Acquire write lock on $W$: `W.mu.Lock()`.
   * For each direct child $c$: acquire read lock `c.mu.RLock()`, copy values, release `c.mu.RUnlock()`.
   * Release write lock on $W$: `W.mu.Unlock()`.
   * Move to parent $P = W.\text{Parent}$.
3. Because locks are **never held simultaneously across levels**, the resource allocation graph has no cycles, making deadlocks mathematically impossible.

#### 3. Fine-Grained Node Mutexes vs Single-Project RWMutex
* **Fine-Grained Node Mutexes:**
  * **Pros:** Extremely high write throughput. Updates to unrelated branches (`WBS 1.0 Civil` vs `WBS 2.0 Electrical`) run fully parallel across CPU cores without contention.
  * **Cons:** Memory overhead of maintaining mutexes on every node; requires strict discipline to prevent lock leaks.
* **Single-Project RWMutex (`project.mu.Lock()`):**
  * **Pros:** Simple to reason about; zero risk of deadlocks.
  * **Cons:** Complete serialization of all edits. When 50 site engineers submit daily progress, write requests queue up, creating latency spikes on HTTP APIs.
* **Architecture Recommendation:** Use fine-grained mutexes with fine-scoped locking inside the ancestor walk.

## 🏗️ Section C: Database Architecture & System Design

### Solution 11: Database Persistence Tradeoffs: Triggers vs Application Rollup

#### 1. Failure Modes of Proposal A (Database Triggers) During F9 Schedule
When a project scheduler runs CPM Schedule on a 15,000-activity network:
1. **15,000 Cascading Trigger Invocations:** Every activity row update fires an `AFTER UPDATE` trigger that issues recursive queries to update its parent, grandparent, and root WBS nodes.
2. **Lock Thrashing on Root Node:** The Project Root WBS row is updated **15,000 consecutive times within the same database transaction**. Concurrent transactions attempting to read or update the project experience immediate row-lock contention (`ShareLock` / `ExclusiveLock`), causing transaction timeouts.
3. **Write-Ahead Log (WAL) Explosion:** 15,000 updates to the root row generate 15,000 dead row versions (MVCC churn), causing table bloat and overwhelming PostgreSQL autovacuum.

#### 2. Why Working Calendars Make PL/pgSQL Unmaintainable
Computing the effective duration of a WBS summary node requires calendar logic:
* 6-day site calendar with Rajasthani gazetted holidays, Diwali shutdowns, and monsoon weather moratoriums.
* Implementing calendar arithmetic in PL/pgSQL requires multi-table joins against a `calendar_exceptions` table for every date difference calculation.
* This is slow in SQL and difficult to unit test compared to compiled Go routines.

#### 3. Production PostgreSQL Batch Update Query (Under 10ms for 500 Nodes)
Under Proposal B, the Go engine calculates all 500 WBS nodes in memory and pushes them in a single batch query using PostgreSQL `UNNEST()`:

```sql
-- High-Performance Batch Update of WBS Summary Nodes via UNNEST()
UPDATE wbs_nodes AS w
SET 
    early_start            = data.early_start,
    early_finish           = data.early_finish,
    late_start             = data.late_start,
    late_finish            = data.late_finish,
    actual_start           = data.actual_start,
    actual_finish          = data.actual_finish,
    bac                    = data.bac,
    earned_value           = data.earned_value,
    cost_percent_complete  = data.cost_percent_complete,
    total_float            = data.total_float,
    is_critical            = data.is_critical,
    updated_at             = NOW()
FROM (
    SELECT 
        UNNEST($1::uuid[])        AS id,
        UNNEST($2::timestamptz[]) AS early_start,
        UNNEST($3::timestamptz[]) AS early_finish,
        UNNEST($4::timestamptz[]) AS late_start,
        UNNEST($5::timestamptz[]) AS late_finish,
        UNNEST($6::timestamptz[]) AS actual_start,
        UNNEST($7::timestamptz[]) AS actual_finish,
        UNNEST($8::numeric[])     AS bac,
        UNNEST($9::numeric[])     AS earned_value,
        UNNEST($10::numeric[])    AS cost_percent_complete,
        UNNEST($11::numeric[])    AS total_float,
        UNNEST($12::boolean[])    AS is_critical
) AS data
WHERE w.id = data.id;
```

#### 3. Next.js / TanStack Query Granular Cache Patching
To prevent re-rendering the entire 2,000-row Gantt chart:
1. **Normalized Cache:** In TanStack Query (`@tanstack/react-query`), store the WBS and activity data as a normalized map indexed by `id`: `Record<string, WBSNode>`.
2. **WebSocket Listener Hook:**
   ```typescript
   // hooks/useGanttSync.ts
   import { useQueryClient } from '@tanstack/react-query';
   import { useEffect } from 'react';

   export function useGanttSync(projectId: string) {
     const queryClient = useQueryClient();

     useEffect(() => {
       const ws = new WebSocket(`wss://api.solar-ppm.com/ws/${projectId}`);

       ws.onmessage = (event) => {
         const message = JSON.parse(event.data);
         if (message.event === 'WBS_ROLLUP_UPDATED') {
           // Granularly patch cache without triggering full tree refetch
           queryClient.setQueryData(['project-wbs', projectId], (oldData: any) => {
             if (!oldData) return oldData;
             const updatedMap = { ...oldData.nodesById };
             message.updatedNodes.forEach((node: any) => {
               updatedMap[node.id] = { ...updatedMap[node.id], ...node };
             });
             return { ...oldData, nodesById: updatedMap };
           });
         }
       };

       return () => ws.close();
     }, [projectId, queryClient]);
   }
   ```
3. **Virtualized Row Rendering with `React.memo`:**
   Each row in the virtualized Gantt list (using `@tanstack/react-virtual`) is wrapped in `React.memo` with a custom comparison function:
   ```typescript
   export const GanttWBSRow = React.memo(
     ({ node }: { node: WBSNode }) => {
       return (
         <div className="gantt-row">
           <WBSSummaryBar {...node} />
         </div>
       );
     },
     (prev, next) => {
       // Only re-render if visual rollup metrics changed
       return (
         prev.node.costPercent === next.node.costPercent &&
         prev.node.earlyFinish === next.node.earlyFinish &&
         prev.node.totalFloat === next.node.totalFloat &&
         prev.node.isCritical === next.node.isCritical
       );
     }
   );
   ```
4. **Performance Result:** When an activity updates, only the **3 affected ancestor rows** re-render on the DOM in under **16 milliseconds (60 FPS smooth animation)**, delivering an instantaneous desktop-class user experience in the browser.
